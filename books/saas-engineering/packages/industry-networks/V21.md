# V21 · 约束计划怎样走到交付与运费支付

供应网络把企业的交付承诺分给供应商、仓库和承运商。计划员回答“按现有约束能怎样交付”，采购批准人回答“企业是否愿意承担这项采购义务”，收货人回答“实际收到多少”，财务回答“哪些运输服务已有付款依据”。这些判断依赖彼此，却不能彼此代签。一个最优计划可能没有获得批准，一辆已签约的车可能尚未到场，一份签收记录也可能不支持发票上的全部附加费。

本例延续包内的“承诺—资源—执行证据—结算”模型，构造一家分销商的两日运输任务。所有数量、费用、状态、审批门槛和技术实现都是 **synthetic 教学设计**，不代表 SAP、GS1 或某家承运商的实际部署。SAP IBP 的公开介绍把需求、供应、库存与 S&OP 放在共同计划范围，并说明 response and supply planning 考虑容量、提前期和库存；这只支持计划问题的边界，不证明下文的整数模型或审批流程是 SAP 的实现。[SAP IBP，What is SAP IBP / Which modules are part of SAP IBP](https://www.sap.com/products/scm/integrated-business-planning.html)。

## 识题：不可拆分配与执行承诺

先辨认眼前卡住的关系，再选择解法。以下线索对应后文的演算与变式。

| 识别线索 | 先选的方法 | 接着查什么 |
|---|---|---|
| 总容量够，却总有一单装不上车 | 先写不可拆与每天容量约束，再比较可行解的成本 | 计划器的约束、求解状态、时限及可行性检查 |
| 计划获批，但货还没有进入仓库 | 把未来供给份额与实物预留分开 | 采购确认、分批收货、库存预留与发运接口 |
| 运输已交付，发票仍有不能支付的行 | 逐行匹配费率、运输和有效履约证据 | 运费附加费授权、签收更正与付款回查 |

## 解法：计划、承诺和实物分别记账

计划输入必须先固定版本。需求 A、B、C 共 16 托盘；仓库已有 4 托盘，计划拟向供应商采购 12 托盘，要求运输开始前到货，采购批准尚未完成。情景版本 P7 把这 12 托盘作为有条件供给，页面应显示这个条件，而不能把“可采购”涂成“已在库”。采购批准仅使采购单可发出，供应商确认才支持预计到货，仓库点收才增加可用库存。P7 获批时锁定这份有条件供给的分配份额，避免另一个计划重复承诺同一份未来供给；这与实物库存预留是两项记录。SC1 实收后，仓库才可按当前库存版本预留 16 托盘供两趟运输使用。本例要求出车时已有对应物理预留；真实业务若允许在途转运，需要增加交接与货权规则，不能直接删除这道检查。

| 对象与身份 | 权威与独立状态 | 转换所需证据 |
|---|---|---|
| Plan P7，含输入快照与规则版本 | 计划服务；draft → feasible → approved → superseded | feasible 要通过容量、时间与物料约束；approved 还要有批准人和所批准的版本 |
| Supply commitment SC1 | 采购服务记录本地义务，供应商回执证明其接受；proposed → approved → acknowledged → received，另有 rejected | 采购批准不等于供应商承诺；received 需要实际接收的数量，部分收货保留余额 |
| Physical reservation IR1 | 仓储服务；waiting → reserved → consumed / released | waiting 可关联未来供给，但只有实收后的可用量能转成 reserved；按运输分批消耗 |
| Shipment S1 / S2 | 运输服务；planned → tendered → accepted → dispatched → delivered，另有 exception / cancelled | accepted 是承运商接单；delivered 要核对收货方、货物身份与数量 |
| Delivery evidence E1 / E2 | 证据服务保留来源与修订；reported → verified / disputed → corrected | 承运商报告可作为线索，争议签收不直接作为结算依据 |
| Freight invoice FI1 与付款尝试 PAY1 | 应付服务核对应付，支付系统确认结算；received → matched / disputed → approved → payment_pending → paid | 每个收费行需匹配运输、费率与履约证据；超时属于付款尝试的 unknown，不把发票改成 paid |

计划员可以修改候选分配，不能确认供方已经接受；采购批准人可以批准限额内的供给，不能自报收货；仓库与收货方可以报告数量，不能改运输费率；财务可以批准匹配的收费行，不能删除不利的交付证据。跨组织共享也按关系授权：承运商只能读自己的 shipment，收货方只能提交指向获授权订单的接收记录，不能因为消息中出现了一个 tenant ID 就相信其归属。

数量守恒比单一“完成”标签更能暴露欠交。每条订单在同一计量单位下满足“已交付 + 在途 + 未发 + 已取消 = 已订购”，同一托盘不能同时计入两辆车。计划层预测的 16 托盘与仓库实有的 16 托盘还需分别核对；预测表的求和正确不能补出缺少的货。

## 演算：先求可行，再比较代价

三个订单不可拆分，A 占 6 托盘，B、C 各占 5 托盘。D1、D2 每天各有一辆容量 10 托盘的车，每辆费用 100 记账单位；所有订单均希望 D1 到达，本例把 D2 到达视为迟一天。迟交的内部评估成本按托盘每天计算：A 为 9，B、C 为 7。它是计划目标中的 synthetic 权重，既不是客户赔偿条款，也不是可直接扣减的运费。

设 `x(i,d)` 表示订单 i 是否安排到 d 日，每个值只能为 0 或 1。每个订单必须满足 `x(i,1)+x(i,2)=1`；每天满足 `6x(A,d)+5x(B,d)+5x(C,d)≤10`。目标为两辆车的 200，加上 D2 订单的迟交成本。两日各运输一次、全部订单在 D2 前完成，是这个小模型的边界；模型尚未包括真实道路、装卸时长、多站顺序、温区和司机工时。

逐项列举三个订单的 8 种日期组合，只剩两种可行方案。A 在 D1、B+C 在 D2，负载为 6、10，成本为 `200+5×7+5×7=270`。B+C 在 D1、A 在 D2，负载为 10、6，成本为 `200+6×9=254`。后一方案在这个完整枚举的小问题中最优。按每托盘迟交成本从高到低选 A，看起来先保住了最重要的订单，却把另两单合计 70 的代价留下；按销售额最大优先也不能修复这个容量组合问题。

这属于 `ALG:optimization` 与 `ALG:scheduling`：依赖决定供货未到时哪趟运输不能开始，容量决定同时放哪些订单，目标决定可行解中选哪一个。对 n 单、D 个可选日期直接枚举有 D 的 n 次方种分配。稍大问题可把合成整数模型交给 OR-Tools CP-SAT，保存求解输入、时限、可行性检查和求解状态；限时只得到可行解时显示“当前可行方案”，没有证明最优就不写“最低成本”。先按截止日排序再装车是容易解释的启发式，但上述反例说明局部优先级会漏掉组合收益。

物料约束和运输约束必须一起检查。若批准人把供货从 12 改为 8，则预计总供给只有 12，装车模型即使仍算出 254，也已不再代表可执行的全链计划。正确结果是标明 P7 的输入已失效，重新选择延期、补充供给或客户同意取消的订单；不能在无货时继续发出全部运输任务。计划审批检查供给份额与版本，实际收货后的物理预留事务另查当前库存与剩余量；两道检查分别防止超额承诺未来供给和抢用已在库货物。

## 从情景预览到运输确认

React 配合 TypeScript 可实现需求表、容量条和方案比较：每次拖动订单立即计算本地预览，同时保留“未批准”的明显标识；Vue 也适用，关键取舍是团队维护成本与现有组件，而不是框架决定业务正确性。键盘移动必须与拖动等价，容量超限要给出“D1 超出 1 托盘”的文字，不能只变红。方案详情同时列出预计交付、采购条件和成本分解，不能用目标总分隐藏欠交对象。

点击“批准计划”时，UI 发送 tenant、plan ID、P7 版本、输入摘要与 operation ID。FastAPI 适合把 Python 求解任务接到已有团队；若以 Java 业务系统为主，Spring Boot 可保留成熟的事务与权限边界，求解器独立运行。PostgreSQL 存储批准版本、供给份额、独立物理预留、运输身份和 outbox；审批成功的事务只保存可审计承诺，不等承运商网络调用完成。worker 可据获批计划提前订车，外部 `accepted` 回执才更新 shipment；正式发车仍须等待实际收货及物理预留。服务器发送事件（Server-Sent Events，SSE） 或轮询把状态投影回页面，页面先报“P7 已批准，待供货 12 托盘；S1 等待承运商”，不报“货已发出”。这些技术是候选实现，未声称 provider 使用它们。

拓扑中的 `commands` 是 UI 提出的动作，`requests` 是运输服务给承运商的请求，`emits` / `delivers` 是回执的消息交接，`owns` 才表示对象事实的权威归属。实物不沿消息箭头移动，`delivered` 的证据也不能由“消息成功写入队列”替代。承运商确认丢失时，按 `(tenant, carrier account, client shipment reference)` 核对已有订单；外部不提供可核对的幂等身份时，操作保持 unknown，交给调度员联系承运商，不能换一个 ID 再订一辆。

## 交付证据和结算的分岔

GS1 EPCIS（Electronic Product Code Information Services，GS1事件共享标准，后文保留 EPCIS） 区分 eventTime 与 recordTime：前者描述采集应用声称事件发生的时间，后者是 EPCIS repository 记录时间。这使“D1 签收、D3 才收到消息”能够同时表达，不必为了消息晚到而改写交付日。EPCIS 的 ErrorDeclaration 表示此前断言有误，保留原记录，并允许链接更正事件；它不是在旧行上无痕改字段。、[EPCIS 标准 §7.4.1 / §7.4.1.2](https://ref.gs1.org/standards/epcis/2.0.1/)。标准描述事件语义，不替参与方保证事实真实，也不规定本例的支付条件。

这个细节改变接收层设计。普通重复投递可以依据发送方消息身份去重；EPCIS 错误声明允许与原事件使用相同 eventID，而且除 errorDeclaration 与 recordTime 外，其余字段必须与原事件一致。接收服务必须逐字段验证这个条件，保存错误声明及更正引用，不能用 `UNIQUE(eventID)` 把它丢掉，也不能因 ID 相同就接受内容不同的伪声明。内部 inbox 可用发送方传输身份，或经契约明确的“eventID + 声明类型 + declarationTime + 内容摘要”区分记录；无 eventID 的来源需商定稳定采集身份，不能把相似内容的两次真实扫描一律合并。

正常路径是 P7 获批、SC1 接收 12 托盘，S1 运 B+C、S2 运 A，收货方分别确认 10、6 托盘。应付服务把 FI1 的两项基本运费与两趟运输及约定费率匹配，200 记账单位可进入审批。如果 FI1 总额为 250，多出的 50 标为未经批准的附加费，进入争议；“整单已交付”不等于“整张发票都应付”。内部目标中的迟交成本 54 也不能自动从 200 中扣除，是否赔付或抵扣要查合同并另建调整记录。

失败路径更能说明对象分离：S1 报告收到 10 托盘，收货方只确认 9，delivery evidence 进入 disputed。仓库调查发现一托盘未卸货，下一次补送形成新的实物事件；这不是原签收数据录错，因此不能伪造成 ErrorDeclaration。若调查证实扫描把 9 录成 10，才记录错误声明与更正，重算受影响的交付余额。已经支付的款项不因证据修订而凭空退回；应付账另开争议/追偿对象，保存已支付事实。付款请求已被外部接受但响应超时时，PAY1 保持 unknown，确认结算参考号后才把批准金额标记 paid。

## 验算：约束、外部确认与收费依据

合成负载目标为 50 个租户，每租户每日 5,000 单，计划窗口 14 天；在线列表 100 并发时 p95 小于 500 ms，审批持久化 p95 小于 800 ms，单个隔离求解作业预算 30 秒。它们是待测目标。求解按租户设并发配额，防止一个大网络占满 worker；超时保留已验证可行解或明确“尚无可行解”，不能把 CPU 超时翻译成“业务不可行”。按 tenant、plan revision、input hash 缓存结果；库存或供给修订产生新输入身份，旧预览可查但不能直接批准。单条 shipment 的回执与更正按版本处理，异步投影落后时显示最后核对时间。

| 验收情境 | 必须看见的结果与证据 |
|---|---|
| 正常提交、供货与两趟交付确认 | P7、SC1、S1/S2、两份签收和 FI1 收费行可互查；固定演算给出 254，付款依据为 200 |
| 同一承运回执重复；随后同 eventID 的合法错误声明 | 原回执一个业务效果；错误声明仍被保存，交付余额重算，不能误当重复丢弃 |
| D2 的 delivered 先到，D1 的 dispatched 后到 | 保留两种时间，重建证据次序，不按消息到达次序把已交付改回在途 |
| SC1 实收后，两项发运同时预留最后 16 托盘 | 一个物理预留成功，另一个得到明确版本/余量冲突；P7 的条件批准不替代这道检查 |
| 两个租户都有 S1，承运商账号也不同 | 详情、附件下载与缓存均只返回授权范围；跨租户回执隔离待查 |
| 承运商已接单，HTTP 响应丢失 | 操作 unknown，可按客户参考核对到已有承运订单，没有第二辆车 |
| 更新签收后 worker 崩溃，恢复重放 | 数量和收费匹配不重复；outbox/inbox 与业务唯一键解释最后状态 |
| 发票 250 中有 50 未批准附加费 | 200 与 50 分行展示、分行审核；不得因总额低于某个阈值全部放行 |

核心计划和付款使用明确规则，不需要生成式 AI。若加入发票字段抽取，先由模型生成候选收费行，引用原页坐标并保留人工批准。可设置 20 份开发样本、60 份独立留出样本，其中 20 份附加费、20 份重复/近似重复、20 份币种或单位陷阱；报告错误金额字段数/全部金额字段数、未标记附加费份数/20，以及人工修正份数/60。阈值和验收集需要业务方确认，不能用模型语言流畅率代替金额正确率。

## 变式：容量、行程与更正

**练习一：每天容量从 10 降到 9，仍要求两天送完。** A 不能与任一其他订单同车，B+C 也达 10，因此每车最多一单，两天两车无法覆盖三单。即使总容量 18 大于总需求 16，仍然不可行。保持的不变量是每单恰好分配一次且每车不超载；失效条件是不可拆订单的组合，而非容量总和。可观察检查是枚举所有 8 种分配，结果为零个可行解，UI 应提供增加班次或修改不可拆条件的明确入口。

**练习二：把运输模型迁到 V10 维护排班，两项任务占 5 小时、5 小时，班次 10 小时。** 容量约束可以保留，但两项任务若必须由同一技师在相距两小时的地点完成，10 小时并不可行。必须增加行程、技能、许可及设备可用窗口；反例是只把工时相加。检查在时间线插入行程后能发现超窗，不能直接沿用货物装箱结果。`TR:V21:V10:capacity-with-travel`。

**练习三：签收 10 改为 9 时，200 已付。** 保持原付款与原证据历史，修正交付余额并发起合同约定的争议流程；不回退成“从未支付”，也不自动发起负向付款。核对原结算参考号仍可找到、待处理数量为 1，调整对象指向更正原因。这个机制能迁到 V07 的发货收款链，前提是区分客户应收与承运商应付；二者的收款方、计价和抵扣权不能混用。`TR:V21:V07:evidence-before-settlement`。

**实践探索方向。** 进入陌生供应行业时，先拿一张真实业务表单的匿名结构，辨认它究竟表达预测、采购义务、实物交接还是收费请求，再追问每个数字的单位、版本、允许修改的人和外部确认渠道。计划系统适合探索多情景的资源分配，企业资源计划（enterprise resource planning，ERP）/仓储适合落实采购与实物账，运输管理与应付系统分别承担承运执行和收费核对；只有对象身份和交接条件稳定，组合这些成熟方案才有意义。下一步应查采购确认/部分收货文档、承运接口的客户参考与查询能力、签收更正规则及运费合同，再用“供给变少、重复签收、附加费争议、订车结果未知”四组路径验收边界。本文提供的是可研究、可复算的教材与目录底稿，后续可视化的布局和交互由本地实现者选择。
