# V22 · 通信产品的开通、计费与退役

客户买下一项可用的通信产品，网络为它配置资源，计费系统按一段时间内可收费的服务和用量计算费用。产品订单、服务实例、网络资源、usage 和账单必须相互关联，各自的状态却合不成一条“下单—成功—关闭”的轴：订单受理后网络可能还没连通，服务退役后可能还有迟到用量，账单结清了，号码或端口也未必可以重新分给别人。

本例构造一项 IoT 数据连接服务，演示“Product order → service activation → usage → bill → retirement”，并允许退役后继续完成最终计费。以下套餐、计价、工作流和实现均为 **合成的教学政策**，不取自任何运营商的资费、地区规则或平台实现；TM Forum 只作接口标准的参照。其 TMF622 公开概览把 product order 定义为基于 catalog 中 product offering 的订购，offering 带有价格、选项等商业特征；本例据此把商业承诺的版本与后续网络执行分开记录。[TMF622 v5.0 Overview](https://www.tmforum.org/open-digital-architecture/open-apis/product-ordering-management-api-tmf622/v5.0)。

## 识题：开通、计价与退役边界

| 识题线索 | 首选解法 | 后续查证 |
|---|---|---|
| 订单已受理，客户仍不能使用 | 分解订单、资源、网络操作与健康确认 | 目录版本、异步 monitor、资源配置和补偿语义 |
| 迟到或分批的 usage 改变同一周期的费用 | 按发生时间与商业区间归属，累计额度后再计价 | usage 身份、单位、修订和套餐额度政策 |
| 客户已退订，网络仍活跃或仍有账务工作 | 分别关闭商业计费、技术配置、资源与结算 | 退订生效约定、撤销确认、最终账单和调整接口 |

## 解法：订单、服务、资源与账单的分工

客户同意套餐 O3：30 个等长教学日为一周期，月费 3,000 分，周期含 10 GB，超过部分每 GB 200 分。固定费按获批准的商业计费区间 billable_interval 分摊，包含额度在本例不按比例缩减；税、跨币种、漫游、家庭共享和预付余额不在模型内。正常路径从 day 5 实际开通，客户获准 day 20 退订，网络按时关闭，此时 billable_interval 与技术活动区间 technical_active_interval 恰好都是 `[5,20)`。二者仍分别保存：计费从开通确认开始，按获批的退订政策结束；网络关闭失败只会让技术区间变长，不能据此要求客户继续付费。商业承诺绑定 O3 的价格版本和计费政策，月底不能用“当前最新套餐”重算历史用量。

| 参与者与对象 | 权威与状态 | 分开的原因 |
|---|---|---|
| 客户、客服、网络操作员、计费人员 | 客户发起授权订购/退订；客服处理商业例外；网络人员处理配置失败；财务批准已出账调整 | 客服改备注证明不了端口已停用，网络人员也无权改历史价格 |
| Product order PO1 / 退订订单 PO2 | 订单服务；draft → acknowledged → in_progress → completed / failed | PO1 完成后保留购买历史；退订是新操作，不能把 PO1 从 completed 改为 cancelled |
| Service instance SV1 | 服务库存；designed → activating → active → terminating → retired，另有 failed | active 需要网络确认和本例的健康检查；retired 以执行确认为据，只收到退订请求还不够 |
| Billing interval BI1 | 计费服务；pending → running → ended | 开始关联实际开通确认，结束关联获批商业政策；与 technical_active_interval 独立 |
| Resource assignment RA1 | 资源库存与网络域分别负责分配意图、实际配置；reserved → configured → releasing → released | 资源标识、号码或端口重用之前要确认旧配置已撤销，避免两个客户共享一份遗留权限 |
| Usage U1 / U2 | 接入与计量服务；received → validated / quarantined → rated；更正产生 superseded 关系 | 网络观测需校验订阅归属、时间、单位与来源；接收到 usage 不直接产生收费 |
| Bill B1 与调整 ADJ1 | 计费服务；accumulating → frozen → issued，之后另有 adjustment | 账单确认后依据固定；迟到的更正另记调整，不悄悄覆盖客户已经看到的金额 |

TMF640 的公开概览明确包含服务操作与监视异步请求的 monitor 资源，可据此区分“激活请求已受理”与“服务实际可用”；下文的状态名称、探测标准和补偿步骤是本例自设，并非该标准的完整状态机。[TMF640 v4.0 Overview](https://www.tmforum.org/open-digital-architecture/open-apis/service-activation-management-api-TMF640/v4.0)。TMF635 的概览区分 rated 与 non-rated usage，TMF678 的概览提供账单及 applied billing rates 的查询；计价规则仍由运营商自己选择。[TMF635 v4.0 Overview](https://www.tmforum.org/open-digital-architecture/open-apis/usage-management-api-TMF635/v4.0)；[TMF678 v4.0 Overview](https://www.tmforum.org/open-digital-architecture/open-apis/customer-bill-management-api-TMF678/v4.0)。

## 订单提交与网络执行

客户端先显示套餐摘要、生效时间、单位与退订规则。点击“提交订单”后，React 或 Vue 页面保存可再次查找的 operation ID；客服工作台展示订单、服务、网络任务和计费开始日四个状态，避免一个绿色标签掩盖配置等待。表单校验帮客户发现漏项，身份、offer version、账户权限与请求版本仍由服务端校验。用户断网刷新后，系统按 operation ID 找回原来那次提交，不把重新加载页面当成新的购买。

订单服务在 PostgreSQL 的一个事务中保存 PO1、客户接受的 O3 版本及 outbox。编排 worker 依次预留资源 RA1、请求网络配置、核对执行结果、执行本例的健康检查，然后才记录 SV1 active 与 effectiveAt。Spring Boot 适合已有 Java 运营支撑系统（operations support systems，OSS）/业务支撑系统（business support systems，BSS）的团队；Node.js/TypeScript 便于小团队共享数据类型，但远程调用、事务边界与任务恢复仍要自己设计，类型系统保证不了。Temporal 可以持久化长时编排的进度；小规模使用数据库任务表更易运维，但要自行实现超时、重试与人工接管。两种方案都必须把可重试命令的业务身份传到适配器。

网络控制器不是订单数据库的一部分，跨域配置无法与订单提交放进同一个本地事务。假设设备配置已经成功，网络响应却丢失：本地 activation operation 记为 unknown，服务页显示“等待核对”；系统既不马上再配置一次，也不当作失败去释放号码。worker 用 `(tenant, network domain, service ID, operation ID)` 读取 monitor 或网络库存；确认配置与健康条件后补记 active，确认没有执行才安全重试。查不清时由网络人员处理，附上已知对象、请求摘要与最后检查结果。

若端口已经配置但健康检查失败，补偿按相反的依赖次序进行：撤销配置并确认，然后释放资源。数据库删除 RA1 不会让网络里的旧配置消失，因而“删除订单回滚”不是有效恢复。另一种业务选择是保留资源等待修复，这时要明确状态和占用超时。两种政策只能取其一，否则会一边维修、一边把资源重新分给别人。

## 演算：发生时间与商业区间

固定费先算商业计费区间与计费周期的交集。周期是 `[0,30)`，billable_interval 是 `[5,20)`，长度为 `min(30,20)-max(0,5)=15` 天，固定费 `3000×15/30=1500` 分。U1 在 day 6 使用 4 GB，U2 在 day 18 使用 8 GB，有效总用量为 12 GB。超量为 `max(0,12-10)=2 GB`，费用为 `2×200=400` 分，最终 1,900 分。这个分解必须能从 UI 账单行追到 BI1、开通依据、两个 usage ID 与 O3 规则版本。

包含额度按周期共享。不能对每条记录分别减 10 GB，否则 4 与 8 各自都不超额，400 分就消失了；也不能先按到达批次各自计算再简单相加。同一周期内维护累计有效用量，新增记录的增量费用等于“更新后超量费减更新前超量费”；出现更正时按受影响的周期重算，保留已出账与新应计的差额。若单位改为 MB 或字节，先按套餐定义的换算规则归一，不把十进制 GB 与二进制 GiB 混用。金额用整数最小币种单位或精度明确的小数，比例尾差按已批准的规则处理；JavaScript 浮点显示值不能直接记账。

U2 即使在 day 22 才到达，也属于 day 18 的使用；退役已在 day 20 生效，不是拒收历史证据的理由。本例设置 day 23 为最终账单截点：先保留未出账的累计窗口，收到有效 U2 后重算。截点只是业务接受迟到数据的期限，并不保证所有来源都已到齐。恰好发生在 day 20 的记录不在 BI1 的 `[5,20)` 中，先隔离核对商业截止依据、网络残留或关联错误，不自动收费；即使网络仍 active，也不能延长 BI1。把 arrival time 当成 occurrence time，会漏收合法的历史用量，也可能把新的使用错误塞回旧套餐。

`ALG:windows` 完成区间切分，`ALG:lookup` 找到有效订阅和价格版本。朴素做法每次重读整月 n 条 usage，单次 O(n)，频繁更新时重复计算会越积越多；按 `(tenant, subscription, cycle, tariff revision)` 保存累计并维护唯一的 usage revision，普通增量处理的开销接近常数。服务或套餐变更时先按生效区间排序，用二分查找为一条 usage 定位，m 段有效期的查询约 O(log m)；跨边界的一段聚合用量若只有总量、没有可分割的证据，不能想当然均摊，应当隔离，或采用明确且获授权的分摊政策。

账单已按 1,900 分 issued 后，来源把 U2 从 8 GB 更正为 5 GB，有效总量变为 9 GB，超量费归零，产生 `1500-1900=-400` 分的调整。不能只把新记录 5 GB 追加进去得到 17 GB，也不能擦掉原账单。usage 原始证据、修订链、rating run 与调整都必须可以联查；原始数据可按来源分区保存在对象存储里，已校验的明细与可付款金额存入带约束的账务库。Kafka 适合持续高吞吐的接入，ClickHouse 可做明细检索和分析，但分析副本不直接批准收费；小量原型先用 PostgreSQL 分区和批量作业即可，没有负载依据就不引入多套存储。

## 退役与账务关闭

客户提交 PO2 后，服务进入 terminating，页面同时展示客户要求的时间与网络确认的实际 effectiveAt。本例先停网络权限，核对停用，再解除资源占用，最后允许 RA1 released。迟到的旧 active 通知不能覆盖已经确认的退役版本；处理器要比较操作身份和配置版本，两者矛盾时读取网络的当前状态。没有新 usage 只是“没有收到观测”，不能据此证明服务已经停用。

退役失败时同样要区分商业权利和技术事实。本例采用“已核准退订时间后停止固定费，截止后残留 usage 隔离、不自动计入客户账单，网络延误列为运营异常”的合成政策。例如 billable_interval 已是 `[5,20)`，网络到 day 22 才停，technical_active_interval 就是 `[5,22)`；后两天交给运营处理，不用来延长 BI1。资源未释放会占用容量，错误的提前释放则可能泄露旧连接权限，二者的恢复优先级不同。

正常闭环是客户接受 O3、PO1 完成、SV1 从 day 5 active、U1/U2 校验计费、PO2 使 day 20 技术退役、day 23 出最终账单，随后完成支付与资源核对。失败可能出现在网络已成功但回执丢失、用量迟到、价格变更竞争或出账后更正等环节；每条路径都分别保留商业承诺、网络状态与金额依据，三者不必同时变绿。

## 验算：配置、用量与收费的依据

合成运行目标为 100 个租户、合计 100,000 个服务实例、每日 5,000,000 条 usage，平均约 58 条/秒，但验收峰值应覆盖 2,000 条/秒和批次回灌；接收容量要按峰值选，不能只看日均量。待测目标是接收持久化 p95 小于 1 秒、服务详情 p95 小于 400 ms、正常投影落后小于 10 秒；不承诺网络配置时长。开通流量与用量回灌分队列，按租户配额，避免一个批次让人工停用命令排队数小时。套餐缓存按版本读取；授权和计费生效区间以权威记录为准，已退役读模型的陈旧状态不能延长收费。

| 验收情境 | 预期结果与证据 |
|---|---|
| O3、服务 `[5,20)`、U1=4/U2=8 | 订单、SV1、资源、usage、账单关联完整；固定 1500、超量 400、合计 1900 分 |
| 重发同一个 activation 命令与同一个 usage revision | 一份配置、一份资源分配；账单金额不增加；查 operation 与 usage 唯一键 |
| 退役已确认后旧 active 通知到达；day18 的 usage 在day22到达 | 旧通知不复活服务，合法迟到用量仍入原周期；保存发生/到达时间与核对日志 |
| 一位客服修改 O3，另一位同时提交订购 | 一个请求按原版受理，另一方要确认冲突或改用新版；不出现价格与额度混合的订单 |
| 两个租户同为 SV1 / U1 | cache hit、明细查询、原始附件与网络适配器均隔离；外部标识含网络域 |
| 网络已配置但请求超时 | 保持 unknown，查 monitor 或库存后补记成功；没有重复分配的资源，也没有提前释放 |
| rating 已提交、消费标记前崩溃 | 重放后仍为 1900；修订为 9 GB 后另记 -400 调整，不追加成 17 GB |
| 退役失败但商业计费已停止 | 页面仍显示技术未关闭和接管人；账务停止不把资源标成 released |

模型不决定开通、退役或收费，核心 AI eval 不适用。若加入 AI 账单解释，冻结 30 份开发题和 120 份留出题，留出题中迟到、更正、边界题各 40 份。评估金额错误的回答数/120、无依据宣称已开通或已停用的回答数/120、应拒答而未拒答数/缺证据题数，以及人工修改的回答数/120；答案必须引用账单行与使用区间。目标是金额或服务状态的无依据断言为零；即使样本通过，模型也不获得写入账务的权限。

## 变式：额度、到达次序与退役延误

**练习一：10 GB 额度也按商业计费日比例缩减。** 账单变成多少？

简答：BI1 占 15/30 周期，额度变为 5 GB，12 GB 用量超出 7 GB，费用为 `1500+7×200=2900` 分。冻结规则与输入后能够重演计价，这是保持的不变量；失效的旧前提是“额度不按比例缩减”。固定费不变，变的是 allowance policy，因此要新建一个明确的规则版本。反例是后台改了规则、历史账单仍显示原来的 10 GB。检查：新旧规则对同一冻结 fixture 分别返回 2900、1900，并能解释 1000 分的差额。

**练习二：把 occurrence time 改为接收时间入账。** 账单会怎样变化？

简答：U2 在 day22 到达，会落在退役之后而被错误排除，账单只剩 1500 分。不变量应是每条合法用量按实际发生的区间归属，有效修订只计一次；失效条件是源时间不可信，或聚合记录跨越套餐边界，这时要补证，而不是猜测。验收时交换两条记录的到达顺序，最终金额仍为 1900；day20 的边界记录保持隔离。

**练习三：退订后网络仍活跃，按“没有用量”释放号码。** 这样做是否可行？

简答：不可行。没有观测到用量，证明不了配置已撤销；要取得旧配置不存在的证据，或由有权限的人工流程确认处置，资源才能进入 released。检查：持续送入空用量流，资源仍停在 releasing；加入确认撤销的事件后，才允许下一客户预留。这个 guard 可迁到 V10 的设备安全复归，但设备现场隔离的专业证据不能换成通信 monitor。`TR:V22:V10:release-after-confirmation`。

`TR:V22:V11:late-usage-window` 把事件时间、有效修订与计价输入的分离迁到 meter/校验、估算与编辑（validation, estimation and editing，VEE）；通信记录可能含会话、套餐和多种服务单位，表计读数则可能是累计量、估算和周期差值，一次会话去重不能直接当成 meter reset 处理。`TR:V22:H01:entitlement-and-billing` 保留承诺、使用权与账单的分离；H01 的预付开通 guard 不适用于本例的后付政策。

演示中可以拖动激活和退役区间、调整额度政策、迟送 U2、重放旧 active 回执，观察服务条带、用量窗口和账单行各自的变化。

## 进入通信服务的先查项

进入陌生的通信服务时，先区分卖给客户的 product、实际提供能力的 service、被占用的 resource，以及产生费用的 usage；再逐项找出商业生效时间、网络配置权威、计量来源和账务修订责任。产品目录与订单管理适合保存版本化的商业承诺，服务编排与库存管理跨网络执行，计量与计价系统负责单位、迟到和资费规则；能否组合取决于稳定身份、可核对的异步操作和明确的数据语义，接口名称相似说明不了什么。下一步查所选 API 的确切版本与状态定义、网络 monitor 和资源释放保证、usage 修订与时间精度、实际资费与退订条款，再用“已配未回、商业已止而网络未停、用量迟到、出账后纠错”验收整条链。
