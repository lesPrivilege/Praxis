# P06 · 生产、资产与供应网络

一家企业答应交付一批设备，首先要知道交付的是哪版设计，随后安排材料、设备和人；制造记录证明做过什么，检验决定哪些可以出厂，运输证明哪些到达客户，账单和付款再结清相应义务。设备投入使用后，还会产生维护、计量和服务费用。七个案例沿这些关系展开：同一件实物可以参与多条工作链，每条链却有自己的权威、证据和结束条件。

本包是一份供 vibe coder 阅读的紧凑教材。先读本页的共同模型，再进入案例；正文中的数字、系统架构和业务策略均明确作为合成设计。公开产品事实在主张附近引用一手资料，产品没有公开的实现不由演算代填。正文和拓扑 JSON 可以供后续 HTML、motion 或应用原型使用，呈现方式由实现者决定。

## 承诺、执行、证据和结算

订单表达承诺，计划寻找可行办法，执行消耗现实资源，证据说明实际发生的事，授权决定证据是否足够，结算确定与履约对应的债权债务。这个共同模型是本包的原创分析，不是要求所有厂商都采用六张表。它帮助开发者发现缺少的对象。例如，“生产完成 100 件”还没有回答有多少件通过检验；“抄表数据已到达”也没有回答哪些数值经过估算、允许怎样计费。

| 对象职责 | 回答的问题 | 容易混淆的对象 | 案例中的区别 |
|---|---|---|---|
| 承诺与基线 | 承诺哪种结果，依据哪个版本 | 计划、最新文件 | 生产单绑定已发布设计；旧批准不会自动覆盖新配方 |
| 计划与资源预约 | 在什么约束下做得到 | 执行事实 | 车有容量不证明承运人已接受；任务 DAG 可排不证明许可证足够 |
| 执行记录 | 谁在何时对什么做过什么 | 汇总进度 | 一批混合物的投料与损耗需要守恒；离线维修可能迟到上报 |
| 证据与处置 | 哪些结果支持哪项决定 | 原始信号、模型建议 | 检验报告、时序报告和 VEE 的校验结果各有适用范围 |
| 授权与放行 | 谁可在什么条件下推进 | 自动计算结果 | 质量人员放行批次；设备许可限定现场作业；服务激活需核对资源 |
| 结算与关闭 | 哪项义务已经结清 | 发货、开票、付款 | 部分交付保留欠交量；已停服务仍可能有迟到用量待结算 |

每个对象至少有三种身份：业务身份（批次或服务实例）、版本身份（这次判断使用的输入）、操作身份（这次提交和重试）。业务身份让人追踪一件事，版本身份阻止旧证据批准新对象，操作身份让重复送达不重复扣料或收费。三者不能用一个自增行号替代。租户、站点、外部账户和允许的合作伙伴关系还要进入授权范围；把编号拼接进缓存键只能防误命中，不能代替服务端权限。

## 把页面接到现实

合成系统的最小闭环是：人通过工作台发命令，服务检查权限和对象版本，数据库保存尝试，连接器把确定的请求交给现场或外部系统，回执进入持久收件箱，业务服务核对后改变状态，读模型再更新页面。拓扑中 `commands`、`requests`、`delivers` 表达不同交接，`owns` 表达事实归谁负责，`derived_from` 表达计算依据。实物运输和现金支付另有业务记录，不能由一条消息箭头证明。

页面应把“请求已保存”“外部已接受”“业务已确认”显示成可区分的事实。需要数小时运行的芯片设计任务、离线维修、迟到的电表读数，尤其不能依赖一个旋转图标。用户关闭浏览器再回来，仍应找到同一操作及待办责任。结果未知时先查询既有外部对象；现场实物已被改变时，恢复往往是追加修正、返工、隔离或对账，无法靠数据库回滚抹去。

原型可以从 React 或 Vue 工作台、一个模块化业务服务、PostgreSQL 和对象存储开始。关系库适合在事务内保护版本和数量约束，对象存储适合检验附件、版图和签名清单；时间序列、图遍历、优化器和消息中间件应随案例中的真实查询或规模需求引入。它们是本包的实现选项，不是被引用厂商的技术栈。每例给出选择触发条件，避免先堆基础设施再寻找业务理由。

跨例保持的是“判断绑定依据，动作有权威，数量和时间可核对”；变化的是允许推进的条件。V08 的 lot release 需要质量责任，V09 的 release 需要设计证据，V22 的 active 需要技术状态。三个英文词即使都呈现为绿色，也没有可互换的审批语义。

## 进入陌生行业时怎样使用

先选最接近当前承诺的案例，照着辨认业务对象与权威，再列出本行业改变了哪些单位、时间、授权和失败条件。每例沿“识题 → 解法 → 演算 → 验算 → 变式”展开：看到线索后选择已知方法，用小数据算清楚，再用不变量和反例检查，最后改变前提判断哪里必须重做。每例的实践探索方向给出可考察的成熟方案家族、需要补读的产品文档与验证输入；方案名称只是研究入口，适用性取决于能否覆盖已识别的职责和证据边界。
