# P01 · 交易、财务与资金

一笔业务可以同时拥有已经生效的合同、尚未交完的服务、已结清的发票和还未完成的收入计划。财务软件的难处，是把这些事实保存在各自的对象中，再解释它们为何相容。只在订单表加一个 `status`，很容易把“客户欠多少”“企业还欠什么”“钱现在在哪里”混成一个问题。

## 先建立共同模型

设一家合成企业收取 300 单位预付款，承诺提供 30 个等长服务日。第 10 天，客户可能已不欠钱，企业仍欠 20 天服务。把收到的 300 全显示成已赚取，会隐藏剩余承诺；只显示“服务进行中”，又无法回答能否用这笔现金付款。下表的六种记录帮助系统回答不同问题；这是教学分类，不是会计准则分类。

| 记录 | 回答的问题 | 足以改变它的证据 | 常见错误 |
|---|---|---|---|
| 承诺与授权 | 答应交付什么，谁可作此决定 | 已接受的确定版本、审批范围 | 把报价草稿当合同，把审批当已执行 |
| 履行与接收 | 实际交付、成交或验收多少 | 服务期间、验收记录、成交报告 | 用付款证明交货，用撤单请求证明已撤 |
| 应收与应付 | 哪一方还欠哪一方多少 | 开票、分配、贷项与结算记录 | 只按金额相等合并不同客户或法人 |
| 现金与证券 | 哪个账户实际增加或减少什么 | 外部确认、银行或托管核对 | 把请求受理、支票签发当最终到账 |
| 估计与期间结果 | 还可能承担多少，当前期间归属多少 | 规则版本、估计依据、截止范围 | 把准备金当付款，把利润当可用现金 |
| 集团合并调整 | 集团视角哪些内部重复应去除 | 对手方关系、匹配单据、抵销批次 | 用合并抵销删除法人原账或免除债务 |

这些记录之间是有条件的关系。预付服务要求付款核对通过才开通；赊销服务可以先开通，但会新增信用限额和催收责任。采购先验收再付款，也可能按合同预付。迁移机制时应保留“动作需要什么证据”，再改证据的具体内容，不能照搬箭头顺序。

### 一个业务身份需要多个坐标

`tenant` 是客户组织的隔离范围，`legal_entity` 是承担义务的法人，`provider_account` 是外部账户，三者不能互换。一个集团租户可能有多个法人，同号发票也可能来自不同供应商。对象键至少表达它在哪个范围唯一；跨系统映射保留原对象 ID，而不拿一个可编辑显示编号充当身份。每笔金额还需要币种、精度和方向，每项数量需要单位，每个期间需要起止与截止规则。相等的裸数字不证明同一业务。

同一数据库的事务可以约束本地对象一起提交，却无法使外部银行、交易场所或保险支付系统同时提交。操作记录因而要保存“想做什么、发出了什么、确认了什么”。`unknown` 表示缺少结果证据；`failed` 表示已有失败证据。若外部已经付款但回执丢失，改一个新请求号重发会把网络问题变成重复资金流。各章分别说明如何找回结果，不能用统一的“失败重试”按钮覆盖。

### 从屏幕走到可解释的结果

页面应同时回答对象状态与动作状态。例如发票仍为 `open`，付款尝试正在核对；贷款已批准，放款尚未确认；订单部分成交，撤单正在等待。列表适合发现异常，详情需要展示来源版本、剩余数量、责任人和下一步动作。权限由服务端依据身份、对象范围与动作重新判断。隐藏按钮方便使用，但不是授权机制。

本包把 UI、service、store、external system 的信息边画进 JSON，把现金、实物和证券变化写进业务对象。一个 `delivers` 箭头表示消息交接，不表示钱或货已经到达。`owns` 指定谁对事实作权威判定；存储副本和报表投影不能据此取得同样权力。完整状态转换、前提和恢复点在每例的结构文件中，正文负责解释这些前提为何存在。

## 从陌生行业开始探索

本包按“识题 → 解法 → 演算 → 验算 → 变式”学习：先由现象认出问题类型，选有前提的已知方法，手算可观察结果，用不变量与反例检查，再改变条件判断方法是否仍适用。每例开头的识别线索和后文的具体推演相连，便于遇到陌生业务时先找到研究入口。

先找出承诺对象、履行证据、数量或金额约束、决定权限与外部权威，再判断需要哪一类成熟机制：版本化合同、匹配与hold、来源级对账、期间与事件重演、分组估计账务、受约束分配或跨公司协同。方案的名字只是入口，适用条件决定能否迁移。每章的“下一步探索”给出最小合成试验、需要继续查的文档和可观察成功条件。

状态图应把“事件触发了什么”与“哪个对象依赖哪个前提”分开：H03正文中的A先于B执行，对应结构里的B `depends_on` A，而不是同方向的数据传输。

## 如何使用例子与检查

每章的金额、政策、技术选型和性能目标，除明确带来源的产品事实外，均为 synthetic 教学设计或原创推理。它们说明实现需要哪些决定，不提供通用会计、信贷、保险或交易合规结论。上线前需要针对产品、制度与接口版本重新确认。厂商文档用来限定真实行为，不能据此推断厂商内部采用了本包的算法或技术栈。

先手算例子，再改变一个条件：时间、数量、价格、权限或外部确认。每章给出至少两道有简答的练习；观察不变量在哪一步遭到破坏，比增加更多页面更有助于判断系统是否完整。

从 Praxis 仓库根目录运行以下命令，无须安装第三方依赖。先读 [checks.py](../../../../vault/distilled/saas-engineering-atlas/packages/commercial-finance/checks.py) 的输入与断言，再改一项条件复算：

```bash
python3 vault/distilled/saas-engineering-atlas/packages/commercial-finance/checks.py
```

它覆盖七章的固定算术、区间可加性、数量占用、配对、依赖图和不可行条件，没有建立服务或模拟实际并发数据库。维护者另外用 `python3 scripts/validate_saas_atlas.py --self-test` 验证共同结构，用 [validate-package.py](../../../../vault/distilled/saas-engineering-atlas/packages/commercial-finance/validate-package.py) 检查证据身份与引用：

```bash
python3 vault/distilled/saas-engineering-atlas/packages/commercial-finance/validate-package.py
```

所有外部集成、权限执行、浏览器端到端、故障注入、负载与 AI eval 仍须在实施后单独执行。
