# H05 · 服务恢复以后，哪些工作仍未完成

Incident 记录一次服务中断及其恢复责任；change 记录一次受控修改及其授权、执行与复核；problem 保存需要继续调查的原因。三者可以互相关联，仍各自拥有生命周期。一次回滚让用户重新下单，可以使本例 incident 进入“已恢复，待确认”；回滚本身要留下 change 的执行结果，导致故障的缺陷则可能继续留在 problem 中。把这三个对象一起标成完成，会让下一次事故失去可追查的工作。

本例构造一个内部订单服务：第 0 分钟出现错误，第 10 分钟接管，第 20—40 分钟存在获准暂停计时的外部信息等待，第 45 分钟执行已授权回滚，第 70 分钟服务通过恢复验证，第 90 分钟接收方确认关闭。计时从第 0 分钟开始，全天连续，恢复目标为 45 个有效分钟；暂停规则、阈值、角色与执行策略均为 synthetic 教学假设，并非 ServiceNow 默认配置或通用 服务级别协议（service-level agreement，SLA） 规则。

## 识题与选法

先按下面的线索选择方法，再读正文中的演算和反例；文末变式题改变其中一个条件，检验方法是否仍适用。

| 识题线索 | 解法与演算 | 验算要点 | 继续查证 |
|---|---|---|---|
| 同一分钟被多条暂停记录覆盖 | 先合并区间再扣除；70−20=50，有效时间超目标5分钟 | 重排或重复暂停不改变结果；计时规则能解释每段排除 | SLA 日历、可暂停理由和补录授权 |
| 改一个节点，要找依赖它的对象 | 沿反向依赖遍历；DB→Orders API/Invoice→Checkout | 已知图下结果可复算；删边会产生可见漏项 | 配置管理数据库（configuration management database，CMDB） 边方向、图新鲜度、关键业务探测 |
| 执行成功，业务仍可能失败 | 把计划授权、执行结果和恢复证据分别绑定版本 | 读路径成功但写路径失败时仍保留恢复责任 | 变更类型、计划hash、执行器查询和回退兼容性 |

## 把恢复证据与关闭决定分开

ServiceNow 的 Incident 生命周期文档区分 New、In Progress、On Hold、Resolved、Closed 与 Canceled，并列出等待 caller、change、problem、vendor 等 On Hold 原因。[Life cycle of an Incident](https://www.servicenow.com/docs/r/it-service-management/incident-management/c_IncidentManagementStateModel.html)这些状态告诉界面该展示何种工作，却不能仅凭状态名称推导计时规则；“正在等待”是否暂停承诺的时钟，仍取决于具体规则。

该产品专门的 resolution and closure 文档允许以 temporary workaround 或 permanent solution 使 incident resolved，并说明调用者可以审阅恢复结果，关闭也可以按配置自动发生。[Incident resolution and closure](https://www.servicenow.com/docs/r/it-service-management/incident-management/c_IncidentResolutionAndRecovery.html)因此，恢复可以有可重复验证的事实依据，同时根因调查仍未完成。本文采用这个更具体的解释；来源侧车保留它与生命周期概览中较强措辞的差异，不替厂商消除文本张力。

教学服务要求值班工程师给出恢复证据，业务接收方确认关键操作可用，事故负责人决定关闭。工程师可以提出回滚计划，变更批准人决定是否允许执行，执行器只有在计划版本、授权和允许窗口一致时才接受请求。事故严重并不会使任何人自动取得修改生产环境的权限。ServiceNow 的变更状态说明也区分 normal、standard 与 emergency：standard 预先授权，而 emergency 虽跳过 Assess，仍经过 Authorize。这里只取其公开状态关系；本例的双人授权、回滚阈值和执行器并非该产品事实。[State progression for change models](https://www.servicenow.com/docs/r/it-service-management/change-management/normal-standard-emergency-states.html)

| 对象与权威 | 本例状态与决定 | 独立保留的依据 |
|---|---|---|
| Incident，事故协调服务 | new → investigating → waiting／investigating → restored → closed；恢复失败可回 investigating | 影响、责任人、恢复测量、接收确认、关闭理由 |
| Change，变更协调服务 | draft → authorized → running → review → closed；执行前可 cancelled | 计划 hash、批准人、窗口、目标版本、执行结果与复核 |
| Execution，外部执行器负责实际结果 | queued → running → succeeded／failed；通信中断为 unknown | operation ID、实际版本、日志摘要、回滚或补救结果 |
| Problem，问题负责人 | open → investigating → known → resolved | 原因假设、反证、修复验证；incident 关闭不推进它 |
| SLA calculation，计时服务 | provisional → confirmed；补录后可 revised | 事件时间、可暂停区间、规则版本、截止点 |

变更 closed 还必须保留 outcome。本例一次回滚执行失败，后来由另一方案恢复服务，原变更可以在复核后以 failed 结果关闭；不能为了得到绿色列表，把失败改写为 succeeded。相同逻辑适用于 incident 的 cancelled：它可能是已归并的重复报告，并不证明没有发生服务中断。

## 页面应让操作者看到下一个决定的依据

事故列表显示影响服务、责任人、最近观测时间与计时状态。详情页把故障时间线、关联变更、恢复证据和客户可见说明放在一起；原始告警是线索，不会自动授权变更。工程师点“提出回滚”后，预览应显示计划目标、将受影响的服务、当前版本、回退方法和成功判据。批准人看到的必须是同一计划版本。若工程师随后把回滚目标从 r17 改为 r16，旧授权不再有效，服务端要求重新批准；隐藏前端按钮无法替代这个检查。

“执行变更”提交 `change_id + plan_hash + expected_version + operation_id`。后端在事务中校验授权与窗口、写执行意图和 outbox，然后返回可恢复的操作页面。请求超时显示“执行结果待核对”，允许查看原 operation；不把按钮重新变成一个无身份的“再执行”。一旦执行器按同一 operation 报告结果，适配器保存外部结果并推进 change 到 review。下一步“确认恢复”仍需真实服务观测，不能拿部署成功响应代替用户路径验证。

例如执行器证明所有实例已回到 r17，但订单仍因数据库连接池耗尽而失败。此时 change 可报告“回滚步骤成功，业务效果未达标”，incident 保持 investigating。工程师调整连接池前需要另一个受控计划，不能在原批准范围内无限加动作。业务恢复以后，接收方确认创建订单与查询订单两条路径；若只读路径正常、写入仍失败，页面必须显示部分恢复及未满足的判据。

拓扑中的 `authorizes` 是批准人或规则对执行服务的许可，`requests` 是服务向外部执行器提出动作，`emits` 与 `delivers` 是执行结果的交接；它们没有一条能单独证明恢复。恢复证据对象 `derived_from` 已关联的 execution 与测量，incident `depends_on` 恢复证据才允许转 restored。服务依赖图另有 `depends_on` 关系，含义是运行前提，并非消息调用日志。这些关系在 [H05.json](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/H05.json) 保留不同身份，分别表达“允许做”“已经做”和“确已恢复”。

实现可采用 Vue 或 React 的时间线与计划差异视图，Django 或 NestJS 提供命令接口，PostgreSQL 保存事故、变更、版本与操作账本。小规模列表与时间线适合关系查询；没有必要为了画依赖图就立即引入图数据库。初期用邻接表和递归查询即可检查有限规模的影响范围，只有关系规模、路径查询频率和更新方式使其成为瓶颈时，再评估专用图存储。Prometheus 一类监测系统可以提供时间序列线索；合成设计还需主动探测关键业务路径，单一进程存活指标无法证明订单成功。

恢复记录存测量区间、查询条件、结果摘要与受控日志引用。大体积日志留在日志系统，不能把令牌、完整请求体或客户资料复制到事故评论。服务器发送事件（Server-Sent Events，SSE） 适合由服务器单向推送状态，WebSocket 更适合多人协同编辑但需处理连接恢复和顺序；即使实时连接中断，页面仍须按 operation 重新读取权威状态。执行器能力按操作白名单和目标环境隔离，普通工单 API 不直接持有任意远程 shell 权限。以上是本例的技术选择，未推断 ServiceNow 内部技术栈。

## 计时计算：重叠暂停为什么不能直接相加

SLA 时钟把承诺变成可检验的时间条件。它需要知道截止事件是哪一个、哪些等待可以排除，以及迟到的信息能否修订结果。本例截止到恢复时间 70，而不是关闭时间 90；等待用户确认关闭不继续增加恢复时长。所有区间使用事件发生时间，接收时间只用于记录消息迟到。

假设两条获准暂停记录分别为 `[20,35)` 与 `[30,40)`。它们可能来自同一等待的两个来源。直接相加得到 15 + 10 = 25 分钟，算出的有效时间是 `70 − 25 = 45`，看起来刚好达标；实际第 30—35 分钟被扣了两次。合并后的暂停区间只有 `[20,40)`，长度 20，因此有效时间为 `70 − 20 = 50`，超过目标 5 分钟。这是一个能改变管理判断的错误，不只是时间线画得不好看。

正确算法先把每条暂停裁剪到事故计时区间 `[0,70)`，移除空区间，按起点排序，维护当前合并区间。读到 `[20,35)` 时暂存；读到 `[30,40)`，因为 30 不晚于当前终点 35，把终点扩展到 40；没有新段后累计 20。n 条记录排序为 O(n log n)，扫描 O(n)，额外空间按保存方式为 O(n) 或排序后的 O(1) 扫描状态。朴素逐分钟遍历成本随时间跨度增长，按秒或跨月计时会更贵；区间法的成本跟变更点数量相关。

补录一段 `[60,80)` 时先裁剪为 `[60,70)`，新增暂停 10 分钟，有效时间改为 40。这个结果只有在暂停确获规则授权、且允许事后修订时才有效；算法无法判断理由是否真实。为了防止“改状态使报表达标”，批准暂停、记录等待与修订 SLA 结果分别留痕。使用营业日、节假日或不同时间区的真实 SLA，还要把可计时日历与事故区间求交，不能把本例的连续分钟公式直接部署。

## 影响图只说明可能受影响，不能证明因果

另一个有用计算是沿依赖图找到变更的观察范围。合成图规定：Checkout 依赖 Orders API，Orders API 依赖 DB，Invoice 依赖 DB，Search 依赖 Search Index。若变更目标是 DB，沿反向依赖边遍历，先得到 Orders API、Invoice，再得到 Checkout；Search 不在本次已知影响集合里。广度优先或深度优先搜索在所访问子图上的成本为 O(V + E)，visited 集合避免环导致无限遍历。

如果按原方向从 DB 出发，可能一个消费者也找不到，这个反例说明边的方向比图的漂亮程度更重要。另一个反例是 CMDB 漏掉 Invoice → DB：遍历算法完全正确，所得范围仍不完整。因此教学审批预览把集合标为“已登记依赖下的影响范围”，展示图版本和缺失信息，要求服务负责人补充关键观察点。共享数据库并不证明某次变更导致了所有关联告警；相关性和可达性只能帮助安排检查，不能充当根因结论。

本例最少要求对 Checkout 和 Invoice 验证关键路径，Orders API 与 DB 提供诊断信号。若两个团队同时修改 DB，同一窗口的两个计划即使各自授权，也可能互相破坏回退前提。教学调度先检查目标资源与时间窗冲突，冲突计划由负责人串行安排；只做拓扑排序不足以处理锁、容量、值班人员和禁变窗口。这里不宣称获得全局最优排程。

## 故障恢复需要保留失败本身

正常轨迹为：第 0 分钟建 incident，责任人接管；等待信息的记录与获准暂停分别落库；提出并批准回滚计划；执行器报告实际 r17；第 70 分钟关键路径通过，保存恢复证据并停止本例恢复时钟；第 90 分钟接收方确认后关闭 incident。change 在执行后完成复核，problem 继续调查为什么 r18 导致异常。三个时间点分别支持恢复耗时、接收耗时和根因处理耗时，不能互相替代。

失败轨迹为：执行器已开始回滚，但响应丢失，页面 unknown。值班人员先按 operation 查询执行器，并读取实际版本；若查询也不可用，暂停自动尝试并人工确认当前运行状态。盲目重发可能把刚恢复的服务再次滚动重启。若执行器证明回滚失败，change 记录 failed，incident 保持 investigating，后续补救另建计划。回滚也可能有副作用，例如 r18 已写入 r17 不认识的数据；“恢复旧镜像”不能保证恢复旧业务状态，计划必须在执行前解释数据兼容性或接管条件。

结果通知可能迟到。第 72 分钟收到“执行失败”的旧尝试消息，不能把已由第二次计划验证恢复的 incident 直接退回失败；它只更新对应 execution，并触发检查该失败是否还有未处理影响。两个负责人并发关闭与重新打开事故时，按 incident version 做条件更新；旧关闭请求必须失败，让操作者看见新的失败证据。

教学规模假设为 500 个服务节点、2000 条依赖边、每天 1 万条 incident、事故高峰每秒 300 条观察事件。关键动作接口目标 p95 小于 500 ms，告警写入和去重可异步，业务命令仍保留事务版本。每个 incident 是并发热点，大量相同告警应聚合为计数与时间窗，保留原始观测索引；不能让重复告警刷新事故开始时间。依赖影响集合可按 tenant、graph version、目标节点缓存，图更新必须换版本；缓存缺失时重新遍历，权限过滤不能靠客户端隐藏无权服务。以上容量和延迟只是验收假设，没有负载测量。

## 有意义的端到端验收

| 情境 | 动作与预期 | 要观察的证据 |
|---|---|---|
| 正常路径 | 授权计划执行成功，关键路径恢复并获接收；incident closed，problem 仍 open | 计划、授权、实际版本、恢复探测、接收记录和分别展示的状态 |
| 重复 | 同一告警和执行回执各送两次；不得生成第二次变更执行，也不得重置事故开始时间 | 事件身份、operation 唯一键、原始首次时间 |
| 乱序 | 新恢复证据之后收到旧 execution 失败；只更新旧尝试并核查影响 | execution 身份、恢复依据、未盲目覆盖的 incident |
| 并发 | 同一版本同时批准和改计划；只有完全匹配的 plan hash 可执行 | 版本拒绝、重新审批要求、执行器接收记录 |
| 租户隔离 | 两租户都有 DB-1；图查询、工单与日志引用不得跨租户返回 | 服务端 scope、授权过滤后的路径和受控日志访问 |
| 结果未知 | 执行器已启动而响应丢失；页面 unknown，先查原 operation | 意图记录、查询结果、没有第二次执行的证明 |
| 崩溃恢复 | 本地已保存结果但投影未更新时崩溃；重放后状态可重建且不重执行 | 持久结果、重放记录、刷新后的同一 operation |
| 部分恢复 | 读取正常但创建订单失败；不得进入本例 restored | 两条关键路径的独立结果、未满足的 guard |
| 计时反例 | 输入重叠暂停 15 分钟与 10 分钟；有效时间应为 50，不能误报 45 达标 | 裁剪与合并结果、原输入和规则版本 |
| 拒绝与失败 | 修改授权后的目标版本或回滚前提不成立；拒绝执行或保留 failed | 原授权范围、实际拒绝原因、后续补救计划 |

这些是验收定义，不是已经运行的端到端结果。[合成检查](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/checks-h04-h05.py) 检查区间、图方向、授权版本、未知结果和关闭 guard 的局部性质；真实执行器、监测、权限中间件、浏览器恢复与负载均尚未接入。

若加入 AI，适合先让它整理已发生事实和提出待核实假设，不让它批准变更或自行宣布恢复。一个可执行的评估方案是准备 120 个脱敏合成事故：60 个用于开发提示词与评分器，60 个固定留出；留出集中 20 个只有临时恢复、20 个存在相互矛盾的观测、20 个证据完整且有明确根因。按事故类别固定分层，且同一故障模板的改写不跨开发集与留出集。

评估至少记录：错误宣布根因已消除的次数／40 个不能支持根因结论的案例；遗漏仍失败关键路径的次数／20 个矛盾观测案例；无证据新增事实数／全部生成的可核查事实数；需要工程师实质修正的输出数／60 份输出；不恰当拒答数／20 个证据完整案例。严重错误门槛设为零，其他阈值在使用前约定；即使 0/40 也只是这个留出集没有观察到，不证明生产环境零风险。证据缺失时应列出待检查项而非编造恢复证据。此方案尚未运行，不报告模型分数。

## 条件变化与迁移边界

**练习一：等待 change 的 20 分钟不允许暂停 SLA，仍有两个相互重叠的等待记录。** 短答案：先按规则筛选可暂停理由，再做区间并集；若这两条都是 Awaiting Change，则本例有效时间为 70 分钟，超出目标 25 分钟。保持的是“同一实际时刻最多计算一次”；失效边界是把 On Hold 状态直接当作暂停授权。检查相同时间线、只更换规则版本，结果应从 50 变为 70，并保留原因差异。

**练习二：回滚执行成功，但写订单探测失败；客户只确认查询正常。** 短答案：execution 可以 succeeded，change 进入 review 并记录未达业务目标，incident 保持 investigating 或部分恢复，不能 closed。保持的是局部执行证据与全局恢复判据分开；原先“一条探测即可证明服务”的假设已经失效。检查改变一条关键路径结果，就应阻止 restored 和 closed，而不篡改已经成功执行的历史记录。

`TR:H05:H06:resolution-acceptance` 可迁到支持工单的动作、解决与客户确认，但客户回复“谢谢”未必满足技术恢复判据，支持产品的自动关闭与重开语义也须另查。`TR:H05:V20:partial-completion` 可迁到多次现场 booking：一个子动作完成不足以关闭总责任；现场接收还可能需要签字、材料与实际到场证据，不能用监测曲线替代。`TR:H05:V18:evidence-state` 可迁移“处理状态不消灭未结义务”的原则到法律事项，但事故的自动关闭计时不能迁到 legal hold 的解除权限。演示可切换暂停理由、拖动重叠区间、删掉一条依赖边或让执行回执丢失；读者应能看到哪一项证据改变了哪个决定。

## 先选一条可验证的业务路径

接手陌生服务时，先选用户实际依赖的一条路径，明确失败与恢复的观测证据，再追到服务依赖、变更目标和批准人。IT 服务管理（IT service management，ITSM） 适合管理责任与状态，监测系统提供观测，发布/运行工具执行改变；选型要看这些边界能否关联同一个计划与尝试身份。继续研究现有 emergency 变更权限、执行器查询能力、数据兼容性和真实 SLA 日历；有仪表盘不等于这些条件已具备。让一条读路径恢复而写路径仍失败，检查执行成功是否仍能与事故未恢复并存，再用临时 workaround 验证关闭事故不会抹去 problem 责任。
