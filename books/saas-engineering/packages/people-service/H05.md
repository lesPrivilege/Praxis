# H05 · 事故恢复之后的未结工作

Incident 记录一次服务中断及其恢复责任；change 记录一次受控修改及其授权、执行与复核；problem 保存需要继续调查的原因。三者可以互相关联，但各有各的生命周期：回滚之后用户又能下单，incident 可以进入“已恢复，待确认”，回滚本身作为 change 要记下执行结果，导致故障的缺陷可能仍在 problem 里等待调查。本例覆盖恢复与关闭的依据、SLA 时钟、变更的观察范围和计划的重新批准。改变判断的是证据各自证明什么：执行器回执只证明某个计划版本已经执行，restored 要靠关键业务路径的恢复测量。

本例是一个内部订单服务：第 0 分钟出现错误，第 10 分钟有人接管，第 20—40 分钟有一段获准暂停计时的外部信息等待，第 45 分钟执行已授权的回滚，第 70 分钟服务通过恢复验证，第 90 分钟接收方确认关闭。计时从第 0 分钟开始，全天连续，恢复目标为 45 个有效分钟。

## 识题：重叠暂停、反向依赖与执行证据

本例有三道题：重叠的暂停先合并区间再扣除，变更影响沿反向依赖遍历，执行成功与业务恢复分别绑定版本。

| 识题线索 | 解法与演算结果 | 验算要点 | 待查规则 |
|---|---|---|---|
| 同一分钟被多条暂停记录覆盖 | 先合并区间再扣除；70 − 20 = 50，有效时间超目标 5 分钟 | 重排或重复暂停不改变结果；每段被排除的时间都能用计时规则解释 | 服务级别协议（service-level agreement，SLA）日历、可暂停理由和补录授权 |
| 改一个节点，要找依赖它的对象 | 沿反向依赖遍历；DB→Orders API/Invoice→Checkout | 按已登记的图可复算；删去一条边，漏项应可见 | 配置管理数据库（configuration management database，CMDB）边方向、图的新鲜度、关键业务探测 |
| 执行成功，业务仍可能失败 | 把计划授权、执行结果和恢复证据分别绑定版本 | 读路径成功但写路径失败时仍保留恢复责任 | 变更类型、计划 hash、执行器查询和回退兼容性 |

## 解法：恢复证据与关闭决定

恢复、执行与关闭由不同的角色凭不同证据决定，incident、change、execution、problem 与 SLA 计算各留一份依据。状态名只告诉界面该展示哪类工作，暂停与否、何时截止要由计时规则另行规定。

ServiceNow 的 Incident 生命周期文档区分 New、In Progress、On Hold、Resolved、Closed 与 Canceled，并列出等待 caller、change、problem、vendor 等 On Hold 原因（[Life cycle of an Incident](https://www.servicenow.com/docs/r/it-service-management/incident-management/c_IncidentManagementStateModel.html)）。状态名告诉界面该展示哪类工作，计时规则却不能从状态名推出来：“正在等待”是否让承诺的时钟暂停，取决于具体规则。

ServiceNow 另有一篇讲 resolution and closure 的文档：incident 可以凭 temporary workaround 或 permanent solution 进入 resolved，caller 可以审阅恢复结果，关闭也可以按配置自动发生（[Incident resolution and closure](https://www.servicenow.com/docs/r/it-service-management/incident-management/c_IncidentResolutionAndRecovery.html)）。所以恢复可以有可重复验证的事实依据，根因调查却仍未完成。生命周期概览的措辞更强，两篇文档的差异记在来源说明里，不替厂商抹平；本文按这篇更具体的文档解释。

本例要求值班工程师给出恢复证据，业务接收方确认关键操作可用，事故负责人决定关闭。工程师可以提出回滚计划，变更批准人决定是否允许执行，执行器只有在计划版本、授权和允许窗口一致时才接受请求。事故再严重，也没有人因此自动获得修改生产环境的权限。ServiceNow 的变更状态说明也区分 normal、standard 与 emergency：standard 预先授权，emergency 虽跳过 Assess，仍要经过 Authorize。本例只借用这层公开的状态关系。[State progression for change models](https://www.servicenow.com/docs/r/it-service-management/change-management/normal-standard-emergency-states.html)

| 对象与权威 | 本例状态 | 分别保留的依据 |
|---|---|---|
| Incident，事故协调服务 | new → investigating → waiting／investigating → restored → closed；恢复失败可回 investigating | 影响、责任人、恢复测量、接收确认、关闭理由 |
| Change，变更协调服务 | draft → authorized → running → review → closed；执行前可 cancelled | 计划 hash、批准人、窗口、目标版本、执行结果与复核 |
| Execution，外部执行器 | queued → running → succeeded／failed；通信中断为 unknown | operation ID、实际版本、日志摘要、回滚或补救结果 |
| Problem，问题负责人 | open → investigating → known → resolved | 原因假设、反证、修复验证；incident 关闭不推进它 |
| SLA calculation，计时服务 | provisional → confirmed；补录后可 revised | 事件时间、可暂停区间、规则版本、截止点 |

change 进入 closed 时仍要保留 outcome。本例一次回滚执行失败，后来由另一方案恢复服务，原变更可以在复核后以 failed 结果关闭；不能为了得到绿色列表，把失败改写为 succeeded。incident 的 cancelled 也一样：它可能只是一份归并掉的重复报告，不说明服务没有中断。

## 计划预览与执行回执

批准绑定同一计划版本，执行请求携带 operation 身份；超时只显示“待核对”，部署成功也要等真实的服务观测才能确认恢复。事故列表显示影响服务、责任人、最近观测时间与计时状态。详情页把故障时间线、关联变更、恢复证据和客户可见说明放在一起；原始告警是线索，不会自动授权变更。工程师点“提出回滚”后，预览显示计划目标、将受影响的服务、当前版本、回退方法和成功判据。批准人看到的必须是同一计划版本。若工程师随后把回滚目标从 r17 改为 r16，旧授权即失效，服务端要求重新批准；隐藏前端按钮代替不了这项检查。

“执行变更”提交 `change_id + plan_hash + expected_version + operation_id`。后端在事务中校验授权与窗口，写入执行意图和 outbox，然后返回可恢复的操作页面。请求超时时，页面显示“执行结果待核对”，可以查看原 operation；按钮不会变回一个不带 operation 身份的“再执行”。执行器按同一 operation 报告结果后，适配器保存外部结果，把 change 推进到 review。下一步“确认恢复”仍要有真实的服务观测，部署成功的响应代替不了用户路径验证。

例如执行器证明所有实例已回到 r17，订单却仍因数据库连接池耗尽而失败。这时 change 可以报告“回滚步骤成功，业务效果未达标”，incident 保持 investigating。调整连接池要另提一个受控计划，不能在原批准范围里不断追加动作。业务恢复以后，接收方确认创建订单与查询订单两条路径；若只读路径正常、写入仍失败，页面要显示部分恢复及未满足的判据。

拓扑中的 `authorizes` 是批准人或规则对执行服务的许可，`requests` 是服务向外部执行器提出动作，`emits` 与 `delivers` 是执行结果的交接；其中没有一条能单独证明恢复。恢复证据由已关联的 execution 与测量得出（`derived_from`）；incident 依赖这份恢复证据（`depends_on`），有了它才能转为 restored。服务依赖图另有 `depends_on` 关系，含义是运行前提，不是消息调用日志。这些关系在 [H05.json](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/H05.json) 里身份各不相同，分别表达“允许做”“已经做”和“确已恢复”。

实现可以用 Vue 或 React 做时间线与计划差异视图，Django 或 NestJS 提供命令接口，PostgreSQL 保存事故、变更、版本与操作账本。规模不大的列表与时间线用关系查询就够，依赖图也可以先用邻接表和递归查询求有限规模的影响范围；等关系规模、路径查询频率或更新方式真的成了瓶颈，再评估专用图存储。Prometheus 一类监测系统可以提供时间序列线索；设计还要主动探测关键业务路径，单一进程的存活指标证明不了订单成功。

恢复记录存测量区间、查询条件、结果摘要与受控日志引用。体积大的日志留在日志系统；令牌、完整请求体和客户资料不得复制到事故评论里。服务器发送事件（Server-Sent Events，SSE）适合由服务器单向推送状态，WebSocket 更适合多人协同编辑，但要处理连接恢复和顺序；实时连接一旦中断，页面要按 operation 重新读取权威状态。执行器能力按操作白名单和目标环境隔离，普通工单 API 不直接持有任意远程 shell 权限。

## 演算：重叠暂停的合并

本例有效恢复时间为 50 分钟，超出目标 5 分钟：两条暂停合并后只扣 20 分钟，直接相加会误报达标。SLA 时钟把承诺变成可检验的时间条件。它要知道截止事件是哪一个、哪些等待可以排除，以及迟到的信息能否修订结果。本例截止到恢复时间 70，而不是关闭时间 90；等待用户确认关闭的时间不再增加恢复时长。所有区间都用事件发生时间，接收时间只用来记录消息迟到。

假设两条获准暂停记录分别为 `[20,35)` 与 `[30,40)`，它们可能来自同一次等待的两个来源。直接相加得到 15 + 10 = 25 分钟，算出的有效时间是 `70 − 25 = 45`，看起来刚好达标；实际上第 30—35 分钟被扣了两次。合并后的暂停区间只有 `[20,40)`，长度 20，因此有效时间为 `70 − 20 = 50`，超过目标 5 分钟。这个错误会把超时报成达标，改变管理判断。

正确的算法先把每条暂停裁剪到事故计时区间 `[0,70)`，移除空区间，按起点排序，维护当前的合并区间。读到 `[20,35)` 时暂存；读到 `[30,40)`，因为 30 不晚于当前终点 35，把终点扩展到 40；没有新段后累计 20。n 条记录排序为 O(n log n)，扫描 O(n)，额外空间按保存方式为 O(n)，或排序后 O(1) 的扫描状态。朴素的逐分钟遍历，成本随时间跨度增长，按秒或跨月计时会更贵；区间法的成本只跟变更点的数量相关。

## 验算：补录暂停与真实日历

补录一段 `[60,80)` 时，先裁剪为 `[60,70)`，新增暂停 10 分钟，有效时间改为 40。前提是这段暂停确实获得规则授权，并且规则允许事后修订；理由是否属实，算法判断不了。为了防止有人靠改状态让报表达标，批准暂停、记录等待和修订 SLA 结果各自留下记录。真实 SLA 若按营业日、节假日或不同时区计时，还要把可计时日历与事故区间求交，本例的连续分钟公式不能直接部署。

## 演算：依赖图上的影响范围

变更 DB 时要观察 Orders API、Invoice 与 Checkout；这个集合沿反向依赖边求出，只覆盖已登记的依赖。依赖图规定：Checkout 依赖 Orders API，Orders API 依赖 DB，Invoice 依赖 DB，Search 依赖 Search Index。若变更目标是 DB，沿反向依赖边遍历，先得到 Orders API、Invoice，再得到 Checkout；Search 不在本次已知的影响集合里。广度优先或深度优先搜索在所访问子图上的成本为 O(V + E)，visited 集合避免环导致无限遍历。

如果按原方向从 DB 出发，可能一个消费者也找不到：结果取决于边的方向。另一个反例是 CMDB 漏掉 Invoice → DB：遍历算法完全正确，所得范围仍不完整。因此审批预览把集合标为“已登记依赖下的影响范围”，展示图版本和缺失信息，要求服务负责人补充关键观察点。共享同一个数据库，不说明某次变更引起了所有关联告警；相关性和可达性只能帮助安排检查，不能当作根因结论。

本例最少要求对 Checkout 和 Invoice 验证关键路径，Orders API 与 DB 提供诊断信号。若两个团队同时修改 DB，同一窗口里的两个计划即使各自获得授权，也可能互相破坏回退前提。调度先检查目标资源与时间窗冲突，冲突的计划由负责人串行安排，不求全局最优；只做拓扑排序处理不了锁、容量、值班人员和禁变窗口。

## 正常、失败与迟到的轨迹

每个结果只更新它所属的对象：恢复、接收与根因各有自己的时间点，丢失的回执先按原 operation 查询，迟到的失败消息只更新对应的 execution，不改写已经验证的恢复。

正常轨迹是：第 0 分钟建 incident，责任人接管；等待信息的记录与获准的暂停分别落库；提出并批准回滚计划；执行器报告实际版本 r17；第 70 分钟关键路径通过，保存恢复证据并停止本例的恢复时钟；第 90 分钟接收方确认后关闭 incident。change 在执行后完成复核，problem 继续调查 r18 为什么导致异常。三个时间点分别用来计算恢复耗时、接收耗时和根因处理耗时，彼此不能替代。

失败轨迹是：执行器已开始回滚，但响应丢失，页面显示 unknown。值班人员先按 operation 查询执行器，读取实际版本；若查询也不可用，就暂停自动尝试，人工确认当前运行状态。盲目重发可能让刚恢复的服务再次滚动重启。若执行器证明回滚失败，change 记录 failed，incident 保持 investigating，后续补救另建计划。回滚也可能有副作用，例如 r18 已写入 r17 不认识的数据；“恢复旧镜像”不能保证恢复旧的业务状态，计划要在执行前说明数据兼容性或接管条件。

结果通知可能迟到。第 72 分钟收到旧尝试的“执行失败”消息，不能把已由第二次计划验证恢复的 incident 直接退回失败；这条消息只更新对应的 execution，并检查这次失败是否还有未处理的影响。两个负责人并发关闭与重新打开事故时，按 incident version 做条件更新；旧的关闭请求要失败，让操作者看见新的失败证据。

下面的容量和延迟是验收假设，没有做负载测量。规模假设为 500 个服务节点、2000 条依赖边、每天 1 万条 incident、事故高峰每秒 300 条观察事件。关键动作接口的目标是 p95 小于 500 ms，告警写入和去重可以异步，业务命令仍保留事务版本。每个 incident 都是并发热点，大量相同的告警应聚合为计数与时间窗，保留原始观测索引；重复告警不能刷新事故开始时间。依赖影响集合可以按 tenant、graph version 和目标节点缓存，图一更新就换版本；缓存缺失时重新遍历，权限过滤不能靠客户端隐藏无权查看的服务。

## 验算：端到端验收情境

验收看每个情境留下的证据：同一 operation 不执行第二次，部分恢复进不了 restored，重叠暂停算出 50 而不是 45。下表是验收定义。[配套检查](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/checks-h04-h05.py) 只覆盖区间、图方向、授权版本、未知结果和关闭 guard 的局部性质；真实执行器、监测、权限中间件、浏览器恢复与负载都还没有接入。

| 情境 | 动作与预期 | 要观察的证据 |
|---|---|---|
| 正常路径 | 授权计划执行成功，关键路径恢复并获接收；incident closed，problem 仍 open | 计划、授权、实际版本、恢复探测、接收记录和分别展示的状态 |
| 重复 | 同一告警和执行回执各送两次；不得生成第二次变更执行，也不得重置事故开始时间 | 事件身份、operation 唯一键、原始首次时间 |
| 乱序 | 新恢复证据之后收到旧 execution 失败；只更新旧尝试并核查影响 | execution 身份、恢复依据、未盲目覆盖的 incident |
| 并发 | 同一版本同时批准和改计划；只有完全匹配的 plan hash 可执行 | 版本拒绝、重新审批要求、执行器接收记录 |
| 租户隔离 | 两租户都有 DB-1；图查询、工单与日志引用不得跨租户返回 | 服务端 scope、授权过滤后的路径和受控日志访问 |
| 结果未知 | 执行器已启动而响应丢失；页面 unknown，先查原 operation | 意图记录、查询结果、没有第二次执行的证明 |
| 崩溃恢复 | 本地已保存结果但投影未更新时崩溃；重放后状态可重建且不重执行 | 持久结果、重放记录、刷新后的同一 operation |
| 部分恢复 | 读取正常但创建订单失败；不得进入本例 restored | 两条关键路径的独立结果、未满足的 guard |
| 计时反例 | 输入重叠暂停 15 分钟与 10 分钟；有效时间应为 50，不能误报 45 达标 | 裁剪与合并结果、原输入和规则版本 |
| 拒绝与失败 | 修改授权后的目标版本或回滚前提不成立；拒绝执行或保留 failed | 原授权范围、实际拒绝原因、后续补救计划 |

若加入 AI，可以先让它整理已发生的事实、提出待核实的假设，但不让它批准变更或自行宣布恢复。下面的评估方案尚未运行，所以没有模型分数。准备 120 个脱敏的合成事故：60 个用于开发提示词与评分器，60 个固定留出；留出集中 20 个只有临时恢复、20 个存在相互矛盾的观测、20 个证据完整且有明确根因。按事故类别固定分层，同一故障模板的改写不跨开发集与留出集。

评估至少记录：错误宣布根因已消除的次数／40 个不能支持根因结论的案例；遗漏仍失败的关键路径的次数／20 个矛盾观测案例；无证据新增的事实数／全部生成的可核查事实数；需要工程师实质修正的输出数／60 份输出；不恰当的拒答数／20 个证据完整案例。严重错误的门槛设为零，其他阈值在使用前约定；即使 0/40，也只是这个留出集里没有观察到，不证明生产环境零风险。证据缺失时，输出应列出待检查项，不能编造恢复证据。

## 变式：条件变化与迁移

规则版本或一条关键路径的结果改变，结论随之改变：不允许暂停的等待让有效时间从 50 变为 70，写路径失败就挡住 restored 与 closed。

**练习一：等待 change 的 20 分钟不允许暂停 SLA，仍有两个相互重叠的等待记录。** 有效时间是多少？

简答：先按规则筛选可暂停的理由，再做区间并集；若这两条都是 Awaiting Change，本例有效时间为 70 分钟，超出目标 25 分钟。不变的是同一实际时刻最多计算一次；失效的是把 On Hold 状态直接当作暂停授权的做法。验算时保持时间线不变、只换规则版本，结果应从 50 变为 70，并记下两版规则的差别。

**练习二：回滚执行成功，但写订单探测失败；客户只确认查询正常。** incident 能否 closed？

简答：不能。execution 可以 succeeded，change 进入 review 并记录未达业务目标，incident 保持 investigating 或部分恢复。不变的是局部执行证据与全局恢复判据分开；原先“一条探测即可证明服务”的假设已经失效。验算时只改一条关键路径的结果，restored 和 closed 就应被挡住，已经成功执行的历史记录保持不变。

`TR:H05:H06:resolution-acceptance` 可迁到支持工单的动作、解决与客户确认，但客户回复“谢谢”未必满足技术恢复判据，支持产品的自动关闭与重开语义也要另查。`TR:H05:V20:partial-completion` 可迁到多次现场 booking：一个子动作完成不足以关闭总责任；现场接收还可能需要签字、材料与实际到场证据，监测曲线替代不了。`TR:H05:V18:evidence-state` 可把“处理状态不消灭未结义务”的原则迁到法律事项，但事故的自动关闭计时不能迁到 legal hold 的解除权限。演示可以切换暂停理由、拖动重叠区间、删掉一条依赖边或让执行回执丢失；读者应能看到哪一项证据改变了哪个决定。

## 进入服务运维的先查项

接手陌生服务时，先选用户实际依赖的一条路径，明确失败与恢复的观测证据，再追到服务依赖、变更目标和批准人。IT 服务管理（IT service management，ITSM）系统适合管理责任与状态，监测系统提供观测，发布/运行工具执行改变；选型要看这几类系统能否用同一个计划身份和尝试身份关联起来。接着查清现有的 emergency 变更权限、执行器查询能力、数据兼容性和真实 SLA 日历；有了仪表盘，这些条件也未必具备。再让一条读路径恢复、写路径仍失败，检查执行成功能否与事故未恢复并存，然后用临时 workaround 验证关闭事故不会抹去 problem 的责任。
