# V18 · 案件中的保全、审阅与交付

一个案件接收表可以在一分钟内填完，案件中的证据义务却不会因此完成。法务需要知道哪些材料必须保存，审阅者需要判断哪些材料可对外交付，财务需要知道哪家服务商做了什么、费用能否批准。这三种决定引用同一个 matter（案件事项），却不能共享一个“已完成”开关。本例接续本包共同模型：**请求建立责任，证据支持决定，接收关闭的是特定义务**。

以下是 synthetic 教学系统：企业收到一项合同争议，负责人建立案件 M1；两位 custodian（材料保管人）各有邮箱及附件，初次收集得到 6 个来源实例、4 份不同字节内容；外部审阅团队提交 1 张费用单。案件范围、保全解除、privilege（法律特权）与交付规则由本例的案件负责人确定，不从关键词或文件 hash 推出。具体法域、协议和专业标准必须由负责人员另行制定；教材只讨论如何让决定与其依据在软件中保持一致。

电子证据开示参考模型（Electronic Discovery Reference Model，EDRM） 2.0 把 Preservation 描述为防止相关材料改变或毁损，把 Review 描述为对相关性、特权等事项的评价，把 Production 描述为按相应格式交付。它明确说明该模型是概念视图，步骤可以重复和回返。因此，新增保管人可以重新触发收集，已经交过一批材料也不代表保全终止。[EDRM 当前模型](https://edrm.net/edrm-model/current/)。

## 先分开文件、来源和判断

文件库最容易出现的设计错误是“一份内容一行记录”。同一附件可能来自甲的邮箱，也来自乙转发的邮件；相同字节只说明内容层相同，不证明取得途径、邮件上下文、案件范围或专业判断相同。系统需要至少三层身份：blob 标识原始字节，occurrence 标识这份材料在某次收集中的出现，review decision 标识某案件、某实例或明确的审阅分组上的判断及版本。跨租户绝不共用可查询的内容目录；即使内部复用物理存储，也不能通过“已经存在”泄露别人的材料。

Relativity 的 Processing profiles 文档确实区分 Global 与 Custodial 去重，并保留 All Custodians、路径等去重元数据。其处理配置不等于本例设计，尤其文档对父子文件的处理另有规则。这里借它说明“减少重复审阅”和“保留来源关系”是两个需求，不声称 Relativity 按本例算法认定特权。[Deduplication settings](https://help.relativity.com/RelativityaiR/Content/Relativity/Processing/Processing_profiles.htm#Deduplicationsettings)。

| 对象 | 权威与关联 | 允许改变的证据 |
|---|---|---|
| Matter M1 | 案件服务保存负责人、范围与版本；外部律所只能访问获分配范围 | 负责人接收；范围变更形成新版本 |
| Hold H1 | 保全服务保存指令、目标位置和逐位置回执；源系统负责实际保全状态 | 有权限的负责人签发；每个目标确认后才算本例的 active |
| Collection C1 / occurrence O1…O6 | 收集清单保存来源、保管人、取得时间、内容校验及父子关系 | 收集任务完成且数量、错误、hash 核对通过 |
| Review decision D | 审阅服务保存负责人批准的相关性、特权、遮盖及理由 | 适用协议版本、材料版本和审阅权限一致 |
| Production P1 | 交付服务保存冻结清单、呈现版本、编号和接收证据 | 清单内每项已批准；接收回执才使 sent 变成 received |
| Spend invoice S1 | 费用服务批准费用，账务系统确认实际支付 | 服务项、费率与证据通过核对；批准不代表已付 |

Hold 的 `draft → applying → active → release_requested → released` 与案件的 `intake → accepted → active → closed` 并行存在。若一个源位置失败，hold 进入 `partial`，负责人能看到成功位置和未覆盖位置；重试仅针对失败目标。正文中的“active”是本例全部目标确认的规则，不是任何厂商通用状态。签收保全通知的人也不能替源系统确认保全已生效。一个 hold 解除，只取消这个 hold 的责任；仍有 H2 引用同一材料时，不得把数据交给清除任务。

审阅决定可以是 `unreviewed → approved_produce / approved_withhold / out_of_scope / needs_resolution`，已有决定的修正创建新版本并把旧版本标记为 `superseded`。文件完整性校验、相关性、特权和是否批准交付是分开的字段；把它们合成一个“审核通过”会使运维人员无法知道究竟缺什么。Production 还要独立经历 `draft → frozen → sending → received`，超时保持 `unknown`；冻结以后修改材料或遮盖必须形成新清单，不覆盖已经发送的记录。

## 一次“冻结交付”怎样走过系统

工作台按案件列出范围、hold 覆盖、未处理文件和待解决的审阅冲突。审阅详情将原始文件、来源上下文与可交付呈现分栏，并允许只看分配给自己的材料。外部审阅者不能靠改 URL 读到同案其他工作组；权限检查同时覆盖元数据 API、文件下载和检索结果。点击“批准交付”时，页面提交的是材料版本、决定版本和理由，不直接把原始文件传给接收方。

冻结预览显示“4 个不同内容、6 个来源实例、2 个拟交付实例、1 项待解决”，而不是只显示一个总文件数。用户点击“冻结并提交”后，服务端读取权威版本，验证范围与审阅决定，将生产批次、清单和 outbox 写入同一事务。HTTP 成功仅表示任务已保存。worker 按清单生成呈现、计算呈现 hash，核对页数、编号与附件，然后向接收端请求交付。接收端回执进入 inbox，交付服务核对批次身份和清单 hash，工作台才显示“接收已确认”。JSON 中的 `commands`、`requests`、`delivers` 分别表达请求、外部调用和通知传递，任何一条都不是现金或证据所有权转移。

前端可用 React/TypeScript 配合虚拟列表承载大量材料，PDF.js 显示经过隔离处理的预览；预览不能执行附件中的脚本。小团队也可用 Django 服务端页面及分页，减少前后端状态分裂，代价是复杂多窗审阅交互需要补充客户端代码。后端可选 Django 或 FastAPI，PostgreSQL 保存关系、版本和操作记录，对象存储保存不可覆写的原始件与每次呈现。仅用对象存储标签表示法律判断会失去事务性；只把大文件放数据库又会扩大备份与查询压力。全文检索可先用 PostgreSQL 的文本检索，语料与并发增长后再考虑 OpenSearch；检索索引是可重建副本，冻结清单必须回读权威记录。这些是教学选型，未声称 EDRM、Wolters Kluwer 或 Relativity 使用该栈。

Microsoft Purview 当前文档把 case 作为组织 searches、holds、review sets 的单元，并区分源位置与复制到 review set 的内容。这支持“保全责任与审阅副本分离”的产品参照；本例不实现其 API 或许可模型。[Learn about eDiscovery](https://learn.microsoft.com/en-us/purview/edisc)。对接真实源系统时，要逐一确认保全适用位置、状态查询与失效语义，不能用“文件已下载”代替源端保全。

## 手算：去重节省的是存储，不是责任

以下 6 个实例都在租户 T1、案件 M1，hash 字母是便于演算的代号；真实实现需记录算法、完整摘要和字节长度，不能使用截短显示值作为唯一依据。

| 实例 | 保管人 / 来源上下文 | 内容代号 | 本例审阅决定 |
|---|---|---|---|
| O1 | 甲 / 邮件附件 | A | produce |
| O2 | 乙 / 转发附件 | A | needs_resolution |
| O3 | 甲 / 文件目录 | B | withhold |
| O4 | 乙 / 邮件附件 | C | produce |
| O5 | 乙 / 另一封邮件附件 | B | withhold |
| O6 | 甲 / 文件目录 | D | out_of_scope |

逐个实例扫描，以 `(tenant, digest, byte_length)` 查内容桶，同时保留完整 occurrence 表：A→{O1,O2}，B→{O3,O5}，C→{O4}，D→{O6}。得到 4 个内容桶、6 个实例。交付判断仍在 occurrence/决定层做，所以本例 P1 只能纳入 O1、O4；O2 的上下文未解决，不能继承 O1 的 produce。这个差异是合成审阅政策，不代表内容相同就实际具有不同法律特权。它证明 hash 无法提供作该判断所需的上下文。

逐对比较 n 个文件，最坏要做 O(n²) 次比较；hash 建桶需要读取总字节 B，预期 O(B+n)，额外元数据 O(n)，碰撞桶需要按长度与实际字节复核。比对时间降低，并未降低应保存的实例数量。一个故意错误的实现会先按 hash 取第一份，再只看第一份决定：它“去掉”了 O2，也删除了尚未解决的问题。另一个错误实现把 blob A 的权限改成 O1 的权限，使乙的来源信息通过共享链接泄露。正确输出要同时给出内容数、实例数、允许交付实例数和未解决数量。

保全解除可用 `ALG:graph-paths`：从 blob 反向找到所有 occurrence，再找到引用它们的 active hold 和独立保留规则。只有这些阻止条件全部解除、且有明确处置授权，才进入本例的清除候选。遍历一个受影响子图为 O(V+E)；“M1 closed”不在这个公式里自动等于可删除。如果一个共享附件还属于 M2，关闭 M1 只消掉一条边。图遍历必须在服务端的授权边界内执行，对无权用户只返回“仍有其他保留义务”，不能透露另一个案件的名称。

## 正常路径与失败路径

正常路径从负责人接受 M1 开始：H1 的各目标分别确认，C1 留下 6 个来源实例及 4 个内容桶，审阅者记录 O2 尚待补充的上下文，O2 继续保持 needs_resolution 并排除本批；负责人冻结只包含 O1、O4 的 P1，接收方按清单确认。外部律所随后提交 S1；费用审核核对案件、服务期间和费率，批准后才向账务系统请求支付。Wolters Kluwer ELM Solutions 的公开页面将 matter management、legal spend 和 bill review 列为其业务能力；这只支持这些能力的存在，不证明某笔费用或某次 production 已获接收。[Enterprise Legal Management](https://www.wolterskluwer.com/en/solutions/enterprise-legal-management)。

失败路径选择一个具体缝隙：P1 的压缩包已上传，接收响应丢失。若操作员再点一次就生成 P2，接收方可能拿到两组不同编号。合成设计使用稳定 `(tenant, matter, production_id, manifest_hash)` 作为重试身份；支持按该身份查询的接收端先核对，不支持查询时保留 `unknown` 交给负责人确认，不自称“失败可重发”。恢复后若发现已接收，再补写本地回执；若确认未接收，才能继续同一尝试。已对外交付的错误材料也不能靠本地删除回滚，必须建立纠正批次与接收方处置记录，专业负责人决定后续行动。

另一个危险窗口在冻结与发送之间：审阅决定撤回了，旧 worker 仍持有 approved 的副本。本例让每个批次带 `decision_epoch`，并把“核对 epoch、把 frozen 改成 sending、写入唯一发送认领”放在同一本地事务中；撤回也锁住同一批次与决定版本。这给两项本地动作一个明确顺序：撤回先提交，认领就失败，批次失效；认领先提交，后来的撤回只设置“可能已发，须核对/纠正”标记，即使网络请求尚未返回也不能保证拦住它。worker 可以在发现标记后尝试停发，但已经离开本地事务的外部请求不能被数据库回滚。此时保存原发送/unknown 状态与处置标记，先查接收端，再决定停止或纠正；已接收则显示“已发出，待处置”，不能改成未发送。单独一次发送前检查不能消除检查与动作之间的竞态。

容量假设为 20 个租户、每租户 50 个活跃案件，单个大案件 100 万个实例、平均原始件 200 KB、50 个审阅者并发。存储约 200 GB/大案件，未含呈现、索引与副本。待测目标是页大小 100 的材料列表 p95 < 800 ms、审阅写入 p95 < 500 ms，分别测冷索引和热缓存；这不是运行结果。按案件做批次配额，避免大案 光学字符识别（optical character recognition，OCR） 队列阻塞小案保全核对；OCR 任务失败不伪装成“无命中”。查询缓存 key 包含租户、案件、权限版本、过滤器和索引版本，撤权使下载授权立即失效，不能等列表缓存过期。原始件和清单分别备份；恢复演练必须重新核对清单对应字节，而不只验证 SQL 行数。

## 验收与 AI 的责任边界

AI 可以建议优先审阅顺序和疑似敏感片段，本例禁止模型直接批准交付、解除 hold 或认定特权。评估计划冻结 200 个训练/校准实例和另 100 个留出实例，按案件及邮件家族切分，防止同一附件同时出现在两边。假设留出标签中 20 个必须暂缓，模型拦截 18 个、漏掉 2 个，并误拦另外 10 个，则暂缓召回率为 18/20=90%，拦截精确率为 18/28≈64.3%；总体正确数 88/100 会掩盖 2 次危险漏放。数字是演算，不是已执行模型结果。记录每案漏判、语言/文件类型、无法读取比例、人工修正数及模型版本；任一真实暂缓材料被自动加入清单即使总体准确率高也拒绝上线。无法读取、上下文缺失、模型依据与原文矛盾时转人工。

| 检查 | 操作与可观察证据 |
|---|---|
| happy_path | 6 个实例完成上述流程；UI、清单、对象库分别显示 6/4/2，接收回执匹配 P1 hash；费用批准和付款状态分列 |
| duplicate | 同一收集事件和接收回执各投递两次；inbox 可留接收记录，但 occurrence 与 P1 接收效果不重复 |
| out_of_order | 先处理审阅 v3，再收到 v2；冻结仍用 v3，旧决定进入历史，不能回退当前审批 |
| concurrency | 冻结与撤回审批竞争；撤回先提交则认领失败；认领先提交则标记可能已发并核对，必要时纠正，不承诺网络停发 |
| tenant_isolation | 两租户上传相同字节；检索、下载、缓存命中和“已存在”反馈均不透露另一租户信息 |
| unknown_outcome | 接收端已受理但调用超时；同一 P1 保持 unknown，核对后补回执，没有第二批编号 |
| recovery | 清单已保存、worker 未标记完成时崩溃；恢复重放相同清单，hold 解除任务仍检查其他引用 |
| 领域反例 | 只用 hash 合并 O1/O2 或关闭 M1 就删除 M2 引用内容；合成检查必须抓住这两种错误 |

这些定义覆盖未来端到端实现需要取证的边界；当前的标准库检查只执行身份、选择、版本和保留条件等合成不变量。它没有验证真实审阅质量、文件解析安全、provider API、网络或 UI。

## 改变前提后重新推理

**练习一：从 M1 扩展到 M2。** A 的字节没变，但 M2 的负责人只允许另一组人访问，能否直接复制 M1 的审阅结论？简答：blob 可复用的前提是内部授权安全，结论必须在 M2 的范围、协议和专业权限下确认。不变量是每个交付决定都有案件与依据版本；失效条件是把 hash 当决定主键。检查让同一 hash 在两个案件分别为 produce 和 needs_resolution，确认冻结 M2 仍被阻止。这一机制可迁到 V17 的成绩更正：成绩值相同不等于修订依据相同；成绩没有文件保全和特权语义，不能照搬解除规则。`TR:V18:V17:identity-and-decision`。

**练习二：把 H1 解除，案件已经关闭，但 H2 仍有效。** 是否可以删除共同内容？简答：不可以，保留依赖图仍有活动边。保持“不丢失仍被有效义务引用的数据”；失效条件是只有一个 `is_on_hold` 布尔值且解除 H1 把它清零。检查先解除 H1，删除候选仍为空，再解除 H2 并满足独立保留规则才出现候选。它可以迁到 H04 的离职后数据保留，但员工停用账号只是访问决定，不是数据处置授权。`TR:V18:H04:release-versus-retention`。

**练习三：P1 已接收，S1 费用被驳回。** 能否把 production 回退到未完成？简答：不能。交付义务和费用争议分别存在；新增费用异议与补正单，保留接收事实。检查账单状态变动不得改写 P1 的清单与回执。这可接到 V19 的“批准工时、开票、收款分别核对”，但案件特权判断不能被服务费用审批替代。`TR:V18:V19:delivery-and-spend`。

演示可让读者切换“按内容 / 按实例”计数，改变 O2 的审阅结论、撤回决定或切断接收响应，观察哪些对象可以前进。HTML 与动效形式留给后续实现，始终保留未解决项与合成假设。结构见 [V18.json](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/V18.json)，事实与推理边界见 [evidence.json](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/evidence.json)。

## 从保全目标和交付清单倒推能力

进入新案件流程时，先由有权负责人明确保全目标、专业判断依据、接收协议和数据处置权限，工程人员负责把这些决定接到可查询的对象。源系统保全、eDiscovery 收集审阅、production 交付与 ELM 费用管理分别解决不同责任；一个统一入口不必意味着单一产品承担全部权威。下一步查具体源位置的保全覆盖、附件/邮件家族处理、审阅权限和接收端批次查询能力，并让负责人确认未决材料能否排除在某批交付外。用本例6个实例/4个内容/2个交付对象，加一项认领后撤回，核对数量、来源关系、未决义务和已发出事实都未被隐藏。
