# V18 · 案件中的保全、审阅与交付

案件接收表一分钟就能填完，案件里的证据义务却不会随之完成：保存、对外交付和服务商费用由法务、审阅者和财务分别决定，三种决定引用同一个 matter（案件事项），却不能共享一个“已完成”开关。本例把原始字节（blob）、收集中的出现（occurrence）与案件下的审阅决定分成三层身份，覆盖保全解除和交付批次。字节相同只能共用存储，不能共用判断；已经发出的批次只能核对和纠正，删不回来。本例沿用本包的共同模型：**请求产生责任，证据支持决定，接收只关闭特定义务**。

一家企业收到一项合同争议，负责人立案 M1；两位 custodian（材料保管人）各有邮箱及附件，初次收集得到 6 个来源实例、4 份不同字节内容；外部审阅团队提交 1 张费用单。案件范围、保全解除、privilege（法律特权）与交付规则由本例的案件负责人确定，不从关键词或文件 hash 推出。具体法域、协议和专业标准由负责人员另行制定；软件要做的，是让每个决定与它的依据保持一致。

电子证据开示参考模型（Electronic Discovery Reference Model，EDRM）2.0 中，Preservation 指防止相关材料改变或毁损，Review 指对相关性、特权等事项的评价，Production 指按相应格式交付。EDRM 说明这个模型是概念视图，步骤可以重复、回返（[EDRM 当前模型](https://edrm.net/edrm-model/current/)）。所以新增保管人可以重新触发收集；交过一批材料，保全也并未终止。

## 识题：同一内容、多重义务与撤回

本例有三道题：字节相同而来路、判断不同时，分开 blob、occurrence 与 decision；解除一项保全时，沿依赖图检查所有阻止条件；准备发送时遇到撤回，让认领与撤回在本地串行。

| 识题线索 | 首选解法与演算 | 验算要点 | 后续查证 |
|---|---|---|---|
| 字节相同，来路与判断不同 | 分开 blob、occurrence 与 decision；6 实例→4 内容桶→2 拟交付实例 | 相同 hash 不覆盖 O2 的未决判断；实例、内容与交付三种数量分别核对 | 去重 scope、邮件家族、审阅协议和来源字段 |
| 解除一项保全，材料仍被其他义务引用 | 沿保全与保留依赖图检查所有阻止条件 | 解除 H1 而 H2 有效时，删除候选为空 | 源端保全覆盖、独立保留规则和处置授权 |
| 准备发送时，有人撤回决定 | 发送认领与撤回在本地串行；请求发出后按原批次核对 | 撤回先提交，认领失败；认领先提交，标记“可能已发” | 接收端批次查询、纠正交付和版本回执能力 |

## 解法：内容、来源与判断的三层身份

系统至少需要三层身份：blob 标识原始字节，occurrence 标识材料在某次收集里的一次出现，review decision 标识针对某案件、某实例或某个明确审阅分组的判断及其版本。文件库最容易出现的设计错误是“一份内容一行记录”。同一附件可能来自甲的邮箱，也可能来自乙转发的邮件；相同字节只说明内容层相同，不证明取得途径、邮件上下文、案件范围或专业判断相同。跨租户绝不共用可查询的内容目录；即使内部复用物理存储，也不能借“已经存在”的反馈泄露别人的材料。

Relativity 的 Processing profiles 文档区分 Global 与 Custodial 去重，并保留 All Custodians、路径等去重元数据；文档对父子文件另有处理规则，与本例设计不同（[Deduplication settings](https://help.relativity.com/RelativityaiR/Content/Relativity/Processing/Processing_profiles.htm#Deduplicationsettings)）。可见“减少重复审阅”和“保留来源关系”是两个需求。

| 对象 | 权威与关系 | 推进状态的依据 |
|---|---|---|
| Matter M1 | 案件服务保存负责人、范围与版本；外部律所只能访问分配给它的范围 | 负责人接受案件；范围变更生成新版本 |
| Hold H1 | 保全服务保存指令、目标位置和逐位置回执；源系统负责实际保全状态 | 有权限的负责人签发；全部目标确认后，才进入本例的 active |
| Collection C1 / occurrence O1…O6 | 收集清单保存来源、保管人、取得时间、内容校验及父子关系 | 收集任务完成，数量、错误与 hash 核对通过 |
| Review decision D | 审阅服务保存负责人批准的相关性、特权、遮盖及理由 | 适用的协议版本、材料版本和审阅权限一致 |
| Production P1 | 交付服务保存冻结清单、呈现版本、编号和接收证据 | 清单内每项已批准；接收回执核对后，才从 sending 进入 received |
| Spend invoice S1 | 费用服务批准费用，账务系统确认实际支付 | 服务项、费率与证据通过核对；批准之后，付款仍待账务确认 |

Hold 的 `draft → applying → active → release_requested → released` 与案件的 `intake → accepted → active → closed` 并行。若一个源位置失败，hold 进入 `partial`，负责人能看到成功位置和未覆盖位置；只重试失败的目标。这里的 active 是本例的规则：全部目标确认后才进入。签收保全通知的人也不能替源系统确认保全已生效。一个 hold 解除，只取消这个 hold 的责任；只要 H2 仍引用同一材料，数据就不能交给清除任务。

审阅决定按 `unreviewed → approved_produce / approved_withhold / out_of_scope / needs_resolution` 流转；修正已有决定时创建新版本，旧版本标为 `superseded`。文件完整性校验、相关性、特权和是否批准交付是分开的字段；合成一个“审核通过”，运维人员就看不出究竟缺了哪一项。Production 另走 `draft → frozen → sending → received`，超时停在 `unknown`；冻结以后修改材料或遮盖，要生成新清单，已经发送的记录不被覆盖。

## 冻结交付的提交路径

交付以冻结清单为单位提交：HTTP 成功只说明任务已经保存，接收回执核对过批次身份与清单 hash，才算接收。工作台按案件列出范围、hold 覆盖、未处理文件和待解决的审阅冲突。审阅详情把原始文件、来源上下文与可交付呈现分栏显示，审阅者可以只看分配给自己的材料。外部审阅者不能靠改 URL 读到同案其他工作组的材料；权限检查同时覆盖元数据 API、文件下载和检索结果。点击“批准交付”时，页面提交的是材料版本、决定版本和理由，不直接把原始文件传给接收方。

冻结预览显示“4 个不同内容、6 个来源实例、2 个拟交付实例、1 项待解决”，不只给一个总文件数。用户点击“冻结并提交”后，服务端读取权威版本，验证范围与审阅决定，把生产批次、清单和 outbox 写入同一事务。HTTP 返回成功，只说明任务已经保存。worker 按清单生成呈现、计算呈现 hash，核对页数、编号与附件，然后向接收端请求交付。接收端回执进入 inbox，交付服务核对批次身份和清单 hash 之后，工作台才显示“接收已确认”。

前端可以用 React/TypeScript 配合虚拟列表显示大量材料，用 PDF.js 显示经过隔离处理的预览；预览不能执行附件中的脚本。小团队也可以用 Django 服务端页面加分页，免得前后端各持一份状态，代价是多窗审阅这类复杂交互要另写客户端代码。后端可选 Django 或 FastAPI，PostgreSQL 保存关系、版本和操作记录，对象存储保存不可覆写的原始件与每次呈现。只用对象存储标签记录法律判断，会失去事务性；把大文件也放进数据库，又会加大备份与查询的压力。全文检索可以先用 PostgreSQL 的文本检索，语料与并发增长后再考虑 OpenSearch；检索索引是可重建的副本，冻结清单必须回读权威记录。

Microsoft Purview 当前文档把 case 作为组织 searches、holds、review sets 的单元，并区分源位置与复制到 review set 的内容（[Learn about eDiscovery](https://learn.microsoft.com/en-us/purview/edisc)）。可见真实产品也把保全责任与审阅副本分开；本例不实现它的 API 与许可模型。对接真实源系统时，要逐一确认保全适用的位置、状态查询与失效语义，不能用“文件已下载”代替源端保全。

## 演算：内容去重与保全解除

6 个实例落入 4 个内容桶，P1 只能纳入 O1、O4；解除 H1 之后，只要还有 hold 或独立保留规则引用材料，清除候选就为空。下表 6 个实例都属于租户 T1、案件 M1，hash 用字母代号便于演算；真实实现要记录算法、完整摘要和字节长度，截短的显示值不能作唯一依据。

| 实例 | 保管人 / 来源上下文 | 内容代号 | 本例审阅决定 |
|---|---|---|---|
| O1 | 甲 / 邮件附件 | A | produce |
| O2 | 乙 / 转发附件 | A | needs_resolution |
| O3 | 甲 / 文件目录 | B | withhold |
| O4 | 乙 / 邮件附件 | C | produce |
| O5 | 乙 / 另一封邮件附件 | B | withhold |
| O6 | 甲 / 文件目录 | D | out_of_scope |

逐个实例扫描，以 `(tenant, digest, byte_length)` 查内容桶，同时保留完整的 occurrence 表：A→{O1,O2}，B→{O3,O5}，C→{O4}，D→{O6}，得到 4 个内容桶、6 个实例。交付判断仍在 occurrence 与决定层上做，所以本例 P1 只能纳入 O1、O4；O2 的上下文尚未解决，不能沿用 O1 的 produce。O1 与 O2 字节相同、处理不同，是本例审阅政策的设定；它说明 hash 本身不带作这种判断所需的上下文。

逐对比较 n 个文件，最坏要做 O(n²) 次比较；按 hash 分桶要读完总字节 B，预期 O(B+n)，另占 O(n) 元数据；同一桶内若有碰撞，按长度与实际字节复核。去重缩短的是比对时间，应保存的实例数量不变。一个故意写错的实现先按 hash 取第一份，再只看第一份作决定：它“去掉”了 O2，也删掉了尚未解决的问题。另一个错误实现把 blob A 的权限改成 O1 的权限，乙的来源信息就通过共享链接泄露出去。正确输出要同时给出内容数、实例数、允许交付的实例数和未解决的数量。

保全解除可用 `ALG:graph-paths`：从 blob 反向找到所有 occurrence，再找到引用它们的 active hold 和独立保留规则。只有这些阻止条件全部解除，且有明确的处置授权，材料才进入本例的清除候选。遍历受影响的子图需要 O(V+E)；M1 进入 closed，材料也不会因此自动可删。如果一个共享附件还属于 M2，关闭 M1 只去掉一条边。图遍历必须在服务端的授权边界内执行，对无权用户只返回“仍有其他保留义务”，不透露另一个案件的名称。

## 正常路径与失败路径

接收响应丢失时，按稳定的批次身份核对，不生成第二批编号；冻结与发送之间的撤回由本地事务定出先后，已经离开本地的请求只能核对或纠正。

正常路径从负责人接受 M1 开始：H1 的各目标分别确认，C1 收集到 6 个来源实例、4 个内容桶，审阅者记下 O2 尚待补充的上下文，O2 保持 needs_resolution，不进入本批；负责人冻结只包含 O1、O4 的 P1，接收方按清单确认。外部律所随后提交 S1；费用审核核对案件、服务期间和费率，批准后才向账务系统请求支付。Wolters Kluwer ELM Solutions 的公开页面把 matter management、legal spend 和 bill review 列为业务能力，可作费用管理一侧的产品参照（[Enterprise Legal Management](https://www.wolterskluwer.com/en/solutions/enterprise-legal-management)）。

失败路径：P1 的压缩包已上传，接收响应丢失。若操作员再点一次就生成 P2，接收方可能拿到两组不同编号。本例以稳定的 `(tenant, matter, production_id, manifest_hash)` 作重试身份。接收端支持按这个身份查询时，先查询核对；不支持时保持 `unknown`，交负责人确认，界面不显示“失败，可重发”。恢复后若发现已接收，再补写本地回执；确认未接收，才能继续同一次尝试。已对外交付的错误材料，也不能靠本地删除回滚：要另立纠正批次，记录接收方的处置，后续行动由专业负责人决定。

另一个危险窗口在冻结与发送之间：审阅决定撤回了，旧 worker 仍持有 approved 的副本。只在发送前检查一次，检查与动作之间仍有竞态，所以本例让每个批次带 `decision_epoch`，并把“核对 epoch、把 frozen 改成 sending、写入唯一发送认领”放在同一个本地事务里；撤回也锁住同一批次与决定版本。两项本地动作于是有了确定的先后：撤回先提交，认领就失败，批次失效；认领先提交，后来的撤回只设置“可能已发，须核对/纠正”标记，这时网络请求即使还没返回，也不一定拦得下。worker 发现标记后可以尝试停发，但已经离开本地事务的外部请求，数据库回滚不了。此时保存原发送/unknown 状态与处置标记，先查接收端，再决定停止或纠正；已接收的批次显示“已发出，待处置”，不能改成未发送。

容量假设为 20 个租户、每租户 50 个活跃案件，单个大案件 100 万个实例、平均原始件 200 KB、50 个审阅者并发。存储约 200 GB/大案件，未含呈现、索引与副本。待测目标是页大小 100 的材料列表 p95 < 800 ms、审阅写入 p95 < 500 ms，冷索引与热缓存分别测。按案件设批次配额，以免大案件的光学字符识别（optical character recognition，OCR）队列堵住小案件的保全核对；OCR 任务失败要如实显示，不能显示成“无命中”。查询缓存 key 包含租户、案件、权限版本、过滤器和索引版本；撤权立即让下载授权失效，不等列表缓存过期。原始件和清单分别备份；恢复演练要重新核对清单对应的字节，不只核对 SQL 行数。

## 验算：AI 边界与验收检查

AI 可以建议审阅的先后和疑似敏感的片段，但本例不允许模型直接批准交付、解除 hold 或认定特权。评估计划冻结 200 个训练/校准实例和另 100 个留出实例，按案件及邮件家族切分，防止同一附件同时出现在两边。假设留出标签中 20 个必须暂缓，模型拦截 18 个、漏掉 2 个，并误拦另外 10 个，则暂缓召回率为 18/20=90%，拦截精确率为 18/28≈64.3%；总体正确数 88/100 会掩盖 2 次危险漏放。记录每案漏判、语言/文件类型、无法读取比例、人工修正数及模型版本；只要有一份真实应暂缓的材料被自动加入清单，总体准确率再高也不能上线。无法读取、上下文缺失、模型依据与原文矛盾时转人工。

| 检查 | 构造输入与预期业务结果 | 应观察的证据 |
|---|---|---|
| 正常路径 | 6 个实例走完上述流程 | UI 显示 6 个实例、4 份内容、2 个拟交付实例，分别与 occurrence 表、对象库和清单一致；接收回执匹配 P1 hash；费用批准和付款状态分列 |
| 重复 | 同一收集事件和接收回执各投递两次 | inbox 可以记两条，occurrence 与 P1 的接收只生效一次 |
| 乱序 | 先处理审阅 v3，再收到 v2 | 冻结仍用 v3，旧决定进入历史，不回退当前审批 |
| 并发 | 冻结与撤回审批竞争 | 撤回先提交则认领失败；认领先提交则标记可能已发并核对，必要时纠正，不承诺网络停发 |
| 租户隔离 | 两租户上传相同字节 | 检索、下载、缓存命中和“已存在”反馈都不透露另一租户的信息 |
| 未知结果 | 接收端已受理但调用超时 | 同一 P1 保持 unknown，核对后补回执，没有第二批编号 |
| 恢复 | 清单已保存、worker 未标记完成时崩溃 | 恢复时重放相同清单，hold 解除任务仍检查其他引用 |
| 领域反例 | 只用 hash 合并 O1/O2，或关闭 M1 就删除 M2 引用的内容 | 检查必须抓住这两种错误 |

上表是将来端到端实现要取证的检查；目前的标准库检查只执行身份、选择、版本和保留条件这些不变量，真实审阅质量、文件解析安全、provider API、网络和 UI 都没有验证。

## 变式：条件变化与迁移

扩展到新案件、解除部分保全、费用被驳回，都改不了已有的判断或交付事实：审阅决定在新案件下重新确认，能否清除看依赖图上是否还有活动边，费用争议另开单据。

**练习一：从 M1 扩展到 M2。** A 的字节没变，但 M2 的负责人只允许另一组人访问，能否直接复制 M1 的审阅结论？

简答：不能。blob 可以在内部授权安全的前提下复用，审阅结论要在 M2 的范围、协议和专业权限下重新确认。不变量是每个交付决定都有案件与依据版本；失效条件是把 hash 当决定主键。检查时让同一 hash 在两个案件里分别为 produce 和 needs_resolution，确认 M2 的冻结仍被拦下。这一机制可以迁到 V17 的成绩更正：成绩值相同，修订依据未必相同；成绩没有文件保全和特权语义，解除规则不能照搬。`TR:V18:V17:identity-and-decision`。

**练习二：H1 解除、案件关闭，H2 仍有效。** 是否可以删除共同内容？

简答：不可以，保留依赖图仍有活动边。不变量是“不丢失仍被有效义务引用的数据”；失效条件是只有一个 `is_on_hold` 布尔值，解除 H1 就把它清零。检查时先解除 H1，删除候选仍为空；再解除 H2，且满足独立保留规则后，才出现候选。它可以迁到 H04 的离职后数据保留，但员工停用账号只是访问决定，不是数据处置授权。`TR:V18:H04:release-versus-retention`。

**练习三：P1 已接收，S1 费用被驳回。** 能否把 production 回退到未完成？

简答：不能。交付义务和费用争议各自独立：另开费用异议与补正单，接收事实不动。检查时让账单状态变化，P1 的清单与回执保持不变。这可以接到 V19 中批准工时、开票、收款分别核对的做法，但案件特权判断不能由服务费用审批代替。`TR:V18:V19:delivery-and-spend`。

## 进入法律案件管理的先查项

进入新的案件流程时，先由有权的负责人定下保全目标、专业判断依据、接收协议和数据处置权限，工程人员再把这些决定落到可查询的对象上。源系统保全、eDiscovery 收集审阅、production 交付与 ELM 费用管理各管一种责任；入口可以统一，权威不必集中在一个产品里。下一步查具体源位置的保全覆盖、附件/邮件家族处理、审阅权限和接收端批次查询能力，并请负责人确认未决材料能否排除在某批交付之外。最后用本例的 6 个实例、4 份内容、2 个拟交付实例，加一次认领后的撤回，核对数量、来源关系、未决义务和已发出的事实都还看得见。
