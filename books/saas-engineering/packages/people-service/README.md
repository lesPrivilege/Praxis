# P02 · 人员、专业服务与接收

人员与服务系统把承诺交给有资格的人，再由有权接收的人判断工作是否完成。一次录用需要兑现用工约定；一次故障处理要恢复服务；一张成绩单要表达经过批准的学习结果。它们都在协调责任，却不能共用一个含义模糊的“完成”字段。

本包的对象状态、算法数字和自建技术方案中的教学设定都是合成设计；产品事实在各例用来源链接与 claim ID 单独标明。

## 共同模型：承诺、能力与完成

假设一家服务机构答应客户安装并校准一台设备。两位技师的名字出现在排班表上，只能证明已经排了班。技师还需要相应资质、可用时间和现场权限；他们上传作业记录，才能证明做过哪些工作；客户或主管接收结果后，才有约定的履约证据。财务据此生成应收，收款还需要另一个权威系统的确认。把这几步压成一条进度条，就解释不了“技师下了班，设备却仍未通过校准”。

可迁移的模型保存五类事实及其关系：**承诺规定应做什么，资格规定谁能做，执行记录说明实际做了什么，接收决定哪些结果可被认可，结算说明认可后的义务怎样清偿。** 这五类事实可以由同一个应用管理，也可以分属多个系统；划分的依据是谁作决定、什么证据能推翻决定，而不是微服务的数量。

| 事实 | 常见对象与权威 | 容易混淆的替代证据 |
|---|---|---|
| 承诺 | 人事的任用版本、客户签认的 engagement、注册处的选课记录 | 邮件已发、表单已填、销售已口头同意 |
| 资格与容量 | 有效任职、角色授权、技能有效期、可用时间窗 | 名字出现在目录里、上次可以访问、日历没有颜色块 |
| 执行 | 变更尝试、服务动作、学习活动、booking 与工时 | 排程已确认、命令已接收、worker 已启动 |
| 接收与裁决 | 客户确认、主管批准、正式成绩、production 放行 | 技师自报完成、模型建议通过、队列已清空 |
| 结算 | 应付/应收版本、限额占用、外部付款凭据 | 工时获批、账单寄出、支付请求没有报错 |

这里的“接收”既可能是技术层的消息落盘，也可能是业务层接受结果。前者只说明系统有了一个待处理输入；后者需要特定角色、对象版本和判断依据。各例都写明指的是哪一种，不拿 HTTP 成功响应去证明它证明不了的事。

## 时间与权限

“某人是员工”不足以判断今天是否应该有某项权限。任用有生效和终止时间，账号有自己的启停状态，工资有计费期间。三个时间轴不一致时，系统要把差异记下来，不能拿最后写入的值覆盖所有对象。权限也是这样：老师能提交成绩，未必能发布正式 transcript；支持人员能提出退款，未必能自行扩大退款上限。

每个动作可以写成一个可检查的句子：**角色 R 对租户 T 的对象 O 的版本 v，凭证据 E，在时间 t 请求动作 A；服务端检查规则后保存结果及原因。** 同一请求重试使用原操作身份，旧版本请求得到冲突说明。若动作越过外部系统边界，页面保留“已请求、待核对、已确认”的区别。`unknown` 只表示本系统还不知道外部结果，外部可能已经执行。

状态也不总是按编号单调增加。离职撤销、成绩更正、客户重新打开请求，都可能是合理的后续事实。防止乱序消息破坏数据，要靠对象身份、版本或向权威复查；把所有状态排成从小到大的整数做不到这一点。历史记录保留原决定，更正记录说明改动的原因。

## 解题五步

每例按“识题 → 解法 → 演算 → 验算 → 变式”展开，五步的含义见[把业务问题算清楚](../../foundations/README.md)。识题先认出题目结构：是时间区间、版本竞争、资源约束、证据关联，还是额度分配。再选相应方法，代入一组能手算的输入，检查不变量是否成立，最后改变一个条件重做。识题线索记的是方法的适用条件，反例用来判断何时需要换方法。各例开头的选法表连到正文演算。

## 手算与检查

界面演示最容易漏掉中间证据：按钮变灰了，操作是否已落盘；列表变绿了，权威对象是否已确认；小例子算对了，换一个租户、遇到并发修改或迟到事件后是否仍然成立。各例有正常路径、反例和条件变化练习。先手算输入，再沿 UI → 服务校验 → 持久化 → 外部核对 → 页面反馈检查一遍，最后故意打断其中一步，就能看出系统还欠谁一个结果。

## 进入陌生行业

每例文末的探索方向用于进入陌生行业，列出继续补足术语、产品能力和组织规则的入口：先用合成业务走通对象与责任，再选择方案族，逐项核查其适用条件，最后运行能推翻错误设计的反例。
