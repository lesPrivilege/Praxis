# P02 · 人员、专业服务与接收

人员与服务系统把承诺交给有资格的人，再让有权接收的人判断工作是否完成。一次录用需要兑现用工约定；一次故障处理要恢复服务；一张成绩单要表达经过批准的学习结果。它们都协调责任，却不能共用一个含义模糊的“完成”字段。本章从共同模型出发，逐步解释权限、工作队列、专业裁决与结算。对象状态、算法数字和自建技术方案中的教学设定均为 synthetic；产品事实在各例以来源链接与 claim ID 单独标明。

## 先把承诺、能力与完成分开

假设一家服务机构答应客户安装并校准一台设备。两位技师的名字出现在排班表上，只能证明安排已经形成。技师还需要相应资质、可用时间和现场权限；他们上传作业记录，才能证明做过哪些工作；客户或主管接收结果后，才有约定的履约证据。财务据此生成应收，收款还需要另一个权威系统的确认。把这几步压成一条进度条，会让读者无法解释“技师结束了班次，但设备仍未通过校准”。

一个可迁移的模型是保存五类事实之间的关系：**承诺规定应做什么，资格规定谁能做，执行记录说明实际做了什么，接收决定哪些结果可被认可，结算说明认可后的义务怎样清偿。** 这五类事实可以由同一个应用管理，也可以分属多个系统；划分依据是由谁作决定以及什么证据能推翻决定，而非微服务数量。

| 事实 | 常见对象与权威 | 容易混淆的替代证据 |
|---|---|---|
| 承诺 | 人事的任用版本、客户签认的 engagement、注册处的选课记录 | 邮件已发、表单已填、销售已口头同意 |
| 资格与容量 | 有效任职、角色授权、技能有效期、可用时间窗 | 名字出现在目录里、上次可以访问、日历没有颜色块 |
| 执行 | 变更尝试、服务动作、学习活动、booking 与工时 | 排程已确认、命令已接收、worker 已启动 |
| 接收与裁决 | 客户确认、主管批准、正式成绩、production 放行 | 技师自报完成、模型建议通过、队列已清空 |
| 结算 | 应付/应收版本、限额占用、外部付款凭据 | 工时获批、账单寄出、支付请求没有报错 |

这里的“接收”既可能是技术层的消息落盘，也可能是业务层接受结果。前者只说明系统有了一个待处理输入；后者需要特定角色、对象版本和判断依据。本章明确写出是哪一种，避免让 HTTP 成功响应承担它无法证明的责任。

## 时间与权限使对象有边界

“某人是员工”不足以判断今天是否应该有某项权限。任用有生效和终止时间，账号有自己的启停状态，工资有计费期间。三个时间轴不一致时，系统必须表达差异，而不是选一个最后写入的值覆盖所有对象。类似地，老师能提交成绩，不意味着能发布正式 transcript；支持人员能提出退款，不意味着可以自行扩大退款上限。

每个动作可以写成一个可检查的句子：**角色 R 对租户 T 的对象 O 的版本 v，凭证据 E，在时间 t 请求动作 A；服务端检查规则后保存结果及原因。** 同一请求重试使用原操作身份，旧版本请求得到冲突说明。若动作越过外部系统边界，页面保留“已请求、待核对、已确认”的区别。`unknown` 描述的是我们不知道外部结果，不等于外部没有执行。

状态也不总是按编号单调增加。离职撤销、成绩更正、客户重新打开请求，都可能是合理的后续事实。能防止乱序消息破坏数据的是对象身份、版本或权威复查，而非把所有状态排成从小到大的整数。历史记录留下原决定，更正记录说明为什么改变。

## 按“识题 → 解法 → 演算 → 验算 → 变式”学习

先识别题目结构：是时间区间、版本竞争、资源约束、证据关联，还是额度分配。再选相应方法，代入一组能手算的输入，检查不变量是否成立，最后改变一个条件重做。识题线索帮助记住方法的适用条件；反例帮助判断何时需要换方法。各例开头的选法表连到正文演算，末尾给出具体研究入口，便于在陌生行业中继续补足术语、产品能力和组织规则。

## 按机制阅读七个案例

| 案例 | 阅读问题 | 主要计算与迁移边界 |
|---|---|---|
| [H04](H04.md) · Offer → 员工 → 薪资 → 离职 | 人事生效时间怎样影响访问与薪资，但又不代替它们的确认？ | 有效时间窗口与依赖；停账号不能清掉工资义务 |
| [H05](H05.md) · Incident → 受控变更 → 恢复 → 关闭 | 紧急恢复怎样保留执行授权、验证和失败撤回？ | 依赖与影响传播；变更成功不能替代服务恢复证据 |
| [H06](H06.md) · 支持请求 → 动作 → 客户确认 → 关闭 | 客服答复为何可能结束对话却未解决问题？ | 队列与时限；模型说“已解决”不能自行触发业务副作用 |
| [V17](V17.md) · 注册 → roster → 学习 → 成绩批准 → transcript | 名单同步怎样连接教学与正式记录？ | 版本化名单与成绩派生；互操作格式不决定成绩发布权 |
| [V18](V18.md) · Matter → hold → discovery → production → legal spend | 同一文档怎样在不同 matter 下保留不同责任？ | 证据关联与筛选；内容去重不能合并保全与特权判断 |
| [V19](V19.md) · Engagement → 配员 → 工时批准 → capped bill → 收款 | 已批准工时怎样竞争一个有限计费额度？ | 资源分配与额度累计；可计费并不等于已收款 |
| [V20](V20.md) · 服务请求 → 两次 booking → 完成 → posting → 付款 | 一次上门完成为何不能证明整个承诺兑现？ | 约束排程与时间区间；取消一次预约不自动取消工作范围 |

建议先读 H04 建立身份和时间观念，再比较 H05 与 H06 的关闭条件；V17、V18 将相同架构带入必须由专业角色裁决的场景；V19 与 V20 最后把人员、履约和金额连接起来。每例的 JSON 保存可供后续 HTML/motion 使用的节点、关系、状态与检查，正文承担“为什么”的解释。演示可以自由改变布局与动效，但要保留能失败的动作、未知结果和具体权威。

## 用反例检查设计

界面演示最容易漏掉的是中间证据：按钮变灰了，但操作是否落盘；列表变绿了，但权威对象是否确认；小例子算对了，但换一个租户、并发修改或迟到事件后是否仍成立。各例提供正常路径与反例，并给出改变前提的练习。先手算输入，再沿 UI → 服务校验 → 持久化 → 外部核对 → 页面反馈检查一次，最后故意打断其中一步，能看出系统还欠谁一个结果。

每例末尾的探索入口用于进入陌生行业：先用合成业务走通对象与责任，再选择解决方案家族，逐项核查其适用条件，最后运行能推翻错误设计的反例。
