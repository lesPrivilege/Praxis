# V19 · 专业服务怎样从配员走到收款

咨询公司卖的是一个承诺的结果，排进去的是人的可用时间，客户收到的是按合同规则计算的账单。三者相互约束，却不是同一种量。某人有空并不证明他具备技能；一小时已经发生，不证明经理认可它；经理认可的工时，也可能超过合同可收费上限。软件的职责是保留这些差别，让项目经理知道还能安排谁，让财务解释每一分钱来自哪里。

本例是一项 synthetic 的数据迁移 engagement（服务委托）：客户确认范围，合同总收费上限为 10,000 记账单位，已 release for invoicing（释放给开票流程）7,000；本期两条已批准工时按约定费率分别计 2,000 和 1,600。合同允许拆分行金额，先按服务日期、再按稳定行号分配剩余限额；不含税、汇率、差旅、预付款、收入确认或退款。600 的超额留在争议/变更队列，不自动记作下一期应收。所有数值与这套限额政策均为教学构造。

这里接回 P02 的共同模型：人员承担执行，批准者确认记录，接收方与资金权威分别提供下一步所需的证据。客户确认交付结果、经理批准 timecard（工时单）、财务 release billing event、账务确认收款，分别关闭一种责任。把它们塞进项目的 `done` 字段，会让“项目已完成但账单被拒”无法表达。

## 承诺、产能、工时与现金各有自己的对象

项目经理负责委托范围与交付依赖；资源经理协调不同项目争用同一个人；顾问申报已经做过的工作；审批人核对工作与合同；开票员处理计费；财务核对实际资金。顾问可编辑自己的草稿，却不能自行批准；资源经理可以排班，不能单凭排班生成已发生工时。客户是否必须验收、谁能授权超额，都是需要配置的合同条款，不从岗位名称推断。

Certinia 的 Timecards 文档提供工时列表与详情入口；其 Approving and Rejecting Timecards 文档说明审批过程要由管理员配置，提交、批准和拒绝取决于该配置。因而下表中的状态与职责划分是本例的实现政策，不能冒充 Certinia 所有组织的默认流程。[Timecards](https://help.certinia.com/main/2022.3/Subsystems/PSA/Content/topics/Timecards/AboutTimecards.htm)、[审批概览](https://help.certinia.com/main/2022.3/Subsystems/PSA/Content/topics/Timecards/AboutApprovingRejectingTimecards.htm)。

| 对象 | 权威与关系 | 不能混同的事实 |
|---|---|---|
| Engagement E1 / contract version | 委托服务保存客户接受的范围、费率和上限版本 | 估算不是承诺；范围变更需新授权 |
| Assignment A | 排班服务保存人员、任务、时间窗与占用小时 | proposed 尚未锁住资源；confirmed 也不证明工作发生 |
| Timecard T / time line | 工时服务保存服务日期、人员、任务、小时、版本和审批人 | approved 不等于 billable；修改 approved 行需更正记录 |
| Billing event B | 计费服务把符合条件的明细冻结并扣减本例的限额可用额 | release 表示交给开票流程，不能写成 paid |
| Invoice I / payment allocation P | 账务系统负责发票与收款分配；本地只保留映射和核对副本 | 收到一笔钱要匹配发票；收到通知不等于已核对 |

Assignment 走 `proposed → confirmed → completed / cancelled`；改期生成新版本，不能覆盖已经用于工时核对的历史排班。Timecard 走 `draft → submitted → approved / rejected`；驳回后带理由回到草稿，批准后的更正从旧行派生 adjustment，不无痕改小时。Billing event 走 `draft → reserved → released → invoiced`，外部结果不明时停在 `unknown`，而 Invoice 另有 `open → partially_paid → paid`。这些是局部教学状态集，不是 Certinia 完整对象模型。

Certinia 的 Billing Event Generation 文档明确把生成 billing event 与 release for invoicing 分开，能选择 timecards、expenses 等来源记录，并展示批处理进度。它没有说生成成功就已经开票或收到现金。[Billing Event Generation Tab](https://help.certinia.com/main/2022.2/Subsystems/PSA/Content/topics/BillingItemsEvents/GeneratingBEsTab.htm)。本例沿用这个有用区分，并额外设计自己的外部核对机制。

## 先做可行排班，再比较成本

周一有两个必须当天完成、各需 4 小时的任务：J1 需要 SQL，J2 需要 Python。甲会 SQL 和 Python，当天可用 4 小时；乙只会 SQL，当天可用 4 小时。输入还应包含已确认占用、休假、任务的时间窗、资格到期日；为了手算，暂不计通勤、切换成本与跨时区。

若按任务编号贪心，并给 J1 选“技能最多的甲”，剩下的乙无法做 J2。总可用 8 小时等于总需求 8 小时，排班仍然失败。把问题画成二部图就看清原因：J1 连甲、乙，J2 只连甲。先处理候选更少的 J2，分给甲，再把 J1 分给乙，两项都可完成。小例子可以枚举 2×2 个候选组合，验证这个解可行；它没有证明“最少候选优先”对任意规模都最优。

对于每项任务必须整块交给一个人、且每人只接一个任务的这一特例，二部匹配可以直接求是否存在完整匹配；一般增广路实现可按 O(VE) 估计，V 是节点数、E 是合格候选边数。加入可拆工时、每天容量和技能可用期后，需要变量 `x[人,任务,日]`，约束每天已占用加新分配不超过净可用小时、技能合格、任务在时间窗内完成，再最小化成本或迟延。可用 OR-Tools 建立求解模型，但其解也只对列出的约束有效；求解超时要区分已找到可行解与完全无解，不把“没找到”显示成“无人可做”。未实际运行求解器，也不声称 Certinia 采用上述算法。

前端排班板应同时提供表格和时间轴；拖拽先显示候选方案及冲突，再由服务端提交。客户端缓存里甲还有 4 小时，不能成为最终依据。两个项目经理同时给甲排 4 小时，后端在同一人员/日期的容量记录上做串行检查，只有一个成功；另一人看到冲突与重新计算入口。每日总小时适用于本例的弹性日容量。如果合同要求 09:00–13:00 连续工作，仅检查日总量会错过时间重叠，还需要区间交叠检查；必要时同时约束日容量和连续时间窗。

## 再算工时：同一小时可以有三个价格意义

顾问申报的是工作事实；审批人确认的是本例允许计入的记录；合同费率计算的是候选收费额。内部成本率可能不同于对客收费率，不能用客户账单估算员工工资。排班算例只截取周一两个子任务，以下计费取整周的迁移工作，并非把周一 8 小时改成 18 小时。为了看清限制，本期 T1 为 10 小时×200=2,000，T2 为 8 小时×200=1,600，两条都已批准且符合本例的 billable 条件。

剩余限额为 `10,000−7,000=3,000`。按本例的稳定顺序分配：T1 获得 2,000，余额变成 1,000；T2 获得 1,000，另 600 标为 over_cap。原始批准小时仍是 18，候选收费额仍是 3,600，release 的金额是 3,000。不能为了让账单好看把 T2 的 8 小时改成 5 小时；那会同时破坏工作记录和项目成本。对本例每次冻结的候选集合，应满足 `候选金额 = 本次分配金额 + 本次超额金额`，合同维度则满足 `累计释放 + 尚未释放的有效预留 ≤ 上限`。后一个式子的预留与释放必须互斥计数。

扫描 n 条已排序明细的分配为 O(n)，事先按服务日期、行号排序为 O(n log n)；合成实现用整数最小货币单位，禁止二进制浮点误差使 0.01 越过上限。全表重算直观，但不应在每次打开页面时扫描所有历史；可以保存已释放总额与操作账本，在同一事务内按预算版本更新，并定期用明细重算核对。这是 `ALG:windows` 与 `ALG:lookup` 的组合：服务期间筛选决定候选集合，稳定业务键定位已处理行，二者都不能替代扣减上限的并发控制。

Certinia 2025.1 的预算限额文档用预算金额减 Amount Released for Invoicing 计算可开票额，并明确 Amount Consumed 不参与该计算；文档还允许特定条件下的客户容差，并禁止同一项目同时设置预算级与项目级 cap。本例只选择一个合同级上限且容差为零；拆分行和 over_cap 队列是自己的政策，不复刻其产品行为。[Applying a Billing Cap to Individual Budgets](https://help.certinia.com/main/2025.1/Content/PSA/Features/Budgets/ApplyBillingCapOnBudgets.htm)。

反例一是拿“成本消耗 9,000”来计算可收费 1,000：成本率和销售费率不同，这个数未必有计费意义。反例二是两个 worker 同时读取余额 3,000，分别 release 2,000，总额变成 11,000。页面同时禁用按钮不能解决竞争；计费服务必须在权威事务内锁定预算或用版本条件写入。第三个反例是把 600 静默带入下月：合同总上限没有因月份变化而重置，下个月仍然超额，除非客户接受新范围或新上限。

## 从操作反馈到收款核对

工时表按日期、任务和审批状态显示，保存草稿与提交审批使用不同动作。提交后锁定本例的审批版本，拒绝时把理由附在原行旁；离线编辑回来的旧版本不能覆盖经理刚批准的内容。审批页展示“已排班 8 小时、申报 10 小时、差异 2 小时”，要求解释而不是自动裁成 8。排班是预测，实际可超出；是否接受超出由本例的授权规则决定。

计费页先预览“已批准候选 3,600；剩余上限 3,000；拟释放 3,000；待处理超额 600”，再由获授权的开票员确认。后端验证合同、审批版本和已处理明细唯一键，保存 allocation、reserve 和 operation ID，异步请求账务系统开票。本例将 released 明确定义为“账务已受理这项开票请求且已核对”，此时把同一金额从 reserve 移到 released，两者不能短暂被其他事务一起忽略；具体发票 I1 的身份与金额核对完成后才进入 invoiced。若受理响应已经带回发票，两个逻辑步骤可以在同次处理内完成，仍分别保存证据。页面分别显示“提交已保存”“账务受理中”“发票 I1 已确认”。账务提供已核对收款 1,800 时，I1 是 partially_paid，未收 1,200；第二笔核对 1,200 后才 paid。客户发来一张付款截图不是本例指定的现金权威。

前端可以选择 Vue/TypeScript 或 React/TypeScript：两者都适合可编辑表格、冲突提示和排班时间轴；关键是将服务端版本冲突映射为可恢复的行，而不是在浏览器里复制审批规则。小规模应用可用 Django + HTMX 表单减少双端状态，代价是离线批量编辑需要另外设计。后端用 PostgreSQL 保存员工/日容量、合同版本、工时审批和计费分配；用整数分钟及整数分存数量和金额。队列可从数据库 outbox 加 worker 起步；跨系统开票或通知量大后再采用托管队列，付出重复投递处理和运维成本。可选外部 专业服务自动化（professional services automation，PSA） 提供排班或工时数据，但字段映射、授权与版本需要 adapter 明确处理，不能把两个系统都写成同一对象的权威。这些是原创选型，不是 Certinia 内部栈说明。

正常路径是客户接受 E1，甲乙的排班分别确认，顾问填写并提交 T1/T2，审批人批准，B1 原子预留 3,000，账务受理核对后转为 released，具体 I1 核对后变为 invoiced，财务逐笔核对 1,800 与 1,200 的收款。交付结果的客户验收可先于开票，也可依合同成为 release 的额外 guard；本例假设 release 前已经获得交付验收，但仍保存独立证据。

失败路径选择“账务已开票，网络响应丢失”。B1 保持 `unknown`，3,000 的预留不能释放回可用额，否则另一次开票会吃掉同一剩余限额。adapter 按 `(tenant, ledger_account, billing_operation_id)` 查询；已存在的 I1 绑定回来，不新造 I2。若账务不支持可靠的相关键查询，则人工核对未知结果，不能用“超时十分钟就撤销预留”的规则赌它没成功。确认未受理后才能取消；确认已开错票后走更正/贷项流程，不直接删除工时或历史发票。反向调整是否重新增加 cap 必须有合同及账务政策，本例不自动增加。

容量假设为 50 个租户、每租户 2,000 位顾问、每周每人 5 条工时，合计每周 500,000 条；月底某租户同时提交 20,000 行计费。待测目标是单人周工时页 p95 < 500 ms、审批提交 p95 < 700 ms，批量计费每 500 行一个可恢复分片；未做负载实测。不要按所有项目共享一个锁；按人员/日期保护产能，按合同与币种保护跨版本的计费占用账本，cap 版本是授权输入而不是另一个可独立扣款的余额。版本切换与新预留也受同一个合同级并发控制；旧版本停止新增预留，新版本继承累计 released 与所有未决有效 reserve，不能只继承已开票金额。例如已释放 7,000，另有结果未知的预留 3,000，上限从 10,000 调至 10,600 后，新可用额仅为 600；若错误地另建新版余额，就会得到 3,600 并重复用掉那 3,000。但一个巨大合同仍会成为热点，要限制同一 cap 的并发批次。报表缓存可按租户、项目、周期与权限版本分区，月底批处理更新后显示投影水位；可用额预览明确是估算，release 总要重新校验。恢复时重新核对 allocations、reserved、released 与账务发票，不能只重放“创建发票”消息。

## 验收必须穿过计费与现金的边界

| 检查 | 操作与需要留下的证据 |
|---|---|
| happy_path | 两任务都可行；18 小时获批、候选 3,600、release 3,000、超额 600；收到 1,800 后仍欠 1,200，再收到 1,200 才 paid |
| duplicate | 同一工时审批事件、B1 请求及付款通知重复；审批版本、源明细分配、支付分配均只产生一次效果 |
| out_of_order | 已核对第二笔付款后到达旧 open 信息；以账务当前分配结果核对，不按通知时间把 paid 回退 |
| concurrency | 两经理同时占用甲的 4 小时、两 worker 同时扣剩余 3,000；分别发生一项排班冲突与 cap 冲突，无超配/超额 |
| tenant_isolation | 两租户都有 E1、T1、I1；查询、缓存、adapter 相关键均带作用域，不能串账或显示工资成本 |
| unknown_outcome | I1 已创建但响应丢失；预留保持有效，按同一操作核对得到一个 I1，不释放预留再开票 |
| recovery | reserve 已写入、消息发送标记未写时崩溃；outbox 重放后只有一项释放，最终 reserve=0、累计 release=10,000 |
| 领域反例 | 故意执行“先广技能者”“只校验日总量”“用成本代 cap”“超时即返还额度”；每个错误都应有固定反例使其暴露 |

本例的配员可行性、限额分配和审批 guard 用确定性规则判断，核心路径不需要 AI。若以后让模型提取工时描述中的任务编号，只能提供建议，人工确认后进入正常 guard。可选评估计划冻结 200 条样本：120 条开发、80 条留出，按顾问和项目切分；记录 80 条中正确提取数、20 条含歧义样本的拒答数、60 条无歧义样本的误拒数及人工修正数。假设模型强行给 20 条歧义样本中的 4 条分配错误任务，不能把非空输出率当成功率。模型或提示词变化必须重新评估；不得凭描述自动批准工时或加大限额。当前未运行模型评估。

## 改变前提后重新计算

**练习一：乙改为只能周二上班，J1 仍要求周一完成。** 能否沿用原排班？简答：不能，SQL 技能仍在，但时间窗删掉 J1→乙 这条可行边，周一 8 小时需求只剩甲的 4 小时。保持不变量“资格与时间同时满足”；失效条件是只按技能匹配。检查 UI 不应显示“总计两人足够”，应列出 J1/J2 的竞争资源，要求改期限、找替代人员或调整范围。可迁到 V20 的 booking，现场任务还可能受地点、行程与设备约束，按日工时匹配不足以保证可达。`TR:V19:V20:capacity-and-window`。

**练习二：客户把合同 cap 提高到 10,600，变更今天才接受。** 600 能否立即重写进原账单？简答：不应改已冻结/已发的 I1。保留旧 cap 版本及 3,000 的分配，以新授权创建剩余 600 的新计费尝试；先检查其适用服务期间和同一源行尚未计费部分。若 B1 还 unknown，旧预留 3,000 同样进入新版本的共同占用账本，新上限 10,600 减已释放 7,000 减预留 3,000，仍只剩 600。不变量是每次计费可追溯合同版本且不能重复；失效条件是以最新上限重新解释历史。检查 T2 两次分配合计最多 1,600，旧 I1 的金额保持 3,000。可迁到 H01 的合同版本，但订阅权利的开通时点需另外决定。`TR:V19:H01:versioned-billing`。

**练习三：合同变成固定费 10,000，实际做了 25 小时。** 能否仍按小时×费率生成客户账单？简答：不可以。工时继续支持产能和成本分析，计费来源改为合同约定的里程碑/交付验收；若规定 40%/60%，两次候选额为 4,000、6,000，与工时变化不直接联动。保持“计费依据显式”；失效条件是把 timecard 当所有合同的唯一计费依据。检查额外 5 小时不能自动增加固定费账单，未完成里程碑也不能因工时已批准就 release。这个边界能帮助 V18 区分审阅工作量、交付接收与费用批准。`TR:V19:V18:effort-versus-acceptance`。

演示可让读者修改技能、可用日期、cap 与回执延迟，同时观察排班可行性、工时、候选金额、预留、已释放、发票和已收金额。任何 UI 形式都应让超额 600 留在可见的处理队列，而不是在动画结束时消失。结构见 [V19.json](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/V19.json)，事实与合成政策见 [evidence.json](../../../../vault/distilled/saas-engineering-atlas/packages/people-service/evidence.json)。

## 从合同计费条款倒推选型

进入陌生专业服务行业时，先取得一份虚构但完整的合同规则：按时、固定费还是里程碑，上限覆盖哪段期间，超额、预留、贷项和变更怎样处理。PSA 的资源规划、工时审批与 billing 能提供基础对象，账务系统仍负责发票与到账；现成模块是否适用取决于它的额度口径和本合同是否一致。下一步查供应商的 cap/approval/release 定义、费率生效与部分行处理，确定外部开票相关键，而不是从演示字段名猜测。以unknown预留期间提高cap为验收输入，再检查同一工时多次部分分配的总额；能把尚未确认的3000保留为占用，才没有借换版重复使用额度。
