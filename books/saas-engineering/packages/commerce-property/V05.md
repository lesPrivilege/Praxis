# V05 · 菜单选择、厨房交接、分账与结账

餐厅向一桌客人承诺按约定做出食物，并把每份消费和每次付款解释清楚。软件必须协调两种速度：厨房接到单后就可能开始消耗食材，收银却可能在最后才确认由谁付多少。订单、制作、账单和支付因此各有状态；一次“取消”不能同时把已做的菜、客人应付的钱和银行卡交易倒退回起点。

本例是合成堂食系统，使用 Toast 的公开对象定义作参照。两位客人点了 3,200 分和 2,800 分的主菜，共享 1,900 分配菜；原价 7,900 分，整单优惠 501 分，净应付 7,399 分。为看清拆分关系，例内排除税、服务费、小费、外币、离线银行卡授权和跨营业日重开；这些真实条件加回时必须重新定义价格和关闭规则。本例允许先出餐后收款，关闭需要应付额已被确认付款覆盖、所有支付尝试已解释、制作取消或报损有责任人。

## 识题：做几份、谁欠钱、钱怎么付

餐饮问题先问变化发生在哪一层。口味变化影响制作内容，分账影响消费责任，组合付款影响收款工具；选错层就会出现多做一盘菜或多收一次钱。

| 识题线索 | 先选的解法与适用条件 | 怎样验算、接着查什么 |
|---|---|---|
| 同一道菜，有人要不同口味 | selection 固定每组配置，modifier 树表达组成；不同配置拆选择 | 总份数与每份配置都完整；查菜单必选项、数量和版本约束 |
| 一盘菜多人付，一张账多次付 | 前者拆 check 责任，后者建 tender attempts；未决尝试保留占额 | 拆账总额不变、制作仍一份、可收余额不负；查折扣继承与终端交易查询 |
| 点了撤销，厨房已经开火 | 撤菜请求与厨房确认分开，已耗资源用报损或新处置解释 | 老回执不能重启已取消任务；查 KDS 去重/确认及纸质打印的人工交接 |

## 解法：菜单项是选择模板，selection 是这次要做的东西

菜单管理员维护菜品及 modifier（口味、配料或规格选项）。客人点一份“不加酱”的主菜，服务员就创建一次 selection；同一菜单项的另一份正常口味必须有自己的选择内容。选择保存菜单版本、选项树、数量、接受的价格与备注。菜名后来更改不会让厨房旧单变成另一道菜。自由文本备注可以提醒人员，不能自动证明某种食物安全要求已经满足；无法可靠表达的要求需要工作人员确认。

Toast 文档把 modifiers 放在 `Selection` 中，并规定 modifier 数量应与所属 selection 数量相等；同一道菜的不同份数需要不同 modifier 时，应拆为不同 selection。这个约束说明“2 份主菜、其中 1 份不加酱”不能靠一个含糊的数量 2 行表达。参见 [Specifying modifiers and instructions，Requirements for modifier quantities](https://doc.toasttab.com/doc/devguide/apiSpecifyingModifiersAndInstructions.html)（`P05-SRC-toast-modifiers-C1`；）。本例选项验证和价格快照由自己的服务实现，不假设 Toast 使用本例的数据表或算法。

服务员可新建选择、发送尚未制作的项目和提出撤菜；厨房确认收到、开始制作、完成或无法停止；收银员收取限定余额的款项；经理授权送厨后的撤销、折扣与报损。任何角色都不能凭按钮自认银行卡扣款成功。餐厅是数据边界，桌号只在门店与营业场景内有意义；“12 号桌”不能充当全球订单 ID。共享设备上切换员工时，当前操作要重新绑定员工身份和权限。

| 对象 | 权威与稳定身份 | 本例独立状态 |
|---|---|---|
| selection | 点餐服务；selection ID、菜单版本、modifier 快照 | `draft → committed`；未发送可修订，发送后变更用 amendment 保留原内容 |
| kitchen ticket | 厨房接收记录；ticket ID、selection revision | `queued → accepted → preparing → ready → served`；撤销请求另走 `cancel_requested → cancelled/too_late` |
| check | 账单服务；check ID、定价版本 | `open → settling → paid → closed`；拆账更改应付归属，不能重发制作任务 |
| tender attempt | 本地资金操作；attempt ID、支付账户、终端交易身份 | `prepared → submitted → succeeded/declined/unknown`；unknown 是知识状态，不代表失败 |
| shift close | 门店对账服务；营业日、班次、明细版本 | `open → balanced` 或 `exception`；关闭一张账单不证明收银抽屉与结算已相符 |

Toast 自己的状态名必须按原义理解：`approvalStatus` 仅反映是否送厨，不证明已完成或已付款；selection 的 `NEW/HOLD/SENT/READY` 描述制作，其中 `READY` 依赖使用 Toast KDS。其 check 的 `PAID` 与 `CLOSED` 还区分付款及小费调整，本例不含小费，不能把合成 `closed` 规则说成完整 Toast 行为。参见 [Order object summary，Order status information](https://doc.toasttab.com/doc/devguide/apiOrdersOrderObjectSummary.html)。

## 送厨是一次不可凭数据库回滚撤销的交接

点餐页用可选项表达常见口味，并在提交前列出每份最终配置；缺少必选项时定位到对应组，保留已经选好的内容。价格发生变化时展示差额，服务员确认后才接受新版本。点击“送厨”将指定 revision 的 selection 固定为制作依据，保存 ticket 和 outbox；界面先显示“待厨房接收”，得到厨房确认后才显示“厨房已接单”。如果只把数据库写入当作已接单，打印机断纸、终端断网时前厅会承诺一个厨房从未见过的等待时间。

同一 `ticket_id + revision` 重发给可去重的 KDS，只显示一次待做工作；纸质打印没有可靠的电子完成回执，打印成功也不证明厨师看到。本例在这种模式下保留“打印结果待确认”，重打显著标为副本并由人员确认，不宣称所有物理副作用都能做到 exactly once。服务员刷新页面不会生成新 ticket。厨房拒绝制作时，selection 仍保留原承诺，前厅必须向客人提供换菜、等待或取消方案。

已经送厨的“撤菜”是新请求。厨房在尚未制作时可以确认停止；若已经开火，经理决定继续上菜、重做或报损，并给账单作明确调整。系统不能删除原 selection 来掩盖已经耗用的食材。厨房事实与应收政策也不能绑定成同一布尔值：餐厅可以因服务问题免单，但菜确实做过；也可以在菜取消前已经收到款，需要再处理退款。相应 audit trail 保存原 revision、变更理由、批准人、厨房响应和资金操作引用。

## 分账改变谁欠钱，多种付款只改变钱怎么进来

Split check 是把消费责任拆成多个 check：两人各付自己的主菜，各承担共享配菜一半。每个新 check 都有应付额和自己的关闭条件。Split tender 是同一 check 用多次付款覆盖余额，例如 3,000 分现金加 4,399 分银行卡；它不会自动创建两份菜品或两张账单。Toast 的操作文档同时描述按项目拆账，以及保持账单合并、逐个输入付款金额和 tender type 的方式。参见 [Split Checks on the POS](https://support.toasttab.com/en/article/Splitting-Checks-by-Item-1492811097734)（`P05-SRC-toast-split-C1`；）。同一文档提醒，按项目拆账时服务费及项目级折扣不会自动继承，需要重新处理；下文保持总优惠不变的比例分配是本例政策，不是 Toast 的产品保证。

合成分账界面把原 check 放在左侧，拟生成的 A、B 账单放在右侧；共享项目可分配消费份额，但保留原 selection 与厨房 ticket 引用。预览同时显示分配前后金额总和和优惠归属。提交带原 check version；两个服务员同时拖动同一个项目时，后提交者收到冲突并重新预览，不能最后写入者覆盖。已开始付款的账单暂不允许自动拆分，先确认每次支付归属；否则一笔已付的钱可能留在空账单，另一张账单又向客人收费。允许带支付拆分的产品需要额外的款项重分配对象，不在本例偷偷补一个字段。

同一合并账单的收款页则显示“应付 7,399；已确认 3,000；处理中／待核对 4,399；当前可发起 0”。客人和收银员都能看到待核对不等于未付款。刷卡超时后，页面保留原 attempt，允许查询、呼叫经理和记录处理意见；不提供会偷偷建立第二笔扣款的普通“再试一次”。现金输入的是本次交付金额和找零，实际记入该 check 的已付额才减少欠款；例如交付 5,000、找零 2,000，应用付款为 3,000，不能把 5,000 全计作消费收款。

## 演算：一次分账与一次未知支付的手算

算法先冻结选择和价格，再分消费责任，最后收款。A 的原价责任为 `3200 + 1900/2 = 4150`，B 为 `2800 + 1900/2 = 3750`，两者合计仍为 7,900 分。501 分优惠按两人的原价责任分配：A 理想分配 `501×4150/7900 ≈ 263.1835`，B 约 237.8165。取整后为 263 和 237，还剩 1 分给余数较大的 B，得到 A 净付 3,887、B 净付 3,512，合计 7,399。平手按固定新 check ID 排序，预览和提交使用同一规则版本。

朴素实现容易先拆出两张新账单，再对每张重复应用“优惠 501 分”，让总优惠翻倍；也可能把共享项目复制为两份，导致厨房再做一盘。正确实现把责任份额作为从原 selection 派生的记录，所有子份额总和为 1，并在同一事务中把原账单标为已替代。共享菜在消费责任上可分成两半，制作任务仍只有一份。若不能精确平分一分钱，仍用最大余数法安排尾差；这是价格守恒，不是厨房配方的数量单位。

分账预览需要遍历 n 个消费份额并按余数排序，约 O(n log n)；典型一桌几十个份额无需复杂分布式计算。modifier 树的验证按 v 个节点、e 条父子关系遍历，约 O(v+e)，同时检查选项属于相应菜单版本、必选数量、深度上限和重复关系；不能只凭叶子名称相同就接受。合成系统以此防止客户端把价格较低的另一道菜选项拼入当前选择，实际 provider 规则须由其 API 再验证。

若不分账而保留 7,399 分合并 check，现金成功后已确认 3,000；卡尝试 4,399 已送出但响应丢失。收款服务使用 `可发起金额 = 应付 − 已确认应用金额 − 未决尝试占额`，得到 0。未知占额不是成功收入，只是阻止并发重复收费的暂留。核对卡成功后，已确认变为 7,399，未决归零；核对明确拒绝后，已确认仍为 3,000，未决归零，允许新尝试收 4,399。错误实现仅相减已确认金额，会在卡结果未知时仍允许现金再收 4,399，等迟到成功到达便多收一份。

## 从平板到厨房与支付终端

React 或 Vue 可实现桌台、菜单、拆账和收款工作台；厨房屏需要清晰的大字号、可操作的聚焦顺序和不会因刷新跳动的 ticket 身份。服务端可以采用 Kotlin/Spring 或 TypeScript/NestJS；强类型金额与版本对象有助于减少误传，选择依据仍是团队能力。PostgreSQL 事务保存 selection、check 份额、付款占额和 outbox，唯一键限制同一 ticket revision、同一 attempt 的重复业务效果。菜单静态内容可按餐厅、版本、语言缓存；当前应付与可收余额从权威服务确认，不能用本地缓存作最终决定。浏览器本地存储可以保护未提交草稿，但断网草稿只显示“未送厨”，不能伪装成餐厅已接单。

拓扑中点餐 UI 的 `commands` 到订单服务，厨房 UI 的 `commands` 到厨房服务；厨房确认事件通过 `emits → delivers` 更新 ticket。账单服务 `owns` check，check `derived_from` selection，tender `depends_on` 被接受的 check version。资金服务 `requests` 外部支付方并 `reads` 原交易核对；`projects` 把厨房、账单与支付三种事实分别呈现。Stripe 是回调风险的公开参照，Toast 是餐饮对象的公开参照，不表示本例已经把二者接成一个生产集成。Stripe 文档讨论签名验证、重复事件与乱序；这些提醒本例消费者保留身份并查权威结果。参见 [Stripe Webhooks](https://docs.stripe.com/webhooks)。

正常流程中，服务员提交选择，厨房确认接单并完成，客人收到菜；收银员选择分账或同账多次付款，资金确认覆盖余额后关闭账单，班次核对现金应用额、找零、卡交易及退款。异常流程中，卡受理后超时，本地保存 unknown；收银页继续保留桌台和责任人，后台按原交易查询。若查询也不可用，经理在未决清单接管；本例不自动改收现金。业务允许客人先离店时，另建明确的应收／人工交接记录，不能把它记作已收款。

送厨事务提交后 worker 崩溃，则重放同一 outbox；重复副本在 KDS 按 ticket revision 合并。厨房已确认撤销，而晚到的旧“已接收”消息到达时，不能把 ticket 恢复为待做；读取当前 revision 和撤销确认后修复投影。付款状态同样不按消息到达次序决定。若系统无权查询支付端结果，unknown 可以持续，自动恢复的前提已不成立。

## 验算：高峰时关注哪一种等待

合成容量目标为 50 家餐厅、每店峰值 60 个活跃桌台、每桌最多 80 个 selection、8 台点餐设备；平台峰值每秒 150 次修改或付款动作。本地提交 p95 目标 300 ms，在线厨房确认可见 p95 目标 2 秒，外部终端时延单独计量，不能把未决交易从统计中删除。共享菜单读取容易缓存，真正的竞争点是同一 check 和同一桌的修改。按 check 版本拒绝冲突比给整家餐厅加一把锁更细；对一桌的短事务仍要序列化金额占用，避免两台终端同时收走同一余额。

告警区分最老未接收 ticket、制作超时、未知卡支付年龄和班次差异。厨房正忙不是消息未送达，卡网络慢也不是厨房未完成；混成一个“处理中”会让员工做错恢复动作。对支付 unknown 的核对队列按餐厅公平调度，避免一个大门店重试淹没其他门店的结账。

[结构数据](../../../../vault/distilled/saas-engineering-atlas/packages/commerce-property/V05.json)给出七种必需检查及本例反例：modifier 数量不匹配应在送厨前拒绝；同一个 ticket 重投不生成第二份制作；撤菜迟到不抹去报损；拆账守恒且不重送厨房；unknown 占额阻止第二次收款；支付拒绝才释放占额；不同餐厅同桌号不得串单；关闭后迟到的未付款消息不能回退当前事实。检查必须观察 UI 提示、保存的 selection revision、厨房确认、每次付款和最后余额。本例不使用 AI 决定配方、收款或是否关账，AI eval 不适用。JSON 是验收定义，未实施的 UI、设备、网络和负载检查不得记为已通过。

## 变式：改变条件再做判断

**练习一：三份同菜中，一份不加酱、两份正常，服务员只提交一个 quantity=3 的 selection，再附 quantity=1 的“无酱”。** 怎样改才保住责任？

简答：建立 quantity=1 的无酱选择和 quantity=2 的正常选择，各自固定 modifier 内容，厨房按两份明确的配置执行。不变量是每一实际份数都有完整配置，不能靠备注让人猜其作用范围；Toast 的上述数量约束也不接受这个不匹配。反例是厨房给三份都去酱或仅凭顺序猜一份。检查菜单验证拒绝旧输入，新输入生成两组配置、总份数仍为 3。若某要求关系到食物安全且系统无法结构化确认，自动化边界到此为止，需工作人员确认。

**练习二：卡付 4,399 分仍 unknown，顾客建议先付同额现金。** 能否先关账，以后再说？

简答：不能把未知当拒绝。保持原卡尝试占额并核对；已确定拒绝后才收现金。若经理决定例外收现金，必须建立独立重复付款风险和后续退款责任，当前基础模型需扩展，不能把卡尝试删掉。反例是后来卡成功导致总应用金额 11,798 分。检查在 unknown 时第二个普通收款命令被拒绝，页面显示未决金额；核对拒绝后允许一次新的 4,399 分付款。支付端无法查证时，此自动恢复路径失效，留下人工接管记录。

**练习三：厨房已做出共享配菜，客人才要求把账单拆为两张。** 是否应再给厨房发送两份各 950 分的配菜？

简答：不应。新 check 份额引用同一个 selection；制作对象不变。验证两张账单合计 7,399 分、原 ticket 数量仍为 1。若拆分发生在送厨之前，界面仍可选择如何编排打印，但消费份额不是增加制作数量的依据。

`TR:V05:V04:allocation-conservation` 把账单份额守恒迁到商品拆单；共同点是子对象必须能加回父对象，失效处是共享菜可以分摊金额但不能按付款份额重新制造实物。`TR:V05:V06:charges-versus-payments` 把消费项目与付款分离迁到住宿 folio；住宿包含多日记账、押金、离店后调整，不能照搬本例“本次应付已付即可关账”。演示可让读者改变 modifier、晚发撤菜、切换拆账与多次付款、延迟卡回执，看见制作数量不变而收款权限随证据改变。

## 进入餐饮系统时先查什么

跟随一桌包含不同 modifier、共享菜和两种付款方式的消费，分别记录厨房实际收到什么、账单由谁承担、终端实际收了多少。成熟解法是 POS 的 selection/check/payment 模型、KDS 的制作交接和班次对账；纸质打印、无回查能力的终端与离线收款会改变恢复边界。下一步先查菜单数量约束、厨房确认机制、终端交易查询及取消能力，再研究小费、税费和营业日重开。验证应包含“拆账后制作任务仍一份”和“终端超时后不能普通补收”两条路径；只看收银页金额相等，无法证明客人没有多付或厨房没有多做。
