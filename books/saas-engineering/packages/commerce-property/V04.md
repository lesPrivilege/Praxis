# V04 · 产品目录、拆分履约与退货后的净结算

商店向顾客承诺的是具体商品、数量、价格和交付方式。收到了钱，只证明其中一项义务有了进展；商品可能仍分散在两座仓库，退回的商品也可能暂时不能再次出售。本例接续 H01 的“承诺—履约—收款”模型，把一份承诺拆成可以逐件核对的数量账，并让实物与资金各自保留证据。

下文是一家合成家居商店的设计，不是 Shopify 的内部实现。顾客购买茶杯 3 个，每个 4,000 分；杯盖 2 个，每个 1,000 分。商品总额 14,000 分，整单优惠 1,001 分，应付 12,999 分。只使用一种币种和整数最小货币单位；不含税、运费、换汇、换货、拒付和会计收入确认。退货期限、可退状态和手续费均为教学政策，真实商店须另定规则。案例的关闭条件是所有订购数量已交付、已取消或已有获批的异常处置，所有已批准退款已有可核对结果，库存处置和支付对账均没有悬项，而不是订单列表显示一个“完成”。

## 识题：一单多去处，先分数量账

遇到“总订单已经付款，部分商品却还没交付”，先拆承诺的数量去向，再分别处理逆向实物与资金。下面三条线索帮助选方法；后文会把每种方法放回同一张订单里演算。

| 识题线索 | 先选的解法与适用条件 | 怎样验算、接着查什么 |
|---|---|---|
| 一单多仓，先到一部分 | 订单行加履约分配；每份数量有稳定身份及唯一当前去向 | 子数量加回订购量；查仓库交接和取消的实际确认边界 |
| 整单优惠，逐件退货 | 接受时冻结金额快照，用最大余数分配整数尾差 | 改变退货顺序，总退款不变；查计价单位、unit 映射与赔偿规则 |
| 退了钱，货却未回；净结算也不同 | 退货验收与支付交易独立，按交易身份建立结算桥 | 退款不直接增加库存；收款减退款及费用解释净额；查 returnProcess、OrderTransaction 与批次明细 |

## 解法：商品目录保存今天的选项，订单保存当时的承诺

目录中的 variant 表示一个可销售规格，例如“陶瓷茶杯／白色／300 mL”。SKU 是业务识别码，不应代替不可变的内部身份；改名或重新使用 SKU 都不应改变既有订单。合成系统让目录管理员发布带版本的名称、规格、价格和可销售规则，客户提交时由服务端重新确认版本，然后把接受的内容、单价、优惠分配和规则版本复制到订单行。以后目录改成 4,500 分，旧订单的退款计算仍取 4,000 分的购买快照。快照保存的是承诺依据，不意味着把所有库存数据也冻结。

顾客只能请求购买、取消未交接部分或申请退货；客服可以批准符合政策的退货，却不能凭聊天记录宣布钱已退到顾客账户。库存服务掌握各仓可用数量，仓库操作员确认拣货和实物交接，财务审核退款及结算差异。退款超过例内权限额度时进入复核；审核人在确认页看到原付款、既有退款、此次金额和剩余额度。租户、商店、仓库与支付账户的映射在服务端决定，不信任浏览器提交的 `tenant_id`。

Shopify 的公开模型区分 `Order`、`FulfillmentOrder` 和 `Fulfillment`：履约单组织同一地点要履约的项目与数量，实际履约记录另含发货项目和追踪信息；一个订单还可能包含不同交付方式。这些对象定义支持“承诺、安排、发货证据分开”的判断，不证明本例的库存算法。参见 [Apps in order management，API objects and relationships](https://shopify.dev/docs/apps/build/orders-fulfillment/order-management-apps#api-objects-and-relationships)。

| 对象 | 本例的权威与身份 | 独立状态及允许变化的证据 |
|---|---|---|
| 订单及行快照 | 订单服务；`order_id + line_id + accepted_version` | `draft → accepted → resolved`；接受固定价格，关闭只汇总已解释的数量与例外，不改写历史 |
| 仓库分配 | 库存服务；订单行、仓库、allocation ID | `reserved → handed_over` 或 `released`；只有原子占量成功才能承诺仓库份额，实物交接后不能释放成未发货库存 |
| 发货批次 | 履约服务；shipment ID | `planned → packed → handed_over → delivered`；承运回执或人工留证分别确认交接、交付，途中丢件进入 `exception` |
| 退货 | 退货服务；原发货行、return ID | `requested → authorized → received → inspected → disposed`，或 `rejected`；收到包裹不等于可售，验收决定返库、隔离或报损 |
| 退款尝试 | 资金服务保存请求；支付方确认处理结果 | `prepared → pending → succeeded/failed/unknown`；批准金额不是支付成功，未知结果必须查原尝试 |
| 结算核对 | 本地对账服务；支付账户、结算批次、规则版本 | `open → reconciled` 或 `discrepancy`；依据交易及结算明细，不能由退款页面推断银行入账 |

这些状态并不组成一条单向漏斗。订单可以已付款、部分发货，同时有一笔缺货退款；也可以全部交付、退货已收件、退款仍在核对。页面必须允许这些组合存在。

## 数量必须有去处，不能只给订单贴标签

本例对每条原始订单行维护不相交的去向：`订购量 = 未分配量 + 已占未交接量 + 累计已交接量 + 交接前取消量`。拣货属于“已占未交接”，不是额外加一次。退货是已交接历史的后续分支，不能从累计交接量里扣除后又释放成未发货库存；另核对 `已收退货量 ≤ 可追溯的已交付量`，以及 `重新可售量 ≤ 检验通过且尚未返库的退货量`。拒收、丢件和补寄需要独立原因与补寄义务，本例不凭负数量抹平。

北仓有茶杯 2 个、杯盖 2 个，南仓有茶杯 1 个、杯盖 0 个。服务先校验商品可售和价格，再以库存行版本创建北仓 4 件、南仓 1 件的分配。对单仓单规格，`可用量 = 实存量 − 有效占用量`。占量与 allocation 写入同一数据库事务；两个订单同时争最后一个杯子时，只允许一个条件更新成功。缓存显示“有货”不能越过这个条件。

北仓先发货后，汇总是“已交接 4／5，另 1 件已占待交接”，而非“已发货”。南仓迟迟未确认时，客服可以催办或请求取消该份额，但系统须先确认南仓尚未交接。若实物已出库而本地回执丢失，直接释放占用会让另一位顾客买到并不存在的库存。这正是分配状态和外部未知结果必须相连的地方。

## 按钮承诺的是哪一步

商品页允许按规格选购，购物车只给预估；结账确认页显示服务端重新计算的价格和拆分交付方案。若目录版本变化，界面保留选项并列出差额，要求接受新报价；不把价格冲突包装成“网络错误”。订单页并列展示付款、各仓份额、每批追踪和退货退款卡片。列表为查询投影，详情展示最后核对时间；返回页面后，用户仍能通过同一操作身份找到提交结果。

仓库点击“确认交接”提交 `operation_id、allocation_id、expected_version、quantity、交接证据引用`。服务校验该仓权限及未交接量，在事务中保存状态和待通知事件，然后返回“交接已记录”。异步 worker 把事实交给其他系统；HTTP 成功不等于承运人已送达。客服点击“退款”则先取得计算预览，提交绑定同一预览版本和父付款的请求；等待页面区分“请求已保存”“支付方处理中”“结果待核对”“已确认退款”。“重新查询”可用，“换一个请求再退”在 unknown 时不可用。

拓扑 JSON 中，`operates` 是人进入界面，`commands` 是界面提出动作，`owns` 指明谁对事实负责，`stores` 指明记录保存在哪里。`requests` 把本地操作送往仓储／支付系统，`emits → delivers` 只是通知交接；商品实际移动仍由 shipment 和 return 的证据表达。`projects` 把对象状态投影到界面，不能反过来成为授权依据。支付 provider 节点是可替换边界，Shopify 在这里提供对象模型参照；不假定 Shopify 与 Stripe 是同一条已配置链路。

一个可实现的起点是 React 或 Vue 做订单工作台，服务端用 TypeScript/NestJS 或 Python/Django，PostgreSQL 保存订单行快照、库存、分配与资金操作。React 便于复用多步表单，Vue 也能表达同样的状态；选择取决于团队维护成本。PostgreSQL 的事务与唯一约束适合量和金额的竞争更新。队列可先由数据库 outbox 加 worker 承担，量增大后再用托管消息队列；引入队列增加交接点，仍要保留业务唯一键。Redis 可缓存目录和订单列表，不掌握最终可用量。以上是合成技术选项，没有推断 provider 使用这些栈。

## 演算：一分钱和一个仓库怎样分配

优惠分配与仓库分配都叫“分配”，目标却不同。优惠必须精确守恒，仓库安排还受库存和运输成本约束，不能用同一种比例把两者解决。

先把 5 件商品视为稳定 unit ID。总优惠 1,001 分按原价权重分配，三个茶杯各得 `1001 × 4000 / 14000 = 286` 分；两只杯盖各应得 71.5 分。先取整数部分得到 `286,286,286,71,71`，合计 1,000 分；剩下 1 分给余数最大的杯盖，平手按固定 unit ID 排序。因此最终优惠为 `286,286,286,72,71`，实付分别 `3714,3714,3714,928,929`，合计 12,999 分。unit ID 是金额归属身份，不要求商品有实物序列号；同规格商品无法逐件辨认时，本例按最小的尚未退 unit ID 归属退货，并在预览中明确这条规则。金额、余数用整数乘法和整除计算，避免二进制浮点误差。最大余数法全排序代价是 O(n log n)，对普通订单的 n 件商品足够；大批量同价商品可按区间保存分配，仍需稳定映射到可退单位。

顾客后来退回一个茶杯和第一只杯盖，按原快照退款 `3714 + 928 = 4642` 分。若每次都按当前目录价格或把优惠重新分摊到剩余商品，分批退货的总额可能与一次全退不同。朴素地把两只杯盖都四舍五入成 72 分，优惠会变成 1,002 分；反过来都舍去则只优惠 1,000 分。保存接受时的单位分配，是让最后一件也能对齐的原因，不是追求小数显示漂亮。

仓库安排可以先逐 SKU 扫描可用仓库，生成满足数量的可行解，D 个 SKU、W 个候选仓库的简单扫描约 O(DW)。本例库存使两仓拆分成为必要。若优化目标改成最少包裹或最低运费，逐件选“最便宜仓”并不可靠：A 仓只有杯子、发一包成本 4；B 仓有杯子和杯盖、发一包成本 5。先把杯子给 A，再从 B 发杯盖，总成本 9；全部从 B 发只需 5。固定开包成本把不同 SKU 连接起来。小规模可枚举仓库集合验证最优，较大规模可用有时间预算的整数规划或启发式；演示只能把启发式结果称作可行方案。价格算准与履约选优是两项独立验收。

## 退货、退款与结算重新相遇

正常路径中，两仓分别交接、承运证据确认交付；退货申请引用原发货行，仓库收件后检验。茶杯完好返库，杯盖有划痕进入隔离，本例分别增加可售库存 1 和 0。财务按批准金额发起 4,642 分退款，确认成功后才计入已退款合计。未交接商品经核实取消后的退款，依据原订单取消记录发起，无需伪造一个实物退货对象；两种退款都受原付款和原单位实付上限约束。Shopify 文档把 return 定义为买方退回商品的意图，并说明 `returnProcess` 可处理全部、部分或延后退款，以及是否重新入库的处置；这支持把逆向实物和退款分开跟踪。参见 [Build for return management，Step 1 与 Step 9](https://shopify.dev/docs/apps/build/orders-fulfillment/returns-apps/build-return-management#step-9-issue-a-refund-and-dispose-return-items)（`P05-SRC-shopify-returns-C1`；）。

退款记录本身仍不足以宣称资金已成功处理；Shopify 的 `Refund` 文档明确要求查看关联 `OrderTransaction` 状态。参见 [Refund，说明与 transactions](https://shopify.dev/docs/api/admin-graphql/latest/objects/Refund)（`P05-SRC-shopify-refund-C1`；）。本例退款 worker 若在支付方受理后超时，把原尝试保留为 unknown，按支付账户和外部交易身份查询；核对为成功后追加成功证据，不能再创建第二笔退款。重复通知只补全同一效果；晚到的 pending 不能覆盖已核实的成功。Stripe 的文档说明事件可能重复、无送达顺序保证，并要求验证签名；本例借此说明回调消费者的边界，不把 Stripe 事件规则冒充所有仓储系统的保证。参见 [Stripe Webhooks，Event ordering 与 Handle duplicate events](https://docs.stripe.com/webhooks)。

本例再假设支付手续费固定 260 分且不退还，且收款和退款在同一合成结算批次。净待结算额为 `12999 − 4642 − 260 = 8097` 分。它既不是 8,357 分的顾客净支付额，也不是利润；利润还需要成本和其他费用。若 provider 实际先结算收款、后扣退款，应分别显示两批及尚未结算余额，不能强行要求某一笔银行入账恰好等于 8,097。核对顺序是先按交易身份匹配，再核对金额、币种、批次和手续费；金额相同不能证明是同一笔付款。

## 验算：规模与能观察到的失败

合成负载目标为 100 家商店、每店 2 万个活跃 SKU、平台峰值每秒 100 张订单、每单最多 50 行；单个热门 SKU 可占写入的 30%。目录热缓存下读取 p95 目标 200 ms，本地订单接受及占量 p95 目标 500 ms，不含支付和物流网络耗时。这些是待测目标，不是测量结果。缓存 key 包含 tenant、商品版本与币种；发布目录使旧版本停止用于新报价，历史订单不失效。热点库存按仓库和 SKU 串行化条件更新，不能为降低延迟跳过竞争检查。定时扫描最老的 unknown 与未送达 outbox，比只看平均请求延迟更能暴露顾客仍在等待的责任。

检查沿 UI、命令记录、数量账、外部核对和投影逐段收集证据，不能只断言接口返回 200。[结构数据](../../../../vault/distilled/saas-engineering-atlas/packages/commerce-property/V04.json)定义了七种必需路径及额外反例：两人抢最后一件；重复退款通知；迟到的待发状态；跨商店同号订单与缓存；退款受理后断网；占量提交后 worker 崩溃；部分发货取消；不合格退货被错误加回可售库存；分批退款总额溢出；结算扣费遗漏。尤其应保留一个故意错误的实现：把退款成功直接加回库存，它在“已退款但货未寄回”输入下必须失败。本例没有模型参与定价、批准或状态确认，AI eval 不适用。

## 变式：改变条件再做判断

**练习一：南仓实际已交接，但回执丢失，顾客要求取消最后一个茶杯。** 能否立即把剩余 1 件释放并退款？

简答：保持“每一份数量只有一个当前去处”。本地缺回执不证明实物未动，先把该分配放入待核对，查询仓库交接身份；确认未交接才取消并释放，已交接则转拦截或退货政策。反例是先释放后收到交接回执，两个订单共占一件不存在的货。可观察检查是回执迟到后数量不变负、没有第二次售出，顾客页面保留取消待确认的原因。若仓库无法提供身份或交接证据，自动恢复条件失效，交给仓库主管核查。（`TR:V04:V05:irreversible-handoff`）

**练习二：两只杯盖先后分两次退货，目录已经涨价到 1,200 分。** 两次各退多少？

简答：沿原 unit ID 退 928 和 929 分，总共 1,857 分；不是按新价，也不是每次重新均分余下优惠。不变量是这两件的累计退款不超过其原分配实付，整单全退最多 12,999 分。反例是两次都退 929 导致多退 1 分。检查交换退货顺序，累计仍为 1,857。若销售政策允许额外赔偿，另建 goodwill adjustment 并授权，不能把赔偿藏入原商品退款上限。

`TR:V04:V06:partitioned-obligation` 把“总承诺拆成可核对部分”迁到住宿房晚，但商品占量释放与日历时间不同：过去的一晚不能重新卖回库存，日期变化须重新检查容量。`TR:V04:V16:return-and-money` 把“实物验收与资金处置分离”迁到退租和押金；类比止于结构，不能把电商退款期限或可退价套给押金扣款。

## 进入零售履约时先查什么

先用一张跨仓订单及其一次售后，把订单行、仓库分配、运单、退货收件和支付交易逐一对应，要求每个金额和数量都能找到原身份。成熟解法包括 OMS 的拆分履约、库存预留、逆向物流与支付对账；适用前提是能取得足够细的行项目和交接证据。若仓库只有每天汇总表，实时取消就不能沿用这里的自动核对路径。下一步研究应优先查实际连接器的可取消阶段、退货处置、refund transaction 状态与数据更新频率，再补税费、换货和拒付规则。验收从一件货“已出库但回执迟到”开始：订单解释、库存数量和退款责任应保持相容，再扩展到更多仓库。
