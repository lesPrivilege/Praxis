# 第二章：先知道要找什么，再选索引

查找的核心是排除不可能的候选。知道完整编号，可以按 hash 找桶；知道范围，可以利用顺序；知道前缀，可以沿字符路径缩小范围。数据结构预先付出组织与维护成本，使之后的查询少做无用比较。

## 识题：相等、范围与前缀

“找到租户 A 的订单 O7”问相等；“找交付日落在第 10 到第 20 天的订单”问范围；“输入 re 后列出产品”问前缀。它们可能在同一个页面出现，却需要不同索引。先写出查询形状、数据量和更新频率。还要明确找到的是一条、全部匹配项，还是仅前十条；输出一万条至少要付出传送这一万条的成本。

## 解法与演算：四种排除方式

### Hash：先分桶，再比完整身份

设教学 hash 把 `(A,O7)` 放进桶 2，把 `(A,O9)` 也放进桶 2，把 `(B,O7)` 放进桶 5。查 `(A,O7)` 时先到桶 2，再比较完整 key，排除 O9 后返回目标。桶冲突不等于对象相同。实际桶号由所选 hash 函数与表容量决定。

良好散列与合适装载率下，查找的期望成本接近 O(1)，空间 O(n)；拥挤桶会增加比较，扩容还可能搬迁全表。长字符串计算 hash 本身也要读字符。优先用语言的 Map/dict/set；持久化身份约束交给数据库。哈希表机制及其期望、摊还前提见 [Open Data Structures 5.1](https://opendatastructures.org/ods-python/5_1_ChainedHashTable_Hashin.html)。

**误用反例。** 用 `order_number=O7` 当全局 key，A、B 两租户发生覆盖；或者以 hash 值相同就跳过去重。验算必须放入同号不同租户、碰撞但不同 key、缺失 key。并发“先查不存在再插入”也不能靠 hash 解决，要有持久化唯一约束。

### 二分：让候选范围每次缩半

已排序交付日为 `[2,5,8,12,17]`，要求第一个不早于第 9 天的订单。比较中间的 8，左半连同 8 都太早；比较剩余部分的 17，保留左边界；再比 12，得到 12。关键不变量是：答案若存在，始终留在当前候选区间里。对“第一个满足条件”的二分，条件必须沿排序方向单调，即一旦满足，后面也满足。

随机访问有序数组的查找为 O(log n)，一百万项约二十次折半；为一次查询先排序仍需计入排序成本。数组中间插入通常要搬动 O(n) 项，故二分并未把整个更新变成对数时间。[Python bisect](https://docs.python.org/3/library/bisect.html)明确区分查找插入位置与实际插入。

**误用反例。** `[2,12,5,17,8]` 未排序却二分；或询问“第一个有空位的日期”，但空位模式为有、无、有，误以为条件单调。验算先检查排序与谓词；边界覆盖空列表、全早于目标、恰好等于目标及重复值。

### B-tree：把很多分岔放在同一页

数据库不能为每次比较都读一块磁盘。B-tree 把多个有序分隔键放进一个节点，以较大的分支数减少层数。教学根节点存 `[10,20]`，三个孩子存 `[2,5]`、`[12,17]`、`[23,29]`。查 17 时读根，判断落在 10 与 20 之间，再读中间孩子。查 `[12,24)` 则沿有序结构取出 12、17、20、23；分隔键 20 本身也在结果里。配套例子采用最小度数 t=2：非根节点有 1–3 个键，内部节点孩子数为键数加一，所有叶子同深；检查程序同时验证占用、分隔范围与平衡后才枚举区间值。

B-tree 还维持两个条件：所有叶子深度相同，非根节点的占用有下界。只知道一页最多容纳多少分支，不能排除几乎退化成链的树。在分支数上下界都与 B 同阶、根节点允许例外的条件下，树高才与 O(log_B n) 同阶；查询还需计算返回记录的代价。节点满时分裂，写入会维护索引，更多索引意味着更多空间和更新工作。[Open Data Structures 14.2](https://opendatastructures.org/ods-python/14_2_B_Trees.html)给出外存模型；[PostgreSQL Index Types](https://www.postgresql.org/docs/current/indexes-types.html)说明其 B-tree 可用于相等、范围及排序，Hash 索引只支持简单相等比较。

订单列表常按租户过滤、再按到期日和 ID 排序。候选索引可围绕 `(tenant_id, due_at, id)` 研究，是否真正被优化器选择要看查询计划、选择率和返回量。不能因为索引存在就宣称某次查询快。范围查到全表大部分数据时，顺序扫描可能更合算。

**误用反例。** 为所有字段建索引却不观察写入成本；或把内存 hash 的平均 O(1) 直接当成数据库服务的延迟承诺。验算应比较有无索引的实际执行计划、读取页数与写入成本，使用接近真实分布的数据。

### Trie：公共前缀只走一次

产品代码为 `car, cart, cat, dog`。trie 从根依次按字符走边，`ca` 共用一路，后面分成 `r` 与 `t`；`car` 节点还要标明一个词在此结束，否则会把 `car` 与 `cart` 混掉。查询 `ca` 走两步到前缀节点，再枚举其下三项。机制可从 [Open Data Structures 的 BinaryTrie](https://opendatastructures.org/ods-python/13_1_BinaryTrie_digital_sea.html)理解：该来源处理整数的位路径；这里把路径推广为字符，是教学推演。

长度 L 的 key 在每步子边访问为常数的实现中需 O(L)；列出结果还需遍历结果字符。空间随保存的前缀增长，压缩路径与字符表示影响很大。面向多语言、拼写错误和排名的搜索，优先检查成熟数据库或搜索服务能力，trie 只是其中一种候选结构。

**误用反例。** 把前缀搜索当作任意子串或语义搜索；`cat` 不会因“宠物”这个意思自动命中。大小写、Unicode 归一化和分词若不一致，同一可见字符串也可能走不同路径。验算用空前缀、完整词、词前缀、无匹配及归一化后的重复项。

## 验算：索引改变速度，约束保护事实

把四种查询都与少量样本的逐条扫描比较，结果集合应一致。再分开检查三件事：身份是否唯一、读取是否授权、索引是否加快了目标查询。查到一行不证明有权读取；普通索引也不自动成为唯一约束。UI 的自动补全仍须在服务端限定租户和可见范围，不能先取全体候选再靠浏览器隐藏。

## 变式：从发票到样本，从目录到对账

**题一。** H01 的外部发票映射迁移到 V03 的实验样本；不同实验室都有样本 `1001`。仍能用编号查找吗？

**答案。** 可保留相等查找，key 改为明确的组织/实验室与样本身份，外部系统另带 provider scope；结果版本独立保存。反例是用最新样本结果覆盖同号样本。检查两个范围中同号样本互不覆盖，结果修订保留原版本依据。

**题二。** V04 的产品前缀提示被改为 H03 的“金额相同且日期接近的对账候选”。trie 还能直接沿用吗？

**答案。** 需求已变成金额相等与日期范围的组合，研究数据库组合索引或先按金额分组再筛时间；需要同时保留多个候选。金额相同不能证明同一交易。验算应返回候选集合，再由明确匹配规则或人工证据决定是否消除差异。
