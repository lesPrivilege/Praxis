# 第二章：先知道要找什么，再选索引

查找就是排除不可能的候选。数据结构事先花成本组织和维护数据，之后的查询就少做无用的比较。

## 识题：相等、范围与前缀

“找到租户 A 的订单 O7”问相等；“找交付日落在第 10 到第 20 天的订单”问范围；“输入 re 后列出产品”问前缀。三种查询可能出现在同一个页面上，需要的索引却不同。先写清查询条件、数据量和更新频率，再说清要返回一条、全部匹配项，还是前十条：输出一万条，至少要付出传送这一万条的成本。

## 解法：按查询条件排除候选

知道完整编号，可以按 hash 找到桶；知道范围，可以利用顺序；知道前缀，可以沿字符路径逐步缩小范围。

## 演算：四种排除方式

### Hash：分桶与完整 key 比较

设合成例子里的 hash 函数把 `(A,O7)` 放进桶 2，`(A,O9)` 也放进桶 2，把 `(B,O7)` 放进桶 5。查 `(A,O7)` 时先到桶 2，再比较完整 key，排除 O9，返回目标。落在同一个桶里的两个对象未必相同。实际桶号由所选 hash 函数与表容量决定。

hash 分布均匀、装载率合适时，查找的期望成本接近 O(1)，空间为 O(n)；桶一拥挤，比较次数就增加，扩容还可能搬迁全表。对长字符串求 hash，本身也要逐个读字符。优先使用语言自带的 Map/dict/set；需要持久保存的身份唯一约束交给数据库。hash 表的机制，以及期望成本和摊还分析的前提，见 [Open Data Structures 5.1](https://opendatastructures.org/ods-python/5_1_ChainedHashTable_Hashin.html)。

**误用反例。** 用 `order_number=O7` 当全局 key，A、B 两个租户的 O7 会互相覆盖。另一种误用是一见 hash 值相同，就当作重复项跳过。验算样本要包括不同租户的同号订单、hash 碰撞但 key 不同的记录，以及不存在的 key。并发下“先查不存在、再插入”的竞争，hash 也解决不了，要靠持久化的唯一约束。

### 二分：逐次折半的候选区间

已排序的交付日为 `[2,5,8,12,17]`，要找第一个不早于第 9 天的订单。先比中间的 8：左半连同 8 都太早。再比剩余部分的 17：它已满足条件，右边界收到这里，左边界不动。再比 12，得到 12。关键不变量是：答案若存在，始终留在当前候选区间里。找“第一个满足条件”的位置时，条件必须沿排序方向单调：某一项满足，其后各项也都满足。

在可随机访问的有序数组上查找，成本为 O(log n)，一百万项约折半二十次；若为一次查询先排序，排序成本也要算进去。在数组中间插入通常要搬动 O(n) 项，所以二分并没有让更新也变成对数时间。[Python bisect](https://docs.python.org/3/library/bisect.html)明确区分查找插入位置与实际插入。

**误用反例。** 对未排序的 `[2,12,5,17,8]` 做二分。或者找“第一个有空位的日期”，空位却是有、无、有交替出现，误以为条件单调。验算先确认数据已排序、条件单调；边界样本包括空列表、全部早于目标、恰好等于目标和重复值。

### B-tree：一页多分岔

数据库不能为每次比较都读一块磁盘。B-tree 把多个有序分隔键放进一个节点，用较大的分支数减少层数。在合成例子里，根节点存 `[10,20]`，三个孩子存 `[2,5]`、`[12,17]`、`[23,29]`。查 17 时读根，判断落在 10 与 20 之间，再读中间的孩子。查 `[12,24)` 则沿有序结构取出 12、17、20、23；分隔键 20 本身也在结果里。配套例子取最小度数 t=2：非根节点有 1–3 个键，内部节点的孩子数等于键数加一，所有叶子同深。配套的检查程序先验证占用、分隔范围与平衡，再枚举区间内的值。

B-tree 还维持两个条件：所有叶子深度相同，非根节点的占用有下界。只知道一页最多容纳多少分支，排除不了几乎退化成链的树。在分支数上下界都与 B 同阶、根节点允许例外的条件下，树高才与 O(log_B n) 同阶；查询成本还要加上返回记录的代价。节点满了就分裂；每次写入都要维护索引，索引越多，占用的空间和更新工作越多。[Open Data Structures 14.2](https://opendatastructures.org/ods-python/14_2_B_Trees.html)给出外存模型；[PostgreSQL Index Types](https://www.postgresql.org/docs/current/indexes-types.html)说明 PostgreSQL 的 B-tree 可用于相等、范围及排序，Hash 索引只支持简单的相等比较。

订单列表常按租户过滤，再按到期日和 ID 排序。可以考虑 `(tenant_id, due_at, id)` 这样的组合索引；优化器是否真的选用它，要看查询计划、选择率和返回量。范围覆盖全表大部分数据时，顺序扫描可能更合算。

**误用反例。** 给所有字段建索引，却不看写入成本。另一种误用是把内存 hash 的平均 O(1) 直接当成数据库服务的延迟承诺。验算用接近真实分布的数据，比较有无索引时的实际执行计划、读取页数和写入成本。

### Trie：共用的前缀路径

产品代码为 `car, cart, cat, dog`。trie 从根依次按字符走边，`ca` 共用一路，后面分成 `r` 与 `t`；`car` 节点还要标明有一个词在此结束，否则分不出 `car` 本身是词，还是只是 `cart` 的前缀。查询 `ca` 走两步到前缀节点，再枚举它下面的三个词。机制可参考 [Open Data Structures 的 BinaryTrie](https://opendatastructures.org/ods-python/13_1_BinaryTrie_digital_sea.html)：该来源讲的是整数的二进制位路径，这里把路径推广到字符，属于教学推演。

如果每一步访问子边只要常数时间，查长度为 L 的 key 需要 O(L)；列出结果还要遍历结果的字符。空间随保存的前缀增长，是否压缩路径、字符怎样表示，对空间影响很大。要支持多语言、拼写错误和排名的搜索，先看成熟数据库或搜索服务能否满足，trie 只是候选结构之一。

**误用反例。** 把前缀搜索当作任意子串搜索或语义搜索；`cat` 不会因为“宠物”这个意思自动命中。大小写、Unicode 归一化和分词若不一致，看起来相同的字符串也可能走不同路径。验算样本包括空前缀、完整词、词前缀、无匹配，以及归一化后的重复项。

## 验算：扫描对照、唯一约束与读取授权

在少量样本上，四种查询的结果集合都应与逐条扫描一致。此外分开检查：身份是否由唯一约束保证，普通索引不提供这一保证；读取是否经过授权，查得到一行不等于有权读取；索引是否加快了目标查询。UI 的自动补全也要在服务端限定租户和可见范围，不能先取出全部候选，再靠浏览器隐藏。

## 变式：从发票到样本，从目录到对账

**变式题一。** 把 H01 的外部发票映射迁移到 V03 的实验样本，不同实验室都有样本 `1001`。还能按编号查找吗？

**简答。** 能。相等查找可以保留，但 key 要改成明确的组织/实验室与样本身份，外部系统的编号另带 provider scope；各版本结果单独保存。反例是用最新的样本结果覆盖同号样本。验算检查两个范围里的同号样本互不覆盖，结果修订后仍保留原版本的依据。

**变式题二。** 把 V04 的产品前缀提示改成 H03 的“金额相同且日期接近的对账候选”，trie 还能直接沿用吗？

**简答。** 不能直接沿用。需求已经变成金额相等加日期范围的组合查询，可以考虑数据库组合索引，或先按金额分组、再按时间筛选，并同时保留多个候选。金额相同不能证明是同一笔交易。验算时返回候选集合，由明确的匹配规则或人工证据决定是否消除差异。
