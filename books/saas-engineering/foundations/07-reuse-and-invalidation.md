# 第七章：复用结果，也保存它成立的条件

缓存把“这组输入曾得出这个结果”保存下来，下次遇到相同的请求直接复用，省掉重复计算。难处在于判断输入是否仍然相同，以及内存不够时留下哪些结果。

## 识题：纯计算重复与远端状态重复

“同一报价计算一百遍”“同一报表被反复打开”都可以考虑复用。报价函数的输入固定且没有副作用，就可以按输入记住结果；报表来自持续变化的数据，缓存就必须带快照或失效规则。H01 的计价、H07 的报表、H09 的文档版本、X01 的租户服务都可能用到缓存，但它们允许的陈旧程度不同。

## 解法：以输入为 key 的记忆化

设合成服务包 A 价值 3，B 价值 4，组合报价规则只做固定相加。工作台两处都要计算 `price(A,B,rule=v2)`，第一次得 7，第二次复用。规则升到 v3、加收 1 时，key 必须包含 v3，结果才是 8；只用 A、B 作 key，会返回旧价。第六章 DP 的 `(已考虑项目,剩余预算)` 也可以作记忆化 key：递归分解时，遇到相同的子题就查表。

若实际访问 S 个不同的子问题，每个最多做 T 次局部工作，记忆化把重复路径压缩为约 O(ST) 的计算，另付 O(S) 的存储及 key 成本。记忆化并不保证 S 很小；状态不完整会算错，状态分得过细则复用少。[Python functools](https://docs.python.org/3/library/functools.html)提供 `cache` 与 `lru_cache`，并说明即使内部结构线程安全，同一计算在并发首次访问时仍可能执行多次。

**误用反例。** 给 `charge(customer,40)` 加缓存，希望避免重复收费。扣款是副作用，缓存被淘汰或服务重启后仍会再执行；多个实例也不共享同一块内存。防止重复扣款，要靠第九章的持久化操作身份与核对协议。验算时比较缓存命中与未命中的输出，并统计纯函数被调用的次数；带副作用的方法另做业务幂等检查。

## 演算：同一请求序列上的 LRU 与 LFU

### LRU（least recently used，最近最少使用）：按最近访问淘汰

容量为 2，请求序列为 `A,A,B,A,C,B`。按“旧→新”列出缓存：第一次 A 后为 `[A]`，第二次 A 命中；B 后为 `[A,B]`；A 命中后为 `[B,A]`；C 到来淘汰 B，得 `[A,C]`；最后 B 又未命中，淘汰 A，得 `[C,B]`。LRU 在这组序列上命中 2 次、未命中 4 次。

精确的 LRU 通常用 hash 表定位缓存项，用双向链表调整使用先后，访问和淘汰平均 O(1)，空间 O(C)。这里 C 是按项数计的容量；对象大小差别大时，容量必须按字节计算。最近用过的对象很快会再被用到，LRU 才有效；顺序扫描大量一次性对象，会把热点冲出缓存。

### LFU（least frequently used，最不经常使用）：按访问次数淘汰

仍用同一序列，容量 2，合成 LFU 记录驻留项的访问次数，同频时按 LRU 淘汰。A 访问三次、B 一次之后，C 到来淘汰 B，保留 A；最后 B 到来，淘汰只用过一次的 C。结果留下 A、B，同样命中 2 次。这六次请求里两种策略的命中数相同，留在缓存里的项却不同；第七次再访问 A，LRU 未命中，LFU 命中。把第七次 A 接入同一序列，LRU 共 2 次命中、5 次未命中，留下 `[B,A]`；LFU 共 3 次命中、4 次未命中，留下 A、B。检查时两种策略分别计命中与未命中数。

LFU 适合较稳定的热点，但永不衰减的旧热度会压住新热点。精确实现可以用频率桶；朴素地按计数扫描，每次淘汰要多花 O(C)，成本不一定是常数。生产缓存可能采样或估计频率；[Redis Key eviction](https://redis.io/docs/latest/develop/reference/eviction/)明确说明它的 LRU/LFU 是近似实现，LFU 带频率衰减。所以 Redis 不一定每次都按这里的手算淘汰。

**误用反例。** 只拿一次热缓存的演示比较两种策略，真实流量的热点却每天在换。验算应回放相同的请求序列和对象大小，分别观察命中率、未命中代价、内存，以及热点切换后的恢复时间。命中率提高不一定节省成本：命中的若全是便宜的小查询，昂贵的查询仍未命中，收益可能很小。

## 失效：旧结果的可信范围

缓存 key 可以组合 `(tenant, object, object_version, rule_version, locale)`，只加入实际改变结果的维度。与权限相关的投影，key 还要带授权上下文；即使 key 已按身份隔离，服务端仍要检查权限。不可变版本的缓存较容易管理：对象从 v2 变成 v3，直接读新 key，旧 key 稍后回收。列表与聚合依赖许多对象，可以用事件失效、版本水位、较短的存活时限（time to live，TTL），或者重算后切换发布指针；选哪一种，看对新鲜度的要求。

合成竞态如下：读者从数据库取到 v2，暂未写缓存；写者提交 v3 并删除缓存；读者随后把 v2 写回缓存。简单的“更新后删缓存”仍会留下旧值。版本化写入、拒绝较低版本的覆盖、与事务关联的变更事件，以及关键操作直接查权威记录，各自堵住一类边界情形。写回来源和链路延迟也受控时，TTL 才给得出一个说得清的陈旧上限；读副本延迟和失效事件丢失，TTL 本身修复不了。

热点同时过期时，大量请求会一起回源到同一份数据。可以考虑请求合并（single flight）、给过期时间加抖动，以及有限度的后台刷新。允许旧报表临时展示时，要注明输入版本和刷新状态；确认付款、撤权或释放库存之前，则要读取满足业务一致性要求的证据。缓存里旧的“可用”标记，不能当作新的授权。

## 验算：去掉缓存后的业务正确性

检查 cold/warm 两条路径的结果相同，跨租户的同号对象相互隔离，规则与对象修改后不再复用旧 key。注入三种情形：“提交后尚未失效”“失效后旧值回填”“缓存整体丢失”。系统应能从权威记录重建，不因缓存清空而丢失已发生的义务。再测命中率、数据年龄、回源并发和回源错误，不只测一次成功读取的耗时。

## 变式：从报表到批准，从一个进程到多个实例

**题一。** H07 的历史月报缓存，移到 H09 的当前批准核验。**答案：** 不可变的历史版本可以长期复用；当前批准可能因修订或撤回而失效，必须绑定目标版本并核验当前是否有效。反例是缓存了旧批准，放行了新文档。检查撤销后新的执行请求被拒绝，历史审阅记录仍然保留。

**题二。** 单进程 memoization 扩成 X01 的三个 API 实例。**答案：** 各实例重复做纯计算，通常只影响成本；若靠缓存给扣费去重，就会重复计费。纯计算的缓存可以先由各实例分别保存，再测命中率；业务效果要靠共同的持久化边界保证。验算让三个实例同时处理同一操作，观察业务记录数，而不是缓存函数被调用了几次。
