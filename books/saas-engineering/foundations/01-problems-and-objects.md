# 第一章：先看对象，再认题型

一家维修企业接到订单 O7，要交付 3 次服务，每次 40 个记账单位。客户付清 120，技师完成 2 次，第三次在等零件。工作台的“订单状态”若只剩一个绿色标记，财务能解释收款，调度却看不见还欠一次服务：几个对象被压进了同一个字段。解开的办法是把每个动作归回它改变的对象：身份、版本、权限和动作前提决定动作能否执行，汇总值从子对象的事实算出。需求里的量词再把问题归到查找、排序、区间、图、依赖、选择、复用或近似等题型。计算与执行要分开：“还欠几次服务”可在固定输入上算出，“第三次服务能否确认、重试会不会确认两遍”要靠权威记录、并发控制与恢复机制；算式全对时，重复投递和并发修改仍可能造成重复退款或丢失更新。

## 识题：动作归回对象

先把需求改写成“谁对哪个对象做什么，看到什么才算完成”。客户付款改变付款记录；技师提交记录改变一次服务的执行证据；接收人验收改变该次服务的确认状态。订单汇总这些事实，事实本身仍留在各自的对象上。H01 的合同、发票和服务权利，V04 的订单与分批履约，V20 的工单与两次 booking，都可以这样拆开。

对象至少有身份、状态和允许改变状态的动作；一个动作能不能执行，还要看版本、权限和动作前提（guard）。身份确定是哪一件，版本确定是哪一份，权限确定谁可以做，guard 确定在什么条件下可以做。在多租户系统里，`tenant=A, order=O7` 与 `tenant=B, order=O7` 是不同对象；版本 3 得到的批准只属于版本 3，版本 4 要重新批准。状态名应当对应可以核对的事实：`submitted` 只表示请求已保存，`confirmed` 要有接收证据。

读需求时，先标出量词和限制。

| 需求中的线索 | 对应模型 | 候选方法 | 必须追问的条件 |
|---|---|---|---|
| 按编号找到、判断是否重复 | 完整键（key）→ 对象 | 散列（hash）、数据库唯一索引 | 编号的唯一范围 |
| 某日期之后、某价格区间 | 有序集合与边界 | 二分查找、B 树（B-tree） | 边界开闭、数据是否已排序 |
| 输入前几个字就提示 | 前缀 → 候选词 | 前缀树（trie）、搜索服务 | 语言归一化、权限和结果数量 |
| 最急的十项、最大的几笔 | 可比较的记录 | 排序、前 K 项（Top-K） | 并列顺序、公平性、过滤范围 |
| 连续、最近一小时、累计 | 序列与区间 | 双指针、窗口、前缀和 | 事件时间、迟到和负数 |
| 哪些会受影响、最少转几次 | 有方向和含义的边 | 广度优先搜索（breadth-first search，BFS）、深度优先搜索（depth-first search，DFS）、最短路 | 每条边的代价、方向和权限 |
| 全部前提完成才能开始 | 依赖图与就绪集合 | 有向无环图（directed acyclic graph，DAG）、拓扑排序、队列 | 资源上限 |
| 在预算内尽量多、最省费用 | 变量、约束、目标 | 贪心、动态规划（dynamic programming，DP）、搜索、求解器 | 可拆分性、最优要求 |
| 总在重复算、热点访问 | 输入身份 → 可复用结果 | 记忆化（memoization）、最近最少使用（least recently used，LRU）/最不经常使用（least frequently used，LFU） | 过期时机、依赖的版本 |
| 大概多少、相似候选、先排除 | 允许误差的摘要或索引 | HyperLogLog（HLL）、近似最近邻搜索（approximate nearest neighbor search，ANN）、布隆过滤器（Bloom filter） | 错误方向与后续精确核对 |

“去重”两个字至少对应三种问题。两条完全相同的展示行，删掉重复项是集合运算；两次扣款属于同一业务身份时，防止重复扣款需要持久化的业务身份和执行协议；两个名字相似的客户是否同一人，又是证据判断。先认清对象和代价，再确定方法管到哪里。

## 解法：计算与执行分开

维修工作台要回答两类问题。计算问题是“还欠几次服务”：`3 − 2 − 0 = 1`，可由纯函数在固定输入上得到。执行问题是“第三次服务能否确认、由谁确认、重试会不会确认两遍”，要靠权威记录、并发控制与恢复机制。

权威记录（system of record）保存哪些事实，由业务责任决定；投影（read model）把这些事实整理成列表、图表和搜索结果。权威服务可以和投影放在同一个应用、同一个数据库里，也可以分开；一个应用加一个数据库就足以承载这种分工。订单详情显示 `delivered=2`，这只是它读取时的版本；提交第三次服务时，仍要核验当前版本与证据。

一条可以检查的动作链是：人提出动作命令（command） → 服务核验身份、权限、版本和业务约束 → 原子地保存本地决定 → 必要时发起外部动作 → 核对回执 → 更新投影。用户界面（user interface，UI）的 `editing/sending/awaiting/confirmed/conflict` 记录人操作到了哪一步，业务的 `pending/fulfilled/cancelled` 记录对象本身的事实。两套状态分开存放，之间写明映射。

## 演算：从列表到不变量

汇总数字连回子对象，才查得出错误来源，修订之后也能重建。

订单 O7 有三个子项 S1、S2、S3，各 1 次。S1、S2 已确认，S3 待处理。数量不变量为：

`已确认 2 + 待处理 1 + 已取消 0 = 已订购 3`。

<!-- /figure -->

客户申请取消 S3。服务检查 S3 尚未执行，保存取消决定后，数量变为 `2 + 0 + 1 = 3`。退款另开一条请求 R1，金额 40。R1 可能还在等外部结果，所以订单可以显示“服务义务已处理；退款待确认”：取消走完了动作链，退款停在核对回执之前。界面若只显示“订单已结束”，客户会把义务处理与资金到账混为一谈。

<!-- svg: f01-chain -->

把每个数字连回子对象，就能查出错误的来源。`delivered=2` 来自 S1、S2 的确认；`cancelled=1` 来自 S3 的取消决定；`refund_due=40` 来自退款规则和取消数量。每个汇总值都带着输入版本，修订之后可以重建。

## 验算：答案、成本与执行证据

计算正确性的检查从守恒开始：每个数量都不小于零，每个子项只落在已确认、待处理、已取消中的一类，总和回到 3。检查执行可靠性时，把同一取消 command 投递两次，让两个操作员同时修改 S3，让退款请求在发出后超时。即使算式完全正确，这三个实验也可能暴露重复退款或丢失更新。

算法成本说明工作量怎样随输入增加。O(n) 表示扫描次数与记录数大致同阶；O(log n) 表示每次排除固定比例的候选；O(n²) 常来自两两比较。查 1,000 行本地内存与发出 1,000 次远端请求同为线性，延迟却差得很远。真正的规模包括记录数、返回数、租户偏斜、并发、网络、读写比和内存，性能要在具体工作负载上测。

先选最容易核对的正确方法，再找实际瓶颈。一天只有十笔人工审批时，扫描十笔可能已经足够；把它改成分布式缓存，反而增加失效与权限问题。

## 变式：从服务次数到住宿夜数

从服务次数换到住宿夜数，沿用的是“子项证据支持汇总”这条关系，要改的是计价规则与退款 guard。

**变式题。** 把 O7 改为 V06 的三晚住宿，客人已住两晚并提前退房。是否仍可计算 `已住 2 + 已取消 1 = 已订 3`，再自动退 40？

**简答。** 夜数守恒仍可作为台账的检查；退款金额要重新建模，因为提前退房费用、不可退款条款和已产生的消费都可能改变金额。反例是一见夜数减少就机械地减账单。验算时分别比较住宿区间、folio 明细、退款决定和到账回执。
