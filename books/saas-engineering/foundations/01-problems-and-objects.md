# 第一章：先看对象，再认题型

一家合成维修企业接到订单 O7，要交付 3 次服务，每次 40 个记账单位。客户付清 120，技师完成 2 次，第三次等待零件。工作台的“订单状态”若只剩一个绿色标记，财务能解释收款，调度却看不见欠交。问题出在对象被压成了一个字段，换框架或增加动画都不能补回这项事实。

## 识题：把动词还给对象

先把需求改写成“谁对哪件对象做什么，看到什么才算完成”。客户付款改变付款记录；技师提交记录改变一次服务的执行证据；接收人验收改变该次服务的确认状态。订单汇总这些事实，但不能替代它们。H01 的合同、发票和服务权利，V04 的订单与分批履约，V20 的工单与两次 booking，都适合用这个方法拆开。

对象至少有身份、状态和允许改变状态的动作。身份回答“哪一件”，版本回答“哪一份”，权限回答“谁可以”，动作前提（guard）回答“在什么条件下可以”。在多租户系统里，`tenant=A, order=O7` 与 `tenant=B, order=O7` 是不同对象；版本 3 的批准也不会自然覆盖版本 4。状态名应对应可核对的事实。例如 `submitted` 只承诺请求已保存，`confirmed` 要有接收证据。

自然语言往往已经给出计算结构。阅读时标出量词和限制，比搜索框架名字更有效。

| 需求中的线索 | 先建立的模型 | 候选方法 | 必须追问的条件 |
|---|---|---|---|
| 按编号找到、判断是否重复 | 完整键（key）→ 对象 | 散列（hash）、数据库唯一索引 | 编号在哪个范围唯一 |
| 某日期之后、某价格区间 | 有序集合与边界 | 二分查找、B 树（B-tree） | 边界是否包含、数据是否已排序 |
| 输入前几个字就提示 | 前缀 → 候选词 | 前缀树（trie）、搜索服务 | 语言归一化、权限和结果数量 |
| 最急的十项、最大的几笔 | 可比较的记录 | 排序、前 K 项（Top-K） | 并列顺序、公平性、过滤范围 |
| 连续、最近一小时、累计 | 序列与区间 | 双指针、窗口、前缀和 | 事件时间、迟到和负数 |
| 哪些会受影响、最少转几次 | 有方向和含义的边 | 广度优先搜索（breadth-first search，BFS）、深度优先搜索（depth-first search，DFS）、最短路 | 每条边的代价、方向和权限 |
| 全部前提完成才能开始 | 依赖图与就绪集合 | 有向无环图（directed acyclic graph，DAG）、拓扑排序、队列 | 资源是否也有限 |
| 在预算内尽量多、最省费用 | 变量、约束、目标 | 贪心、动态规划（dynamic programming，DP）、搜索、求解器 | 可拆分吗、是否要求最优 |
| 总在重复算、热点访问 | 输入身份 → 可复用结果 | 记忆化（memoization）、最近最少使用（least recently used，LRU）/最不经常使用（least frequently used，LFU） | 结果何时过期、依赖哪些版本 |
| 大概多少、相似候选、先排除 | 允许误差的摘要或索引 | HyperLogLog（HLL）、近似最近邻搜索（approximate nearest neighbor search，ANN）、布隆过滤器（Bloom filter） | 错误方向与后续精确核对 |

“去重”不能独自决定算法。删除重复的展示行是集合运算；防止重复扣款需要持久化业务身份和执行协议；两个名字相似的客户是否同一人又是证据判断。先识别对象和代价，方法才有明确的工作范围。

## 解法：把一件事分成计算与执行

合成维修工作台需要两种答案。计算回答“还欠几次服务”：`3 − 2 − 0 = 1`。执行回答“第三次服务能否确认、由谁确认、重试会不会确认两遍”。前者可由纯函数在固定输入上得到；后者需要权威记录、并发控制与恢复机制。

权威记录（system of record）保存哪项事实，以业务责任决定；投影（read model）把这些事实整理成列表、图表和搜索结果。权威服务可以与投影同在一个应用和数据库里，也可以分离。分开职责不要求先建微服务。订单详情展示 `delivered=2`，只是它读到的版本；提交第三次服务时仍应核验当前版本与证据。

一条可检查的动作链是：人提出动作命令（command） → 服务核验身份、权限、版本和业务约束 → 原子保存本地决定 → 必要时发起外部动作 → 核对回执 → 更新投影。用户界面（user interface，UI）的 `editing/sending/awaiting/confirmed/conflict` 处理人的操作进度，业务的 `pending/fulfilled/cancelled` 描述对象事实。两套状态之间应有映射，不能直接绑定一个布尔值。

## 演算：从一张列表走到一条不变量

订单 O7 有三个子项 S1、S2、S3，各 1 次。S1、S2 已确认，S3 待处理。数量不变量为：

`已确认 2 + 待处理 1 + 已取消 0 = 已订购 3`。

客户申请取消 S3。服务检查 S3 尚未执行，保存取消决定后，数量变为 `2 + 0 + 1 = 3`。退款请求另建 R1，金额 40。R1 可能仍在等待外部结果，因此订单可显示“服务义务已处理；退款待确认”。若界面仅显示“订单已结束”，客户会把义务处理与资金到账混为一谈。

将每个数字连回子对象，可以查出错误的来源。`delivered=2` 来自 S1、S2 的确认；`cancelled=1` 来自 S3 的取消决定；`refund_due=40` 来自退款规则和取消数量。汇总值都带输入版本，修订后能重建。这个小例子同时给后续章节提供查找 key、数量累计、依赖、异步任务和测试断言。

## 验算：答案、成本与执行证据

计算正确性的检查从守恒开始：不能有负数量，不能把同一子项同时算作已交付和已取消，总和必须回到 3。执行可靠性的检查则把同一取消 command 投递两次、让两个操作员同时修改 S3、让退款请求发出后超时。三个实验即使算式完全正确，也可能暴露重复退款或丢失更新。

算法成本说明工作量怎样随输入增加。O(n) 表示扫描次数与记录数大致同阶；O(log n) 表示每次排除固定比例候选；O(n²) 常来自两两比较。它们不直接给出毫秒数。查 1,000 行本地内存与发出 1,000 次远端请求同为线性，延迟却很不一样。真正的规模包括记录数、返回数、租户偏斜、并发、网络、读写比和内存，性能需要在具体工作负载上测。

先选择最容易核对的正确方法，再找实际瓶颈。一天只有十笔人工审批时，扫描十笔可能已经足够；把它改成分布式缓存，反而增加失效与权限问题。复杂度是排除不可扩展方案的工具，不是自动选择最复杂方案的理由。

## 变式：从服务次数到住宿夜数

**题目。** 把 O7 改为 V06 的三晚住宿，客人已住两晚并提前退房。是否仍可计算 `已住 2 + 已取消 1 = 已订 3`，再自动退 40？

**答案。** 夜数守恒仍可作为合成台账的检查；退款金额必须重新建模，因为提前退房费用、不可退款条款和已产生消费可能改变金额。保持“子项证据支持汇总”的关系，改变计价规则与退款 guard。反例是夜数减少就机械减账单。验算应分别比较住宿区间、folio 明细、退款决定和到账回执。这是从 V20 到 V06 的机制迁移，不是行业规则继承。
