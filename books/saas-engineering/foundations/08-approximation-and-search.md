# 第八章：用可说明的误差换取空间与速度

“可能见过”“大约多少”“最相似的候选”分别对应集合成员筛选、去重数量估计和近邻搜索。三者都可牺牲某种精确性，但错误的方向与补救方式不同。先说明允许怎样错，再选择近似方法。

## 识题：近似结果要交给谁使用

H07 的趋势报表可以展示估算，X01 的用量结算需要按契约核对精确事实；H06 的知识检索可以先给候选，H08 的封禁决定不能凭“相似”自动生效。适合近似的是探索、预筛与候选召回，业务确认是否允许误差仍由具体承诺决定。

## 解法与演算：三种摘要保留了什么

### 布隆过滤器（Bloom filter）：用共享位图证明一部分不存在

合成位图有 8 位、两个 hash。插入 A 时把第 1、4 位设为 1；插入 B 时把第 4、6 位设为 1。查询 C 的位置为 1、6，两位都是 1，所以回答“可能存在”，即使 C 从未插入。查询 D 的位置为 2、6，第 2 位为 0，便回答“确定不在这个过滤器所表示的集合里”。

它只保存若干位被点亮，丢掉了是哪条记录点亮的信息；所以阳性要到精确集合核对。在 hash 一致、插入已完整同步且没有错误清位的条件下，已插入元素不会因标准 Bloom 算法产生阴性。分布式同步落后仍会让新对象查成不存在，这属于运行问题。[Redis Bloom 文档](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)说明误报、容量与查询语义。

插入/查询要算 k 个 hash，成本 O(k)，位图空间 m 位。若每次落点独立且均匀，插入 n 项后的 kn 次落点都避开某一位的概率是 `(1−1/m)^(kn)`，约为 `exp(−kn/m)`。再近似把查询涉及的 k 位视为独立，误报率便是 `(1−exp(−kn/m))^k`。这是参数估算，不是每组数据的精确概率。固定目标误报率时空间随 n 增长，要求更低误报也需更多空间。工程上交给成熟实现按预计容量和错误预算选参数，实际测误报率。

**误用反例。** 把“可能存在”当成付款事件已处理而直接丢弃，会漏记真正的新事件。普通 Bloom 也不能随意把某项对应位清零，因为这些位可能与别项共享。验算用精确集合产生真值，分别统计误报和已插入项漏报；漏报首先检查同步、重建与删除协议。

### HyperLogLog（HLL）：用稀有位模式估计不同元素数

随机 hash 后，连续很多个前导零很少见；见过的数据越多，遇到这种模式的机会越大。HLL 用 hash 前几位分桶，剩余位中首个 1 的位置更新各桶最大值，再用经过校正的组合估计去重数。[Flajolet 等人的原论文 §1、Figure 2](https://algo.inria.fr/flajolet/Publications/FlFuGaMe07.pdf)给出算法与约 `1.04/√m` 的渐近标准误差；m 为寄存器数，这不是每一次估计的最大误差保证。

为看清更新，取仅 4 个桶的教学示意，初始寄存器 `[0,0,0,0]`。A 的 hash 写成 `00|001…`，首个 1 在剩余串第 3 位，得到 `[3,0,0,0]`；B 为 `00|01…`，第 2 位不足以替换 3；重复 A 仍不变；C 为 `10|0001…`，得到 `[3,0,4,0]`。这解释了重复项为什么不增加信息。四桶只用于演示，不把它套进大样本公式宣称得到可靠人数。

实际实现含小范围等校正。每项更新访问一个寄存器，常见固定宽度 hash 模型下 O(1)，空间主要由精度参数决定；兼容 hash、寄存器布局与精度的摘要可逐桶取最大值合并，合并成本 O(m)。[Redis HLL 文档](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/)给出其实现的内存与标准误差说明，可作为产品能力参照。

**误用反例。** 周一独立访客约 100、周二约 100，直接相加得到两日独立访客 200。两日可能完全重合，应合并兼容摘要或精确去重。HLL 不能列出这些人，也不能当精确扣费明细。验算按多个已知精确集合和不同基数比较相对误差分布，重复项与重复合并不应改变摘要；不能以一次碰巧相等作为精度证明。

### ANN：少看一些向量，争取找回最邻近的候选

向量把对象映射到一个可计算距离的空间，近似最近邻搜索（approximate nearest neighbor search，ANN search）为减少比较而容许漏掉真正最近的点。HNSW（hierarchical navigable small world，分层可导航小世界）用多层邻近图缩小搜索范围；其结构直觉见 [Malkov 与 Yashunin 论文摘要](https://arxiv.org/abs/1603.09320)。

合成查询向量 Q=(0,0)，四篇文档 A=(1,0)、B=(0,2)、C=(3,0)、D=(4,0)。欧氏距离为 1、2、3、4，精确 Top-2 是 A、B。一个受搜索预算限制的候选过程只见到 A、C、D，再精排返回 A、C，`recall@2=|{A,C}∩{A,B}|/2=1/2`。把候选重排得再准确，也找不回从未召回的 B。

精确扫描 n 个 d 维向量通常需 O(nd) 距离工作；ANN 的时间、内存和召回率取决于索引、维度、分布与搜索预算，不给所有数据一个固定 O(log n) 保证。数据较少或过滤很强时，先精确查询可能更直接。[pgvector README 的 Indexing、Filtering](https://github.com/pgvector/pgvector)解释精确/近似索引以及过滤后结果不足的问题。

**误用反例。** 搜全租户向量后只在页面过滤，既可能泄露信息，也可能把前 k 项都过滤掉；或用语义相似度证明证据支持某结论。正确做法要把授权范围纳入检索与返回协议，在相同过滤范围内测召回，再评估候选是否真的回答业务问题。

配套 ANN 演算要求查询与所有向量具有相同的正维数，坐标是有限数值（配套脚本没有处理相减、平方后超出浮点范围的极大坐标，这时精确排序可能出错），k 是 1 至向量总数之间的整数，候选 ID 已存在且不重复。候选集可以少于 k；此时 recall 的分母仍是精确 top-k 的 k，不能靠缩小分母美化缺失。

## 验算：错误预算有分母、有方向

Bloom 的误报率分母是实际不存在的查询数；HLL 比较估算与精确基数，报告误差分布；ANN 的 recall@k 比较同范围、同距离规则的精确 Top-K。业务相关性又是另一层标签。测量还要固定输入、索引参数与版本，记录构建时间、增量更新延迟、内存和查询尾延迟。

## 变式：从检索到计费，从推荐到证据

**题一。** X01 的大概活跃用户数改为按独立用户精确收费。**答案：** HLL 可保留为趋势或异常比较，收费要回到可审计的精确身份与计量记录。反例是估算多 1% 就多收 1%。检查账单能回查到每项应计费身份与规则版本。

**题二。** H06 的常见问题（frequently asked questions，FAQ）候选检索迁移到 V18 的证据检索。**答案：** 可保留 ANN 召回机制，但改变遗漏代价、权限、保全、来源与版本要求，通常需要关键词/结构化检索补充及人工复核。检查已知必须找到的证据是否被漏掉，检索候选与可提交证据分开记录。

**题三。** V04 商品缓存前的 Bloom 被用于 V12 放款请求去重。**答案：** 阴性可在同步条件满足时省一次无效查询，阳性必须查权威操作台账；放款去重依赖持久化唯一业务身份。把 Bloom 当台账会把一次误报变成漏放款。
