# 第二章　企业前端的工作面与契约

上一章的采购链里有五类事实、几个责任人和一个暂时未知的付款结果。用户不会逐条去读数据库记录；他要先发现异常，再弄清依据，在权限之内作出决定，最后确认决定是否生效。企业界面怎样组织，要看能不能帮人走完这条判断链。表格、表单、详情页、工作台、看板、批量操作和设置在企业软件里反复出现，是因为它们各自对应一种工作方式：比较一组对象、提出一项变更、检查一个对象、处理不断到来的队列、观察整体、对一组对象执行同一动作，以及修改后续动作要用的规则。选哪种工作面，看用户这次要下什么判断；每种工作面都要把后端的版本、权限和结果语义带到页面上。

## 识题：按用户要下的判断选页面

先问清用户这次打开页面要决定什么，再定信息密度和动作的位置。主管每周找一次异常，会计每天处理几百张发票，两人读的可能是同一批对象，需要的工作面却不同。

| 判断任务 | 工作面 | 页面保留的后端语义 |
|---|---|---|
| 比较、筛选、排序同类对象 | 表格或列表 | 查询范围、稳定身份、排序与分页语义 |
| 提出或修改事实 | 表单 | 字段规则、草稿、版本前提、提交结果 |
| 判断一个对象能否推进 | 详情页 | 证据、关系、历史、可用动作及拒绝原因 |
| 边查证边处理队列 | 工作台 | 任务归属、领取冲突、交接与下一件 |
| 观察趋势、分布和异常 | 看板 | 指标定义、分母、时间、数据新鲜度与下钻集合 |
| 对明确的集合执行同一动作 | 批量操作 | 选择范围、逐项版本、部分成功与恢复 |
| 修改规则、角色、模板与集成方式 | 设置 | 配置作用域、生效版本、影响预览与审计 |

一个“管理控制台”可以同时包含这几种工作面，一个“详情抽屉”也可能装下一次完整的决策。判断标准是：用户能否看到足够的依据，并能把动作结果追溯到权威记录。

## 解法：为每种工作面定契约

每种工作面对应一份后端契约：查询范围、版本前提、操作身份和部分成功的结果，都要在页面上有落点。

### 表格让比较可以重复

表格把同一种对象的同一属性放在相同位置。会计沿列比较金额、到期日与异常原因，比逐张打开卡片更容易发现偏差。列多本身没有错；错在把与当前判断无关的字段，和必须看到的字段混在同一层。

以待匹配发票表为例，首要列是发票身份、供应商、币种金额、匹配状态、阻塞原因和下一责任人；创建时间、解析器版本等字段可以放进详情。长名称被截断时，要能读到完整文本；金额省略显示时不能丢掉币种；排序时空值不能悄悄排成最大金额。

后端查询必须回答：搜索哪些字段，过滤条件怎样组合，排序发生在整个结果集还是当前页，同值时怎样稳定排序，翻页期间新增记录怎么办。一种可行的契约是按 `(due_at, invoice_id)` 排出稳定次序，由游标保存查询与排序条件；需要冻结批量集合时，再返回快照身份。普通浏览不一定要数据库快照，但不能把一个不断变化的列表称作“已选全部的固定集合”。缓存键还要包含租户、权限范围和查询条件。

Carbon 把全表工具栏、逐行动作与批量动作分开；进入批量模式后，它建议禁用逐行动作，让用户看清当前作用范围。可以借用的是它减少作用对象歧义的做法。[Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines)。

表格要不要做成交互网格（grid），看用户是否需要在单元格之间移动、编辑和选择。只展示数据时，原生表格通常就够了；一旦要在单元格间导航、编辑和选择，就得管理焦点、方向键和编辑模式。万维网联盟（World Wide Web Consortium, W3C）的 ARIA Authoring Practices Guide（APG）写明了 grid 的这些键盘职责；ARIA（Accessible Rich Internet Applications）是为网页控件补充无障碍语义的一组属性。给普通表格加上 `role="grid"`，并不会自动具备这些行为。[Grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)。

### 表单把输入变成有依据的请求

表单按用户要做的动作来设计，不照搬数据库表。用户想的是“修订发票”，不会去想“更新 invoice 表的哪几列”。系统只让用户填写本次动作需要的字段，并展示必要的依据：原金额、修改原因、附件关系、变化后的影响。不可编辑的字段与当前值一起显示，能减少重复输入和误认。

本例的发票修订表单接受数量、对应的供应商修订凭据与原因，金额按已确认单价计算。提交时带 `invoice_id、expected_version、operation_id`。服务端先检查字段类型与范围，再检查业务约束与权限。客户端即时校验可以减少无效输入，不能替代服务端的决定。

草稿和正式提交要分开：自动保存的草稿可以恢复意外关闭的输入，但还不是正式请求。正式提交后即使超时，也不能显示成“没有保存”。恢复页面时，按同一个操作身份查询，告诉用户当前是未受理、受理后等待、明确拒绝还是结果未知。

错误提示应指向用户能改动的地方。GOV.UK 的 error summary 模式同时提供页首错误摘要与字段旁错误，把摘要链接到对应字段，并管理键盘焦点。[Error summary](https://design-system.service.gov.uk/components/error-summary/)。“验收不足”则不同：会计不能靠改数量消除它，页面应把它显示为业务阻塞，并指向验收责任人或有依据的修订动作。

### 详情页解释一项决定的依据

详情页围绕一个对象组织信息，但不能只显示它自身的字段。决定发票能否付款，需要采购承诺、验收数量、已分配数量、当前发票版本与授权。关系是决策依据，不是装饰性的“相关记录”。

详情页可以依次回答：我正在看什么版本，目前到了哪里，依据是什么，有哪些分歧，谁可以做下一步。活动历史应区分用户提交、服务接受、外部确认和业务接收；把它们都写成“操作成功”会抹去关键差别。正文附件、权限敏感的内容和过期引用，也要按各自的权限读取，详情页能打开，不等于所有附件都可见。

长时间的操作应有可以重新进入的操作记录。用户刷新、离开或换设备，都不应失去查询付款结果的入口。临时提示（toast）适合提醒有了变化，但不能作为唯一的回执。

### 工作台按责任组织队列

工作台适合持续处理一类工作。常见的安排是左侧挑待办、中间看证据、右侧执行动作；无论怎样布局，切换任务时上下文和责任都不能丢。

领取任务不等于拥有业务对象。一个操作员打开了发票，另一个人仍可能更新验收。若需要排他处理，后端要有领取者、租约或显式分派；若允许并行，只需在提交时检测版本冲突。不要用“当前在线”图标暗示对象已被锁定。用户离线、请假或浏览器崩溃后，任务要能重新分配，已有草稿与正式动作分别处理。

队列也不该只按创建时间排序。等待外部回执、等待另一部门补件和等待本角色行动，是不同的等待原因。把它们混在一列“待办”里，用户会反复打开自己无权处理的记录。队列应显示下一责任人、下一可行动时间与升级条件；计时规则要写明是否暂停、为何暂停。

### 看板描述集合

有了看板，就不必翻看全量记录，适合发现“本周异常率上升”“某队列积压”这类情况。每个指标都要有对象、过滤条件、时间口径与分母。本例的“处理率”可能是 9/10 张发票已处理，9/10 台到货已合格，或者 9/12 台承诺量已结算，三个数字回答的是不同的问题。

下钻时要沿用指标所用的集合和口径。如果看板显示的是昨天 18:00 的快照，点进去却打开实时全量列表，两边数字对不上时，页面要能说明原因。外部回执已收到、尚未进入投影的，也要计入数据新鲜度和待核对数量。

### 批量操作改变错误处理

“全选”首先是集合问题：当前页的 25 条，还是满足筛选的 2,430 条？本例的交互分两步：先列出可见的候选集合并预检权限、状态和版本，再确认动作。预检只帮助用户了解影响，正式执行时仍要逐项重新校验。

批量更新可以全有或全无，也可以逐项独立完成，取决于业务：同一张凭证的借贷行可能需要一起成立，不同供应商的发票通常应能分别处理。若允许部分成功，结果记录必须逐项包含对象 ID、所用版本、操作 ID、状态与原因。重试时只重发失败的那部分，已成功的项目不再发起。

取消批任务，只是停下尚未执行的部分；已发出的外部操作仍要核对。页面要分别计数“已完成”“未开始”“结果未知”。进度条到 100% 可以表示任务已遍历完毕，文案要说明其中有多少失败项和待核对项。

### 设置是后续动作的规则

金额阈值、角色映射、计价模板、营业日历和集成目标都会改变后续行为，设置页因此也是业务工作面：谁能提议，谁批准，在哪些组织生效，何时生效，旧单据用旧规则还是按新规则重算。

配置预览应拿有代表性的输入演示改动前后的差异。例如把“必须验收”改为“仅需收货”，应显示哪些在途发票的资格会改变。批准配置的人不一定有权批准这些发票本身。配置生效时，要保存配置版本、变更理由和回退方案；表单的版本问题在设置页同样存在，只是牵涉的对象更多。

## 演算：把 EM-E01 的事实接到页面

页面把 EM-E01 的数字逐层展开：列表给状态摘要，详情给来源，匹配与付款是由不同的人授权的两个动作。

会计从“待处理发票”进入 `INV-9`。列表上显示简短状态“等待验收或单据修订”，详情里展开为“采购 12 台；已收 10；合格 9；本票 10；可用合格量 9；缺口 1”，并可直接进入这些数字的来源和相关记录。

取得供应商的修订后，会计提交版本 2 的 9 台发票，后端确认 720,000 分与有效依据一致，返回新版本。会计点击“匹配”，生成操作 `MATCH-17`；成功后页面显示已占用 9 台、剩余合格量 0。随后由资金人员进入单独的付款动作，看到金额、收款目标的已确认版本与依据；会计页面上的“匹配成功”不能代替这一步授权。

简化的匹配命令：

```json
{
  "command": "match_invoice",
  "object_id": "INV-9",
  "expected_version": 2,
  "operation_id": "MATCH-17",
  "evidence_versions": {"PO-17": 1, "INS-9": 1},
  "rule_version": "PUR-3"
}
```

操作者与租户取自服务器已验证的会话；请求里即使写了另一个租户，也改变不了访问范围。返回值至少区分已接受、已拒绝与版本冲突；异步动作另外提供可查询的操作身份。

| 服务端结果 | 页面显示 | 用户下一步 |
|---|---|---|
| 匹配完成，分配 9 台 | 已取得付款资格，720,000 分 | 有权人员进入付款授权 |
| 版本冲突，验收已改 | 展示原依据与当前差异，保留输入 | 重读差异并重新提交 |
| 权限拒绝 | 动作没有执行；说明所需角色或交接路径 | 请求适当的责任人处理 |
| 付款已提交但响应中断 | 同一 PAY-17 结果待核对 | 查询原操作，不创建新付款 |
| 银行已结算、列表投影未到 | 操作详情已有确认，列表正在同步 | 保留权威结果并刷新投影 |

批量的情形：会计选择 4 张发票，预检显示 A、B 可匹配，C 缺验收，D 无权限。确认时集合冻结为 A、B。执行前 B 又被修订；A 成功，B 冲突。批任务应报告候选 4、排除 2、提交 2、成功 1、冲突 1，各类别不能混用分母。修复 B 后只重试 B，A 不会再分配第二次。

## 验算：沿一次动作逐层检查

视觉检查要和业务检查连在一起：表格列对齐，用户才好比较同类数量；错误摘要能获得焦点，用户才能就地修正输入；操作页能重新进入，未知结果才找得回来。

| 场景 | 通过条件（界面与后端） |
|---|---|
| 同号异租户发票 | 搜索、详情、附件、缓存和批任务都留在授权范围 |
| 点击提交后刷新 | 凭操作身份找回结果，没有产生第二笔业务意图 |
| 详情停留期间版本改变 | 提交被拒绝或按明确的合并规则处理，不覆盖未知修改 |
| 批量部分成功 | 成功记录有回执；只重试失败项；未知项单列核对 |
| 键盘处理一张异常发票 | 选择、详情、证据、提交、错误恢复全程可达，焦点不丢失 |
| 看板数字与列表不同 | 能定位时间、范围或投影延迟的差异，指标口径可复算 |
| 修改设置 | 能看见作用域、版本、生效时间和受影响对象；执行时按指定规则重验 |

空状态有四种：真的没有待办、筛选无结果、没有权限、数据尚未载入。全都显示成“暂无数据”，用户在最需要判断的时候反而失去了依据。

## 变式：改变选择范围与工作节奏

选集合、保留对象与权限、识别分母的做法可以复用；动作的后果、设备与网络条件或进度的口径一变，完成条件跟着变。

**变式一：批量动作从“标记已阅读”改成“发起付款”。** 选集合的方式可以复用，后果和完成条件却变了：每笔付款都要绑定金额、目标、授权和唯一的操作身份；结果未知的保留核对路径；取消只影响尚未发送的部分。检查重试整批时，已发出的付款引用没有变化，新的操作身份也不能绕过仍在途的业务义务。

**变式二：用户从办公室电脑转到仓库手机。** 对象与权限不变；狭窄屏幕可能更适合卡片和逐件确认，而不是横向缩小几十列的表格。编号、数量、单位和异常原因必须保留，离线草稿要注明尚未提交。网络恢复后重新检查版本；“离线确认 10 台”不能覆盖另一人已经记录的退货。

**变式三：看板显示“90% 完成”，负责人要据此关闭采购单。** 先识别分母。9 台已结算占 10 台到货的 90%，只占 12 台承诺的 75%。能否关闭，取决于剩余 3 台怎样处理以及相关的接收条件。检查下钻对象与承诺量，不能把一个视觉进度直接变成关闭命令。

界面讲清了这些条件，agent 才可能按同样的工作语义行事。
