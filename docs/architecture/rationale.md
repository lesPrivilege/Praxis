# Praxis 的架构理由

本文是Astra对多轮材料的编订。采纳的是能够约束当前仓库和后续实现的理由；它不替外部产品、模型机制或未来训练路线作事实背书。

当前状态：用户确认本轮材料不存在企业数据。以下数据分区是为后续真实工作预留的架构契约，不表示当前仓库已经持有客户资料。

## 为什么是Kit与环境契约

Praxis处理的不止一种文体或工具动作。它连接企业工作对象、材料来源、人员角色、账号scope、模型路由、review和交付。它们拥有不同的数据归属、生命周期和执行责任，因此需要可分别维护和检查的结构。

企业邮件、会议、联系人和原始文件属于组织Source Vault；客户项目保存业务state和客户差异；secret与机器配置在受控环境管理；Kit保存规则、参考、模板与可复用成果。资料进入模型、工具或导出物之前，应有明确scope和用途，不能因为某个agent能访问就默认可以跨域消费。

这直接产生当前目录与未来实现边界：vault保存Kit研究资产，kit承载消费契约，docs记录裁决，scenario定义闭环，demo运行合成/受审查fixture，真实项目另行管理。本文中的vault不是客户Source Vault的别名。

数据隔离最终需要权限、存储、工具接口和runtime落实。当前仓库提供的是可检查契约，尚未实现这些执行控制；文字声明不能被当作安全控制已经生效的证据。

## 为什么Skill保持薄

Kit维护长期grammar、证据、政策、工具索引、样例、评估与版本关系；Skill负责一种具体工作怎么开始、需要什么输入、读哪部分Kit、调用什么能力、交付什么以及如何验收。

这种划分让信息按任务渐进消费，并让同一条规则只有一个权威维护位置。写PPT、会议抽取和访谈整理可以共享证据与数据边界，同时保留不同的操作方法。把它们组织为独立入口，能够减少重复文案和局部变更的影响面。

Expert表达工作职责；runtime/model表达执行选择。这是产品与维护职责的划分，不是宿主指令优先级。Kit、Skill和Expert命名都不能自行提升权限或覆盖用户指令。

## 抗折旧来自什么

对象、状态、规则、证据、决定、人工修改和验收标准，来自实际工作及其责任关系。模型可以帮助发现或改进这些结构，但每次任务重新猜一遍会增加不一致和验证成本。把已验证结构留成契约，使不同人、不同session和不同runtime拥有共同起点。

相对值得长期维护的是工作schema、来源定位、review事件、fixture、eval与迁移记录；更容易变化的是某一模型版本的提示技巧、插件接口和执行步骤。模型能力进步后，可以减少手工步骤，仍以相同业务结果与验收要求检验替换是否成功。

“稳定”需要真实场景支持，并允许修订；不能把当前字段清单称为永恒本体。具体哪类模型更便宜、更快、更可靠，需要任务数据与实际费用回执，而非名称或宣传推断。

## Trace的价值与限度

语义trace连接任务、来源、规则、提议、人工修正和结果，首先用于复盘、回归评估和分工改进。未来是否用于训练是另一项需要数据权限、用途和效果验证的决定。存在trace不等于可以训练，拥有字段也不能保证训练收益。

关于attention权重如何影响遵守、模型何时内化专业语义，以及后训练是否必然替代编排，均保留为待验证假说。架构采用可观测的行为、边界和验收结果，而不依赖这些假说成立。

## 当前与跨项目消费

当前Praxis采纳知识组织、薄Skill入口方向、数据分区契约和评估优先原则。Courtwork的Expert实体、composer选择器、extension切换、独立Praxis Agent、harness fork与训练系统属于其他项目或后续实现。

这些建议保存为带来源、状态和触发条件的交接条目。它们可被相关项目消费；只有项目owner接受、实现并验证之后，才能更新为已落地能力。不要用Praxis中的文档替代其他项目的设计裁决。

具体边界见 [ADR-006](../decisions/006-demo-project-vault.md)、[ADR-007](../decisions/007-environment-expert.md)；研究来路见 [r3提炼](../../vault/distilled/work-system/r3/README.md)。

[r4 治理与抗折旧澄清](../../vault/distilled/work-system/r4/README.md) 补充上述理由与边界，不改变已采纳架构，也不新增 runtime 实现承诺。
