# ADR-022：来源卡由谁维护要在 catalog 里声明，以及自足性审查的处置

日期：2026-10-02。状态：accepted（catalog 的一个字段、生成脚本与校验的范围、三处当前状态的校订）。用户当日交来一份没有署名的《Praxis 自足性审查与最小增量方案》，没有另加说明。Opus 5.5 主会话逐条对回本地、在隔离副本里实跑、裁决并编订，没有派代理。Luna 在本会话不可用。改动没有提交。

## 问题

[修订流程](../governance/evolution.md)写着“生成索引从明确的入账和来源记录重建；新批次接入须能重复生成相同结果”，[脚本说明](../../scripts/README.md)把来源卡列为 catalog 的生成投影。审查从静态阅读指出社区语法一批对不上：catalog 用 `card_path` 把 45 个链接聚成 13 张卡，生成脚本却固定一个 slug 写一张。

主会话把 `ff96b9a` 导出到隔离目录，照脚本说明运行了一次 `render_source_cards.py`。结果比审查写的范围大：

| 会发生什么 | 数量 |
|---|---|
| 手写的来源卡被模板覆盖 | 108 张，分属 7 份 catalog |
| 索引页被覆盖 | 24 页，含整层的 Provenance 索引，手写的批次说明会丢 |
| 多写出来、没有任何入口指向的文件 | 137 个 |
| 与现有内容逐字相同、没有变化的卡 | 286 张，分属 17 份 catalog |

31 份 catalog 实际上有两种做法：早期批次的卡是脚本生成的；后来的 14 批是入账时手写的，卡里有 catalog 没有的内容，卡片位置也不都在 `cards/` 下。脚本不知道这个区别，校验也不查。从第一批手写卡入账起，这条命令就不能照说明运行。手写卡现在都完好，可见那之后它没有被运行过。

## 决定

1. 每份 `vault/provenance/**/catalog.json` 顶层写 `cards`，取 `generated` 或 `maintained`。没有写时生成和校验都报错，新批次入账时必须选一种。
2. `generated`：一个 slug 一张卡，放在该 catalog 的 `cards/` 下，加两页索引，内容只来自 catalog。`card_path` 写了就必须等于默认位置。生成脚本只在内容不同时写，不删文件。校验把磁盘上的卡和索引与 catalog 的投影逐字比对。
3. `maintained`：卡片和索引手写。可以一张卡对多个 URL，可以放在别处，位置由每条的 `card_path` 给出。生成脚本不读不写。校验查两件事：`card_path` 指向的文件存在（原有检查）；几条来源共用一张卡时，卡里要出现每一条的 URL。
4. `vault/provenance/README.md` 是整层的手写索引，生成脚本不再写它。
5. 现有 17 份标 `generated`，14 份标 `maintained`，按卡片现在是否与模板逐字相同来分。没有改任何一张卡的内容。
6. 工单这类在途状态只在主题页自己的裁决表里记一份。上层入口说用途、给链接，不复述做到哪一步。[决定索引](README.md)里，一条决定被后来的决定替代或修订的部分在索引行注明，原文不改。

## 没有采纳的

| 审查的内容 | 处置 |
|---|---|
| 让生成脚本读 `card_path`，把共用一张卡的来源聚合写出，使 13 张卡可以重复生成 | 没有照做。手写卡有 catalog 没有的内容，十四批写法各不相同；要重现它们得把模板扩成多份，或者丢内容。声明归属之后，生成的那一种只有一份真相，手写的那一种由校验守住身份 |
| 把 `used_for` 投影到生成的卡和索引（A2） | 不做。带这个字段的三份 catalog 都是手写卡，卡里已有用途；没有读者因此选错的证据 |
| 缩短两个上层入口里所有批次的描述（S2） | 只改了已经漂移的一处。其余条目记的是定下来的结论 |
| 瘦身兼容入口 `kit/design/references.md`（S4） | 只把根 README 改成直链。兼容入口里的维护边界有没有别的主责页，没有逐条核对 |
| 用最新入口做一次带对照的消费验收（A3） | 采纳方向，没有做。要一件真实任务 |

审查的 S3、S5、S6 是“保持现状”的判断，同意，没有动。

## 与既有决定的关系

落实 [修订流程](../governance/evolution.md)里“可重复生成”的那一句，没有改它的措辞。延续 ADR-011：使用指引由文档结构承担，脚本说明改成与脚本实际行为一致。延续 ADR-021 的做法：审查建议的方案先实跑再裁决，实跑改变了做法。不改 ADR-002：这是维护工具的修复，不是共享组件的晋升。不改入账规范的字段表；`cards` 只是 catalog 的顶层字段，registry 不读它。

## 验证与限制

隔离副本里试过：连续生成两次都不写文件；改一条 `generated` 的摘要后只重写一张卡；slug 含路径、slug 重复、`card_path` 指到别处、缺 `cards` 四种坏输入都报错不写；14 份 `maintained` 的目录前后逐字相同。全量副本里手改一张生成卡、从一张共用卡里删掉一个 URL，校验都报出来。共用卡检查在仓库里第一次运行就查到一处真缺口并已补上。过程见 [回执](../verification/self-contained-review-20261002.md)。

这些试验没有留成仓库里的测试文件。手写卡与 catalog 之间，除了 URL 身份之外的一致性没有检查：状态、摘要改了而卡片没有跟着改，校验发现不了。审查说的“当前结构大体具备发现与消费自足”来自静态走读，这一轮没有新的实测。

重访：出现第三种卡片维护方式；某份手写卡没有跟着 catalog 更新而被读错；或有人要把手写的某一批改回生成。
