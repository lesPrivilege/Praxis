# 施工发现 · 第二轮

2026-10-04，施工者 Opus 5.5。这一轮加了第二个场景：付款复核台，取自用户给的研究 brief。要回答的是第一轮末留下的问题：`web/workbench`、`web/api` 和后端里那些自称与业务无关的部分，换一件不同的工作之后还剩多少能用。

仍然只有受 Kit 约束的一组，没有对照组。另请了一个不知道主会话结论的只读代理复查，它的发现单列在后面。

## 结论

通用的那一层大体站住了，但第一轮的“通用”是没经过检验的说法：要到写第二个场景时才看得出哪些地方其实带着第一个场景的形状。改动不大，集中在三类：类型里写死的枚举、组件里直接调用的场景 hooks、公共结构里用了场景的字段名。改完之后，付款复核台的页面第一次打开就能用，结果未知、版本冲突、取消与离开这些机制一行没重写。

更有用的一条是反过来的：第一轮里有一块最该通用的东西放在了场景目录里。“表单绑定读过的版本、换动作清空、取消丢弃、离开前拦一下”全写在事项工作台的 `RiskActions` 里，要到第二个场景需要同样的东西时才认出它不属于任何场景。

所以对“第一轮的工作面通不通用”，回答是：九成的代码通用，一成要改；但哪一成要改、哪一块该挪进来，只凭一个场景判断不出来。这和 [晋升规则](../../../docs/decisions/002-promotion.md)要第二个独立场景才算候选是一个意思，这一轮给了它一次具体的印证。

## 公共部分里藏着的场景形状

这些都是写第二个场景时才暴露的，类型检查和第一轮的测试对它们无能为力。

| 编号 | 藏在哪 | 是什么 | 怎样暴露 |
|---|---|---|---|
| G1 | 公共的记录结构 | `AuditEvent` 有一个必填字段叫 `matterId` | 写付款场景的记录时要给一个“事项编号”，才发现字段名是另一个场景的 |
| G2 | 公共的动作结果 | `ActionResult.createdTasks`：产生的东西被假定为任务 | 付款场景的动作不产生任务，但可能产生别的对象 |
| G3 | 后端的异常行为 | 响应丢失按请求体里的 `riskId` 触发 | 付款场景的请求体里没有 `riskId` |
| G4 | 前端请求客户端 | 默认身份写死成一个 fixture 里的人 | 第二个场景的人不一样（第一轮复查的 N7） |
| G5 | 工作面组件的类型 | 动作类型、事件类型、角色、搜索结果种类用了场景的枚举 | 第一轮复查已指出（N1） |
| G6 | 工作面组件的取数 | 外壳和搜索对话框自己调用场景的 hooks | 同上 |
| G7 | 场景目录 | 版本绑定的动作表单整个写在 `RiskActions` 里 | 第二个场景需要一模一样的机制 |

G5 和 G6 第一轮的复查者读代码就看出来了；G1 到 G4 和 G7 它没有列，主会话也没有想到，都是动手写第二个场景才碰上的。读代码能找出“这里用了场景的类型”，找不出“这个名字其实是场景的词”。

## 没有进公共层、两个场景各写了一遍的

按晋升规则，这些现在各有两份，是下一批候选；第三个场景出现之前不抽。

| 重复的东西 | 两处 |
|---|---|
| 列表页骨架：查询与地址互转、分页、页码越界回退、空与失败与刷新失败 | `MatterListPage`、`CaseListPage` |
| 场景接口模块的样板：建客户端、带身份头、回查与恢复 | `web/matter/api.ts`、`web/payment/api.ts` |
| 记录页：读记录、按尝试编号标出 | 两个页面里各一个 `ActivityPanel` |
| 人的记录列表的排法 | `RisksPanel`、`CasePage` |
| 后端：规则违反的构造、信息隔离、角色与版本检查、fixture 自洽检查的骨架、“同事并发提交”的调度 | 两个 `domain.ts`、`store.ts`、`scenario.ts` |

## 只有一个场景用、留在场景里的

付款复核台需要而工作面没有的：按“材料、版本、位置”打开依据的抽屉、检查结果列表（缺项与冲突）、机器提议的呈现、金额的显示与录入。事项工作台有而付款复核台没用上的：批量作业对话框、可保存的视图、列表加详情的分栏。公共契约里的 `Job` 和 `JobItem` 目前只有一个场景在用。

## Kit 在这一轮

| Kit 里的话 | 变成了什么 |
|---|---|
| “AI 的 extract/check/compare/draft 动作返回可审查结果，人工决定保留独立记录” | 机器提议单独一块，不改状态；采纳、修正还是不采纳，在人的提交记录里写明 |
| “来源、推断、规则结果、人工决定可区分” | 复核页的三处：规则检查、机器提议、人的判断 |
| “外部 provider 不得成为领域 schema 的所有者” | 公共契约里不留任何场景的词；枚举由场景自己收窄 |
| 晋升规则 | 两个场景各写一遍的东西先不抽 |

第一轮“Kit 对界面语法没有话说”的结论没有变。这一轮界面层的约束主要来自研究 brief 的反例表和第一轮复查留下的教训，不来自 Kit：

- 提交的结论由后端按检查结果给出，人不选。这是第一轮复查 N2（界面重复后端规则）的直接后果：这次没有让界面去判断“有未通过的检查就必须作为例外”，而是让后端随对象返回“现在提交会带什么”。
- 按 brief 的反例表逐行做了：缺材料写明缺什么、谁补；冲突两个写法并列；没有金额不显示 0；按金额筛选不带币种时拒绝。十行里只有“首次无数据”没有 fixture 可以走到。

## 施工过程

第二个场景的界面在浏览器里第一次打开就能用，主会话走查时没有再遇到第一轮那种只有点了才发现的界面缺陷。原因不是这一轮写得更小心，而是出问题的那些机制（版本绑定、尝试结果、离开拦截、窄屏导航）已经在公共层里被第一轮的走查和复查修过，这一轮没有重写。这算是公共层的一个实际收益，但只有一次观察。

事项工作台在重构之后重走了三条路径：提出建议、批量指派、切换身份。其余靠后端的 20 项测试和类型检查，没有逐条重验。

重走批量指派时，对话框停在“已处理 0 个”不动。查下来不是重构碰坏的：浏览器面板当时在后台，查询库在页面不可见时暂停了定时轮询。后端的作业其实已经跑完。处置是让作业进度在后台也继续轮询。这件事第一轮没有暴露，因为那时面板在前台。

给金额的录入与显示补了 5 项测试，当场拦下一处缺陷：超过精确整数范围的金额被悄悄取整，而不是拒绝。这是前端第一批自动化测试，也是两轮里第一处由前端测试而不是由人发现的缺陷。

## 独立复查

复查者是一个 Sonnet 只读代理，拿到的是本目录、付款场景的预期行为一段话和八个问题，没有主会话的结论，不能改文件。它跑了类型检查和测试，把后端的检查函数拿边界输入实际跑过，没有开浏览器；界面上的发现来自读代码。下面是主会话逐条核对之后的处置。

### 属实并已修正

| 编号 | 发现 | 修正 | 确认方式 |
|---|---|---|---|
| P1 | 付款列表页：填了金额范围再清掉币种，页面直接崩溃 | 没有币种时不解析金额 | 浏览器 |
| P2 | 在一个事项上打开的表单，跳到另一个事项后还在；两者版本号相同时，前一个的内容会提交到后一个上 | 动作面板随事项重建 | 浏览器 |
| P3 | 用“带入”按钮填的内容不算未提交，离开时不拦。两个工作台都有 | 带入也算填写 | 浏览器 |
| P4 | 刷新只重取事项本身，检查、机器提议和记录还是旧的，“已核对第 N 版”却说上面已是当前内容。两个工作台都有 | 刷新连同它名下的面板一起重取 | 读代码 |
| P5 | 防止重复提交靠的是渲染后的状态，连点两下都能过 | 提交一开始就上锁 | 读代码 |
| P6 | 页码越界回退用的是上一个查询的总数，会把合法的第 2 页改回第 1 页。两个工作台都有 | 新查询的结果到了再判断 | 读代码 |
| P7 | 付款条件表在、只是没写结算币种时，检查说“没有付款条件表”并让人去补这份表 | 文件缺失和文件里没写分开说 | 新增测试 |
| P8 | 手上的验收记录是别的里程碑的，检查判成“未通过”，于是可以只写一句说明就作为例外提交 | 改判“无法判断”，写明缺本次里程碑的验收记录 | 新增测试 |
| P9 | “提交后材料有变”只比已有材料的版本：之后新增一份材料不算有变；少一份材料时整个列表报错 | 比较的是材料的集合加版本 | 新增测试 |
| P10 | 基于旧版本材料的机器提议、或与检查结果相反的机器提议，可以被原样“采纳”；记录里不写采纳的是哪一份 | 这两种情况只能修正后采纳或不采纳（规则 SUB-3）；可选的处置由后端随对象给出；记录里写提议编号 | 新增测试 |
| P11 | 规则得出的结论显示在“人的判断”下面，写成“提交复核：材料充分”，而全部通过时提交人可以一个字不写 | 结论单列一行，标明是规则得出；用词改成“三项检查全部通过”；没写说明的照实写没写 | 浏览器 |
| P12 | 机器提议已经过时，仍可以把它的文字带入说明 | 只有基于当前材料的提议才能带入 | 读代码 |
| P13 | 列表、筛选和记录里的状态只写“已决定”，只有事项页说了没付款 | 状态处处写“材料已接受，未付款” | 浏览器 |
| P14 | 内核把每个对象都有的继承属性名当成动作类型，`/actions/constructor` 返回 500 | 只认场景自己的动作类型 | 新增测试 |
| P15 | 空的金额参数被当成 0 | 拒绝 | 新增测试 |
| P16 | 小项：标签名守卫认继承属性；关掉依据抽屉后按返回又打开；输入法确认候选词的回车被当成选中；搜索框和金额错误没有可访问名称；同一种材料有两份时后一份被悄悄忽略 | 逐项改了，最后一项改成 fixture 检查 | 读代码 |

### 属实，这一轮没有修

| 编号 | 发现 | 为什么留着 |
|---|---|---|
| Q1 | 材料出新版本不会带动事项的版本号。复核员按第 1 版读完检查，第 2 版到了，仍能提交，后端会把他的说明记在第 2 版名下 | 现在没有登记材料的途径，第 2 版到不了，所以是潜在的。场景契约里补了一条：材料新增或出新版本时事项版本加一。做登记材料那天必须一起做 |
| Q2 | 切换演示身份会重建页面，未提交的内容和“结果未知”的尝试编号直接丢，没有任何提示 | 身份切换是演示用的控制，不是产品路径 |
| Q3 | 公共层仍带着一个场景的形状：内核认定 202 就是作业、给动作的“跑完了”回调只有事项场景用；响应丢失只匹配请求体顶层的字符串，批量指派测不到；动作面板假定一个整数版本和一个结果，批量指派绕开了它；动作生效后作废的是两个工作台的全部缓存 | 是第三个场景或第二种作业出现时要改的地方 |
| Q4 | 两个场景重复的清单比上面“各写了一遍”列的更长：两个接口模块里二十来个结构相同的读取 hook、两个外壳、两份地址互转、后端的事件列表与排序分页；金额格式化前后端各有一份 | 同上，按晋升规则先不抽。上面“各写了一遍”一节只列了主要的几项 |
| Q5 | 界面仍自带的知识：币种清单写死在列表页；复核员下拉按角色过滤；“复核员（尚未指定）”是界面拼的；有几句静态文字写明谁来重新提交 | 前两项要契约给出可选值；后两项是用词 |
| Q6 | 没有规则要求合同文件在场；金额为 0 的发票能通过上限检查 | 演练规则本来就只有三条，是否要管由懂行的人定 |
| Q7 | 契约检查不校验日期格式，也不校验请求体 | 未处理 |
| Q8 | 离开前的拦截只管应用内的跳转；关标签页、刷新、回到一条整页加载的历史记录都不拦 | 这一条是主会话验证 P3 时自己撞上的。之后加了浏览器的离开确认，见 [合并后的独立复验](reverification.md#关标签页和刷新的离开确认) |

复查者没有找到重构造成的事项工作台退化，但它说明了自己没有基线可比。

### 这次复查说明了什么

第一轮复查找出的多是“界面机制写错了”。这一轮机制是共用的、已经修过的，找出来的换了一类：规则对边界材料的判定（P7 到 P10）和三种陈述之间的界线（P10 到 P13）。后一类正是这个场景要检验的东西，主会话在浏览器里看过那一页，没有看出“材料充分”四个字挂在了人的名下。

两轮都是同一个结果：施工者走通之后，第二个读者还能找出十几处确实存在的缺陷。

## 下一步

这是第二轮末的清单，照原样留着。第 1 项不做，第 3 项先留成 [候选条目](candidates.md)，见 [收尾](README.md#收尾)；第 2、4 项还开着。

1. 不给 Kit 的对照组仍然没有做。两轮下来“Kit 起了作用”依旧只是相关。
2. 给前端补自动化测试，先覆盖 `ActionPanel` 和尝试状态机。现在两个场景都靠它们，改坏一处两边都坏。
3. 把这两轮用到的界面决定写成带反例的条目，提交裁决是否进入 `kit/ui`。brief 的反例表和这里的 G1 到 G7 是现成的底稿：前者是“界面该怎样”，后者是“公共层不该带什么”。
4. 第三个场景出现时，再决定上面“各写了一遍”的那几项抽不抽。
