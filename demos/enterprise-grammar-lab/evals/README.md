# 施工发现

每轮一份。两轮都只有受 Kit 约束的一组施工，没有对照组；施工者自评有偏，所以每轮另请一个不知道主会话结论的只读代理复查代码，发现和处置各自记在当轮文件里。

| 文件 | 问的是什么 | 回答 |
|---|---|---|
| [第一轮](round-1.md) | 只给 Kit 的企业工作语法和一份场景契约，施工出来的东西像生产软件还是像演示用的 CRUD | 行为语义上像生产软件，而且每一处都能指回 Kit 里带反例的条目；界面语法上 Kit 没有可以约束的内容。施工者自己走通之后，独立复查仍找出 14 处缺陷 |
| [第二轮](round-2.md) | 第一轮的“通用”部分，换一件不同的工作之后还剩多少能用 | 工作面九成代码没动，一成要改；但要改的地方和该挪进公共层的一块，都是写第二个场景时才看得出来。独立复查找出 16 处缺陷，多在规则对边界材料的判定和“规则、机器、人”三种陈述的界线上 |
| [候选条目](candidates.md) | 两轮的教训里，哪些值得提交 Kit 裁决 | 四条带反例的候选和每条在两个场景里的对照。未裁决，没有进 Kit |

## 两轮合起来能说的

这些说的都是这两轮施工怎样消费了 Kit，不是 Kit 的效果。

- 施工时直接用得上的是带反例的条目。[共同工作语法](../../../kit/grammar/work.md)的不变量表被逐行写成了接口、测试和界面状态；只有定义没有反例的条目，施工时找不到可以照着做的东西。
- 读过并照做了的条目没有挡住同一处的缺陷。“规则结果、人工决定可区分”这一句第二轮读过，三种陈述也分了三处呈现，规则的结论仍然被写在了人的名下。缺的是那一句下面的反例。
- Kit 的 [界面候选](../../../kit/ui/README.md)只有名字，施工时没有可以照着做的内容。两轮里界面层的决定来自任务来文、研究 brief 的反例表和复查留下的教训。
- “通用”要第二个场景来检验。只有一个场景时，场景的词会悄悄进到公共结构里，该通用的机制会留在场景目录里。
- 施工者自己的走查不够。类型检查、后端测试和浏览器走查都通过之后，第二个读者两轮各找出十几处确实存在的缺陷。公共层修过的机制第二轮不再出错，出错的换成了新场景自己的语义。

## 不能说的

- Kit 约束比不给 Kit 好多少，或者上面哪一条是 Kit 造成的。没有对照组，也不打算做。
- 这些工作面是通用的。两个场景共用，按 [晋升规则](../../../docs/decisions/002-promotion.md)是候选。
- 界面对使用者有用。没有律师、合同或财务人员、任何使用者看过。

## 收尾

第二轮末留给用户的三件事，按用户 2026-10-04 转来的收尾建议处置。那份建议是用户贴入的文字，没有入账。

| 留下的问题 | 处置 |
|---|---|
| 要不要做不给 Kit 的对照组 | 不做。施工轨迹和缺陷记录留在这两份轮次文件里；结论限定为这两轮怎样消费了 Kit |
| 技术栈要不要写成实现 ADR | 写了一份只对本 demo 有效的：[实现 ADR](../stack-adr.md)。没有进 `docs/decisions`，不改变 Kit 里技术栈的状态 |
| 界面决定和公共层教训要不要提交 Kit 裁决 | 先留成带反例的 [候选条目](candidates.md)，四条。提交和裁决还没有发生 |

用户同时给了一份交接稿，推荐的正是已经做完的付款复核场景。它列的 12 条不变量与现状的逐条对照在 [实现说明](../demo.md#与交接稿的对照)：五条有，七条部分有。

还开着的：

- 候选条目提交给谁、何时裁决，由用户定。
- 交接稿指出本目录在它核对的 `main` 里取不到。那时目录还没有提交。现在已经合并进 `main` 并推送，第二个执行者可以拿到；它对事项工作台列的核验点还没有人做。
- 两份轮次文件里记着没修的项（第一轮 N 系列，第二轮 Q1 到 Q8）和 README 里“没有验证的”清单都原样留着。
