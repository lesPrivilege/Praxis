# 候选条目

状态：候选，未裁决，没有进 Kit。2026-10-04，编订者 Opus 5.5 主会话。依据是用户同日转来的收尾建议第 3 条：两轮的教训值得提交 Kit 裁决，先保留成带反例的候选条目。

四条都写成 [共同工作语法](../../../kit/grammar/work.md)不变量表的形式：条件、约束、反例。反例后面带编号的，是这两轮施工里真的出过的缺陷，编号指向 [第一轮](round-1.md)和 [第二轮](round-2.md)的记录；不带编号的没有出过，是施工时照着避开、有测试或走查守着的。每条后面有一张对照，写这条关系在两个场景里各落在什么对象上、哪些参数不能共用。

证据的范围：同一个施工者做的两个合成场景，没有对照组，没有专业人员看过。所以这里能说的是“手里拿着 Kit 施工时，在这些地方出了错”，不能说“写成规则就不会出错”。

## C1 规则结果、机器提议、人的判断分开归属

Kit 已有的话：[契约](../../../kit/contracts/README.md)的检查点“来源、推断、规则结果、人工决定可区分”；[企业工作面语法](../../../kit/grammar/README.md)的“AI 的动作返回可审查结果，人工决定保留独立记录”。两句都没有反例。第二轮施工时这两句都读过、都照做了，三种陈述在页面上分了三处，下面带编号的缺陷仍然出现：分开呈现不难，难的是一条记录、一次带入、一个状态名里的归属。

| 条件 | 约束 | 反例 |
|---|---|---|
| 一条人的记录里带着规则算出的内容 | 这部分标明规则与版本，单独呈现；人没有写的，照实显示没写 | 三项检查全部通过，提交人一字未写，记录显示成“某某提交复核：材料充分”（P11） |
| 人对机器提议作处置 | 记下处置的是哪一份、作了哪一种处置；能作哪几种由持有规则的一方给出 | 记录里只有“采纳”两个字，查不出采纳的是哪一份（P10） |
| 机器提议的输入变了，或它与规则结果相反 | 不能原样采纳；提议标明它基于哪一版材料 | 按第 1 版发票生成的提议，在发票出了第 2 版之后被原样采纳（P10） |
| 机器或别人的文字进入人的陈述 | 带入算人的一次填写；已经失效的来源不能带入 | 被退回的建议仍可带入决定（R13）；过时的机器提议可以带入说明（P12） |
| 给状态起名 | 名字说的是哪一种陈述的结果，不借更重的词 | 材料被接受的事项在列表里写“已决定”，读起来像已同意付款（P13） |

| | 事项工作台 | 付款复核台 |
|---|---|---|
| 规则结果 | 动作规则的判定：谁能做、为什么不能 | 另有三条检查规则对材料的判定 |
| 机器提议 | 没有 | 预制的一份，带编号和所基于的材料版本 |
| 人的判断 | 主办律师的建议，合伙人的决定或退回 | 复核员的提交，负责人的接受或退回 |
| 出过的反例 | R13 | P10、P11、P12、P13 |
| 不能共用的 | 带入发生在人与人之间 | 提交的结论由规则得出，人不选；对提议的处置三选一 |

证据强度：前三行和第五行只在付款复核台出过，因为事项工作台没有机器提议。第四行两个场景都出过。

## C2 未提交的填写绑定对象身份

Kit 已有的话：[状态与可达性](../../../kit/design/interaction/states.md)的“对象身份、版本和作用范围在操作前可知”和“切换视图、关闭视图、取消任务和删除对象分别表达”。它说的是对象和动作，没有说表单里还没提交的内容也有归属。

| 条件 | 约束 | 反例 |
|---|---|---|
| 界面上有未提交的填写 | 它属于一个对象、读到的那个版本、一种动作；三者任何一个变了，填写不跟过去 | 在甲事项上填的说明，跳到版本号相同的乙事项后被提交到乙名下（P2）；在“退回”里写的理由，切到“作出决定”后被当成决定的理由（R2） |
| 填写期间对象被别人更新 | 提交被拒；已填内容保留；给出当前版本、更新人和时间，由人看过再提交 | 静默覆盖；或拒绝之后清空表单 |
| 离开带着未提交填写的页面 | 先问；手输和带入都算填写 | 用按钮带入的内容不算填写，离开不拦（P3） |
| 取消填写、关闭视图、撤回已提交的动作 | 三件事分开：取消丢弃填写，关闭不取消已发出的尝试，撤回是另一个有权限和理由的动作 | 结果未知时对话框关不掉（R4） |
| 上一次提交的结果提示 | 属于那一次尝试；换动作或重开表单之后不再显示 | 收起表单再打开，上一次被拒的提示还在（R3） |

| | 事项工作台 | 付款复核台 |
|---|---|---|
| 对象与版本 | 风险，一个整数版本 | 复核事项，一个整数版本；材料的版本另记 |
| 表单的宿主 | 风险详情，随风险编号重建 | 复核页，随事项编号重建（P2 之后） |
| 出过的反例 | R2、R3、R4 | P2、P3 |
| 不能共用的 | 批量指派不带读到的版本，绕开了共用的动作面板（N3、Q3） | “读过的版本”应当包含材料的版本，现在不包含（Q1） |

证据强度：两个场景都出过。机制在共用的 `ActionPanel` 里，没有自动化测试，靠浏览器走查。拦截只管应用内的跳转，关标签页和刷新不拦（Q8）。

## C3 结果未知之后的恢复

Kit 已有的话：不变量“外部动作结果未知：保留尝试身份，核对影响后决定恢复”，反例“把超时当未执行，无条件重试”；契约的“写入超时先核对外部影响；重复执行有稳定身份”。这是 Kit 说得最完整的一条，两个场景的接口和测试都从它直接写出来。两轮补出的是它下面更细的分岔。

| 条件 | 约束 | 反例 |
|---|---|---|
| 请求发出后连接断开，或服务器报 5xx | 算结果未知，不算被拒绝 | 带说明文字的 500 被显示成明确的拒绝（R6） |
| 回查一次尝试 | 只有权威的“没有收到”才允许用同一编号重发；回查自己失败，结果仍是未知 | 回查出错让“核对中”永不结束；查不到作业被当成“没有收到”（R6） |
| 回查有了结论 | 按它本来的种类呈现：已生效、被拒、版本冲突各是各的 | 回查出的是版本冲突，却没有冲突的呈现（R6） |
| 同一尝试编号再次到达 | 内容相同就返回第一次的结果，不产生第二次效果；内容不同就拒绝 | 每次重发都新写一条记录 |
| 结果未知期间 | 不能再发新的尝试；尝试编号留在页面上；离开先问 | 连点两下发出两次提交（P5）；尝试编号只在页面内存里，刷新就丢（N6，未修） |

| | 事项工作台 | 付款复核台 |
|---|---|---|
| 动作 | 提出建议、决定、退回、批量指派 | 提交、接受、退回 |
| 两种丢失的 fixture | R-3106 生效后丢，R-3107 没有到 | PR-4110 生效后丢，PR-4111 没有到 |
| 后端测试 | 三项：重复、生效后丢、没有到 | 一项，含两种丢失 |
| 不能共用的 | 批量指派回查到的是一个作业，不是一个结果（R4、Q3） | 没有 |

证据强度：两个场景都有，后端有测试，前端的尝试状态机没有测试。保证止于假后端的一次运行：尝试记录在内存里，重启即失；“没有收到”在真实系统里要约定多久之内算数，这里没有约定。

## C4 判断绑定材料的版本

Kit 已有的话：定义里“证据须定位到版本与片段”；不变量“输入实质改变：检查版本相关判断和批准”，反例“沿用旧版本批准执行新内容”。

| 条件 | 约束 | 反例 |
|---|---|---|
| 一项判断记下它的依据 | 记的是材料的集合和各自的版本；之后新增、减少、出新版本都算变了 | 只比原有材料的版本，提交之后新增一份材料不算变；少了一份时整个列表报错（P9） |
| 依据变了 | 已有的判断标为待重验，并且有一条走得通的路 | 已决定的风险标着“需重新核对”，却没有任何可做的动作（R11） |
| 人读过材料之后材料变了 | 他手上“读过的版本”失效，提交被拒 | 发票出了第 2 版，事项的版本没变，按第 1 版写的说明被记在第 2 版名下（Q1，未修，目前到不了） |
| 打开一处依据引用 | 打开的是所记的那一版、那一处；版本没有保留就说没有；位置不在就照常显示这一版并提示 | 拿当前版本或相近的段落顶替 |
| 手上的材料属于别的对象 | 算缺本对象的材料，结果是无法判断，写明缺什么、由谁补 | 别的里程碑的验收记录被判成“未通过”，于是写一句说明就能作为例外提交（P8） |
| 材料在场，但没写要查的内容 | 和材料缺失分开说 | 付款条件表在、只是没写结算币种，检查说“没有付款条件表”（P7） |

| | 事项工作台 | 付款复核台 |
|---|---|---|
| 材料 | 文书，带版本；依据引用文书的某一版 | 五种材料，带版本；依据引用“材料、版本、位置” |
| 被绑定的判断 | 合伙人对风险的决定 | 复核员的提交，机器提议 |
| 变了之后的路 | 合伙人引用当前版本重新决定，旧决定留在记录里 | 负责人退回，复核员按新版本重新提交 |
| 出过的反例 | R11 | P7、P8、P9、Q1 |
| 不能共用的 | 比的是所引文书的版本 | 比的是整个材料包的集合加版本 |

证据强度：两个场景都有，后端有测试。Kit 说的是“实质改变”，两个场景都没有定义什么算实质，任何新版本都算变了。

## 没有写成条目的底稿

下面几项两轮里也用到了，材料比上面四条薄，留作下一批。

## 交给裁决的问题

这些由裁决者定，这里只列出来：

1. 四条各自放哪。C3、C4 是不变量表里已有两行的细化；C1 接在契约“证据与规则”的检查点后面；C2 说的是界面上的填写，Kit 里最近的位置是状态与可达性或 `kit/ui`。
2. 只在一个场景出过的行（C1 的四行）要不要等第二个有机器提议的场景。
3. 带编号的反例是这个 demo 的缺陷记录。进 Kit 时写成一般的说法还是保留出处。
