# 事项工作台场景契约

## 1. 工作与机会

场景 `matter-workbench`，revision `0.2`，Kit 基线 `main@d4fd387`。0.2 相对 0.1 没有改业务规则：接口挪到 `/api/matter` 下，与另一个场景共用的部分抽成了公共契约。施工者是 Opus 5.5 主会话，接收者是用户，尚未接收。专业复核者空缺：没有执业律师看过对象模型和规则，法律内容只用来承载工作结构，不是法律意见。

工作范围是一家律所商事争议团队在举证期限前的风险处置：主办律师核对一项风险的依据，提出处置建议；合伙人作出决定；决定留下记录，产生的后续任务有人接手。使用者是主办律师和合伙人，律师助理只读。

这个场景要检验的不是律所业务，而是一条链能否在界面和后端同时成立：对象 → 语境 → 关系 → 决定 → 动作 → 记录。没有现场流程、基线和观察窗口；非 AI 替代方案不适用，本轮没有任何模型参与业务动作。继续条件是这条链在第二个领域（金融）换对象后仍能复用同一组工作面；发现页面只能靠重写才能迁移时停下来改抽象。

启动不需要账号、企业资料或网络服务。全部数据是合成的。

## 2. 对象、证据与动作

一个使用者、一类输入件、一个动作、一个人工验收点：主办律师拿到一项风险及其依据，提出处置建议，合伙人决定是否采纳。

### 对象

| 对象 | 身份与版本 | 权威位置 | 说明 |
|---|---|---|---|
| 事项 Matter | `M-` 编号，整数版本 | 后端 | 阶段、状态、主办合伙人、复核人、最近期限 |
| 当事方 Party | `P-` 编号 | 后端 | 委托人、对方、对方代理人、法院 |
| 文书 Document | `D-` 编号，整数版本 | 后端 | 新版本不覆盖旧版本的编号；特权文书对助理只显示标题和存在，不显示内容 |
| 依据 Evidence | `E-` 编号 | 后端 | 定位到文书、文书版本和片段；文书出了新版本后，引用旧版本的依据标为版本落后 |
| 风险 Risk | `R-` 编号，整数版本 | 后端 | 状态 `open → proposed → decided`；决定所引的依据版本落后之后可以重新决定；与依据的关系带立场：支持、反驳或限制 |
| 任务 Task | `T-` 编号 | 后端 | 持续责任，有责任人和期限，记着由哪次动作产生 |
| 记录 AuditEvent | `EV-` 编号 | 后端 | 谁在何时对哪个对象的哪个版本做了什么，关联尝试编号和规则 |

对象之间的关系由后端保存，页面按对象取用：事项页是事项及其关联对象的投影，风险详情是风险及其依据的投影。没有独立的“文书模块”或“任务模块”。

### 角色

| 演示身份 | 角色 | 可以 |
|---|---|---|
| 周明远 | 合伙人 | 阅读全部；决定风险处置；退回建议；指派复核人 |
| 林知夏 | 主办律师 | 阅读全部；提出处置建议 |
| 陈一苇 | 律师助理 | 阅读非特权内容；信息隔离的事项不可见 |

身份是演示用的假身份，由请求头携带，没有认证。权限由后端判定，随对象返回“当前可做的动作及不可做的理由”，界面不自行推断。

### 动作

动作是业务事务，不是字段修改。每次提交带尝试编号，后端按编号去重并可回查。

| 动作 | 前置 | 效果 |
|---|---|---|
| 提出处置建议 `propose-risk-disposition` | 风险为 `open`；对象版本与提交时一致；至少引用一项当前版本的依据 | 风险变为 `proposed`，保存建议与所引依据的版本，写一条记录 |
| 决定处置 `decide-risk` | 风险为 `open` 或 `proposed`，或已决定但所引依据版本落后；版本一致；依据要求同上；角色为合伙人 | 风险变为 `decided`；处置为“采取措施”或“上报”时产生后续任务；写记录 |
| 退回建议 `return-risk-proposal` | 风险为 `proposed`；版本一致；角色为合伙人；写明理由 | 风险回到 `open`，原建议保留在历史里；写记录 |
| 指派复核人 `assign-reviewer` | 批量；角色为合伙人；逐项检查事项未结案、复核人与当事方无已登记的利益冲突 | 逐项设置复核人；事项已有未完成的复核任务时把它转给新复核人，没有才新建；逐项写记录；未通过的项保留理由 |

### 规则

| 规则 | 版本 | 内容 | 例外交给 |
|---|---|---|---|
| EV-1 | 1 | 建议和决定须引用至少一项依据，所引依据须是文书的当前版本 | 主办合伙人 |
| ROLE-1 | 1 | 决定、退回和指派由合伙人作出；主办律师可以提出建议 | 管理合伙人 |
| COI-1 | 2 | 复核人不得与事项当事方存在已登记的利益冲突 | 合规负责人 |
| ST-1 | 1 | 已结案的事项不接受指派 | 主办合伙人 |
| VER-1 | 1 | 提交时的对象版本须是当前版本 | 无例外，重新核对后再提交 |
| ST-2 | 1 | 建议只能对 `open` 的风险提出；已决定的风险不接受建议和退回，所引依据没有变化时也不接受新的决定 | 无例外 |
| REF-1 | 1 | 动作的对象须存在，并且对提交人可见 | 无例外 |

规则判定全部是确定性的，由后端执行；人的建议和决定各自成记录，互不覆盖。

每项风险随时回答“下一步等谁”：待处置的等复核人提出建议，已有建议的等主办合伙人决定，所引依据落后的等主办合伙人重新核对；复核人未指派时照实写未指派。

## 3. 失败与恢复

| 情况 | 处理规则 |
|---|---|
| 缺依据 | 风险没有可引用的当前版本依据时，建议和决定不可提交，理由随对象返回（EV-1）。登记依据不在本轮范围内 |
| 依据版本改变 | 文书出新版本后，引用旧版本的依据标为版本落后，不能再被引用；已有的建议或决定若引用了它，风险标为“需重新核对”，合伙人可以引用当前版本的依据重新决定，原记录不改写 |
| 对象被他人更新 | 提交时版本不一致返回冲突，附当前版本、更新人和时间；界面保留已填内容，换上对象的当前内容，由人重新核对后再提交。界面不逐项标出哪里变了 |
| 提交后结果未知 | 连接中断、超时或服务端错误都不等于未执行。界面保留尝试编号，先回查该次尝试；确认未收到才用同一编号重试。尝试编号只保存在当前页面，离开或刷新后只能靠对象的当前状态判断 |
| 重复提交 | 同一尝试编号再次到达时返回首次结果，不重复产生记录和任务 |
| 批量部分失败 | 作业逐项给出结果；通过的项生效，未通过的项保留规则和理由，不整体回滚 |
| 局部读取失败 | 一个面板取数失败不影响同页其他面板；面板自己给出错误和重试 |
| 权限不足 | 无权的动作显示为不可用并写出规则；无权的对象返回拒绝并说明找谁；特权文书的依据只显示文书标题和存在 |
| 人工退回 | 原建议、退回理由和退回人都留在风险的历史里 |
| 取消、离开 | 取消填写丢弃尚未提交的内容；填到一半或结果未知时离开页面先提示后果。两者都不撤销已经提交的动作，撤回一份建议只能由合伙人退回 |

## 4. 验证与结果

合成 fixture 在 [fixtures](../fixtures/README.md)，每种失败情形都有一个固定的对象，见该目录的对照表。验证分三层，结果记在 [README](../README.md)：

- 契约：后端的每个响应按 [OpenAPI](../contracts/matter.openapi.yaml)的 schema 校验；前端和后端共用同一份生成的类型。
- 系统行为：对后端直接跑上表各情形的测试。
- 界面：在浏览器里走通正常路径和各失败状态。

接受率、修正率、复核时间和净减负都没有样本，保持未知。合成数据只用于演练。

## 5. 接收与后续责任

交付物是可运行的工作台、契约、fixture、测试和一份 [施工发现](../evals/README.md)。允许用途是检验 Kit 的企业工作面语法能否施工，不用于任何真实事项。

第一轮末留给用户的三件事已经处置，见 [收尾](../evals/README.md#收尾)：不做对照组；技术栈记在只对本 demo 有效的 [实现 ADR](../stack-adr.md)；教训先留成候选条目。第二个场景是 [付款复核台](payment-review.md)。这里的组件和它共用的那些，按 [晋升规则](../../../docs/decisions/002-promotion.md)是两个独立场景在用的候选，不是 Kit 组件。
