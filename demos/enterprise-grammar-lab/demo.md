# 实现说明

两份场景契约见 [scenarios](scenarios/README.md)。这里记录实现时作的选择、没有采用的做法，以及与任务来文不一致的地方。这些选择只对本 demo 有效，不改变 Kit 里“候选、未裁决”的技术栈状态；决定、替换边界和没有验证的能力另记在 [本 demo 的实现 ADR](stack-adr.md)。

## 结构

```text
web/matter      web/payment        每个工作台自己的接口模块、用词、地址、页面
      ↘          ↙
   web/workbench + web/api         工作面和接口层的公共部分，不知道任何场景
            ↓  只认识 /api 和契约
contracts/work.yaml  ←  matter.openapi.yaml、payment.openapi.yaml 引用并收窄它
            ↑                       生成 *.d.ts，前后端共用
   backend/kernel.ts               HTTP、演示身份、动作尝试、异常行为
      ↗          ↖
backend/matter  backend/payment    每个场景的状态、规则、动作  ←  fixtures/*.json
```

替换后端的接缝是 HTTP：`API_TARGET=<地址> npm run web` 把 `/api` 代理到另一个实现了同样契约的服务，前端代码不动。这一点只有结构上的依据，没有第二个后端实际跑过。

## 选了什么，没选什么

| 问题 | 采用 | 没有采用 | 理由 |
|---|---|---|---|
| 假后端放在哪一层 | 独立的 HTTP 进程 | 浏览器里的 MSW；前端内部的 repository 接口加 fake adapter | 进程是有状态的，能真实地断开连接、延迟和跑后台作业；前端和将来的真实后端之间只隔一个地址。MSW 和进程内 adapter 都让“假”留在前端包里 |
| 契约到代码 | OpenAPI → openapi-typescript 生成类型，openapi-fetch 作客户端 | Orval 生成客户端、MSW handler 和 Faker 数据 | 需要的只是类型和一个很薄的客户端；fixture 要按情形手写，随机数据帮不上 |
| 状态样张 | 每种状态对应一个固定的 fixture 对象和地址 | Storybook stories | 这一轮先确认状态在真实页面里走得通。Storybook 留到要做视觉回归或给人逐状态审阅时再装 |
| 界面验证 | 在浏览器里逐条手走，结果记在 README | Playwright 脚本、截图基线 | 同上，属于下一层 |
| 应用框架 | Vite 单页应用 | Next.js、shadcn dashboard 模板 | Kit 的候选是 React + Vite + Ant Design；模板自带的仪表盘骨架正是这轮要避开的东西 |
| 工作面组件 | 直接组合 Ant Design，另写 10 个小组件；第二个场景出现后才把它们与场景解开 | 先建一层通用组件库 | 按 [晋升规则](../../docs/decisions/002-promotion.md)，一个场景时留在本地，两个场景时是候选 |
| 两个场景怎样共处 | 一个应用两棵路由树，一个后端进程两个前缀，一份公共契约被两份场景契约引用 | 两个独立的应用各抄一份；或把两个场景的对象并进一份契约 | 抄一份就量不出“通用部分”到底通不通用；并成一份会让一个场景的词进到另一个场景里 |
| 公共契约里的枚举 | 公共部分用开放的字符串，各场景用 `allOf` 收窄成自己的枚举 | 公共部分直接写死枚举；或全用字符串不收窄 | 前者做不到公共，后者丢掉场景代码里的穷尽检查 |
| 读取失败 | 不自动重试，面板显示错误 | TanStack Query 默认重试 3 次 | 默认重试会让“暂时失败”状态永远看不到；真实产品里对只读请求重试一次是合理的，这里为了可见性关掉 |

## 与来文不一致的地方

- 来文说 Praxis 已登记一套 golden path。仓库里它的状态是“候选，未裁决”（[技术栈图景](../../vault/distilled/themes/tech-stack-boundaries.md)），所以这里只当作起点，没有引用为既定规范。
- 来文建议 OpenAPI → Orval → MSW → Faker、Storybook 和 Figma Code Connect。都没有装，理由见上表。
- 来文建议做 SaaS 基线、对象中心基线和 Kit 约束重建三组对照。两轮都只做了受 Kit 约束的一组，没有对照组，所以不能得出“Kit 约束比自由发挥好”的结论。
- 来文建议把法律场景换成金融名词来检验复用。第二轮没有换皮，做的是另一件工作（付款复核）：按晋升规则，同场景换皮不算独立证据。
- 来文建议的关系图、截图基线都没有做。
- 来文把这件事说成消费 Palantir 与 SaaS 的 distill。仓库里 [palantir](../../palantir/README.md)和 [tally](../../tally/README.md)都只有登记，没有完成的提炼，所以没有东西可消费；对象中心的结构来自来文自己的描述和 Kit 的工作语法。

## 与研究 brief 的对照

brief 的身份见 [README](README.md#材料来路)。它是建议稿。第一轮末拿它对照过事项工作台，第二轮做了它建议的场景；下面是两次之后的取舍。

| brief 的建议 | 处置 | 说明 |
|---|---|---|
| fixture 校验器：重复 ID、悬空引用、无效状态，错误带稳定代码和路径，不自动修复 | 采用 | 后端启动时检查，有问题就列全并拒绝启动。合并后的独立复验查出它对“无效状态”有漏检，已补，见 [复验](evals/reverification.md) |
| 使用者能说出“交给谁” | 采用 | 契约给风险加了 `next`：等的是哪一步、由谁负责，由后端给出 |
| 关闭、返回、取消分别处理 | 采用 | “取消填写”明确丢弃已填内容；填到一半或结果未知时离开会被拦下；两者都不撤销已提交的动作 |
| 返回列表后查询与滚动位置可恢复 | 采用 | 查询本来就在地址里；补了滚动位置恢复 |
| 写明假后端不能证明什么 | 采用 | 见 [假后端](backend/README.md) |
| 键盘焦点、缩放检查 | 部分 | 键盘走了一条路径；缩放只验了等效宽度下的重排 |
| fake 用 MSW，本地 API 只在需要真实 HTTP 生命周期时引入 | 不同 | 这里用的是本地进程。理由正是它列的那个条件：要真实地断开连接、跑后台作业、让另一个人并发修改 |
| P0 工具先做成独立小件：fixture 校验器、有限查询执行器、证据定位解析器、决定与尝试的 reducer、adapter 契约测试包 | 部分 | 校验器、查询、定位、动作都在后端里实现并有测试，但没有做成可单独运行的工具；动作是就地修改状态的函数，不是纯 reducer |
| 先手工定义六个操作，再决定是否用 OpenAPI | 不同 | 第一轮已经从 OpenAPI 生成类型，没有出现它担心的两份定义各改一份 |
| 同一套契约案例对两个 adapter 都跑 | 没有做 | 测试只对假后端跑。它们走的是 HTTP，换一个地址和同样的种子数据就能对另一个后端跑，但没有第二个后端可试 |
| 证据定位解析器，点开后定位准确 | 采用（付款复核台） | 依据引用是“材料、版本、位置”，点开标出那一处；版本不存在、位置不存在各有提示，不拿相近的内容顶替。事项工作台仍只带定位文字和摘录 |
| 确定性检查、机器建议、人工判断三种身份分开 | 采用（付款复核台） | 三处分开呈现；提交的结论由检查结果决定，人不选；对机器提议的处置在提交时写明 |
| 证据冲突时两个写法并列 | 采用（付款复核台） | 上限的两个写法和各自出处并列，规则不替人挑一个 |
| 金额用最小单位或精确十进制，缺项不显示成 0 | 采用（付款复核台） | 币种加最小单位的整数；没有发票显示“未知”；按金额筛选必须带币种，不同币种不比较 |
| 场景：合同付款条件与发票例外复核 | 采用 | 第二轮做成付款复核台 |
| 核心对象控制在 ReviewCase、Evidence、CheckResult、Proposal、Decision、Attempt | 采用 | 对应 Case、File 与 EvidenceRef、CheckResult、Proposal、ReviewRecord、ActionAttempt |
| 约 12 个事项，1 个深度事项，其余自洽摘要 | 不同 | 12 个事项各带完整材料，因为状态是从材料当场算出来的，摘要没法自洽 |
| 按状态、责任人、日期和金额范围查询 | 采用 | 另加一条：金额范围不带币种时后端拒绝 |
| 切换 persona，负责人接受或退回 | 采用 | |
| 首次无数据与筛选无结果两种空状态 | 部分 | 两句说明不同；fixture 里没有“一个事项都看不到”的身份，前一种只有代码路径 |
| 落点：`demos/payment-review-workbench/` 单独一个目录 | 不同 | 放进了本实验目录，和事项工作台共用代码。要回答的是共用部分通不通用，分开放就量不出来 |
| 研究稿入 `vault/distilled/`，场景契约只留一份权威版本 | 没有做 | brief 没有入账；场景契约只有本目录 `scenarios/` 下各一份 |

## 与交接稿的对照

交接稿的身份见 [README](README.md#材料来路)。它推荐的第二个场景和研究 brief 是同一件工作，写得更细：一份可落成 fixture 的最小内容和 12 条带预期结果的不变量。它到的时候付款复核台已经做完，所以在这里是对照材料，不是施工输入；下面没有因为它改代码。

它写明自己取不到本目录。原因是它写的时候本目录还没有提交，它核对的 `main@d4fd387` 里没有这些文件。它对事项工作台列的核验点因此都还没有人做。

| 交接稿的不变量 | 现状 | 说明 |
|---|---|---|
| E01 正常包：净额、税额、总额的等式成立，按验收日加 30 个日历日算出到期日；检查通过之后人的决定仍不存在 | 部分 | 检查全部通过的事项停在“可提交”，没有人的记录，这一半成立。没有行项目、税额和总额等式；期限是 fixture 里写的申请期限，不是算出来的 |
| E02 总额的差额精确到最小单位 | 部分 | 金额是最小单位的整数，超过上限时差额精确给出。没有总额等式这条规则 |
| E03 币种或精度不符时返回不可比较，不换算 | 部分 | 币种不同时上限检查是无法判断；按金额筛选不带币种被拒；不换算。金额不带精度字段，小数位按币种推出，没有“不支持的币种”这种结果 |
| E04 同一字段的两个声明都保留、冲突未决；人选依据要留理由和没采纳的那个声明 | 部分 | 上限的两个写法和出处并列，规则不挑，提交被挡住。没有“人选一个依据”的动作，冲突只能等材料更新。只做了上限这一个字段 |
| E05 缺件写明是哪份文件、作什么用、谁供应、谁跟进、对方是否已接收 | 部分 | 写明缺什么、由谁补。没有跟进人，没有“对方已接收”的状态，没有未分派的义务 |
| E06 提议有编号、输入版本、生成方式与版本；接受、改写、拒绝各生成独立的人的记录，原提议保留 | 部分 | 有编号和所基于的材料版本；处置写在人的提交记录里并指回提议编号，原提议保留。提议不带生成方式和版本，也不关联某一次检查；页面写的“机器生成”其实是 fixture 里预先写好的文字，只靠页顶的演示环境提示说明 |
| E07 发票、合同、规则或关键证据出了新版本，旧提议和旧决定标为待重验，旧记录保留 | 部分 | 材料新增、减少或出新版本都会触发，旧记录保留。规则版本变化没有做 |
| E08 并发提交被拒，返回当前版本，草稿保留 | 有 | 测试和浏览器走查 |
| E09 两种丢失都先算未知，按尝试编号回查；同编号同内容不新增，同编号不同内容拒绝 | 有 | 两个场景都有测试。“同编号不同内容”只在事项工作台测了，机制在共用的内核里 |
| E10 关闭视图不取消已发出的尝试；离开未提交的填写先问；撤回已提交的决定是另一个动作 | 有，范围有限 | 应用内的跳转由页面拦截，关标签页和刷新请求浏览器的离开确认；切换演示身份不拦。接受之后只有材料有变时才能退回，没有无条件的撤回 |
| E11 fixture 不自洽时拒绝装载；运行状态与业务状态分开 | 有 | 启动时检查，有测试 |
| E12 无权的角色提交被拒；复核员可以不采纳机器提议，原提议仍可查 | 有 | 只验证演示角色的规则，不证明服务端授权 |

交接稿的其他建议：

| 建议 | 处置 | 说明 |
|---|---|---|
| 金额的最小单位用十进制整数字符串，带精度字段 | 不同 | 用的是 JSON 数字，不带精度字段；录入时拒绝超出精确整数范围的值 |
| 检查每跑一次有一个运行编号 | 没有做 | 检查结果在读取时按材料的当前版本现算，不留运行记录 |
| 保留本地进程的假后端，不换 MSW，不为第二个场景造第二个后端 | 一致 | |
| 第二个 adapter 等真的出现不同的接入需求再做 | 一致 | 没有做 |
| 呈现证据写明浏览器及版本、fixture、视口和缩放方式；文字缩放用真实机制检查 | 部分 | 写了视口和 fixture；浏览器只写了“应用内置的 Chromium”，没有版本；真实文字缩放没有检查 |
| 完成后写一张差异记录：每条共有的关系在两个场景里各处理什么对象、谁是权威、正常例、反例、不可共用的参数 | 采用 | 写在 [候选条目](evals/candidates.md)每条后面的对照表里 |
| 不提前抽一个大的企业 schema | 一致 | 公共契约只有 12 个与业务无关的结构 |
| 不宣称 Kit 的因果增益、生产收益或组件已晋升 | 一致 | 见 [施工发现](evals/README.md) |

## 没有实现的范围

事项工作台：登记依据、上传文书、完成任务、给单个事项指派复核人、关系图。付款复核台：登记或上传材料、给事项指定复核员、催补材料、发起付款、换算。两边都没有：通知、导出、真实身份与认证、持久化、生产构建。
