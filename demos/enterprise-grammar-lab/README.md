# 企业工作面语法实验

状态：2026-10-04，两轮，可运行。两个合成的企业工作台装在一个应用里：律所争议团队的事项工作台，和合同运营的付款复核台。它们各有一份 OpenAPI 契约、一个行为像真实系统的假后端和一套真实可操作的界面，并共用一层与业务无关的契约、后端内核和工作面。全部数据是合成的。

实验问两件事。第一轮：只给 Kit 的企业工作语法和一份场景契约，施工出来的东西像生产软件还是像演示用的 CRUD。第二轮：第一轮做出来的“通用”部分，换一件不同的工作之后还剩多少能用。答案和证据在 [施工发现](evals/README.md)。没有做不给 Kit 的对照组，也不打算做，所以结论只说这两轮怎样消费了 Kit，不说 Kit 的效果。没有受众或专业人员看过。

合并进 `main` 之后，用户另找的执行者做了一次独立复验，只到代码和后端，没有看界面；它报告的两处 fixture 检查漏检已修，见 [合并后的独立复验](evals/reverification.md)。

执行者：Opus 5.5 主会话完成设计、实现和验证；每一轮各有一个 Sonnet 只读代理在不知道主会话结论的情况下复查代码，两轮分别找出 14 处和 16 处经核对属实并已修正的缺陷，另各有若干记录在案没有修。Luna 在本会话不可用，没有工作记在 Luna 名下。

## 运行

需要 Node 24 以上（实测 25.9.0）。依赖不会自动安装：

```sh
cd demos/enterprise-grammar-lab
npm install
npm run backend    # 终端一：假后端，http://127.0.0.1:8787/api/matter 与 /api/payment
npm run web        # 终端二：前端，http://localhost:5180
```

左上角切换工作台，右上角切换演示身份。每种状态怎样触发，见 [fixture 对照表](fixtures/README.md)。后端状态在内存里，重启恢复原样。

```sh
npm test           # 两个场景的后端行为、契约一致性、fixture 自洽，和金额录入，45 项
npm run typecheck  # 前后端对生成的契约类型做类型检查
npm run contract   # 改了契约之后重新生成类型
```

## 两个工作台

| | 事项工作台 `/matters` | 付款复核台 `/reviews` |
|---|---|---|
| 工作 | 主办律师核对一项风险的依据，提出处置建议；合伙人决定或退回 | 复核员看一笔付款申请的规则检查结果，提交复核；负责人接受或退回 |
| 判断的对象 | 带立场（支持、反驳、限制）的依据 | 规则检查的结果：通过、未通过、无法判断、依据冲突 |
| 页面的组织 | 事项页六个投影，风险是列表加详情 | 事项页三个投影，复核页把规则、机器提议和人的判断分三处 |
| 只有它有的 | 批量指派复核人（后台作业、逐项结果）、可保存的视图、特权文书 | 精确金额与币种、按“材料、版本、位置”打开依据、冲突的两个写法并列、预制的机器提议 |
| 场景契约 | [matter-workbench](scenarios/matter-workbench.md) | [payment-review](scenarios/payment-review.md) |

两边都有的：对象带版本，动作绑定读过的版本；后端告诉界面现在能做什么、为什么不能、下一步等谁；提交后结果未知时先核对再重发；所依据的材料出了新版本，已有的判断要重验；每次动作留下带尝试编号和规则的记录。

## 验收

对象与版本：本目录，基线 `main@d4fd387`，经分支 `claude/enterprise-grammar-lab-20261004` 合并进 `main`（`9514ce4`）；独立复验之后的修正是其后的一次提交。执行者 Opus 5.5，日期 2026-10-04。

| 层 | 结果 | 证据与范围 |
|---|---|---|
| 文档一致性 | 通过 | `python3 scripts/validate_repository.py` |
| 契约 | 通过 | 后端测试里每个响应按契约 schema 校验，未声明的状态码算失败；前后端共用生成类型，`tsc` 无错误 |
| 系统行为（后端） | 通过，40/40 | 事项工作台 21 项，付款复核台 19 项，覆盖两份场景契约第 3 节的各种情形 |
| 系统行为（界面） | 手走通过，范围见下；自动化测试只有金额录入与显示的 5 项 | 应用内置浏览器（Chromium），1360×900 与 390×844 |
| 材料与呈现 | 部分 | 界面文字按 Kit 的成文规则写，主会话自查；没有第二个人审过 |
| 业务接受与影响 | 未执行 | 没有律师、合同或财务人员、使用者看过；接受率、复核时间等均未知 |
| 运营与退出 | 不适用 | 演示，不运营 |

事项工作台在界面上走过的路径（第一轮）：提出建议并在记录页看到对应事件；同事并发提交后再提交，被拒并保留已填内容；两种响应丢失的核对与重发；带入建议内容；退回；重新决定依据版本落后的风险；批量指派三个事项，其中一个因利益冲突未通过；信息隔离、特权依据、无权身份；缺依据、空事项；面板读取失败与重试；停掉后端后刷新，保留旧内容；筛选、翻页、保存和删除视图；搜索与跳转；只用键盘完成一次提出建议；填到一半离开被拦下；返回列表恢复滚动位置；390 与 680 像素宽度下没有横向溢出。第二轮重构之后重走了三条：提出建议、批量指派（含一项利益冲突）、用下拉切换身份。

付款复核台在界面上走过的路径（第二轮）：点依据打开发票第 1 版并标出金额栏，位置不存在时提示定位失效，版本不存在时提示未找到；作为例外提交，带入机器提议的文字并写明“修正后采纳”；负责人接受，状态显示“材料已接受，未付款”；退回；提交后发票重开的事项不能接受、只能退回；上限冲突的两个写法并列；缺验收记录时写明缺什么、由谁补；没有发票时金额显示未知；检查面板读取失败不影响页面其余部分；观察员看保密事项被拒；按金额筛选，小数位过多时不提交；两种响应丢失；同事并发提交；390 像素宽度下没有横向溢出。复查之后又走了四条：填了金额再清币种不再崩溃；带入机器提议的文字之后离开被拦下；在一个事项上打开的表单不会带到另一个事项；记录里规则结论单列一行。

没有验证的：

- 前端的自动化测试只覆盖金额的录入与显示；动作面板和尝试状态机没有测试。生产构建没有运行过（`vite build`）。
- 读屏、浏览器文字缩放、减少动效、其他浏览器。键盘只走了事项工作台的一条路径，付款复核台没有用键盘走。
- 两轮独立复查之后的修正里，只改代码没有在浏览器里重走的，分别列在两份施工发现里。
- 换一个实现同一契约的真实后端。可替换性只有结构上的依据。
- 第三个场景。两个场景共用不等于通用。

## 材料来路

第一轮的任务来自用户在 2026-10-04 会话里贴入的两段 Chat 文字，内容是把这件事做成企业界面语法实验的建议。原文没有入账 Vault，仓库里没有它的副本。

第二轮的场景来自用户给的一份研究 brief：`legal-finance-workbench-research.md`（2026-10-04，只读研究建议稿，sha256 `a05e5727…1c3f03`，在用户的下载目录，没有入账 Vault，仓库里没有副本）。第一轮末先拿它的反例表对照过事项工作台；用户随后决定做它建议的付款复核场景。对它的逐项取舍见 [实现说明](demo.md#与研究-brief-的对照)。

收尾时用户又给了两份材料。一份是交接稿 `handoff(1).md`（另一个执行者写给 Claude 的，核对日期 2026-10-04，基线 `main@d4fd387`，sha256 `1eff9247…463f46eb`，在用户的下载目录，没有入账，仓库里没有副本）。它推荐的第二个场景在它到之前已经做完，这里只拿它的不变量表对照了现状，见 [实现说明](demo.md#与交接稿的对照)；它自己报告的核查结果这里没有复验。另一份是用户贴入的三条收尾建议，处置见 [施工发现](evals/README.md#收尾)。
