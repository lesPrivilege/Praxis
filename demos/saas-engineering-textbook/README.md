## 构建与运行

```bash
node demos/saas-engineering-textbook/build/build.mjs
```

无需安装：Markdown 解析（marked 18.0.4）与图布局（dagre 0.8.5）的副本在 [vendor](vendor/README.md)。构建做的事见 [build](build/README.md)；输出放在一个平铺目录 `site/`，因为仓库要求每个目录有 README。正文改动一律改 Books，再重建。

本地预览需要从仓库根目录起服务（页面里指向 Vault 的链接是相对仓库根的）：

```bash
python3 -m http.server 8796 --bind 127.0.0.1
```

然后打开 `http://127.0.0.1:8796/demos/saas-engineering-textbook/site/index.html`。直接双击 `site/index.html` 也能读，只是 Vault 链接打开的是原始文件。

## 编订变更

主线 13 个文件按 Prose 审阅方法改写：四名审阅者共给出约 600 条意见（含标为保留的条目），主会话逐条裁决后整篇重写。大多数采纳；以下几类退回或改写后采纳：把书面语压成口语的建议（“弄懂”“根本处理不了”）改回书面语；删去承担内容的对照（如“结构有效只证明能表达”“1/1 或 9/9 不满足 10/10 政策”）的建议退回。

改动的性质：

- **叙述与设防**：删去作者的预告、自我说明与重复的免责声明；合成与来源的分界在每例开头说一次，未实测、未执行的验证和迁移边界各保留一处。
- **结构位置**：五步小标题统一为“步骤：名词短语”；表头、行标题改成并列的名词短语；问句式标题改为陈述。
- **措辞**：直译搭配、模型惯用搭配（形成、建立、承担、作出）、“回答”式拟人、公文腔字眼改写；对象作主语。
- **术语统一**：批量操作、详情页、合成、原语言术语、带类型的关系、简答、退款。

### 第二批

54 个文件分 21 批，每批 1–8 个文件：方法第 2–12 章，H01、V04、V20 以外的 30 例，`architecture.md`、`problem-index.md`、`case-catalog.md`、`transfer-map.md`、`semantics.md`，`foundations/README.md`、`packages/README.md` 与六个包入口页。每批先由一名只读的 Opus 审阅者按 Prose 规则与委托方反馈出意见表（合计约 2,250 条），再由另一名未参与审阅的 Opus 编辑逐条裁决、整篇改写，写下裁决记录；主会话复核每条语义改动、抽读改写稿，并统一跨批的体例。分工与主线不同：主线由主会话自己裁决改写，第二批量大，裁决交给编辑代理，主会话负责复核。

- **设防**：合成身份、provider 只作参照、未实测，在每例开头说一次（第三轮已删去，见下节）；其余补述删去。“不代表”“不证明”“不声称”等由约 94 处减到 23 处，留下的都防止误读。句末反射式的“不能……”只留划定边界的。
- **结构位置**：五步标题一律“步骤：名词短语”，合并标题拆开，每个方法章五个步骤词各有一节；问句或判断句式的章名、小节标题改为名词短语；案例末节统一为“进入……的先查项”，练习答案统一为“简答”且先给结论；识题表头全书用“识题线索”，同包各例的表头、检查表表头逐字一致；六个包入口页的栏目、次序、案例表表头并列。
- **术语**：synthetic 在正文统一为“合成”；同一概念一词（如 hash、多重集、guard、write skew、correlation key、持久 inbox、已学案例 / 变式案例）；临时译名改回英文原词或通行说法。
- **跨页名称**：`case-catalog.md` 称“案例目录”，`case-index.json` 称“案例索引”，`semantics.md` 称“共同词表与读图约定”，`packages/README.md` 称“六组行业案例”；入口页、`claude-handoff.md`、`terminology.md` 与 `foundations/terms.md` 的锚文本和锚点随之更新。

### 第三轮：来路标签与版式

用户读后指出，“两条贯穿全册的例子都是原创的合成设计，不复原任何厂商产品的内部实现”这类表述“完全是冗余，不能承载任何读者功能”；版式“更接近格式化 markdown 渲染”，期待接近知识视频的编排、鲜明的可视化并 anti-ai-slop，必要时用 SVG 绘制。

- **正文**：一名 Opus 编辑删去 63 个文件里约 70 处来路声明与约 190 处“合成”“教学”“虚构”修饰，主会话复核留下的句子，再删去 V03、V10、V14、V16、H01、V13、H05 七处“不是某项标准 / 不对应某家产品”的声明。构造与真实的分界只在 `semantics.md` 说一次。用测试数据评估、要求读者自造测试输入、软件不负责的责任边界属于正文，保留。拓扑 JSON 里 32 个节点名去掉同类修饰；`commercial-finance/validate-package.py` 中要求“合成”字样的断言删去。Kit 随之补写成文原理第 8 条，见 [ADR-034](../../docs/decisions/034-state-limits-once-and-keep-process-out.md)。
- **版式**：主会话按 Design Kit 重排外壳，一名未参与的 Opus 审阅者看截图与代码给出 14 条意见。采纳：去掉场景头里的步骤词与装饰短线、删去标题卡上与进度轨重复的站点条、链接改为墨色（强调色只表示“当前位置”）、案例角色按分道排、生命周期的 guard 常显、首页链图去掉强调色与渐层底色、路线表按列排、去掉悬停底色与图内边框标签。退回：把每场的首个展项提到标题下——会改变正文的阅读次序。
- **静态图**：一名 Opus 只读扫描主线找出 18 处“读者要在脑中拼图”的段落，三名 Opus 绘制者按章分文件施工，每个数字对照原句；主会话逐张看图，删去两处重复图注的图内说明。

### 第四轮：全景与局部答案

用户交来一份写作规范，评语是“gpt 文笔不足采”，结构理念可取。取用的三项见 [ADR-035](../../docs/decisions/035-local-answers-and-link-relations.md)，原件登记与取舍见 [Vault](../../vault/distilled/technical-compilation-writing-research-20261014/knowledge-organization-spec-20261015.md)。

- **做法**：六名 Opus 编辑按文件分工，处理全书 77 个文件：章首写成可以独立成立的概览，每节首段先给这一节的判断，链接旁写明关系。另一名 Opus 把超过 320 字的 16 段章首压到 180–270 字。站点把章首和节首排成大字，所以版式不用改；只修了 V01–V03 开头的“返回”链接被当成章首的问题。
- **随手删去**：V07、V09、V05、V15、V06、V02、V17、H04、H05 里“并非 SAP API”“本例的设计”“尚未端到端运行”一类来路与过程说明，归第三轮的同一类。
- **核对**：全书行内代码、代码块、链接、图件与静态图标记、标题与改写前快照逐项比对，无丢失；`transfer-proposals.json` 的出处摘录全部仍逐字出现。
- **留给用户的结构问题**：案例页的二级标题把五步与“技术选型”“lineage 与影响范围”一类专题并列；“进入……的先查项”有的是独立一节、有的是变式里的一段；企业机制第 3 章的“从工具连接到授权动作”夹在五步之间；首页仍写“这份教材写给 vibe coder”。
