医疗、临床试验与实验室·V01

从检查请求到一笔可核销的收款

诊疗机构要完成适当的诊疗、保存可解释的结果，再向正确的付款方请求费用。临床人员关心结果能否用于后续判断，收费人员关心谁承担多少费用，财务人员关心款项是否收到。把三者塞进“已完成”这一个状态，软件会在业务尚未结束时就不再提醒责任人。本例让请求、报告、理赔提交和款项核销各走自己的生命周期：裁决按行冻结，付款分配用完整身份查找对应的责任行，金额相同不能决定归属；报告更正沿反向依赖找出要重审的费用决定，只生成重审清单，不自动退款。提交后超时，状态记为未知，先核对外部是否受理，再决定是否重发。

本例取一位病人的一次就诊：检验收费 120、影像检查收费 180，单位均为记账单位；不含税、退款、外币、预授权、追偿和多保险协调。两份报告由专业人员复核后，收费人员提交一份两行 claim。支付方认可金额为 100 与 150，其中支付方承担 80 与 120，病人承担 20 与 30；支付方暂时只汇入 180。检查是否必要、身份怎样纠错、结果怎样解释、真实费用由谁承担，都由相应专业人员决定。

01识题：跨系统金额与报告更正

**金额相同的两笔款可能属于不同费用；获赔是支付方的决定，收款是到账的事实。**跨系统的金额要彼此对上时，先找身份映射与对账方法；旧报告的变化会影响后续决定时，先找版本依赖图。

识题线索 解法 验算与后续查证
多个付款项要对应多条费用责任，局部金额相同 完整身份的 lookup 与两侧余额约束 逐行核对责任、付款预算与未分配额；查支付方行号、币种、重放和更正规则
报告更正后，待重审的费用决定不明 版本化证据与反向依赖遍历 列出受影响的集合与不受影响的反例；查源报告的替代语义与机构补件流程

FHIR（Fast Healthcare Interoperability Resources）是交换医疗信息用的一组标准资源定义，中文译名不统一，后文沿用英文。本例以 R5 的语义为参照：ServiceRequest 表达请求或计划，Observation 表达单项测量，DiagnosticReport 汇集结果及解释；报告可以引用它所响应的请求。这份资源说明存在这样一条记录；每项检查是否做完、结果是否正确，要另看执行与复核的证据。ServiceRequest、Observation、DiagnosticReport。

影像还多一层。ImagingStudy 保存 study、series、instance 等检查组织信息和检索线索，不把全部医学数字成像和通信（Digital Imaging and Communications in Medicine，DICOM）图像放进 FHIR 资源。DICOMweb 提供影像对象的查询、存储与检索事务。系统把影像像素留在影像归档与通信系统（picture archiving and communication system，PACS），工作台只取经授权的引用和按需加载的影像。FHIR ImagingStudy、DICOM PS3.18 §10.1。

Claim 向付款方请求费用，ClaimResponse 表达处理和裁决，PaymentReconciliation 描述付款及其分配。FHIR 明确区分裁决响应和支付；本例即使收到付款分配记录，也要等财务凭证核对后再关闭相应应收。这里分开的是三种信息的职责；账务用什么格式传输，由各机构的接口决定。Claim、ClaimResponse、PaymentReconciliation。

02解法：并行生命周期与明确关联

请求、报告、理赔提交与款项核销各有独立的状态，靠明确的引用关联，每一方由自己的证据推动。本例中，请求按 draft → active → completed 推进，未执行时可进入 revoked；进入 completed 的依据是执行证据，账单成功不触发它。报告从 preliminary → final，之后可能变为 amended 或 entered-in-error。报告更正必须保留替代关系和通知责任；迟到的旧 final 通知不能覆盖较新修订。FHIR DiagnosticReport 也专门讨论修订与撤回，接收方必须处理这些变化；历史怎样存、提醒怎样发，仍由应用自行设计。DiagnosticReport §10.3.6.5。

理赔提交有自己的 draft → ready → submitted → adjudicated 路径，外部请求超时则进入 unknown；adjudicated 只说明响应已核对，可能部分获准，也可能全部拒绝。报告被更正后，已提交的 claim 进入 review-required，由收费人员判断是否需要补件或更正提交。旧 claim 原样保留，支付方的旧裁决也由支付方处理。这组提交状态由应用自己定义，与 FHIR Claim.status 是两套状态。

以就诊为单位的应收核销聚合按 unmatched → partly-allocated → reconciled 推进，记录这次就诊还有多少责任金额未结清；其中每条 allocation 都是有独立身份的分配项。付款侧另有 payment budget，记录一笔已确认的收款还有多少可分配金额。180 全部分配完时，付款侧为 fully-allocated，就诊应收仍为 partly-allocated，因为还欠 20。发现错配时进入 disputed，用冲销记录恢复，已有资金流水保持原样。机构可以完成检查、收到裁决却仍有未收款，也可以先收病人预付款而还没有报告。正因状态彼此独立，工作台并排显示“报告 2/2、裁决已收到、支付方待收 20”，三项各报各的进度，不合成一个总百分比。

03提交按钮与系统边界

提交理赔时，服务端重查权限与版本，在一个事务里保存这次尝试与待发送记录；外部超时后按同一 operation 查询，不产生新 claim。收费列表按就诊显示请求、报告修订、claim 版本和待处理原因。进入详情后，用户先看两项服务的费用依据、所引用的报告版本和分担规则，再点击“提交理赔”。服务端重查角色、就诊权限和版本；两位收费人员同时打开旧页面时，第二个提交返回已有操作或版本冲突，并标出变更的项目。禁用浏览器按钮改善的是体验；防止重复提交由服务端负责。

本地事务提交成功时，服务已保存 operation ID、claim 快照、两条行映射及待发送的 outbox 记录，界面先显示“已保存，等待支付方确认”。worker 发送外部请求，并保存外部受理号。断网后再次进入详情，浏览器用 operation ID 找到原尝试；“重试查询”只读取进展，不产生新 claim。外部接口支持可核对的客户业务号或幂等语义时，超时后才有依据自动重新提交；接口不支持时转人工核对，自建队列同样受这条限制。

图中对象和边可在 V01.json 逐一定位。depends_on 指明提交依据，不表示报告已经传送；实际读取由 reads 表达。delivers 只表示事件交接。样本运输和款项转账不画成消息箭头，本例只模拟它们的证据。

通知接收端先验证来源与授权范围，再把原始事件身份、对象引用和接收时间写入 inbox。worker 核对当前外部对象，结合已接受的修订关系更新本地投影。收到先前版本的回执时，只记下收到过它，不回退报告，也不覆盖新裁决。同一业务决定可能对应多个 event ID，所以去重除了按事件，还要用外部裁决身份和本地 claim 版本约束业务效果。来源错误、tenant 错误或缺少行号的通知进入隔离区，由人处理，不按“尽量匹配”自动入账。

技术选项与取舍

小团队可以用 React + TypeScript 构建分栏工作台，用 TanStack Query 管理查询和提交后的失效重取；它的文档明确区分标记陈旧与后台重新获取。界面要显示上次核对时间，不把客户端的乐观更新显示成“已获赔”。查询 key 带 tenant、访问范围、就诊和修订；退出账号时清理缓存，敏感详情不持久存入浏览器离线缓存。组件化便于对比版本，代价是要划清客户端缓存和服务端权限各自管什么。Query Invalidation。

业务后端可选 Python + FastAPI 或 Java + Spring Boot。前者适合团队快速编写费用映射与独立计算模块；后者适合已有 Java 团队把接口、事务和 FHIR 工具集成在一起。临床身份、收费合法性和对账语义由应用自己建模，两种框架都只提供承载它们的结构。若需要实现 FHIR 资源服务器，可以评估 HAPI FHIR JPA Server；它的 starter 提供标准资源操作，并可配置数据库。沿用专门的服务器可以少写重复的接口，代价是还要验证 profile、术语、授权、升级和业务库之间的映射；通用的资源 CRUD 只覆盖本例流程中的存取部分。HAPI FHIR JPA starter。

关系数据库可以保存提交快照、行映射、核销账和操作记录；报告附件和原始接口文件放在受控对象存储，影像留在 PACS，库内保存可授权解析的引用，而非长期签名 URL。PostgreSQL 的复合唯一约束适合 (tenant, payer account, operation key)，相关列必须非空；引用 tenant 的外键防止跨租户的行关联。普通 CHECK 约束单行；跨行金额总和由事务保证：在同一事务中锁定付款预算行与所有涉及的应收行，再重查两边余额。行锁协调的是库内竞争，支付方的网络请求在这个事务之外。Constraints §5.5.1/3/5、Row-Level Locks §13.3.2。

起步时可以由数据库 outbox 加单独的 worker 驱动重试；需要多订阅者或突发量较大时，再评估 RabbitMQ 等独立消息系统。后者带来更多隔离和调度空间，也带来积压、顺序、重放与运维责任。选择依据是实测吞吐、恢复时间和团队能力；行业是医疗，本身不构成拆分微服务的理由。

04演算：费用责任与款项匹配

支付方的 180 核销到 L1 的 80 与 L2 的 100，L2 仍欠 20；报告更正则沿反向依赖生成重审清单。先冻结裁决版本，再按行分配。“收费额”“认可额”“支付方责任”“病人责任”“合同调整”分列，各列数值由本例明确的合同规则确定，不能从一个总数反推出各方的权利。

服务行 收费额 C 认可额 A 支付方责任 P 病人责任 U 合同调整 J=C−A
L1 检验 120 100 80 20 20
L2 影像 180 150 120 30 30
合计 300 250 200 50 50

先逐行验算 A=P+U 和 C=P+U+J。这里没有扣款追偿、二次保险或拒赔争议，所以能用简单等式；真实场景要把新增的责任类别显式列出。不能为凑这条等式，把未经判断的拒赔款塞进 U。金额以整数最小记账单位存储，实际币种与舍入规则另定。

支付方提供一笔金额 180 的付款分配记录，引用 L1 的 80 和 L2 的 100；银行或财务导入也确认实际收到 180。本例先把两条裁决行放入字典，key 为 (tenant, payer account, claim ID, claim revision, line sequence, currency)。依次查找付款分配项：分配项 1 金额 80 查到 claim 行 1（L1），分配项 2 金额 100 查到 claim 行 2（L2），每次核对金额非负、币种相同、身份唯一；L1 待收变为 80−80=0，L2 为 120−100=20。病人另付 50 并完成独立核销后，全案满足：

收费 300 = 合同调整 50 + 已收 230 + 未收 20
收费300=合同调整50+已收230+未收20

此时付款侧的 180 已全部分出，处于 fully-allocated；就诊应收的 L2 仍差支付方的 20，处于 partly-allocated。

若 180 的银行凭证只到达一份，分配记录却被投递两遍，累计已收仍是 180：幂等 key 绑定付款身份与分配项身份，重投的分配项 1 与原来的 key 相同，只记一次；相同 key 的内容一旦改变，必须报冲突。若有两笔各 100 的付款却没有可信的项目引用，它们留在未分配现金，等人处理；金额相同不足以决定归属。“求和相等”和“对应正确”因此是两种检查。

这属于 ALG:lookup。朴素办法对 m 个付款项逐一扫描 n 条裁决行，代价 O(mn)；构建字典耗 O(n) 时间和空间，理想散列条件下处理付款项平均 O(m)，整体平均 O(n+m)。数据库复合树索引更适合不把全部历史载入内存的场景，单项查找通常 O(log n)。算法降低的是匹配成本；输入是否来自真实银行、病人身份是否有错，要靠来源核对与人工复核，模糊匹配给出的是供人复核的候选。

第二种计算用于报告更正，属于 ALG:graph-paths。保存“提交包依赖报告 r1、裁决依赖提交包”的有向关系，用反向邻接表从 r1 找出受影响的提交与裁决，访问集合防止重复，遍历代价 O(V+E)。结果只是重审清单，不是自动退款清单：依赖旧报告的某个项目可能不受本次文本更正影响，要由收费人员判断；不能沿病人关联边把所有历史账单都作废。

05正常路径与故障路径

正常路径停在“仍有支付方应收 20”；两条故障路径都靠核对和新记录恢复：提交超时记为未知并核对，报告换版只标出依赖旧版的 claim，已收流水保留。

正常路径中，临床人员确认请求，两处检查机构返回复核后的报告；收费人员按相应版本生成 claim v1；支付方受理并返回按行裁决；财务人员核对 180 的付款与两条分配项，再核对病人的 50。屏幕最后显示“诊疗证据齐备，仍有支付方应收 20”。这个结果准确说明了还剩哪一笔、由谁欠。

演示中最容易被掩盖的故障是提交后断网：支付方已接受 claim，客户端却没拿到受理号。此时状态记为 unknown，意思是外部是否受理尚未确认，并非提交失败。worker 用已持久化的业务引用向支付方查找；找到相同内容就补记受理号，找不到且查询完整性不确定时继续待核对。只有明确未受理，或对方保证相同操作 key 可以安全重放时，才重新发送。工作人员离开页面后，这项核对仍由 worker 和待核对队列承担。

另一条故障路径发生在钱已部分到账之后：报告 r1 被宣布错误，r2 到达，随后迟到的 r1 通知又出现。本例保留 r1，把当前报告指针切到 r2，标出依赖旧版的 claim；已收 180 的流水照旧保留，报告换版也不触发自动退款。收费人员确认是否需要调整理赔，财务人员依据正式更正结果记冲销或差额。恢复的目标是有解释的历史与当前余额；各对象停在各自的版本上，不回滚到同一时刻。

06规模假设与优化次序

规模压力集中在核销竞争与大批量文件：所有核销入口按统一顺序先锁付款预算、再锁应收，付款文件分块验证，缓存不授权新动作。

容量预算为 20 个机构、每日共 10,000 次就诊、每次平均 4 份报告，保留一年约 1,460 万份报告元数据；影像像素不计入这份元数据预算。假设业务高峰有 100 个并发工作台、每秒 50 条通知、付款文件一次含 50,000 个分配项。拟验收目标是：50 行已授权列表读取 p95 小于 500 ms，本地提交持久化 p95 小于 300 ms，正常负载下 99% 已接收事件在 30 s 内反映到投影；支付方响应时间单独计量，本地成功延迟不含它。以上均未压测。

列表按 tenant 与时间范围分页，详情按需加载，影像独立限流；付款文件先分块验证再提交核销，错误行隔离，并保留文件级合计。若一个付款文件包含同一应收的许多项目，应先合并该应收的增量再锁定，避免反复争锁。所有核销入口按统一顺序先锁付款预算，再按稳定 ID 锁应收，重查双方余额后提交。只锁应收会漏掉一种竞争：同一笔到账 180 被同时分给 80 与 120 两笔应收，两人各自看到可用 180，合计却写入 200。共享付款预算也进入事务后，先成功的一笔会减少后续可用额：80 先提交，可用额只剩 100，第二笔 120 必须拒绝或调整。事务保持短小，死锁中止后用同一操作身份重试。

跨 tenant 设队列配额，一个机构的大批量影像导入只占用自己的配额，其他机构的裁决处理照常进行。

缓存 key 含访问 scope 和对象版本，报告更正触发相关查询失效；读模型落后了多久，要在界面上看得到。发送理赔和核销时到权威状态核验，不能让缓存中旧的“已复核”标签授权新动作。恢复演练应测量积压的最长年龄、未确认操作数量、无法匹配的金额和修订未通知的数量；只看请求成功率，会漏掉这几类未完成的责任。

08变式：条件变化与迁移

到账少于分配、先提交部分费用、迁到批次检验，三种变化里证据与费用身份分离的机制不变，变的是可核销上限、提交 guard 和证据的代表性。

练习一：到账少于分配记录。 支付方仍承诺 200，银行只收到 170，分配记录仍写 180。原先的等式应怎样变化？

简答：责任总额不变，变的是实际可核销上限的证据。先把分配记录与到账之间的差异 10 留在争议队列，不直接按 180 核销；确认的 170 怎样分到 L1/L2，还要有可靠引用或财务决定。要保持的不变量是“已收、未收和调整能解释收费”；错误做法是把差额自动减为合同调整。检查一笔付款的已分配额不超过经确认的可用额，并记下未分配与待核对的差额。若真实政策涉及手续费或净额结算，要新增显式的费用对象后重算，不能沿用本例无手续费的前提。

练习二：影像报告未定稿时先提交检验。 影像报告尚未 final，机构允许先提交检验费用。是否必须等两份报告都齐？

简答：不必。本例“报告齐全再提交”的 guard 可以改，临床证据与费用身份分离的机制不变。把提交包拆成只含 L1 的 v1，以及后续 L2 的独立请求或明确的更正关系，并保留按服务行唯一的收费义务；预览要显示这是部分提交。反例是为了赶进度把 preliminary 报告显示成 final。检查重复提交不会对同一服务行产生未经说明的双重请求；修改提交策略仍要经机构和支付方规则复核。

练习三：迁移到 V03 批次检验。 从病人的检查转到 V03 批次检验，能否沿用同样的报告更正传播机制？

简答：可以保留“决定绑定证据版本，变更生成重审清单”的关系（TR:V01:V03:evidence-revision）。V03 还必须追溯 sample 与 lot 的代表性、方法、校准和质量控制（quality control，QC）；一个 sample 的结果不能代表任意批次。检查受影响的证书是否都能追到失效输入，同时未关联的 lot 不被误停。医疗报告的更正并不自动具有批次召回或证书撤销的法律效力。

可迁移到 H01 的是“请求、外部确认、权利或余额分别保存”（TR:V01:H01:adjudication-payment-separation）；订阅付费后即开通的策略则不能套到诊疗处置上。Stripe 发票文档也提醒，paid 可能来自余额抵扣或线下标记；这里借它说明状态要读清证据来源。Invoice lifecycle / Paid invoices。

09进入诊疗机构的先查项

进入一个陌生的诊疗机构时，可以先跟随一笔脱敏的部分拒赔或部分到账案例，把请求号、报告版本、费用行、支付方引用和收款凭证画在一起，问清每次人工补录究竟在弥补哪个身份或责任缺口。先辨认现有的 EHR/HIS、LIS、PACS、理赔清算接口和应收核销系统各自拥有哪些事实，再决定新增的工作台该做查询聚合、适配器还是独立业务服务。下一步索取实际采用的 FHIR profile 与 CapabilityStatement、DICOM Conformance Statement、支付方重放/查询规则和更正文件样例；读到适用版本后，再评估接口库或成熟产品能否覆盖这一段。首个验证切片应让同一就诊经历一次报告更正、一次外部超时和一次部分付款，并由临床、收费与财务人员分别确认自己的对象没有被另一方的状态覆盖。这样的切片比先实现完整菜单更能暴露方案的适用前提。
