计算与系统方法·第八章

用可说明的误差换取空间与速度

“可能见过”“大约多少”“最相似的候选”，分别由布隆过滤器（Bloom filter）、HyperLogLog（HLL）和近似最近邻搜索（approximate nearest neighbor search，ANN）回答，三者都用可说明的误差换取空间与速度，错误的方向却不同：Bloom 在同步完整时只会误报、不会漏报，HLL 给出带标准误差的去重估计，ANN 可能漏掉真正最近的点。探索、预筛和候选召回适合用近似；结果要用于计费、付款去重、封禁或证据提交时，回到精确集合、可审计的记录或人工复核。

01识题：近似结果的用途

探索、预筛和候选召回适合用近似；业务确认能否容许误差，要看具体承诺了什么。H07 的趋势报表可以展示估算，X01 的用量结算需要按契约核对精确事实；H06 的知识检索可以先给候选，H08 的封禁决定要回到可审计的记录或人工复核，“相似”只提供线索。

02解法：错误方向与补救方式

这三种近似各牺牲一种精确性，错误的方向与补救方式各不相同：Bloom 的阳性回到精确集合核对，HLL 的估计靠合并兼容的摘要组合，相加会把重合的部分算两遍，ANN 漏召回的项靠扩大搜索预算或补充检索找回。先说清允许哪一种错，再选近似方法。

03演算：三种近似结构

三个小例各显出一种错误：Bloom 把从未插入的 C 报成“可能存在”，HLL 的四个桶只演示更新、估不出可靠人数，ANN 召回不到的 B 再怎么精排也回不来。

布隆过滤器（Bloom filter）：共享位图与不存在判定

设位图有 8 位、两个 hash。插入 A 时把第 1、4 位设为 1；插入 B 时把第 4、6 位设为 1。查询 C 的位置为 1、6，两位都是 1，所以回答“可能存在”，尽管 C 从未插入。查询 D 的位置为 2、6，第 2 位为 0，于是回答“确定不在这个过滤器所表示的集合里”。

位图只记下哪些位被点亮，不记是哪条记录点亮的，所以阳性结果要回到精确集合核对。在 hash 一致、插入已完整同步且没有错误清位的条件下，已插入元素不会因标准 Bloom 算法产生阴性。分布式同步落后时，新对象仍可能被查成不存在，这类漏报出在运行环节。Redis Bloom 文档说明误报、容量与查询语义。

插入和查询都要算 k 个 hash，成本 O(k)，位图空间 m 位。若每次落点独立且均匀，插入 n 项后，kn 次落点都避开某一位的概率是 (1−1/m)^(kn)，约为 exp(−kn/m)。再近似地把查询涉及的 k 位视为独立，误报率便是 (1−exp(−kn/m))^k。这是参数估算，每组数据的实际误报率要实测。固定目标误报率时，空间随 n 增长；要求更低的误报率，也需要更多空间。工程上由成熟实现按预计容量和错误预算选参数，再实测误报率。

误用反例

把“可能存在”当成付款事件已处理而直接丢弃，会漏记真正的新事件。普通 Bloom 的每一位可能由几项共享，把某项对应的位清零，共享这些位的其他项就会变成漏报。验算用精确集合给出真值，分别统计误报和已插入项的漏报；出现漏报，先查同步、重建与删除协议。

HyperLogLog（HLL）：稀有位模式与去重计数

随机 hash 后，连续很多个前导零很少见；见过的数据越多，遇到这种模式的机会越大。HLL 用 hash 的前几位分桶，用剩余位里首个 1 的位置更新该桶的最大值，再把各桶的值经校正组合，估计去重数。Flajolet 等人的原论文 §1、Figure 2给出算法与约 1.04/√m 的渐近标准误差，m 为寄存器数。它描述估计误差的分布，单次估计的误差可能更大。

用 4 个桶演示更新，初始寄存器为 [0,0,0,0]。A 的 hash 写成 00|001…，首个 1 在剩余串第 3 位，得到 [3,0,0,0]；B 为 00|01…，第 2 位不足以替换 3；重复的 A 不改变寄存器；C 为 10|0001…，得到 [3,0,4,0]。重复项因此不增加信息。四个桶太少，代入大样本公式也得不出可靠的人数。

实际实现还有小范围校正等修正。每项更新访问一个寄存器，在常见的固定宽度 hash 模型下为 O(1)，空间主要由精度参数决定；hash、寄存器布局与精度都兼容的摘要，可以逐桶取最大值合并，合并成本 O(m)。Redis HLL 文档给出其实现的内存与标准误差说明，可作为产品能力的参照。

误用反例

周一独立访客约 100、周二约 100，直接相加得到两日独立访客 200。两日的访客可能完全重合，应合并兼容的摘要，或者精确去重。

沿用前面四个桶的例子把这件事缩小：周一来了 A、B、C，寄存器为 [3,0,4,0]；周二来了 A、C 和 D，D 的 hash 为 01|1…，周二的寄存器为 [3,1,4,0]。精确地数，两天各 3 人，相加得 6，实际只有 A、B、C、D 4 人。逐桶取最大值合并得 [3,1,4,0]，与把 A、B、C、D 依次插进同一个摘要的结果相同。

HLL 只保存寄存器，列不出这些人；扣费明细要用精确记录。验算用多个已知的精确集合、不同的基数，比较相对误差的分布；重复项和重复合并都不应改变摘要。精度看误差分布，一次碰巧相等只是一个样本。

近似最近邻搜索（ANN）：搜索预算与召回

把对象表示成向量后，就能在空间里计算距离。ANN 为了少做比较，容许漏掉真正最近的点。HNSW（hierarchical navigable small world，分层可导航小世界）用多层邻近图缩小搜索范围；其结构直觉见 Malkov 与 Yashunin 论文摘要。

设查询向量 Q=(0,0)，四篇文档 A=(1,0)、B=(0,2)、C=(3,0)、D=(4,0)。欧氏距离为 1、2、3、4，精确 Top-2 是 A、B。搜索预算有限，候选过程只看到 A、C、D，精排后返回 A、C，recall@2=|{A,C}∩{A,B}|/2=1/2。把候选重排得再准确，也找不回从未召回的 B。

精确扫描 n 个 d 维向量，通常需要 O(nd) 的距离计算；ANN 的时间、内存和召回率取决于索引、维度、数据分布与搜索预算，没有对所有数据都成立的固定 O(log n) 保证。数据较少或过滤很强时，先做精确查询可能更直接。pgvector README 的 Indexing、Filtering讲解精确索引与近似索引，以及过滤后结果不足的问题。

误用反例

搜全部租户的向量，只在页面上过滤，既可能泄露信息，也可能把前 k 项都过滤光。另一种误用是拿语义相似度证明证据支持某个结论。授权范围要纳入检索与返回协议，召回要在相同的过滤范围内测，候选是否真的回答了业务问题，还要另行评估。

配套的 ANN 演算对输入有这些要求：查询与所有向量的维数相同且为正，坐标是有限数值，k 是 1 至向量总数之间的整数，候选 ID 都已存在且不重复。配套脚本没有处理极大坐标在相减、平方后超出浮点范围的情形，这时精确排序可能出错。候选集可以少于 k；此时 recall 的分母仍是精确 Top-K 的 k，不能靠缩小分母掩盖缺失。

04验算：误差的分母与方向

Bloom 的误报率，分母是实际不存在的查询数；HLL 比较估算与精确基数，报告误差分布；ANN 的 recall@k 与同一范围、同一距离规则下的精确 Top-K 比较。候选在业务上是否相关，还要另做一层标注。测量时还要固定输入、索引参数与版本，记录构建时间、增量更新延迟、内存和查询尾延迟。

05变式：从估算到计费，从候选到证据，从预筛到放款去重

三题的共同判断：近似结构可以留作趋势、预筛或候选召回，承诺精确结果的环节要回到可审计的精确身份与记录。

题一

X01 原本只估算活跃用户数，现在要按独立用户精确收费。答案： HLL 可以保留，用于趋势或异常比较；收费要回到可审计的精确身份与计量记录。反例是估算多 1%，就多收 1%。检查账单能否回查到每项应计费的身份与规则版本。

题二

H06 的常见问题（frequently asked questions，FAQ）候选检索迁移到 V18 的证据检索。答案： ANN 召回机制可以保留，但遗漏的代价、权限、保全、来源与版本要求都变了，通常还要用关键词或结构化检索补充，并加人工复核。检查已知必须找到的证据有没有被漏掉，检索候选与可提交的证据分开记录。

题三

V04 放在商品缓存前的 Bloom 过滤器，改用于 V12 的放款请求去重。答案： 同步条件满足时，阴性可以省去一次无效查询；阳性必须查权威的操作台账。放款去重依赖持久化的唯一业务身份。把 Bloom 当台账，会把一次误报变成漏放款。
