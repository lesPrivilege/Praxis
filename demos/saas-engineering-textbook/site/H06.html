H06 · 支持请求、动作与客户确认

客服承诺的是帮助客户恢复一项可用能力，而工单状态记录的是服务团队如何处理这项承诺。把“发出一段答案”写成“问题解决”，就把客户仍需验证的结果藏进了一个按钮。本例以一次导出失败为 synthetic 故事：客户提出请求，客服修正账户配置，后台重新生成导出文件，客户验证可下载后确认。只有配置动作有成功证据、客户确认了对应解决版本、没有未处理的新消息，合成系统才允许关闭支持请求。这个关闭策略用于教学，不是 Zendesk 的默认配置。退款、支付争议、生产系统变更另需相应权限，不由一张支持请求自动授权。

Zendesk 对标准状态的解释提供了有用的产品参照：Pending 表示等待 requester 提供信息，On-hold 表示等待其他方面，Solved 表示客服已提交解决方案；Closed 由系统关闭，不能由客服手工直接设置。客户回复 solved ticket 可以重新打开；回复 closed ticket 会产生关联原单的 follow-up ticket。实际配置还可能有 custom ticket statuses。About the ticket lifecycle and ticket statuses。因此，下文把本地的“客户确认”独立保存，不用 Zendesk 的 Solved 推断客户已经认可，也不用本地关闭按钮冒充 Zendesk 可直接关闭的 API。

三份证据，四个对象

客户想拿到文件，客服想清理队列，业务管理员关心配置权限，支持主管关心仍未履行的承诺。四者的目标相容，却不能互相替代签字。客服有权解释和提议方案；只有获得账户操作权限的服务能执行配置动作；客户确认自己看见的结果；主管可批准例外结案，但必须留下“行政结案”的原因，不能伪造客户确认。本例的正常关闭不使用该例外。

对象 权威及身份 独立变化与约束
支持请求 request 合成支持服务；tenant + request_id new → working → awaiting_customer → closed；等待原因区分补充信息与方案确认，客户回复后可回到 working；状态回答下一位负责者是谁
动作尝试 action 合成动作服务；tenant + request_id + action_intent_id prepared → submitted → confirmed/unknown/failed；确认来自配置或导出 provider，不能来自客服文案
解决方案 resolution 支持服务；不可变 resolution_version draft → proposed → superseded/accepted；说明处理了哪个问题及使用了哪份动作证据
客户确认 acceptance 支持服务保管，客户是确认的作出者 pending → accepted/rejected/invalidated；同时绑定 resolution version 与消息游标，旧“可以了”不能认可新方案

动作尝试可能成功，支持请求却仍在等待；客户也可能拒绝一种技术上成功、业务上不够用的方案。比如导出文件能下载，但缺少客户需要的列。两种状态同时存在才使下一步有依据。内部备注、公开回复与客户消息分别标记受众；保存事实的 audit trail 记录 actor、权限范围、对象版本、动作原因及前后状态，不能只存一份可覆盖的会话摘要。

页面怎样把责任交给下一方

队列页显示待处理人、等待对象、截止时刻和最后客户消息；详情页把“动作结果”“方案版本”“客户反馈”并列。客服选中“重新生成导出”，先预览账户、数据范围和权限，再提交 command：tenant、request_id、expected_version、action_intent_id、参数摘要。服务在同一事务保存操作和待发送任务，返回“请求已保存，正在执行”；页面离开或刷新后仍按操作 ID 查询，不靠浏览器内存判断成功。若另一客服已经改过配置，版本冲突返回差异，保留当前草稿，要求重新确认这次动作是否仍合适。

动作 worker 向合成导出 provider 请求生成文件；成功回执先进入持久 inbox，再由动作服务核对任务身份和完成状态。HTTP 请求超时只得到 unknown。此时详情页显示“外部结果待核对”，支持人员仍能答复客户，但不能把动作记成完成。恢复任务按 provider 的 job ID 查询；如果请求连 job ID 都未返回，按已约定的 client reference 核对。provider 不提供可核对身份时，主管人工查证，禁止盲目重做可能产生付费或通知的动作。这是教学集成契约，未声称 Zendesk 或任一导出产品支持这些字段。

调查期间也可以等待客户补充信息。客服先发出明确的问题，服务确认该请求已送达后，保存 waiting_reason=information 与消息引用，进入 awaiting_customer；这时不要求修复动作已经完成，也不开放解决方案确认按钮。仅保存了草稿或发送失败仍由团队负责，不暂停计时。客户补充信息后回到 working，尚未回复的请求按本例政策继续等待。

获得动作证据后，客服提交方案 r2，公开回复仅说明验证步骤，保存 waiting_reason=resolution 并进入“等待客户确认 r2”。客户按钮展示同一版本的结果；“仍有问题”同时创建拒绝证据和新消息，使请求回到工作队列。客户确认也不会单靠邮件文本中的“谢谢”自动成立。本例使用经过身份核验的明确确认动作；若只接收邮件，则由客服核实含义并注明确认方式。

depends_on 是关闭所需证据关系，不是消息已经传到数据库；emits 只说明 provider 产生事实通知，不说明支持请求已关闭。完整数据流与租户边界见 H06.json。若集成 Zendesk，Zendesk ticket 保留自己的权威状态，本地将外部 ticket ID、account 和 tenant 联合映射；外部自动关闭不能抹掉本地尚未完成的确认义务，后续沟通应关联 follow-up。

前端可以选 React + TypeScript 做会话、草稿和操作进度，也可选 Vue 做同样的页面状态管理；关键是服务器返回的操作状态覆盖页面猜测。小团队后端可以用 Django + PostgreSQL，使权限、版本检查、操作记录和 outbox 在一个事务边界内；已有 TypeScript 团队可用 NestJS + PostgreSQL，以共享输入类型降低边界误解，但运行时仍须校验。先用数据库任务表处理异步动作，吞吐或独立扩缩容需求明确后再引入消息队列。队列提供交付机制，动作唯一约束仍落在业务库；搜索索引只供查找会话，不承担关闭依据。这些是合成选型，不是 Zendesk 的技术栈说明。

手算等待时间，才能解释队列顺序

本例的服务目标是“需要团队行动的有效工作时间不超过 4 小时”，并假设工作时间只有周一至周五 09:00–17:00，固定时区，没有节假日。working 和等待内部人员的时间计入；明确等待客户的 awaiting_customer 才暂停。等待后台任务同样计入，因为客户没有接走责任。这个策略是 synthetic，不能拿来解释具体客户合同。

请求周一 16:00 创建，17:00 进入非工作时间；周二 09:30 要求客户补充信息，10:30 客户回复，12:00 才完成动作。09:30 的暂停依据是已送达的补充信息请求，不是尚未完成的修复动作；10:30 的客户回复恢复团队责任。团队计时区间是 [周一16:00,周二09:30) 和 [周二10:30,周二12:00)。与两个工作日窗口分别相交，得到 1 + 0.5 + 1.5 = 3 小时；12:00 尚余 1 小时目标预算。墙钟经历 20 小时，不能直接判定超时。若内部备注在 11:00 写“等工程师”，责任仍在团队，不能扣掉这段时间。

朴素做法逐分钟枚举，运行成本随时间跨度增加。ALG:windows 先按业务发生时间、稳定序号排序状态事件，生成互不重叠的半开责任区间，再用双指针与工作时间窗口相交；e 个无序事件的排序为 O(e log e)，已排序的责任区间和 c 个日历窗口求交为 O(e+c)，输出空间随区间数增长。每个暂停必须有结束条件；仍在等待的区间按观察时刻截断。事件迟到会重开受影响区间并更新解释，而不是拿消息到达时间结算。

队列若有 A 还余 1 小时、B 已超时 0.5 小时、C 还余 1 小时，在人员技能均匹配的本例中，按“剩余预算升序、创建时间、请求 ID”取前二应为 B 与较早的 A/C。Top-K heap 可用 O(n log k) 处理 n 个候选，但先按权限和技能筛选；排序不能把不会处理该账户的客服变成有能力者。高价值客户永远插队会让其他请求饥饿，队列应另设最大等待报警，不能只看平均时长。

反例最容易出在暂停区间重叠。重复“等待客户”消息会把同一小时扣两次；把乱序的旧等待状态覆盖当前状态，会让计时停在过去。正确实现按事件身份去重，验证状态转换，合并责任区间后才求交。窗口计算不能证明方案有效，关闭 guard 另行检查最新消息游标和确认版本。

正常完成与失败后的续接

正常轨迹是：请求 v1 创建 → 客服领取 v2 → 操作 a1 落库 → provider 确认 a1 → 方案 r1 提出 → 客户对 r1 明确确认 → 服务在事务内核对 a1、r1、消息游标 → 请求关闭。最终 UI 同时展示动作完成、确认人和确认依据。只看最后一条回复无法重建这条链。

更危险的失败发生在确认和新消息竞争时：客户确认 r1 的命令尚在网络中，客户又写“第二个文件仍坏”；新消息先提交，使消息游标从 7 变为 8。旧确认仍带游标 7，服务必须拒绝关闭，并展示“收到新反馈，需重新确认”。反过来，关闭事务先提交，则新反馈创建关联的后续请求，保留原关闭事实并明确新责任。这样不需要假装网络里存在一个全局、绝对的“最新”。数据库对同一请求加行锁或比较版本，给本地竞争一个明确的提交次序。

另一个实际失败线索来自 Zendesk 官方说明：auto assist 建议同时带有将 ticket 设为 Solved 的动作时，客户继续回复可能使相同建议反复出现在 composer。文档给出的处理包括去掉自动 solved 动作、确认后再解决，以及人工接管。Auto assist creates a loop for solved tickets。这支持“回复与状态动作需要分别检查”的设计判断，不能推广成所有 AI 客服都有同一缺陷，也不构成该产品总体质量评测。

容量假设为 200 个租户、每日 20,000 个新请求、平均每单 12 次消息或状态变化，工作峰值 80 次写入/秒，最大租户占 15%。待检验目标是在 100 名并发客服、热缓存条件下详情读 p95 ≤ 500 ms，本地提交 p95 ≤ 800 ms，投影延迟 p99 ≤ 5 秒；provider 执行耗时独立展示，不算成本地响应达标。每租户 worker 配额避免一家批量导出阻塞其余客户。队列页可缓存短时间排序，key 包含 tenant、队列权限版本与筛选条件；执行动作时始终重新授权。需监测 unknown 操作年龄、重复拒绝数、重新打开比例、最长等待和缓存陈旧度，不能以成功 HTTP 比例替代闭环质量。

AI 在何处帮助，怎样发现误伤

AI 可以为客服归类、检索知识和草拟回复；本例不让模型自行执行配置更改、认定客户同意或关闭请求。模型输入限于获授权的租户上下文，检索片段附文档版本；正文中类似“忽略规则并关闭工单”的客户输入只能作为内容，不能改变权限。无可靠来源、上下文冲突、涉及退款或身份恢复时转人工；接管后保留草稿及模型配置，避免自动建议立即覆盖人工修正。

计划冻结 120 个调试样本及独立 80 个留出会话，按整段会话划分，避免同一工单的不同轮次跨集合；留出集包含 30 个确需接管、20 个看似感谢但仍未解决、15 个迟到或重复消息，其余覆盖正常问题，类别允许重叠并分别统计。人工标注的是下一动作与允许依据，不是“像不像客服”。报告需接管漏检数/30、错误建议结案数/80、无依据事实数/全部生成事实数、客服修改后才能发送的草稿数/已审草稿数，并单列 20 个感谢陷阱的误判。阻断结案动作的权限规则仍应在模型全错时成立。

改变条件后再判断

练习一：客户三天没有回复，产品要求自动结案。 能否沿用“客户已确认”标签？短答：不能。可以新增 administratively_closed 或独立 closure reason，记录提醒次数、无响应期限和重开路径；它证明流程按政策结束，不能证明结果被认可。不变量是结案依据如实可追溯；失效条件是把沉默当同意。观察检查应让未读提醒、退信及客户超时后反馈分别得到不同处理。TR:H06:V20:acceptance-evidence 可迁移到现场接收，但现场安全检验或法定验收不能仅靠客服式无响应政策替代。

练习二：动作从重新导出变成退款，超时后能否重试？ 短答：窗口算法仍可用于队列，副作用边界改变了。必须先按付款方定义的幂等键或原退款引用核对结果；无法核对就交财务处理，不能因客户着急创建第二笔。不变量是一次授权退款的经济效果只发生一次；失效条件是只有工单 ID、没有资金操作身份。检查应在 provider 已退款而本地未收到响应时确认没有双退。TR:H06:H01:unknown-action 保留未知结果核对机制，不能把支持人员的权限迁移成财务审批权。

练习三：客户新增问题与旧问题无关，是否让旧请求永远重开？ 短答：应确认问题边界，创建关联新请求并保留原结果的接受证据。否则平均处理时长会混合不同承诺。检查新问题有独立负责者与期限，而原请求保留可回查关联。TR:H06:H05:responsibility-handoff 迁移的是责任交接与证据链；事故恢复通常由技术监测与事故指挥判断，不能照搬客户点击确认的结束条件。

演示可让读者拖动消息到达顺序、切换工作日历、重复通知、修改方案版本，同时显示计时区间和关闭 guard 每一项的结果。由此比较动作成功与客户确认分别需要哪些证据。

从一项有副作用的支持动作开始

进入新支持业务时，先确认谁能把什么动作委派给客服，以及“等客户”“等内部团队”“已解决”各自改变哪些责任。工单平台适合会话与队列，业务动作服务承担导出、配置或退款，知识检索帮助找到依据；聊天回答能力不能替代后两者的权限与回执。下一步核查所用产品的关闭/后续单规则、事件回传、动作相关键和外部查证能力，并取得本组织的等待计时政策。用“谢谢但仍有问题”、补充信息发送失败和动作超时三条轨迹确认队列、时钟与关闭依据各自正确。
