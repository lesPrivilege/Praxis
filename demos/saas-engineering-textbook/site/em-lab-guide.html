可执行例子与适配器契约

实验把正文里最容易被一个“成功”标签掩盖的条件做成可观察行为：旧批准是否还能用，合格数量是否被重复占用，发送后断线是否会造成第二次效果，以及效果已确认后能否越过接收人关闭工作。两例都能复现：EM-E01 的采购付款与 EM-E02 的服务变更，各由 fake 与 HTTP 两种适配器跑同一组契约检查。提供方是本机服务；fake 和本机 HTTP 都通过，仍不能证明真正的 provider 接受同一约定。

01运行与阅读

全部检查由一个测试文件运行；下表把代码入口对到正文里的机制。

从 Praxis 仓库根目录运行：

python3 vault/distilled/saas-engineering-atlas/enterprise-mechanisms/test_mechanism_lab.py

只使用 Python 标准库；临时 SQLite 数据库由测试创建并清理，本机 HTTP 服务绑定 127.0.0.1 的临时端口。代码不需要依赖安装、账号或外部地址。

文件与入口 阅读目的
mechanism_lab.py 的 PurchaseLedger 发票修订保留历史；批准版本检查；数量检查与分配在同一 SQLite 事务中
同文件的 Change 确定方案与批准范围的绑定；执行窗口
同文件的 OperationJournal 意图与发送状态持久化；业务意图唯一；结果未知后核对；接收权限
同文件的 FakeAdapter / HttpAdapter 同一应用端口的内存实现和实际 HTTP 编解码实现
test_mechanism_lab.py 的 ReferenceProvider 独立实现本地参考协议，能够在生效后主动断开响应
同文件的 AdapterContract 同一组契约检查分别执行在 fake 与 HTTP 适配器上
fixtures.json 切换前 20 项工作、来源状态与算术预期值

02两条完整实验轨迹

两条轨迹各从批准走到结算或关闭，响应丢失后都按原键核对，外部效果始终只有一次。

test_e01_end_to_end_both_adapters 从批准采购开始。10 台发票因只有 9 台合格而拒绝；收到供应商修订后保留版本 1，使用版本 2 的 9 台形成 720,000 分分配。再来 1 台的发票因余额不足被拒绝。资金角色创建 PAY-17，provider 记录效果后丢失响应，本地得到 unknown；按原键查询得到 settled，外部效果计数保持 1。fake 和 HTTP 两种接入分别走完整条链。

test_e02_end_to_end_both_adapters 从确定的 CHG-42/r3 批准开始。OP-42 发出后外部配置到达版本 9，响应丢失。未核对时禁止接收；查询后进入 awaiting_acceptance；8/10 探测拒绝接收，10/10 与服务负责人身份允许关闭。关闭后再次查询不会退回未接收，外部效果仍为 1。

03端口与线协议

应用端口只暴露 submit(intent) 与 lookup(tenant, operation_id)。提交意图包括租户、操作 ID、业务意图键、动作类型和目标；变更额外带期望版本、目标值、批准引用和窗口，付款额外带金额与币种。业务意图键阻止调用方仅换一个操作 ID 就重复执行同一笔义务。

HTTP 线协议使用 POST /operations 与 GET /operations?tenant=...&operation_id=...。结果必须提供 tenant、operation_id、target、state、receipt。applied 的变更结果还要有正确的 version、desired；前提版本来自持久化请求，检查 version = expected_version + 1，不声称 provider 回传了前提版本。付款结果要有正确的 amount_minor、currency。本参考协议把付款的 applied 定义为已有结算事实；实际支付接口可能区分更多阶段，不能照搬映射。

同键不同内容 明确拒绝 fake / HTTP 共用测试

对象模型与传输契约分别检查。test_two_connections_compete_for_last_unit 用两个线程各开一个 SQLite 连接，同时争用最后 1 台验收量；结果必须一项分配、另一项拒绝，累计为 9。重启检查先关闭再打开同一个日志数据库，恢复 unknown；另一个检查直接构造“外部已生效、本地仍为 sending”的崩溃窗口，证明核对不需要新建意图。

04反例怎样变成练习

每个反例只改一项输入，预期结果是拒绝、批准失效或保持原状态，不会变成成功。

可以先阅读测试名称，再预测结果。把期望配置版本从 8 改成 7，应得到 rejected；只把业务意图的操作 ID 改成 OP-43，应被本地唯一约束拒绝；把批准后的目标值从 6 改成 8，应使批准失效。将切换记录里的 sent_unknown 改为未定义的 done，应被映射拒绝；删除原操作引用也应失败。

真实适配器的接入验证沿用同样的步骤，但增加确切 provider 的验证环境、身份与最小权限、API 版本、外部查询一致性、错误码、重复请求保留期限及结果关联规则。需要同时核对请求响应与实际效果。只有传输成功，不能证明业务已完成；只有 fake 通过，也不能证明真正 provider 接受同一约定。

发送失败与核对也可能并发。配套回归检查先保存已确认效果，再让原发送者收到延迟的传输、契约或拒绝异常；工作日志只允许仍处于 sending 的记录转为 unknown，已确认事实保持不变。

05实现范围

本实验的 HTTP 适配器是实际传输代码，提供方是本机服务。它没有连接银行、Palantir、Camunda 或任何生产账户；Pact 被用作契约思想的来源，未安装其框架。角色字符串是来自测试夹具的已验证身份假设，没有实现身份认证、真实权限撤回或跨租户数据访问控制。

SQLite 检查覆盖局部事务与持久化意图，没有模拟分布式数据库、外部 provider 持久化、服务崩溃的所有时序、支付退款、审批撤回广播、浏览器或负载。分钟值 1200–1230 表示本例 UTC 日内执行窗口；真实运行需要完整日期、时区与可信时钟。对象模型保留本次演算需要的证据，未实现完整单据管理系统。上述边界不影响已经执行的局部结论；初始实验结果见 作者验证记录，追加验收、回执与修订身份回归见 复核修复记录。

同一 CHG-42 的后续修订使用自己的批准、业务键和操作身份：r3 保留原 OP-42，重新批准的 r4 使用 OP-42-r4；同一修订的重试不得改内容或换键。验收读取已保存的 SVC-ACCEPT-1 政策，固定要求10/10。终态观察矛盾另记入 observation_conflicts，界面状态返回 evidence_conflict；原效果保留，冲突未处理时不能接收。
