计算与系统方法·第十一章

先用成熟技术，再按问题研究

选择技术栈时，先列出要守住的业务不变量和要实现的工作。表单、授权、事务、查询、文件、队列和观测各交给哪一部分处理，决定了需要哪些能力；分工定下来以后，比较框架才有意义。

01识题：产品形态与部署边界

一个几十人使用的审批工作台，可能用服务器渲染页面、一个业务应用和一个关系数据库就够了。一个需要复杂拖拽、离线编辑或大量交互状态的产品，可能更适合独立前端与 API。每多一条部署边界，接口、鉴权、观测和可能出故障的地方都会随之增加，所以新的边界要对应一个已经识别的问题。

02解法：需求特点与成熟选项

需求特点 成熟选项与搭配 取舍与核查点
以表单、台账、管理操作为主 Django 的模型、模板与管理能力；或既有企业框架 集成程度高；领域动作与权限要专门编写，通用 admin 不能直接充当面向客户的工作流
交互丰富的多人编辑工作台 React 或 Vue 等前端能力，配契约清楚的 API 局部状态、服务器状态、冲突与离线同步分开处理；团队能否维护这套生态，比语法偏好更重要
Python 数据处理与 API FastAPI 配数据库访问、迁移与 worker schema 与接口文档生成方便；事务、后台任务与权限要自己组合并写清楚
已有 .NET 业务与团队 ASP.NET Core 与既有数据访问、认证和后台机制 沿用现有团队与运维体系；部署与升级边界另行核对
以 TypeScript 为主的团队 前后端采用团队熟悉的 TypeScript 框架与运行时 前后端共享类型，可减少接口定义不一致；运行时输入验证和持久化约束照样需要

这些是选型方向，不是固定套餐或性能排名。具体能力可回查 Django overview的模型、模板与管理界面，FastAPI features的 OpenAPI 接口描述与 JSON Schema 数据约束（JSON 即 JavaScript Object Notation），以及 ASP.NET 官方说明的请求、模板与认证。前端状态怎样组织，可参照 React 文档；想渐进地接入前端框架，可读 Vue Guide。实际选择时再固定版本、许可、依赖与升级策略。

存储先按数据责任拆分：关系数据库负责身份、约束、事务和常规查询；对象存储保存文件内容，文件的身份、权限与版本仍记在数据库里；搜索索引保存供检索用的投影；缓存存放可以重建的结果；队列存放待处理的工作。一个系统可能只需要前两项。搜索和向量检索可以先用数据库已支持的功能，测出瓶颈后再拆成独立服务。

实现算法时，同样先查现成能力：Map/set、标准排序与 heap；数据库 WHERE/ORDER BY/GROUP BY 和索引；库中的图遍历；求解器中的约束与优化；缓存的淘汰策略；数据库或检索库里的 Bloom、HLL、ANN。自己写算法适合教学、研究，或现有库表达不了的规则；放进生产环境，就要自己负担边界、并发、持久化与维护的成本。

03演算：单应用方案与多服务方案

设一个维修产品有 50 名内部操作员，每天 2,000 个操作，要求取消不重复、退款可核对，列表允许等几秒再刷新。方案 A：一个应用处理页面/API与领域事务，一个关系数据库保存权威对象和 outbox，一个 worker 派发并对账；不先增加分布式缓存。方案 B：独立前端、多个服务、专用消息 broker、搜索索引和共享缓存。

两种方案都可能实现相同功能，差别在边界：A 的取消、OP7 与 outbox 可以在一次本地事务里完成；B 若把它们分到不同服务，就要另外设计交接协议。团队没有独立扩容或组织边界的要求时，A 更容易完整验证；以后某类数据处理确实需要独立扩容，再从稳定的任务或 API 边界拆出去。这是本例约束下的判断。

04验算：完整链路与对照实验

验收先打通一条完整链路：

  1. 1页面提交
  2. 2权限与版本
  3. 3事务
  4. 4worker
  5. 5测试 provider
  6. 6投影
  7. 7对账

用两个租户、重复请求、未知结果和并发修改来验算。只能走通 happy path 的框架原型，还比较不出可靠性成本。

链路打通以后，进一步的研究由运行中观察到的具体问题触发。

已观察到的问题 下一步研究 最小对照实验
查询随租户数据增长变慢 索引、查询计划、分页、分区 同分布数据比较页读取与尾延迟，不只看平均值
重复计算占 CPU memoization、批处理、缓存 固定请求回放，计入失效和回源成本
大图遍历超预算 预计算、增量传播、图存储 比较影响集合完整性、更新延迟与查询成本
复杂排程经常不可行 约束建模、CP-SAT / 混合整数规划（mixed-integer programming，MIP）、启发式 小例穷举、大例与人工基线对照，报告可行率与界
事件迟到导致报表反复变动 流处理、水位、重算发布策略 注入迟到分布，测最终准确性与修订时间
检索快却漏重要文档 混合检索、过滤策略、ANN 搜索预算、候选重排（reranking） 固定授权范围与留出集，比较召回、质量和成本
多步骤流程常停在结果未知状态 持久化工作流、状态机、outbox、对账 按每个崩溃边界恢复，测未决义务年龄
AI 工具调用超出用户意图 受限动作契约、审批、评估与轨迹 检查拒绝条件、注入不可信内容、重复工具调用

研究方向要写成能被实验否定的问题。例如“把搜索预算从小调大，授权范围内 recall@10 是否提高，p99 还能否达标”，比“接入最先进向量库”更可验证。写清输入分布、期望的改进和可接受的代价，实验结果才能用来决定要不要增加组件。

05变式：从内部应用到多租户产品

变式题。 将内部维修台转为 X01 的外部多租户 SaaS，原有技术栈是否必须全换？

简答

不必先换框架。要新增并验证的是租户身份传播、数据隔离、配额、计量、配置、支持和退出流程。共享表、分 schema、独立数据库这几种隔离方式，按风险、成本与运维约束来比较。原有算法仍可复用，但每个查询、缓存、任务和错误响应都要带上相应的租户边界。验算时检查同号对象、跨租户事件和退出后仍在途的任务。
