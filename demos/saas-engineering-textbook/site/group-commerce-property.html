P05 · 消费履约、住宿与空间

顾客买了三件商品、点了一桌菜、订了两晚房，企业就有了一项带数量、期限和条件的承诺。工程承包商接受变更、物业交出房屋钥匙，同样涉及承诺。软件帮不同角色确认：还欠什么，资源是否可用，哪部分已经交付，钱应当怎样处理。这几件事彼此相关，却很少同时了结。

本包的金额、经营政策、系统架构、性能目标与故障轨迹都是标明的合成教学设计；公开产品文档只支撑紧邻引用处的产品事实。下文的共同模型是本包的原创分析，各 provider 内部未必采用同一模型。

共同模型：承诺、资源、履约与资金

一笔业务至少要分别保存四类记录。承诺记录写清买的是什么、价格和条件属于哪个版本；资源记录描述商品件数、厨房产能、房夜或可用空间；履约记录保存出库、出餐、入住、验收或交还的证据；资金记录解释应收、已收、待退款和有争议的金额。“完成”指这些记录都达到本业务规定的相容状态，总状态栏里的一个 done 说明不了。

以三件预付商品为例：付款已确认，仓库只发出两件，第三件取消。承诺数量可核对为 3 = 2 已发 + 1 已取消 + 0 待处理；取消的一件又带来一项待退款义务。退款请求即使已被受理，结果仍要由资金方确认。退回一件已发商品时，累计已发数量仍是二，退货另记为一条反向流；把累计已发直接减为一，就分不清“从未交付”和“交付后退回”。V04 把这个模型展开成可逐行核对的行项目。

资源的性质不同，不变量也不同。一晚空房无法在次日补交给昨晚的住客；厨房已经做出的食物无法通过数据库回滚变回原料；已施工的墙体需要新的施工才能撤除。V05、V06、V15 因而各有自己的补救动作。V16 更进一步：房屋已经归还，押金仍可能处于责任争议中。物理工作结束、合同义务关闭和资金结清要分别证明。

权威、命令与撤销

actor 指执行动作并为它负责的角色，object 是有身份和历史的业务对象。仓库人员可以确认拣货，客服可以提出退款；两个按钮出现在同一页，这两项权限也不会因此合并。租户标识 tenant_id 指软件客户的隔离边界，租约里的承租人则是业务主体；一个物业软件租户可以管理许多承租人，两者不能共用一个字段。

每个对象要指定 system of record，即哪一方对哪项事实负责。本地订单服务决定退款申请是否符合合成政策，支付方对款项执行结果负责，仓库对收回货物的检验记录负责。同一个外部编号还要附 provider account 与 tenant scope，才不会把两个商户的编号 1001 当成同一对象。列表、图表和搜索索引只是 read model，即为阅读构造的投影；它们应带版本或核对时间，副作用也不能凭它们批准。

界面发出的 command 只是请求。以“退回 1 件并申请退款”为例，它先成为一条带行项目、金额、授权人和操作身份的请求；服务端检查版本、权限和余额，在本地事务里保存状态和待执行工作。外部调用一旦离开本地事务，就可能出现“对方成功，但回执丢失”。这时记为 unknown，意思是本系统还不知道结果，应凭同一操作身份查询、对账或人工确认。换一个新操作 ID 重发，一次重试就成了第二笔业务。

撤销怎样做，取决于对象。未提交的表单可以丢弃；已入库的错误记录需要更正记录；已经发生的款项或物理交付需要补偿。把这些动作做成一个没有说明的“撤销”，操作者会误以为所有后果都已消失。恢复责任人、应保留的证据和用户能看到的等待状态，见各例的故障轨迹。

技术选型与事务边界

第一版实现用一个按领域分模块的后端加关系数据库，更容易把本地约束放进同一个事务。订单、付款尝试和待发送工作可以存在同一个库里，后台 worker 再执行外部请求。拆成微服务会多出交接与恢复责任；写入规模、团队边界或独立可用性的要求值得这些代价时，再拆。

前端可以用 React/TypeScript 或 Vue/TypeScript 处理多对象状态、表单校验与冲突提示；后端可以用 Node.js 配合共享类型，也可以用 Django 或 ASP.NET Core 复用已有的领域代码和事务能力。共享类型减少字段误用，却不能让浏览器成为权限权威。为什么需要日历、厨房屏、版本差异或责任明细，这些界面又依赖哪些后端事实，见各例。

关系数据库守住会改变业务结果的约束；缓存适合加速候选列表和读模型，不能凭过期可售数确认最后一间房。消息队列承接要等待的工作；消息重放以后，哪次已经生效、哪次是重复，靠业务操作身份和持久化记录判断。对象存储保存图纸或验收附件；文件在那里只证明有文件，批准另需证据。

解题五步

每例按“识题 → 解法 → 演算 → 验算 → 变式”展开，五步的含义见把业务问题算清楚。本包的识题先找重复结构：一单多去处、多次付款争同一余额、每个时间点可行而全程不可行、同一来源多路径到达、成本与责任不一致。解法为这些结构选择数量分区、尝试占额、区间与排程、集合去重或责任分桶；随后用小数字算一遍，再以守恒、权限和确认依据验算。变式只改一个条件，看方法何时仍然适用，何时要增加对象或换方法。

要记住的是决定方法的线索，API 字段不必逐个背下。各例开头的识题表把线索连到解法和下一步研究方向；正文给出因果解释和完整例子，练习检查能否迁移。进入陌生行业时，先认出对象、承诺、约束与权威，再选有适用前提的解法；各例文末的探索方向列出下一步查什么、怎样验证。

手算与检查

各例的计算：V04 按行分配折扣与退款，V05 分摊共享菜品与组合支付，V06 计算区间占用和连续住宿，V15 沿变更来源去重并核对累计证书，V16 把有依据的扣款与未解决争议分开。计算代价和业务正确性分开解释；算法得出结果以后，多人同时使用这个结果还要靠事务保护。

先手算正文的小输入，再改变一个条件：多一个操作者、少一份确认、晚到一条账单、同编号属于另一商户。每例至少有两道带简答的条件变化练习，检验不变量是否仍然成立。

跨案例迁移

H01 的承诺、付款与服务权利到了 V04，要再加上数量和反向流。V04 的“子项完成不代表整单完成”可以用在 V20 的多次上门工单上。V06 的区间占用可以搬到 V16 的空间使用，租约中的法律权利却不能由酒店夜数定义。V15 把技术答复与商业批准分开，能帮 V07 理解图纸变更，但替代不了生产放行。X01 的隔离要求贯穿所有 case；物业里的租客身份要单独记录，tenant_id 替换不了。
