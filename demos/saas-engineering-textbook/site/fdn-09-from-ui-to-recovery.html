计算与系统方法·第九章

从一次点击到可恢复的业务结果

算法在固定的输入上回答问题；应用面对的输入却一直在变。两个人可能同时编辑，网络可能在成功之后断开，消息可能重复，投影可能滞后。工程的工作是保存足够的身份和证据，让下一次处理知道上一次做到了哪里。

  2. 02 / 06命令与本地事务
  3. 03 / 06退款的可恢复阶段
  4. 04 / 06幂等、顺序与补偿
  5. 05 / 06等待与冲突的呈现
  6. 06 / 06从退款到放款，从报名到资源预订

01识题：结果变得不确定的边界

延续第一章的维修订单 O7。操作员取消最后一次尚未执行的服务 S3，并请求退还 40 单位。UI、业务服务的应用编程接口（application programming interface，API）、本地数据库、外部退款服务（provider）、消息接收器与列表投影，各自在不同的时刻观察状态。一次超文本传输协议（Hypertext Transfer Protocol，HTTP）请求结束，只能证明该响应所承诺的那个阶段已经完成。服务若返回“已受理”，页面应显示待处理；请求超时时，结果可能未知，页面不能把它显示成确定的失败。

每个对象由谁负责、哪些内容必须保存、哪些可以重建，决定了数据放在哪里：

对象 权威与职责 持久保存的内容 可重建的投影
服务子项 S3 业务服务：是否允许取消 状态、版本、取消原因、依据 订单进度与未完成数
操作 OP7 本地应用：一次逻辑请求的跟踪 租户、对象、请求摘要、操作 key、状态 操作进度条与历史列表
退款 R1 外部 provider：外部结果的确认 provider scope、外部 ID、本地映射、回执 退款状态与最后核对时间
outbox / inbox 本地应用：交接身份的持久化 事件 ID、对象版本、尝试、处理结果 队列深度与待核对列表

数据库是保存位置，业务服务对 S3 的规则负责，provider 对外部退款事实负责。搜索索引与缓存都可以重建；已发生的取消决定和外部操作映射，不能因清缓存而消失。

02解法：命令与本地事务

UI 发出的 command 携带对象身份、读到的版本、参数及稳定的操作 key。服务从可信会话取得用户和租户范围，再检查权限、输入、当前版本和 guard。校验不能只靠前端；即使按钮已被禁用，旧页面或另一个客户端仍可能提交。

服务在一个本地事务里原子地保存 S3 的取消、OP7、退款意图和 outbox 记录。重复的请求若 key 和参数都相同，返回原操作；key 相同而参数不同，按冲突明确拒绝。唯一约束保护完整的业务身份；版本比较挡住用户依据旧内容做出的决定。唯一性、授权和状态转换是不同的检查，各有各的失败结果。

用一个库存例子看并发：库存为 1，甲乙都先读到 1，然后各自写回 0、各承诺一件，合计承诺了 2 件。正确的做法之一，是在事务内执行带条件的扣减：只有库存仍至少为 1 时才减 1，并以实际更新的行数判断是否成功；另一种做法是适当加锁，或使用可串行化事务。跨多行的不变量要覆盖完整的集合，一个行锁保护不了所有关联约束。PostgreSQL Transaction Isolation §13.2说明各隔离级别的差异，以及冲突后整笔事务的重试。

03演算：退款的可恢复阶段

  1. 操作员提交 OP7(cancel S3, expected_version=2, amount=40)。事务提交后，S3 为 cancelled/v3，OP7 为 awaiting_external，outbox 里有退款意图。
  2. worker 领取意图，用同一个外部操作身份发出退款请求。provider 已经接受，但响应在网络中丢失。OP7 进入 unknown，UI 显示退款结果待核对。
  3. 恢复任务按 provider 的查询与幂等语义核对原来的那次尝试。查到 R1 成功后，保存外部 ID 和确认依据，OP7 变为 confirmed。
  4. 投影消费对应的版本，显示取消 1 次、退款已确认 40。重复的通知只会得到同一个效果；后到的旧 pending 记录不能覆盖已核对的新状态。

在第一步事务提交之前崩溃，没有本地决定；提交之后、派发之前崩溃，outbox 保留着待办；派发之后、收到响应之前崩溃，外部结果未知；确认之后、更新页面之前崩溃，权威事实已经存在，投影可以重建。恢复的依据取决于停在哪个边界，不能一律“重新执行全部”。

Stripe Idempotent requests是一个具体的协议参照：其 API v1 在执行开始后保存同一 key 的首次响应，重试时返回该响应，并比较参数；key 的保留与清理有时间条件，v2 的行为也有区别。工程实现要读所用 API 的实际语义，不能把一个 provider 的期限与错误处理推广到所有外部系统。

04幂等、顺序与补偿

event ID 去重处理同一通知的重投，业务唯一键保证同一义务不会因不同的通知而重复生效。一次购买可能产生多种事件，只按 event ID 去重，仍可能重复开通；这次购买带来的开通本身也要有唯一身份。去重记录保留多久，要覆盖允许的重放与恢复窗口；超过保留期的旧消息，应另有核对办法。

处理乱序消息时，不能按字符串大小比较状态。可以使用对象版本、已核对的快照或明确的转换规则；遇到缺失的前提事件，先等待，或查询权威对象。有些业务允许重开工单，closed 不一定是最后的状态；合法的重开是一次新的、有依据的状态转换。

本地事务无法回滚已完成的外部动作。退款成功后才发现取消有误，就需要恢复服务、重新收款或人工处理，每种都要有新的业务授权和记录。补偿是一个有条件、也可能失败的新动作，不是删除历史。跨步骤的工作可以考虑 saga 或持久化工作流，但要先列出每一步由谁确认、怎样补偿、谁来接管，再决定是否需要引擎。

05验算：等待与冲突的呈现

UI 至少要能区分输入错误、无权操作、版本冲突、处理中、结果未知与确认完成。冲突时，应保留用户的编辑，并展示新的权威版本；结果未知时，提供按原 OP7 查询进度的路径。乐观更新适合可撤销、冲突代价明确的局部交互；涉及资金或关键资源的承诺，要等相应的权威确认后，再显示为完成。怎样组织前端状态，可以参考 React Choosing the State Structure中关于避免矛盾和重复状态的原则，这些原则不限于 React。

API 契约要把成功和失败都写清楚：字段、单位、金额精度、时区、缺省值、分页、版本、错误码、幂等 key、速率限制与超时语义。服务端不能向客户端返回它无权查看的冲突详情。后台操作要保存可追踪的 operation ID；观测记录把 UI 请求、事务、队列任务和外部 ID 串起来，便于对账。

误用反例

catch timeout 后生成新 key 重试退款；为了避免重复，把所有失败永久吞掉；为了让列表“实时”，让缓存值直接批准资源占用。验算分别观察业务效果数、未决操作的年龄、资源余额与最终的对账差额。没有重复效果，也可能漏了工作；没有报错，也可能一直停在 pending。

配套的 SQLite 演算按实际的表行生成轨迹。提交前回滚，库里应只留下旧对象，operation 与 outbox 都为空；提交后，先读出指定租户和 operation 的持久待办，再由这条待办派发；核对成功后，读回 confirmed 状态和外部身份。删掉 outbox 写入、提交后丢掉待办，或者删掉确认写入，检查都应失败。

06变式：从退款到放款，从报名到资源预订

题一。 V04 的退款恢复移到 V12 的放款。答案： 原操作身份与未知结果的核对可以保留；放款的资格、批准有效性、资金义务和补偿可行性要重新定义。不能把“退回原订单状态”当作款项未发出。检查超时后先查原放款记录，账务与外部结果一致后才能结束。

题二

V17 的课程报名移到 V06 的房间预订。答案： 限额竞争的机制相似，但房间容量按时间区间变化，只保护一个全局库存数不够。先把住宿区间转成占用约束，再设计事务，或者采用成熟的预订能力。检查重叠区间的并发预订以及取消后的释放，非重叠区间应能同时成功。
