消费履约、住宿与空间·V05

点餐、厨房交接、分账与结账

餐厅向一桌客人承诺按约定做出食物，并把每份消费和每次付款解释清楚。厨房接单后就可能开始消耗食材，收银却可能到最后才确认谁付多少，两边的节奏不同。所以订单、制作、账单和支付各有状态；一次“取消”无法让已做的菜、客人应付的钱和银行卡交易同时回到起点。

本例是一个堂食系统，以 Toast 的公开对象定义作参照。两位客人点了 3,200 分和 2,800 分的主菜，共享 1,900 分配菜；原价 7,900 分，整单优惠 501 分，净应付 7,399 分。本例不含税、服务费、小费、外币、离线银行卡授权和跨营业日重开；加回这些真实条件时，价格和关闭规则都要重新定义。本例允许先出餐后收款；账单关闭的条件是：已确认的付款覆盖应付额，每次支付尝试都有解释，每项制作取消或报损都有责任人。

01识题：制作、责任与收款

餐饮问题先看变化落在哪一层。口味变化影响制作内容，分账影响消费责任，组合付款影响收款工具；选错层，就会多做一盘菜或多收一次钱。

识题线索 首选解法与适用条件 验算与后续查证
同一道菜，有人要不同口味 每个 selection 固定一组配置，modifier 树表达组成；配置不同的份数拆成不同 selection 总份数与每份配置都完整；查菜单必选项、数量和版本约束
一盘菜多人付，一张账多次付 多人分付时按消费责任拆 check，一张账分次付时逐次记录 tender attempt；未决尝试保留占额 拆账总额不变、制作仍为一份、可收余额不为负；查折扣继承与终端交易查询
撤菜时厨房已开火 撤菜请求与厨房确认分开记录，已耗资源用报损或新处置解释 迟到的旧回执不能让已取消的任务重新开始；查厨房显示系统（kitchen display system，KDS）的去重与确认，以及纸质打印的人工交接

02解法：菜单模板与 selection

菜单管理员维护菜品及 modifier（口味、配料或规格选项）。菜单项只是模板，selection 记录这一次要做的菜：客人点一份“不加酱”的主菜，服务员就创建一个 selection；同一道菜另一份正常口味，要另建一个 selection。selection 保存菜单版本、选项树、数量、接受时的价格与备注，菜名后来改了，厨房的旧单也不会变成另一道菜。自由文本备注能提醒工作人员，却不能自动证明某项食物安全要求已经满足；系统无法可靠表达的要求，由工作人员确认。

Toast 文档把 modifiers 放在 Selection 中，并规定 modifier 数量应与所属 selection 的数量相等；同一道菜的不同份数需要不同 modifier 时，应拆成不同的 selection。按这条约束，“2 份主菜、其中 1 份不加酱”不能写成一行含糊的数量 2。参见 Specifying modifiers and instructions，Requirements for modifier quantities（P05-SRC-toast-modifiers-C1）。本例的选项验证和价格快照由自己的服务实现。

服务员可以新建 selection、发送尚未制作的项目、提出撤菜；厨房确认收到、开始制作、完成或无法停止；收银员在限定余额内收款；经理授权送厨后的撤销、折扣与报损。任何角色都不能按一下按钮就把银行卡扣款记为成功。餐厅是数据边界，桌号只在门店与营业场景内有意义；“12 号桌”不能充当全球订单 ID。共享设备上切换员工时，当前操作要重新绑定员工身份和权限。

对象 权威与稳定身份 本例的状态流转
selection 点餐服务；selection ID、菜单版本、modifier 快照 draft → committed；发送前可以修订，发送后的变更用 amendment 记录，原内容保留
kitchen ticket 厨房接收记录；ticket ID、selection revision queued → accepted → preparing → ready → served；撤销请求另走 cancel_requested → cancelled/too_late
check 账单服务；check ID、定价版本 open → settling → paid → closed；拆账只改应付归属，不重发制作任务
tender attempt 本地资金操作；attempt ID、支付账户、终端交易身份 prepared → submitted → succeeded/declined/unknown；unknown 表示结果尚未查明，不等于失败
shift close 门店对账服务；营业日、班次、明细版本 open → balanced 或 exception；账单关闭了，收银抽屉与结算未必相符

Toast 的状态名要按它自己的定义理解：approvalStatus 只反映是否送厨，看不出是否已完成或已付款；selection 的 NEW/HOLD/SENT/READY 描述制作进度，其中 READY 依赖餐厅使用 Toast KDS。Toast check 的 PAID 与 CLOSED 还区分付款和小费调整；本例不含小费，这里的 closed 规则不能当作 Toast 的完整行为。参见 Order object summary，Order status information。

03送厨交接

点餐页用可选项表达常见口味，提交前列出每份的最终配置；缺少必选项时定位到对应的组，已经选好的内容保留。价格有变化时展示差额，服务员确认后才接受新版本。服务员点“送厨”后，系统把指定 revision 的 selection 固定为制作依据，并保存 ticket 和 outbox；界面先显示“待厨房接收”，得到厨房确认后才显示“厨房已接单”。如果数据库写入就算作已接单，打印机断纸或终端断网时，前厅会向客人报出等待时间，厨房却从没见过这张单。

同一 ticket_id + revision 重发给可去重的 KDS，厨房屏上只出现一份待做工作；服务员刷新页面也不会生成新 ticket。纸质打印没有可靠的电子完成回执，打印成功了，厨师也未必看到。这种模式下，本例保留“打印结果待确认”，重打的单显著标为副本，并由人员确认；物理副作用并非都能做到 exactly once。厨房拒绝制作时，原 selection 及其承诺保持不变，前厅要向客人提出换菜、等待或取消的方案。

送厨无法靠数据库回滚撤销，已经送厨的“撤菜”是一个新请求。厨房在尚未制作时可以确认停止；若已经开火，由经理决定继续上菜、重做或报损，并明确调整账单。原 selection 不能删除，否则已经耗用的食材就无从解释。厨房做了什么与客人应付多少，也不能合成同一个布尔值：餐厅可以因服务问题免单，菜却确实做过；也可能菜取消前款已收到，还要另行退款。audit trail 保存原 revision、变更理由、批准人、厨房响应和资金操作引用。

04分账与多次付款

Split check 把消费责任拆到多个 check：两人各付自己的主菜，共享配菜各承担一半。每个新 check 都有自己的应付额和关闭条件。Split tender 是同一个 check 用多次付款覆盖余额，例如 3,000 分现金加 4,399 分银行卡；它不会自动生成两份菜品或两张账单。Toast 的操作文档同时描述了按项目拆账，以及保持账单合并、逐笔输入付款金额和 tender type 的做法。参见 Split Checks on the POS（P05-SRC-toast-split-C1）。同一文档提醒，按项目拆账时服务费和项目级折扣不会自动继承，需要重新处理；下文保持总优惠不变的比例分配是本例政策，不是 Toast 的产品保证。

分账界面把原 check 放在左侧，拟生成的 A、B 账单放在右侧；共享项目可以分配消费份额，但保留原 selection 与厨房 ticket 的引用。预览同时显示分配前后的金额总和与优惠归属。提交时带上原 check 的 version；两个服务员同时拖动同一个项目时，后提交的一方收到冲突并重新预览，不按“最后写入者胜出”覆盖前者。已经开始付款的账单暂不允许自动拆分，先确认每次支付的归属；否则一笔已付的钱可能留在空账单上，另一张账单又向客人收费。产品若允许拆分已有付款的账单，需要另设款项重分配对象，不能在本例的模型上补一个字段了事。

不分账时，合并 check 的收款页显示“应付 7,399；已确认 3,000；处理中／待核对 4,399；当前可发起 0”。页面让客人和收银员都能看出，待核对不等于未付款。刷卡超时后，页面保留原 attempt，允许查询、呼叫经理和记录处理意见；页面不提供普通的“再试一次”，因为它会另起第二笔扣款。收现金时录入的是客人这次交付的金额和找零，只有实际记入该 check 的已付额才冲减欠款：交付 5,000、找零 2,000，应用付款为 3,000，不能把 5,000 全计作消费收款。

05演算：优惠分摊与未知支付占额

算法先冻结 selection 和价格，再分消费责任，最后收款。A 的原价责任为 3200 + 1900/2 = 4150，B 为 2800 + 1900/2 = 3750，两者合计仍为 7,900 分。501 分优惠按两人的原价责任分配：A 的理想分配为 501×4150/7900 ≈ 263.1835，B 约 237.8165。取整后为 263 和 237，剩下的 1 分给余数较大的 B，得到 A 净付 3,887、B 净付 3,512，合计 7,399。余数相同时按新 check ID 的固定顺序分配，预览和提交使用同一规则版本。

朴素实现容易先拆出两张新账单，再对每张重复应用“优惠 501 分”，使总优惠翻倍；也可能把共享项目复制成两份，让厨房再做一盘。正确实现把责任份额记为从原 selection 派生的记录，所有子份额之和为 1，并在同一事务中把原账单标为已替代。共享菜的消费责任可以分成两半，制作任务仍只有一份。一分钱无法平分时，仍用最大余数法安排尾差；尾差只关系到金额守恒，与厨房的制作数量无关。

分账预览要遍历 n 个消费份额并按余数排序，约 O(n log n)；一桌通常只有几十个份额，用不上复杂的分布式计算。modifier 树的验证按 v 个节点、e 条父子关系遍历，约 O(v+e)，同时检查选项是否属于相应的菜单版本、必选数量、深度上限和重复关系；只凭叶子名称相同不能接受。系统以此防止客户端把另一道菜价格较低的选项拼进当前 selection；真实 provider 的规则还要通过它的 API 再验证。

若不分账、保留 7,399 分的合并 check，现金成功后已确认 3,000；4,399 的卡尝试已送出，但响应丢失。收款服务使用 可发起金额 = 应付 − 已确认应用金额 − 未决尝试占额，得到 0。未知占额不是已成功的收入，只是为阻止并发重复收费而暂时占住的额度。核对到卡成功后，已确认变为 7,399，未决归零；核对到明确拒绝后，已确认仍为 3,000，未决归零，允许新的尝试收 4,399。错误的实现只减去已确认金额，卡结果未知时仍允许再收 4,399 现金；迟到的成功结果一到，就多收了一份。

06技术选型与系统拓扑

React 或 Vue 可以实现桌台、菜单、拆账和收款工作台；厨房屏需要清晰的大字号、便于操作的焦点顺序，以及刷新后保持不变的 ticket 身份。服务端可以采用 Kotlin/Spring 或 TypeScript/NestJS；强类型的金额与版本对象有助于减少误传，取舍仍看团队能力。PostgreSQL 事务保存 selection、check 份额、付款占额和 outbox，唯一键保证同一 ticket revision、同一 attempt 只产生一次业务效果。菜单的静态内容可以按餐厅、版本、语言缓存；当前应付与可收余额由权威服务确认，本地缓存不作最终决定。浏览器本地存储可以保护未提交的草稿，但断网时的草稿只显示“未送厨”，不能显示成餐厅已接单。

拓扑中，点餐 UI 的 commands 指向订单服务，厨房 UI 的 commands 指向厨房服务；厨房的确认事件经 emits → delivers 更新 ticket。账单服务 owns check，check derived_from selection，tender depends_on 被接受的 check version。资金服务 requests 外部支付方，并 reads 原交易来核对；projects 把厨房、账单与支付三种事实分别呈现出来。Toast 用来参照餐饮对象，Stripe 用来参照回调风险；两者在本例中没有接成生产集成。Stripe 文档讨论签名验证、重复事件与乱序，所以本例的事件消费者保留事件身份，并回查权威结果。参见 Stripe Webhooks。

正常流程中，服务员提交 selection，厨房确认接单并做完，客人收到菜；收银员决定分账还是同账多次付款，资金确认覆盖余额后关闭账单，班次核对现金应用额、找零、卡交易及退款。异常流程中，卡已受理但响应超时，本地把这次尝试记为 unknown；收银页继续保留桌台和责任人，后台按原交易查询。若查询也不可用，由经理在未决清单中接管；本例不自动改收现金。业务允许客人先离店时，另建明确的应收或人工交接记录，不能把它记作已收款。

送厨事务提交后 worker 崩溃时，重放同一 outbox；重复的副本在 KDS 上按 ticket revision 合并。厨房已确认撤销后，晚到的旧“已接收”消息不能把 ticket 恢复为待做；读取当前 revision 和撤销确认后修复投影。付款状态同样不按消息到达的次序决定。若系统无权查询支付端结果，这笔尝试会一直停在 unknown，自动恢复的前提也就不成立。

07验算：容量目标与失败检查

容量目标为 50 家餐厅、每店峰值 60 个活跃桌台、每桌最多 80 个 selection、8 台点餐设备；平台峰值每秒 150 次修改或付款动作。本地提交 p95 目标 300 ms，在线厨房确认可见 p95 目标 2 秒；外部终端时延单独计量，未决交易不能从统计中删除。共享菜单的读取容易缓存，真正的竞争点是同一 check 和同一桌的修改。按 check 版本拒绝冲突，粒度比给整家餐厅加一把锁更细；同一桌的金额占用仍要在短事务里串行处理，避免两台终端同时收走同一笔余额。

告警分别统计最老的未接收 ticket、制作超时、未知卡支付已等待的时长和班次差异。厨房正忙不是消息未送达，卡网络慢也不是厨房未完成；混成一个“处理中”，员工就会做错恢复动作。支付 unknown 的核对队列按餐厅公平调度，避免一个大门店的重试淹没其他门店的结账。

结构数据定义了七类必需检查，并列出本例的反例，包括：modifier 数量不匹配应在送厨前拒绝；同一个 ticket 重投不生成第二份制作；撤菜迟到不抹去报损；拆账守恒且不重送厨房；unknown 占额阻止第二次收款；支付被拒绝才释放占额；不同餐厅的同号桌台不能串单；关闭后迟到的未付款消息不能回退当前事实。检查要观察 UI 提示、保存的 selection revision、厨房确认、每次付款和最后余额。配方、收款和是否关账都不由 AI 决定，AI eval 不适用。JSON 是验收定义；尚未实施的 UI、设备、网络和负载检查，不能记为已通过。

08变式：条件改变后的判断

练习一：三份同菜中，一份不加酱、两份正常，服务员只提交一个 quantity=3 的 selection，再附 quantity=1 的“无酱”。 怎样改才能让每一份的责任明确？

简答：改成 quantity=1 的无酱 selection 和 quantity=2 的正常 selection，各自固定 modifier 内容，厨房按两组明确的配置制作。不变量是每一份都有完整配置，不能靠备注让厨房去猜它管哪几份；Toast 的上述数量约束也不接受这种不匹配。反例是厨房给三份都去酱，或只凭顺序猜出一份。检查：菜单验证拒绝旧输入，新输入生成两组配置，总份数仍为 3。若某项要求关系到食物安全，而系统又无法结构化确认，自动化到此为止，交由工作人员确认。

练习二：卡付 4,399 分仍是 unknown，顾客提议先付同额现金。 能否先关账，事后再处理？

简答：不能。未知不等于拒绝：原卡尝试的占额保留，先核对；确定被拒绝后才收现金。若经理决定破例收现金，要单独记录重复付款的风险，并明确后续退款由谁负责，当前的基础模型需要为此扩展；原卡尝试不能删除。反例是卡后来成功，总应用金额变成 11,798 分。检查：unknown 期间第二个普通收款命令被拒绝，页面显示未决金额；核对为拒绝后，允许一次新的 4,399 分付款。支付端无法查证时，这条自动恢复路径失效，转由人工接管并记录。

练习三：厨房已做出共享配菜，客人才要求把账单拆为两张。 是否应再给厨房发送两份各 950 分的配菜？

简答：不应。新 check 的份额引用同一个 selection，制作对象不变。验证两张账单合计 7,399 分，原 ticket 的数量仍为 1。若拆分发生在送厨之前，界面仍可决定怎样编排打印，但消费份额不是增加制作数量的依据。

TR:V05:V04:allocation-conservation 把账单份额守恒迁到商品拆单；共同点是子对象必须能加回父对象，失效处在于共享菜可以分摊金额，却不能按付款份额重新造出实物。TR:V05:V06:charges-versus-payments 把消费项目与付款的分离迁到住宿 folio；住宿有多日记账、押金和离店后的调整，不能照搬本例“本次应付已付即可关账”的规则。在演示中，读者可以改 modifier、延后发出撤菜、在拆账与多次付款之间切换、推迟卡回执，看到制作数量不变，而能否收款随证据变化。

09进入餐饮系统的先查项

跟随一桌包含不同 modifier、共享菜和两种付款方式的消费，分别记录厨房实际收到什么、账单由谁承担、终端实际收了多少。成熟解法是销售点系统（point of sale，POS）的 selection/check/payment 模型、KDS 的制作交接和班次对账；纸质打印、无法回查的终端与离线收款都会改变恢复边界。下一步先查菜单数量约束、厨房确认机制、终端交易查询及取消能力，再研究小费、税费和营业日重开。验证要包含“拆账后制作任务仍为一份”和“终端超时后不能普通补收”两条路径；只看收银页金额相等，证明不了客人没有多付、厨房没有多做。

动作与交接

  • operates人通过界面观察或发起动作。
  • commands界面提出动作请求，成功需另有确认。

  • emits产生事实通知；不保证接收方已处理。

权威与存储

  • owns声明对象事实的权威归属；不是存储副本。
  • stores持久化对象或事件；不自动成为业务权威。
  • reads读取状态或核对外部结果。
  • authorizes允许执行动作的权限/规则关系，不表示动作发生。

依赖与来路

  • depends_on目标是前提或依赖，不表示已有数据传输。
  • derived_from计算或证据派生；注明规则与版本。
