P01 · 交易、财务与资金

一笔业务可能同时有已经生效的合同、尚未交完的服务、已结清的发票和还未完成的收入计划。财务软件的难处，是把这些事实分别存进各自的对象，再说明它们为什么相容。只在订单表加一个 status，很容易把“客户欠多少”“企业还欠什么”“钱现在在哪里”混成一个问题。本包把一笔业务的事实分存在六种记录里，每种回答一个问题、要求自己的证据；每笔金额带上身份坐标，每个外部动作保存“想做什么、发出了什么、确认了什么”。七个案例从订阅收入、采购付款和关账，延伸到贷款、保险、投资订单与集团内部交易。外部结果缺少证据时只能记为未知，不能当作失败去重试。

01共同模型：六种记录

六种记录各回答一个问题，各有改变记录所需的证据；记录之间的先后带有条件，不是固定的箭头。

设一家企业收取 300 单位预付款，承诺提供 30 个等长服务日。第 10 天，客户可能已不欠钱，企业仍欠 20 天服务。把收到的 300 全显示成已赚取，会隐藏剩余承诺；只显示“服务进行中”，又说明不了能否用这笔现金付款。下表把记录分为六种，各回答一个问题。

记录 回答的问题 改变记录所需的证据 常见错误
承诺与授权 答应交付什么，谁可作此决定 已接受的确定版本、审批范围 把报价草稿当合同，把审批当已执行
履行与接收 实际交付、成交或验收多少 服务期间、验收记录、成交报告 用付款证明交货，用撤单请求证明已撤
应收与应付 哪一方还欠哪一方多少 开票、分配、贷项与结算记录 只按金额相等合并不同客户或法人
现金与证券 哪个账户实际增加或减少什么 外部确认、银行或托管核对 把请求受理、支票签发当最终到账
估计与期间结果 还可能承担多少，当前期间归属多少 规则版本、估计依据、截止范围 把准备金当付款，把利润当可用现金
集团合并调整 集团视角哪些内部重复应去除 对手方关系、匹配单据、抵销批次 用合并抵销删除法人原账或免除债务

记录之间的先后带有条件。预付服务要求付款核对通过才开通；赊销服务可以先开通，但会新增信用限额和催收责任。采购先验收再付款，也可能按合同预付。迁移机制时保留“动作需要什么证据”这一问，再按新行业换掉证据的具体内容；箭头顺序不照搬。

02身份坐标

tenant 是客户组织的隔离范围，legal_entity 是承担义务的法人，provider_account 是外部账户，三者不能互换。一个集团租户可能有多个法人，同号发票也可能来自不同供应商。对象键至少要说明对象在哪个范围内唯一；跨系统映射保留原对象 ID，不拿可编辑的显示编号充当身份。每笔金额还需要币种、精度和方向，每项数量需要单位，每个期间需要起止与截止规则。两个数字相等，不能说明它们属于同一笔业务。

同一数据库的事务可以约束本地对象一起提交，却无法让外部银行、交易场所或保险支付系统同时提交。因此操作记录要保存“想做什么、发出了什么、确认了什么”。unknown 表示缺少结果证据；failed 表示已有失败证据。若外部已经付款但回执丢失，换一个新请求号重发，会把网络问题变成重复资金流。找回结果的办法各章不同，一个统一的“失败重试”按钮覆盖不了。

03页面与权威

页面要同时显示对象的状态和动作的状态。例如发票仍为 open，付款尝试正在核对；贷款已批准，放款尚未确认；订单部分成交，撤单正在等待。列表适合发现异常，详情需要展示来源版本、剩余数量、责任人和下一步动作。权限由服务端依据身份、对象范围与动作重新判断。隐藏按钮方便使用，但不是授权机制。

本包的 JSON 画出 UI、service、store、external system 之间的信息传递，现金、实物和证券的变化则记在业务对象里。一个 delivers 箭头表示消息交接，不表示钱或货已经到达。owns 指明哪一方对某项事实说了算；存储副本和报表投影没有这种权力。状态图把“事件触发了什么”与“哪个对象依赖哪个前提”分开：H03 正文中 A 先于 B 执行，对应结构里的 B depends_on A；这条边表示依赖，不表示沿箭头方向传输数据。完整的状态转换、前提和恢复点在每例的结构文件里，正文解释这些前提为什么存在。

04案例与阅读顺序

七个案例从单个法人的收入、采购和关账出发，再引入本金、损失估计和在途成交，最后扩展到集团。

案例 工作链 要学会的判断
H01 · 拓扑 报价 → 合同 → 服务 → 收款 → 收入 区分价格版本、付款分配、权利开通与期间收入；解释中途变更
H02 · 拓扑 请购 → 验收 → 发票匹配 → 付款 用累计数量和容差决定可付范围，解释为什么相等总额仍不够
H03 · 拓扑 子账 → 对账 → 关账 → 管理报告 判断截止范围和匹配粒度，发现净差为零掩盖的错账
V12 · 拓扑 申请 → 审批 → 放款 → 贷后 → payoff 分开批准额度、已放本金、计息与结清报价的有效期
V13 · 拓扑 Submission → quote → issue → claim → reserve → payment 区分保障、损失估计、可赔金额、付款授权与现金
V14 · 拓扑 投资订单 → fills/cancel → allocation → settlement 处理撤单与成交竞争，保持数量守恒并解释交收失败
X02 · 拓扑 集团销售 → 实物流/虚单 → 内外结算 → 合并核对 连接实物流、内部交易和外部销售，区分结算与合并抵销

先读 H01、H02，再用 H03 检查它们怎样进入期间报告。V12、V13、V14 分别引入“时间里的本金”“不确定的损失”“在途的成交”，一个金额字段都不再够用。X02 把边界从一个法人扩展到集团：局部正确，合并时仍可能重复计算。

05解题五步

每例按“识题 → 解法 → 演算 → 验算 → 变式”展开，五步的含义见把业务问题算清楚：由现象认出问题类型，选有前提的已知方法，手算可观察的结果，用不变量与反例检查，再改变条件看方法是否仍然适用。每例开头的识别线索连着后文的具体推演。

06手算与检查

先手算例子，再改变一个条件：时间、数量、价格、权限或外部确认。每章至少有两道带简答的条件变化练习；看不变量在哪一步被破坏，比增加更多页面更能判断系统是否完整。

从 Praxis 仓库根目录运行以下命令，不需要安装第三方依赖。先读 checks.py 的输入与断言，再改一项条件复算：

python3 vault/distilled/saas-engineering-atlas/packages/commercial-finance/checks.py

它覆盖七章的固定算术、区间可加性、数量占用、配对、依赖图和不可行条件，没有建立服务，也没有模拟实际的并发数据库。外部集成、权限执行、浏览器端到端、故障注入、负载与 AI eval，都要在实施后另行验证。

共同结构用 python3 scripts/validate_saas_atlas.py --self-test 检查，证据身份与引用用 validate-package.py 检查：

python3 vault/distilled/saas-engineering-atlas/packages/commercial-finance/validate-package.py

07进入陌生行业

先找出承诺对象、履行证据、数量或金额约束、决定权限与外部权威，再判断需要哪一类成熟机制：版本化合同、匹配与 hold、来源级对账、期间与事件重演、分组估计账务、受约束分配或跨公司协同。方案的名字只是入口，适用条件决定能否迁移。遇到陌生业务，可以先从每例开头的识别线索找研究入口；文末的探索方向列出最小试验、需要继续查的文档和可观察的成功条件。
