P06 · 生产、资产、公用与供应网络

一家企业答应交付一批设备，首先要知道交付的是哪版设计，随后安排材料、设备和人；制造、检验、运输、账单和付款各自证明或结清一部分义务，设备投入使用后还会产生维护、计量和服务费用。七个案例沿这些关系展开：同一件实物可以参与多条工作链，每条链却有自己的权威、证据和结束条件。改变判断的是证据能否支持这项决定：生产完成说明不了检验通过，抄表数据到达说明不了数值可以计费；现场实物已被改变时，恢复只能追加修正、返工、隔离或对账。

01共同模型：从承诺到结算

订单表达承诺，计划寻找可行办法，执行消耗现实资源，证据说明实际发生的事，授权决定证据是否足够，结算确定与履约对应的债权债务。这个模型用来发现缺少的对象，并不要求所有厂商都实现成六张表。例如，“生产完成 100 件”还说明不了有多少件通过检验；“抄表数据已到达”也说明不了哪些数值经过估算、允许怎样计费。

对象职责 回答的问题 容易混淆的对象 案例中的区别
承诺与基线 承诺哪种结果，依据哪个版本 计划、最新文件 生产单绑定已发布设计；旧批准不会自动覆盖新配方
计划与资源预约 在什么约束下做得到 执行事实 车有容量不证明承运人已接受；任务 DAG 可排不证明许可证足够
执行记录 谁在何时对什么做过什么 汇总进度 一批混合物的投料与损耗需要守恒；离线维修可能迟到上报
证据与处置 哪些结果支持哪项决定 原始信号、模型建议 检验报告、时序报告和 VEE 的校验结果各有适用范围
授权与放行 谁可在什么条件下推进 自动计算结果 质量人员放行批次；设备许可限定现场作业；服务激活需核对资源
结算与关闭 哪项义务已经结清 发货、开票、付款 部分交付保留欠交量；已停服务仍可能有迟到用量待结算

每个对象至少有三种身份：业务身份（批次或服务实例）、版本身份（这次判断使用的输入）、操作身份（这次提交和重试）。业务身份让人追踪一件事，版本身份阻止旧证据批准新对象，操作身份让重复送达不重复扣料或收费。三者不能用一个自增行号替代。租户、站点、外部账户和允许的合作伙伴关系还要进入授权范围；把编号拼接进缓存键只能防误命中，不能代替服务端权限。

02页面与现场

命令、外部请求和回执各是一段交接，业务状态只在核对回执之后改变。

系统的最小闭环是：人通过工作台发命令，服务检查权限和对象版本，数据库保存尝试，连接器把确定的请求交给现场或外部系统，回执进入持久收件箱，业务服务核对后改变状态，读模型再更新页面。拓扑中 commands、requests、delivers 表达不同交接，owns 表达事实归谁负责，derived_from 表达计算依据。实物运输和现金支付另有业务记录，一条消息箭头证明不了。

页面要把“请求已保存”“外部已接受”“业务已确认”分开显示。运行数小时的芯片设计任务、离线维修、迟到的电表读数，尤其不能只靠一个旋转图标表示进度。用户关闭浏览器再回来，仍应找到同一操作及待办责任。结果未知时先查询既有外部对象；现场实物已被改变时，恢复往往是追加修正、返工、隔离或对账，数据库回滚抹不掉。

03技术选型与触发条件

原型可以从 React 或 Vue 工作台、一个模块化业务服务、PostgreSQL 和对象存储开始。关系库适合在事务内保护版本和数量约束，对象存储适合检验附件、版图和签名清单；时间序列、图遍历、优化器和消息中间件按案例中的真实查询或规模需求再引入。各例写明引入每种组件的触发条件：先有业务理由，再加基础设施。

七个案例共用“判断绑定依据，动作有权威，数量和时间可核对”这一结构，区别在允许推进的条件。

V08 的 lot release 需要质量责任，V09 的 release 需要设计证据，V22 的 active 需要技术状态。三个英文词即使都呈现为绿色，也没有可互换的审批语义。

从 V07 读起，先熟悉“承诺到履约”这条线；V08、V09 比较实体谱系与数字证据图；V10、V11 解释现场事实怎样晚于动作进入系统；V21、V22 把局部完成扩展到跨组织和跨资源闭环。

05解题五步

每例按“识题 → 解法 → 演算 → 验算 → 变式”展开，五步的含义见把业务问题算清楚：看到线索后选择已知方法，用小数据算清楚，再用不变量和反例检查，最后改变前提判断哪里必须重做。每例末尾的条件变化练习检验迁移边界。算法回答“选什么、算多少、受什么影响”，恢复流程回答“现实究竟做到了哪里”，两者分别验收。

06进入陌生行业

先选最接近当前承诺的案例，照着辨认业务对象与权威，再列出本行业改变了哪些单位、时间、授权和失败条件。每例文末的探索方向列出可考察的成熟方案族、需要补读的产品文档与验证输入；方案名称只是研究入口，适用性取决于能否覆盖已识别的职责和证据边界。
