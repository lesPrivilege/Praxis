从业务承诺到可恢复的系统

同一件工作，常由几个岗位分别判断：销售承诺交付，运营证明交付，财务核对收款。各方看的是同一笔业务的不同部分，各自的判断要彼此相容。软件即服务（Software as a Service，SaaS）因此要保存足够的身份、状态与证据，让一次点击不会悄悄替另一方做决定。

本书所说的 SaaS，指以持续服务的形式提供的软件能力。用户界面（user interface，UI）供人查看信息、提出请求；应用程序接口（application programming interface，API）规定系统之间怎样读写。人工智能（artificial intelligence，AI）可以帮助生成候选方案和解释，系统里的动作仍受对象、权限和确认条件约束。标识符（identifier，ID）用来定位对象，它在多大范围内唯一，取决于租户、来源等条件；本书配套的结构数据用 JSON（JavaScript Object Notation）保存。其他缩写在各行业首次出现处展开，集中查阅见 术语索引。

工作对象与完成条件

每个案例都从一项承诺和一个可检查的结束条件开始。例如，工单关闭需要完成记录与接收确认，列表里少了一行并不算关闭。随后要找出 actor、object、state、action、event：谁有权提出动作，动作针对对象的哪个版本，哪项事实允许状态变化，谁能确认变化已经发生。

同一个对象会出现在多个页面和系统里，它的各项状态却往往归不同系统管理。合同的 accepted、发票的 paid、服务的 active 可能同时成立，也可能暂时分离。案例要说明 system of record（权威记录系统）与 read model（供查询的投影）各是什么，以及投影更新滞后时用户会看到什么。数据库里有一行、外部系统已受理、业务已完成，是不同的证据。

四个可互相定位的视角

视角 核心机制 通向下一视角
业务 承诺、资源、责任、期限、资金与实物流；对象的不变量 每个动作指向对象、权限和状态条件
交互 可查看、可修改、可提交的内容；等待、拒绝、冲突和恢复 每个提交对应 command，每个确认指向权威事实
拓扑 服务、存储、外部 provider、队列与边界；同步调用和异步事件 每条边标明传递内容、接收方和失败的发现方式
计算与运行 输入规模、计算方法、误差、缓存、并发、恢复、成本 每个选择用可观测的正确性和性能条件验收

拓扑图里的每条边都有确定含义：owns 表达权威归属，stores 表达持久化位置，delivers 表达事件交接，depends_on 表达前提，四者不能互换。把产品 logo 连成一串并不构成拓扑。对象之间有派生关系，也不说明数据已经传过去。边的具体用法受 关系类型约束；对象的生命周期写在各自的状态表里。

算法推理与可靠运行

算法说明一个输入怎样变成一个结果：匹配订单、筛选候选、累计时间区间、沿图追溯、安排依赖、分配资源或近似估计。可靠运行说明同一结果在重试、并发、宕机和外部不确定性下怎样仍能被正确使用。lookup 再高效也替代不了幂等约束；排程即使最优，也证明不了现场已经执行。

计算家族 直觉与适用问题 代价与反例
lookup 用稳定 key 找一件对象，避免逐条比较 hash 平均查找可近似 O(1)，树索引查找通常 O(log n)；两者都有存储、更新及具体实现前提
sorting / Top-K 按一个可解释的顺序先处理最重要的 k 件 全排序 O(n log n)，大小为 k 的 heap 通常 O(n log k)；分数相同时要有稳定的先后次序
windows 把事件按业务时间放入相同窗口再计算 event time 与收到时间不同；迟到、重叠与补录会改变结果
graph paths 沿关系解释来源、影响范围或可达性 有向边、环与访问权限影响遍历；用户无权访问的节点不能经由路径泄露
dependencies / scheduling 先满足前提，再安排可开始的任务 DAG 的先后关系不等于机器、人员、时间窗都可满足
optimization 在约束下找较好的资源分配 写明目标、硬约束、可行解与停止预算；启发式结果不称全局最优
caches 复用以前的计算，减少反复读取 命中率之外还要看失效、租户隔离、冷启动和最坏陈旧时间
approximate computation 用可说明的误差换空间或速度 估计可用于探索；未经确认，不用于付款、放行或安全决策

上表是本书的教学分类。复杂度描述的是给定计算模型下的推理，不是服务延迟实测；要说某个产品用了哪种算法，需要另有公开证据。每个案例只选真正起作用的家族，用一组小输入、一遍人工演算和一个反例说明；按问题查找见 解题索引。

从点击到业务结果

端到端链条至少覆盖：UI 发起 → 服务校验 → 持久化请求与对象版本 → 外部受理或拒绝 → 事件/轮询核对 → 状态投影 → 用户可见结果 → 业务对账。异步系统可以短暂不一致，但必须说明哪一方尚未确认、多久检查一次、由谁接管失败。

性能参数写成待检验的目标，注明请求量、对象数、租户分布、并发、延迟分位数、错误率与缓存条件。恢复设计要区分已提交、未提交和结果未知三种情形；每个可重试的操作都要有身份和核对依据。AI 输出参与判断时，还要另外评估错判、漏判、人工修正和拒绝条件；语言流畅不能代替业务正确性的度量。
