V19 · 专业服务的配员、工时、计费与收款

咨询公司卖出的是对结果的承诺，排进去的是人的可用时间，客户收到的是按合同规则算出的账单。三者相互约束，却不是同一种量。有空的人未必具备所需技能；已经做过的一小时，经理未必认可；经理认可的工时，也可能超过合同的可收费上限。软件要把这些差别保留下来，项目经理才知道还能安排谁，财务才能解释每一笔钱的来历。

本例是一项合成的数据迁移 engagement（服务委托）：客户确认范围，合同总收费上限为 10,000 记账单位，已 release for invoicing（释放给开票流程）7,000；本期两条已批准工时按约定费率分别计 2,000 和 1,600。合同允许拆分行金额，先按服务日期、再按稳定行号分配剩余限额；不含税、汇率、差旅、预付款、收入确认或退款。600 的超额留在争议/变更队列，不自动记作下一期应收。所有数值与这套限额政策都是教学构造。

本例沿用本包的共同模型：人员执行工作，批准者确认记录，接收方与资金权威分别提供下一步所需的证据。客户确认交付结果，经理批准 timecard（工时单），财务把 billing event 释放给开票流程，账务确认收款，各自关闭一种责任。把它们都塞进项目的 done 字段，“项目已完成但账单被拒”这种情况就无从表达。

解法：承诺、产能、工时与现金的对象

项目经理负责委托范围与交付依赖；资源经理协调不同项目争用同一个人；顾问申报已经做过的工作；审批人核对工作与合同；开票员处理计费；财务核对实际资金。顾问可以编辑自己的草稿，却不能自行批准；资源经理可以排班，不能单凭排班生成已发生工时。客户是否必须验收、谁能授权超额，都是需要配置的合同条款，不从岗位名称推断。

Certinia 的 Timecards 文档提供工时列表与详情入口；其 Approving and Rejecting Timecards 文档说明审批过程要由管理员配置，提交、批准和拒绝取决于该配置（Timecards、审批概览）。在 Certinia 里，实际流程取决于各组织的配置，所以下表的状态与职责划分是本例的实现政策。

对象 权威与关系 易混的事实
Engagement E1 / contract version 委托服务保存客户接受的范围、费率和上限版本 估算不是承诺；范围变更需新授权
Assignment A 排班服务保存人员、任务、时间窗与占用小时 proposed 尚未锁住资源；confirmed 也不证明工作发生
Timecard T / time line 工时服务保存服务日期、人员、任务、小时、版本和审批人 approved 不等于 billable；修改 approved 行需更正记录
Billing event B 计费服务把符合条件的明细冻结并扣减本例的限额可用额 release 表示交给开票流程，不能写成 paid
Invoice I / payment allocation P 账务系统负责发票与收款分配；本地只保留映射和核对副本 收到一笔钱要匹配发票；收到通知不等于已核对

Assignment 走 proposed → confirmed → completed / cancelled；改期生成新版本，不能覆盖已经用于工时核对的历史排班。Timecard 走 draft → submitted → approved / rejected；驳回后带着理由回到草稿；批准后的更正从旧行派生 adjustment，原小时数不直接改掉。Billing event 走 draft → reserved → released → invoiced，外部结果不明时停在 unknown；Invoice 另走 open → partially_paid → paid。

Certinia 的 Billing Event Generation 文档把生成 billing event 与 release for invoicing 分开，能选择 timecards、expenses 等来源记录，并展示批处理进度；文档没有说生成成功就等于已开票或已收到现金（Billing Event Generation Tab）。本例沿用这一区分，外部核对机制是本例自设的。

演算：排班可行性

周一有两个必须当天完成、各需 4 小时的任务：J1 需要 SQL，J2 需要 Python。甲会 SQL 和 Python，当天可用 4 小时；乙只会 SQL，当天可用 4 小时。完整的输入还应包含已确认占用、休假、任务时间窗和资格到期日；为了手算，暂不计通勤、切换成本与跨时区。

若按任务编号贪心，并给 J1 选“技能最多的甲”，剩下的乙无法做 J2。总可用 8 小时等于总需求 8 小时，排班仍然失败。把问题画成二部图就看清原因：J1 连甲、乙，J2 只连甲。先处理候选更少的 J2，分给甲，再把 J1 分给乙，两项都可完成。小例子可以枚举 2×2 个候选组合，验证这个解可行；它没有证明“最少候选优先”对任意规模都最优。

如果每项任务必须整块交给一个人，每人也只接一个任务，二部匹配可以直接判断是否存在完整匹配；一般增广路实现可按 O(VE) 估计，V 是节点数，E 是合格候选边数。加入可拆工时、每天容量和技能可用期后，需要变量 x[人,任务,日]。约束是：每天已占用加新分配不超过净可用小时，技能合格，任务在时间窗内完成；目标是最小化成本或迟延。可以用 OR-Tools 建模，但解只对列出的约束有效；求解超时要区分已找到可行解与完全无解，不把“没找到”显示成“无人可做”。本例没有实际运行求解器。

前端排班板应同时提供表格和时间轴；拖拽时先显示候选方案和冲突，提交后由服务端确认。客户端缓存显示甲还有 4 小时，这不能作最终依据。两个项目经理同时给甲排 4 小时，后端在同一人员/日期的容量记录上做串行检查，只有一个成功；另一人看到冲突与重新计算入口。每日总小时适用于本例的弹性日容量。如果合同要求 09:00–13:00 连续工作，只检查日总量会漏掉时间重叠，还需要区间交叠检查；必要时同时约束日容量和连续时间窗。

演算：工时、限额与超额

顾问申报工作事实，审批人确认本例允许计入的记录，合同费率算出候选收费额。内部成本率可能不同于对客收费率，不能用客户账单估算员工工资。前面的排班只取周一的两个子任务；下面的计费按整周的迁移工作算，18 小时并不是由周一的 8 小时改来的。本期 T1 为 10 小时×200=2,000，T2 为 8 小时×200=1,600，两条都已批准且符合本例的 billable 条件。

剩余限额为 10,000−7,000=3,000。按本例的稳定顺序分配：T1 获得 2,000，余额变成 1,000；T2 获得 1,000，另 600 标为 over_cap。原始批准小时仍是 18，候选收费额仍是 3,600，release 的金额是 3,000。不能为了让账单好看把 T2 的 8 小时改成 5 小时，这样会同时破坏工作记录和项目成本。本例每次冻结的候选集合满足 候选金额 = 本次分配金额 + 本次超额金额；在合同层面满足 累计释放 + 尚未释放的有效预留 ≤ 上限，式中的预留与释放必须互斥计数。

扫描 n 条已排序明细的分配为 O(n)，事先按服务日期、行号排序为 O(n log n)；合成实现用整数最小货币单位记账，以免二进制浮点误差让金额多出 0.01、越过上限。全表重算直观，但不应在每次打开页面时扫描所有历史；可以保存已释放总额与操作账本，在同一事务内按预算版本更新，并定期用明细重算核对。这是 ALG:windows 与 ALG:lookup 的组合：服务期间筛选决定候选集合，稳定业务键定位已处理行，二者都不能替代扣减上限的并发控制。

Certinia 2025.1 的预算限额文档用预算金额减 Amount Released for Invoicing 计算可开票额，Amount Consumed 不参与该计算；文档还允许特定条件下的客户容差，并禁止同一项目同时设置预算级与项目级 cap（Applying a Billing Cap to Individual Budgets）。本例只设一个合同级上限，容差为零；拆分行和 over_cap 队列是本例自己的政策。

反例一是拿“成本消耗 9,000”计算可收费 1,000：成本率和销售费率不同，这个数未必有计费意义。反例二是两个 worker 同时读取余额 3,000，分别 release 2,000，总额变成 11,000。在页面上禁用按钮解决不了竞争；计费服务必须在权威事务内锁定预算，或用版本条件写入。反例三是把 600 静默带入下月：合同总上限没有因月份变化而重置，下个月仍然超额，除非客户接受新范围或新上限。

工时审批、开票与收款

工时表按日期、任务和审批状态显示，保存草稿与提交审批是两个不同的操作。提交后锁定审批版本，拒绝时把理由附在原行旁；离线编辑回来的旧版本不能覆盖经理刚批准的内容。审批页显示“已排班 8 小时、申报 10 小时、差异 2 小时”，要求顾问说明差异，不自动裁成 8 小时。排班是预测，实际可以超出；是否接受超出由本例的授权规则决定。

计费页先预览“已批准候选 3,600；剩余上限 3,000；拟释放 3,000；待处理超额 600”，再由获授权的开票员确认。后端验证合同、审批版本和已处理明细唯一键，保存 allocation、reserve 和 operation ID，异步请求账务系统开票。本例把 released 定义为“账务已受理这项开票请求且已核对”。到这一步，同一金额在同一事务里从 reserve 移到 released，其他事务看不到这笔金额两边都没有计入的中间状态；具体发票 I1 的身份与金额核对完成后，才进入 invoiced。若受理响应已经带回发票，两个逻辑步骤可以在同一次处理内完成，证据仍分别保存。页面分别显示“提交已保存”“账务受理中”“发票 I1 已确认”。账务提供已核对收款 1,800 时，I1 是 partially_paid，未收 1,200；第二笔 1,200 核对后才 paid。客户发来的付款截图不能作现金证据，本例的现金权威是账务系统。

前端可以选 Vue/TypeScript 或 React/TypeScript：两者都适合可编辑表格、冲突提示和排班时间轴；要做的是把服务端的版本冲突映射成可以恢复的行，审批规则不在浏览器里另写一份。小规模应用可以用 Django + HTMX 表单，免得两端各持一份状态，代价是离线批量编辑需要另外设计。后端用 PostgreSQL 保存员工/日容量、合同版本、工时审批和计费分配，用整数分钟及整数分存数量和金额。队列可以从数据库 outbox 加 worker 起步；跨系统开票或通知量变大后再换托管队列，代价是要处理重复投递，并承担运维。也可以由外部的专业服务自动化（professional services automation，PSA）系统提供排班或工时数据，但字段映射、授权与版本要由 adapter 明确处理，不能把两个系统都写成同一对象的权威。以上选型是本例自设。

正常路径是客户接受 E1，甲、乙的排班分别确认，顾问填写并提交 T1/T2，审批人批准，B1 原子预留 3,000，账务受理核对后转为 released，具体 I1 核对后变为 invoiced，财务逐笔核对 1,800 与 1,200 的收款。客户对交付结果的验收可以先于开票，也可以按合同约定作为 release 的额外 guard；本例假设 release 前已经获得交付验收，但仍保存独立证据。

失败路径：账务已开票，网络响应丢失。B1 保持 unknown，3,000 的预留不能释放回可用额，否则另一次开票会占用同一份剩余限额。adapter 按 (tenant, ledger_account, billing_operation_id) 查询；查到已存在的 I1，就绑定回 B1，不另开 I2。若账务不支持可靠的 correlation key（把本地开票操作与外部发票对上的键）查询，就人工核对未知结果，不能靠“超时十分钟就撤销预留”这种规则去赌请求没有成功。确认未受理后才能取消；确认开错票后走更正/贷项流程，不直接删除工时或历史发票。反向调整能否恢复 cap 下的可用额，要由合同和账务政策决定；本例不自动恢复。

容量假设为 50 个租户、每租户 2,000 位顾问、每周每人 5 条工时，合计每周 500,000 条；月底某租户同时提交 20,000 行计费。待测目标是单人周工时页 p95 < 500 ms、审批提交 p95 < 700 ms，批量计费每 500 行一个可恢复分片；未做负载实测。锁不在所有项目间共享：产能按人员/日期加锁，跨版本的计费占用账本按合同与币种加锁；cap 版本是授权输入，本身不是一个可以单独扣减的余额。按合同加锁之后，一个巨大合同仍会成为热点，要限制同一 cap 的并发批次。版本切换与新预留也受同一个合同级并发控制；旧版本停止新增预留，新版本继承累计 released 与所有未决的有效 reserve，不能只继承已开票金额。例如已释放 7,000，另有结果未知的预留 3,000，上限从 10,000 调到 10,600 后，新可用额只有 600；若错误地给新版本另建余额，就会算出 3,600，把那 3,000 重复用掉。报表缓存可按租户、项目、周期与权限版本分区，月底批处理更新后显示投影已更新到的时间点；可用额预览标明是估算，release 时总要重新校验。恢复时重新核对 allocations、reserved、released 与账务发票，不能只重放“创建发票”消息。

本例的配员可行性、限额分配和审批 guard 用确定性规则判断，核心路径不需要 AI。若以后让模型从工时描述中提取任务编号，模型只提供建议，人工确认后再进入正常 guard。可选的评估计划冻结 200 条样本：120 条开发、80 条留出，按顾问和项目切分；记录 80 条中正确提取数、20 条含歧义样本的拒答数、60 条无歧义样本的误拒数及人工修正数。假设模型对 20 条歧义样本中的 4 条硬给出错误任务：这些输出都不为空，却都是错的，所以非空输出率不能当成功率。模型或提示词变化后必须重新评估；也不能凭描述自动批准工时或提高限额。本例尚未运行模型评估。

变式：条件变化与迁移

练习一：乙改为只能周二上班，J1 仍要求周一完成。 能否沿用原排班？

简答：不能。乙的 SQL 技能还在，但时间窗去掉了 J1→乙 这条可行边，周一 8 小时的需求只有甲的 4 小时可用。不变量是“资格与时间同时满足”；失效条件是只按技能匹配。检查时 UI 不显示“总计两人足够”，而是列出 J1、J2 争用的资源，并提示改期限、找替代人员或调整范围。可迁到 V20 的 booking，现场任务还可能受地点、行程与设备约束，按日工时匹配不足以保证可达。TR:V19:V20:capacity-and-window。

练习二：客户把合同 cap 提高到 10,600，变更今天才接受。 600 能否立即重写进原账单？

简答：不应改已冻结或已发出的 I1。保留旧 cap 版本及 3,000 的分配，按新授权为剩余 600 另起一次计费；先检查它适用的服务期间，以及同一源行尚未计费的部分。若 B1 还是 unknown，旧预留 3,000 同样进入新版本的共同占用账本：新上限 10,600 减已释放 7,000 再减预留 3,000，仍只剩 600。不变量是每次计费都可追溯到合同版本且不重复；失效条件是用最新上限重新解释历史。检查时 T2 两次分配合计最多 1,600，旧 I1 的金额仍是 3,000。可迁到 H01 的合同版本，但订阅权利的开通时点需另外决定。TR:V19:H01:versioned-billing。

练习三：合同变成固定费 10,000，实际做了 25 小时。 能否仍按小时×费率生成客户账单？

简答：不可以。工时继续支持产能和成本分析，计费来源改为合同约定的里程碑/交付验收；若规定 40%/60%，两次候选额为 4,000、6,000，与工时变化不直接联动。不变量是“计费依据显式”；失效条件是把 timecard 当作所有合同的唯一计费依据。检查时额外的 5 小时不自动增加固定费账单，未完成的里程碑也不因工时已批准就 release。这个边界能帮助 V18 区分审阅工作量、交付接收与费用批准。TR:V19:V18:effort-versus-acceptance。

演示可以让读者修改技能、可用日期、cap 与回执延迟，同时观察排班可行性、工时、候选金额、预留、已释放、发票和已收金额。不论用哪种 UI，超额 600 都要留在看得见的处理队列里，不能随动画结束消失。结构见 V19.json，事实与合成政策见 evidence.json。

进入专业服务的先查项

进入陌生的专业服务行业时，先准备一份完整的合同规则样例，可以是虚构的：按时、固定费还是里程碑，上限覆盖哪段期间，超额、预留、贷项和变更怎样处理。PSA 的资源规划、工时审批与 billing 能提供基础对象，账务系统仍负责发票与到账；现成模块是否适用，取决于它的额度口径和本合同是否一致。下一步查供应商对 cap、approval、release 的定义，费率生效与部分行的处理，确定外部开票的 correlation key，不从演示字段名去猜。验收时，在预留结果 unknown 期间提高 cap，再检查同一工时多次部分分配的总额：尚未确认的 3000 仍计为占用，才说明换版没有重复使用额度。

结构、生命周期与迁移

由 V19.json 生成：18 个节点、40 条带类型的边、7 个生命周期、9 条检查定义。所有边都是本例的合成设计。

算法家族dependencies / scheduling、optimization / 优化、windows / 窗口计算、lookup / 查找、caches / 缓存

动作与交接

  • operates人通过界面观察或发起动作。
  • commands界面提出动作请求，成功需另有确认。
  • requests发给外部 provider 的请求；timeout 可能留下未知结果。
  • emits产生事实通知；不保证接收方已处理。
  • delivers异步通知交接；接收与完成分开。
  • projects对象被投影为可见内容，注明新鲜度。

权威与存储

  • owns声明对象事实的权威归属；不是存储副本。
  • stores持久化对象或事件；不自动成为业务权威。
  • reads读取状态或核对外部结果。

依赖与来路

  • depends_on目标是前提或依赖，不表示已有数据传输。
  • derived_from计算或证据派生；注明规则与版本。
