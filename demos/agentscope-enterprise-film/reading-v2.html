项目全貌

AgentScope 将推理循环接到会话、执行环境和业务交付。

Python 2.0 与 Java Harness/Service 是两条完整实现路径。旧 Runtime 与 Studio 的职责已归入 Python 2.0。

AgentScope：把 Agent 接成工作系统

合同助手接到任务后，需要读取材料、查规则、形成意见，必要时等待审批，再把文件和结果交回业务应用。模型生成文字只是其中一步。AgentScope 覆盖推理与工具循环，也覆盖托管会话、执行环境和前端事件。

  • Agent决定下一步，调用工具，维护工作上下文。
  • Service接收请求，管理会话，把进展和结果送回应用。
  • Workspace为文件、终端和工具提供执行环境。

产品需求同时涉及推理、执行、状态与交付。

把这些职责分开，PM 才能判断一个功能应该修改提示词、增加工具、调整服务，还是接入业务系统的控制。贯穿本片的合同助手用于解释对象和动作怎样流转。

02

Agent 内核

一次回复由状态检查、模型调用与工具反馈推进。

消息保存完整记录，事件提供实时增量。合法参数、执行权限和运行环境分别约束调用。

Agent 是推理与行动的循环引擎

Agent 执行循环，配置说明它能使用什么，AgentState 说明这次工作到了哪里。新消息进入上下文并开始回复；确认事件或外部结果续接一个暂停中的回复。

  • 配置模型、工具、提示词、权限与中间件。
  • 运行状态上下文、当前消息、工具与暂停信息。
  • 调用入口接收消息或事件，返回结果或等待输入。

连续工作需要保存和恢复正确的运行状态。

Agent 根据状态选择推理、行动、暂停或结束。服务层把同一会话的状态交给正确运行实例，才能在多个请求之间维持连续工作。

机制与条件

为什么需要
跨请求继续工作，需要保存同一会话的上下文、当前回复、权限、工具和任务状态。
怎样工作
AgentState 可序列化为 JSON。等待状态由该 agent 尾部的 assistant Msg 判断：调用为 asking，或已 submitted 但还没有匹配结果。回复 R1 与工具 T1 的身份把确认事件接回原工作。
当前默认与前提
固定 2.0.10dev 源码的 max_iters 默认 50；结构化输出另有 5 轮宽限。序列化的 Schema 不保留进程内自定义 validator 的全部语义。
失败与恢复
匹配结果已经补齐的 submitted 调用不再等待。运行中的旧持久快照不能覆盖 worker 实时状态。

推理与工具结果组成反馈回路

ReAct 的核心是反馈。模型返回工具请求后，Agent 校验并执行；工具结果进入当前消息，下一轮模型据此决定继续或结束。每轮还会处理上下文压缩与运行提示。

  • 检查状态选择推理、行动、暂停或结束。
  • 调用模型发送上下文；无工具请求时形成答复。
  • 执行工具按参数运行可用工具。
  • 接收结果写回消息，再决定下一步。

工具失败也是下一轮推理的输入。

等待人工确认或外部执行时，循环暂停，当前事件流结束而回复尚未完成。后续结果事件到达才续接。超过迭代预算有明确结束状态，普通文本还可进行禁用工具的总结。

Formatter 把内部 Msg 转成供应商请求格式，Model 处理调用、重试、流式返回和用量。流式接口输出增量及最终完整响应，Agent 再转成事件。

工具把模型请求接到真实函数

Toolkit 把 Python 函数、MCP 工具和工具组收成可调用集合。模型看见函数名称、说明和参数 Schema，运行时再次检查工具是否激活并校验输入。ToolChunk 表达进展，ToolResponse 聚合最终结果。

  • 登记函数读取签名、类型与说明。
  • 形成 Schema公开名称和可填参数。
  • 执行调用找到函数，校验并传入参数。
  • 返回结果聚合执行内容，写回消息。

参数校验通过后才进入副作用执行。

未注册工具、未激活工具组或参数不匹配会返回模型可读的错误。业务工具边界应与动作一致，例如查询合同状态、保存候选批注和发布文件，分别配置输入与授权。

机制与条件

为什么需要
模型需要工具说明，界面需要进展，后续推理需要完整结果；三者的对象不同。
怎样工作
Schema 定义可填参数。ToolChunk 逐块输出，ToolResponse 按内容 block ID 聚合；最后以工具调用 ID 写入 ToolResultBlock。
当前默认与前提
文字块追加文本；Base64 数据先还原二进制再合并；URL 数据不能按字符串追加。聚合结果保留已经发生的 error。
失败与恢复
未注册工具、未激活工具组或参数不匹配在副作用前返回错误。后来的 success 不能抹掉前面的 error。

权限判定发生在工具执行前

DEFAULT 模式按 deny、ask、只读快速路径、工具自检、allow 和默认 ASK 等阶段判定。EXPLORE 先检查显式 deny/ask 规则；未命中这些规则的非只读请求才默认拒绝。显式 ask 仍可在人工确认后执行，allow 规则不能改变非只读的默认拒绝。BYPASS 的控制含义不同，需要明确配置。

  • ALLOW继续执行工具。
  • DENY返回拒绝结果，交回推理循环。
  • ASK暂停并发出人工确认事件。

批准关联具体动作与参数。

权限系统决定是否执行，工具审查检查实际输入，沙箱限制运行环境。三个层次共同工作。人工确认应展示具体工具、参数和作用对象，答复要关联等待中的调用。

机制与条件

为什么需要
合法参数只表明请求结构正确，执行权限还要单独判断。
怎样工作
DEFAULT 按 deny → ask → 只读快速路径 → 工具自检 → allow → 默认 ASK 判定。确认结果以嵌套 ToolCallBlock 的身份关联原调用。
当前默认与前提
EXPLORE 未命中显式 deny/ask 的非只读请求会被拒绝；显式 ask 可在用户确认后执行。DONT_ASK 把需要询问的结果转为拒绝，BYPASS 则跳过工具的 safety ASK。
失败与恢复
确认对象或回复身份不匹配不能续接。工具可用性、JSON 和 Schema 的失败先于副作用执行。

上下文与协作

长任务靠可见上下文、可回查材料与明确分工继续。

压缩、offload、memory 与 RAG 处理不同的信息需要；计划、verifier 和 team 组织工作。

模型输入由三层组装

上下文是 Agent 的工作记忆。每轮模型调用组装系统提示、历史摘要和近期消息。系统提示还会经过 on_system_prompt 变换，工具 Schema 取自当前激活集合。

  • 系统提示基础提示、技能说明与中间件变换。
  • 压缩摘要保留较早历史的必要信息。
  • 近期上下文最近消息、结果和运行提示。

上下文决定模型下一步能依据什么。

会随执行变化的时间、任务状态和用量以运行提示注入上下文。讨论回答质量时，应检查必要材料和约束是否进入了本轮输入，而不只分析模型型号。

为什么需要

怎样工作

网络重试必须保留同一个幂等键与请求体，服务会返回原Turn。只有真正的新任务才换键；排队、审批或前一Turn未结束时，后续Turn可能保持等待。 Managed 在同一 Session 保留上下文；Team 和 Workflow 每个 Turn 启动独立协作或流程。

机制与条件

为什么需要
接收任务、开始使用输入和完成任务是不同阶段；重试必须保留原工作身份。
怎样工作
Session 固定目标配置。Turn 用幂等键和相同请求体持久接收；202 queued 表示 accepted，input.applied 表示运行时已经使用输入。等待批准的 Turn 持有队列中的当前位置。
当前默认与前提
Managed 保留会话上下文；Team 和 Workflow 的各个 Turn 启动独立协作或流程。修改 Agent 不自动改变既有 Session。
失败与恢复
刷新应读原快照与事件；新的幂等键会创建新任务，不能用于修复一次观察断线。
