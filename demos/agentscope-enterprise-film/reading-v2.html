AgentScope 接成企业工作系统

业务任务 → 运行机制 → 服务交付

合同助手接到任务后，需要读取材料、查规则、形成意见，必要时等待审批，再把文件和结果交回业务应用。AgentScope 把推理与工具循环，接到托管会话、执行环境和前端事件。

  • Agent决定下一步，调用工具，维护工作上下文。
  • Service接收请求，管理会话，把进展和结果送回应用。
  • Workspace为文件、终端和工具提供执行环境。

产品需求同时涉及推理、执行、状态与交付。

模型与提示词决定推理输入，工具连接业务动作，Service 管理请求和状态，Workspace 提供执行环境。一个功能跨越哪些职责，决定它需要哪些接口与控制。

Agent 是推理与行动的循环引擎

配置定义能力；AgentState 保存跨请求的工作状态

Agent 执行推理与行动循环。配置说明它能使用什么，AgentState 保存这次工作到了哪里；新消息开始回复，确认事件或外部结果续接暂停中的回复。

  • 配置模型、工具、提示词、权限与中间件。
  • 运行状态上下文、当前消息、工具与暂停信息。
  • 调用入口接收消息或事件，返回结果或等待输入。

等待由尾部同一 Agent 的调用与结果共同判定。

实现与条件

AgentState 可序列化为 JSON，保存摘要、上下文、当前 reply、权限、工具、任务和中间件状态。ReplyContext 还保留 reply_id、当前迭代数和结构化输出要求。

等待判定只查看该 Agent 写出的尾部 assistant Msg：调用处于 ASKING，或处于 SUBMITTED 且没有同 ID 的 ToolResultBlock。匹配结果已存在的 SUBMITTED 调用不再等待；其他 Agent 的观察消息也不能据此判定本 Agent 等待。

结构化 Schema 在进程内可以是 Pydantic class，保存时变成 JSON Schema；恢复后的字段结构不能代表原自定义 validator 和 default factory 全部随之恢复。

推理与工具结果组成反馈回路

下一步由当前消息和工具状态决定

ReAct 的核心是反馈。模型返回工具请求后，Agent 校验并执行；工具结果进入当前消息，下一轮模型据此决定继续或结束。每轮还会处理上下文压缩与运行提示。

  • 检查状态选择推理、行动、暂停或结束。
  • 调用模型发送上下文，读取答复与工具请求。
  • 执行与回灌校验、执行，结果写回同一回复。
  • 迭代预算默认 50 轮；普通文本超限做无工具总结。

权限拒绝与工具失败仍可进入下一轮推理。

等待人工确认或外部执行时，循环暂停，当前事件流结束而回复尚未完成。后续结果事件到达才续接。超过迭代预算有明确结束状态，普通文本还可进行禁用工具的总结。

实现与条件

固定 2.0.10dev 的 max_iters 默认 50，约束一次 reply 的 reasoning–acting 迭代。普通文本到上限后有一次禁用工具的总结；这不是 Service 任务的统一时限，也不是固定的模型请求次数。

默认 stop_on_reject=False，拒绝结果仍可交回推理循环。等待人工确认或外部结果则暂停当前事件流，后续事件续接同一 reply。

权限判定发生在工具执行前

DEFAULT：deny → ask → 只读 → 工具自检 → allow → ASK

DEFAULT 模式按 deny、ask、只读快速路径、工具自检、allow 和默认 ASK 等阶段判定。EXPLORE 先检查显式 deny/ask 规则；未命中这些规则的非只读请求才默认拒绝。显式 ask 仍可在人工确认后执行，allow 规则不能改变非只读的默认拒绝。BYPASS 的控制含义不同，需要明确配置。

  • ALLOW继续执行工具。
  • DENY返回拒绝结果，交回推理循环。
  • ASK暂停并发出人工确认事件。

EXPLORE 的显式 ASK 可逐次确认执行。

权限系统决定是否执行，工具审查检查实际输入，沙箱限制运行环境。三个层次共同工作。人工确认应展示具体工具、参数和作用对象，答复要关联等待中的调用。

实现与条件

DEFAULT 的第一个决定性结果生效：deny 规则、ask 规则、按本次输入判断的只读快速路径、工具自检、allow 规则，最后兜底 ASK。工具自检产生的 safety ASK 不被后面的 allow 覆盖。

EXPLORE 先保留 deny 与显式 ask，再判断只读；它跳过工具自检和 allow，剩余非只读调用才兜底 DENY。合法待确认调用经 confirmed=True 可进入本次执行；后续调用仍重新按模式判定。

DONT_ASK 把需要询问的结果转为拒绝，适用于没有确认者的运行。BYPASS 跳过工具 safety ASK，但显式 deny/ask 和工具 DENY 仍生效；运行环境的权限和沙箱边界另行约束执行。

人工确认把暂停接回执行

确认事件关联待执行调用和用户答复

ASK 将工具调用改为 ASKING，并发出 RequireUserConfirmEvent。当前事件流结束，reply 尚未完成；调用方保存状态并展示实际工具、参数与作用对象，随后用确认事件续接。

  • 待确认调用保存工具名称、参数与调用 ID。
  • 暂停回复ASKING 发出确认请求；reply 尚未完成。
  • 匹配答复reply_id 与嵌套 tool_call.id 对应原对象。
  • 单次继续confirmed=True 放行；False 返回拒绝。

确认界面呈现实际批准的工具、参数与对象。

外部执行走另一条交接：external 工具发出执行请求，外部完成后带回结果。输入确认、执行结果和最终消息分别关联原调用。

实现与条件

Webhook 的至少一次投递允许同一事件重试。接收方按事件身份合并通知并保存处理结果；接收确认说明通知处理到了相应阶段，业务事务另有结果。

  • 发出事件运行产生带身份的通知。
  • 接收投递同一事件可能重复到达。
  • 身份去重接收方合并同一事件。
  • 业务处理副作用使用自己的幂等契约。

通知已接收与业务事务完成分别核对。

实现与条件

接收顺序是验证原始请求体签名与时间，持久化通知，再按事件身份去重。事件触发的下游写入使用自己的幂等键和回执查询；通知处理结果与业务动作结果分别保存。
