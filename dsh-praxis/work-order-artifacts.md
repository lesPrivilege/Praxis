# 下一轮工单：把整合包接到产物取用

状态：2026-10-25 已按本工单施工，裁决见 [ADR-039](../docs/decisions/039-dsh-praxis-artifacts.md)，结果与逐项采用情况见 [回执](../docs/verification/dsh-praxis-artifacts-20261025.md)；DSH 桌面实测待做。设计理由见 [架构参考](architecture.md)。

## 目标与完成体验

在 DSH 中完成一次小任务后，Agent 主动登记产物与实际依据；人可以从 Praxis 找到它、预览并 review 具体版本，再直接取出文件；另一个 MCP/CLI 消费者能读到相同记录。修订后，新旧版本与 review 的关系仍然清楚。

首个场景建议为一份简短技术说明：合成来源 → MD 底稿 → HTML 交付件 → 一次 review → 修订版。用它验证实际需要的数据与动作，不先铺设全部媒介的生产引擎。worker 可以选择更能验证同一目标的有界场景并说明理由。

## 建议执行切片

### 1. 收敛当前基线与宿主可行性

复核备份覆盖、预设冲突、跨入口错误语义、来源变化追踪、历史内容与 review 版本。只处理尚未解决且影响本轮的项。用最小合成文件尝试 DSH 预览及原生拖出，尽早知道插件能承担什么。

补充基线见 [DSH 调用方反馈与核对](../docs/verification/dsh-praxis-acceptance-20261025.md#补充dsh-调用方反馈与只读核对)：`535dd67` 已含前轮修复，另发现原生工具返回的嵌套 `undefined` 与 DSH 无损 JSON 契约不兼容。先检查 upkeep/stale 及其他可选字段的原始结果，不能以 CLI 能 stringify 代替 DSH 验证。预设为空视为未配置，不为消除空列表写入虚构 provider 或密钥设置。

输出一段有证据的裁决：保留哪些现有结构、真实缺口是什么、首轮采用哪些文件类型、拖出如何实现或为何受阻。不要把“需要新增一个表”当作产品需求。

### 2. 让产物登记可被各入口消费

在已有 consume/run 上选择最小扩展，使 Agent 能登记产物与版本、查询并回查依据；重复提交同一次产出不应无意义地生成多个作品。既有 run 中的产物可被发现，缺少的信息保持未知。

具体工具名称、独立 artifact 表与否、版本保留方案由 worker 裁决。所有新增写入遵守共同校验与冲突语义，MCP/CLI 和 UI 不各维护一份记录。

### 3. 在 DSH 完成发现、review 与取用

给产物一个直接可达的入口。让人看见名称、用途、版本和可执行动作，进入后能看内容及依据，review 绑定所见版本。优先复用宿主预览与打开能力；列表、卡片、详情面板或其他布局由实际数量和操作决定。

实现直接取用并做桌面验证。界面缓存不能让人把对旧内容的判断记录到新版本；文件丢失应明确显示，重新定位不得悄悄替换历史内容。日常阅读不必先理解 catalog、hash 或底层目录结构。

### 4. 用同一任务完成修订与恢复检查

对首份产物提出一次具体修改，生成新版本并登记，确认旧 review 和旧依据可回查；来源变化时找出受影响产物。用隔离工作区恢复一次备份，检查产物记录、关系和声明纳入的文件，而不只检查归档 hash。

完善安装与数据根说明。个人使用可继续依赖完整 checkout；如果独立包不是必要条件，写清前提即可，不为形式上的自包含扩大实现。

## 验收场景

这些是建议用于判断目标的可观察场景。Opus 可调整技术验证方法；删减或延后场景时，要说明未交付的用户能力与理由。

| 场景 | 通过时应观察到 |
|---|---|
| Agent 交付并登记 | 同一次交付有可见登记结果；来源关系来自实际取用，记录失败能被发现 |
| 从控制面找产物 | 无需进入 Finder 搜索目录，能找到并预览约定类型的交付件 |
| Review 后修订 | review 清楚指向 v1；v2 出现后不继承“v1 已通过”的含义，旧依据仍可读 |
| 从桌面拖出 | 目标应用收到所选版本的真实文件并可用；若受阻则此项未通过，另报告已验证替代方式 |
| MCP/CLI 共数据 | 一端登记或 review 后另一端可读到同一身份与版本；查询失败不返回成功状态 |
| DSH 原生返回值 | 无待办、有 stale 但无 preset、预设变更等结果均满足宿主无损 JSON 契约；不仅能经 JSON.stringify 输出，原生工具也可正常消费 |
| 重复登记与并行修改 | 重试没有重复作品；过期写入不会覆盖新内容或产生部分修改 |
| 来源变更与文件搬移 | 能区分“依据更新”和“文件找不到”，定位受影响交付；重新绑定不伪造旧版本 |
| 隔离恢复 | 记录、版本关系和备份声明内的文件可恢复；不在包内的外部文件有明确缺口 |
| 隐私与既有内容 | 合成夹具足以验收；个人图片、Chat 原文和私有文件未进入仓库；旧 catalog 和 Kit 仍可使用 |

开工及结束均根据需要运行窄测试；功能有变化时运行相关 core/adapter 检查与验收探针。交付前运行 `python3 scripts/validate_repository.py`。桌面、真实 Agent 工作和隔离夹具的证据分开报告，未跑的项目写明未跑。

## 交付与最后裁决

交付应包含可用实现、必要迁移/兼容说明、使用入口和一份验收回执。回执记录实际基线、覆盖与未覆盖项，并逐项说明本文建议的采用、替换或延后，保留重要理由即可，不要求额外治理矩阵。

Opus worker 拥有最后实现与设计裁决权，包括 scope 拆分、对象结构、保存位置、工具形态、界面和取用方式。以现状和用户期待判断，不以还原旧 Chat 方案为目标。若目标暂时只能部分完成，应说明已可用的闭环、明确阻碍与后续动作，不将未验证能力标成完成。

本工单根据现有实现、已执行验收和本轮用户明确的产品方向整理。只提炼理念与设计，不保存补充 Chat 的原文、图片、附件或个人细节；没有把未读取的助手正文或图片内容当作设计依据。未新增外部来源核验或依赖快照。
