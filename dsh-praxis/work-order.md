# 下一轮工单：自用跑通，再拆出 release

状态：2026-10-25 编制；四项决定已确认。A2 按用户改定的做法施工（管线登记为来源，[ADR-043](../docs/decisions/043-dsh-praxis-pipelines-as-sources.md)）；A4 除集合类来源的增减淘汰外已施工（[ADR-042](../docs/decisions/042-dsh-praxis-upstream-checks.md)，[回执](../docs/verification/dsh-praxis-pipelines-roster-20261025.md)）。A1 已施工，例外已按用户指示处理（[ADR-041](../docs/decisions/041-dsh-praxis-projects.md)，[回执](../docs/verification/dsh-praxis-projects-20261025.md)）。上一轮的产物工单见 [work-order-artifacts](work-order-artifacts.md)，来源闭环见 [ADR-040](../docs/decisions/040-dsh-praxis-source-loop.md)。

## 目标与完成体验

**自用。** 在这个仓库里，Praxis 管住三类事：
- **每件工作的最终产物：** 底稿 md、html、视频，按项目分开，可预览，可按版本 review，能回查依据；
- **来源名册：** 每条来源说得清为何收录、服务哪些任务、谁读过；
- **DSH worker 的消费：** 不经人提示，worker 自己按任务取用 Kit 单元与来源，交付时记下读过什么、产物在哪。

**release。** 一个新用户装上插件，交给一个 fresh agent 和一个空目录：
1. 补几条必要的来源，agent 就能比较完整地完成一件 design 或 reporting 任务；
2. 中间产物与最终产物落在约定位置，最终产物由控制面登记管理，目录不会越堆越乱；
3. 人在 DSH 的 UI 里管理来源、产物与管线，其他 agent 经 MCP 和命令行用同一份数据、同样的渐进披露；
4. 用的过程中，upkeep 能提出对来源或 Kit 的修订（RSI）。

先做自用，再拆 release。拆分时自用不中断：这个仓库以“仓库模式”接入同一个包。

## 设计原则：登记链接，不收录正文

这是 Praxis 从一开始的特点，各切片都按它取舍：

- **名册登记的是链接。** 原件的形式多种多样：skill、design.md、文章、作品收集网站、组件库、动画库等，大多公开在互联网上。每条来源记：
  - 原件在哪：URL，或本地路径、档案号等定位；
  - 入账时写明的功效与推荐何时用；
  - 读的是哪里：摘录的定位与它支持的说法；
  - 为何收录、挂在哪些页面、谁读过。

  不收录原件全文。
- **用时直接打开。** agent 和人需要时，按链接与定位回到原件取用。网页由 agent 抓取或打开；本地文件交给 DSH 预览或系统应用。
- **经渐进目录找到。** 入口 → 层 → 单元 → 挂在单元上的来源（功效与何时用）→ 原件，逐级展开。是否打开原件由模型按任务决定。不需要安装 skill，也不预载全部内容。
- **消费过的留本地记录。** 运行记下读了哪条来源、读到哪里，并关联到这次会话的记录。agent 打开原件时读到的正文在会话记录里，之后照样可用；更精确的维护与 RSI 以这些记录为依据。
- **长期维护的是链接与关系，随上游同步。** 维护对象包括：
  - 链接是否还在、内容是否变了；上游新增或下线的条目随之增减，过时的淘汰；
  - 挂在哪页、对这页有什么用；
  - 读过它的运行与产物。

  快照只在需要固定版本时取，例如原件可能失效，或要核对变化。
- **Kit 正文不引外部材料。** 正文讲方法；来源经关系由名册披露。这在 release 里是硬条件：包里的 Kit 不能链到包外。

## A. 自用

### A1. 项目对象与产物治理

**项目**是一个目录，带用途和一个结构模板。模板先给一种，取现有项目的共同做法：
- 底稿：`draft/`
- 中间产物：`build/`
- 最终产物：`out/` 或 `site/`

规则：
- 产物按“项目 + 相对路径”记录；
- consume 要带项目，最终产物必须落在模板约定的位置，或明确指名；
- 这就是“要求 agent 记录逻辑对象的位置”：位置是登记的一部分，不是事后去找。

upkeep 只增加两类信号：
- 最终产物目录里有没登记的文件；
- 登记的产物落在约定之外。

中间产物的数量、大小不进清单。

试点：`jev/`、`palantir/reading-list-series/`、`dsh-praxis-explainer/`。三者现有结构不同，先看模板能否不改文件就套上；套不上的地方记成模板的选项，不为单个项目加特例。

完成标志：
- 三个项目已登记，控制面按项目列出最终产物；
- 至少一条违例被发现并由人处理；
- 旧的仓库相对产物按项目重新归属，不改版本与 review。

### A2. 管线进 Publish 层

管线是 Publish 层的一个单元，加一个可执行的工具：
- 输入是底稿与预设；
- 输出登记为产物，带 `derived_from` 指向底稿的版本。

范围：
- **html：** 底稿 md → html，先做一份简短技术说明。
- **video：** 从现有项目的脚本里收拢一条最短的可用链（底稿 → 配音 → 合成），由预设驱动。密钥只记环境变量名，执行前检查依赖是否存在，不自动安装。

注意：DSH 的文档预览不含视频。视频的预览与 review 路径要先实测，不通时用“打开”交给系统播放器。

完成标志：
- 一份 md → html 与一段短视频都经管线产出并登记，派生链可回查；
- 控制面里能按版本 review；
- 改底稿再跑，产出新版本，旧 review 不继承。

### A3. DSH worker 自主消费

装载方式（宿主能力已由只读调研核对）：
- 不装 skill。系统提示里只留一段短入口，作为渐进目录的根：有哪些层与任务类型、先 resolve 再按需展开。
- 加 `/praxis` 宿主命令，给人一个显式入口；
- agent 默认可见的工具收窄到取用路径（entry、resolve、unit、source、capture、curate、consume，约 5.6k 字符），维护类工具留在命令行与控制面；
- `praxis_resolve` 与 `praxis_consume` 在会话里显示为卡片，可一键打开对应单元或产物。

验收用真实任务做对照：同一件 html 任务，一次在有素材的 DSH 会话里做，一次不用素材，记录：
- worker 是否自己调用了 resolve；
- 是否按摘录定位回到原件；
- consume 是否记下读过的来源；
- 交付里是否用上了，两份的差别在哪。

agent 打开原件是按链接与定位去读，不是读 Praxis 存下的正文。consume 记下读过的来源与读到的位置，并带上会话标识（DSH 会话、MCP 客户端会话），让读到的正文能从会话记录里找回。回执里记下它实际打开了哪些链接。

完成标志：在一个 fresh DSH 会话里，没有人提到 Praxis，worker 完成上面的取用与登记；对照结果写进回执。

### A4. 名册维护

- **挂载说明按位置写：**（已施工：Design 108 条。）先改 Design 的 78 条，写清这个来源对这一页有什么用；用 [审阅方法](kit/writing/review.md)检查，不抄概要。
- **与上游同步：** 失效的链接、内容已变的来源进 upkeep；集合类来源（作品集、组件库、动画库）的上游增减时，提出增补或淘汰，由人或 agent 处理，带理由记进 history。（失效与内容变化已施工；集合类来源的增减淘汰待做。）
- **refresh 只判断变化：** 默认只记内容 hash、状态与时间，用来发现链接失效或内容变化，不存正文；需要固定版本时才存快照。先覆盖被运行读过、或挂在常驻与任务类型单元上的来源。（已施工，见 ADR-042；被任务类型取到的 11 个来源已检查。）
- **写回不重排：** curate 写回 JSON 时保持原有排版，只改动到的字段。（已施工，与 refresh 一并见 [ADR-042](../docs/decisions/042-dsh-praxis-upstream-checks.md)。）

完成标志：
- Design 挂载说明不再与来源概要相同；
- 常用来源能报出“链接失效”或“内容已变”；
- curate 的 diff 只含改动到的字段。

## B. release 拆分

在 A 完成、自用稳定之后开工。

### B1. 数据目录与仓库模式

一个配置决定数据根：
- 默认在插件自己的数据目录，DSH、MCP、命令行共用；
- 仓库模式指回 `dsh-praxis/data` 与 vault。

core 不再调用仓库里的 Python 脚本，所有路径经同一处解析。

### B2. 名册自有存储与预设分类

来源名册改为 Praxis 自己的存储，存链接、定位、摘录说法与关系，不存正文；按预设的分类目录组织（按层与领域，与 Kit 的层对应）：
- fresh 安装得到空名册和建好的目录；
- 这个仓库的 vault 用 [ADR-040](../docs/decisions/040-dsh-praxis-source-loop.md) 的按引用登记机制作为来源包接入，vault 结构与 `build_registry.py` 留在仓库这一侧。

### B3. 基础 Kit 自足

包内 Kit 正文不链到包外：
- 正文对来源卡的引用改为关系，由名册披露；
- 对 ADR 与 docs 的引用，把理由收进单元正文，或删去；
- demos 里的样例按本地定位登记为来源，组成可选的来源包，不复制进包。

validator 为包内 Kit 加一条规则：没有包外链接。

### B4. 用户覆盖层与 RSI

用户与 agent 对 Kit 单元的修订存进数据层的覆盖层，带依据的范例与 history；包升级时，有冲突的修订进 upkeep。RSI 的边界写进 [Kit 使用约定](../kit/Agent.md)对应位置：agent 自主改的是数据层，包内 Kit 随版本更新。

### B5. 其他 agent 的封装

MCP 增加 resources 与 prompts，做渐进披露：
- **resources：** 渐进目录本身：入口、层、单元、来源条目（链接与定位，不含原件正文）、产物；
- **prompts：** 按任务类型的入口；
- **instructions：** 交代顺序。

命令行读写同一份数据，可用 `npx` 起服务。

### B6. fresh 目录走查，作为 release 的回归测试

脚本化：
1. 新 profile 安装插件；
2. fresh agent 在空目录里做一件 design 或 reporting 任务；
3. 补两三条来源；
4. 检查：
   - 最终产物已登记；
   - 中间产物在约定位置；
   - 运行记下了单元与来源；
   - upkeep 提出至少一条修订。

只用合成材料，个人数据不进包。

### B7. 打包

确定包的内容与版本，写安装说明。发布与创建远端由用户执行。

## 顺序与依赖

- **A 内部：** A1 先于 A2，管线产物要按项目登记；A3、A4 与 A1 互不依赖，可以并行，但改到同一批文件时由一个 worker 负责。
- **B 内部：** B1 → B2 → B3 依次进行；B4、B5 在 B1 之后；B6 最后，B7 在 B6 通过之后。

## 约束

- 交付前运行 `python3 scripts/validate_repository.py`。
- 新目录有 README。
- 不自动安装依赖，不发布，不建远端。
- 不保留兼容层，旧路径改完即删。
- 维护清单只列需要人处理的例外。
- 写给读者的文字遵守 [成文原理](kit/writing/principles.md)，领域术语保持英文原形。
- 每个切片一份回执：写明实际基线、验证方式、未验证项。
- 桌面实测与真实 agent 任务的证据，和隔离夹具的证据分开报告。
- 插件代码改后，DSH 要重启才加载；测前先看 `praxis_entry` 是否带 `reload`。
