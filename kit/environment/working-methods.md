# 工作开展方式 · 备用素材

状态：备用素材，取用优先级 normal。不是规则，不是 skill，不默认加载。碰到下表左栏的情形时可以取用，取了什么、结果如何记回项目自己的 index。

来路：2026-10-02 对十个社区 skill 与 prompt 样本的研究。留下的是换了工具和模型仍然成立的判断，原包没有安装，原文没有保存。五条里四条的来源由主会话按固定提交回读过，一条没有读。除标明的以外都没有实测。

| 碰到什么 | 取哪一条 | 状态 |

| 把研究或核对交给别人去做 | [让对方交回证据不支持什么](#把研究交出去) | 真实任务一次，没有对照 |

## 一批动作做到一半

把每一项分成三类：已经成立，没有成立，不知道。依据是外部系统里现在的状态，不是运行日志和工具的回报。不知道的那些先查，不当作没执行。只补没有成立的那一步，已经成立的不重放。后面的动作依赖前面的结果时，先确认前面的。

停下找人：查到的状态和日志对不上并且解释不了；同一个不可撤回的动作已经发生了两次；没有权限的项不靠重试或换账号解决。

不该用：只读、可以整份重做、对外没有影响的任务，直接重跑并核对结果。

定义与反例在 [共同工作语法](../grammar/work.md#不变量与反例)的“外部动作结果未知”一行，契约字段在 [工作契约](../contracts/README.md)的失败与恢复。这一条比它们多的是“部分成功”这一格和项与项之间的依赖。

## 原因不明时

先拿到现象和边界上的证据，再提一条假设，并写下什么结果会推翻它。只做最小的、能撤回的改动去验。支持才修，修完复验；不支持就回去查，不在失败的改动上再叠一个。接连几次都没有得到新信息时停下，把判断交给人。

不该用：损失正在扩大的事故，按已授权的做法先回滚或隔离，根因之后再查；原因已知、范围很小、可以撤回的修正。

陌生领域也适用：客户说“报价慢”，“慢在等客户补型号”是一条假设，推翻它的结果是“不缺信息的询价同样慢”，最小的验证是看二十份询价的耗时，不是先做一个助手。

## 要说一条规则有用

留一个对照：同一份任务书给不读这条规则的执行者，或给读改动前版本的执行者。两边都做到的部分不记在规则名下。

留一个没参与调整的任务：改措辞时反复用过的任务只说明改到了什么。措辞改定之后，用留出的那一个只跑一次。

产出和代价一起看：多读了什么，多花了多少，有没有被带进用不着的流程。两边都能通过的检查项不算证据。

对照已经全部做到时，这条规则对这类执行者拿不出作用，不因此写成规则；它若是给人看的契约，或给更弱的执行者用，另写理由。样本小的时候只用来筛掉坏方案，不说普遍有效。

不该用：改错字、改链接、登记来源。做不到独立上下文时记“未对照”，不说有效。

## 分给几支再汇总

每一支交回时带上它是怎样结束的：正常完成，预算或时间用尽，执行失败。汇总时三种不合并，没有正常结束的不算进“已覆盖”。失败的那一支按权限有限地重试，重试不了就在结果里写明缺了哪一块。

不该用：把权限或安全上的拒绝当成可以重试的失败。

本仓库的交接项见 [Kit 使用约定](../Agent.md)的分工一节，回执字段见 [使用与额度登记](agent-usage.md)。

## 检查通过之后

动手前先存原件。交付后分开查看得见的呈现、结构、与原件的差异。该有的痕迹没有出现，本身就要查。说“通过”时写明检查看了哪一部分，没看的部分不算通过。

按输出逐项要核对什么，见 [内容验收](../write/shared/verification.md)。

## 把研究交出去

把自己记得、还没有核对的说法逐条列给对方，标明是待核对的。请对方交回三样：每条说法的出处和读到的范围；证据不支持什么；哪些话可以说、哪些不能说。写稿时以最后一样为界。

不该用：查一个已知位置的事实，自己去看更快。

## 自查通过之后

对外交付之前，请一位没有参与制作的人按交付要求再查一遍。复查稿分开列出查过且一致的、有问题的、没能查的。任务书里划出去不查的部分，交付前要么补查，要么写明没有查。

不该用：内部草稿、可以随时改的材料；找不到独立上下文时记“未复查”，不说通过。

## 感知不到的部分

制作方听不了声音、看不了实际播放，或打不开目标设备时，先找能量出来的量，例如响度、音高走势、文字与时间戳的覆盖、帧与帧的差异。交付时写明量了什么、量不到什么、哪一部分只能由人来看和听。量出来的数正常，不等于那一部分没有问题。

不该用：有人能直接看和听的时候，用测量代替他们。

这三条来自一条知识片的制作，过程和证据见 [过程重建](../../vault/distilled/knowledge-film-001-distill-20261005/README.md)。只有一次制作、同一名主笔。

## 从外面拿一条做法之前

一条外部的 skill 或 prompt 先拆成四层：

| 层 | 是什么 | 怎样处理 |
|---|---|---|
| 稳定判断 | 什么时候需要这一步，它保住什么，什么反馈会改变下一步 | 留下 |
| 局部实现 | 接口、工具、格式、目录、模型和权限的约定 | 留在可替换的适配层，不进这一页 |
| 能力补丁 | 为某个模型的某种失误加的反复提醒或格式约束 | 没有版本对照或实验时标“待验证”，不说它过时 |
| 作者选择 | 语气、固定字数、展示结构、方法偏好 | 先分清是规则、默认还是风格取舍 |

留下的那一层要写得出“在什么条件下，依据什么证据，做什么；看到什么之后继续、恢复、停止或交给人”。“先想、再做、再检查”这样的话没法用反例检验，不留。

强制的措辞不一定是旧模型的补丁，也可能在保一条真的业务约束。一个上游项目把论证删到只剩一行标签之后，压力情形下的遵循从十次里八次降到五次，普通情形不变；这是维护者报告的小样本，本仓库没有复跑。删短一条规则之前先看压力情形。
