class="blog-post-title">Can Jev Make SRE Agents More Reliable?</h1><p class="blog-muted mt-6 max-w-3xl text-lg leading-relaxed font-semibold sm:text-xl">We tested TypeSafe AI&#x27;s Jev as a decision layer for SRE agents.</p><p class="blog-byline"><span class="blog-muted">By </span><span><a href="https://hacksonclark.github.io/">Jackson Clark</a></span><span><span class="blog-muted">, </span><a href="https://saadmrp1038.github.io/">Saad Mohammad Rafid Pial</a></span><span><span class="blog-muted">, </span><a href="https://yimingsu01.github.io/">Yiming Su</a></span><span><span class="blog-muted">, </span><a href="https://tianyin.github.io/">Tianyin Xu</a></span></p></header><div class="blog-article-grid "><div class="min-w-0"><div class="blog-article-cover"><img src="/blog/jev/cover.svg" alt="The agent investigates and repairs; Jev ranks and reviews. Pass rate: 40% without Jev, 48% with Jev." width="760" height="500"/></div><details class="blog-mobile-contents"><summary>In this article</summary><ol class="blog-contents-list"><li><a href="#how-we-integrated-jev"><span aria-hidden="true">01</span>How we integrated Jev</a></li><li><a href="#results"><span aria-hidden="true">02</span>Results<!-- --></a></li><li><a href="#where-jev-helped"><span aria-hidden="true">03</span>Where Jev helped</a></li><li><a href="#where-jev-failed"><span aria-hidden="true">04</span>Where Jev failed</a></li><li><a href="#future-work"><span aria-hidden="true">05</span>Future Work</a></li><li><a href="#summary"><span aria-hidden="true">06</span>Summary</a></li></ol></details><article class="blog-prose prose max-w-none min-w-0"><p><a href="https://typesafe.ai/blog/introducing-system-one-models-and-jev" rel="noreferrer noopener" target="_blank">Jev has been getting a lot of attention</a> for its speed and strong performance on structured decision tasks. It is TypeSafe AI&#x27;s first System One Model, a small decision model built to make fast, focused judgments over supplied context. Instead of asking a large model to reason through everything from scratch, Jev can quickly compare choices, score evidence, or answer targeted questions.</p>
<p>We wonder what this new capability could do for Site Reliability Engineering (SRE). Incident response is a long sequence of small decisions: what to inspect next, which evidence to trust, which explanation best fits, and when it is safe to act. Live systems also produce plenty of plausible distractions (noises), from stale errors to noisy telemetry. A lightweight classifier could help an agent choose more informative diagnostic actions and behave more consistently without replacing the agent or operating the cluster itself.</p>
<p>We integrated Jev into <a href="https://github.com/SREGym/SREGym" rel="noreferrer noopener" target="_blank">SREGym</a> (our SOTA SRE benchmark) as a decision-support tool available to the agent during an incident. We then evaluated Jev using the Codex harness with <code>gpt-5.6-luna</code> across 10 <a href="https://github.com/SREGym/SREGym/blob/main/docs/SREGym-Lite.md" rel="noreferrer noopener" target="_blank">SREGym-Lite</a> problems (a problem may compose multiple faults). Our main metric is reliability – if an agent solves an incident three times out of five, can access to Jev help it get closer to five?</p>
<p><strong>The Jev-assisted agent passed 24/50 attempts, compared with 20/50 without Jev, improving from 40% to 48%.</strong> The trajectories show both where Jev improved reliability and where the current design still fell short. This experiment measured pass rate rather than time-to-diagnosis, so faster diagnosis remains a hypothesis for future evaluation.</p>
<h2 class="flex scroll-m-28 flex-row items-center gap-2" id="how-we-integrated-jev"><a data-card="" href="#how-we-integrated-jev" class="peer">How we integrated Jev</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h2>
<p>Jev helps the agent choose tests and review its conclusions. The agent still runs the tests and makes repairs. We exposed two tools:</p>
<ul>
<li><strong><code>jev_plan</code> — choose tests.</strong> The agent proposes three to five competing hypotheses and a read-only test for each. The tool adds a fresh, bounded snapshot of the namespace, then uses Jev Choice and Score questions to rank the proposed tests. It did not run those tests or reveal the benchmark answer; the agent still has to execute them and interpret the output.</li>
<li><strong><code>jev_submit</code> — review results.</strong> Jev reviews the evidence before submitting a diagnosis or mitigation result to the grader. A diagnosis needs evidence for the causal mechanism and a current application failure. A mitigation needs evidence that the applied repair addresses the cause, restored functionality, and appeared durable.</li>
</ul>
<p>The submission gate asks Jev to vote twice per attempt: once before diagnosis and once before mitigation. <strong>Every required question has to reach a probability of <code>0.70</code></strong>. If a review rejects a submission, the agent has to call jev_plan again and gather new evidence rather than merely rewording the same claim.</p>

<p>We ran five attempts per problem in each condition. Both conditions used <code>gpt-5.6-luna</code> with the Codex harness.</p>

<p><strong>These results are encouraging for a first experiment.</strong> Jev improved SRE agents in three problems that passed intermittently: the request-filter problem rose from 2/5 to 4/5, network-policy from 1/5 to 2/5, and DNS-policy from 3/5 to 4/5. It also turned the internal-traffic-policy problem from 0/5 into 3/5.</p>
<p>Five attempts per problem are not enough to claim a general eight-point improvement, and two problems did regress. But the current integration asks Jev for help at only a few fixed points and does not yet use repeated voting, continuous action guidance, or prospective safety checks. <strong>We believe those extensions could increase these scores substantially and make the gains more consistent across incidents.</strong></p>
<h2 class="flex scroll-m-28 flex-row items-center gap-2" id="where-jev-helped"><a data-card="" href="#where-jev-helped" class="peer">Where Jev helped</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h2>
<p>The largest gain came from <code>internal_traffic_policy_local_astronomy_shop</code>, which improved from 0/5 to 3/5. The problem misconfigures <code>internalTrafficPolicy</code> to be <code>Local</code> on the <code>recommendation</code> Service while its only endpoint and the frontend pod run on different nodes. Both pods appeared Ready, but the frontend could not reach recommendation through the Service.</p>
<p>Baseline agents repeatedly followed nearby distractions, including OpenTelemetry errors and unrelated workloads. With Jev’s assistance, the agent blamed the frontend listener – the review agreed that an active failure existed but rejected the causal explanation. Further testing connected frontend timeouts to the Service&#x27;s traffic policy and the cross-node endpoint placement. The agent then changed <code>Local</code> to <code>Cluster</code> and restored the request path.</p>
<p>Jev helped for the same reason on <code>edge_request_filter_cpu_saturation</code>, which improved from 2/5 to 4/5: more runs connected the adversarial request, CPU saturation, and the catastrophic-backtracking regex before editing the filter. <strong>In both problems, the main challenge was distinguishing a causal mechanism from believable noise.</strong></p>
<h2 class="flex scroll-m-28 flex-row items-center gap-2" id="where-jev-failed"><a data-card="" href="#where-jev-failed" class="peer">Where Jev failed</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h2>
<h3 class="flex scroll-m-28 flex-row items-center gap-2" id="recovery-was-mistaken-for-a-durable-repair"><a data-card="" href="#recovery-was-mistaken-for-a-durable-repair" class="peer">Recovery was mistaken for a durable repair.</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h3>
<p>On <code>namespace_memory_limit</code>, agents restored Search by adding memory declarations to the rejected workload but left the namespace-wide quota in place, so another unconfigured pod could still fail admission. On <code>rolling_update_misconfigured_social_network</code>, agents restored three Ready replicas but left <code>maxUnavailable: 100%</code> and <code>maxSurge: 0</code>, allowing a future rollout to reduce availability to zero. Secret rotation exposed the same gap: some runs restored requests by changing the database role or rewriting the Secret, but the benchmark required preserving the rotation and keeping the old credential invalid.</p>
<p>In each case, Jev accepted evidence of current functionality without fully testing the invariant that made the repair durable and correct.</p>
<h3 class="flex scroll-m-28 flex-row items-center gap-2" id="jev-could-not-rescue-a-missing-hypothesis"><a data-card="" href="#jev-could-not-rescue-a-missing-hypothesis" class="peer">Jev could not rescue a missing hypothesis.</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h3>
<p>On <code>service_wrong_pod_selection_hotel_reservation</code>, several runs pursued MongoDB or tracing issues without testing the faulty Service selector. On <code>duplicate_pvc_mounts_social_network</code>, some runs focused on telemetry or application data instead of the conflict among multiple replicas, a ReadWriteOnce volume, and cross-node placement.</p>
<p>If the correct explanation and test never enter the candidate set, ranking the available options cannot recover them.</p>
<h2 class="flex scroll-m-28 flex-row items-center gap-2" id="future-work"><a data-card="" href="#future-work" class="peer">Future Work</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h2>
<p>Our current design uses Jev at a few explicit gates. A more ambitious integration would move it earlier and more continuously into the action space: ask Jev three to five times and aggregate the votes, or ask after each tool call which diagnostic action would be most informative next. That could test whether action classification actually shortens diagnosis, rather than only improving the final answer.</p>
<p><strong>We also want to evaluate Jev as a prospective safety reviewer for mitigation actions.</strong> Before the agent changes a workload, Jev could assess blast radius, reversibility, and threatened invariants. We have not run that experiment. A safety experiment would need explicit unsafe-action labels and controlled measurements, not an inference from these pass rates.</p>
<p><strong>Agent capability is another useful axis.</strong> Our experiment paired Jev with a lower-cost model (Luna). We would like to compare the same integration with a frontier model, a medium model, and a weaker model to learn whether Jev mainly lifts less capable agents or improves consistency across the board.</p>
<p><strong>Here is a radical idea</strong>: collecting every safely available view of cluster state, evaluate those views in parallel with classifiers for incident and root-cause labels, and use the ranked outputs to guide the investigation. This would require strict bounds on secrets, context size, and stale evidence, but it could reveal whether broad parallel classification outperforms existing sequential loops. Given Jev&#x27;s speed, we believe we could increase diagnosis speeds by an order of magnitude.</p>
<h2 class="flex scroll-m-28 flex-row items-center gap-2" id="summary"><a data-card="" href="#summary" class="peer">Summary</a><svg xmlns="http://www.w3.org/2000/svg" width="24" height="24" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round" class="lucide size-3.5 shrink-0 text-fd-muted-foreground opacity-0 transition-opacity peer-hover:opacity-100" aria-label="Link to section"><path d="M10 13a5 5 0 0 0 7.54.54l3-3a5 5 0 0 0-7.07-7.07l-1.72 1.71"></path><path d="M14 11a5 5 0 0 0-7.54-.54l-3 3a5 5 0 0 0 7.07 7.07l1.71-1.71"></path></svg></h2>
<p>Jev improved this SREGym-Lite slice because it added useful friction before premature diagnosis and repair. But it is a decision aid, not an oracle. The strongest design pairs its fast evidence review with executable checks that encode the system invariant the recovery must preserve.</p>
<p><strong>We are excited to see how incorporating Jev throughout the stack can improve the speed, safety, and reliability of SRE agents.
