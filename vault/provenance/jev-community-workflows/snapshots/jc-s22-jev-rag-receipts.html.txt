                <h2>
  <a name="how-i-went-from-trust-me-bro-to-boomer-with-receipts-using-jev" href="#how-i-went-from-trust-me-bro-to-boomer-with-receipts-using-jev">
  </a>
  How I went from "Trust me, bro" to "boomer with receipts" using Jev
</h2>

<blockquote>
<p><em>By separating relevance from injection risk and contradiction, you hand the IDE agent a level of structural awareness that most RAG pipelines never expose.</em></p>
</blockquote>

<p>I'm Enrique, developer of <a href="https://github.com/KikeVen/zerikai_memory" target="_blank" rel="noopener noreferrer">Zerikai Memory</a>, and I recently got access to <a href="https://typesafe.ai/" target="_blank" rel="noopener noreferrer">Jev</a>, TypeSafe's new judgment model. My first use was having it judge which code chunks are worth sending to the synthesizing LLM.</p>

<h2>
  <a name="1-ranking-is-not-the-same-as-judging" href="#1-ranking-is-not-the-same-as-judging">
  </a>
  1. Ranking is not the same as judging
</h2>

<p>Zerikai Memory already has a strong retrieval core. Tree-sitter deterministically parses a codebase into typed entities (functions, classes, docstrings, Markdown sections) with no API calls, and those entities land in a local ChromaDB store. On a query, it retrieves by L2 distance, filters with a distance threshold, re-ranks the survivors lexically, and hands the top hits to an LLM to synthesize an answer with <code>file:line</code> citations. Every hit is factual and traceable by design: a real entity, a real file, a real line, and a distance score.</p>

<p>That pipeline works, and it works because the indexing and the thresholds are tuned. But it shares a limit with most RAG pipelines: lexical re-ranking can order candidates by closeness and keyword overlap, but it cannot judge them. It never rejects a passage. So when a query pulls in chunks that merely share vocabulary with it, all of them reach the synthesizer, and the model has to separate the useful evidence from the near-misses. Usually it does. Occasionally it fills a gap with something the sources do not support.</p>

<p>That is the gap Jev closes: an optional add-on, not a replacement. I wanted the retrieval layer to judge which chunks are actually worth sending to the synthesizing LLM, the model that writes the final answer, not just rank them by similarity: which ones answer the question, which are only topically nearby, and whether any of them look like they are trying to manipulate the model.</p>

<h2>
  <a name="2-just-a-bit-more-context-about-zerikai-memory" href="#2-just-a-bit-more-context-about-zerikai-memory">
  </a>
  2. Just a bit more context about Zerikai Memory
</h2>

<p>Zerikai Memory is persistent, workspace-isolated memory for IDE agents. The design goals are local-first, cost-aware, and fast:</p>

<ul>
<li>
<strong>Deterministic indexing.</strong> Tree-sitter parses source into entities (signatures, docstrings, line numbers) and writes them to a local ChromaDB vector store. No network, no tokens.</li>
<li>*<em>Local MCP interface.</em>,* The IDE agent talks to it over stdio, so context is assembled on the developer's machine, and only the precise retrieved chunks travel to the model.</li>
<li>
<strong>Cheap synthesis.</strong> Becaus the injected context is small and structured, it pairs well with local Ollama models and low-cost APIs like DeepSeek, and it keeps the system prompt stable enough to maximize KV-cache hits.</li>
<li>
<strong>Strict source verification.</strong> Every answer is anchored to an entity, file, and line number, with an L2 distance so you can sanity-check how close the match really was.</li>
</ul>

<p>The query path looked like this:<br>
</p>

<p>And here's the honest read on it: the lexical layer works well, but it only ever answers one question, <em>is this relevant?</em>, and it can only answer it by shuffling. The synthesizing LLM gets the hits and the scores and assembles an answer. The IDE agent gets the answer. The hits themselves are factual and traceable, but the leap from "relevant" to "answers the question" was never verified.</p>

<h2>
  <a name="3-enter-typesafe-jev-the-system-one-model" href="#3-enter-typesafe-jev-the-system-one-model">
  </a>
  3. Enter TypeSafe Jev: the "System One" model
</h2>

<p>Jev is a different kind of model. Where an LLM generates text token by token, Jev reads a <code>state</code> and returns a <strong>typed decision</strong> (a probability, a label, a score) with no prose to parse. TypeSafe calls this class of model "System One," borrowing Kahneman's fast, instinctive mode of thought: a split-second intuition engine that produces a structured judgment instead of a paragraph.</p>

<p>That maps onto three primitives, and the shapes matter because your code branches on them:</p>

<div class="table-wrapper-paragraph"><table>
<thead>
<tr>
<th>Primitive</th>
<th>It asks</th>
<th>It returns</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Noul</strong></td>
<td>Is this statement true?</td>
<td>
<code>noul</code>: a probability from 0 to 1</td>
</tr>
<tr>
<td><strong>Score</strong></td>
<td>Rate this on a rubric</td>
<td>
<code>score</code>: a probability-weighted value + <code>probabilities</code>
</td>
</tr>
<tr>
<td><strong>Choice</strong></td>
<td>Pick one from a list</td>
<td>
<code>choice</code>: a label + <code>probabilities</code>
</td>
</tr>
</tbody>
</table></div>

<p>Two things make this a good fit for a memory layer. First, it's fast, and it's <strong>one batched call per decision point</strong>, not one call per chunk. TypeSafe's own benchmarks put batched calls at roughly 11× cheaper and 10× faster than the sequential equivalent. Second, Jev is <strong>probabilistic, not deterministic</strong>, and that's fine, because I consume its probabilities with my own thresholds. Tree-sitter stays the deterministic part; Jev is the judgment part.</p>

<p>The IDE agent gets the answer. The retrieval layer has done everything it was built to do.</p>

<h2>
  <a name="4-the-first-test-replacing-lexical-filters-with-jev-primitives" href="#4-the-first-test-replacing-lexical-filters-with-jev-primitives">
  </a>
  4. The First Test: Replacing Lexical Filters with Jev Primitives
</h2>

<p>I need to be precise about what I removed, because it's the whole point.</p>

<blockquote>
<p><strong>Status:</strong> This is an early look. The Jev integration described here is <strong>not in the public Zerikai Memory repo yet</strong>. It's experimental and off by default, so with the flag disabled, the server behaves exactly as it does today. When I ship it, it works the same way: built in, off by default, and enabled with a flag when you want it. I hope to drop a version of <a href="https://github.com/KikeVen/zerikai_memory" target="_blank" rel="noopener noreferrer">Zerikai Memory</a> with this feature by the end of the week or early next week.</p>
</blockquote>

<p>My lexical layer never <em>filtered</em>. It re-ordered. Given the candidates that survived the L2 distance cutoff, it scored each one by <code>1/distance + (keyword_hits × weight)</code> and handed the top five to the synthesis LLM. Nothing was judged. Nothing was dropped. If you typed a question that pulled in five superficially keyword-adjacent chunks, all five went to the LLM, and the LLM was left to sort treasure from noise, and occasionally it didn't.</p>

<p>So the honest framing isn't "Jev replaced my lexical filter." It's: <strong>my retrieval could rank, but it couldn't judge. Jev added the keep/drop decision that was missing.</strong></p>

<h3>
  <a name="the-implementation" href="#the-implementation">
  </a>
  The implementation
</h3>

<p>I kept the entire retrieval path untouched. L2 still fetches the candidates. Then, instead of the lexical re-rank, I send the candidate set through one batched Jev call. Every passage gets four typed questions, and the set gets three global ones:<br>
</p>

<div class="highlight js-code-highlight">
<pre class="highlight python"><code><span class="k">def</span> <span class="nf">evidence_questions</span><span class="p">(</span><span class="n">passage_ids</span><span class="p">:</span> <span class="nb">list</span><span class="p">[</span><span class="nb">str</span><span class="p">])</span> <span class="o">-&gt;</span> <span class="nb">dict</span><span class="p">:</span>

<p>The contrast that convinced me: on a different query, <em>"how tree-sitter works,"</em> that same <code>LanguageConfig</code> passage scored 0.44 / 0.47 and got <strong>kept</strong>. Same chunk, different verdict, depending on the question. That's the "dynamic" part.</p>

<h3>
  <a name="what-it-costs" href="#what-it-costs">
  </a>
  What it costs
</h3>

<p>The guard is one batched call. At TypeSafe's published rate for Jev 1.13 ($0.042 per million input tokens, output tokens free), a call carrying ~7,000 input tokens costs about <strong>$0.0003</strong>, roughly three hundredths of a cent. Across the whole test window, that was 53 calls and ~210k input tokens, or <strong>under a cent total</strong>. During early access, the calls logged as unbilled, so my out-of-pocket cost so far is zero.</p>

<h3>
  <a name="what-the-ide-agent-sees" href="#what-the-ide-agent-sees">
  </a>
  What the IDE agent sees
</h3>

<p>The tool doesn't hand the IDE agent prose. It hands it a plain-text payload: the synthesized answer, wrapped in a machine-oriented report. The <strong>Legend runs first</strong>, so the agent knows how to read every number that follows.<br>
</p>

<div class="highlight js-code-highlight">
<pre class="highlight plaintext"><code>Legend: relevance, evidence, contradicts, and injection are probabilities from 0 to 1. High relevance/evidence = the passage is on-topic and usable as evidence. Sources = L2 vector distance; lower is closer (a separate scale from the 0-1 probabilities above).

Tree-sitter parses Markdown through the tree-sitter-markdown grammar, wired in as `MD_LANG`
... (#code_indexer.py:64 | 0.76 L2).

<p>That's the raw text. Every claim in the answer has a receipt: which passage, how relevant, how evidentiary, and whether it was kept or dropped. The agent isn't asked to trust an answer; it's handed the reasoning.</p>

<p><strong>Then the IDE agent reformats it.</strong> It strips the Legend, Assessment, and Guidance (the machinery) and hands me the prose answer with the citations inline. On a sibling query through this same payload, Claude Haiku 4.5 returned an architectural summary citing the exact kept passages (<code>code_indexer.py:204</code>, <code>:663</code>, <code>:1256</code>), noted the <code>injection=0.02</code> context was clean, and never echoed the Legend at me.</p>

<p><a href="https://media2.dev.to/dynamic/image/width=800%2Cheight=%2Cfit=scale-down%2Cgravity=auto%2Cformat=auto/https%3A%2F%2Fdev-to-uploads.s3.us-east-2.amazonaws.com%2Fuploads%2Farticles%2F13jhyxuvatrxp386jn9s.png" class="article-body-image-wrapper"><img src="https://media2.dev.to/dynamic/image/width=800%2Cheight=%2Cfit=scale-down%2Cgravity=auto%2Cformat=auto/https%3A%2F%2Fdev-to-uploads.s3.us-east-2.amazonaws.com%2Fuploads%2Farticles%2F13jhyxuvatrxp386jn9s.png" alt="human-readable answer by IDE Agent" loading="lazy" width="608" height="972"></a></p>

<p>That's the two layers the design was aiming for: a plain-text report the <strong>agent</strong> can act on, and a human-readable answer the <strong>developer</strong> reads. The receipts travel with the agent; the prose reaches the developer.</p>

<p>The anchor quote I keep coming back to: <em>by separating relevance from injection risk and contradiction, you hand the IDE agent a structural awareness that most RAG systems never expose.</em> Jev doesn't just return better passages; it tells the agent <em>why</em> they're better, and where the doubt is.</p>

<h2>
  <a name="5-conclusion-amp-the-next-frontier-the-postsynthesis-guard" href="#5-conclusion-amp-the-next-frontier-the-postsynthesis-guard">
  </a>
  5. Conclusion &amp; The Next Frontier: The Post-Synthesis Guard
</h2>

<p>The experiment answered the question I set out to test. Guarding the <em>input</em> context with Jev made retrieval disciplined without slowing the loop: one batched call, roughly a second on the evidence step, and in exchange a synthesis prompt that is smaller, cleaner, and defensible, reordered. Two passages were dropped that my lexical layer, by design, could only have re-ordered. The answer didn't get shorter; it got more honest.</p>

<p>Two honest caveats. The thresholds are mine and they're calibrated on a small sample. I expect to tune them, and I already saw a borderline query flip status when a global score landed exactly on a cutoff. And everything I built here judges the <em>retrieved passages</em>, not the <em>written answer</em>. It proves the context is clean. It does not yet prove the final sentences are faithful to it.</p>

<p>That's the next frontier.</p>

<p>The obvious next layer sits between synthesis and delivery: a <strong>Faithfulness Guard</strong> that audits the model's output against the passages Jev already vouched for. The primitives map cleanly. For each citation, a <code>Choice</code> question sorts it into one of four states (<em>verified, unsupported, contradicted, fabricated</em>), and a <code>Score</code> produces an overall <code>grounded</code> value that rides along in the same report. Same shape as today, one desk further down the pipeline: the evidence guard vets the ingredients, the post-synthesis guard checks the dish.</p>

<p>I haven't built it yet. That's the point of part two.</p>

<blockquote>
<p><strong>If this was useful, help me reach my goal on AI implementation research on</strong> <a href="https://ko-fi.com/enriquebruzual/goal?g=0" target="_blank" rel="noopener noreferrer">Ko-fi</a></p>
</blockquote>

<p>If you're working on retrieval-augmented pipelines, I'd genuinely like your read on one thing: <strong>when the guard drops a passage for low evidence but decent relevance, is that the right call, or am I throwing away the connective context the synthesis model actually needs?</strong> That's the trade-off I'm least sure about, and the one I'll be testing next.</p>

          <p>This is the clean separation the Jev wave needs: ranking reorders; judging keep/drops.</p>

<p>Lexical re-rank answers “how close?” — it never rejects. That’s why topical near-misses still reach the synthesizer. Making relevance / evidence / injection <em>typed</em> decisions (with thresholds <em>you</em> own) is the missing contract layer — not a magic model swap.</p>

          if (event.origin !== 'https://forem.com' && event.origin !== window.location.origin) {
            return;
          }

          var data = event.data;

          if (data.authenticated && !userSignedIn) {
            authenticateUser(data.token);
          } else if(data.authenticated && window.ReactNativeWebView && window.ReactNativeWebView.postMessage) {
            window.ReactNativeWebView.postMessage(JSON.stringify({
              action: 'login',
              token: data.token,
            }));
          }
        });
      }

      function authenticateUser(token) {
        fetch('/auth_pass/token_login', {
          method: 'POST',
          credentials: 'include',
          headers: {
            'Content-Type': 'application/json',
            'X-CSRF-Token': getMetaContent('csrf-token'),
          },
          body: JSON.stringify({ token: token }),
        })
        .then(function(response) {
          return response.json();
        })
        .then(function(data) {
          if (data.success) {
            if (document.head.querySelector('meta[name="user-signed-in"][content="false"]')) {
              // Reload the page to update the user's state
              location.reload();
            }
          }
        })
        .catch(function(error) {
          console.error('Error during authentication:', error);
        });
      }

      function getMetaContent(name) {
        var element = document.querySelector('meta[name="' + name + '"]');
        return element ? element.getAttribute('content') : '';
      }
  }
</script>
