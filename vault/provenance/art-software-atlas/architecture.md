# 参考书架构 · 有边界的实现快照

本批扩展既有 Design / Write 来源—语法结构，不另建一套风格总分类。来源正文继续在 Vault，可消费的推导继续在 Kit 原有 composition、interaction、motion、references 分支；这一研究集合的书目、实体和查询投影放在一起。设计师可以从模糊意图进入，也可以从作品、传统、媒介或工具进入，最终得到可比较的操作与限制。

## 已有结构与实际缺口

既有 [书目索引](../design-writing-encyclopedia/index.json)已经区分行业、任务、产物、操作、技术、谱系和语言，保留来源证据、权利与双向语法链接，因此不需要因来源更多而重建分类。[参考生命周期](../../../docs/governance/reference-lifecycle.md)也已覆盖普通参考、优先参考、规范采纳和退出。

实际新增的是多种实体之间的关系：Codrops 目录页不是里面的作品，D3 API 不是汽车散点图，艺术家作品不是馆方仿真环境。[Rhizome 模型来源](discovery/cards/rhizome-model.md)更明确区分作品、变体、参与者与保全活动；单一 URL → grammar 边不能表达这些差别。本批只为这个缺口增加 `entities.json` 与限定关系，没有迁移旧卡，没有部署图数据库。归属和读法仍服从既有规范。

## 五类身份及关系

| 身份 | 回答的问题 | 唯一正文与本批表示 |
|---|---|---|
| source-record | 这次证据是哪一 URL，支持哪项主张，实际读/看/运行了什么？ | 分支 catalog + 来源卡；沿用既有字段，生成索引时明确 kind |
| discovery-corpus | 该集合如何收集、分类、连接材料？ | entities 中的集合身份；描述分类的 source-record 独立存在 |
| exemplar | 哪一件作品、标本、代码示例或具体变体？ | 实体身份及对应来源；不把整个传统写成一件 exemplar |
| implementation-substrate | 哪个库、引擎、格式、字体系统或工具提供什么接口？ | 实体身份与官方文档来源；许可和依赖不从同目录继承 |
| derived-grammar | 本仓库从来源推导了哪种关系和可调操作？ | Kit 单一正文及稳定 ID；index 只投影入口、证据边和操作 |

`documents` 连接证据与对象；`contains` 仅表示集合收录；`discovered-via` 仅表示发现路径；`informs` 表示推导线索；`implements` 需限定实现的是哪一局部操作；`contrasts` 保留反例。每条边写 basis 与 limits，不能由 contains 推出核验、权利或作者认同。原作和变体若尚未获得可识别定位，不伪造实体，只登记缺口；未来需要时追加具体 variant 与参与者关系，不先铺空本体。

此快照不是知识图谱服务。JSON 可由现有命令行工具读取；`schema.json` 校验字段形状，外键、双向链接和 URL 去重另有本批验证回执。旧书目保持既有索引，复用来源通过 `reused_sources` 指向原卡，不复制摘要或改造旧 ID。

## 渐进展开及停止点

| 层级 | 用户看见什么 | 何时停止/继续 |
|---|---|---|
| L0 路由 | 一句任务意图 → 两三个候选操作 | 找到与任务匹配的关系便进入该条；不加载全体来源 |
| L1 条目摘要 | 做什么、何时不用、证据形态、下一产物 | 仅为选路或排除候选时到此停止；不是可独立施工的深条目 |
| L2 深条目 | 原语境 → 意图 → 变量/不变量 → 实现选择 → 检查例 → 反例 | 能给出最小试件与失败条件即可回项目设计；无须遍读书目 |
| L3 证据 | 逐源摘要、主张定位、原 URL、权利与依赖边界 | 拟引用历史事实、依赖具体行为或复用资产时按需下钻 |
| L4 验证/保全 | 版本、访问与运行回执、证据文件、消费反馈 | 复现、维护和审阅时读取；不会自动证明设计效果 |

层级表示展开深度，不是艺术价值、成熟度或规范强度。`source_record.status=verified` 只能对应它列出的主张；L2 可以依赖 partial 证据，但必须缩小结论。目录 lead 仍是 lead，不因挂到 Kit 就变成已消费作品。

## 正交分面与原分类

沿用 `industry_author` / `industry_applicability` 区分作者所在语境和推测用途；`artifact` 表示媒介/产物，`stack_runtime` 表示实现条件，`style_lineage` 保留历史或传统标签，`operation` 描述可调整关系，`task` 描述消费目标，`language` 保留语言条件。未标注不同于 unknown；not-applicable 不等于“没有”。值允许多选，basis 明示 explicit/inferred，evidence 指向来源或主张 ID。

证据形态、来源可用性、权利、依赖、实现成熟度、采纳和检索优先级是独立字段，不压成一个质量分。行业/媒介/技术/谱系不能拼成一棵“艺术风格树”。供应方的 Skills/MCP/Agent Harness、档案的 artwork/variant、印刷实践的原术语保留在来源卡与条目里；本地操作名另置，不声称原作者按本书分类。

例如 `operation=retain-context` 与 `artifact=interactive-chart` 可以找到范围选择，再依任务决定 SVG、Canvas 或原生输入；它不会证明任何框选图都适合统计分析。`style_lineage` 命中也不授予挪用某群体符号的文化授权。版权许可、社区/语境适切性与技术可用性分别检查。

## 条目深度与广度边界

一个深条目至少给出具体语境与来源、一项沟通/感知意图、可调变量与不变量、两种实现取舍、已检查的具体实例、一个反例及最小产物。文字研究不能冒充作品观看，影像观看不能冒充现场身体经验，源码不能冒充 demo 执行；本批逐项披露。并非每种传统都有可以忠实翻译的软件版本，拒绝翻译是有效的设计判断。

样本刻意跨织物、文字、图形、空间、时间、声音、可编程规则与软件组件；它测试模型的承载能力，不代表艺术史地域覆盖已经充分。代表性反例既来自来源的限制，也来自本仓库构造的压力情景；二者显式区分。未读流派、未听的音乐、未运行的工具留在 [研究流地图](streams.md)，不填满一张看似完整的百科表。

## 维护、整合与退出

1. 新 URL 先与全仓 catalog/registry 的 canonical URL 比较。已有身份追加独立复核记录并复用原卡；不同作者描述同一作品仍是不同 source-record，同一作品实体则可共享。
2. 新发现先登记 lead，读取其原文/实例才增加支持主张；写成深条目后挂到现有最邻近的任务入口。只有描述和链接修复不了的发现失败才提出结构变更。
3. 消费者留薄记录：任务、实际读取路径、采用/改写/拒绝、变化和遗漏。发现失败回修路由；效果结论需要对照，少量独立任务只证明该次发现。
4. 来源漂移、失效依赖、误归属、权利变化或消费者反例触发复核。缩小可支持范围，必要时降为 historical 并同步所有入口；不让一张失效卡继续显示 preferred。
5. 重复 grammar 合并到唯一正文，旧 ID 与路径保留重定向、替代及理由。没有替代时明确终止推荐；来源证据身份不删除。索引 `redirects` 为空表示尚未发生合并，不表示无需退出机制。
6. 一轮维护完成于：变更身份清楚、所有影响入口同步、双向链接/模式通过、失败已披露、薄消费记录可回查。无需重排整批旧文档来制造一致外观。

本批不新增治理规则，不宣称 preferred，不改变实现晋升门槛，不把参考库接入任何 agent runtime。日期、实际工作角色和版本在 [独立交付记录](../../../docs/verification/art-software-atlas-20261011/README.md)。
