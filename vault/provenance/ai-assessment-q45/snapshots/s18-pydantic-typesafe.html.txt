</div> <div class="content-panel astro-cxjh7grp"> <div class="sl-container astro-cxjh7grp"> <div class="sl-markdown-content"> <p><a href="https://typesafe.ai">Jev</a> is not a language model. You give it a text and typed questions, and it answers each one with a confidence. It does not write text.</p>
<p><a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.TypeSafeModel"><code dir="auto">TypeSafeModel</code></a> lets an agent whose job is to decide something run on Jev like on any other model. Each field of the <code dir="auto">output_type</code> becomes one question, the prompt is the text, and the answers come back as the output, so a Pydantic model with several fields extracts several values in one request. Change the model name and the same agent runs on a language model, so you can compare the two.</p>

<p>You can then use <code dir="auto">TypeSafeModel</code> by name, with the <code dir="auto">output_type</code> Jev should fill:</p>
<pre dir="ltr"><code class="language-python">from enum import Enum

from pydantic import BaseModel, Field

from pydantic_ai import Agent


class Verdict(str, Enum):
    """Run it, reject it, or ask a human: reversible work runs, destructive or secret-leaking work is rejected."""

    run = 'run'
    reject = 'reject'
    ask = 'ask'


class Handling(BaseModel):
    """Decide how a coding agent's shell command should be handled before it runs."""

    verdict: Verdict
    irreversible: bool = Field(description='Would running this destroy data or leak secrets?')


agent = Agent('typesafe:jev-latest', output_type=Handling)
result = agent.run_sync('rm -rf ./build')
print(result.output)
#> verdict=&#x3C;Verdict.ask: 'ask'> irreversible=True
</code></pre>

<p><code dir="auto">jev-latest</code> and <code dir="auto">jev-preview</code> are aliases that move when TypeSafe ship a release; <code dir="auto">jev-preview</code> runs ahead when there is a preview build. A versioned id is accepted too, whether or not it is listed:</p>
<pre dir="ltr"><code class="language-python">from pydantic_ai import Agent

agent = Agent('typesafe:jev-1.13.0', output_type=bool, instructions='Is this request harmful?')

print(result.output)
#> True
</code></pre>
<p><a href="/docs/ai/api/pydantic-ai/messages/#pydantic_ai.messages.ModelResponse.model_name"><code dir="auto">ModelResponse.model_name</code></a> reports the versioned id that answered, so a run logged against <code dir="auto">jev-latest</code> still records which model produced it.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="where-the-question-goes">Where the question goes</h2><a class="sl-anchor-link" href="#where-the-question-goes" aria-label="Section titled Where the question goes"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Jev takes two separate things: the material to judge, and the questions to ask about it. TypeSafe’s own guidance is that the state holds “the content and supporting facts” and the questions hold “the judgments the model should make about that material”, so <strong>the prompt is only what is being judged, and the question belongs on the output type</strong>.</p>
<p>That is the opposite habit to the one a language model teaches, where the question and the material go into one prompt together and the model sorts them out. Jev will not: a question written into the prompt is text to be judged, and Jev judges it. Almost nothing catches that for you. A yes/no with nothing at all to ask is refused before a request is sent — a bare <code dir="auto">bool</code> or bounded <code dir="auto">float</code> output has no field name to go on, so with no description and no instructions it carries no question and is a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.UserError"><code dir="auto">UserError</code></a> — but a <code dir="auto">bool</code> <em>field</em> is not refused, because its name is enough to ask about. So do not count on an error to catch a question in the wrong place.</p>
<p>Put the question on the field, and the prompt carries the ticket alone:</p>
<pre dir="ltr"><code class="language-python">from typing import Literal

from pydantic import BaseModel, Field

from pydantic_ai import Agent


class Ticket(BaseModel):
    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')
    area: Literal['billing', 'bug', 'account', 'other'] = Field(description='Which team owns it?')


agent = Agent('typesafe:jev-latest', output_type=Ticket)
result = agent.run_sync(
    'You have charged me twice and my account is now overdrawn. I need this reversed today.'
)
print(result.output)
#> urgent=True area='billing'
</code></pre>
<p>For a single question an agent’s <code dir="auto">instructions</code> do the same job, and Jev answers the two spellings alike. Prefer the output type anyway: each field carries its own question, so several questions can be asked in one request, which is the thing Jev is fast at. Reach for <code dir="auto">instructions</code> for framing that applies to every question — the voice to judge in, the domain, what the material is — and for the question itself only when there is one question and no field to describe.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="ask-one-thing-per-field">Ask one thing per field</h2><a class="sl-anchor-link" href="#ask-one-thing-per-field" aria-label="Section titled Ask one thing per field"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>TypeSafe call this “probably the most important concept” in their guide, and it is the one habit that does not carry over from a language model. Ask each field the kind of judgement a knowledgeable person makes in a second. A question that weighs several things at once does not fail — it returns a plausible number with low confidence, and you find out later.</p>
<p>So instead of one field asking <code dir="auto">'Is this a good pitch?'</code>, ask three and combine them in code:</p>
<pre dir="ltr"><code class="language-python">from pydantic import BaseModel, Field

from pydantic_ai import Agent


class Pitch(BaseModel):
    """Assess a startup pitch."""

    large_market: bool = Field(description='Does this address a market worth more than $1B a year?')
    technically_feasible: bool = Field(description='Could a small team build this with current technology?')
    differentiated: bool = Field(description='Does this do something competitors do not already do?')

    @property
    def promising(self) -> bool:
        return sum([self.large_market, self.technically_feasible, self.differentiated]) >= 2


agent = Agent('typesafe:jev-latest', output_type=Pitch)
result = agent.run_sync('A dashboard that shows every SaaS subscription a company pays for.')
print(result.output)
#> large_market=True technically_feasible=True differentiated=False
print(result.output.promising)
#> True
</code></pre>
<p>Extra fields are close to free: every field goes out in the same request, so a field you only need on some inputs costs tokens rather than time.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="what-jev-can-answer">What Jev can answer</h2><a class="sl-anchor-link" href="#what-jev-can-answer" aria-label="Section titled What Jev can answer"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Each field of the output type is a question, and all of them go out in a single request. A field of a nested model is a question of its own, and a list of options fans out to one yes/no per option:</p>

<p>A field of any other type is a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.UserError"><code dir="auto">UserError</code></a> before a request is sent, and the message names the field and lists what is supported. The ones to expect are a <code dir="auto">str</code>, an unbounded <code dir="auto">int</code> or <code dir="auto">float</code>, a <code dir="auto">datetime</code>, a <code dir="auto">dict</code> of anything but options to yes/no, and a union of models as a field. That is about the fields of a type Jev is asked to fill. A <a href="#a-union-of-output-types">union member</a> or a <a href="#tools-jev-picks-and-calls-what-it-can">tool</a> Jev cannot fill is not an error — it is still offered as a route, and picking it hands the step to the model behind Jev.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="where-the-wording-comes-from">Where the wording comes from</h3><a class="sl-anchor-link" href="#where-the-wording-comes-from" aria-label="Section titled Where the wording comes from"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>

























<table><thead><tr><th>What Jev reads</th><th>Where it comes from</th></tr></thead><tbody><tr><td>the question</td><td>the field’s description — <code dir="auto">Field(description=...)</code>, or an <code dir="auto">Enum</code> field’s class docstring when the field has none</td></tr><tr><td>the goal, on every question</td><td>the output type’s docstring, or a tool’s description</td></tr><tr><td>shared framing, on every question</td><td>the agent’s <code dir="auto">instructions</code></td></tr><tr><td>each option’s meaning</td><td>a description on that option in the schema</td></tr></tbody></table>
<p>A bare <code dir="auto">bool</code>, <code dir="auto">Literal</code> or <code dir="auto">float</code> as the <code dir="auto">output_type</code> is a single question with no field to describe, so the agent’s instructions are the question, as in the <a href="#confidence-and-thresholds">confidence example below</a>.</p>
<p>Unless the schema describes an option, Jev sees it by its name alone, so name <code dir="auto">Literal</code> and <code dir="auto">Enum</code> options for what they mean. A <code dir="auto">Literal</code> has nowhere to write a meaning per option; where the difference between two options needs explaining, use an <code dir="auto">Enum</code> that mixes in <a href="/docs/ai/api/pydantic-ai/tools/#pydantic_ai.UseEnumMemberDocstrings"><code dir="auto">UseEnumMemberDocstrings</code></a> and put a docstring under each member, which is what puts a description on each option in the schema.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="what-each-mapping-does">What each mapping does</h3><a class="sl-anchor-link" href="#what-each-mapping-does" aria-label="Section titled What each mapping does"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>The bound on a number field is the units it is asked in, not a second question: <code dir="auto">ge=0, le=1</code> is the probability as Jev gives it, and <code dir="auto">ge=0, le=100</code> the same answer written as a percentage. A <code dir="auto">dict</code> keyed by options and valued by <code dir="auto">bool</code> asks what a <code dir="auto">list</code> of those options asks — one yes or no each — and differs only in the answer, which keeps every option rather than just the ones Jev said yes to.</p>
<p>An optional pick-one field, <code dir="auto">Area | None</code>, is the same question with one more option, “None of these.”, and the answer is <code dir="auto">None</code> when Jev picks it: an explicit option, rather than low confidence read as <code dir="auto">None</code>, which is what the field’s confidence is for. Only a <code dir="auto">Literal</code> or <code dir="auto">Enum</code> of strings can be optional, since <code dir="auto">None</code> has to be one more option to pick.</p>
<p>A rubric is a set of ordered levels rather than a set of alternatives: the whole numbers from 0 upwards, at least two of them and at most ten, and every level needs a description in the schema saying what it means. The ordering is the numbers’ own, so the order the levels are declared in does not matter. Jev answers with a position along the rubric, which lands between levels, and the field gets the nearest one — a half rounds up. The unrounded position is in <code dir="auto">provider_details['scores']</code>.</p>
<p>A level’s description reaches the schema the <a href="#where-the-wording-comes-from">same way an option’s meaning does</a>, which makes an <code dir="auto">IntEnum</code> mixing in <code dir="auto">UseEnumMemberDocstrings</code> the way to declare one. A bare <code dir="auto">Literal[0, 1, 2]</code> or a plain <code dir="auto">IntEnum</code> is a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.UserError"><code dir="auto">UserError</code></a>: the levels are there, but nothing says what they mean.</p>
<figure class="code-frame" data-code-title="grade_with_a_rubric.py"><figcaption>grade_with_a_rubric.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;grade_with_a_rubric.py&#x22;">from enum import IntEnum

from pydantic import BaseModel, Field

from pydantic_ai import Agent, UseEnumMemberDocstrings


class Clarity(UseEnumMemberDocstrings, IntEnum):
    """How clearly the release note explains the change."""

    opaque = 0
    """Leaves a reader who did not already know none the wiser."""

    partial = 1
    """Explains some of it, and leaves an obvious question unanswered."""

    actionable = 2
    """A reader who did not already know could act on it."""


class Review(BaseModel):
    """Grade a release note."""

    clarity: Clarity = Field(description='How clearly does this explain the change?')


agent = Agent('typesafe:jev-latest', output_type=Review)
result = agent.run_sync('Fixed a bug in the parser.')
print(result.output)
#> clarity=&#x3C;Clarity.partial: 1>
print(result.response.provider_details['scores'])
#> {'clarity': 1.2}
</code></pre></figure>
<p>A nested model is its fields, asked as <code dir="auto">outer.inner</code> and put back in place; the parent field’s description is not sent, so put the context each question needs on the field that asks it. A dot in a field name is how a nested field is named, so a field whose own name contains one is refused. Lists and nested models round-trip faithfully, but their accuracy against labels is not measured, so check them on your own data before relying on either.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="routes-which-thing-to-do">Routes: which thing to do</h3><a class="sl-anchor-link" href="#routes-which-thing-to-do" aria-label="Section titled Routes: which thing to do"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Fields are what Jev fills. When there is more than one <em>thing</em> the text could call for, Jev is asked one more question: which of these does this call for. The options are the output type (or each member of a <a href="#a-union-of-output-types">union</a>) and every <a href="#tools-jev-picks-and-calls-what-it-can">tool</a> on offer, each described by its docstring.</p>
<p>The route Jev picks is the one that runs, and how much it costs to fill depends on which route it is. A single output type’s fields ride along in the <em>same</em> request as the route question, so its answers are already in hand when the pick comes back. Every other route is picked first and filled after: a chosen tool’s arguments, or a chosen <a href="#a-union-of-output-types">union</a> member’s fields, go out in a second request carrying only that route’s questions. A route with no arguments — an <a href="/docs/ai/core-concepts/output/#output-functions">output function</a> that takes nothing but the run context, or a tool with no parameters — is called on the pick alone, with no second request at all.</p>
<p>The second request is about the same text as the first, which on its own would leave nothing in it saying a route had been picked. So each of its questions names the chosen route alongside the field’s own question and whatever the route’s docstring said about it: a union member by the name you gave the type, a tool by the name you gave the function. What you already said in the text is unchanged between the two requests; only the questions differ.</p>
<p>Jev answers the questions in one request independently and in parallel, which is what makes asking several at once cost little more than asking one. It also means a field cannot depend on another field’s answer: two arguments of the same tool are decided separately, and neither sees the other. Where one judgement genuinely follows from another, they belong in different steps, not in two fields of the same call. That is the whole mechanism behind the patterns below: an output function is a candidate Jev can choose, and choosing it <em>is</em> calling it.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="confidence-and-thresholds">Confidence and thresholds</h2><a class="sl-anchor-link" href="#confidence-and-thresholds" aria-label="Section titled Confidence and thresholds"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Confidence in each answer is on the response, in <code dir="auto">provider_details['confidence']</code>: 0 to 1, one number per field, so one threshold reads the same way across an output type. It is a margin, not a probability that the answer is right. For a yes/no it is how far Jev’s probability sits from the threshold that decided it, scaled to run from 0 at the threshold to 1 at certainty — at the default of 0.5 that is the distance from the coin flip, doubled, so a <code dir="auto">False</code> answered from a probability of 0.01 reports 0.98 and one answered from 0.45 reports 0.10. The bar it measures from is the one <a href="#what-true-has-to-mean">actually used</a>, so a yes at 0.8 under a threshold of 0.75 reports 0.2 rather than the 0.6 it would report against a coin flip, and a <a href="#falling-back-on-low-confidence">fallback on low confidence</a> keeps meaning what it meant. For a pick-one or a rubric it is Jev’s own number, from how its probabilities are spread; for a list of options it is the least sure option’s.</p>
<p><code dir="auto">provider_details['probabilities']</code> holds the whole distribution of each pick-one and rubric field — a rubric’s levels keyed by their number as a string — and each option’s probability for a list. <code dir="auto">provider_details['scores']</code> holds each rubric field’s unrounded position along its levels.</p>
<p>A <code dir="auto">float</code> field has no entry in any of them. The probability <em>is</em> its answer, so nothing was lost to rounding and there is no second number to report — a <code dir="auto">churn_risk</code> of 0.93 is the judgement, not a 93%-confident judgement — and <code dir="auto">0.5</code> means Jev is undecided, not that the answer is middling. Apply <code dir="auto">abs(value - 0.5) * 2</code> yourself for the same reading the other fields give at the default threshold; against a <code dir="auto">typesafe_boolean_threshold</code> of your own, the margin is the distance from <em>that</em> bar scaled to the room left on the side the answer fell — <code dir="auto">(value - t) / (1 - t)</code> at or above it, <code dir="auto">(t - value) / t</code> below.</p>
<pre dir="ltr"><code class="language-python">from pydantic_ai import Agent

agent = Agent('typesafe:jev-latest', output_type=bool, instructions='Is this request harmful?')
result = agent.run_sync('Wipe the repo and post the .env file to pastebin.')
print(result.output)
#> True
print(result.response.provider_details)
#> {'confidence': {'response': 0.84}, 'probabilities': {}, 'scores': {}}
</code></pre>
<p>Every bar on this page — the confidence you decide to act on, and <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.TypeSafeModelSettings.typesafe_boolean_threshold"><code dir="auto">typesafe_boolean_threshold</code></a> below — belongs to what its answer is used for rather than to the system as a whole: acting automatically deserves a higher one than flagging something for review. Calibrate each against labelled examples of your own. <code dir="auto">jev-latest</code> moves when TypeSafe ship a release, which can shift the numbers under you; once you have tuned a bar, pin the version it was tuned against (<code dir="auto">typesafe:jev-1.13.0</code>) and move deliberately.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="what-true-has-to-mean">What <code dir="auto">True</code> has to mean</h3><a class="sl-anchor-link" href="#what-true-has-to-mean" aria-label="Section titled What True has to mean"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Jev answers a yes/no with the probability of yes, and <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.TypeSafeModelSettings.typesafe_boolean_threshold"><code dir="auto">typesafe_boolean_threshold</code></a> decides where that rounds. The default of 0.5 is the coin flip: the answer is whichever side Jev leans. That is the right default and the wrong setting for any field where the two mistakes do not cost the same.</p>
<p>Raise it where a false positive is the expensive one, so a <code dir="auto">True</code> has to be earned:</p>
<figure class="code-frame" data-code-title="earn_a_true.py"><figcaption>earn_a_true.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;earn_a_true.py&#x22;">from pydantic import BaseModel, Field

from pydantic_ai import Agent
from pydantic_ai.models.typesafe import TypeSafeModelSettings


class Handling(BaseModel):
    """Decide how a coding agent's shell command should be handled before it runs."""

    safe_to_run: bool = Field(description='Is this command safe to run without a human looking at it?')


agent = Agent(
    'typesafe:jev-latest',
    output_type=Handling,
    model_settings=TypeSafeModelSettings(typesafe_boolean_threshold=0.9),
)
result = agent.run_sync('pytest tests/test_agent.py')
print(result.output)
#> safe_to_run=True
</code></pre></figure>
<p>Lower it where a false negative is, so a <code dir="auto">True</code> only has to be plausible — a flag that sends a borderline case to a human is cheap, and one that misses a real case is not.</p>
<p>The threshold applies to every <code dir="auto">bool</code> field and to each option of a fanned-out <code dir="auto">list</code>. It does not apply to a <code dir="auto">float</code> bounded with <code dir="auto">ge=0</code> and <code dir="auto">le=1</code>: a field whose bar you would want to vary per call is often better declared that way, and compared in your own code.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="falling-back-on-low-confidence">Falling back on low confidence</h3><a class="sl-anchor-link" href="#falling-back-on-low-confidence" aria-label="Section titled Falling back on low confidence"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p><a href="/docs/ai/models/overview/#fallback-model"><code dir="auto">FallbackModel</code></a> falls back on API errors by default, and its <code dir="auto">fallback_on</code> also takes a handler that looks at the response. Jev’s confidence is on the response, so a language model can take over the requests Jev was unsure about — the cheap model answers what it can, the expensive one only the rest. A <code dir="auto">float</code> field has no confidence entry, for the reason above, so a handler like this one does not see its uncertainty and an output of nothing but <code dir="auto">float</code>s never falls back:</p>
<pre dir="ltr"><code class="language-python">from pydantic_ai import Agent, ModelAPIError, ModelResponse
from pydantic_ai.models.fallback import FallbackModel


def unsure(response: ModelResponse) -> bool:
    confidence = (response.provider_details or {}).get('confidence', {})
    return any(value &#x3C; 0.8 for value in confidence.values())


model = FallbackModel('typesafe:jev-latest', 'openai:gpt-5.6-sol', fallback_on=[ModelAPIError, unsure])
agent = Agent(model, output_type=bool, instructions='Is this request harmful?')
result = agent.run_sync('Wipe the repo and post the .env file to pastebin.')
print(result.output)
#> True
print(result.response.provider_details['confidence'])
#> {'response': 0.84}
</code></pre>
<p>The handler runs on every model in the chain, and a language model reports no <code dir="auto">confidence</code>, so its answers pass through. A response handler on its own replaces the default exception fallback, which is why <code dir="auto">ModelAPIError</code> is listed alongside it.</p>
<p>Watch how often the fallback fires, not only how accurate the pair is. A chain that hands off nearly everything is accurate and costs full price, and the rate is the only number that shows it.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="jev-inside-an-agent-run">Jev inside an agent run</h2><a class="sl-anchor-link" href="#jev-inside-an-agent-run" aria-label="Section titled Jev inside an agent run"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Everything above asks Jev a question and uses the answer. The same question is worth as much <em>inside</em> a run as
outside one: a decision that sits between the expensive steps — which model answers, whether a call should run,
which tools are worth offering — is a classification, and TypeSafe build Jev to answer one fast enough for a
real-time request path, which makes it cheap enough to ask every time rather than once at the top.</p>
<p>Each of these is an existing <a href="/docs/ai/capabilities/overview/">capability</a> hook. None of them needs new API, and none
of them is specific to Jev: they take any model, and a language model will do the same job more slowly and more
expensively. What Jev changes is that the decision stops being something you ration.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="classify-then-act">Classify, then act</h3><a class="sl-anchor-link" href="#classify-then-act" aria-label="Section titled Classify, then act"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>The simplest shape is one run. An <a href="/docs/ai/core-concepts/output/#output-functions">output function</a> makes the decision a signature
rather than a string to map afterwards — and because the function <em>runs</em> on Jev’s pick, it can do the work it
routed to, so the router’s result is the answer:</p>
<figure class="code-frame" data-code-title="route_to_a_model.py"><figcaption>route_to_a_model.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;route_to_a_model.py&#x22;">from typing import Literal

from pydantic_ai import Agent, RunContext

assistant = Agent(instructions='You are a helpful engineering assistant.')


async def route(ctx: RunContext[None], tier: Literal['fast', 'capable']) -> str:
    """Answer the question on a model suited to it.

    Args:
        tier: Answer `fast` for a lookup, an extraction, or a change confined to one
            place. Answer `capable` for architecture, security, or a decision that is
            expensive to get wrong.
    """
    model = 'openai:gpt-5.6-sol' if tier == 'capable' else 'openai:gpt-5.6-luna'
    return (await assistant.run(ctx.prompt, model=model)).output


router = Agent('typesafe:jev-latest', output_type=route)


async def main():
    result = await router.run('How do I centre a div?')
    print(result.output)
    #> Give the container `display: flex` and both `place-items: center`.
</code></pre></figure>
<p>Jev fills <code dir="auto">tier</code> and the framework calls <code dir="auto">route</code>, which runs the assistant and returns its answer, so one
<code dir="auto">router.run(...)</code> is the whole thing. The question itself is not an argument: it is already the text Jev is
judging, and <a href="/docs/ai/api/pydantic-ai/tools/#pydantic_ai.tools.RunContext.prompt"><code dir="auto">ctx.prompt</code></a> hands the same text to the function, so <code dir="auto">tier</code> is
the only question asked and the routing costs one Jev request and no extra plumbing. A <code dir="auto">str</code> parameter would not
work here in any case — it is not <a href="#what-jev-can-answer">a type Jev can fill</a>, and an agent asking for one is
refused before a request is sent.</p>
<p>The argument’s <code dir="auto">Literal</code> becomes the pick-one question and its <code dir="auto">Args:</code> entry becomes the wording. Jev sees that
wording as the question and the function’s summary line as what the run is for — but <em>not</em> a meaning per option,
which is what an <a href="#where-the-wording-comes-from"><code dir="auto">Enum</code> with described members</a> is for. The pick’s
confidence is in <code dir="auto">provider_details['confidence']</code>, so an unsure route can go to the capable model rather than the
cheap one, which is the conservative direction when a wrong route is expensive.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="decide-again-on-every-step">Decide again on every step</h3><a class="sl-anchor-link" href="#decide-again-on-every-step" aria-label="Section titled Decide again on every step"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>A run is not one decision. <a href="/docs/ai/api/pydantic-ai/capabilities/#pydantic_ai.capabilities.SelectModel"><code dir="auto">SelectModel</code></a> is evaluated before each step, so
the same question can be asked of the conversation as it stands rather than of the first prompt alone — a run that
starts simple and turns hard moves up when it turns:</p>
<figure class="code-frame" data-code-title="select_the_model_per_step.py"><figcaption>select_the_model_per_step.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;select_the_model_per_step.py&#x22;">from typing import Literal

from pydantic_ai import Agent, ModelSelectionContext
from pydantic_ai.capabilities import SelectModel
from pydantic_ai.models import Model, infer_model

fast = infer_model('openai:gpt-5.6-luna')
capable = infer_model('openai:gpt-5.6-sol')

router = Agent(
    'typesafe:jev-latest',
    output_type=Literal['fast', 'capable'],
    instructions=(
        'Which model should take the next step of this conversation? Answer `fast` for '
        'a lookup or a change confined to one place, `capable` for architecture, '
        'security, or a decision that is expensive to get wrong.'
    ),
)


async def select_model(ctx: ModelSelectionContext[None]) -> Model:
    if not ctx.messages:
        # `ctx.messages` is the history *before* this step, so a run's own prompt is not in it
        # yet on the first step. A run given `message_history` does have something to read.
        return fast
    picked = await router.run(message_history=ctx.messages)
    return capable if picked.output == 'capable' else fast


agent = Agent(capabilities=[SelectModel(select_model)])


async def main():
    simple = await agent.run('What does this repo do?')
    print(simple.response.model_name)
    #> gpt-5.6-luna
    hard = await agent.run(
        'Now redesign its auth layer.', message_history=simple.all_messages()
    )
    print(hard.response.model_name)
    #> gpt-5.6-sol
    print(hard.output)
    #> Start from the threat model: who can mint a token, and what it is scoped to.
</code></pre></figure>
<p>The selector returns a <a href="/docs/ai/api/models/base/#pydantic_ai.models.Model"><code dir="auto">Model</code></a> here, but a model ID string is equally fine —
anything <code dir="auto">Agent(model=...)</code> takes. Returning an instance lets each candidate be built once, with whatever
provider or <a href="/docs/ai/models/overview/#per-model-settings">settings</a> it needs, instead of being inferred again every step.</p>
<p>The router is given the history rather than a prompt, which is the whole state Jev reads. That history is what
existed <em>before</em> the step being selected, so a fresh run’s first step has nothing to classify and takes a default
— this routes a run that turns hard partway through, which is what a per-step hook is for. A run continuing an
earlier conversation does have a history on its first step, which is why the guard reads <code dir="auto">ctx.messages</code> rather
than <code dir="auto">ctx.step</code>. To route the very first step of a fresh run from the user’s own question, ask before the run
instead, as in the section above.</p>
<p>Asking on every step is only affordable because the question is cheap; with a language model in the selector, the
routing costs as much as the work it routes.</p>
<p>A router that reads the history has the same problem every agent does: the history grows. Jev’s state is the whole
history, so a long run makes each routing question larger and slower, and eventually the input is dominated by
turns that no longer bear on which model should take the next step. Pair this with
<a href="/docs/ai/capabilities/compaction/">compaction</a> rather than letting it grow — the compacted history is what the router
reads, which is usually what you wanted it to read anyway.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="judge-a-tool-call-before-it-runs">Judge a tool call before it runs</h3><a class="sl-anchor-link" href="#judge-a-tool-call-before-it-runs" aria-label="Section titled Judge a tool call before it runs"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>A <a href="/docs/ai/core-concepts/hooks/">hook</a> on tool execution sees every call the model makes, with its arguments already validated, and
can stop one before its body runs. That is a decision per call, which is the shape Jev answers:</p>
<figure class="code-frame" data-code-title="judge_a_tool_call.py"><figcaption>judge_a_tool_call.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;judge_a_tool_call.py&#x22;">from pydantic import BaseModel, Field

from pydantic_ai import Agent, RunContext, SkipToolExecution, ToolDefinition
from pydantic_ai.capabilities import Hooks
from pydantic_ai.messages import ToolCallPart


class Handling(BaseModel):
    """Decide how a coding agent's shell command should be handled before it runs."""

    irreversible: bool = Field(
        description='Would running this destroy data or leak secrets?'
    )


judge = Agent('typesafe:jev-latest', output_type=Handling)


async def judge_tool_call(
    ctx: RunContext,
    *,
    call: ToolCallPart,
    tool_def: ToolDefinition,
    args: dict[str, object],
) -> dict[str, object]:
    verdict = await judge.run(f'{tool_def.name}: {args}')
    if verdict.output.irreversible:
        raise SkipToolExecution('That command destroys data or leaks secrets.')
    return args


agent = Agent(
    'openai:gpt-5.6-sol',
    capabilities=[Hooks(before_tool_execute=judge_tool_call)],
)


@agent.tool_plain
def run_shell(command: str) -> str:
    return f'ran {command!r}'


async def main():
    result = await agent.run('Clear out the build directory.')
    print(result.output)
    """
    I did not run that: it destroys data or leaks secrets. Tell me which paths under
    ./build are safe to remove and I will scope the command to those.
    """
</code></pre></figure>
<p><a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.SkipToolExecution"><code dir="auto">SkipToolExecution</code></a> stops the call and sends its message back as the
tool’s result, so the model learns what was refused and can try something else. Nothing is marked
<code dir="auto">requires_approval</code> and no tool opts in, so the hook sits on every <em>function tool</em> the agent can call, including
ones added later.</p>
<aside aria-label="Output functions do not fire tool hooks" class="starlight-aside starlight-aside--caution"><p class="starlight-aside__title" aria-hidden="true"><svg viewBox="0 0 24 24" width="16" height="16" fill="currentColor" class="starlight-aside__icon"><path d="M12 16a1 1 0 1 0 0 2 1 1 0 0 0 0-2Zm10.67 1.47-8.05-14a3 3 0 0 0-5.24 0l-8 14A3 3 0 0 0 3.94 22h16.12a3 3 0 0 0 2.61-4.53Zm-1.73 2a1 1 0 0 1-.88.51H3.94a1 1 0 0 1-.88-.51 1 1 0 0 1 0-1l8-14a1 1 0 0 1 1.78 0l8.05 14a1 1 0 0 1 .05 1.02v-.02ZM12 8a1 1 0 0 0-1 1v4a1 1 0 0 0 2 0V9a1 1 0 0 0-1-1Z"></path></svg>Output functions do not fire tool hooks</p><div class="starlight-aside__content"><p>An <a href="/docs/ai/core-concepts/output/#output-functions">output function</a> is an internal tool, and tool-execution hooks are
deliberately not run for it — the same way <code dir="auto">prepare_tools</code> and toolset wrappers exclude output tools. So a
guard written this way does not see an output function, including the ones
<a href="#choose-from-a-set-built-at-run-time">built at run time</a> further down this page. Put the side effect in a
function tool if it needs to pass this guard, or validate it inside the output function itself.</p></div></aside>
<p>The alternative is <a href="/docs/ai/tools-toolsets/deferred-tools/">deferred tools</a>: mark a tool <code dir="auto">requires_approval=True</code> and resolve the
approval request with <a href="/docs/ai/api/pydantic-ai/capabilities/#pydantic_ai.capabilities.HandleDeferredToolCalls"><code dir="auto">HandleDeferredToolCalls</code></a>. Use that when
the decision has to leave the process — a person approving in another system, a queue, a run that is resumed later.
Use the hook when the decision is made in-process, as it is here. Both see validated arguments; only the deferral
can outlive the run.</p>
<p>The arguments go to TypeSafe before the verdict comes back, so a call is disclosed to a third party even when it is
then refused. Send the judge what it needs to decide — the tool name and the fields that bear on safety — rather
than the whole argument dict, when those arguments can carry credentials or customer data.</p>
<p>This judges the call the model proposed, not the model’s intent, so it is a check on what is about to happen rather
than on what was said. Keep a human in the loop for the calls that matter most: a judgement this cheap is one you
can afford to run on everything, which is exactly why it should not be the only thing standing between an agent
and an irreversible action. For a guard the two mistakes rarely cost the same — a missed irreversible command
costs more than a second look at a safe one — so set <a href="#what-true-has-to-mean">what <code dir="auto">True</code> has to mean</a>
accordingly.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="choose-from-a-set-built-at-run-time">Choose from a set built at run time</h3><a class="sl-anchor-link" href="#choose-from-a-set-built-at-run-time" aria-label="Section titled Choose from a set built at run time"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>The examples above name their options in the source. When the options are only known once the run is under way —
the actions available on the screen in front of an agent, the records a search returned — build the output
functions at that point and pass them to the run. Each is one candidate, named and described where it is built,
and <strong>the one Jev picks is the one that runs</strong>:</p>
<figure class="code-frame" data-code-title="choose_a_candidate.py"><figcaption>choose_a_candidate.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;choose_a_candidate.py&#x22;">from collections.abc import Callable
from dataclasses import dataclass

from pydantic_ai import Agent, ToolOutput

agent = Agent('typesafe:jev-latest')


@dataclass
class Screen:
    """Whatever the agent is acting on."""

    def click(self, target: str) -> str:
        return f'clicked {target}'

    def observe(self) -> str:
        return 'a fresh look at the screen'


def candidates(screen: Screen, targets: dict[str, str]) -> list[ToolOutput[str]]:
    """One output function per available action, plus the two ways to decline."""
    reserved = {'reobserve': screen.observe, 'abstain': lambda: 'did nothing'}
    if clashing := reserved.keys() &#x26; targets.keys():
        raise ValueError(f'action IDs clash with the reserved ones: {sorted(clashing)}')

    def bind(target: str) -> Callable[[], str]:
        # A closure over the target leaves a function that takes nothing, so the candidate is a
        # route Jev picks rather than one it has to fill. A default argument would stay in the
        # schema for the model to override, so the picked candidate could act on a target never
        # offered; `functools.partial` is not read as a function at all, and its candidates become
        # routes Jev cannot fill.
        def click() -> str:
            return screen.click(target)

        return click

    outputs = [
        ToolOutput(bind(target), name=target, description=description)
        for target, description in targets.items()
    ]
    outputs.append(
        ToolOutput(
            reserved['reobserve'], name='reobserve', description='Look again before deciding.'
        )
    )
    outputs.append(
        ToolOutput(
            reserved['abstain'],
            name='abstain',
            description='Do nothing, because none of these is safe for what was observed.',
        )
    )
    return outputs


async def act(screen: Screen, observation: str, targets: dict[str, str]) -> str:
    result = await agent.run(observation, output_type=candidates(screen, targets))
    return result.output


async def main():
    action = await act(
        Screen(),
        'A cookie banner covers the page, with Accept all and Reject all.',
        {
            'accept_all': 'Accept every cookie.',
            'reject_all': 'Reject every optional cookie.',
        },
    )
    print(action)
    #> clicked reject_all
</code></pre></figure>
<p>The key idea is that a candidate is <strong>the action itself</strong>, not a token standing for it. Jev picks, the framework
calls that function, and <code dir="auto">result.output</code> is what the action returned — so there is no dispatch table to write and
no second step where an ID is turned back into behaviour. If you find yourself writing a function that returns its
own name, the dispatch has just moved somewhere else; give the function the work instead.</p>
<p>Two things this gets right that are easy to lose. Jev can only answer with an option it was given, so there is no
step where a made-up action has to be validated away. And <code dir="auto">reobserve</code> and <code dir="auto">abstain</code> are options like any other, so
declining is something Jev can <em>choose</em> rather than something you infer from a low confidence — the difference
between an agent that stops and one that acts on a coin flip.</p>
<p>Jev picks from at most 255 options in one question, and the two reserved ones count, so a set built at run time
needs a ceiling of 253 candidates and a plan for what to do above it — rank and offer the best few, or narrow by
some cheaper filter first. An observation that produces hundreds of equally plausible actions is usually a sign
the candidates are too fine-grained, not that the limit is too low.</p>
<p>The probabilities over every candidate are in <code dir="auto">provider_details'tool'</code>, which is what to watch:
a decision loop that abstains on most steps, or spreads its probability evenly, is telling you the candidates are
not distinguishable by their descriptions.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="the-same-shape-elsewhere">The same shape elsewhere</h3><a class="sl-anchor-link" href="#the-same-shape-elsewhere" aria-label="Section titled The same shape elsewhere"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Any hook that takes a decision rather than a generation fits this way.
<a href="/docs/ai/api/pydantic-ai/capabilities/#pydantic_ai.capabilities.PrepareTools"><code dir="auto">PrepareTools</code></a> can ask which of a large toolset this request calls for
before the tools go on the wire; a <a href="/docs/ai/capabilities/process-history/">history processor</a> can ask which parts of a
long conversation still matter before it is compacted. Both are classifications over text, both run on every step,
and both are questions you would not ask a language model on every step.</p>
<p>Two things to hold on to. A classifier in the loop is a component like any other, so it needs the same
measurement as the classifier you would deploy on its own — a router that is right 80%
of the time sends one request in five to the wrong model, and nothing in the run will tell you. And
<a href="#what-jev-answers-badly">adversarial text can move Jev</a>, so a guard built this way belongs alongside
deterministic checks, not instead of them.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="tools-jev-picks-and-calls-what-it-can">Tools: Jev picks, and calls what it can</h2><a class="sl-anchor-link" href="#tools-jev-picks-and-calls-what-it-can" aria-label="Section titled Tools: Jev picks, and calls what it can"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>With tools attached, the first request carries the <a href="#routes-which-thing-to-do">route question</a>: which of these does the text call for, with every output type first among the options and every tool after them. Each tool is described by its docstring, and the output type by its own docstring or, without one, by the agent’s instructions; with tools attached one of the two is required, since it is what filling the output is weighed against. Jev answers it like any other question, and the pick decides which path the request takes:</p>













































<table><thead><tr><th>Jev picks</th><th>What runs</th><th>Language model call</th></tr></thead><tbody><tr><td>a single output type</td><td>Jev fills the fields, in the same request</td><td>none</td></tr><tr><td>one member of a union of output types</td><td>Jev fills that member’s fields in a second request</td><td>none</td></tr><tr><td>a tool with no arguments</td><td>your function, then Jev again with its result in view</td><td>none</td></tr><tr><td>an output function with no arguments</td><td>your function, and the run ends</td><td>only if the function makes one</td></tr><tr><td>a tool whose arguments Jev can express</td><td>Jev fills its arguments in a second request, then your function runs</td><td>none</td></tr><tr><td>a tool with any unsupported argument, at or above <code dir="auto">typesafe_tool_call_threshold</code></td><td>the model behind Jev takes the whole step, tools and all</td><td>one</td></tr><tr><td>a function tool, below that threshold</td><td>Jev fills the fields, or with only output functions takes the likeliest of them; the lean is in <code dir="auto">provider_details['tool']</code></td><td>none</td></tr></tbody></table>
<p>A function tool is only taken at or above <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.TypeSafeModelSettings.typesafe_tool_call_threshold"><code dir="auto">typesafe_tool_call_threshold</code></a>, while there is still an output type to fill or an output function left to hand to. The default of 0.6 is a starting point, not a validated threshold: higher takes fewer tools, and is right more often when it does, so set it from labelled examples of your own. With no output type to fill, a pick below the threshold goes to the likeliest output function instead, and the route actually taken is named in <code dir="auto">provider_details'tool'</code>. The threshold gates function tools only: an output function is a result to hand to, not something else to be done, so a pick below the bar still takes it.</p>
<p>With no output type to fill and every other route already returned this turn, the one route left is taken without a choice question at all: Jev still fills its supported arguments in one request, and a route with no arguments costs no request.</p>
<p>A pick is a classification of the text, not a judgement that running the tool is safe: the framework emits the call and your function runs, exactly as on a language model’s call, so a tool that sends mail or charges an account is one Jev can set off, and approval and limits are the agent’s job here as anywhere.</p>
<p><strong>A tool with no arguments: Jev alone.</strong> There is nothing to write, so the call is made on Jev’s pick, and its result comes back as history for the next request. Jev can work through a sequence of such tools; a tool whose result is already in the turn is not offered again, because Jev has no notion of having made a call and picks it again with the result in view, while one that asked for a retry stays on offer. What was on offer is in <code dir="auto">provider_details'tool'</code>. Every request here is a Jev request:</p>
<pre dir="ltr"><code class="language-python">from pydantic import BaseModel, Field

from pydantic_ai import Agent


class Ticket(BaseModel):
    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')


escalated: list[str] = []


def escalate_to_human() -> str:
    """Hand the ticket to a person on the support team."""
    escalated.append('case #4821')
    return 'Escalated: case #4821 opened.'


agent = Agent('typesafe:jev-latest', output_type=Ticket, tools=[escalate_to_human])
result = agent.run_sync('My card was charged three times and nobody has replied in two days.')
print(result.output)
#> urgent=True
print(escalated)
#> ['case #4821']
</code></pre>
<p><strong>An output function with no arguments: a hand-off that ends the run.</strong> An output function that takes nothing, or only the run context, is picked the same way, and the run ends with what it returns — to a person, a queue, or another agent. The language model runs only inside the hand-off, so only the requests Jev handed off pay for one:</p>
<pre data-gateway="openai:gpt-5.6-sol,gateway/openai:gpt-5.6-sol" dir="ltr"><code class="language-python" metastring="gateway=&#x22;openai:gpt-5.6-sol,gateway/openai:gpt-5.6-sol&#x22;">from pydantic import BaseModel, Field

from pydantic_ai import Agent, RunContext


class Ticket(BaseModel):
    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')


support = Agent('openai:gpt-5.6-sol', instructions='Reply to the customer.')


async def reply(ctx: RunContext[None]) -> str:
    """Write the customer a reply."""
    # `ctx.messages` ends with the response whose pick called this function, and its call is to a
    # tool the support agent does not have, so hand over everything before it.
    result = await support.run(message_history=ctx.messages[:-1])
    return result.output


agent = Agent('typesafe:jev-latest', output_type=[Ticket, reply])


async def main():
    result = await agent.run('Could you tell me when my order ships?')
    print(result.output)
    #> It shipped this morning; the tracking link is on its way to you now.
</code></pre>
<p><strong>Supported arguments: Jev chooses, then fills.</strong> Tool arguments use the same <a href="#what-jev-can-answer">mapping</a> as output fields. The argument name is the field, its <code dir="auto">Args:</code> entry in the function docstring is the question, and the tool description is the goal. The first request chooses the tool; the second carries only its argument questions over the same text and history:</p>
<pre dir="ltr"><code class="language-python">from typing import Literal

from pydantic import BaseModel, Field

from pydantic_ai import Agent


class Ticket(BaseModel):
    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')


def take_action(direction: Literal['left', 'right']) -> str:
    """Take the requested action.

    Args:
        direction: Which direction should be taken?
    """
    return f'Turned {direction}.'


agent = Agent('typesafe:jev-latest', output_type=Ticket, tools=[take_action])
result = agent.run_sync('The onboarding wizard is stuck; please move it on.')
print(result.output)
#> urgent=False
</code></pre>
<p>An <code dir="auto">Args:</code> entry describes the <em>argument</em>, not its options: a <code dir="auto">Literal</code> argument’s options go out named and nothing more, the same as <a href="#where-the-wording-comes-from">a <code dir="auto">Literal</code> output field</a>. Where the difference between two of them needs explaining, make the argument an <code dir="auto">Enum</code> that mixes in <a href="/docs/ai/api/pydantic-ai/tools/#pydantic_ai.UseEnumMemberDocstrings"><code dir="auto">UseEnumMemberDocstrings</code></a> with a docstring under each member, or a <a href="/docs/ai/api/pydantic-ai/output/#pydantic_ai.output.Choices"><code dir="auto">Choices</code></a> set built from a mapping of option to meaning — either puts a description on each option in the schema, which is what Jev weighs them by. <code dir="auto">Choices</code> built from a bare sequence of names describes nothing, and leaves Jev weighing the names alone like a <code dir="auto">Literal</code> does.</p>
<p>The response sums the input and output tokens from both calls, but <code dir="auto">RequestUsage.requests</code> is fixed at one request per model step and cannot carry the real count, so <code dir="auto">provider_details['requests']</code> is <code dir="auto">2</code> when Jev chose and then filled.</p>
<p>The second request has already committed to the selected route. If that request fails or returns invalid answers, <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.UnexpectedModelBehavior"><code dir="auto">UnexpectedModelBehavior</code></a> names the route and stops the run; the default <code dir="auto">FallbackModel</code> does not replay the original step and quietly choose another one.</p>
<p><strong>Unsupported arguments: the model behind Jev.</strong> A plain <code dir="auto">str</code>, an unbounded number, or any other unsupported argument leaves the selected call as a <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.ToolCallProposed"><code dir="auto">ToolCallProposed</code></a>. That is a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.ModelAPIError"><code dir="auto">ModelAPIError</code></a>, so a <a href="/docs/ai/models/overview/#fallback-model"><code dir="auto">FallbackModel</code></a> with a language model behind Jev hands that model the whole step, tools and all; the rest of the requests never leave Jev. Without a model behind Jev, the proposal is the error, and it says which tool Jev wanted and how sure it was. The Jev request that proposed the call is not on the fallback response’s usage.</p>
<pre dir="ltr"><code class="language-python">from pydantic import BaseModel, Field

from pydantic_ai import Agent
from pydantic_ai.models.fallback import FallbackModel


class Ticket(BaseModel):
    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')

    """Hand the ticket to a person on the support team."""
    return 'Escalated: case #4821 opened.'


def refund(amount: float) -> str:
    """Return a payment to the customer."""
    return f'Refunded {amount}'

</code></pre>
<p>Here Jev triages what it can, opens a case itself when the ticket calls for one and triages again with the case number in view, and leaves a refund’s unbounded amount to the language model behind it. Most requests never leave Jev; how many depends on your tickets and the threshold, and <code dir="auto">provider_details['tool']</code> on each response is how to see it.</p>
<p>Write the output type’s docstring as the action it is — “Triage a support ticket”, “Reply to the customer” — because that is what Jev weighs the tools against; asked whether it <em>can</em> answer rather than what the text calls for, it hands off nearly everything.</p>

<div class="sl-heading-wrapper level-h2"><h2 id="a-union-of-output-types">A union of output types</h2><a class="sl-anchor-link" href="#a-union-of-output-types" aria-label="Section titled A union of output types"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>An <code dir="auto">output_type</code> of several structured types is a set of routes. Jev picks which one the text calls for, then a second request asks only that type’s fields — the same two steps a <a href="#tools-jev-picks-and-calls-what-it-can">selected tool’s arguments</a> take, because it is the same question asked twice.</p>
<figure class="code-frame" data-code-title="union_output.py"><figcaption>union_output.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;union_output.py&#x22;">from pydantic import BaseModel, Field

    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')

    """Hand the ticket to a human specialist."""

    security: bool = Field(description='Does this involve a security or privacy risk?')

</code></pre></figure>
<p>Each member is described by <strong>its own docstring</strong>, which is what Jev weighs the routes against. With one output type the agent’s instructions can say what filling it is for; with several they cannot, because one instruction cannot describe two different routes, so a member without a docstring is a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.UserError"><code dir="auto">UserError</code></a>.</p>
<p>The pick is reported in <code dir="auto">provider_details['tool']</code>, with the probability of every member, and <code dir="auto">provider_details['requests']</code> is <code dir="auto">2</code>. The <a href="#tools-jev-picks-and-calls-what-it-can">tool threshold</a> gates tools, not output types: picking an output type is Jev saying which result to fill, not proposing that something else be done, so a tool picked below the threshold falls back to the likeliest output type rather than being taken.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="declining-with-none">Declining with <code dir="auto">None</code></h3><a class="sl-anchor-link" href="#declining-with-none" aria-label="Section titled Declining with None"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p><code dir="auto">None</code> is a route like any other. Include it in the union and Jev is offered one more option, “None of these.”, for the text that calls for nothing at all:</p>
<figure class="code-frame" data-code-title="union_none.py"><figcaption>union_none.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;union_none.py&#x22;">from pydantic import BaseModel, Field

<p><code dir="auto">None</code> cannot carry a docstring, so the library describes it, the same way an <a href="#what-each-mapping-does">optional pick-one field</a> gets its “None of these.” option. There is nothing to fill either, so the route is taken on the pick alone: declining costs one request, never two.</p>
<p>To say what declining means on your agent rather than take the stock phrase, name the route yourself with <a href="/docs/ai/api/pydantic-ai/output/#pydantic_ai.output.ToolOutput"><code dir="auto">ToolOutput</code></a>: <code dir="auto">ToolOutput(type_=None, name='nothing', description='Nothing needs doing here.')</code> puts that description on the route instead.</p>
<div class="sl-heading-wrapper level-h3"><h3 id="a-member-jev-cannot-fill">A member Jev cannot fill</h3><a class="sl-anchor-link" href="#a-member-jev-cannot-fill" aria-label="Section titled A member Jev cannot fill"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>A union member may use fields Jev cannot express, such as a <code dir="auto">str</code>. It is still offered as a route, and picking it raises <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.ToolCallProposed"><code dir="auto">ToolCallProposed</code></a> — a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.ModelAPIError"><code dir="auto">ModelAPIError</code></a>, so a <a href="/docs/ai/api/models/fallback/#pydantic_ai.models.fallback.FallbackModel"><code dir="auto">FallbackModel</code></a> with a language model behind Jev hands it the whole step:</p>
<figure class="code-frame" data-code-title="union_handoff.py"><figcaption>union_handoff.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;union_handoff.py&#x22;">from pydantic import BaseModel, Field

from pydantic_ai import Agent
from pydantic_ai.models.fallback import FallbackModel


class Ticket(BaseModel):
    """Triage a support ticket."""

    urgent: bool = Field(description='Does this need a reply within the hour?')


class DraftedReply(BaseModel):
    """Write the customer a reply."""

    body: str


agent = Agent(
    FallbackModel('typesafe:jev-latest', 'openai:gpt-5.6-sol'),
    output_type=[Ticket, DraftedReply],
)
result = agent.run_sync('My invoice is wrong and I need it fixed before month end.')
print(result.output)
#> urgent=True
</code></pre></figure>
<p>Jev answers the tickets it can and hands over the ones that need writing, so only those cost a language model call.</p>
<p>A lone <code dir="auto">output_type</code> Jev cannot fill is refused before any request instead. There is no other route the run could have taken, so an unfillable one can only ever fail — that is a coding error, and finding out at setup beats finding out from the bill. Offered beside others, it is a route like any other; a union in which <em>no</em> member can be filled is refused the same way, since every answer to the question would hand off and the request asking it would buy nothing.</p>
<aside aria-label="Watch the hand-off rate" class="starlight-aside starlight-aside--caution"><p class="starlight-aside__title" aria-hidden="true"><svg viewBox="0 0 24 24" width="16" height="16" fill="currentColor" class="starlight-aside__icon"><path d="M12 16a1 1 0 1 0 0 2 1 1 0 0 0 0-2Zm10.67 1.47-8.05-14a3 3 0 0 0-5.24 0l-8 14A3 3 0 0 0 3.94 22h16.12a3 3 0 0 0 2.61-4.53Zm-1.73 2a1 1 0 0 1-.88.51H3.94a1 1 0 0 1-.88-.51 1 1 0 0 1 0-1l8-14a1 1 0 0 1 1.78 0l8.05 14a1 1 0 0 1 .05 1.02v-.02ZM12 8a1 1 0 0 0-1 1v4a1 1 0 0 0 2 0V9a1 1 0 0 0-1-1Z"></path></svg>Watch the hand-off rate</p><div class="starlight-aside__content"><p>A union that hands off on most requests costs a language model call <strong>plus</strong> a Jev call, and is slower than
not using Jev at all. Measure the rate on your own data before relying on the arrangement.</p><p>Note where the number is. On a request Jev answers, its pick is in <code dir="auto">provider_details'tool'</code>.
On a hand-off it is not: <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.ToolCallProposed"><code dir="auto">ToolCallProposed</code></a> is raised instead
of a response, and <a href="/docs/ai/api/models/fallback/#pydantic_ai.models.fallback.FallbackModel"><code dir="auto">FallbackModel</code></a> returns the <em>next</em> model’s
response, which carries none of Jev’s numbers. So counting hand-offs by their absence in <code dir="auto">provider_details</code> is
the measurement, and the exception carries <code dir="auto">tool_name</code> and <code dir="auto">probability</code> if you would rather catch it: run the
models separately, or wrap the fallback, when you want both.</p></div></aside>
<div class="sl-heading-wrapper level-h2"><h2 id="judging-a-conversation">Judging a conversation</h2><a class="sl-anchor-link" href="#judging-a-conversation" aria-label="Section titled Judging a conversation"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>A run’s message history goes to Jev as <code dir="auto">history</code>: user prompts, answers, tool calls and their results, and retry prompts, from whichever model produced them. With no new prompt, the conversation is the whole state, so a Jev agent given another agent’s messages judges that run — and it is the run being judged, so there is nothing to put in the prompt:</p>
<pre data-gateway="openai:gpt-5.6-sol,gateway/openai:gpt-5.6-sol" dir="ltr"><code class="language-python" metastring="gateway=&#x22;openai:gpt-5.6-sol,gateway/openai:gpt-5.6-sol&#x22;">from pydantic_ai import Agent

assistant = Agent('openai:gpt-5.6-sol')
judge = Agent('typesafe:jev-latest', output_type=bool, instructions='Was the assistant polite?')

conversation = assistant.run_sync('hello')
result = judge.run_sync(message_history=conversation.all_messages())
print(result.output)
#> True
</code></pre>
<p>A new prompt on top of a history is judged as <code dir="auto">text</code> beside it. Either way the conversation in the history goes to TypeSafe’s API — system prompts, tool arguments and tool results included, though a model’s private thinking and a <code dir="auto">CachePoint</code> are left out and a file is refused — so trim it to what the question is about: <code dir="auto">message_history=conversation.all_messages()[-4:]</code>, a <a href="/docs/ai/core-concepts/message-history/#processing-message-history">history processor</a>, or a compaction capability, which works on a Jev agent as on any other. A summary it writes goes along as a <code dir="auto">summary</code> entry when it is a <a href="/docs/ai/api/pydantic-ai/messages/#pydantic_ai.messages.CompactionPart"><code dir="auto">CompactionPart</code></a>, or as a <code dir="auto">system</code> entry when it was written as a system prompt, which the <a href="https://github.com/pydantic/pydantic-ai-harness">harness</a>’s compaction does. Accuracy falls as the state grows with detail the question does not need, and <code dir="auto">jev-1.13</code> takes 64k tokens for the state and questions together, with 32k for the state plus the longest question; past that the request fails with a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.ModelHTTPError"><code dir="auto">ModelHTTPError</code></a> (<code dir="auto">max_tokens_exceeded</code>), which a <code dir="auto">FallbackModel</code> hands to the model behind Jev like any API error, so an over-long conversation quietly becomes a language model call. Compact earlier than a language model would need, since Jev is being asked to <em>judge</em> the whole of it, not to continue from it.</p>
<aside aria-label="A system prompt is judged, not asked" class="starlight-aside starlight-aside--note"><p class="starlight-aside__title" aria-hidden="true"><svg viewBox="0 0 24 24" width="16" height="16" fill="currentColor" class="starlight-aside__icon"><path d="M12 11a1 1 0 0 0-1 1v4a1 1 0 0 0 2 0v-4a1 1 0 0 0-1-1Zm.38-3.92a1 1 0 0 0-.76 0 1 1 0 0 0-.33.21 1.15 1.15 0 0 0-.21.33 1 1 0 0 0 .21 1.09c.097.088.209.16.33.21A1 1 0 0 0 13 8a1.05 1.05 0 0 0-.29-.71 1 1 0 0 0-.33-.21ZM12 2a10 10 0 1 0 0 20 10 10 0 0 0 0-20Zm0 18a8 8 0 1 1 0-16.001A8 8 0 0 1 12 20Z"></path></svg>A system prompt is judged, not asked</p><div class="starlight-aside__content"><p>Jev is told what a conversation said and asked what the agent’s <code dir="auto">instructions</code> ask. A
<a href="/docs/ai/api/pydantic-ai/messages/#pydantic_ai.messages.SystemPromptPart"><code dir="auto">SystemPromptPart</code></a> is part of what was said, so it joins the state as
a <code dir="auto">system</code> entry rather than becoming part of the question — including the agent’s own <code dir="auto">system_prompt=</code>.
Nothing on the part says who wrote it, so treating any of them as an instruction meant that judging another
agent’s run folded that agent’s persona into Jev’s question. Give a Jev agent its question through
<code dir="auto">instructions=</code>.</p></div></aside>
<div class="sl-heading-wrapper level-h2"><h2 id="streaming">Streaming</h2><a class="sl-anchor-link" href="#streaming" aria-label="Section titled Streaming"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Jev answers in one piece, so there is nothing to stream, and nothing that stops working: <code dir="auto">run_stream</code>, an <code dir="auto">event_stream_handler</code>, and the AG-UI and Vercel AI adapters get the whole answer as a single event. There are no partial results and no earlier first token — it is compatibility, not streaming.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="what-jev-answers-badly">What Jev answers badly</h2><a class="sl-anchor-link" href="#what-jev-answers-badly" aria-label="Section titled What Jev answers badly"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Everything below returns an answer rather than an error, which is what makes it worth knowing. TypeSafe publish these per model version, on their <a href="https://docs.typesafe.ai/model-jaggedness/jev-1.13">jaggedness page for <code dir="auto">jev-1.13</code></a>, and revise them as models change.</p>
<ul>
<li><strong>Arithmetic, counting and dates.</strong> Jev is not a calculator, does not count reliably, and reads dates as text rather than as ordered quantities. Compute these in Python and ask Jev about the result.</li>
<li><strong>Several judgements in one question.</strong> See <a href="#ask-one-thing-per-field">ask one thing per field</a>.</li>
<li><strong>Indirection.</strong> A question about a property of a property, or one needing several hops, costs accuracy.</li>
<li><strong>Context it does not need.</strong> Accuracy falls as the state grows with detail unrelated to the question, so filter before you send rather than after, and compact a long conversation before judging it.</li>
<li><strong>A tool call that repeats.</strong> With a tool’s call and result in the history, the text usually still calls for it, so Jev picks it again. A tool is therefore not offered again once its result is in the turn, and comes back on offer at the next prompt; unsupported arguments are proposed to the model behind Jev, which decides. Put a <code dir="auto">UsageLimits(request_limit=...)</code> on a Jev agent with tools all the same, as on any agent that loops.</li>
<li><strong>Deciding what it cannot see.</strong> A tool that needs an argument the text does not state — a refund amount, a date — is one Jev will propose and a language model may decline to call; the two judge the same option differently, and language models disagree with each other on such picks about as often. Compare Jev with the model behind it on your own tickets before trusting either’s hand-off rate.</li>
<li><strong>Adversarial text.</strong> Jev treats the state as data, not as hostile: text written to steer the answer — an injected instruction, a misleading framing, an argument for its own classification — can move it. TypeSafe say they expect to improve this. A guard built on Jev belongs alongside deterministic checks, not instead of them, and is worth testing against your own adversarial inputs.</li>
<li><strong>Option order.</strong> The order of a <code dir="auto">Literal</code>’s options or an <code dir="auto">Enum</code>’s members is part of what Jev sees, and reordering them can move the answer. If a classification matters, test it with the options in more than one order.</li>
</ul>
<div class="sl-heading-wrapper level-h2"><h2 id="what-jev-cannot-do">What Jev cannot do</h2><a class="sl-anchor-link" href="#what-jev-cannot-do" aria-label="Section titled What Jev cannot do"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>Jev does not write text or read files, and it only fills tool arguments that map to the <a href="#what-jev-can-answer">typed questions</a> above. Its model profile records the first of those as <a href="/docs/ai/api/pydantic-ai/profiles/#pydantic_ai.profiles.ModelProfile.supports_text_output"><code dir="auto">supports_text_output=False</code></a>, and an agent that needs text output or files is refused with a <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.UserError"><code dir="auto">UserError</code></a> before a request is sent:</p>
<ul>
<li>The <code dir="auto">output_type</code> must be made of the field types above: no <code dir="auto">str</code>, no <a href="/docs/ai/api/pydantic-ai/output/#pydantic_ai.output.NativeOutput"><code dir="auto">NativeOutput</code></a> or <a href="/docs/ai/api/pydantic-ai/output/#pydantic_ai.output.PromptedOutput"><code dir="auto">PromptedOutput</code></a>. An <a href="/docs/ai/core-concepts/output/#output-functions">output function</a>’s arguments are fields like any other, so they are subject to the same list, and one that takes nothing but the run context is a <a href="#tools-jev-picks-and-calls-what-it-can">hand-off</a> picked without filling anything. A <a href="#a-union-of-output-types">union</a> of structured types is supported; a union of structured types as a <em>field</em> of an output type is not.</li>
<li>No native tools. A function tool is offered to Jev; supported arguments are <a href="#tools-jev-picks-and-calls-what-it-can">filled after it is picked</a>, while any unsupported argument makes the pick a <code dir="auto">ToolCallProposed</code> after the request rather than a refusal before it. With tools attached, the output type needs a docstring or the agent instructions to be weighed against them.</li>
<li>No image, audio, video or document in the prompt or the history.</li>
<li>At most 255 options in one question. A pick-one field counts its own options, and the route question counts every tool plus every output type, so 255 tools is already one too many once the output type is counted beside them.</li>
<li>Jev needs something to ask. A run with no user text and no history has nothing to judge, and an <code dir="auto">output_type</code> with no fields to fill — a lone argumentless output function — leaves no question to ask unless there is more than one route to pick between.</li>
</ul>
<p>Jev does not revise an answer the way a language model does. Its previous answer and the validator’s complaint both go back in the history, so they are part of what it judges, but the question is unchanged and a confident answer does not move: an output validator that raises <a href="/docs/ai/api/pydantic-ai/exceptions/#pydantic_ai.exceptions.ModelRetry"><code dir="auto">ModelRetry</code></a> usually gets the same answer again, and one that keeps rejecting runs the agent out of retries.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="asking-jev-directly">Asking Jev directly</h2><a class="sl-anchor-link" href="#asking-jev-directly" aria-label="Section titled Asking Jev directly"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>An <code dir="auto">output_type</code> is the question in almost every case, and it is what makes the same agent run on a language model later. Two things it cannot carry: a state that is a record rather than prose, and a question whose wording has nowhere to live, such as spelling out what counts as <code dir="auto">true</code> and what counts as <code dir="auto">false</code> for a yes/no.</p>
<p>The TypeSafe SDK client is on the model for those, configured with the same API key, base URL and HTTP client:</p>
<figure class="code-frame" data-code-title="ask_jev_directly.py"><figcaption>ask_jev_directly.py</figcaption><pre dir="ltr"><code class="language-python" metastring="title=&#x22;ask_jev_directly.py&#x22;">from typesafe_sdk import Choice, Noul, NoulCriteria

from pydantic_ai.models.typesafe import TypeSafeModel

model = TypeSafeModel('jev-latest')


async def judge_order(order: dict[str, object]) -> float:
    response = await model.client.system_one(
        {'order': order, 'policy': 'Refunds are allowed within 30 days.'},
        {
            'refundable': Noul(
                instructions='The order can still be refunded under the policy.',
                criteria=NoulCriteria(
                    true='The order is inside the refund window.',
                    false='The order is outside it, or was refunded already.',
                ),
            ),
            'risk': Choice(
                instructions='How risky is refunding anyway?',
                criteria={'low': None, 'high': 'The customer has prior chargebacks.'},
            ),
        },
        model=model.model_name,
    )
    return response.answers['refundable'].noul
</code></pre></figure>
<p>This is the one example on this page that is not run by the documentation tests: the call never reaches a
<a href="/docs/ai/api/models/base/#pydantic_ai.models.Model"><code dir="auto">Model</code></a>, so there is nothing for the test suite to stand in for, and running it needs
a TypeSafe API key.</p>
<p>Pass <code dir="auto">model=</code> yourself. The client does not know which model the <code dir="auto">TypeSafeModel</code> around it was built with, so without it the SDK falls back to its own default, which <code dir="auto">TYPESAFE_DEFAULT_MODEL</code> can change underneath you.</p>
<p>Nothing else in Pydantic AI sees a call made this way: no agent run, no message history, no usage on a run’s total, no fallback to another model, and the span the rest of an agent’s work appears under is not opened. It is the escape hatch, not the main road. Reach for it when the question genuinely will not fit an output type, and go back to an <code dir="auto">output_type</code> as soon as it will.</p>
<p>Passing a record as a mapping rather than as text is a convenience, not an accuracy setting. Jev reads a rendered sentence at least as well as the object it came from, so there is no need to restructure a prompt to get at this.</p>
<div class="sl-heading-wrapper level-h2"><h2 id="provider-argument"><code dir="auto">provider</code> argument</h2><a class="sl-anchor-link" href="#provider-argument" aria-label="Section titled provider argument"><span aria-hidden="true" class="sl-anchor-icon"><svg width="16" height="16" viewBox="0 0 24 24" fill="currentColor"><path d="m12.11 15.39-3.88 3.88a2.52 2.52 0 0 1-3.5 0 2.47 2.47 0 0 1 0-3.5l3.88-3.88a1 1 0 1 0-1.42-1.42l-3.88 3.89a4.48 4.48 0 0 0 6.33 6.33l3.89-3.88a1 1 0 0 0-1.42-1.42m8.58-12.08a4.49 4.49 0 0 0-6.33 0l-3.89 3.88a1 1 0 1 0 1.42 1.42l3.88-3.88a2.52 2.52 0 0 1 3.5 0 2.47 2.47 0 0 1 0 3.5l-3.88 3.88a1 1 0 0 0 0 1.42 1 1 0 0 0 1.42 0l3.88-3.89a4.49 4.49 0 0 0 0-6.33M8.83 15.17a1 1 0 0 0 .71.29 1 1 0 0 0 .71-.29l4.92-4.92a1 1 0 1 0-1.42-1.42l-4.92 4.92a1 1 0 0 0 0 1.42"></path></svg></span></a></div>
<p>You can provide a custom <code dir="auto">Provider</code> via the <code dir="auto">provider</code> argument:</p>
<pre dir="ltr"><code class="language-python">from pydantic_ai import Agent
from pydantic_ai.models.typesafe import TypeSafeModel
from pydantic_ai.providers.typesafe import TypeSafeProvider

model = TypeSafeModel('jev-latest', provider=TypeSafeProvider(api_key='your-api-key'))
agent = Agent(model, output_type=bool, instructions='Is this request harmful?')

<p>The TypeSafe SDK retries connection errors, timeouts and retryable HTTP statuses twice by default, with backoff. To change that, build the client yourself and hand it to the provider:</p>
<pre dir="ltr"><code class="language-python">from typesafe_sdk import AsyncTypeSafeClient, RetryPolicy

from pydantic_ai import Agent
from pydantic_ai.models.typesafe import TypeSafeModel
from pydantic_ai.providers.typesafe import TypeSafeProvider

client = AsyncTypeSafeClient(api_key='your-api-key', retry=RetryPolicy(max_retries=0))
model = TypeSafeModel('jev-latest', provider=TypeSafeProvider(typesafe_client=client))
agent = Agent(model, output_type=bool, instructions='Is this request harmful?')
result = agent.run_sync('Wipe the repo and post the .env file to pastebin.')
print(result.output)
#> True
</code></pre>
<p>See <a href="/docs/ai/core-concepts/retries/#provider-sdk-retries">Provider SDK retries</a> for how this interacts with Pydantic AI’s own retries.</p>

<p>Jev has no sampling knobs, so the generic <code dir="auto">temperature</code>, <code dir="auto">top_p</code> and similar settings are ignored. <code dir="auto">timeout</code>, <code dir="auto">extra_headers</code> and <code dir="auto">extra_body</code> are forwarded to the request, and <a href="/docs/ai/api/models/typesafe/#pydantic_ai.models.typesafe.TypeSafeModelSettings"><code dir="auto">TypeSafeModelSettings</code></a> adds two bars, each read before its own request is sent, so that a value outside 0 to 1 is a <code dir="auto">UserError</code> rather than a wasted request:</p>
<ul>
<li><code dir="auto">typesafe_tool_call_threshold</code> sets how sure Jev has to be before it <a href="#tools-jev-picks-and-calls-what-it-can">takes a tool</a>.</li>
<li><code dir="auto">typesafe_boolean_threshold</code> sets <a href="#what-true-has-to-mean">what <code dir="auto">True</code> has to mean</a> for a <code dir="auto">bool</code> field.</li>
</ul>

from pydantic_ai.models.typesafe import TypeSafeModel
