## 2. 产出：今天的恢复步骤

**原则**：运行日志只是事件记录，不是权威状态。工单状态以工单系统为准，邮件是否发出以邮件网关为准。邮件收不回，所以今天只补能补的，不确认就不发信。

**A. 先核对（只读，不动任何东西）**
1. 确认昨晚的进程确实已死，没有调度器或守护进程会自动重启它，也没有第二个实例。
2. 把 40 张工单固定成一份清单，每张记工单号、负责人邮箱。
3. 对 40 张全部查：
   - 工单系统：当前状态，以及批处理开始后有没有被别人改过。
   - 邮件网关：从批处理开始前留一点余量起，到现在，按收件人和时间查发送记录，同时看有没有排队中或延迟的记录。
   - 22 张“两步完成”也一起查，不信日志。日志写的是进程以为发生了什么，不是外部系统里实际发生了什么。
4. 每张分到下表一格。网关只能按收件人和时间查，所以如果同一负责人名下有多张工单，要靠邮件主题或正文里的工单号对应，对应不上就按“停下”处理。

| 状态是已升级？ | 网关有该工单的通知？ | 处理 |
|---|---|---|
| 是 | 是（恰好 1 封） | 完成，不动 |
| 是 | 否 | 只补发邮件 |
| 否 | 否 | 先改状态，读回确认，再发邮件 |
| 否 | 是 | 邮件已出，**只补状态，绝不再发信** |
| 任意 | 是（≥2 封） | 停下，见 C |

那 3 张权限不足的，按原流程应是状态没改、邮件没发，仍按上表归格，不单独处理。

**B. 再做（顺序：先可逆、后不可逆）**
1. 先处理“否/是”：只改状态。改完读回确认。隔几分钟再读一次，确认没被别的自动化改回去。
2. 再处理“否/否”：改状态，读回确认，再发邮件。
3. 最后处理“是/否”：只补邮件。
4. 每张发信前先写本地台账（工单号、收件人、“升级通知”这个身份），再发，再回查网关确认恰好 1 封。
5. 邮件先发 1 封，回查网关确认正好 1 封，再继续。
6. 任何一步超时或返回不明，先回查外部系统，不直接重试。
7. 全部做完后，对 40 张重跑一遍 A.3，核对每张都落在“是/是（1 封）”。交接时写明：哪几张是补做的，哪几张还没完成，由谁接着处理。

**C. 什么情况下停下来找人**
- 网关里同一工单已有 ≥2 封通知：说明已经重复，停止对该收件人的任何发送，报客户事故负责人。
- 网关或工单系统查询超时、报错或只返回部分结果：“查不到”不等于“没发过”，不能当未执行处理。
- “状态未变但邮件已发”无法解释：这违反“先改状态后发邮件”的顺序，有可能是状态写入被回滚或被自动化改回，也可能是写到了别处。查清原因之前，不批量补状态。
- 那 3 张权限不足，或补状态时再次被拒：找有权限的人处理，不换账号绕过。
- 工单当前状态不是批处理前的“逾期”原样（已关闭、已被人改、负责人换了）：不覆盖，不发信，交给工单负责人或值班负责人。
- 网关有排队或延迟，无法确定某封邮件是否已经发出：等到网关明确，或者找网关管理员。
- 收件人与工单对应不上：停下。
