# 最小闭环与 dirty worker 进入法

## 核心模型

历史回答给出的最小闭环是：

```text
真实材料
    ↓
边界明确的 AI 局部加工
    ↓
原 worker 接受 / 修改 / 拒绝
    ↓
保存输入、输出、修改和结果
    ↓
下一次校准 schema、规则和评估
```

这是 assistant 在 T10/A 提出的工作假设；用户在 T10/U 只提出了问题，并未指定某个具体文档或 KPI。

## 闭环的最小输入与输出

回答中建议先允许极简任务契约：

```text
input
  source_document
  task

output
  extracted_facts
  issues
  proposed_action
  evidence
```

这些字段是候选 contract，不是已经批准的 schema。真正需要的字段应从连续真实任务中的人工修改和缺失上下文中长出来（T10/A）。

首个循环应优先选择：

1. 有天然输入件和输出件，例如合同、PDF、邮件、Excel、工单或会议纪要；
2. 一个 worker 或小组可以单独完成；
3. worker 能快速判断结果是否可用、哪里需要改；
4. 不依赖先清洗全量历史数据；
5. 输出可逆，优先是 draft、recommendation、check 或 extract，而不是付款、签署、删除或自动审批（T10/A）。

## 典型候选切面

下列例子来自历史回答，是可供选场景时比较的候选，不是对客户现状的断言：

### 合同到法务复核

```text
合同 + 明确任务
    ↓
条款/字段抽取或初步审查
    ↓
法务修改/接受
    ↓
最终版本与修改轨迹
```

前置的合同来源、OA 流转和后续盖章先不纳入（T10/A）。

### 供应商报价附件到结构化表

```text
邮件中的报价附件
    ↓
抽取价格、付款条件、交付期、异常条款
    ↓
采购确认/修改
    ↓
继续走原流程
```

第一轮不要求 API，可用上传文件或复制粘贴验证（T10/A）。

### 文档覆盖与异常复核

```text
全量材料
    ↓
结构化抽取 + 明确规则检查 + 语义判断
    ↓
异常与证据位置
    ↓
专业人员确认
```

T9/A 用“从抽查到全量基础检查”的示例说明价值叙事；示例数字不是已验证结果，也不是目标承诺。

## 观测什么

不要把首个循环定义为端到端自动化。历史回答建议观察：

- **Acceptance**：结果可直接消费的比例；
- **Correction**：worker 反复修改的字段、判断或措辞；
- **Missing context**：完成任务还需要去哪里找信息，例如历史客户、财务数据或无 API 的 Excel；
- **Coverage**：有多少原来抽查或延迟处理的材料被基础检查覆盖；
- **Review effort**：专业人员复核所需时间/步骤是否下降；
- **Traceability**：每个结论是否能回到来源材料、规则和人工决定。

前四项和“覆盖面而非裁员”叙事来自 T9/A、T10/A；具体度量单位和通过阈值仍待项目定义。

## 从 dirty workflow 学 schema

回答提出了一个倒序：

```text
artifact
  → AI
  → human correction
  → trace
  → schema refinement
  → 下一轮 automation
```

它要求先保留真实修改，而不是先由顾问画完整流程、定义统一 ontology，再把企业数据装进去。这个顺序是建议，不是说所有客户都必须拒绝先验建模；若客户已有可靠 schema，应允许复用并与实际轨迹比对。

## 扩展方向

闭环稳定后，才根据 trace 决定向哪里扩：

- 向前接入数据源；
- 向后接执行或审批系统；
- 横向覆盖更多 worker；
- 把稳定的人类修改规则编译进 schema/evaluator。

这样可以把“接入”当成证据驱动的后续动作，而不是首个 demo 的先决条件（T10/A）。

- 需要定义 trace 的最小隐私、权限、版本和保留规则；本线程没有给出实现细节。
