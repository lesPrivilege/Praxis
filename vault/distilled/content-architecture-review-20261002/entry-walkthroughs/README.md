# 企业工作路线与不该进分支的请求：前后走读

状态：验证记录，2026-10-02。协议、任务内容与评阅由 Opus 5.5 主会话完成；十四次走读由 Sonnet 5.5 代理各跑一次，只读，从仓库根 `AGENTS.md` 起步。Luna 在本会话不可用。评阅者就是改入口的人，不是独立评阅。

## 结论

三条企业工作路线在改动之前就走得通：读 4 到 10 个文件，没有进 `vault`，没有读维护文档，要守住的内容基本都在。审阅担心的“默认深入研究层”在本地这三条路线上没有出现。

断点在两处。不需要 Kit 的小请求会被当成写作任务带进成文分支；个人经营一题的提案没有写出要对方决定的事。入口各补一句之后，这两处都变了。

直接做也有代价：改短一句话时，读了成文分支的那次留下了“整体”，直接做的两次都把它当冗词删了。

## 做了什么

任务取自 [审阅](../README.md)第七节：三条静态走读路线，三个“不该加载 Kit”的反例。内容是主会话写的合成材料，预期在改入口之前冻结，见 [protocol.md](protocol.md)（sha256 `17bf13eb6a781081dec161748c0b6be8a65d823c95fb8d2ca5c2714416d7f791`，冻结于 15:42）。同一份任务书在三个时点各跑一次：

| 轮次 | 仓库状态 | 跑了哪些 |
|---|---|---|
| 改动前 | `b4e22ce`，没有任何改动 | P1–P3、N1–N3 |
| 改动后 | Kit 任务入口加“不是每个请求都要进分支”一段并改正一处链接；Reporting 入口写明产物要有请求、做到就停；工作系统、企业工作面九项、文档结构契约各改一处 | P1–P3、N1–N3 |
| 再改一句后 | Kit 任务入口那一段的后半句，从“守住原文的事实、限定和确定性”改成指向证据底线，并加“要求有两种读法时说出来” | N1、N3 |

## 因为新写的句子而不同的地方

- N1、N2、N3 改动后都引了“不是每个请求都要进分支”这一段，读完任务入口就停。
- P3 改动后的提案引了 Reporting 入口的新句“写明读完要对方批准、选择、修改或执行什么”，并去读了 brief 和组织动作表里“请求决定”一行。P2 改动后把“要负责人周五定的三件事”放到了最前面，引的是同一句。
- P1、P2、P3 改动后都引了“做到这几点就停，不补齐其他候选文体”作为停下的依据。

## 走读暴露的三件事

- “整体”丢了。N1 改动前读了成文原理和审阅方法，把“整体的响应速度”里的“整体”当范围限定留下；改动后和再改一句后的两次都直接做，把它当冗词删了。预期里没有写这一项，哪种读法对没有定论。入口那一句已经指向证据底线，底线里写着“范围、条件和确定性照原样”，再跑的那次读了底线，仍然删了。
- 补零是出题的毛病。任务书说“改成 2026-10-02 这种写法”，又说“别的不动”，`2026/9/7` 该不该补零有两种读法。三次里两次补了、一次没补，三次都说出了另一种读法。入口加了“要求有两种读法时说出来”，再跑的那次改成了请需求方确认。
- 能做出判断的地方，很多不是仓库教的。三条路线的报告都把关键做法的一部分标成“通用知识”：P1 的耗时怎样拆段、什么情况下不做助手；P2 的采用率与正确率分开、盲标加裁决、改过的标签分层；P3 的小时怎样分、免费支持怎样谈成条款。六份报告的“想找但没找到”集中在三处：没有发现备忘录的样例，没有参考答案不可靠时的做法，没有一个人排时间的方法。这与审阅“覆盖面不等于深度”的判断一致，对应关系见 [候选表](../README.md#九类能力语法候选)。

## 限制

- 每个任务每个时点一次，一种模型。前后差别可能只是运行之间的波动；P1、P2、P3 读取量的升降都在两个文件以内。
- 任务是合成的，都很小。
- 评阅者是改入口的人，“守住了什么”一表是主会话逐项看的。
- 代理的上下文里带着本项目的记忆索引和读 `kit/README.md` 时自动附上的 `kit/AGENTS.md`。P1 改动后那次提到用了记忆里的写作偏好。
- 工作系统页、企业工作面九项和文档结构契约的改动，没有任何一次走读经过。
- 没有不读仓库的对照组。三条路线里出自通用知识的那部分，不读仓库多半也做得出来；这次没有测。
- 预期路线里 P1 和 P2 各多写了一页，实际不需要。
- 没有验证任何宿主里的自动发现，也没有真实读者。

十四份原始报告在 [reports](reports/README.md)。
