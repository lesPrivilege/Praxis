# P05 · 消费履约、住宿与空间

顾客买了三件商品、点了一桌菜、订了两晚房，企业就承担了一项有数量、期限和条件的承诺。工程承包商接受变更、物业交出房屋钥匙，也形成承诺。软件帮助不同角色确认：还欠什么，资源是否可用，哪部分已经交付，钱应当如何处理。这些问题互相关联，却很少在同一时刻结束。

本包先建立共同模型，再用五个案例逐步改变它。它也是后续交互教材的内容底稿：读者进入陌生行业时，可以先识别对象、承诺、约束与权威，再选有适用前提的解法，知道下一步查什么、怎样验证。每章末尾提供具体探索入口；状态、事件和检查身份保留在配套 JSON，供本地 Claude 自由编排。金额、经营政策、系统架构、性能目标与故障轨迹均为明确标注的 synthetic 教学设计；公开产品文档只支持相邻引用中的产品事实。以下概念是本包的原创分析，不声称各 provider 内部采用同一模型。

## 像解题一样学习业务系统

每例沿“识题 → 解法 → 演算 → 验算 → 变式”建立判断。识题先找重复结构：一单多去处、多次付款争同一余额、每个时间点可行而全程不可行、同一来源多路径到达、成本与责任不一致。解法为这些结构选择数量分区、尝试占额、区间与排程、集合去重或责任分桶；随后用小数字算一遍，再以守恒、权限和确认依据验算。变式只改变一个条件，使读者看清方法何时仍适用、何时必须增加对象或换方法。

不用背下每个 API 字段，应该记住决定方法的线索。各章开头的识题表把线索与解法、下一步研究方向连接；正文提供因果解释和完整例子，练习检查能否迁移。具体数字和状态示例保留稳定身份，方便后续教材用可视化呈现条件改变后的结果，而不限定呈现方式。

## 从承诺走到可解释的结束

一笔业务至少要分别保存四类记录。**承诺记录**写清买的是什么、价格和条件属于哪个版本；**资源记录**描述商品件数、厨房产能、房夜或可用空间；**履约记录**保存出库、出餐、入住、验收或交还的证据；**资金记录**解释应收、已收、待退款和有争议的金额。所谓“完成”，是这些记录达到本业务规定的相容状态，不能仅靠总状态栏里的一个 `done`。

以三件预付商品为例：付款已确认，仓库只发出两件，第三件取消。承诺数量可核对为 `3 = 2 已发 + 1 已取消 + 0 待处理`；取消的一件又产生待退款义务。退款请求已被受理，仍需资金方确认结果。退回一件已发商品时，累计已发数量依然是二，退货作为新的反向流记录；把累计已发直接减为一，会使“从未交付”与“交付后退回”无法区分。V04 将这个模型展开为可核对的行项目。

资源改变以后，不变量也要改变。一晚空房无法在次日补交给昨晚的住客；厨房已经做出的食物无法通过数据库回滚变回原料；已施工的墙体需要新的施工才能撤除。V05、V06、V15 因而各有自己的补救动作。V16 更进一步：房屋已经归还，押金仍可能处于责任争议中。物理工作结束、合同义务关闭和资金结清要分别证明。

## 权威决定状态，页面解释状态

actor 是承担动作及责任的角色，object 是有身份和历史的业务对象。仓库人员可以确认拣货，客服可以提出退款；这些权限不会因为两个按钮出现在同一页就合并。租户标识 `tenant_id` 指软件客户的隔离边界，租约里的承租人则是业务主体；一个物业软件租户可以管理许多承租人，两者不能共用同一语义字段。

每个对象要指定 system of record，即哪一方对哪项事实负责。本地订单服务决定退款申请是否符合合成政策，支付方对款项执行结果负责，仓库对收回货物的检验记录负责。同一个外部编号还要附 provider account 与 tenant scope，才不会把两个商户的编号 `1001` 当成同一对象。列表、图表和搜索索引只是 read model，即为阅读构造的投影；它们应带版本或核对时间，不能独立批准副作用。

界面发出的 command 是请求。例如“退回 1 件并申请退款”先形成带行项目、金额、授权人和操作身份的请求。服务端检查版本、权限和余额，在本地事务里保存状态及待执行工作。外部调用一旦离开本地事务，就可能出现“对方成功，但回执丢失”。此时 `unknown` 表示缺少知识，应凭同一操作身份查询、对账或人工确认。重新生成操作 ID 会把一次重试变成第二次业务。

撤销也有对象边界。未提交的表单可以丢弃；已入库的错误记录需要更正记录；已经发生的款项或物理交付需要补偿。把这些动作做成一个没有说明的“撤销”，会让操作者误以为所有后果都已消失。各例的故障轨迹会指出恢复责任人、应保留的证据与用户能看到的等待状态。

## 选择技术时先找事务边界

对于首次实现，一个带领域模块的后端和关系数据库更容易把本地约束放在同一个事务中。订单、付款尝试、待发送工作可以同库保存，后台 worker 再执行外部请求。拆成微服务会引入更多交接与恢复责任；只有写入规模、团队边界或独立可用性要求值得承担这些代价时再拆。此处是合成架构选择，不是 provider 技术栈描述。

前端可以用 React/TypeScript 或 Vue/TypeScript 表达多对象状态、表单校验与冲突提示；后端可以用 Node.js 配合共享类型，也可以用 Django 或 ASP.NET Core 利用已有领域代码和事务能力。共享类型减少字段误用，却不能让浏览器成为权限权威。各例进一步说明为什么需要日历、厨房屏、版本差异或责任明细，以及这些界面真正依赖什么后端事实。

关系数据库守住会改变业务结果的约束；缓存适合加速候选列表和读模型，不能凭过期可售数确认最后一间房。消息队列分担等待，业务操作身份和持久化记录解释重放。对象存储保存图纸或验收附件，文件存在只能证明有文件，批准则需另外的证据。选型围绕这些职责展开，避免每章都重复一套产品名。

## 手算、反例与检查

每例选择真正有用的计算：V04 按行分配折扣与退款，V05 分摊共享菜品与组合支付，V06 计算区间占用和连续住宿，V15 沿变更来源去重并核对累计证书，V16 把有依据的扣款与未解决争议分开。计算代价和业务正确性分别解释；算法得出结果以后，仍需事务保护才能让多人同时使用结果。

先手算正文的小输入，再改变一个条件：多一个操作者、少一份确认、晚到一条账单、同编号属于另一商户。每例至少提供两道有短答案的条件变化练习，检验能否保留正确的不变量。

包内 [synthetic_checks.py](synthetic_checks.py) 可用 Python 标准库运行，具体覆盖见 [verification.md](verification.md) 与 [synthetic-results.json](synthetic-results.json)。脚本执行纯计算、有限状态模型和可重复的故障反例；案例 JSON 中的端到端 checks 是后续实现的验收设计。未调用真实 provider、未运行网页，合成模型通过也不能证明数据库并发或资金到账。

## 迁移到其他章节

H01 的承诺、付款与服务权利到了 V04，需要增加数量及反向流；V04 的“子项完成不代表整单完成”可以迁到 V20 多次上门工单；V06 的区间占用可以迁到 V16 的空间使用，但酒店夜数不能定义租约中的法律权利；V15 的技术答复与商业批准分离，可以帮助 V07 理解图纸变更，却不能替代生产放行；X01 的隔离要求贯穿所有 case，但 `tenant_id` 不能替换物业里的租客身份。

迁移时保留对象关系和证据要求，重新验证领域政策。具体 transfer ID、失效条件和交接建议见各例及 [handoff.md](handoff.md)。本地 Claude 可自由改写、排版和制作 HTML/motion；应保留 stable IDs、数量单位、synthetic 边界、产品名和来源强度，使视觉简化不会改变业务含义。
