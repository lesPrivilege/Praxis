## 人工走读

已逐例核对两条服务行的 300 收费、250 认可、200 支付方责任、50 病人责任、50 合同调整；180 支付方到账与 50 病人到账后仍待收 20。付款自身已经全部分配和应收尚未结清分属两个对象。报告修订只生成受影响决定的重审清单，不自动改资金历史；迟到通知依明确版本关系处理，不排序不透明的外部版本号。

按合成正常路径、外部受理后超时、报告更正后旧通知迟到、跨租户重号、相同金额缺引用、同付款跨应收竞争逐一走读。正文中的逐源链接与主张 ID 已对照证据记录；技术选项保留为候选，未写成 provider 内部实现。三道变式都有改变前提、不变量、反例和检查，文末提供陌生行业的调查与最小验证方向。

## 独立审阅裁决

| 发现 | 修订及原因 |
|---|---|
| 只锁应收不能防同一收款分到不同应收时透支 | 已改为同一事务先锁付款预算、再按稳定顺序锁应收；新增两种串行结果及坏竞态反例。实际 PostgreSQL 事务验证仍未执行 |
| 脚本逐项扫描已分配项会使批处理退化为 O(m²) | 已维护 receipt 与 line 累计字典，使合成逐项余额检查平均 O(1)；正文仍将复杂度限定于给定计算模型，不声称性能实测 |
| 付款分配与全部应收结清可能混为一态 | JSON 增加 payment-budget 对象及生命周期，正文解释 180 已全分配、就诊仍待收 20 的并存状态 |

## 实际执行

命令（仓库根目录）：

```bash
python3 vault/distilled/saas-engineering-atlas/packages/health-science/synthetic-v01.py
```

修订后运行 19 项 unittest，无失败或错误。包括金额守恒、重复与内容冲突、缺身份、跨租户、币种与支付方、非法金额、资金/应收上限、乱序版本、影响图、SQLite 重启后恢复未知操作、陈旧提交 CAS，以及共享付款预算两种合法串行结果。

其中三个检查故意构造错误实现：裁决直接当收款多计 20；忽略 tenant 使两条身份合为一条；没有共享付款 gate 使并发旧快照把 180 分成 200。脚本断言这些错误输出与应有不变量冲突，不能称为三次生产故障注入或三次真实数据库并发测试。

SQLite 只证明这个小操作日志在连接关闭重开后可恢复。Ledger、图和两种竞争次序是进程内合成模型。未运行浏览器、PACS、FHIR server、支付方、银行、PostgreSQL 隔离测试、真实并发 ledger、负载或 AI eval。完整仓库检查由整合记录另列，见 [CHANGELOG](CHANGELOG.md)。
