# 从业务承诺到可恢复的系统

一项 SaaS 服务使不同的人能围绕同一件工作作出相容的决定。销售承诺交付，运营证明交付，财务核对收款。各方看的是同一业务的不同部分；系统要保存足够的身份、状态与证据，使一次点击不会悄悄替另一方作出决定。这是本百科组织案例的起点。

## 工作对象连接整条链

每个案例先写一个承诺与一个可检查的结束条件。例如，工单关闭需要完成记录与接收确认，不能只凭列表里消失的一行。接着找出 actor、object、state、action、event：谁有权提出动作，动作针对哪个版本，什么事实允许状态变化，谁能确认变化已经发生。

对象身份跨越页面和系统，状态却往往各有归属。合同的 accepted、发票的 paid、服务的 active 可能同时成立，也可能暂时分离。案例必须说明 system of record（权威记录系统）与 read model（供查询的投影），再解释投影迟到时用户会看到什么。数据库里有一行、外部系统已受理、业务已完成，是不同的证据。

## 四个可互相定位的视角

| 视角 | 读者需要看懂的机制 | 与下一视角的连接 |
|---|---|---|
| 业务 | 承诺、资源、责任、期限、资金与实物流；对象的不变量 | 每个动作指向对象、权限和状态条件 |
| 交互 | 页面上能看什么、改什么、提交什么；等待、拒绝、冲突和恢复 | 每个提交对应 command，每个确认指向权威事实 |
| 拓扑 | 服务、存储、外部 provider、队列与边界；同步调用和异步事件 | 每条边写传递什么、谁接收、失败如何发现 |
| 计算与运行 | 输入规模、计算方法、误差、缓存、并发、恢复、成本 | 每个选择用可观测的正确性和性能条件验收 |

拓扑不是把产品 logo 串起来。`owns` 表达权威归属，`stores` 表达持久化位置，`delivers` 表达事件交接，`depends_on` 表达前提；它们不能互换。对象之间的派生关系也不自动证明数据已经传输。具体边由 [关系类型](relation-types.json)约束，生命周期由对象自己的状态表表达。

## 算法推理与可靠运行分别讲清

算法解释一个输入怎样变成一个结果：匹配订单、筛选候选、累计时间区间、沿图追溯、安排依赖、分配资源或近似估计。可靠运行解释同一结果怎样在重试、并发、宕机和外部不确定性下仍可被正确使用。高效 lookup 不能替代幂等约束，最优排程也不能证明现场已经执行。

| 计算家族 | 直觉与适用问题 | 需说明的代价或反例 |
|---|---|---|
| lookup | 用稳定 key 找一件对象，避免逐条比较 | hash 平均查找可近似 O(1)，树索引查找通常 O(log n)；两者都有存储、更新及具体实现前提 |
| sorting / Top-K | 按一个可解释的顺序先处理最重要的 k 件 | 全排序 O(n log n)，大小 k 的 heap 通常 O(n log k)；平分时要有稳定次序 |
| windows | 把事件按业务时间放入相同窗口再计算 | event time 与收到时间不同；迟到、重叠与补录会改变结果 |
| graph paths | 沿关系解释来源、影响范围或可达性 | 有向边、环与访问权限影响遍历；无权节点不能通过路径泄露 |
| dependencies / scheduling | 先满足前提，再安排可开始的任务 | DAG 的先后关系不等于机器、人员、时间窗都可满足 |
| optimization | 在约束下找较好的资源分配 | 写目标、硬约束、可行解、停止预算；启发式结果不称全局最优 |
| caches | 复用以前的计算，减少反复读取 | 命中率之外还要看失效、租户隔离、冷启动和最坏陈旧时间 |
| approximate computation | 用可说明的误差换空间或速度 | 估计可用于探索，不未经确认用于付款、放行或安全决策 |

上表是本研究的教学分类。复杂度描述的是给定计算模型下的推理，不是服务延迟实测；具体产品算法要另有公开证据。每例选择有实际作用的家族，用一组小输入、一遍人工演算和一个反例说明；按问题查找见 [解题索引](problem-index.md)。

## 从点击走到可观察的业务结果

端到端链条至少覆盖：UI 发起 → 服务校验 → 持久化请求与对象版本 → 外部受理或拒绝 → 事件/轮询核对 → 状态投影 → 用户可见结果 → 业务对账。异步系统可以短暂不一致，但必须说明哪一方尚未确认、多久检查一次、由谁接管失败。

性能参数写成待检验的目标，注明请求量、对象数、租户分布、并发、延迟分位数、错误率与缓存条件。恢复要说明已提交、未提交与结果未知的区分；每个可重试操作都有身份和核对依据。AI 输出如果参与判断，则另外评估错判、漏判、人工修正和拒绝条件；语言流畅不作为业务正确性的替代指标。
