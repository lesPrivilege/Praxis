# 第四章　软件进入组织之后

演示里的发票和工单从干净的初始状态开始，真实组织却带着历史进入系统：有未结清的款项、口径不同的表格、离职人员的待办、已获批准但尚未执行的变更，还有必须继续运转的旧系统。实施的任务，是在这些条件下建立新的工作秩序，并证明旧责任没有在切换时消失。

因此，实施不是“把代码部署完”。购买、配置、迁移、训练、支持、升级与退出都要回到前三章的问题：哪项事实由谁负责，什么依据仍然有效，谁接收下一步。

## 识题：四种角色，四种成功标准

购买者希望投资改善成本、速度或控制；日常使用者希望少返工、能完成工作；管理员需要管理身份、规则、环境和集成；数据负责人需要决定定义、质量、访问与修订。一个人可以兼任多个角色，但这些责任不会因此自动合并。

| 角色 | 容易提出的要求 | 需要进一步确定的成功标准 |
|---|---|---|
| 购买者与业务负责人 | 缩短处理周期、提高自动化率 | 哪段周期、什么分母、减少了谁的工作、是否把负担转给下游 |
| 日常使用者 | 少填字段、批量处理、快速搜索 | 异常时是否有办法推进，交接后能否找到结果 |
| 管理员与运行团队 | 单点登录、权限模板、配置入口 | 角色撤回、集成失效、租户差异与升级时能否持续控制 |
| 数据负责人及 data steward | 统一口径、清洗数据 | 谁有权确定含义、修正错误、接受迁移结果与维护来源关系 |

data steward 常译为数据管家或数据专员，本册保留原词，指日常维护定义、质量与使用规则的职责；它不等于数据库管理员。Microsoft 的数据治理指南把 stewardship、质量、主数据与使用场景放在一起，强调定义与质量有人的责任。[Data management](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/data-management)（`EM-C11`）。

需求冲突要落到具体工作上。购买者要求自动关闭更多工单，使用者担心客户未确认；解决办法不是折中为一个任意比例，而是区分哪些类别有确定验收证据，哪些仍需接收。管理员要求扩大统一角色，数据负责人担心跨法人暴露；应明确角色的作用域和必要数据，而不是给每个人相同访问。

## 解法：先适配工作，再决定怎样扩展

### 标准能力、配置与定制的边界

配置是在产品支持的变化范围内选择行为，例如审批阈值、字段必填、角色映射或模板。定制则引入新的逻辑、对象、交互或集成。不同产品对这两个词的划分不同，所以合同和设计文档应写具体机制，而不只写“低代码可配”。

面对需求，先检查标准流程能否完成真实工作，再判断差异来自法规、商业策略、操作习惯还是历史系统限制。法规和合同条件有其证据；“以前一直这样做”还需要追问原因。不能为了避免定制而损失必要约束，也不能为了复制旧系统而搬入所有偶然复杂性。

| 需求 | 可能的实现 | 必须算进决策的代价 |
|---|---|---|
| 不同法人使用不同金额阈值 | 版本化配置 | 生效时间、旧单据规则、配置测试 |
| 一个新字段仅帮助搜索 | 扩展字段与索引 | 导入、权限、导出、历史空值与升级 |
| 付款前核对另一个系统的证据 | 集成或领域扩展 | 身份映射、失败恢复、配额、支持责任 |
| 完全不同的工作对象与生命周期 | 独立模块或专门产品 | 双系统权威、数据同步、用户切换与退出 |

Microsoft 的扩展指南将可用性、性能、安全、可维护性与后续演进列为扩展时的考虑，并提醒不要直接复制旧方案。可取用的判断是：新功能的价值要连同长期维护责任一起计算。[Extend your solution](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/extend-your-solution)（`EM-C12`）。

成本可以用一个小模型估计。假设标准配置初期 8 人日、每季度维护 1 人日；定制初期 20 人日、每季度维护 4 人日；比较两年共 8 个季度，则分别为 `8 + 8×1 = 16` 和 `20 + 8×4 = 52` 人日，相差 36 人日。若定制每天节约 30 分钟，每年按 220 个工作日、每人日 8 小时估算，两年节约 `0.5×220×2÷8 = 27.5` 人日，单看劳动尚不足以抵偿差额。它仍可能因为降低重大错误或支持必要业务而值得做，但这些理由要另外说明，不能藏在“效率提升”中。

### 迁移是在转交未完成的责任

迁移首先决定哪些数据需要进入新系统。通常要区分配置数据、主数据、未结交易、历史记录与附件。它们的用途和载入顺序不同。Microsoft 的迁移指南区分 configuration data 与 migration data，并要求明确范围、映射、依赖、角色和切换前后活动。[Configuration and migration data](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/data-management-configuration-data-migration)（`EM-C13`）。

只核对导入条数不够。100 张旧工单变成 100 张新工单，可能已经丢失批准版本、附件关系或客户接收状态。迁移映射至少包括旧 ID、新 ID、身份范围、状态语义、时间语义、数量金额单位、缺失字段策略与来源。不能把旧系统的 `done` 无条件映射成新系统的 `accepted`。

主数据清洗也不能简单“同名合并”。两个供应商可能同名不同法人，一个供应商也可能改过名称。合并要保留别名和旧标识，使未结发票、银行核对与历史追溯还能找到原对象。无法确认的记录进入异常队列，由数据负责人裁决；缺值不可被随意补成有利于流程继续的默认值。

### 切换需要明确唯一执行方

切换计划应把时间、责任人与条件写到同一张可执行表中。全量迁移可以在旧系统继续运行时预演；正式切换要处理最终增量、冻结窗口、在途操作和旧系统的写入边界。两个系统可以同时提供查询，但对同一业务意图，谁有权发出新的外部动作必须明确。

最危险的是重复接管。旧 worker 已发出变更但还没收到结果，新系统把导入状态解释成“尚未执行”，于是再次发送。正确做法是同时移交操作身份和不确定性，先核对再决定下一步。切换结束条件必须包含在途与异常清单的去向，不能只写“导入完成”。

回退也有分界。如果新系统尚未产生对外效果，恢复旧入口通常较简单；若已经创建外部操作，回退要携带这些新事实，防止旧系统重发。可以先暂停新写入、核对操作、决定哪些义务留在新系统完成，再恢复相应入口。恢复数据库备份不等于恢复现实世界。

### 训练与支持必须覆盖异常工作

训练的单位应是一件完整任务，而不是菜单导览。采购人员要能说明为什么发票被阻塞、怎样取得修订；资金人员要知道未知付款不能另起一笔；服务负责人要能区分“已应用”与“已接收”。讲解成功路径之后，让使用者独立处理一次过期批准、一次部分完成和一次回执丢失，比只记录观看时长更能说明准备程度。

Microsoft 的训练指南将训练目标与用户实际工作联系起来，并明确训练持续到上线之后。它支持按角色和任务设定可观察目标的做法。[Training strategy](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/training-strategy)（`EM-C14`）。

支持团队需要接收运行责任：哪些时段提供服务，什么问题由业务负责人、内部技术团队或供应商处理，超时怎样升级，何时允许临时访问。服务水平协议（Service Level Agreement, SLA）定义响应和恢复承诺时，应区分两者。Microsoft 的支持指南把范围、团队与运行安排分开，并要求在上线前检查准备程度。[Transition to support](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/transition-to-support)（`EM-C15`）。

### 升级与技术债改变未来的工作成本

配置、扩展、集成和训练材料都会随版本演进。升级不能只问新版本能否启动，还要问旧动作、旧状态、旧事件和在途任务是否仍能被理解。接口新增字段通常可以兼容，改变同名字段的含义却可能静默破坏工作；新增状态值也需要调用方明确处理，不能默认落入“成功”。

把这些依赖登记为可维护资产：每项定制有业务原因、负责人、契约测试、运行指标与退出条件。技术债不只是代码难看，也包括无人拥有的配置、无法重建的手工操作和没人知道含义的状态映射。偿还顺序由受影响的工作与风险决定，而不是只统计代码行数。

测试随版本持续进行。系统集成测试（System Integration Testing, SIT）检查连接与数据流，用户验收测试（User Acceptance Testing, UAT）检查真实角色能否完成约定工作。Microsoft 的测试指南把测试作为持续活动，并要求范围、进入与退出条件及结果跟踪。[Testing strategy](https://learn.microsoft.com/en-us/dynamics365/guidance/implementation-guide/testing-strategy)（`EM-C16`）。一组适配器契约通过，可以证明其消息理解符合预期；实际工作接收仍有独立的验收目标。

### 退出是系统设计的一部分

退出能力应在购买时就调查：哪些对象、关系、附件、历史和配置可以导出；什么格式保留身份；在途操作如何完成；哪些资料按合同与适用政策保留，哪些可以删除；服务终止后谁还能查询证据。逗号分隔值（Comma-Separated Values, CSV）导出按钮只能证明能导出某些字段，不能证明新系统可以重建原工作。

退出演练可以选一组有修订、有附件、有未完义务的对象，导入独立读取工具，再回答三件事：能否找到当前状态，能否说明决定依据，能否继续剩余责任。完成导出与完成删除也分开记录；备份、归档、保留义务和访问撤销各有自己的处置范围，不能承诺一个按钮具有普遍法律效果。

## 演算：EM-E02 在切换日接管旧工作

服务变更系统准备从旧平台迁到新平台。迁移范围是 20 项未关闭变更。它们实际处于四组状态：12 项已获批但未执行，5 项外部效果已确认但待负责人接收，2 项发送后结果未知，1 项因缺少授权附件而阻塞。20 项都必须有去向。

先建立映射，再允许新系统执行。12 项批准逐项核对范围与有效期；本例均仍有效。5 项携带外部操作引用与效果版本，直接进入待接收。2 项携带原操作身份进入核对队列。缺附件的 1 项进入人工补件队列，不能为了凑齐“迁移成功率”把它改成已批准。

切换当日的安排如下。时间均为 UTC，时长是本例演练输入。

| 时间 | 动作及负责方 | 继续条件 |
|---|---|---|
| 19:30 | 业务负责人冻结新提交；旧执行器停止领取新操作 | 确认无新增领取，已有在途操作清单固定 |
| 19:35 | 数据团队导出最终增量与旧新 ID 映射 | 20 项全部具有去向；附件与引用可访问 |
| 19:45 | 新系统导入并核对状态、批准与操作身份 | 12 ready、5 awaiting_acceptance、2 unknown、1 blocked |
| 20:00 | 有权运行人员核对两项 unknown | 按原键查询，未产生新业务意图 |
| 20:10 | 其中一项查到已应用，另一项仍无法确认 | 分布变为 12 ready、6 awaiting_acceptance、1 unknown、1 blocked |
| 20:15 | 负责人决定开放明确可接管的工作 | unknown 与 blocked 保持专门责任人，新旧执行方没有重叠 |

这里可正常进入新平台处理的记录有 18 项，占 90%；余下 2 项仍被完整接管为异常责任。它不等于 90% 的工作已完成，更不等于其余 10% 可以丢弃。若业务要求所有在途状态在切换前查明，20:15 的决定就应是继续暂停。切换规则要先确定，不能看到结果后再改口径。

给 6 名运行人员做任务训练，其中 5 名能独立完成“查找原操作—核对结果—交接接收”，1 名在 unknown 时新建了操作。任务通过率为 `5/6 ≈ 83.3%`。若执行岗位要求全部通过，则这 1 名先补训、再考核，或由合格人员值守，不能用“培训完成率 100%”代替操作准备程度。

再做出口演练：导出这 20 项工作、20 个旧新 ID 映射、18 项可常规推进记录的依据，以及 2 项异常责任记录。读取工具必须保留 1 项 unknown 的原操作键和 1 项 blocked 的缺件原因。历史资料是否全部迁入另由范围定义；本例仅移交未关闭工作，并保留旧历史查询入口与访问责任。

## 验算：从数量核对走到责任核对

| 层次 | 本例验算 | 能发现的错误 |
|---|---|---|
| 集合 | 切换前后均为 20 个不同业务 ID | 丢单、重复导入、同号合并 |
| 状态 | 初始 `12+5+2+1=20`；核对后 `12+6+1+1=20` | 把 unknown 直接变 ready 或 closed |
| 权威 | 每项批准、效果、接收有正确来源 | 用旧列表状态替代实际外部结果 |
| 动作 | 两项 unknown 沿原操作键核对 | 新旧系统重复提交 |
| 人员 | 6 人中 5 人任务通过，执行职责有安排 | 以出勤代替能力 |
| 退出 | 导出后能重建当前义务和依据 | 只导出摘要字段，丢失关系与在途责任 |

检查必须能揭示错误，而不只是证明每一步被勾选。故意把一个 unknown 映射成 ready、删掉一个附件关系、复制一个业务 ID，才能确认迁移校验是否会挡住这些问题。本册实验提供数量与状态映射的反例检查。

## 变式：经营条件改变之后

**变式一：切换窗口从 45 分钟缩短为 15 分钟。** 不变的是责任与数据核对标准；可调整的是提前预载、增量范围、业务批次和开放节奏。不能把核对步骤删掉来满足时间。以真实演练耗时决定能否切换，若最终增量、核对与批准无法在 15 分钟内完成，就调整范围或窗口。检查最后一笔旧系统写入是否已进入新系统，以及冻结是否真正生效。

**变式二：收购一家新公司，供应商编号可能重复。** 身份范围变了。主键映射加入法人或来源系统，先保留两个独立对象，再根据确证关系合并；历史发票与付款引用跟随原身份。检查两个公司都存在编号 `1001` 时，金额、附件、权限和退出导出均不串联。

**变式三：供应商升级后新增状态 `applied_with_warning`。** 如果业务并未定义警告是否可接受，调用方不能按字符串前缀把它当作 applied。适配器返回显式契约不匹配，操作保留待核对；待业务与技术负责人定义语义并补充测试后再接纳。检查 fake 和 HTTP 适配器都拒绝未识别状态，避免只有演示继续成功。

**变式四：标准配置每天节省的时间变成 60 分钟。** 若增加的节约确实来自定制且持续两年，劳动收益变成 `1×220×2÷8 = 55` 人日，超过前述 36 人日增量成本。仍需计入使用覆盖、支持故障和可替代方案，但决定依据已改变。检查节约是否只是从录入人员转移到数据团队，不能把转移劳动计算成净收益。

## 在陌生业务中继续调查

第一次进入一个行业，可以先带回六件相互关联的材料：一件正常完成的工作、一件失败工作、一份承诺、一份执行证据、一条例外规则和一个接收标准。把它们连成对象与状态，再向实际负责的人确认关系。比起先画覆盖全行业的大图，这样更容易暴露错误前提。

下一步取决于发现的缺口。若身份混乱，先查主数据与范围；若批准失效，查版本与生效条件；若外部结果常常未知，查操作账本、查询与支持路径；若使用者继续绕开系统，观察哪一类工作没有入口；若升级困难，追查定制的契约与所有者。每次调查都要能产生一个小而可验证的改进，并明确它没有解决的剩余责任。

[33 个案例的机制入口](case-connections.md)提供了这些方向的对照。真正可迁移的不是“这个行业也有审批表”，而是你已经能指出：哪一种事实允许哪一次变化，哪一种条件变化会使原方法失效，以及用什么观察判断工作已经完成。
