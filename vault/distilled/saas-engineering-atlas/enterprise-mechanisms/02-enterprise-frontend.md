# 第二章　企业前端的语法与契约

上一章的采购链有五类事实、数个责任人和一个暂时未知的付款结果。用户不会逐条读数据库记录。他需要先发现异常，再理解依据，作出有权作出的决定，最后知道决定是否生效。企业界面的结构，应当帮助人完成这条判断链。

表格、表单、详情页、工作台、看板、批量操作和设置因此反复出现。它们不是行业的皮肤，而是不同工作方式的表达：比较一组对象、提出一项变更、检查一件对象、处理持续队列、观察整体、对集合行动，以及修改未来动作使用的规则。页面可以采用不同视觉风格，这些语义责任仍需有人承担。

## 识题：从用户正在作出的判断选页面

先问用户本次打开页面要决定什么，才能选择信息密度与动作位置。一个主管每周找异常，和一个会计每天处理几百张发票，可能读取相同对象，却需要不同工作面。

| 判断任务 | 合适的工作面 | 页面必须保留的后端含义 |
|---|---|---|
| 在同类对象之间比较、筛选、排序 | 表格或列表 | 查询范围、稳定身份、排序与分页语义 |
| 提出新事实或修改既有事实 | 表单 | 字段规则、草稿、版本前提、提交结果 |
| 判断一件对象是否可以推进 | 详情页 | 证据、关系、历史、可用动作及拒绝原因 |
| 连续处理队列，边查证边行动 | 工作台 | 任务归属、领取冲突、交接与下一件 |
| 观察趋势、分布和异常 | 看板 | 指标定义、分母、时间、数据新鲜度与下钻集合 |
| 给明确集合执行相同动作 | 批量操作 | 选择范围、逐项版本、部分成功与恢复 |
| 改变规则、角色、模板与集成方式 | 设置 | 配置作用域、生效版本、影响预览与审计 |

页面名称不决定它的职责。一个“管理控制台”可以同时含这些工作面，一个“详情抽屉”也可能承载完整决策。判断的标准是用户能否看到足够依据，并把动作结果追到权威记录。

## 解法：让每一种语法有确定契约

### 表格让比较成为可重复的动作

表格适合把同一种对象的同一属性放到相同位置。会计沿列比较金额、到期日与异常原因，比逐张打开卡片更容易发现偏差。列数增多不是天然错误；错误在于把无助于当前判断的字段，与必须看到的字段混在同一层。

以待匹配发票表为例，首要列是发票身份、供应商、币种金额、匹配状态、阻塞原因和下一责任人。创建时间、解析器版本等可在详情中保留。长名称需要可访问的完整文本；金额不能因省略而隐藏币种；排序不能让空值悄悄成为最大金额。

后端查询必须回答：搜索哪些字段，过滤条件怎样组合，排序发生在整个结果集还是当前页，同值时怎样稳定排序，翻页期间新增记录怎么办。一个可行契约是以 `(due_at, invoice_id)` 建立稳定次序，游标保存查询与排序条件；要求冻结批量集合时再返回快照身份。普通浏览不一定需要数据库快照，但不能把不停变化的列表声称为“已选全部的固定集合”。缓存键还必须包含租户、权限范围和查询条件。

Carbon 把全表工具栏、逐行动作与批量动作分开；进入批量模式后，它建议禁用逐行动作，帮助用户看清当前作用范围。这一规则的可迁移部分是减少作用对象的歧义，而不是照搬按钮数量或尺寸。[Data table](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines)（`EM-C03`）。

表格是否需要变成可编辑 grid，应由交互决定。只呈现数据时，原生表格往往足够；进入单元格导航、编辑和选择后，需要管理焦点、方向键与编辑模式。W3C APG 对 grid 明确描述了这些键盘责任；给一个普通表格加 `role="grid"` 并不会自动实现它们。[Grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)（`EM-C04`）。

### 表单把输入变成有依据的请求

表单不是数据库表的直接投影。用户知道的是“修订发票”，而不是“更新 invoice 表的一些列”。系统应让用户填写本次动作真正需要的字段，并展示必要依据：原金额、修改原因、附件关系、变化后影响。不可编辑字段与当前值一起显示，能减少重复输入和误认。

本例发票修订表单接受数量、对应供应商修订凭据与原因，金额按已确认单价计算。提交时带 `invoice_id、expected_version、operation_id`。服务端检查字段类型与范围，再检查业务约束与权限。客户端即时校验减少无效输入，不能替代服务端决定。

草稿和提交必须分开。自动保存草稿可以恢复意外关闭的输入；“已保存草稿”不表示已经提出正式请求。正式提交后的超时也不能退回为“没有保存”。恢复页面应查询同一操作身份，告诉用户当前是未受理、受理后等待、明确拒绝还是结果未知。

错误应连接到用户可以改动的地方。GOV.UK 的 error summary 模式同时提供页首错误摘要与字段旁错误，并将摘要链接到字段、管理键盘焦点。这支持在长表单中帮助用户找到问题的做法。[Error summary](https://design-system.service.gov.uk/components/error-summary/)（`EM-C05`）。但“验收不足”不是一个可让会计随意改数量消除的输入错误；它应显示为业务阻塞，指向验收责任人或有依据的修订动作。

### 详情页使一项决定可被解释

详情页围绕一件对象组织信息，但不能只显示它自己的字段。决定发票能否付款，需要采购承诺、验收数量、已分配数量、当前发票版本与授权。关系是决策依据，不是装饰性的“相关记录”。

详情页可依次回答：我正在看什么版本，目前到了哪里，依据是什么，有哪些分歧，谁可以做下一步。活动历史应区分用户提交、服务接受、外部确认和业务接收；把它们都写成“操作成功”会抹去关键差别。正文附件、权限敏感内容和过期引用也要沿自身权限读取，不能因为详情页能打开就默认全部附件可见。

长时间操作应有可重新进入的操作记录。用户刷新、离开或换设备，不应失去查询付款结果的入口。临时 toast 适合提醒发生了变化，不能承担唯一回执。

### 工作台围绕责任队列安排动作

工作台适合持续处理一类工作：左侧挑待办，中间看证据，右侧执行动作，是一种常见安排；也可以用多窗口、全屏详情或其他结构。真正要解决的是任务切换时上下文和责任不能丢。

领取任务不等于拥有业务对象。一个操作员打开了发票，另一个人仍可能更新验收。若需要排他处理，后端要有领取者、租约或显式分派；若允许并行，只需在提交时检测版本冲突。不要用“当前在线”图标暗示已经锁定对象。用户离线、请假或浏览器崩溃后，任务要能被重新分配，已有草稿与正式动作分别处理。

队列也不是只按创建时间排序。等待外部回执、等待另一部门补件和等待本角色行动是不同等待原因。把它们混成一列“待办”会让用户反复打开自己无能为力的记录。队列应显示下一责任人、下一可行动时间与升级条件；计时规则要明确是否暂停以及为何暂停。

### 看板解释集合，不能制造完成证据

看板减少查看全量记录的成本，适合发现“本周异常率上升”“某队列积压”。每个指标都要有对象、过滤条件、时间口径与分母。本例“处理率 90%”至少可能指 9/10 张发票被处理，9/10 台到货已合格，或者 9/12 台承诺量已结算。三个数字回答不同问题。

下钻要保存指标使用的集合和口径。看板显示昨天 18:00 的快照，点击后却打开实时全量列表，数字不一致时应能解释。已收到但尚未投影的外部回执，也应体现在数据新鲜度与待核对数量中。图表的绿色不能越过证据链直接关闭工单。

### 批量操作改变规模，也改变错误处理

“全选”首先是集合问题：当前页 25 条，还是满足筛选的 2,430 条？本例采用两阶段交互：先形成可见的候选集合，再预检权限、状态和版本，最后确认动作。预检只是帮助理解影响；正式执行仍需逐项重验。

批量更新可以采用全有或全无，也可以逐项独立完成。选择取决于业务：同一张凭证的借贷行可能需要一起成立；不同供应商的发票通常应能分别处理。若允许部分成功，结果记录必须逐项包含对象 ID、使用版本、操作 ID、状态与原因。重试失败子集，不能重新发起全部已成功项目。

取消批任务意味着停止尚未执行的部分，已发出的外部操作仍需核对。页面必须保留“已完成、未开始、结果未知”的分别计数。用进度条到达 100% 表示任务遍历完毕可以，但文案要解释其中的失败与待核对项。

### 设置是未来动作使用的规则

金额阈值、角色映射、计价模板、营业日历和集成目标都会改变后续行为。设置页因此也是业务工作面：谁能提议，谁批准，在哪些组织生效，何时生效，旧单据用旧规则还是重算新规则。

配置预览应使用代表性输入展示差异。例如把“必须验收”改为“仅需收货”，应显示哪些在途发票会改变资格。批准配置的人不一定有权批准这些发票本身。实施时要保存配置版本、变更理由和回退方案；第二章的表单版本问题在设置页仍然成立，只是影响对象变多了。

## 演算：把 EM-E01 的事实接到页面

会计从“待处理发票”进入 `INV-9`。列表使用简洁状态“等待验收或单据修订”，详情展开为“采购 12 台；已收 10；合格 9；本票 10；可用合格量 9；缺口 1”。解释来源与相关记录可直接进入，用户无需猜测红色标记的原因。

取得供应商修订后，会计提交版本 2 的 9 台发票，后端确认 720,000 分与有效依据一致，并返回新版本。点击“匹配”产生操作 `MATCH-17`，成功后显示占用 9 台、剩余合格量 0。资金人员随后进入独立付款动作，看到金额、收款目标的已确认版本与依据；同一会计页面的“匹配成功”不能替代这一步授权。

一次简化的命令与响应可以写为：

```json
{
  "command": "match_invoice",
  "object_id": "INV-9",
  "expected_version": 2,
  "operation_id": "MATCH-17",
  "evidence_versions": {"PO-17": 1, "INS-9": 1},
  "rule_version": "PUR-3"
}
```

操作者与租户来自服务器已经验证的会话；请求里即使声称另一个租户，也不能改变访问范围。返回值至少区分已接受、已拒绝与版本冲突；异步动作另提供可查询的操作身份。

| 服务端结果 | 页面显示 | 用户下一步 |
|---|---|---|
| 匹配完成，分配 9 台 | 已形成付款资格，720,000 分 | 有权人员进入付款授权 |
| 版本冲突，验收已改 | 展示原依据与当前差异，保留输入 | 重读差异并重新提交 |
| 权限拒绝 | 动作没有执行；说明所需角色或交接路径 | 请求适当责任人处理 |
| 付款已提交但响应中断 | 同一 PAY-17 结果待核对 | 查询原操作，不创建新付款 |
| 银行已结算、列表投影未到 | 操作详情已有确认，列表正在同步 | 保留权威结果并刷新投影 |

再看一个批量变式：会计选择 4 张发票，预检显示 A、B 可匹配，C 缺验收，D 无权限。确认时集合冻结为 A、B。执行前 B 又被修订；A 成功，B 冲突。批任务应报告候选 4、排除 2、提交 2、成功 1、冲突 1，各类别不能混用分母。修复 B 后仅重试 B；A 的分配不得增加第二次。

## 验算：沿动作穿过每一层

视觉检查应与业务检查相连。表格列对齐，帮助用户比较同类数量；错误摘要能聚焦，帮助修正输入；操作页能重新进入，帮助恢复未知结果。这些性质都可以用具体场景检查。

| 场景 | 界面与后端共同通过的条件 |
|---|---|
| 同号异租户发票 | 搜索、详情、附件、缓存和批任务都留在授权范围 |
| 点击提交后刷新 | 依据 operation ID 找回结果，未重复形成意图 |
| 详情停留期间版本改变 | 提交被拒绝或按明确合并规则处理，不能覆盖未知修改 |
| 批量部分成功 | 成功记录有回执；只重试失败项；未知项单列核对 |
| 键盘处理一张异常发票 | 选择、详情、证据、提交、错误恢复全程可达，焦点不丢失 |
| 看板数字与列表不同 | 能定位时间、范围或投影延迟差异，指标口径可复算 |
| 修改设置 | 能看见作用域、版本、有效时间和受影响对象；执行时按指定规则重验 |

空状态也有业务意义：真的没有待办、筛选无结果、没有权限、数据尚未载入是四种情况。将它们都渲染为“暂无数据”，会让用户在最需要判断时失去依据。

## 变式：选择范围与工作节奏改变

**变式一：批量动作从“标记已阅读”改成“发起付款”。** 集合选择可以复用，但后果和完成条件改变。需逐笔绑定金额、目标、授权与唯一操作身份，未知结果保留核对路径，取消仅影响未发送项。检查重试整批时，已发出的付款引用没有变化，且新身份不能绕过仍在途的业务义务。

**变式二：用户从办公室电脑转到仓库手机。** 同一对象与权限保留；狭窄屏幕可能适合卡片和逐件确认，而不是横向缩小几十列表格。必须保留编号、数量、单位和异常原因，离线草稿注明尚未提交。恢复网络时重新检查版本；“离线确认 10 台”不能覆盖另一人已经记录的退货。

**变式三：看板显示“90% 完成”，负责人要据此关闭采购单。** 先识别分母。9 台已结算占 10 台到货的 90%，但只占 12 台承诺的 75%。关闭取决于剩余 3 台如何处理及相关接收条件。检查下钻对象与承诺量，不能把一个视觉进度直接变成关闭命令。

当界面能讲清这些条件时，agent 才有可能使用同样的工作语义。下一章把页面中的对象、动作和完成条件进一步分开，形成可以被工具调用消费的契约。
