# 0 · 先写题目，再选算法

## 识题：把“做一个工作台”变成可回答的问题

H02 的采购工作台上有订单、收货单、发票和付款按钮。若需求只写“自动匹配后付款”，AI 很容易把几张卡片连成漂亮流程。真正需要先回答的是：按什么身份匹配、多少已验收、哪些数量已被别的发票占用、差异由谁批准。界面中的一行不是完整题目。

一张可计算的题纸有五项：输入快照、输出、硬约束、目标、确认依据。把“处理发票”改写为：给定同一租户内某采购行的订购量 10、有效验收量 7、已占用量 4，新发票申请占用 3；判断能否再匹配，并输出占用后的余额。硬约束是累计占用不超过有效验收。采购行、验收修订版、发票行均须有稳定身份。金额和数量不混成一种单位。

## 解法：先守住关系，再减少工作

先用最直接的方法算：剩余可用量 = 有效验收量 − 已占用量。这个式子描述输入和输出之间的关系；数据怎样被安全读取和更新，是另一道题。

算法课里的**不变量**是全过程都要守住的关系。例如“占用量 + 可用量 = 有效验收量”。它比“按钮变绿色”更有用：换 UI、数据库或框架，关系仍能检查。**前置条件**是方法开工前必须成立的事实，如数量同单位、对象同租户、验收修订已选定。**后置条件**描述成功返回后必须成立的结果，如新占用量为 7。把前置条件遗漏，正确公式也会产生错误业务结果。

## 演算：先算一次，再让两个人同时算

单次计算：`7 − 4 = 3`，申请 3 恰好可放入，提交后的占用为 `4 + 3 = 7`，余额为 0。

再放入两个操作员 A、B，两人都读到旧占用 4，各申请 3。两份独立算式都得到“可放入”；若两次申请都生效，占用会到 10，超出验收量 7。即使程序把占用字段都覆盖成 7，也只是把一笔申请丢掉，账面数字漂亮而事实已错。

因此，服务要把“核验余额并占用”放进同一受保护的提交边界，例如带版本条件的更新、行锁或适当隔离的事务。若 A 先把版本 8 改为 9，B 用版本 8 提交就应得到冲突，再读取并重新判断。公式负责计算正确性；事务、唯一约束和版本负责竞争下的状态正确性。这两者不能互相代替。

## 验算：用三个尺度看代价

第一种尺度是数据量。逐个比较 n 条发票和 m 条收货记录需要至多 n×m 次候选比较；按完整业务键建立映射后，可用约 n+m 次建表与查询完成候选配对，仍需逐项核验金额、数量和版本。第二种尺度是工作分布：一百个均匀租户与一个占九成请求的热点租户，争用情况不同。第三种尺度是跨边界代价：一次网络调用、磁盘读页、锁等待，可能比几千次内存加法更慢。

O(n) 表示工作量随 n 成比例增长的阶，不表示 n 毫秒。对一百万条数据，线性扫描约检查一百万项，二分约缩小 20 次，但后者需要有序且可随机访问；把无序原件排好本身有成本。缓存命中 1 毫秒与未命中 100 毫秒是需要实测的延迟，不能从 O(1) 推导出来。

练习：把 10 条扩大到一百万条，先查一个 ID 再做一次加法。应优化哪部分？答案是先测查找、I/O 和等待，通常没有理由优化那一次加法。把对象换成十万字文本，hash 的计算也要读文本，不能只写 O(1) 而忽略键长 L。复杂度的计算模型参见 [MIT Hashing，Comparison Model / Word-RAM](https://ocw.mit.edu/courses/6-006-introduction-to-algorithms-spring-2020/ce9e94705b914598ce78a00a70a1f734_MIT6_006S20_lec4.pdf)，证据标识 `FND-SRC-mit-hash`。

## 变式：把同一个结构迁到另一行业

V04 的库存预留也有“可用资源减已占用”的结构；V19 的工时计费上限则把单位换成金额。保持不变量以前，先问资源是否可撤销、是否可分割、是否需要有效期。把 V06 的房间当总数相减就会失败：今晚空一间、明晚空一间，可能不是同一间房，连续住宿需要同一资源的区间可用。

给 AI 的下一份任务可以写成：“先列对象身份、单位与不变量；用 7、4、3 演算；再给出两个并发申请的反例；指出哪一步需要数据库保证；最后画出 pending、confirmed、conflict 的页面状态。”从这个小输入开始，研究真实产品的对象状态、API 幂等语义、隔离级别与查询计划，才知道该换算法还是该补系统边界。
