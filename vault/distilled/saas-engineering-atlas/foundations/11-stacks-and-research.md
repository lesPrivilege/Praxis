# 第十一章：用成熟能力承接方法

选择技术栈时，先把要守住的业务不变量和要实现的工作列出来。表单、授权、事务、查询、文件、队列和观测分别由谁承担，决定了需要哪些能力；框架名字只在这个分工确定之后有意义。

## 识题：团队已经会什么，系统缺哪种能力

一个几十人使用的审批工作台，可能用服务器渲染页面、一个业务应用和关系数据库就能闭合。一个需要复杂拖拽、离线编辑或大量交互状态的产品，可能更适合独立前端与 API。部署边界增加，会同时增加接口、鉴权、观测和故障面；它应该解决已识别的问题。

## 解法：把选项放在同一组责任上比较

| 需求形状 | 成熟选项与组合方向 | 取舍与核查点 |
|---|---|---|
| 表单、台账、管理操作为主 | Django 的模型、模板与管理能力；或既有企业框架 | 集成程度高，仍需专门写领域动作与权限；通用 admin 不自动满足面向客户的工作流 |
| 丰富交互、多人编辑工作台 | React 或 Vue 等前端能力，配契约清楚的 API | 局部状态、服务器状态、冲突与离线同步需分开；团队对生态的维护能力比语法偏好更重要 |
| Python 数据处理与 API | FastAPI 配数据库访问、迁移与 worker | schema 与文档便利，但事务、任务、权限仍需明确组合 |
| 已有 .NET 业务与团队 | ASP.NET Core 与既有数据访问、认证和后台机制 | 可复用团队与运维体系，仍要核对部署与升级边界 |
| 团队主要使用 TypeScript | 前后端采用团队熟悉的 TypeScript 框架与运行时 | 共享类型减少一类漂移，运行时输入验证和持久化约束仍不可少 |

这些是选型方向，不是固定套餐或性能排名。具体能力可回查 [Django overview](https://docs.djangoproject.com/en/5.2/intro/overview/)的模型、模板与管理界面，[FastAPI features](https://fastapi.tiangolo.com/features/)的 OpenAPI 接口描述与 JSON Schema 数据约束（JSON 即 JavaScript Object Notation），以及 [ASP.NET 官方说明](https://dotnet.microsoft.com/en-us/learn/aspnet/what-is-aspnet)的请求、模板与认证。前端状态组织参照 [React 文档](https://react.dev/learn/choosing-the-state-structure)；另一条渐进集成入口是 [Vue Guide](https://vuejs.org/guide/introduction.html)。实际选择时再固定版本、许可、依赖与升级策略。

存储先按数据责任拆分：关系数据库承接身份、约束、事务和常规查询；对象存储承接文件内容，数据库保留身份、权限与版本；搜索索引承接检索投影；缓存承接可重建结果；队列承接待处理工作。一个系统可以只需要其中前两项。搜索和向量能力可先使用数据库已支持的功能，出现可测瓶颈再拆服务。

算法落地也优先检查已有能力：Map/set、标准排序与 heap；数据库 `WHERE/ORDER BY/GROUP BY` 和索引；库中的图遍历；求解器中的约束与优化；缓存的淘汰策略；数据库/检索库的 Bloom、HLL、ANN。自写算法适合教学、研究或现有库不能表达的规则，生产实现要承担边界、并发、持久化与维护成本。

## 演算：两个可行架构如何比较

合成维修产品有 50 名内部操作员，每天 2,000 个操作，要求取消不重复、退款可核对、列表可等待几秒刷新。方案 A：一个应用处理页面/API与领域事务，一个关系数据库保存权威对象和 outbox，一个 worker 派发并对账；不先增加分布式缓存。方案 B：独立前端、多个服务、专用消息 broker、搜索索引和共享缓存。

两者都可能实现相同功能。先计算边界：A 的取消、OP7、outbox 可在一次本地事务完成；B 若把它们分散，需额外设计交接协议。若团队没有独立扩容或组织边界要求，A 更容易完整验证。若后续某类数据处理确需独立扩容，可从稳定的任务或 API 边界拆出。这个判断来自本例约束，不证明单体在所有规模都更好。

验收先做一条竖向闭环：页面提交 → 权限与版本 → 事务 → worker → 测试 provider → 投影 → 对账。用两租户、重复请求、未知结果和并发修改来验算。若框架原型只能展示 happy path，尚不足以比较可靠性成本。

## 验算：研究由具体断点触发

| 已观察的断点 | 下一步研究 | 最小可比较实验 |
|---|---|---|
| 查询随租户数据增长变慢 | 索引、查询计划、分页、分区 | 同分布数据比较页读取与尾延迟，不只看平均值 |
| 重复计算占 CPU | memoization、批处理、缓存 | 固定请求回放，计入失效和回源成本 |
| 大图遍历超预算 | 预计算、增量传播、图存储 | 比较影响集合完整性、更新延迟与查询成本 |
| 复杂排程经常不可行 | 约束建模、CP-SAT / 混合整数规划（mixed-integer programming，MIP）、启发式 | 小例穷举、大例与人工基线对照，报告可行率与界 |
| 事件迟到导致报表反复变动 | 流处理、水位、重算发布策略 | 注入迟到分布，测最终准确性与修订时间 |
| 检索快却漏重要文档 | 混合检索、过滤策略、ANN 搜索预算、候选重排（reranking） | 固定授权范围与留出集，比较召回、质量和成本 |
| 多步骤经常卡在未知 | 持久化工作流、状态机、outbox、对账 | 按每个崩溃边界恢复，测未决义务年龄 |
| AI 工具调用超出意图 | 受限动作契约、审批、评估与轨迹 | 检查拒绝条件、注入不可信内容、重复工具调用 |

研究方向要形成可否定的问题。例如“把搜索预算从小调大，授权范围内 recall@10 是否提高，p99 还能否达标”，比“接入最先进向量库”更可验证。把输入分布、期望改进和可接受代价写清楚，实验结果才足以决定是否增加组件。

## 变式：从内部应用到多租户产品

**题目。** 将内部维修台转为 X01 的外部多租户 SaaS，原有技术栈是否必须全换？

**答案。** 不必先换框架，要新增并验证租户身份传播、数据隔离、配额、计量、配置、支持和退出流程。共享表、分 schema、独立数据库等隔离选项依风险、成本与运维约束比较。原有算法仍可复用，但每个查询、缓存、任务和错误响应都要带相应租户边界。检查同号对象、跨租户事件与退出后在途任务；通过这些检查，比更换框架名称更接近目标。
