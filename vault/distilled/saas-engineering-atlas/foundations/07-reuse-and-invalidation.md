# 第七章：复用结果，也保存它成立的条件

重复计算可以省掉，已经改变的输入不能省略。缓存把“这组输入曾得出这个结果”保存下来，下一次相同请求直接复用。真正困难的是判断输入是否仍相同，以及内存不足时保留哪部分结果。

## 识题：纯计算重复与远端状态重复

“同一报价计算一百遍”“同一报表被反复打开”都适合研究复用。报价函数的输入若固定且无副作用，可按输入记忆；报表来自持续变化的数据，则必须带快照或失效规则。H01 的计价、H07 的报表、H09 的文档版本、X01 的租户服务都可能用到缓存，但它们允许的陈旧程度不同。

## 解法与演算：先定义相同，再决定淘汰

### Memoization：把子问题答案留在输入旁边

设合成服务包 A 价值 3，B 价值 4，组合报价规则只做固定相加。工作台两处都要计算 `price(A,B,rule=v2)`，第一次得 7，第二次复用。若规则 v3 加收 1，key 必须包含 v3，得到 8；只用 A、B 作 key 会返回旧价。第六章 DP 的 `(已考虑项目,剩余预算)` 也可作为记忆化 key，从递归分解改为“遇到相同子题就查表”。

若实际访问 S 个不同子问题，每个最多 T 次局部工作，记忆化把重复路径压缩为约 O(ST) 的计算，另付 O(S) 存储及 key 成本。它没有保证 S 很小；状态不完整会算错，状态过细则复用少。[Python functools](https://docs.python.org/3/library/functools.html)提供 `cache` 与 `lru_cache`，并说明即使内部结构线程安全，同一计算在并发首次访问时仍可能执行多次。

**误用反例。** 给 `charge(customer,40)` 加缓存，希望避免重复收费。扣款是副作用，缓存被淘汰或服务重启后仍会再执行；多个实例也不共享同一内存。它需要第九章的持久化操作身份与核对协议。验算比较缓存命中和未命中输出，同时统计纯函数调用次数；副作用方法不以这个试验替代业务幂等检查。

### LRU（least recently used，最近最少使用）：最近使用的先留下

容量为 2，请求序列为 `A,A,B,A,C,B`。按“旧→新”列缓存：第一次 A 为 `[A]`，第二次 A 命中；B 后为 `[A,B]`；A 命中后为 `[B,A]`；C 到来淘汰 B，得 `[A,C]`；最后 B 又未命中，淘汰 A，得 `[C,B]`。LRU 在这组序列命中 2 次、未命中 4 次。

精确 LRU 常用 hash 表定位项、双向链表移动最近使用位置，访问和淘汰平均 O(1)，空间 O(C)。这里 C 是容量项数；若对象大小差异大，必须按字节预算。最近用过能够预测近期再用时，LRU 有意义；顺序扫描大量一次性对象会冲掉热点。

### LFU（least frequently used，最不经常使用）：常用的先留下

仍用同一序列，容量 2，合成 LFU 记录驻留项的访问次数，同频时按 LRU 淘汰。A 三次、B 一次之后，C 到来淘汰 B，保留 A；最后 B 到来，淘汰只用过一次的 C。结果为 A、B，仍命中 2 次。两种策略在这个前缀的命中数相同，留下的未来候选不同；下一次再访问 A，LRU 未命中而 LFU 命中。

LFU 适合较稳定的热点，但永不衰减的旧热度会压住新热点。精确实现可用频率桶，朴素按计数扫描会多花 O(C)，不能一概承诺常数。生产缓存可能采样或估计频率；[Redis Key eviction](https://redis.io/docs/latest/develop/reference/eviction/)明确说明其 LRU/LFU 是近似实现，LFU 有频率衰减。因此这里的手算不等于 Redis 每次会作出相同淘汰。

**误用反例。** 用一次热缓存演示比较两种策略；真实流量却每天更换热点。验算应回放相同的请求序列和对象大小，分别观察命中率、未命中代价、内存与热点切换恢复时间。命中率提高不一定节省成本，命中的若全是便宜小查询而昂贵查询仍未命中，收益可能很小。

## 失效：淘汰决定留谁，失效决定还能信谁

缓存 key 可组合 `(tenant, object, object_version, rule_version, locale)`，只加入实际改变结果的维度。权限相关投影还需授权上下文；身份隔离不替代服务端权限检查。不可变版本缓存较容易管理：对象从 v2 变成 v3，直接读新 key，旧 key 稍后回收。列表与聚合依赖许多对象，可能采用事件失效、版本水位、较短的存活时限（time to live，TTL） 或重算发布指针，选择由新鲜度要求决定。

合成竞态如下：读者取到数据库 v2，暂未写缓存；写者提交 v3 并删除缓存；读者随后把 v2 写回。简单“更新后删缓存”仍会留下旧值。版本化写入、拒绝较低版本覆盖、事务关联的变更事件或关键操作直接查权威记录，分别解决不同边界。TTL 只有在写回来源和链路延迟也受控时，才可形成可解释的陈旧上限；它不自动修复读副本延迟与丢失失效事件。

热点同时过期还会产生大量同源请求。可研究请求合并（single flight）、过期时间抖动与有限后台刷新。允许旧报表临时展示时，要注明输入版本和刷新状态；确认付款、撤权或释放库存前则要读取满足业务一致性要求的证据。命中一个旧的“可用”标记不应变成新的授权。

## 验算：把缓存拿走，业务仍能成立

检查 cold/warm 两条路径结果相同，跨租户同号对象隔离，修改规则与对象后不复用旧 key。注入“提交后尚未失效”“失效后旧值回填”“缓存整体丢失”三个次序。系统应能从权威记录重建，不因缓存清空丢失已发生的义务。再测命中率、数据年龄、回源并发和回源错误，而非只测一次成功读取耗时。

## 变式：从报表到批准，从一个进程到多个实例

**题一。** H07 的历史月报缓存移到 H09 的“当前批准有效吗”。**答案：** 不可变历史版本可以长期复用；当前批准可能因修订或撤回失效，必须绑定目标版本并核验当前有效性。反例是缓存旧批准后放行新文档。检查撤销后新的执行请求被拒绝，历史审阅记录仍保留。

**题二。** 单进程 memoization 扩成 X01 的三个 API 实例。**答案：** 各实例重复纯计算通常只影响成本；若缓存承担扣费去重，就会重复计费。纯缓存可先各自保存并测命中率；业务效果要靠共同持久化边界。验算让三个实例同时处理同一操作，观察业务记录数，而非缓存函数被调用几次。
