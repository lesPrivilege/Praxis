# 第九章：从一次点击到可恢复的业务结果

算法在固定输入上回答一个问题，应用要把这个答案交给不断变化的世界。两个人可能同时编辑，网络可能在成功之后断开，消息可能重复，投影可能滞后。工程的工作是保存足够的身份和证据，让下一次处理知道上一次做到哪里。

## 识题：哪个边界使结果开始不确定

延续第一章的维修订单 O7。操作员取消最后一次未执行服务 S3，并请求退 40 单位。用户界面（UI）、业务应用编程接口（application programming interface，API）、本地数据库、外部退款服务（provider）、消息接收器与列表投影分别有自己的观察时刻。一次超文本传输协议（Hypertext Transfer Protocol，HTTP）请求结束，只能证明该响应承诺的阶段。服务若返回“已受理”，页面应显示待处理；若请求超时，结果可能未知，不能改写成确定失败。

把运行边界写成表，便能决定数据放在哪里：

| 对象 | 权威职责 | 需要保存的内容 | 可重建的投影 |
|---|---|---|---|
| 服务子项 S3 | 业务服务决定是否允许取消 | 状态、版本、取消原因、依据 | 订单进度与未完成数 |
| 操作 OP7 | 本地应用跟踪一次逻辑请求 | 租户、对象、请求摘要、操作 key、状态 | 操作进度条与历史列表 |
| 退款 R1 | 外部 provider 确认外部结果 | provider scope、外部 ID、本地映射、回执 | 退款状态与最后核对时间 |
| outbox / inbox | 本地持久化交接身份 | 事件 ID、对象版本、尝试、处理结果 | 队列深度与待核对列表 |

数据库是保存位置，业务服务对 S3 的规则负责，provider 对外部退款事实负责。搜索索引与缓存都可重建；已发生的取消决定和外部操作映射不能因清缓存而消失。

## 解法：命令提出意图，事务提交本地决定

UI 发出的 command 携带对象身份、读到的版本、参数及稳定操作 key。服务从可信会话取得用户和租户范围，再检查权限、输入、当前版本和 guard。校验不能只依赖前端；即使按钮被禁用，旧页面或另一个客户端仍可能提交。

本地事务原子保存 S3 的取消、OP7、退款意图及 outbox。请求重复且 key/参数相同，返回原操作；同 key 不同参数，明确拒绝冲突。唯一约束保护完整业务身份，版本比较保护用户基于旧内容作出的决定。唯一性、授权和状态转换是不同检查，各有失败结果。

合成库存例更容易看清并发：库存为 1，甲乙都先读到 1，然后各自写回 0 并承诺一件，合计承诺 2。正确的选择之一是在事务内执行带条件的扣减：仅当库存仍至少为 1 时减 1，并以实际更新行数决定成功；另一选择是适当锁定或可串行化事务。跨多行的不变量要覆盖完整集合，不能以一个行锁保护所有关联约束。[PostgreSQL Transaction Isolation §13.2](https://www.postgresql.org/docs/current/transaction-iso.html)说明隔离差异及冲突后的整笔事务重试。

## 演算：把一次退款拆成可恢复阶段

1. 操作员提交 `OP7(cancel S3, expected_version=2, amount=40)`。事务提交后，S3 为 cancelled/v3，OP7 为 awaiting_external，outbox 有退款意图。
2. worker 领取意图，使用同一外部操作身份发出退款请求。provider 已接受，但响应在网络中丢失。OP7 进入 unknown，UI 显示退款结果待核对。
3. 恢复任务按 provider 的查询与幂等语义核对原尝试。找到 R1 成功后，保存外部 ID 和确认依据，OP7 变为 confirmed。
4. 投影消费对应版本，显示取消 1 次、退款已确认 40。重复通知只会重现同一效果；后到的旧 pending 记录不能覆盖已核对的新状态。

在第一步事务提交之前崩溃，没有本地决定；提交之后、派发之前崩溃，outbox 保留待办；派发之后、收到响应之前崩溃，外部结果未知；确认之后、更新页面之前崩溃，权威事实已在，投影可重建。恢复依据取决于停在哪个边界，不能统一用“重新执行全部”。

[Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests)是一个具体协议参照：其 API v1 在执行开始后保存同 key 的首次响应，重试返回该响应，并比较参数；key 的保留与清理有时间条件，v2 的行为也有区别。工程实现要读所用 API 的实际语义，不能把一个 provider 的期限与错误处理泛化到所有外部系统。

## 幂等、顺序与补偿各自保护什么

event ID 去重处理同一通知的重投，业务唯一键保护同一义务不会由不同通知重复生效。若一次购买可能产生多种事件，仅用 event ID 去重还可能重复开通；应让“该购买对应的开通效果”也有唯一身份。去重记录保留多久，要覆盖允许的重放与恢复窗口；超过保留期的旧消息应另有核对办法。

乱序处理不能盲目比较状态字符串大小。可使用对象版本、已核对快照或明确的转换规则；遇到缺失的前提事件，先等待或查询权威对象。某些业务允许重开工单，`closed` 也不是永远最大状态，合法重开应是新的带依据转换。

本地事务无法回滚已完成的外部动作。退款成功后发现取消错误，需要恢复服务、重新收款或人工处理，各有新的业务授权和记录。补偿是一个有条件、也可能失败的新动作，不是删除历史。跨步骤工作可研究 saga 或持久化工作流，但先列出每步确认、补偿和接管责任，再决定是否需要引擎。

## 验算：看得见等待，也看得见冲突

UI 至少能区分输入错误、无权操作、版本冲突、处理中、结果未知与确认完成。冲突时应保留用户编辑并展示新的权威版本；未知时提供按原 OP7 查询进度的路径。乐观更新适合可撤销且冲突代价明确的局部交互，资金或关键资源承诺应以相应权威确认更新完成态。前端状态组织可参考 [React Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)关于避免矛盾和重复状态的原则；这些状态原则也适用于其他前端技术。

API 契约同时写成功与失败：字段、单位、金额精度、时区、缺省值、分页、版本、错误码、幂等 key、速率限制与超时语义。服务端不能向客户端返回其无权查看的冲突详情。后台操作保存可追踪的 operation ID；观察链把 UI 请求、事务、队列任务和外部 ID 连起来，便于对账。

**误用反例。** catch timeout 后生成新 key 重试退款；为避免重复，把所有失败永久吞掉；为让列表“实时”，让缓存值直接批准资源占用。验算分别观察业务效果数、未决操作年龄、资源余额与最终对账差额。没有重复效果仍可能遗漏工作，没有报错仍可能一直停在 pending。

## 变式：从退款到放款，从报名到资源预订

**题一。** V04 的退款恢复移到 V12 的放款。**答案：** 保留原操作身份与未知结果核对；放款的资格、批准有效性、资金义务和补偿可行性重新定义。不能把“退回原订单状态”当作款项未发出。检查超时后先查原放款记录，账务与外部结果一致后才能结束。

**题二。** V17 的课程报名移到 V06 的房间预订。**答案：** 限额竞争机制相似，但房间容量按时间区间变化，不能只保护一个全局库存数。先把住宿区间映射为占用约束，再设计事务或成熟预订能力。检查重叠区间并发预订以及取消后释放，非重叠区间应可同时成功。
