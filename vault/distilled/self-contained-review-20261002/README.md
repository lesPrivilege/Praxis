### A1 为什么没有照审查的方案修

审查建议让生成脚本读 `card_path`，把共用一张卡的几条来源聚合着写出来，目标是“13 张卡、45 个身份可以重复生成”。

实跑之后看到的情况不一样。14 份 catalog 的卡片不是生成脚本写的，是各批入账时手写或用当批的临时脚本写的，里面有 catalog 没有的内容：两次重访的记录、与台账不符的说明、一组样本的读取范围。让一个生成脚本重现这十四种写法，要么把模板扩成十四份，要么丢内容。

所以改成让每份 catalog 自己声明卡片由谁维护：

- `"cards": "generated"`：一个 slug 一张卡，内容只来自 catalog。生成脚本负责写，校验逐字比对。17 份。
- `"cards": "maintained"`：手写，可以一张卡对多个链接，可以放在别处。生成脚本不读不写。校验只查两件事：`card_path` 指向的文件在；几条来源共用一张卡时，卡里出现每一条的 URL。14 份。

没有声明时生成和校验都报错。整层的 Provenance 索引是手写的，生成脚本不再写它。

审查担心的“两套真相”这样处理：生成的那一种只有 catalog 一份真相；手写的那一种，卡片比 catalog 多出来的内容本来就只有卡片这一份，校验保证的是身份不丢。新加的共用卡检查第一次运行就查到一处真的缺口：drift-checkers 的目录说明提到了 Pages 部署，没有写出它的 URL。已补上。

## 边界

- 审查的结论里，“当前结构大体具备发现与消费自足”来自静态走读，本仓库没有新的实测支持或反对它。
- 生成脚本的四种坏输入和两种漂移都只在隔离副本里试过，仓库里没有留测试文件。
- 手写卡与 catalog 之间除了 URL 身份之外的一致性没有检查，例如状态改了而卡片没有跟着改。

## 何时重访

用户给出一件真实任务；来源卡出现第三种维护方式；某份手写卡没有跟着 catalog 更新而被读错；或要动公开范围。
