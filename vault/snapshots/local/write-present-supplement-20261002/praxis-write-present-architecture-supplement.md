## 先划决策责任 再决定目录

### 四个名字不能直接充当边界

“Write 决定说什么，Present 决定怎么让人理解，Design 决定怎么看，Motion 决定怎么随时间被理解”适合帮助记忆，不够用来分配修改权。

建议按所作决定理解它们：

- **Write**：文字表达、论证、解释与内容组织。对文本主张、指称、限定及其论证关系负责
- **Present**：在明确受众、媒介与内容约束下，安排显现顺序、阅读单元、密度、分页和渐进披露。它提出编排取舍；不能因版面放不下就静默删掉条件或异议
- **Design**：视觉与交互表达，包括信息层级、关系与数量编码、可辨识性、可操作性和无障碍。图表尺度、聚合和颜色语义不是装饰
- **Motion**：随时间发生的表达和行为，包括状态变化、时间编码、节奏、采样与插值，以及减少动态效果时的等价表达。它也可能直接承载数据含义

这不是将全部语义集中到 Write。事实依据属于任务的权威输入；文本、图形和时间编码各有自己的责任者。共同要求是不得静默改变事实、限定、证据关系和因果含义。编排造成这类变化时，应回到受影响的内容或编码责任者重新判断，而非一律“送 Write 审批”。

### Present 有三种合理落点

| 方案 | 适用条件 | 收益与代价 |
|---|---|---|
| A 在现有 Reporting 中维护一块薄的编排契约 | 当前远端；跨媒介规则还主要用于专业材料 | 迁移最小、兼容现入口。需把通用编排与 Reporting 特有 ask、决策流程区分清楚 |
| B 独立 Present，Reporting 成为组合使用入口 | 本地已存在多个独立消费者，反复共用编排规则，且能明确移走旧 owner 的重复正文 | 跨 essay、文档、deck、HTML 更易复用；增加一次发现与维护成本，必须有真实收益 |
| C 放入 Design 的信息编排区 | 实际问题仅是视觉页面或界面布局，非视觉写作任务并不复用 | 少一个 Kit；若后来需要纯文本或音频编排，再决定是否抽出，避免把它们硬塞进视觉入口 |

**建议当前选 A 的变更规模，保留 B 的演进可能。** 如果本地新 Kit 已满足 B，就沿既有 owner 校订，不为与远端一致而倒退。是否独立看重复规则、独立消费任务和发现成本，不看名称是否完整。也不必现在为 Present 建齐 principles、decision tables、recipes、before/after、antipatterns、references 六类空目录；先有有用内容，再安排存放位置。

### 八类 grammar 的归属需要收窄

| proposal 项 | 主要责任 | 互引及触发重新判断的边界 |
|---|---|---|
| Narrative | 论证、解释及内容顺序主要在 Write；相应媒介也有叙事责任 | Present 管既定叙事怎样被显现；实质改变论证依赖、因果或理解条件时，由受影响规则 owner 重新判断；普通重排可在当前任务直接验收 |
| Evidence | 主张与证据关系由内容契约维护 | Present 管证据是否就近、可找到；Design 管图形编码；不能以脚注或动画隐藏关键限制 |
| Density | Present 管单元内负荷与分配，Design 管实际可读性 | 删除、合并、摘要与弱化都需检查意义，不能只看字数是否变少 |
| Hierarchy | 内容层级由内容责任者维护，视觉和交互层级由 Design 维护 | Present 将两者投射到阅读单元，不另造第二套“重要性”判断 |
| Figure | Design 维护关系与数量的表达选择和编码 | 内容责任者核对其主张及证据；Present 管出现位置、说明和前后衔接 |
| Emphasis | 任务需要与内容决定什么重要，Design 实现强调 | 视觉降权可能改变实际理解；需核对被弱化的限制是否仍能在决策前看到 |
| Pagination | Present 管阅读单元、跨页依赖与导出 | 不使读者使用定义时找不到适用条件；必要跨页关系须可发现，渲染后的阅读顺序由实际输出复核 |
| Temporal pacing | Present 提出讲解或披露节奏，Motion 实现随时间的行为 | 数据采样、插值、先后含义和 reduced-motion 方案由 Motion 对自身编码负责 |

每条规则只保留一个规范正文。跨 Kit 引用其 owner，并说明本任务何时需要它；不把所有相关内容复制成各层自己的 Core。

### 1000 字的多媒介练习应区分投影与改编

这项练习值得保留，但不要预先写成“内容没有变”。1000 字到一页、十张幻灯片、90 秒音频，可能只改变排版，也可能发生删减、概括、重新排序、证据降级或交互隐藏。是否语义保持，是需要检验的结果。

至少区分：纯呈现变换；保持关键命题与限制的摘要或改编；新增解释、类比或推论。练习只需附一份短的变更说明：保留哪些主张和限制、删改什么、为什么、影响什么。无需先造完整中间表示或数据 schema。

同一事实集合也不保证同一理解：把警示移到行动之后、把可比较选项拆到互斥标签页、把条件移到折叠区，都可能改变决策。W3C 对[有意义的顺序](https://www.w3.org/WAI/WCAG22/Understanding/meaningful-sequence.html)的说明确认顺序可能影响意义；GOV.UK 的 [Details 指南](https://design-system.service.gov.uk/components/details/)也限制可隐藏信息的范围。容量与完整性不能同时满足时，应说明取舍或调整形式，不能用“projection”掩盖内容变化。

## Write 应分规则等级 不只是分文件夹

Core＋按需语言约定＋可选 Profiles 的方向可用。但 Core 应短，且限定在它真正适用的写作任务中；不宜让十条原文自动变成所有任务的硬性不变量。

| 原 proposal 规则 | 建议等级 | 需要保留的限定或例外 |
|---|---|---|
| 1 一句话有可辨认的信息功能 | 编辑启发式 | 保留功能审查；不强读成每句只能一个功能。条件与动作、判断与限定往往应在同句 |
| 2 具体优先于抽象 | 编辑启发式 | 定义、概括、保密和未知都有必要抽象。不能为“具体”编造主体、数字或结果 |
| 3 标题、开头、结尾不换措辞复述同一结论 | 编辑启发式 | 标题定位、独立摘要、教学回顾、步骤前警示可以重复。审查没有用途的复述，而非消灭同义信息 |
| 4 关系显式且真实 | 真实关系属于语义底线；一律显式属于启发式 | 不制造因果或并列；但不是每种真实关系都要加连接词，清晰的顺序也能表达关系 |
| 5 术语稳定 | 指称一致属于语义底线；字面形式属于语言或任务约定 | 允许已定义别名、缩写、译名与面向不同受众的解释。lint 可报疑点，不能粗暴统一词形 |
| 6 范围和确定性准确 | 语义底线 | 保留事实、推断、经验、建议与可能性的区别；修改文风不能提高证据等级 |
| 7 结构服务内容，不硬凑点数，并列项同级 | 逻辑对应属于底线；反凑点数属于启发式 | 分类中的并列项应遵守同一分类轴；固定表单、程序步骤和交接清单可能按其他关系组织，要明确父子、先后或任务关系 |
| 8 删除无作用的元话语 | 编辑启发式 | 原文“除非确有作用”应保留。导航、范围、来源、限制和交叉引用本来就有作用 |
| 9 保留必要复杂度 | 不损坏推理属于底线；句长与名词化属于启发式 | 不为短句拆散条件，也不把所有长句或名词化当缺陷；术语与过程名称可以必要 |
| 10 内容结束时结束 | 编辑启发式或任务配置 | 删除无增益的自动升华；但摘要、行动请求、完成确认及安全收尾可由任务明确需要 |

因此，较薄的 Core 可保留：不虚构或歪曲任务事实；指称与逻辑关系可靠；范围、条件与确定性准确；改写不静默破坏任务所需信息与推理。功能、具体性、重复、节奏和收尾是带理由与反例的编辑判断。它们仍有价值，只是不应全部以“违规即删”执行。比如 [Google 的句子结构指南](https://developers.google.com/style/sentence-structure)建议先交代条件再给指令，支持条件与动作作为完整理解单元，而非按微功能拆句。

语言层按输出语言和文本区域选择：中文任务用 zh，英文任务用 en，中英混排按各区域使用适用约定。不存在“任何 Agent 默认加载中文规范”的理由。与当前任务无关的 Agent，也不必预载整个 Write Core 正文。

Profiles 建议保留两种真正有用的选择：任务文体，以及任务选用或有可靠偏好依据的个人或品牌风格；可组合。默认不应暗藏个人审美。冲突时先守住任务的准确性、完整性、无障碍与交付约束；本次明确的风格要求高于默认文体或 profile，其余按适用语言、任务文体、可靠个人偏好与通用启发式选择。同一问题有不兼容的强要求时显式裁定，不靠加载顺序覆盖，也不用再造一套大 schema。

### lint 的边界

- **可安全自动修复的候选**：范围明确、规则确定的空白与标点问题；先排除代码、命令、标识符、路径、URL、引文及需忠实转录区域，并展示 diff
- **适合检查而非自动改写**：标题层级、链接可达性、术语疑似漂移、重复片段、单位书写疑点。断链检查不证明来源支持主张；单位规范化不能静默改变数值或精度
- **需要语义判断**：事实准确、逻辑关系、必要重复、证据强弱、语气确定性、抽象是否有用。不要把它们简化为 regex 替换

“信息增量删除测试”比禁词表好，但还应计算导航、记忆、可访问性、情境和行动安全的用途。一段话即使没有新增命题，也可能帮助读者定位或避免错误。问题应是“删掉后，目标读者完成任务是否受损”，而不只是“有没有新事实”。

## 最薄的自主发现与消费边界

保留此前 description → 短 index → 按需 content 的方向，Profiles 为次级使用路径；通用能力关系在 Kit 入口能找到即可，不要求 Agent 从样例或个人配置反推主架构。

1. **发现层只回答是否相关**：name、任务型 description、规范入口。宿主支持的标准元数据可以使用，但具体发现机制遵守该宿主；README 不会自动成为所有 Agent 的已安装能力
2. **短入口只回答下一步**：任务、所需最小输入、目标文件或节、必要依赖、什么时候停止。一次定位已足够时不继续读全库
3. **正文按问题加载**：规则 owner 与反例，相关语言，以及确有需要的 task/profile；查来源、争议或维护规范时才继续读研究材料、历史与治理文档
4. **任务中允许回访**：布局暴露理解问题后可补读内容规则，动效编码改变含义时可补读证据约束。按风险回访，不强制四层全读

日常消费者的“停止”是：已有足够输入、约束、完成标准且没有关键冲突，可以执行当前任务。维护者才需要入账、迁移、晋升等完整步骤。此处是建议调整入口职责，并非让当前 Agent 绕过已有仓库指令。

### 候选 description 文案

以下是待实际 owner 映射后的文案示例，不表示远端已有这些文件。

- **Write**：起草或修订文字内容、论证与解释时使用；按输出语言及文体选规则。只做字节保真排版或确定格式修复时不加载完整写作规范
- **Present**：需要跨媒介改编，或决定阅读单元、密度、分页、证据位置和渐进披露时使用；影响意义的取舍回到相应内容或编码责任者。仅调颜色、字体 token 或普通句子润色时不使用
- **Design**：设计或检查视觉信息编码、层级、布局、可辨识性、交互与无障碍时使用。纯文字校对且不涉及这些问题时不使用
- **Motion**：设计或检查随时间变化的表达、状态转移、时间数据编码及减少动态效果的替代方案时使用。静态材料或单纯朗读时不使用

### 四条取用路线及不加载情况

| 真实任务 | 最小取用路线 | 不应默认加载 |
|---|---|---|
| 修订英文 API 故障排查说明，保留命令原样 | Write 入口 → 相关 Core → en → procedure/reference 文体；按需检查代码保护范围 | zh、Present、Design、Motion、个人随笔风格 |
| 将已审中文 memo 改成 5 分钟现场 deck，并保留风险条件 | Reporting 或现行材料入口 → 内容与改编约束 → zh → live/deck 编排 → 相关视觉规则；实际需要动态表达时才进 Motion | 整套 Design Atlas、所有 profiles、无关 Motion 内容；不能把源稿当不可讨论的恒定内容 |
| 调整仪表板的图表尺度、比较方式与更新动画 | Design → 图表编码规则；需要时间编码时 → Motion；核对权威数据与限定 | 强制先完成 Write，再执行 Present 的流水线；没有文字改写问题时不读整套 Write |
| 仅规范中文 Markdown 空格与标点，明确保留代码及引用 | 对应格式检查入口 → zh 中适用条目 → protected regions → diff | 论证、叙事、个人风格；不能顺手去掉被判为“套话”的原文 |

这些是消费路线的验收目标，不是已经完成的安装或运行结果。

## 用反例验收 不只统计路由命中

后续让未看过前文的消费者，仅从实际可发现入口开始处理一小组代表任务。固定同一任务输入与评审标准，对比现有入口和候选入口；保留失败样例，避免只验证维护者自己知道路径的情况。

| 冷启动反例 | 必须守住的结果 | 可观察证据 |
|---|---|---|
| API 参考的多个独立页面都需要同一限制；教程步骤前再次提醒风险 | 不因“不重复”删掉读者在当前位置必须看到的信息 | 各页面或步骤可独立安全使用；删除 diff 与理由 |
| 90 秒内容无法同时保留全部证据、条件和异议 | 明确摘要/改编与取舍；不冒称内容完全不变 | 源主张到产物的短核对、遗漏与保留理由；关键限制不丢失 |
| 两方案必须并排比较，却被分别藏进 tabs；键盘或线性阅读顺序改变意义 | 关键比较可共同感知，阅读顺序保留必要依赖 | 实际渲染、键盘和线性阅读检查；读者能正确回答比较问题 |
| 动画插值让观测数据看似有中间实测值，或排序变化被理解为增长 | 图形与时间编码都不夸大数据含义；静态或 reduced-motion 路径仍能理解 | 数据到编码的对应检查；不同动态偏好下的等价信息 |
| 英文说明、中文叙述及原样代码并存 | 只用适用语言约定，保留代码、标识符与引用 | 加载记录、受保护区域 diff、术语指称核对 |
| 只改格式，或只是一个不需要写作 Kit 的任务 | 正确不加载、不额外改写 | 第一处可执行入口、读过文件及篇幅、无关加载、回退及人工纠正记录 |

三组指标同时看：

- **信息完整与准确**：任务必须保留的事实、条件、单位、未知、证据状态有没有丢失或被增强；发现关键失真即不通过
- **沟通效果**：目标读者能否找到答案、做正确比较、识别下一步与限制；形式上的统一和缩短不能代替这些结果
- **发现负担**：到达首个可执行规则的跳转、读取量、无关加载与人工纠正是否下降；“命中了四个 Kit”可能反而是失败

本次提供的是静态审查与测试设计，未据此宣称当前远端已通过消费者冷启动验收。样例试跑也不能代替真实受众效果证据。

## 保留 迁移 引用与删除候选

| 处理 | 窄范围建议 |
|---|---|
| 保留 | Reporting 的任务入口、领域特有受众与 ask 流程，以及对证据、独立阅读和最终呈现的消费与验收要求；通用规则正文只在裁定 owner 维护，原路径保留兼容导航 |
| 迁移候选 | 若 Write 已有明确 owner，将通用文字与论证规则迁到一处；若 Present 抽出，只迁跨媒介编排规则。迁移先核本地，不据远端直接移动 |
| 引用 | Reporting 组合引用 Write、编排、Design、Motion 的实际 owner；Design/Motion 引用共同证据限制，保留自己的编码规则；将原始素材或快照视为来源，而非当前指令 |
| 删除候选 | 重复维护的规范正文、空目录、没有消费用途的中转页、绝对禁词或绝对句长规则、无意义的自动结尾；先确认无独立用途和入链依赖，再由维护者决定 |
| 降级而非删除 | 个人审美、局部文体和有合理例外的编辑启发式，改成适用范围明确的可选约定；不要把“不是 invariant”误读成“没有价值” |

以上删除均为建议，不是本次执行动作。不能删除仍承担导航、审计历史、兼容入口、独立阅读或安全提醒的内容。

## 供 Opus 采纳的窄范围补充工单

以下是可转交的建议范围，未发送或执行，也不表示本次扩张为全量重构授权。

**目标**：在现行 owner 上消除 Write、编排、Design、Motion 的职责重复，让消费者能从实际入口选择最少必要规则，并在内容与呈现互相影响时找到明确责任者。

1. **对照版本**：读取当前规范入口与本地新 Kit 的安全规范部分，记录真实 owner 和版本。不要为对照搬运原始聊天、答卷或敏感快照，也不要求推送它们
2. **裁定归属**：以本文规则表为候选，把本次边界涉及的现有规则标成保留、迁移、引用、降级或删除候选。先解决标题、论证顺序、证据、层级、密度、强调和时间节奏的重叠
3. **选最小落点**：先用现有结构承载；只有真实跨媒介消费者反复需要独立编排契约，且能减少重复与发现成本时，才抽独立 Present。若已经存在就校订，不重复创建
4. **精简 Write**：提取少量语义底线，按任务选择语言；将其他条目移到编辑启发式、语言或文体/个人配置。明确 lint 的只报疑点与安全自动修复边界
5. **接好入口**：维护任务型 description、短 index、按需正文、必要 owner 互引和明确停止条件；区别仓库维护与日常消费。保留 Reporting 兼容入口，不通过复制正文维持兼容
6. **再做示例与图**：用同一材料展示纯投影与有取舍的改编；架构图表达可选组合和反馈，不画成四层必经流水线。图先服从已裁定职责，不为图形整齐添加层
7. **核验后交付**：检查入链、引用和唯一 owner；按受影响内容运行仓库既有验证；走读上述正常与反例任务，记录未验证的真实受众效果。若正式实施获授权，再按用户授权范围处理提交和发布

**依赖与停止条件**：步骤 1–2 完成前不批量迁目录；owner 未定时停在冲突清单，不复制规则“临时解决”；本地不可见时保留条件式建议，不宣布缺失；媒体容量与必要信息冲突时报告取舍，不静默删改；无法证明新增入口带来独立价值时，停止扩层，保留现有模块；涉及安装、跨项目变更或对外发送时回到对应授权。

**完成定义**：一个清楚的归属表，一套有用的最薄入口，少量能证明边界的前后例，以及通过和未通过的验收记录。不要顺带创建新完整 Kit、统一所有个人风格或重写所有历史材料。

## 外部参照的用途

外部规范用于校准规则强度和提供反例，不替 Praxis 决定唯一架构。中文技术写作指南、英文技术文档指南、产品内容规范和无障碍标准的适用对象不同，不能整包升级成跨语言硬性 Core。

| 已核原始来源 | 本文采用的有限用途 | 不据此推出的结论 |
|---|---|---|
| [Google Sentence structure](https://developers.google.com/style/sentence-structure) | 条件与动作可放在同一理解单元，句式为读者使用服务 | 所有句子必须使用同一结构 |
| [Microsoft Scannable content](https://learn.microsoft.com/en-us/style-guide/scannable-content/) | 可扫描性同时涉及内容排序、写法、标题、列表与表格，说明职责交叉 | Microsoft 规定 Praxis 必须有或不能有 Present |
| [GOV.UK Details](https://design-system.service.gov.uk/components/details/) | 渐进披露不能隐藏大多数用户需要的信息 | 所有补充信息都该折叠，或任何折叠都会损害理解 |
| [W3C Understanding Meaningful Sequence](https://www.w3.org/WAI/WCAG22/Understanding/meaningful-sequence.html) | 顺序可影响意义；替代呈现仍需保持有意义的阅读顺序 | 所有重排都需人工批准。此页是对 WCAG 2.2 SC 1.3.2 的解释材料，不是另一个架构标准 |
| [阮一峰 中文技术文档 文本](https://github.com/ruanyf/document-style-guide/blob/master/docs/text.md) | 中文约定、指称清晰与强文风/句长偏好混在同一指南，适合演示逐条分级 | 将某个作者的技术文风整包当成所有语言、所有文体的语义底线 |
