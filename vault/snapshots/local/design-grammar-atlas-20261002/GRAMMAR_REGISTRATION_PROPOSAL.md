# Grammar 颗粒度登记建议

状态：研究提案 v0.1，2026-10-02。供后续 Opus 校订体例和选择打样时参考；尚未成为 Praxis 已采纳规则。

## 核心选择

把 grammar 登记为「一个可讨论、可改变、可通过样例检查的构成关系」。它不必是 token，也不必是组件。例：标题与正文怎样建立层级；两个区域怎样对齐；反馈怎样在时间上对应动作；装饰怎样避让读者要辨认的内容。

Style name 是检索入口。Profile 是有范围的解释；primitive 是一次可操作的局部构成；composition 是已组织起来的关系；recipe 是为某个目的选择这些关系的建议；demo 是后续某次实现与观察的证据。它们以有名关系互联，不构成必经流水线，也不必逐层继承。

- 同一个 profile 可以支持多个相反但有历史依据的方向
- 同一个 primitive 可以服务多个 profile，或完全不用风格名
- recipe 可以绕过 profile，直接从任务与构成关系起步
- demo 可以挑战或替换 profile 的解释，不能因一次好看就自动成为通则
- Opus 可以提出新关系、新 profile 或拒绝本包分类，只需保留必要语义，并解释自己实际宣称的依据

## 可试的简短记录

下面六项用于检查一条笔记是否说清了问题，不是必须落实的schema。可以合并、删减、改名；只有实际消费需要时才结构化。

| 字段 | 所回答的问题 |
|---|---|
| id 与标题 | 后续如何稳定引用这条关系 |
| intent | 它帮助读者或操作者解决什么问题 |
| relation | 什么元素相对什么元素，怎样组织或变化 |
| scope | 对哪种媒介、内容或状态有意义；何处不适用 |
| evidence | 出处及其支持的具体断言；观察与本包推断分开 |
| latitude | 哪些可以自由改变；什么结果值得反证 |

按需补充：version/status、约束引用、反例、组合关系、后续 brief、已执行观察。无需为每条填满所有维度。

## 四种责任分开

1. 必须保持：任务已确认内容、数据与状态语义、当前媒介适用的可访问性目标、授权与资产边界
2. 有来源的历史判断：有出处、有范围，允许被更好材料修正；不转写成所有现代产品的强制要求
3. 软先验与提案：有助起步的构成解释，Opus 可偏离、混合、发明
4. 实验结果：只对已实现版本、fixture、环境和观察负责；未执行就是未执行

「必须保持」应引用独立的任务/媒介契约，不复制到八个 profile。规范等级、例外和适用条件跟着引用保留。主观的清晰、优雅、有趣、像不像某风格均不编成硬 boolean。

## 关系词先少量使用

supports、challenges、derived-from、combines-with、conflicts-when、tested-by、supersedes 足够起步。每条关系都带一句条件或理由。组合兼容不是风格标签之间的永久真值；同一对语法在不同层、不同内容上可能有不同结果。

## 只登记到哪里

本轮完成引用与 grammar 粒度，不给 style 分配整套固定 radius/palette/motion，不制作视觉成品或 runtime demo。后续由 Opus选择要打样的关系和范围。若登记单不能帮一个人提出更好的样例，应先删减，而不是继续加字段。
