# Praxis 内容架构与能力语法审阅

日期：2026-10-02  
用途：供 Opus 对照本地版本进行校订与素材提炼；本文是建议稿，未修改仓库

## 结论

Praxis 已具备从真实工作进入、区分知识与运行、保留证据和责任的良好骨架。当前最值得推进的不是再造一套“AI OPC / FDE 总框架”，而是把已有宽覆盖下钻成能独立支持判断的内容单元，并让 description、index 与正文各司其职。

推荐保留现有顶层目录与主要路径，先做三件事：

1. 把入口改为“当前问题 → 最小阅读 → 能形成的产物 → 何时停止”，取消默认深入研究层的隐性要求
2. 在现有位置区分跨域 grammar、场景 profile、任务 recipe、工具能力与证据，不按这些 kind 再造五套目录
3. 先用三个真实任务族补足判断内容：陌生客户诊断与启动、最小介入与验收、个人经营的投入与继续判断；其余能力通过既有 Kit 互引承接

这里的长期能力空间包括理解工作、建立实体与证据关系、选取介入、构建与验证、促成决定、交付与持续运营。RSI 是这些能力在实际工作中改进的反馈机制；它不替代这些能力本身的正文。

## 一 任务框架与证据边界

### 本轮回答什么

用户指出本轮应审的是 Praxis 项目文档、folder 架构编排、description、index、content 体例，以及从第一性原理还应补充或泛化的 grammar 维度。这份审阅据此从上一轮较窄的消费证据与循环机制，转向内容架构与长期工作能力。

OPC 暂作为“AI 辅助个人经营 / one-person company”的任务语境假设，尚不是用户正式定义；FDE 作为现场理解问题、形成有边界介入、交付和承担后续责任的工作语境。两者是压力测试任务集，不是新的目录名，也不是证明每项知识都应进入 Praxis 的理由。

第一性问题是：为了让一个人借助 AI 反复完成有价值、有边界、可接受且可持续的工作，哪些判断不能每次从零猜测？怎样留下可复用语义，同时不把客户特例和工具细节伪装成共同原理？

## 三 横轴任务与纵轴内容类型

任务/function 是“现在要完成什么”，例如判断机会、澄清需求、实现介入、请求决定。kind 是“读到的内容对判断起什么作用”。二者交叉，但不互相替代。

| kind | 它稳定维护什么 | 不能冒充什么 | 当前建议归属 |
|---|---|---|---|
| Grammar | 对象和关系、状态语义、不变量、有效组合与反例 | 工具操作步骤、一个客户的全部字段 | 跨域在 `grammar/work`；专题在已有对应 Kit |
| Profile | 在特定场景对 grammar 的取值、例外和映射 | 新的全局定义或私自放松共同约束 | scenario / 客户项目；企业工作面九问作为已有投影 |
| Recipe | 给定输入后如何走到可验收产物，含分支和停止点 | 永久本体或所有任务必走流程 | 现有指南、模板或有界 Skill |
| Tool capability | 能力、接口、权限、失败模式与版本约束 | 业务语义的 owner 或购买推荐 | adapters / environment；具体实现项目 |
| Evidence | 一项主张的来源、支持/挑战范围、版本与局限 | 已采纳规范、授权或普遍有效性 | vault；原始业务证据仍在受控项目 |

索引、解释、治理与历史决策另有职责，不必硬塞入这五类。上述 kind 可先作为编订检查和局部说明，不要求全站 YAML、统一机器 schema 或新总账。

**权威点选择规则：**同一条语义只由一个位置主责；其他入口转述用途并链接。场景可以收窄适用范围、绑定参数，不能默默改写共同语义。内容维护角色与客户业务决定人不是同一个 owner 字段：前者维护规则，后者对一次工作、授权或验收负责。

例如，跨域的 Approval 定义以 `grammar/work` 为主责，`contracts` 将其映射为操作检查，避免复制另一套定义；某客户的批准人、额度和操作序列属于场景配置；某宿主的 API 名称属于 adapter。若同时更新多处规则正文，必须先决定哪个是规范主责，哪些只是引用和执行投影。

再区分状态权威（哪个系统保存已确认状态）与生成源（哪个 catalog 是编辑源、哪个文件为生成投影）。前者不等于文件维护者，后者不能成为第二个手工编辑的权威。

现有 [领域 Kit 与运行消费者](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/environment/expert-contract.md) 已把 Role、Kit、Skill、Tool、Runtime、Provider/Model 分开，应该继续复用。不要重新把 Praxis 绑成一个万能 Expert 身份。

## 四 description index content 的薄体例

以下是一套编订约束，不是每个页面必填的固定表单。README 可以同时承担 description 和 index；短文档可以一个文件完成。没有必要为了三种职责强造三层目录或三个文件。

### Name 与 description 负责是否进入

- name：稳定、可识别、尽量对应用户会提出的问题；不把完整分类树塞入文件名
- description：一句话说明“何时用、帮助决定或形成什么”，必要时再加一句最容易误用的排除条件
- 状态：规则采纳、使用验证和实现状态分开；状态可继承父级，具体条目只写例外

不理想：“本模块包含若干面向企业的全生命周期能力。”  
更有用：“当一项客户问题尚未判断是否值得介入时，用真实流程、例外和基线形成启动、补证或停止建议；不用于证明已经取得收益。”

### Index 负责选最小路径

一条路由只需要：自然问题 → 当前必须读的条目/锚点 → 最小工件 → 继续或停止条件。能直接到目标的读者不必经过根 README、Kit README、专题 README、研究提炼四层。

“相关材料”应分两种：

1. 当前必须：不读就会改变本次判断或违反约束
2. 按需展开：遇到特定不确定性再读来源、长解释、demo 或历史 ADR

不要用“建议全部阅读”逃避路由责任；也不要为压缩上下文省掉操作前必需的权限、版本与风险边界。

### Content 负责完成一条判断

一个可独立消费条目至少能回答：

1. 要判断的具体问题是什么，适用于什么条件
2. 对象与关系是什么，哪些约束不能被参数选择冲掉
3. 哪些变量可调，调整后影响什么
4. 一个正常例与一个最容易误用的反例
5. 形成什么最小产物，何时继续、补证、升级或停止

来源、demo、profile 和历史理由由精确链接展开。元数据够用即可：规范主责位置、适用范围/状态、依据与重访触发；不应给每个二十行页面附完整治理数据库。

## 五 grammar 能力矩阵

这里的 grammar 是能排除错误结果的关系和约束，不等于职业知识清单。候选应在换工具、换客户后仍帮助判断，并能告诉消费者何时不适用。下面九类用于深化现有内容，不对应九个新目录，也不是每次任务必经的九阶段。

### 与现有 Kit 的对应

| 候选 | 远端已见的承接 | 本轮建议深化什么 | 状态判断 |
|---|---|---|---|
| G1 症状与可干预问题 | landscape、field-loop 发现/选择、scenario §1 | 从事件证据区分症状、原因假说、硬约束与方案请求 | 已有骨架；方法深度需补，现场效用未证 |
| G2 角色 权限 承诺与协商 | work、field-governance、contracts、Reporting brief | 冲突目标、变更请求和沟通怎样成为有权者可决定的问题 | 已有且分散；需要一次协作情景串联 |
| G3 词义 对象 来源与状态 | work、contracts、environment mapping | 同名异义、身份匹配、时效与冲突裁决的具体判例 | 语义已有；跨源映射实践未证 |
| G4 价值 备选与投入边界 | field-loop 选择、field-governance 双账本、Reporting options | 价值机制、最危险假说、投入上限与变更的关系 | 已有原则；个人经营情境需素材校准 |
| G5 情景 边界与最小构建 | scenario、contracts、adapters、demo blueprint | 怎样把可靠/及时等愿望变成可构建的情景和边界 | 已有契约；具体取舍与实现未证 |
| G6 主张 试验与判定 | verification、scenario §4 | 样本代表性、评判分歧、真实终态与有效替代路径 | 已有检查层；评估方法可深化 |
| G7 交付 接收与残余责任 | field-loop、contracts、scenario §5 | 接收准备、使用能力、条件接收与支持界限 | 已有语义；真实交接案例未证 |

| G9 案例 可迁移规则与修订 | evolution、Agent、ADR-002/009/011 | 从个例抽不变量，区分 profile，纠正误触发与撤回 | 治理已有；内容级迁移证据逐项补 |

“候选缺口”是指在本次读取的远端规范中未看到足够独立消费方法；它不等于全仓库或用户本地完全没有材料。G6/G9 的测量与反馈服务前面各类能力，不应取代它们的正文。

### G1 症状与可干预问题

- **重复判断：**“想要 AI/看板/自动化”对应哪个实际工作困难；应补资料、改流程、处理权限还是构建系统？哪项未知会改变下一决定？
- **对象与不变量：**发言者、执行者、受益者和决定人分开；问题主张连到发生过的事件、原过程、阻塞与结果；当前基线、期望、推测原因和已证原因不可混写；方案请求不自动成为需求
- **可调变量：**问题粒度、访谈/观察深度、样本、基线精度、可投入时间
- **反例/边界：**局部且原因已知的低风险修复不必完整 discovery；访谈频率不能冒充总体发生率；紧急故障先处理已授权的恢复
- **最小工件：**问题切片，含一个完整事件、关键未知、可区分假说的下一调查、非 AI 备选及继续/停止条件；不强制每次列固定数量原因
- **触发与入口：**“到底卡在哪”“客户说要 AI”“值得做吗” → `field-loop` 发现/选择；只有组织条件缺口时读 `field-governance`
- **distill 素材：**真实输入/输出、事件回放、等待/返工、执行者纠正、一个最终不做系统的案例

GOV.UK 的 discovery 原文支持先理解问题、约束与整体旅程并决定是否继续；Basecamp 用具体事件与投入意愿限定问题。本文的问题切片体例是转用建议，不是这些来源规定的统一格式。[GOV.UK discovery](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works)、[Basecamp Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03)

### G2 角色 权限 承诺与协商

- **重复判断：**谁可提出、批准、执行、接受或暂停；新要求改变了什么承诺；谈不拢的是事实、判断标准、资源还是决定权？
- **对象与不变量：**角色、能力、权限、义务分别记录；承诺连到对象、条件、承担者和接收者；礼貌认可不等于批准；发送不等于接收；协商应显式保留各方未接受的条件，不制造共识
- **可调变量：**委派范围、升级条件、同步/异步渠道、检查点、可谈与不可谈条件
- **反例/边界：**一人内部可逆动作可极简；不从语气判断法律效力；不能用 RACI 表证明实际授权，更不提供操纵性谈判技巧
- **最小工件：**一页工作约定/变更待决单：已同意什么、分歧、影响、谁决定、下一责任与接收条件；沟通文本从这里生成
- **触发与入口：**“谁拍板”“客户又加一点”“怎么说清楚”“等确认” → `field-governance` 与 `work` 的 Decision/Handoff；写材料时才读 Reporting brief
- **distill 素材：**实际请求和答复、已授权范围、被拒绝/改变的约定、真实角色与升级过程；缺资料就保留权责未知

本项把组织权责与表达分开：Reporting 负责使决定可理解，业务契约负责承诺是否成立。决定留痕可借用 Nygard 的 context、status、后果与替代关系；这不等于把技术 ADR 当商务合同。[Nygard 原始 ADR 说明](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

### G3 词义 对象 来源与状态

- **重复判断：**两份资料的“客户”“订单”“完成”是不是同一含义；源记录指向谁；冲突时哪方有权裁决？
- **对象与不变量：**源记录、实体、文档中的提及分开；身份与属性/状态分开；词义带语境；映射可为等价、包含、派生或不确定；事实保留来源、适用时间和版本，不静默改写历史
- **可调变量：**实体粒度、匹配规则、冲突处理、时效、人工确认阈值
- **反例/边界：**简单表格转换可只保留局部映射；同名或相似度不足以合并身份；无法统一模型时采用翻译和隔离
- **最小工件：**一个对象的语义切片：来源→身份→关键状态→合法变化→下游；附高风险词、冲突和裁决依据
- **触发与入口：**“数据对不上”“哪个为准”“算完成吗” → `grammar/work` Object/State/Source/Evidence，再查 `contracts` 与宿主 mapping
- **distill 素材：**脱敏记录、实际字段值、状态变化、接口样例及业务方对歧义实例的判定

Evans 的原始讨论说明模型语境、翻译边界及组织协作成本，适合支撑“不要全局强行同名合并”；本文的来源级语义切片仍须本地实例验证。[Evans Chapter 14 讨论](https://www.dddcommunity.org/uncategorized/ch14/)

### G4 价值 备选与投入边界

- **重复判断：**为什么现在做；不做、人工、采购和更小改动哪个更合适；哪项假说失效就不再值得继续？
- **对象与不变量：**机会连到受益者、基线、价值机制与结果；方案可运行不证明采用或收益；备选使用可比范围；投入/停止条件先于观察结果写明；变化后重作决定而非惯性追加
- **可调变量：**时间投入、试点范围、最小改善、观察窗口、可逆性和证据强度
- **反例/边界：**必要义务不能只因低回报忽略；未知不得填零；时间释放不自动变现金；此处不是会计、税务或投资建议
- **最小工件：**机会取舍说明：目标、价值机制、真实备选、投入边界、最大未知、下一实验与决定人
- **触发与入口：**“先做哪个”“值不值得”“为什么不买现成的” → `field-loop` 选择与 `field-governance` 价值口径
- **distill 素材：**现状操作量、准备与维护成本、采用/支付等获准的真实信号、替代方案限制、放弃案例

Basecamp 的 appetite 可帮助区分“愿意投入多少”与“预计要花多久”，但不能照搬其六周节奏；这里的决策体例是 Praxis 候选。[Basecamp Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03)

### G5 情景 边界与最小构建

- **重复判断：**先跑通哪一小段能证明关键假说；哪里需要真实集成，哪里可手工/模拟；失败后谁能恢复？
- **对象与不变量：**切片从触发到下游可观察结果；接口有输入、输出、失败与责任；质量要求落到情景；真实/替身边界可见；副作用需处理重复、部分成功和结果未知；“最小”不削掉授权与接收
- **可调变量：**实现/采购/人工、同步/异步、集成深度、质量阈值、重试与人机边界
- **反例/边界：**探索表达的原型不必接全部系统；并非所有动作可回滚，应说明补偿或停止；系统未明时可先做连接探针
- **最小工件：**端到端切片设计，加关键质量情景、一个失败路径、真实/替身说明和恢复去向
- **触发与入口：**“最小跑通什么”“先做 demo”“接哪里”“超时怎么办” → scenario §2–3、`contracts`；工具选择后再读 adapter
- **distill 素材：**真实请求响应、权限、系统限制、手工替代、负载与失败例、质量目标背后的业务后果

SEI QAW 可借用“用业务相关、可衡量的情景澄清质量要求”；不必照搬完整 workshop 或大型架构评审。本文恢复/幂等建议由现有契约和场景需要承接，不宣称全来自 QAW。[SEI Quality Attribute Workshop](https://www.sei.cmu.edu/library/file_redirect/2018_010_001_513488.pdf/)

### G6 主张 试验与判定

- **重复判断：**要证明什么；通过适用哪些输入；失败来自实现、模型、数据、环境还是评判；换方案是否退步？
- **对象与不变量：**主张连到范围、输入、判据和终态证据；task/trial/trace/grade 不混淆；agent 自称完成不算终态；正反例都测；合理替代路径不能仅因步骤不同被判错，必须的安全约束另守
- **可调变量：**样本与覆盖、重复次数、人工/程序/模型评分、校准强度、回归范围
- **反例/边界：**早期可用少量人工判例，不先建平台；低样本不作统计可靠性承诺；benchmark 不等于客户验收
- **最小工件：**小型评估包：任务、输入/环境、标准、通过/失败例、真实结果、判定与未覆盖项
- **触发与入口：**“怎么证明”“换模型会退步吗”“看着不错能交吗” → `verification` 相关层与 scenario §4
- **distill 素材：**实际成功/失败、最终系统状态、专家分歧、必要运行证据和既定标准；不需收集私人隐式思考

Anthropic 的 agent evals 说明任务、尝试、评判器与真实终态的区别及校准问题；本项不采用其示例样本量为 Praxis 硬门槛。[Anthropic agent evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### G7 交付 接收与残余责任

- **重复判断：**做完是否等于对方可使用；交付的是材料、代码、能力还是持续服务；剩余限制谁承担？
- **对象与不变量：**版本、环境、范围与接收人对应；技术符合、实际可用、接收同意、支持就绪分开；未决项随交付传递；有条件接收保留条件与复查点
- **可调变量：**接收粒度、试运行、知识转移、支持窗口、可接受限制与退出方式
- **反例/边界：**截图或发送回执只证明局部事实；内部临时说明不必具备生产运行包；一般检查不能代替专业认证或合同裁决
- **最小工件：**接收包：精确版本、允许用途、标准与证据、起步方式、未决项、恢复/支持责任；适用时由接收者在目标环境独立完成代表性工作
- **触发与入口：**“能验收吗”“交给客户就结束吗”“上线谁维护” → scenario §5、`field-loop` 移交、`contracts` 交接
- **distill 素材：**真实接收反馈、无法使用实例、环境/操作检查、限制与支持能力，不仅是发布通知

NASA 的 verification、validation 和 transition 区分可用于避免一个“done”吞掉不同责任；这里只借用关系，不把飞行器的特定验收含义套成商业签收。[NASA Product Realization](https://www.nasa.gov/reference/5-0-product-realization/)

### G8 运行 异常与下一投入

- **重复判断：**到底净减负了吗；是否将工作转成审核与救火；该修系统、改流程、缩小服务还是停止？个人容量能否承受扩展？
- **对象与不变量：**按完成的工作单位看总投入；设置/学习、正常处理、异常返工、支持分开；成本与质量共用范围和窗口；改善不自动证明因果；异常连到影响、恢复、owner 和下一决定
- **可调变量：**工作单位、观察周期、工时估计、支持边界、异常预算与重评触发
- **反例/边界：**有价值的专业判断不等于浪费；个性化服务不必全产品化；低频高价值工作不能只优化吞吐；短期漂亮数字不证明规模经济
- **最小工件：**运行复盘：工作量/质量、人工和工具投入、主要异常、可比变化、下一项继续/修复/缩小/停止决定
- **触发与入口：**“怎么越做越忙”“省了多少”“值不值得产品化” → `field-governance` 双账本与 `work-system` 未决义务
- **distill 素材：**获准的工时/支持/返工、任务量、采用与质量、基线和范围变化，保留估计与未知

Google SRE 对 toil 的限定有助于区分持续人类判断与重复负担；不照搬其 50% 组织目标，也不据此推导个人经营利润。[Google SRE Eliminating Toil](https://sre.google/sre-book/eliminating-toil/)

### G9 案例 可迁移规则与修订

- **重复判断：**本次什么可复用；哪些仍是客户例外；下一次什么请求应触发；新事实是否推翻旧规则？
- **对象与不变量：**原始材料、观察、解释、候选和已采纳规范分开；共享规则有范围、反例与来源；客户差异留 overlay；替代保留版本和迁移；检索到不代表正确消费
- **可调变量：**推广范围、例子深度、入口措辞、复审触发、保留与自动检查范围
- **反例/边界：**同源转述或同客户复制不算独立证据；单次样张不自动晋升共享组件；不为统一而抹掉专业差异
- **最小工件：**一个有边界的消费条目：自然触发、判断、最小输出、正反例、依据和条件展开链接；必要时留一个误触发检查
- **触发与入口：**“下次能复用吗”“agent 为什么读错”“可以入 Kit 吗” → `evolution` 与对应现行条目；实现晋升才查 ADR-002
- **distill 素材：**可共享的输入/输出、失败/纠正、下游接收、来源及不同语境中的使用记录，不要求公开原始业务资料

Diátaxis 支持按读者需要分工，Anthropic Skills 展示入口信息、主体和按需资源的渐进加载；它们不要求 Praxis 改造成四套目录，也不证明本地效果。真实触发和误用结果才决定下一次增补。[Diátaxis](https://diataxis.fr/start-here/)、[Anthropic Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

**组合时只稳定必要关系。**例如，问题切片能指向取舍依据，取舍能指向场景边界，场景能指向判据，判据能指向接收与剩余责任。没有下游消费需要，不加字段；读者已经能作下一决定，就停止扩写。

## 六 Artifact 媒介选择与交付生命周期

本节纳入用户新增的 Artifact / Release 提案，作为待裁决的架构补充。提案的有效方向是：材料可以为当下理解而临时定制，也可以成为要长期读取、重现、审查和接手的交付物；这应改变所需保证，而不是给不同媒介排价值等级。

### 已有承接与真正增量

| 议题 | 远端已有 | 值得补充 |
|---|---|---|
| 工作目的与媒介分开 | Reporting 已有 intent→audience→decision→evidence→visual→surface；diagram/chart/table/card 分工 | 将 text、HTML、motion、slides、table、prototype 等作为可组合媒介，解释何时值得承担其依赖和交互成本 |
| 内容与呈现一致 | 主张/证据、实际/预测、标题展项、最终渲染与导出检查 | 明确多个媒介共享哪份事实与精确参考；一份视频不能自动替代可检索的细节定位 |
| 分享与交付边界 | contracts、demos、environment 已有权限、接收、数据分区、fixture 与依赖约束 | 对一个 artifact 明确接收者、用途、预计寿命、复现目标、支持责任及出边界前的适用 gate |
| 公开发布 | 有某次公开范围复核回执 | 历史回执不是通用 release 规范，也不是以后素材的默认发布许可 |
| 样例回流为长期资产 | 已有提炼、采纳、场景验证、晋升与修订 | 明确从样张抽的是语义/约束/参数，还是某个可复用 element；别整套搬运偶然实现 |

依据：[Reporting grammar](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/reporting/grammar.md)、[Artifact 研究提炼](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/vault/distilled/reporting/artifact-grammar.md)、[Demo 边界](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/demos/README.md)、[历史公开范围回执](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/docs/verification/luna-publication-review-2026-09-19.md)。后者只用于确认“已有特定批次发布检查”，不重用其旧许可、旧扫描结果或文件范围。

### 将媒介 受众 生命周期和风险分开判断

- Present 回答“怎样帮助人理解、查找、比较或操作”；Release 回答“什么将交给谁、可如何使用、带哪些保证及责任”
- `explore / share / release` 可保留为意图标签，但不是由轻到重的单轴等级：explore 是工作活动，share 是接收者边界变化，release 是约定版本与支持保证的交付行为，它们可以组合
- 内部探索仍受真实性、权限、隐私、依赖执行安全以及实际使用者的可访问性要求约束；内部不等于只有视觉验收
- 私密客户 share 可能比公开的合成 screenshot 风险更高；内部长期工具也可能比一次性公开示例要求更多复现和维护保证
- 不强制 Write→Present→Design→Motion→Release 流水线。一张可靠的表可以直接成为最终交付；一个交互原型也可以只是限定范围的探索

媒介选择应回到语义：精确措辞与可检索记录用 text；结构与依赖可用 diagram；数量与逐项核对用 chart/table；时序或状态变换难以静态表达时考虑 motion；需要真实操作反馈时考虑 prototype。HTML、slides、video 等可以组合这些表达，不凭格式自动获得更高价值或可信度。

这是一项基于原始材料的架构推论：GOV.UK 分别讨论原型形式、使用阶段和分享保护；NASA 则区分产品形式、所处生命周期和接收所需准备。两者支持将这些维度分开看，但没有规定 Praxis 应采用某个统一 Release schema。[GOV.UK Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes)、[NASA Product Transition](https://www.nasa.gov/reference/5-0-product-realization/)

视频加 precision reference 是有用组合：视频负责连续演示，精确参考承载版本、定义、关键状态、数据与可定位依据。仍应按音频/视觉内容提供适用字幕、描述或文字替代；有文字附件并不自动满足所有访问需要。W3C 的媒体规划明确将相关访问需求纳入内部与外部项目要求，且按媒体是否包含关键音频/视觉信息选择支持方式，而非按“内部/外部”简单豁免。[W3C 媒体可访问性规划](https://www.w3.org/WAI/media/av/planning/)

### 最小 artifact decision record

不建议再建一份独立大 schema。沿用 Reporting brief 的目的、受众、ask、证据、renderer，在有交付边界时只补三组信息：

1. **用途与生命周期：**临时理解、协作评审、正式交付还是持续使用；谁接收、预计有效多久、何时失效/撤回
2. **版本与复现承诺：**权威内容/版本在哪里；需重现的是结论、静态外观、交互行为还是构建过程；所需数据与依赖能否获得
3. **交付检查与责任：**本次适用哪些 gate、证据在哪、例外由谁接受；谁接手支持、未决问题、留存和处置

一次自用的临时示意可以只在任务记录写几行；一个客户交付可在既有 scenario/handoff 里展开。内容对象/身份与接收语义仍复用 work/contracts，避免另建一套 Artifact 状态机。

### Release envelope 作为检查菜单

用户提出的十一维可以保留为检查菜单，但不能变成十一套目录或每次全部重做的程序。共同最低要求与依情境加深的检查应清楚分开。

| 检查维度 | 要判断的具体问题与证据 | 建议主责 |
|---|---|---|
| correctness / provenance | 内容、数量、关系和行为是否与所声称范围一致；事实/假设和来源版本能否区分 | 相应业务 grammar、Reporting；证据留受控来源 |
| accessibility | 实际接收者能否感知、操作、理解；必要时有键盘、文本/媒体替代、暂停等支持 | 已有 UI/verification；本地 Design/Motion 边界待核 |
| compatibility / performance | 目标设备、浏览器、离线环境能否使用；加载与交互成本是否适合真实任务 | 具体实现/renderer，验收记录适用环境 |
| visual / editorial | 视觉是否表达正确关系、文字是否可理解、最终输出是否有遮挡、溢出或歧义 | Reporting 与本地 Design/Write 现有主责 |
| security / privacy | 数据/元数据是否允许给该接收者；脚本、网络、依赖和权限是否带来不必要暴露 | environment/contracts；具体实现负责执行保证 |
| licensing | 素材、字体、代码、依赖是否具备本次使用和分发所需权限 | 来源/依赖记录与交付负责人；未核则保留限制 |
| reproducibility | 声称能重现什么；必要的版本、输入、构建/运行说明和可验证结果是否齐备 | scenario/demo 或交付项目 |
| archive | 保留什么版本、多久、谁能访问、怎样失效和处置；是否真的需要保存全部原始材料 | 项目/交付治理，不能默认永久保存敏感原件 |

“未执行”和“不适用”应分开，后者要有与当前受众/用途有关的理由。执行这些检查不等于取得外发或发布授权，接收者范围扩大需重新检查。

### 两个具体实例

**实例 A 一次性 architecture explainer。**目标是帮助两位协作者理解三条依赖边。可用一页 HTML 或 diagram，允许定制布局和一次性实现；把每条边的语义、事实/假设和版本写清，用合成数据，按实际读者需要提供文本结构说明。若没有交互必要，不添加重型运行依赖。确认在目标阅读环境可打开且不会意外加载私密/不可信资源后，可止于当前理解目标；不必包装完整产品、长期 API 或发布工程。以后转发给客户时重新检查 recipient、用途和未证明内容，不能沿用“自用”的免审假设。

**实例 B 客户可复现的流程交付。**目标是让客户脱离作者仍能运行一个已约定的流程并验收。可交付简短演示视频加精确文字参考、固定版本的必要代码/配置、获准样例、依赖与启动说明、失败/恢复及接收标准。明确复现的是哪套行为和结果，不笼统承诺像素或随机输出逐字一致。目标环境、访问需求、许可、性能和安全按真实用途验证，未决项与支持责任由双方可见地记录。只有视频播放成功不能判定交付通过。

### 从临时样张提炼为长期 element

先问样张解决了什么认知/操作问题，再抽出语义不变量与可调变量；留下反例与适用边界，随后用独立任务检查是否仍成立。只在重复需要稳定接口与维护时提升为 element 或共享实现。知识说明、设计参数与运行组件的采纳门槛不同，继续沿既有晋升规则处理。

“代码生成成本接近零”在本轮没有得到证明，不应作为默认引入重依赖的理由。即使生成变快，阅读、验证、依赖安全、兼容、运行和维护仍有具体成本；是否值得由任务与交付承诺决定。

## 七 三条静态任务走读与反例

以下使用具体的合成工作请求，按已读取的远端入口进行静态走读；不是 fresh/cold agent 实测，也没有客户结果。每条同时说明现有路径和需要进一步 distill 的内容。

### 路径一 陌生客户说想用 AI 改善报价流程

**用户目标：**“报价响应慢，能不能先做一个 AI 助手？”真正需要的第一决定是慢在哪里、影响什么、值得介入哪一段。

**最小加载：**已知道要做发现的消费者可直接读 `field-loop` 的发现/选择两行，再读 `field-governance` 的启动与合作；不必先通读所有 Kit、UI、adapter 或技术参考。术语发生争议时才查 `grammar/work` 对 Object、Evidence、Metric、Decision 的定义。

**应形成：**一页现状与问题边界：谁在处理哪个对象；一次正常实例与一个例外；等待与返工出现在哪里；基线何处可得；哪些原因仍是假说；至少一个非 AI 替代方案；谁决定下一步。请求补充材料应具体到待消除的未知，而不是要求客户上传全部资料。

**停止和分支：**
- 关键权限/业务责任未定：停止于诊断与补证清单，不进入生产集成设计
- 能界定一个有数据和接收者的实验：再打开 scenario 模板第 1–2 节，形成有限试点
- 发现只是已有表单配置或现行流程没人遵守：可推荐现成流程改进；不因 Kit 含 AI 能力就强行调用模型

**证据判断：**访谈中的“每天省两小时”是待验证陈述；单个顺利样例不代表例外覆盖；demo 流畅不证明工作负担下降。现有路径已有上述责任与基线骨架，尚应深化“怎样将症状、原因假说、约束和方案分开”的可消费内容。

入口：[现场闭环](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/work-system/field-loop.md)、[组织启动条件](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/work-system/field-governance.md)

### 路径二 已获准做客服工单的只读分流试点

**用户目标：**“把已有工单建议分给合适队列，交给人工确认；这周给负责人决定是否继续。”假设只读范围和使用数据已获准，不假设自动写回或对客户发送。

**最小加载：**直接使用 scenario 模板第 2–5 节；按其中的动作/失败问题读 `contracts` 对应行；按验收目的读 `verification` 的系统行为、业务接受与运营三行。仅在同名客户/工单身份、状态权威不清时查 `grammar/work`。需要人工复核界面时才读企业九问和 UI 候选，不提前研究全部前端生态。

**应形成：**一类输入、一项动作、候选输出、人工接受/修正接口和停止条件；一组代表性正常、缺上下文、冲突、拒绝和重复输入样例；质量预期、人工复核负担、接收者及未决项。

**停止和分支：**
- 缺少可接受答案的判断人：保留技术演示范围，不能宣称通过业务验收
- 原输入或规则版本变化：重验受影响范围，不沿用旧结论
- 结果足以支持继续/修订/停止决定：交付当前证据和未覆盖范围，无需扩建平台
- 若后来要写回队列：这是新动作与批准范围，应补外部确认、幂等和恢复契约后再做

**证据判断：**离线分类质量、人工是否接受建议、实际处理是否改善分别判断；测试通过不能代替接收人的业务判断。现有场景/契约/验收已承接此任务，需要补的是如何选择代表性 eval 样本、如何处理标注分歧，以及接受标准在试点前怎样达成。

入口：[场景模板](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/scenarios/_template/README.md)、[工作接口契约](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/contracts/README.md)、[分层验收](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/verification/README.md)

### 路径三 个人经营者要安排有限交付时间并形成客户提案

**用户目标：**“下两周有两个服务机会和一个产品化想法，我应该优先验证哪个，并怎样向客户说明一个有边界的试点？”这里先整理可比较的工作事实与假设，不替用户做法律、税务、融资或投资决定。

**最小加载：**`field-loop` 的选择阶段与 `field-governance` 的价值口径；记录当前机会的需求证据、可投入时数、交付/维护负担、必要依赖和可退出性。只有要写成对外材料时才进入 Reporting brief 的 Audience、Expectation、Ask、Stage、Evidence、Tension，并读组织动作表中请求决定那一行。

**应形成：**带不确定性的机会比较和最小验证建议；每个选项有下一证据、投入上限、交付边界、接收者与停止条件。客户提案另写清需要对方做出的决定，不能把未协商事项写成双方已承诺。

**停止和分支：**
- 客户需求只来自礼貌性兴趣：先验证愿意投入时间、提供必要输入或接受明确范围等实际信号，不把赞同当稳定需求
- 维护容量或关键成本未知：标为未知，先补会改变排序的少量事实；不伪造精确总分
- 已足以选择下一项有限实验：停止分析，不为长期愿景补齐整套经营体系

**证据判断：**时间释放、现金节约、收入与可复用资产是不同结果；一次成交也不能证明可持续交付或可复制需求。远端已有价值与双账本原则，但未读到专门处理个人容量、维护负担与机会取舍的成熟条目。这是候选深化方向，需由实际任务素材支持，不是本地缺失判定。

入口：[现场选择与价值口径](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/kit/work-system/field-governance.md)、[材料 brief](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/templates/reporting/README.md)

### 不该加载 Kit 的反例

- “把这一句写得短一点”，上下文和事实已足够：直接改写，不先启动发现、场景模板或全文证据登记
- “解释这个普通术语”：通常用当前可信资料回答；仅当问的是 Praxis 自身的特定定义或跨宿主映射时查对应 Kit
- 已有确定性脚本能完成一次可逆格式转换：按工具能力和用户授权完成，不升级成 FDE 试点

这些负例是路由能力的一部分。能拒绝不必要加载，比让每个请求命中某个知识分类更重要。

## 八 整体编排备选与迁移

### 三种整体方案

| 方案 | 好处 | 代价与适用条件 |
|---|---|---|
| A 保留物理结构，增强现有任务入口和条目边界 | 路径稳定，便于与本地新 ADR 合流；先修已证断点 | 需要认真编订链接与正文；推荐现在采用 |
| B 按发现、交付、经营等任务族重组 package | 一个任务所需内容靠近，适合已有稳定团队/消费职责 | 跨任务 grammar 易复制，阶段也可能反复跳转；只有现有结构反复造成实证迷路时再考虑 |
| C 中央 grammar 库加 profile/recipe 的严格类型投影 | 可做机器路由和多宿主复用，语义治理较一致 | 类型及 schema 维护重，易出现百科式本体与读前先学分类；等真正出现重复消费者和自动路由需求再论证 |

**推荐 A。**新增内容优先落在现有专题文件的可链接章节。某条规则能够独立消费、具备不同维护节奏或被多个任务反复引用时，再拆成小文件。这里的拆分依据是消费与维护需求，不是给九类 grammar 各分一个文件夹。

### 保留 合并 互引 暂缓

| 动作 | 对象 | 实施约束 |
|---|---|---|
| 保留 | `vault / kit / docs / scenarios / templates / demos` | 资料、规则、裁决、场景、填表与实现拥有不同生命周期 |
| 保留 | 共同工作语法与企业九问；field-loop 与 field-governance | 前者分别是定义/投影，后者分别是推进路线/组织与价值约束 |
| 校订 | `Agent`、Reporting 入口、提炼总入口的 description/index | 改路由和范围说明，保留当前路径与来源身份 |
| 合并候选 | 不同入口重复出现的同一条长规则正文 | 先比对语义，再保留唯一规范文本，其余链接；没有证据支持删除任何整个文件 |
| 互引 | 事件工作系统、现场生命周期、Reporting、contracts、verification | 用任务和判断触发互链，不相互抄写全过程 |
| 对齐本地 | ADR-015–018 与 Design / Write / Motion | 先确认哪份内容已迁移、哪份仍是主责；旧远端建议不覆盖本地新裁决 |
| 暂缓 | 全站 frontmatter、新 `index.md`、第二套人工总账、知识图谱与自动路由 | 实际消费者提出不可由现有入口解决的需求后再启动 |
| 暂缓 | 新 OPC/FDE 顶层、工具百科、运行平台 | 用真实任务和可重复判断证明有必要，而非以能力愿景扩目录 |

这一建议延续 [ADR-009](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/docs/decisions/009-work-led-knowledge-architecture.md) 和 [ADR-011](https://github.com/lesPrivilege/Praxis/blob/3417dcac34998ce5e128222e6f7a7ca4f2dc8c96/docs/decisions/011-task-documentation.md) 的现有选择；若本地后续 ADR 已改变它们，以本地明确裁决核对迁移。

## 九 首批实施任务与验收停止

建议以下五项按前后依赖推进，不要求一次建设全部候选 grammar。第一项先核对本地，不必等待新的研究。

| 批次任务 | 具体输出与建议位置 | 需要的素材 | 验收和停止 |
|---|---|---|---|
| 1 校准入口职责 | 对照本地差异表；条件化 Agent/Reporting 阅读；修提炼总入口 description；更新现有文档结构约束 | 本地 ADR-015–018、新目录和本文固定 SHA 差异 | 三条静态路径及负例能明确找到必要阅读与停止点；没有重复规范 owner。完成后先停止重组 |
| 2 提炼问题诊断与取舍 | 在 field-loop/field-governance 现有主责下补“症状→假说→证据→下一决定”的小条目与一个示例 | 一次已结束的发现过程、一项最终未采用的方案、现场纠正记录 | 可指出什么证据会改变启动决定；保留非 AI/不做选项；无法支持通用规则的内容留场景 |
| 3 提炼语义映射与最小介入 | 复用 work/contracts/scenario，补同名对象、权威状态、边界动作和失败例 | 一个输入件到业务对象的映射、系统交接、正常/异常实例，均须获准使用 | 读者可写出局部契约，分清提议/批准/效果；输入变化、缺证据和结果未知有处理去向 |
| 4 补验收与接收协商方法 | verification 维护证据分层；field-loop/handoff 维护接收责任；Reporting brief 按需补 artifact 生命周期与交付保证 | 接受、人工修正和拒绝实例；标准分歧；一次临时 explainer 与一次持续交付的差异 | 技术质量、业务接受和持续运营分别结论；能为两类 artifact 选择不同检查且保留共同底线；不造十一套目录 |
| 5 以一项个人经营任务校准容量与复用 | 在价值/资产账本既有边界下形成候选条目，不立即开 OPC 目录 | 真实工作量、准备/复核/维护耗时、一次放弃选择及理由、获准的复用差异 | 能作下一次有边界投入判断；未知保持未知；资产收益与客户收益不混淆。没有素材时标候选并停止扩写 |

内容写入前，逐项记为“已有并保留 / 本地已解决 / 需要补充 / 证据不足暂缓”。对已被本地新版解决的问题，不再实施第二遍。

### 内容验收与持续改进

一次文档修订的验收重点是内容能否用来判断：触发是否命中；必要约束是否在动作前可见；读者能否得到最小工件；未知和停止条件是否明确；反例是否阻止错误泛化。仓库校验只验证链接/登记等一致性，不能证明知识有效。

建议实施后运行仓库约定校验，并记录合成走读；随后在获准的真实任务中收集失败、人工纠正、边界变化和实际接收情况。只有新证据改变某条规则时才修订它。首批无需新 telemetry 平台、完整 run 总账或训练流水线。

长期逐步加深：先识别与判断，再形成可重复 recipe，最后才考虑工具化或共享实现。知识条目的采纳、使用验证与实现晋升分开；现有实现晋升门槛不能机械套在每段解释文字上，也不能因写入 Kit 就宣称已实测。

## 交给实施者的最终判断

先对照本地新版修入口，再用已发生的工作把少数 grammar 写深。此次最小增量可以不新建顶层目录，也不增加机器总账。只有当某条内容能说明“何时用、怎样判断、什么会使它失效、下一人拿到什么”，它才从覆盖面清单成为可复用能力。

Artifact / Release 增补也遵循同一原则：按任务语义选择媒介，按接收者、用途、风险与生命周期选择交付保证；将可复用关系留在 Kit，将客户事实与具体运行责任留在它们的权威位置。
