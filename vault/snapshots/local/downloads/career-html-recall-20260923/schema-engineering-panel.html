Schema Engineering

当概率模型进入专业工作，工作本身必须存在于模型之外。

它不从 Agent、structured output、workflow、memory 或 multi-agent 起笔，而是先问：工作应以什么对象、状态、契约、执行和裁决结构持续存在？

Probabilistic Executor理解、探索、生成、行动候选
→
Professional Work Runtime对象、状态、证据、权限、完成、裁决

模型可以参与工作；工作不能依赖某一次输出、某段对话或某个专家的隐性补位。

开场：先把 Schema 从 JSON 和输出格式中解放出来。真正的问题不是模型如何填一张表，而是模型会被替换、Run 会结束、上下文会压缩以后，一项专业工作怎样仍然存在并承担组织责任。

Evidence before assertion

系统结果不能替单个组件作证。

Model、Runtime、environment、context、Contract 与 evaluator 共同决定结果，并可能强交互。证据必须说明是谁测的、测了什么、在哪个系统组合中成立，以及能否支持因果和市场外推。

EVIDENCE保留证据等级

独立复现、独立 benchmark、vendor report、self-benchmark、community observation 与产品推论不能同权。

SYSTEM系统组合不等于单因果

同一机构设计 benchmark、Harness、grader 与 adaptation，只能证明该组合在其设置下有效。

VERIFY专业正确性是混合裁决

Contract、validator、evaluator 与 Human Review 提供局部可裁决边界，不承诺完整形式验证。

TRACE生产记录先揭示分布

Task、failure、preference 与 escalation distribution 有运行价值；训练价值、权利和经济性另行证明。

ASSETS商业资产分别称重

分发、工作语义、失败分布、专家、环境、权利、集成与 refinement capability 分开评估。

CATEGORY产品范式不等于市场品类

共享 Runtime 可以构成设计范式；独立横向市场仍需 adoption、复用和支付意愿证明。

证据等级、因果贡献与市场外推，是三个必须分开回答的问题。

讲法：同一 Harness 改动在不同模型上可能方向相反，所以不使用“Model × Harness × Contract”这类伪装可分解性的公式。先陈述系统组合，再说明证据能支持到哪一层。

Schema 不是 JSON 的同义词

它是专业工作从概率探索进入组织承诺时的中间表示。

Schema Engineering 只外部化足以支持委派、验证、恢复和审阅的语义。它不承诺把全部专业知识形式化，也不把专家替换成规则。

Schema Engineering 是把专业工作的语义、状态、责任与裁决边界，编译为可版本化、可执行、可验证、可恢复的契约。
OBJECT正在处理什么；正式成果是什么。
RESPONSIBILITY谁能读取、改变、批准和承担后果。
COMPLETION哪些义务已满足；哪些仍需人类裁决。

Schema 是判断边界，不是领域全知模型。

边界：专家无法完整写出自己如何工作，规则也可能只适用于某个机构、客户或时点。正确问题不是“怎样把专业领域全部写进系统”，而是“为了可靠委派，哪些语义必须显式存在”。

为什么概率模型需要契约

模型擅长提议；组织需要可采用、可追责的承诺。

候选答案可以并列、撤回和互相矛盾。正式成果必须有范围、依据、版本、责任与后果。模型不应同时成为执行者、事实来源、完成标准与最终裁决者。

  • 允许试探、撤回和冲突
  • 可以广泛阅读与搜索

Model proposes→System enforces invariants→Evaluator measures semantics→Human adjudicates

P5 · P6Read wide; write narrow. 探索可以扩张，承诺必须收敛。

防守点：专业正确性不是单一 Boolean。系统可以判断格式、坐标、权限、算术和 coverage，但重要性、策略、风险接受和责任仍需人类承担。Schema 的作用是组织混合裁决。

Product Ontology

Session 是基础设施对象；Matter 才是用户对象。

一次 Run 会结束，模型会替换，用户会隔日返回。案件、交易、审计、研究和客户项目却必须继续存在。Conversation 可以保留为交互表面，但不能继续承担工作本体。

SESSION-FIRST

用户管理技术历史

  • new chat、title、branch
  • memory、context、compaction
  • 从 transcript 猜当前状态
  • 靠重放历史恢复工作
→
MATTER-FIRST

用户管理专业事项

  • 材料、问题、成果、证据
  • 修订、批准与 outcome
  • 正式状态存在于对话之外
  • 跨模型、会话和人员继续

P1 · P2 · P10Conversation 是 Matter 的视图和控制表面，不是产品 ontology。

讲法：这不是要求所有长期聊天都叫 Work。普通 Chat 和角色陪伴可以复用持久化 primitives，但专业工作额外拥有 evidence、completion、authority 与 responsibility。

Professional Work Runtime Ontology

把持续工作拆成稳定责任、临时执行与正式状态。

“多 Agent”不能概括持续工作的对象关系。Matter 容纳 Assignment；Operator 承担稳定责任；Lane 处理同一责任主体内的并行；Run 只是一次 activation；Event、Artifact、Semantic State 与 Review 使工作可恢复和裁决。

01Matter

跨时间存在的工作容器：资源、参与者、权限、成果和历史。

02Assignment

有 objective、deliverable、authority、completion 和 review 的可检查委派。

03Operator

承担稳定 responsibility、scope、tools、completion 与 escalation 的 actor。

04Lane

同一 Operator 内的 execution cursor；解决 parallelism，不新造责任。

05Run

某条 Lane 的一次执行；结束、失败或停止不自动等于 Assignment 完成。

06Event

回答 What happened；纠正用新 Event 表达，不静默改写历史。

07Artifact / State

真实 work product 与当前已知、已决、未决和 coverage 的权威表示。

08Review

接受、驳回、修订、追加工作、升级、批准和 policy promotion。

LANEParallelism：同一责任内的并行工作线
OPERATORDelegation：拥有独立责任、权限、完成与升级路径

P9并行执行不会自动产生新的 Agent；只有独立责任才产生新的 Operator。

追问：如果面试官问多 Agent，先问是否真的出现新的责任主体。检索线程、后台任务和并发 lane 共享同一 scope 与 authority，就不该为了架构感包装成 Agent。

Canonical State ≠ Context

发生过什么、现在是什么、模型应看什么，必须由三个不同对象回答。

Transcript 只能证明执行发生过，不能兼任权威当前状态。Context Projection 是面向当前 Operator、Lane、Run 的临时视图，可以压缩和替换；canonical state 不应因此丢失。

What happened?Event / Raw History

完整消息、工具轨迹、历史版本与执行事实。

What is happening?Semantic State

当前事实、判断、开放问题、coverage、版本和 review 状态。

What should model see?Context Projection

为本次执行选择 stable contract、相关状态、资源和可检索历史。

Stable Contract+Relevant State+Selected Resources+Retrievable History+Current Assignment

P3 · P4Continuity = stable contracts + current Semantic State + retrievable history，不是不断压缩 chronology。

验收句：换模型不会抹去 Matter；重启 Run 不用重放完整 Chat；审计者不会把 summary 当作事实源；人无需读完 transcript 也能理解当前工作。

Work Contract 不是万能表

专业责任由一组互补契约共同约束。

Evidence、Completion、Authority、Artifact、Review 与 Escalation 分别回答不同问题。Schema 不把所有判断机械化，而是让局部可验证义务和不可约人类判断各就其位。

EVIDENCE什么主张需要锚点

Provenance 是 state，不是装饰性 prose；同时区分事实、推论、偏好和策略。

COMPLETION什么才算完成

Required artifacts、issue families、coverage、evidence gaps、checks 与 approvals。

AUTHORITY谁能改变什么

Read、propose、modify、approve、publish、external transmit、delegate 与 promotion。

ARTIFACT正式成果是什么

定义 type、identity、version、status、引用关系、审批条件与下游用途。

REVIEW人在哪里承担责任

Accept、reject、revise、request further work、escalate、approve。

ESCALATION怎样表达不能回答

Issue + evidence + alternatives + recommendation + reason for escalation。

P7 · P8模型不被迫回答所有问题；不确定性被送到正确的责任边界。

权限翻译：用户不该批准 write_file，而是在接受成果修订；不该批准 external tool，而是在决定是否向客户发送工作件。技术 capability 与业务 authority 必须分开。

Hidden Human Harness

专家 prototype 的有效性，常常来自作者本人在暗中维持 runtime。

专家选择任务和 context、发现遗漏、重写 framing、换来源、重试、判断重要性并决定能否交付。移除作者后产品失效，说明需要产品化的不是 prompt，而是足以支持委派的隐形干预。

L1Domain invariant

稳定领域义务，进入 product contract 或 evaluator。

L2Institution convention

进入版本化机构配置，不冒充领域真理。

L3Client / Matter context

只约束特定客户、事项与时间范围。

L4Individual habit

默认停留为用户偏好，不因频率自动推广。

产品化专家，不是复制专家全部大脑；是外部化足够多的委派、验证、恢复与审阅边界。

边界：高风险、语境密集且责任不可转移的判断继续留给 expert。Schema Engineering 的核心操作不是 capture 越多越好，而是正确分层和谨慎 promotion。

Capture first, infer later, promote selectively

正常审阅不能被改造成高频数据标注。

Revision 首先是可审计工作事实。系统自动捕获 before / after、角色、Matter、evidence、trajectory 与 outcome；再推断 correction type、scope 和 failure family；只有准备改变未来行为时，才请求一次人类 promotion。

01Capture

记录本来就发生的 Event，不增加 reason code 与 metadata labor。

02Infer

带不确定性推断语义、适用范围、重要性与 reviewer disagreement。

03Promote

只有改变 future behavior 时，才确认 client、institution、product 或 eval scope。

PRODUCTION

揭示真实分布

Task、failure、preference、escalation、accepted-work-product standard 与 environment seeds。

SYNTHETIC

扩展任务与失败模式

专家定义 task family 与 rubric，生成环境，由确定性检查和专家审计争议案例。

P11 · P12生产 trace 不自动成为训练数据；Synthetic scale 也不自动证明真实相关性。

理论姿态：Production feedback 的首要价值是发现真实分布并提供环境种子。客户机密、权利、选择偏差和审阅歧义都可能阻止直接训练。Post-training 始终是可选分支。

Delete scaffolding aggressively

面向模型的脚手架应该折旧；面向工作责任的语义需要谨慎保存。

更强模型会吞掉推理 recipe、prompt trick、过细 workflow 和 checkpoint workaround。继续维护这些实现不是护城河。真正需要保留的是工作是什么、谁承担、何时成立，以及哪些权利允许复用。

P13 · P14 · P15Delete scaffolding aggressively; preserve semantics deliberately.

经济判断：Harness 即使今天有效，也可能被上游模型进步单方面重新定价。好的 specialization 学的是 state、evidence、authority、completion；坏的 overfit 只会固定 wrapper、tool name 和 field order。

Professional Work Runtime

共享 Runtime 是产品范式，不是万能横向平台。

共享 Runtime primitives 可以跨领域复用，但 evidence、artifact、authority、completion 和 review 的专业意义仍由垂直产品定义。Courtwork 是法律实现，不是理论证据闭环，也不是理论边界。

RUNTIME通用 primitives

Durable Matter、responsibility、Lane、Event、State、Artifact、evidence、authority、completion、review。

VERTICAL专业语义

什么算 evidence；存在哪些 Artifact；哪些义务构成完成；谁能决定；何时必须升级。

MODEL可替换执行者

产品在无 proprietary model、fine-tuning 或 post-training 时也必须成立。

HIGHER CONFIDENCE

核心产品命题

  • Matter-first ontology
  • External canonical state
  • Evidence、authority、completion、review
  • Operator 与 Lane 分离
  • 产品吸收 Agent complexity
LOWER CONFIDENCE

学习与商业分支

  • Production feedback 是长期 moat
  • Institution-level generalization
  • Synthetic / production 的经济关系
  • Refinement capability 的商业优势
  • 独立横向市场品类

共享基础设施不取消垂直设计；generic schema 不能替代领域意义。

无 buzzword 定义：Professional Work Runtime 以长期事项和正式成果为中心；模型在契约下执行，系统在对话之外维护状态、证据、权限、完成与历史，人只在专业责任节点裁决。

理论必须允许自己失败

真正的边界，不是“实现很难”，而是什么结果会迫使理论下修。

Falsifiers 为核心理论、学习分支、模型与 Harness、产品类别分别定义必要测试。下面六项足以决定这套理论是跨领域产品范式、垂直架构纪律，还是应进一步收缩。

F1长上下文 Chat 等于或优于外部 State

同一 Matter 分布下比较跨周恢复、审计、成本与 accepted work product。

Semantic State 降为可选优化；P3、P4 必须下修。

F3Runtime primitives 跨领域持续退化

在三个责任结构不同的领域记录例外、绕行、迁移成本和成果接受率。

理论退回 Courtwork 或少数垂直架构。

F5Structured Contract 损害开放判断

比较结构化、弱结构与无结构任务的重大遗漏、锚定和伪正确。

缩小 accountability fields，部分任务放弃 Schema。

F6Human Review 无法集中到高杠杆节点

比较持续干预、阶段 Review 与终局 Review 的专家时间、返工和重大遗漏。

产品退回 expert augmentation。

F14Frontier 平台商品化整个 Runtime

用真实替换决策比较配置成本、领域覆盖、集成留存和支付意愿。

仅保留内部设计纪律，不再构成独立产品机会。

F15横向 Runtime 没有独立 adoption

观察三个垂直实现的独立采用、复用率、集成时间与开发者价值。

不再宣称独立横向市场类别。

必要测试一旦得到证伪结果，就执行对应的收缩，不以实现困难保留命题。

补充：完整 bundle 还有 Production Review 信号质量、Synthetic Environment 经济性、institution pattern、rights、harness portability 与 progressive disclosure 等 16 项 falsifier。宣讲时先用这六项说明理论不是封闭系统。

Minimum Product Acceptance

不要问产品是否“用了 Schema”；检查工作是否真正脱离对话而存在。

一个产品只有同时满足以下条件，才构成 Professional Work Runtime。它们比 Agent、Memory、Workflow 或 Multi-agent 的功能标签更接近真实验收。

01用户返回 Matter，而不是重建一段 Chat。
02不读完整 transcript 也能理解当前工作状态。
03Artifact 与 approved decision 能跨模型、跨 Session 存在。
04Assignment completion 不由执行者单方面宣布。
05Evidence 与 authority 存在于 prose 之外。
06并行执行不会模糊 responsibility。
07Human Review 会改变正式状态，而不只是留下评论。
08系统能分别回答历史、当前状态与模型视图。
09普通专业用户不必学习 Agent engineering。
10完全不做 proprietary post-training，产品仍有真实价值。
P16不要训练可以可靠验证的东西；不要把局部偏好推广成全局规则；不要自动化仍然需要不可约责任的判断。

90 秒收束：Schema Engineering 是 Professional Work Runtime 的契约纪律。模型负责概率探索，系统保存 Matter、Semantic State、evidence、authority 和 completion，人裁决不可约责任。Session 是基础设施，Matter 是用户对象；Transcript 是执行证据，不是 canonical state；Lane 是并行，Operator 是责任。生产 Review 先捕获、后推断、谨慎升级，不自动形成训练飞轮。更强模型淘汰 model-facing scaffold，工作语义则谨慎保留；学习、护城河与横向品类判断继续接受 Falsifiers 检验。
