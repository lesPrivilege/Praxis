§0定本位置

本文试图回答一个基础问题：当概率模型进入专业工作后，工作本身应当以什么对象、状态、契约、执行和裁决结构持续存在？

法律可以提供高要求的实例：事实需要来源，行动受权限约束，成果需要审阅，责任不能交给模型自行宣布。但这些要求也存在于财务、医疗、咨询、研究、工程、合规、审计和其他高价值工作中。

经验性判断必须保留证据等级。独立复现、独立 benchmark、含负面结果的 vendor technical report、vendor self-benchmark、community observation 与产品推论不能被统一称为「已验证」。

系统能力应被理解为 Model、Runtime、Environment、Context、Contract 与 Evaluator 的交互结果。不同组件之间可能存在强交互，甚至同一改动在不同模型上方向相反。

§1定义

Courtwork 原定义为：把领域判断编译成模型可写、系统可验、人可读改签的契约。本文将它上提为：

定义Schema Engineering 是把专业工作的语义、状态、责任与裁决边界，编译为可版本化、可执行、可验证、可恢复的契约，使概率模型能够参与工作，而工作本身不依赖某一次模型输出、某段对话或某个专家的隐性补位。

这里的「编译」不是把全部专业知识形式化，也不是把专家替换成规则。它只要求把对委派真正必要的边界变得明确：

  • 正在处理什么工作对象；
  • 谁承担什么责任；
  • 可以读取和改变什么；
  • 哪些主张需要证据；
  • 当前状态是什么；
  • 什么条件才算完成；
  • 哪些判断可以由系统裁决；
  • 哪些判断必须由人承担；
  • 修改、批准和升级如何改变正式工作成果。

Schema 因而不是 JSON 的同义词。它是专业工作从概率性探索进入组织性承诺时的中间表示和契约纪律。

§3为什么概率模型需要结构化契约

3.1提议不等于承诺

模型擅长提出候选答案、线索、解释、草稿和行动。专业工作要求的是可以被组织采用的主张、决定、成果和行动。两者之间存在结构性差异：

  • 提议可以并列、撤回和互相矛盾；
  • 承诺必须有范围、依据、版本、责任与后果；
  • 推理过程可以探索；
  • 正式成果必须知道哪些内容被接受，哪些仍未解决。

因此模型不应同时成为工作的执行者、事实来源、完成标准和最终裁决者。一个专业系统必须在模型之外维护正式状态和责任边界。

3.2工作必须长于一次执行

一次 Run某条 Lane 上的一次 activation：接受输入、调用工具、生成或修改成果、停止、失败与恢复。 会结束，模型会替换，上下文会压缩，工具会变化，用户会隔日返回。真实工作却必须继续存在。如果工作只存在于 transcript 中，那么连续性依赖于：对历史对话的反复压缩；对旧模型隐含推理的猜测；对一次性 prompt 的复现；对用户记得「上次说到哪里」的要求。这不是稳定的工作状态，只是会话残留。

3.3专业正确性不是单一 Boolean

专业工作通常没有一个廉价、完整的 oracle。系统可以验证字段、权限、版本、引用坐标、算术和明确 coverage，却不能自动替代所有关于重要性、策略、风险接受、例外和责任的判断。因此需要混合裁决：

P6模型提出；确定性系统执行不变量；Evaluator 测量已被明确规定的语义；人裁决不可约的专业判断。

Schema Engineering 不假装消除人类判断，而是把人从持续、隐形的微操，移动到少数真正需要承担责任的节点。

3.4完整编码专业知识既昂贵也脆弱

专家往往无法完整陈述自己如何工作。即使能够陈述，规则也可能只适用于某一机构、客户、时点或个人习惯。把所有隐性知识都写成规则，会制造新的维护负担和伪确定性。

因此 Schema Engineering 的问题不是：如何把专业领域完整地写进系统？而是：为了让工作可委派、可验证、可恢复、可审阅，哪些语义必须显式存在？

Schema 是判断边界，不是领域全知模型。

§4Matter，而不是 Session

Professional Work 产品的一等对象应当是 Matter用户世界中长期存在的工作事项：一宗案件、一项交易、一次审计、一个研究任务、一个客户项目或一项长期职责。：用户世界中长期存在的工作事项。它可以是一宗案件、一项交易、一次审计、一个研究任务、一个客户项目或一项长期职责，并拥有 identity、resources、participants、permissions、assignments、artifacts、semantic state、evidence、event history、reviews 与 outcomes。

Session 是一次技术交互；Matter 是工作本身。传统 Chat 产品让用户管理 new chat、history、title、branch、memory 和 context。Professional Work 产品应让用户管理事项、材料、问题、成果、证据、修订与批准。Conversation 仍然存在，但它只是 Matter 内的一种 interaction surface。正式原则是：

P1Session 是基础设施对象，Matter 才是用户对象。
P2Conversation 是交互表面，不是工作本体。

这并不要求所有长期对话都被称为 Work。普通聊天、角色陪伴和开放探索可以共享持久化 runtime primitives，却不必共享专业工作的证据、完成、权限和责任语义。

§5Professional Work Runtime Ontology

一个最小的 Professional Work Runtime 可以由以下对象构成：

Matter
├── Resources / Context
├── Assignment / Work Contract
├── Operator
│   ├── Lane
│   │   └── Run
│   └── Delegated Operator
├── Event Ledger
├── Semantic State
├── Evidence
├── Artifacts
└── Review
    └── Revision / Outcome

5.1Matter

长期工作容器。它定义资源边界、参与者、权限、当前事实、正式成果和历史。Matter 应能跨模型、跨会话、跨人员继续存在。

5.2Assignment 与 Work Contract

Assignment 是一次可检查的委派，不只是自然语言 prompt。它至少说明 objective、deliverable、audience、constraints、deadline、authority、completion requirements 与 review / escalation requirements。

Work Contract 是约束这项工作的契约集合，包括 evidence、artifact、state、completion、authority、review 和 escalation。重要的是这些语义可被版本化并由 Runtime 执行。Matter 可以同时容纳多个 Assignment：Matter 本身是对象，Work Contract 是规范。

5.3Operator

承担一项稳定责任的 actor，可以是人、主 Agent 或被委派的专门执行者。只有同时出现相对独立的 responsibility、scope、tools、authority、completion 与 escalation，才值得创建新的 Operator。并行调用、检索线程或后台任务不自动等于 Multi-agent。

5.4Lane

同一 Operator 内部的一条独立工作线或 execution cursor。Lane解决 parallelism，不解决 delegation：同一责任主体在不同 Lane 中并行推进，共享责任与权限。 解决的是 parallelism，不是 delegation。同一个责任主体可以在不同 Lane 中检查不同问题、起草不同部分或并行搜集材料。它们共享责任与权限，不需要伪装成多个 Agent。

5.5Run

某条 Lane 上的一次 activation，包括接受输入、调用工具、生成或修改成果、停止、失败和恢复。Run 是暂时的；Operator 是稳定责任主体。一次 Run 的结束不等于 Assignment 完成，更不等于 Matter 结束。

5.6Event

在适用 retention policy 内不可被静默改写的执行事实。纠正应通过新的 Event 表达；删除、归档或匿名化由明确的权利与保留政策处理。Event 例如：assignment accepted、resource accessed、tool called、artifact created、review requested、revision made、approval granted、failure occurred。

Event history 回答「What happened」，但不直接等于当前工作状态，也不应默认全部进入模型上下文。

5.7Artifact 与 Semantic State

Artifact 是可以进入真实工作流的成果：文档、表格、redline、研究记录、结构化 issue、决策记录或其他 work product。Semantic State回答「现在是什么」：已确认的事实与判断、未解决的问题、当前 coverage、evidence gap、已批准的决定、成果的版本与状态。 回答「What is happening now」：已确认哪些事实和判断；哪些问题仍未解决；当前 coverage 如何；存在哪些 evidence gap；哪些决定已经批准；哪些成果处于何种版本和状态。正式原则是：

P3Transcript 是执行证据，不是 canonical work state。

Canonical state 应主要存在于 artifacts、schema instances、evidence graph、issue state、completion ledger、revision state 和 approved decisions 中。

5.8Review

Review 是工作生命周期的一部分，不是异常处理。它包括 accept、reject、revise、request further work、escalate、approve 与 promote policy。专业系统的目标不是让人一路点击 Yes，而是让人只在具有专业意义、权限意义或学习治理意义的节点裁决。

§6状态连续性与 Context Projection

Professional Work Runtime 必须分开三个问题：What happened？——Event 与 raw history；What is happening？——Current Semantic State；What should the model see now？——Context Projection。这三者不能由同一个 transcript 同时承担。连续性可以分为三层：

6.1Stable Contract

长期稳定的 role、institution policy、assignment semantics、professional schema、permissions 和 tool authority。

6.2Current Semantic State

当前事实、已确认判断、开放问题、evidence、coverage、artifact version、decision 和 pending review。

6.3Raw History / Evidence

完整 transcript、原始材料、工具轨迹、低层 Event 和旧版本成果。默认可检索，而非全量注入。由此得到：

P4连续性应建立在 stable contract、current semantic state 与 retrievable history 上，而不是不断压缩 chronology。

Context Projection 是 Runtime 根据当前 Operator、Lane、Assignment 和任务阶段，为模型生成的临时视图。它可以变化、压缩和替换；canonical state 不随其变化而丢失。因此 Memory 不应被设计成一个不断增长的「模型记忆罐」。真正重要的是工作状态的外部化、检索权和语义投影。

§7Contract Discipline

Schema Engineering 通过一组互补契约约束工作，而不是试图用一个万能 schema 表达一切。

7.1读宽写窄

模型可以广泛阅读、搜索、比较、试探和撤回。进入正式成果的内容必须经过更窄的 typed boundary：

P5探索可以概率化和扩张；承诺必须被收敛、定位、版本化并承担责任。

7.2Evidence Contract

需要事实依据的正式主张必须关联 machine-readable provenance。模型可以提出 quote 或 claim；Runtime 负责解析真实来源、版本、坐标和可验证关系。

P7Provenance 应当是 state，而不是装饰性 prose。无锚，不进入需要事实承诺的正式状态。

这不意味着所有专业判断都有可引用来源。Evidence Contract 必须区分事实、推论、偏好、策略与人类裁决，避免用伪引用掩盖判断。

7.3Completion Contract

模型不能单方面定义成功并宣布完成。Completion Contract 应在模型之外维护：required deliverables、required issue families、coverage、unresolved questions、evidence gaps、mandatory checks、required approvals、artifact validation state。专业工作不一定有完整 oracle，但可以被拆成一组局部可验证义务和明确的人类裁决点。

7.4Authority Contract

系统必须知道谁能读取、修改、批准、发布、执行和撤销什么。技术工具权限应被翻译为业务语义：

不是
  • Allow write_file?
  • Run external tool?
而是
  • Accept this revision?
  • Send this work product to the client?

技术对象不应自动成为用户心智对象。

7.5Artifact Contract

最终价值单位是 work product，而不是聊天回答。Artifact Contract 定义成果类型、结构、版本、状态、引用关系、审批条件和下游可用性。

7.6Review 与 Escalation Contract

Escalation 是一等 action，不是模型失败后的兜底。一次合格 escalation 至少应表达：

issue + evidence + alternatives + recommendation + reason_for_escalation

目标不是迫使模型回答，而是让不确定性在正确的责任边界上被处理。

§8从专家 Prototype 到产品

高水平专家做出的 prototype 往往不是「好 prompt」的证明，而是专家本人构成了一层隐形 runtime：

Expert selects task and context
→ Model attempts
→ Expert notices omission or error
→ Expert changes framing, source or search
→ Model retries
→ Expert judges materiality
→ Expert decides what is deliverable

产品化的对象不是 prompt，而是这些干预。

P10产品化专家 prototype，是把足够多的隐形人类 harness 外部化，使其他人能够委派同类工作，而不必继承作者的大脑。

「足够多」很重要。并非所有专家行为都应进入系统：

专家行为默认去向
可重复、低争议、可机械验证Validator / deterministic policy
稳定的领域义务Product contract / evaluator
稳定的机构惯例Versioned institution configuration
客户或 Matter 特有要求Client / Matter context
可委派但仍需判断的步骤Assignment / review surface / escalation
个人表达和捷径User preference，默认不推广
高风险、语境密集且责任不可转移的判断保留给 expert

专家 prototype 通常混合四层知识：domain invariant、institution convention、client / matter context、individual habit。Schema Engineering 的核心操作不是简单 capture，而是正确分层和谨慎 promotion。频率不能自动把个人习惯升级成机构规则，也不能把机构规则误写成领域真理。

§9Review、Revision 与学习

Revision 不是异常；专业工作本来就通过委派、审阅、修改和批准推进。但产品不应要求专业人士为了未来训练，在每次修改时额外填写 reason code、materiality、scope 和 judgment type。那会把真实工作变成数据标注，并最终使审阅界面退化为最低成本点击。本文采用：

P11Capture first, infer later, promote selectively.

9.1Automatically observed facts

系统自动记录本来就发生的事实：before / after；artifact path 与 version；actor 与 role；matter 与 assignment；evidence；surrounding context；trajectory；outcome；learning rights。

9.2Machine-inferred semantics

系统可以带不确定性地推断 correction type、likely scope、materiality、failure family、applicability 与 reviewer disagreement。这些推断可以通过跨 Matter、跨 reviewer 和跨版本比较逐步校正，不应立即成为规则。

9.3Human-confirmed promotion

只有当系统准备改变 future behavior 时，才要求一次明确裁决，例如：Matter 规则是否成为客户偏好；重复客户偏好是否成为机构配置候选；重复机构修正是否成为产品或领域规则候选；某类失败是否进入正式 eval；某类数据是否允许用于 aggregate、evaluation 或 training。

P11不要把低频、高价值的 learning governance，变成高频审阅摩擦。

§10Production Learning 与 Synthetic Environment

结构化产品界面可以成为数据采集界面，但它不会自动形成数据飞轮。真实生产 trace 的独特价值首先是暴露 task distribution、failure distribution、preference distribution、escalation distribution、environment seeds 与 accepted-work-product standard。

它们未必适合直接训练。客户机密、权限、上下文依赖、审阅歧义和选择偏差都可能使原始 production data 无法复用。同时存在另一条路线：

Expert defines task family / rubric ontology
→ synthetic environment generation
→ oracle or multi-agent solve
→ deterministic checks
→ expert audits disagreements and high-value cases
→ accepted eval / training environments

这两条路线不是简单替代关系：Production Learning 告诉系统真实世界在哪里工作、在哪里失败、何种偏好重要；Synthetic Environment Factory 用更低的边际成本扩展这些任务族和失败模式；生产中的 accepted work product 与隐藏分布可作为独立验证集，防止 synthetic system 只优化自己的世界。因此更稳健的裁定是：

P12Production feedback 的首要价值是发现真实分布并提供环境种子；其直接训练价值必须逐项证明。Synthetic generation 可以扩展规模，但不能自行证明分布相关性。

Schema、Evidence 和 Revision 的作用，是让生产事件有机会被解释和治理，而不是保证每个事件都能转化为训练样本。

§11折旧、Eval 与模型战略

11.1双重折旧曲线

Schema 中面向模型的 scaffold 与面向人和系统的语义具有不同寿命。

应主动删除
  • explicit reasoning recipes
  • model-specific prompt tricks
  • 过细 workflow instruction
  • 某一 checkpoint 的 tool workaround
  • 仅为补偿当前模型缺陷的 context orchestration
应谨慎保留
  • artifact semantics · provenance
  • authority · permissions
  • canonical state · completion
  • review · audit
  • institution policy · rights
P13Delete scaffolding aggressively; preserve semantics deliberately.

如果一部分 Schema 只是在补模型智力，它理应被更强模型淘汰——本理论也接受这一点：更强模型应当能够淘汰其中一部分实现，而不是被迫证明所有既有 scaffold 永久必要。真正长期存在的不是对模型「怎么想」的规定，而是工作「是什么、由谁承担、何时成立」的语义。

11.2Eval infrastructure 复利，单个 Eval item 折旧

一个 Eval 条目可能因为模型普遍通过而失去 frontier discrimination value，也可能因任务分布、制度或法规变化而过时。应分别衡量 stable regression value、frontier discriminative value、distribution relevance 与 legal / institutional validity。

P14Eval infrastructure 会复利；单个 Eval item 会饱和并折旧。Environment generation capability 会复利；单个 environment instance 也会饱和。

11.3Harness 的经济折旧

一个 harness scaffold 即使今天有效，也可能被上游模型进步单方面重新定价。模型原生获得规划、恢复、context management、tool repair 或 long-horizon 能力后，下游相应基础设施可能直接折旧。这与「模型是否 overfit 某个 prefix 或 tool name」是两个问题：技术问题是模型是否依赖表面语法；经济问题是下游 harness 的哪些能力拥有独立长期价值。对前者应做 portability 与 robustness eval；对后者应持续删除已被模型吸收的 scaffold。

好的 harness specialization 让模型学会工作环境的语义：state、evidence、authority、completion、escalation。坏的 harness overfit 让模型只会固定 wrapper、tool name、field order 或 prompt template。

11.4Post-training 的位置

Post-training 不是产品理论的终点。顺序应是：

Professional Work
→ stable product semantics
→ production usage
→ failure distribution
→ eval
→ environment
→ selective post-training, only when justified

新的 frontier model 若在 accepted-work-product eval 上超过旧 specialized model，应直接迁移，不为旧 checkpoint 的 sunk cost 辩护。Training 只在可测量地改善 accepted work product、completeness、grounding、escalation calibration、institutional adherence、cost、latency 与 tool efficiency 时存在。

产品即使从未训练任何模型，也必须能通过 Matter、state、evidence、authority、artifact 和 review 产生真实价值。

§12长期资产与商业边界

不存在一个自动成立的单一 moat。需要分别评估 distribution、work semantics、production failure distribution、expert access、environment generation、rights、runtime integration 与 refinement capability。这些资产可能只有组合起来才产生价值，也可能分别被平台商、模型商或垂直软件商品化。Schema Engineering 不保证护城河，只提供一个观察和积累这些资产的结构。

同样，机构真正能够沉淀的是具体对象：work contracts、precedent hierarchy、institution policy、client preference、completion standards、review patterns、escalation rules、eval infrastructure、environment generators、trained policies。若这些对象确实能让专业判断超越原始个体而稳定复现，可以描述为组织能力。

§13它是否定义了一个独立产品

本理论足以定义一种独立的产品范式，但尚不足以证明一个天然成立的横向市场品类。它定义的共同产品问题是：如何让用户面对长期工作对象和正式成果，让概率模型在背后执行，让系统维护状态、证据、权限与历史，让人只在具有专业意义的节点裁决。

这一范式可以由不同垂直产品实现，因为各领域的 artifact、evidence、authority、completion 与 review 语义不同。共享 runtime primitives 不意味着一个无差别的「万能专业 Agent 平台」必然优于垂直产品。Courtwork 是法律方向的实现；它不构成本理论的证据闭环，也不限制理论的外延。最终的无 buzzword 产品定义是：

产品定义Professional Work Runtime 是一种以长期工作事项和正式成果为中心的系统：模型在可执行契约下完成工作，系统在对话之外维护状态、证据、权限、完成条件与可恢复历史，人只在需要专业责任的节点进行裁决。
