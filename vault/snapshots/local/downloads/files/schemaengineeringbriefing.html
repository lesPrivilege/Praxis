§0　定本位置Schema Engineering

§0工作本身应当以什么结构持续存在？

本文接受的两条前提
  • 经验性判断必须保留证据等级——独立复现、独立 benchmark、含负面结果的 technical report、self-benchmark、community observation 与产品推论，不能被统一称为「已验证」。
  • 系统能力是 Model、Runtime、Environment、Context、Contract 与 Evaluator 的交互结果；同一改动在不同模型上可能方向相反。
法律是高要求的实例，不是边界
  • 事实需要来源
  • 行动受权限约束
  • 成果需要审阅
  • 责任不能交给模型自行宣布

同样的要求见于财务、医疗、咨询、研究、工程、合规与审计。

§1　定义Schema Engineering
定义Schema Engineering 是把专业工作的语义、状态、责任与裁决边界，编译为可版本化、可执行、可验证、可恢复的契约，使概率模型能够参与工作，而工作本身不依赖某一次模型输出、某段对话或某个专家的隐性补位。

「编译」不是把全部专业知识形式化，也不是把专家替换成规则。它只要求把对委派真正必要的边界变得明确——

9　项边界
正在处理什么工作对象谁承担什么责任可以读取和改变什么 哪些主张需要证据当前状态是什么什么条件才算完成 哪些判断可以由系统裁决哪些判断必须由人承担修改、批准与升级如何改变正式成果
Schema 不是 JSON 的同义词，而是专业工作从概率性探索进入组织性承诺时的中间表示与契约纪律。§1
§4　Matter，而不是 SessionSchema Engineering

§4用户管理的是事项，不是会话

Matter 应能跨模型、跨会话、跨人员继续存在。Conversation 只是它内部的一种 interaction surface。

Chat 产品让用户管理
  • new chat　·　history　·　title
  • branch　·　memory　·　context
Professional Work 产品让用户管理
  • 事项　·　材料　·　问题
  • 成果　·　证据　·　修订与批准
P1Session 是基础设施对象，Matter 才是用户对象。
P2Conversation 是交互表面，不是工作本体。
这并不要求所有长期对话都被称为 Work——共享 runtime primitives，不必共享证据、完成、权限与责任语义。§4

§6　状态连续性与 Context ProjectionSchema Engineering

§6三个问题不能由同一个 transcript 承担

3　层
WHAT HAPPENED? Tier 3　Raw History 完整 transcript、原始材料、工具轨迹、低层 Event、旧版本成果。默认可检索，而非全量注入。
WHAT IS HAPPENING? Tier 2　Semantic State 当前事实、已确认判断、开放问题、evidence、coverage、artifact version、decision、pending review。
WHAT GOVERNS IT? Tier 1　Stable Contract role、institution policy、assignment semantics、professional schema、permissions、tool authority。
WHAT SHOULD THE MODEL SEE NOW? Context Projection Runtime 依当前 Operator、Lane、Assignment 与任务阶段生成的临时视图。可变化、可压缩、可替换；canonical state 不随其丢失。
P4连续性应建立在 stable contract、current semantic state 与 retrievable history 上，而不是不断压缩 chronology。
Memory 不应被设计成一个不断增长的「模型记忆罐」。真正重要的是工作状态的外部化、检索权与语义投影。§6

§7一组互补契约，不是一个万能 schema

6　种契约
Work Contract约束一项工作的契约集合；可被版本化并由 Runtime 执行
Evidence Contract正式主张须关联 machine-readable provenance；须区分事实、推论、偏好、策略与人类裁决
Completion Contract在模型之外维护：deliverables、coverage、unresolved questions、evidence gaps、approvals
Authority Contract谁能读取、修改、批准、发布、执行与撤销什么
Artifact Contract成果类型、结构、版本、状态、引用关系、审批条件与下游可用性
Review / Escalationissue + evidence + alternatives + recommendation + reason
技术权限翻译为业务语义
不是Allow write_file? 而是Accept this revision? 不是Run external tool? 而是Send this to the client?

P5　探索可以概率化和扩张；承诺必须被收敛、定位、版本化并承担责任。§7

§11.1Scaffold 与语义有不同的寿命

2　条曲线
应主动删除　·　面向模型的 scaffold
  • explicit reasoning recipes
  • model-specific prompt tricks
  • 过细 workflow instruction
  • 某一 checkpoint 的 tool workaround
  • 仅为补偿当前模型缺陷的 context orchestration
应谨慎保留　·　面向人与系统的语义
  • artifact semantics　·　provenance
  • authority　·　permissions
  • canonical state　·　completion
  • review　·　audit
  • institution policy　·　rights
P13Delete scaffolding aggressively; preserve semantics deliberately.
更强模型应当能够淘汰其中一部分实现，而不是被迫证明所有既有 scaffold 永久必要。产品即使从未训练任何模型，也必须能产生真实价值。§11

收束Schema Engineering · Canon
无 buzzword 的产品定义

Professional Work Runtime 是一种以长期工作事项和正式成果为中心的系统：模型在可执行契约下完成工作，系统在对话之外维护状态、证据、权限、完成条件与可恢复历史，人只在需要专业责任的节点进行裁决。

本理论足以定义一种独立的产品范式，但尚不足以证明一个天然成立的横向市场品类。Courtwork 是法律方向的实现；它不构成本理论的证据闭环，也不限制理论的外延。
