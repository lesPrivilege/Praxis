# 给 Opus 的有限消费建议

目的：从《社区 Skills 与 Prompts 的可迁移语法》挑选可检验的机制，为已有 Praxis grammar 补证据、边界与反例。此轮是研究交接，不授权改仓库、安装 skills、调用外部 agents、修改模型配置或运行评测。

## 先消费什么

1. 优先读 Aider 的局部恢复、superpowers 的单一假设与压力退化、Anthropic skill-creator 的基线与轨迹分析。这三者分别回答“状态变了一半怎么办”“为什么又在乱试”“这条规则是否真增加价值”。
2. 第二批读 Open Deep Research 的证据压缩和错误被当完成的反例，以及 DOCX 的产物完整性检查。前者用于 Research，后者只抽独立实现的抽象机制并引用来源；不复制受限原文或脚本。
3. OpenAI 的渐进披露与 BMAD 的发现/交接，先映射现有 description/index/content 和相关领域；能交叉引用就不增加目录。Fabric 留作输出契约和风格过约束的 Vault 对照。

## 每次最多处理一个机制

先定位现有条目，再写一张不超过一屏的候选卡：

- 来源与固定版本、真实原问题、证据强弱
- 触发条件和不应触发的近失例
- 要保住的业务/安全/产物不变量
- 输入证据 → 判断 → 行动 → 可观察反馈 → 停止/升级条件
- 当前环境适配项，以及缺失时的显式退出
- 一个正常例、一个跨领域陌生例、一个会误用的反例
- 与现有条目是同义、细化还是矛盾；默认动作是合并或交叉引用
- 预期收益与可能新增的成本；最小对照方案；状态必须标“未实测”

不要把机制再压成“先思考、再执行、最后验证”之类无法反驳的名字。不要为了对齐目录而拆出没有独立选择条件的原子。

## 若以后获得真实评测授权

固定任务、环境和验收标准，比三种条件：现有流程、只加候选短语法、必要时原包。先检查原任务正确性，再看误触发、错误停止、重复副作用、时间/调用成本；未知任务保留至最终复核。主观写作/设计用盲序人评，代码/表格/文档完整性用独立验收，不把形式遵循当质量。小样本只筛除坏方案，不宣称泛化率。

## 多模型 tip 如何登记为参考

保留“日常处理者、探索者、执行者、复核者、便宜有界分类器”的角色和交接证据；将 Sol/Luna/Astra/Jev、effort、延迟、固定升级时点记为2026-10-02的可替换配置快照。升级应由不可逆承诺、重复无信息失败、证据冲突或高影响交付触发，而不是所有任务机械调用三遍专家。便宜分类器允许 abstain，不能自行扩大权限。

## 兼容性与 RSI 的最小边界

后续无论以用户称呼的“mod”还是其他封装接入，都先保持稳定任务语义与 provider adapter 分离；这里不确认具体产品名或开放状态。兼容性只验发现/加载、资源可达、工具与权限前置条件、产物可交接四条窄通路。遇上游更改或真实失败才重看相关来源，保留上一版与撤回理由即可；不建立全量镜像和每日同步负担。

建议 Opus 后续阅读的完成标准：输出至多3个优先候选及2个暂缓项，每个都能指出来源、反例、现有落点与未验证之处。不能拿此提案当实际接纳、导入或运行的完成证明。
