技术说明 · dsh-praxis

一个插件，把工作方法变成 Agent 能查的工具

dsh-praxis 不是聊天记忆，也不是内容生成器。它是一套按任务类型装配的方法库：Agent 按当前任务读出该用的规则、该找的参考，交付时把产物和所用版本一起登记下来。

结论

dsh-praxis 的核心是「按任务装配方法论」加「运行可追溯」：76 个方法单元经一个入口读出来，21 个工具让人和 Agent 用同一组操作维护它们，每次交付记下用了哪一版规则、产出哪一版文件。

  • 01四层方法库，按任务取用。 Task 决定做什么，Writing 与 Design 常驻，Publish 按媒介分流水线。 见第 1 章
  • 02取用是渐进的，不是全量加载。 一条技术说明只被解析出 12 个单元和 4 条素材，而不是 76 个单元。 见第 2 章
  • 03数据比工具更值钱。 1119 条来源、523 条挂载，带证据状态与取用题解。 见第 3 章
  • 04可回查的是版本，不是正文。 能说清哪一版规则产出哪一版文件，但旧正文能否取回取决于是否另存。 见第 4 章
  • 05入口间行为不一致，是目前最实际的问题。 同一逻辑在 CLI 正常、在 DSH 插件返回错误。 见第 5 章

01

它解决什么问题

没有它时，同一套写作与设计判断要靠每次对话重新交代，参考散在各处，交付完也说不清依据哪一版。

这个方法库要应对的是一个具体矛盾：方法的正文很长，但一次任务只用得上其中很小一部分。把 76 个单元全塞进上下文，既贵又稀释注意力；完全不提供，Agent 每次都要重新发明一套写法。

它的答案是分层加渐进读取。层级不是按主题分类，而是按回答的问题分：

表 1 · 五层各回答什么问题

前四层是 Kit 的方法，第五层是素材。只有 Writing 与 Design 的入口常驻。

层回答的问题读取方式单元数
Task为谁完成什么、走哪条流水线、取哪些方法、怎样验收每次选一个任务类型，或现写 brief8
Writing主张、论证、组织、文体、语言约定怎样写入口常驻，正文按任务展开18
Design关系怎样可见、可操作、随时间呈现入口与判断契约常驻，正文按任务展开42
Publish内容怎样适配一种媒介并成为交付物选定流水线后读取，从不常驻8
Materials来源与资产是什么、依据在哪按条目逐级展开，最多五级1119 条来源

来源：dsh-praxis/layers.md；单元数由实际调用 praxis_units 得到（Task 8 / Writing 18 / Publish 8 / Design 42），与验收文档一致。

边界判断有一条好用的检验：换一种媒介，这条做法还成立吗？成立就归 Writing（例如「整体图景从问题讲起」），只在某媒介里成立就归 Publish（例如「一屏驻留几秒」）。

最容易误读的地方

四层不等于四个文档目录。它是知识的归属：内容组织归 Writing，媒介编排归 Publish，表现范式归 Design，制作与检查归 Publish。同一条规则放错层，下次换媒介时就会带入不适用的约束。

02

怎样工作：一次任务的实际展开

一次技术说明只被解析出 12 个单元和 4 条素材；每条都带选用理由，而不是把整个库交给模型。

入口是 praxis_resolve。它接受任务类型和流水线，返回该读哪些单元、每个为什么被选、以及挂在这些单元上的已启用素材。以下为本次实际调用 resolve 的真实结果：

① 选任务
技术说明：读者要能说出对象、核心关系、主要分支和改变判断的条件
② 定流水线
html：要出视频时另走 video，共用事实底稿
③ 展开方法
机制讲解、论证、构成关系、精确指向、导航、编排
④ 取素材
从目录级开始，需要时逐级展开到原件

表 2 · 一次技术说明实际解析出的 12 个单元

「理由」一列是工具自己给出的，不是本节补写。4 个常驻单元每次都在，其余由任务类型或流水线带入。

单元层次为什么被选
writing常驻Writing 入口与路由表

来源：实际调用 praxis_resolve，参数 task_type=task/types/technical-explainer, pipeline=html。「理由」原文取自返回的 reasons 字段。

配套的 4 条素材是：WAI-ARIA APG 的 Accordion 与 Dialog 模式、Purdue OWL 的 Toulmin 论证、Google 开发者文档风格指南。它们挂在被选中的单元上，且处于启用状态——停用的挂载不会出现在这里，这是「启用」这个控件的实际作用。

细节：76 个单元里，本次没被选中的 64 个是什么

Design 层 42 个单元里，本次只用了 5 个。剩下的大致分三类：

  • 另一类媒介或对象：运动判断、乐谱与时间、规则系统——视频或动态解释才需要。
  • 另一类组件问题：控件语义、范围选择、反馈、状态可达性——做交互界面时才进入。
  • 参考路由：C01–C25 的编排参考、U01–U09 的界面参考、视觉语言与外部设计系统——是查证入口，不是必读规则。

渐进读取的代价是漏选。如果任务实际需要一张复杂图表，而单元清单里没有图形编码，写出来就会缺依据。补救办法是在 resolve 时用 units 参数显式加单元，把它记成「本次指定」。

03

素材与挂载：数据比工具更值钱

来源身份只有一个，挂载可以有多条；每条挂载各带自己的题解、启用状态和 review。

这里有一个容易混淆的区分：来源（Source）是「这是一份什么材料」，挂载（Binding）是「这份材料在某个单元上怎么用」。同一个来源用在两个单元上，是两条挂载，各有各的取用说明。

表 3 · 两个对象的职责分工

分开的理由：同一份材料在「排版」下是结构参考，在「交互」下可能是反例。

对象回答存了什么
Source这是什么，取到了什么出处、概要、语言、读取范围、证据状态、摘录、快照
Binding在这次工作里怎么用description、取用题解、启用、收藏、优先级、tag、review

来源：dsh-praxis/objects.md「对象」与「素材的五级展开」两节。

素材按五级逐层展开，级别只表示展开深度，不表示重要程度：目录 → 来源条目 → 取用题解 → 摘录与定位 → 原件与附件。这个设计让 Agent 可以只看目录就判断「值不值得展开」。

条件不能这样读

启用、收藏、优先级、证据状态、采纳状态是五件独立的事，不互相推断。收藏不提高证据等级，preferred 不等于已采纳为规范。把「收藏了」当成「经过验证」，是这套数据最容易被误用的地方。

细节：现有数据的规模与字段现状

权威数据是 vault/provenance/**/catalog.json：49 个 catalog（27 个 maintained、22 个 generated），共 1119 条来源记录，字段名有一百多种。

挂载关系留在 catalog 的 grammar_paths 里，维护信息（description、题解、启用、收藏、review）存在 dsh-praxis/data/bindings.json，按 <来源 ID>@<页面路径> 对上。这样原有的 SaaS 图谱等脚本照常读 grammar_paths，不需要为控制面改动。

未核实：本轮没有打开 catalog 逐条统计，上述数字取自 objects.md 的记载；控制面实测显示 523 条挂载。

04

运行与产物：可回查的到底是什么

能说清「哪一版规则产出哪一版文件」，但旧正文能否取回，取决于有没有另存。

每次交付调用 praxis_consume，写下的是一条运行记录：用了哪些单元（带版本号）、哪些挂载（带 revision）、哪些来源（带快照 hash）、产出哪些文件（带 sha256）。之后如果某个单元改了，praxis_stale 就能反向找出「哪些交付可能要重看」。

表 4 · 一件产物的实际状态

取自本文档同仓库的既有产物，不是构造示例。三条记录都显示 basis_changed，说明产出它们的规则之后改过。

产物版本文件状态依据是否变了review
jev/site/index.htmlv4current是无
jev/site/src/page.htmlv3current是无
jev/draft/00-overview.mdv2current是无

来源：实际调用 CLI artifacts，核验日期 2026-10-25。hash 与版本号略去，完整记录可用 praxis_artifact 逐件查看。

这个机制的价值在于提问能落到具体版本上：「这条 review 是针对 v3 还是 v4？」「这份交付用的是改版前的成文原理吗？」hash 和版本号让它可以被回答。

这里最容易过度声称

hash 只能校验字节，不能取回正文。运行记录里存的是「当年用了 v1」，但 v1 的正文如果没有另外保存，就无法还原当时的内容。这是验收文档明确写下的边界，不要因为看到版本号就以为历史内容可回查。

细节：CLI 暴露的工具比 DSH 插件多

实测 CLI 的 help 列出 25 个命令，比 DSH 插件暴露的 21 个多出四个产物管理工具：

  • artifacts — 列出交付过的产物，带文件状态与依据变化信号
  • artifact — 读一件产物的每个版本、产出它的运行、派生关系与各版本 review
  • artifact_review — 对某一具体版本记录 review，新版本不继承旧结论
  • artifact_update — 改名、改说明、移除恢复，或文件挪位后重绑定

也就是说：产物管理目前只有 CLI 与 HTTP 入口能用。如果走 DSH 插件，Agent 能登记产物（consume）但看不到产物列表和版本详情。这是两个入口的覆盖差异，不是数据缺失。

未核实：本轮没有逐一确认 DSH 插件是否通过其他途径暴露这四个工具；结论仅基于当前会话可见的工具清单与 CLI 的 help 输出对比。

何时不适用：目前的边界与实测问题

两个只读汇总工具在 DSH 插件里返回错误；同一逻辑经 CLI 调用正常。这是返回值契约问题，不是数据问题。

本次测试中最实际的发现是：praxis_resolve 与 praxis_upkeep 经 DSH 插件调用时都报 value is not lossless JSON，但用 CLI 调同一组操作全部成功。对照实验如下：

所以「可回查」和「可维护」这两个能力本身是成立的，坏掉的是特定入口的返回值契约。对使用者的实际影响：走 DSH 插件时拿不到本次该读哪些单元，只能手动读单元。

其他已记录的边界

  • 预设为空。字段定义齐全，但当前 0 条预设。空表示尚未配置，不是功能错误；跑视频流水线前需要先建一条。
  • npm 包不单独携带 Kit。当前可用方式是完整仓库加 link/plugin，或 MCP/CLI。不能指望复制一个安装包就迁移全部积累。
  • 产物管理界面的文件预览不完整。已有概要、题解、摘录和文件定位，但 UI 里的原件只是路径文字，还没做到在控制面里直接预览与拖出。
  • 没有受众测试。方法库的取用证据来自单个开源项目的讲解页，事实只做了抽查，四问在另一类对象上是否成立尚未验证。

常见追问

它和普通的提示词模板有什么区别？
模板是固定文本，这是一套按任务解析的结构。同一条技术说明走 html 或 video，解析出的单元不同；素材是按挂载关系找出来的，不是写死在模板里。另外它带了维护与追溯：改过的规则有新版本，交付能反向找到用了哪一版。
76 个单元，Agent 每次要读完吗？
不用，也不应该。常驻的只有 4 个：Writing 与 Design 的入口，以及两条底线（证据与来源、设计判断契约）。实测一次技术说明解析出 12 个，其余按需展开。
为什么同一个工具在插件和 CLI 里结果不同？
它们共用同一个 core，差异在返回值如何序列化。core 返回的对象里含 undefined 字段，CLI 的 JSON 序列化会丢弃这类字段，DSH 的严格快照会拒绝。见第 5 章。
能不能用它管我的交付文件？
能登记，但要看入口。CLI/HTTP 有完整的产物管理（列出、读版本、按版本 review、重绑定路径）；DSH 插件目前只能登记（consume）。见第 4 章的细节。
空预设是不是坏了？
不是。字段定义齐全、接口正常，0 条表示还没配置。这是「尚未配置」，不是「功能失效」。
