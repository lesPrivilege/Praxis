# 按内容自身的关系重编排：施工说明

交给认领章节的编辑者。用户的要求：正文要按内容自身天然的结构编排，还原知识的直觉与可视化图景；完成度接近此前做过的知识讲解片，只是由静态或分步出现的 HTML/SVG 承载；不要宽泛的类 Markdown 结构化。

## 要找的段落

一段或几段正文，所讲的知识本身有一个形状，而现在只用句子平铺。常见的形状：

- 几个对象各自前进，同一时刻停在不同状态（并行的生命周期、时钟）
- 包含与范围（租户 ⊃ 法人 ⊃ 场所；权限的作用域）
- 版本、替换、冲销，以及“依据哪一版”
- 同一事物的几种标识与它们之间的映射；看似相同、实际不同
- 数量的拆分、占用、分配、剩余
- 时间轴上的区间、窗口、截止、迟到与补录
- 依赖、前提与结果；守卫条件挡在哪一步
- 责任在几方之间转移，谁接收、谁拒收
- 阈值、比较与取舍：两种做法在同一组条件下的差别

画出这个形状，用正文里的具体对象、数字和名称，不画抽象的方框清单。检验办法：把图中文字全换成占位符，图仍然显示出这一段特有的关系（分叉的泳道、嵌套、两个相同的号码对到两个不同的 ID）；若只剩一排并列的方框或卡片，就是不要的东西。列表改卡片网格、加图标、给条目编号上色，都不算。

不必每段都画。只选图能改变理解的地方，一章或一个案例通常两到五处；已有的 figure、Mermaid 图或静态图已经画出的关系，不再重画。论证、条件和例外仍然用正文。

## 改写正文

1. 正面陈述事物是什么、做什么、在什么条件下发生。删去“不能……”“不该……”“不必……”“未必……”“……还不够”“不等于……”这类不带事实的否定；只在它挡住一个读者很可能做的具体错误时保留一句，并在同一句里写出正确的做法。
2. 正文离开图也能读懂。Books 也会作为 Markdown 直接阅读：图给出图景，不承载正文里没有的新事实；图中出现的每个对象、数字、名称，都要能在正文里找到。为了画图需要的具体例子（例如“两张号码都是 0012 的发票”），先写进正文。
3. 保留每一项事实、数字、ID、链接、引文、`<!-- figure -->`、`<!-- svg -->` 指令和 Mermaid 代码块（缩进原样）。百科语体：不写“如图所示”“下面”“我们”，不加免责、来路说明或设防。术语前后一致；AI 与 agent 术语保持英文稳定形式。
4. 每节首段先给这一节支持的判断（第四轮已补写，改写时保持）。

## 样板

`projects/books/saas-engineering/enterprise-mechanisms/01-organization-to-system.md` 的“对象按生命周期划分”一节和它的五张图：`src/drawings/em01-lifecycles.html`、`em01-object.html`、`em01-ids.html`、`em01-relations.html`、`em01-allocation.html`。原来的三段是一组“能各自变化……不能共用一个状态字段”“对象至少要有……不能因为名称相似就自动合并”“只写……还不足以结算”；现在每段先正面说出关系，再接一张画出这层关系的图。改动前的文本见 `git show HEAD:projects/books/saas-engineering/enterprise-mechanisms/01-organization-to-system.md`。

画法、类名、尺寸与分步出现见 [静态图施工说明](drawing-brief.md)，必读。图的文件名用所改文件的前缀：`em02-…`、`f05-…`、`v04-…`、`h01-…`、`x02-…`。

- 不提交，不推送，不安装依赖。

## 自查

1. `SITE_OUT=<你的临时目录> node projects/saas-engineering-textbook/build/build.mjs` 通过（不要写进共享的 `site/`）。
2. 用无头 Chrome 截图看每张新图：文字不重叠、线不穿字、字号可读；正文数字与图中数字逐一比对。分步出现的图，在截图前把 `.drawing` 加上 `play` 类，或直接看 SVG 源确认每步内容。
