# 消息行程 · 设计卡

目标：观众能沿同一个 R1 指出“增量更新了哪个内容块、调用和结果怎样配对、结果怎样参与下一次推理”，并指出跳过、暂停和失败回灌的位置。覆盖 message / events / react；192 秒，无声音。

## 对象与空间

主角是持续存在的 Msg R1。B1 的两段文字从事件来源移入消息，随后一直保留；不再给飞行文字另造一个已落地副本。T1 调用留在消息内，连线伸到实际工具；T1 结果自身沿返回路径收入消息，用同一条垂直配对线连接调用。Msg 在局部展开时向左移，右侧空出运行环路；同一模型对象从最初输出端移动到下一次输入端。

模型输出、消息记录、工具执行是空间中的三种角色，不做三块等大的讲义。Msg 边框表达实际包含；分隔线区分有序块。标签附着对象，不另列重复解释。蓝色只强调当前被更新的对象与正在建立的关系。默认预算是下方的计数上限，不画 50 个格子，也不把它等同模型请求数。

## 三个关键帧

1. **变化前 / 8 秒**：空白 Msg R1 与 B1 槽，左边是模型输出端。观众先认消息身份与内容容器。
2. **变化中 / 43 秒**：两个相继到达的 delta 已成为 B1 两行内容，仍只有一份文字。标明 reply_id=R1、block_id=B1 的目的端。49–64 秒错 R9 的增量停在边界，R1 不改变。
3. **变化后 / 130 秒**：同一 R1 现在包含 B1、调用 T1、结果 T1；调用与结果靠纵向配对轨连接。整条记录经上方回路参与下一次模型输入，而非只把最终一句文本送回模型。

## 否决

- 两个 delta 变成两张消息，或落地后仍留一份飞行副本。
- 只靠相同 T1 文字说“匹配”，没有可追踪连接。
- ASK 到达前工具已开始，或主路径把 ASK / 失败画成必经。
- 返回路径把 error 改成 success；预算被表述成固定 50 次模型请求。
- 标题、旁文和三个等大面板比 R1 更像画面主角。
