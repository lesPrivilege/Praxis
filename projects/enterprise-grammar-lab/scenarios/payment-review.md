# 付款复核台场景契约

## 1. 工作与机会

场景 `payment-review`，revision `0.1`，Kit 基线 `main@d4fd387`。施工者是 Opus 5.5 主会话，接收者是用户，尚未接收。专业复核者空缺：没有合同、财务或法务人员看过对象模型和规则。场景取自用户给的研究 brief（身份见 [README](../README.md#材料来路)），对象和规则由施工者按 brief 的最小要求写出。

工作范围是一家合成企业的合同运营：面对一笔服务合同的付款申请，回答现有的合同、发票与验收材料是否足以交给人复核；不足的话缺什么、由谁补。使用者是复核员和复核负责人，观察员只读。

页面不发起付款，不修改合同，不给法律或财务意见，不对外发通知。全部公司、人员、文件、金额和规则都是为演练写的。没有现场流程、基线和观察窗口；机器提议是预先写在 fixture 里的，没有调用任何模型。

这个场景在实验里的用处，是检验第一轮做出来的通用工作面换一件工作之后还剩多少能用。发现见 [第二轮施工发现](../evals/round-2.md)。

## 2. 对象、证据与动作

一个使用者、一类输入件、一个动作、一个人工验收点：复核员拿到一个付款复核事项和它的材料包，看规则检查的结果，提交给负责人复核；负责人接受或退回。

### 对象

| 对象 | 身份与版本 | 权威位置 | 说明 |
|---|---|---|---|
| 复核事项 ReviewCase | `PR-` 编号，整数版本 | 后端 | 一笔付款申请：供应方、合同号、里程碑、申请期限、负责的复核员 |
| 材料 File | `F-` 编号，整数版本 | 后端 | 合同片段、付款条件表、补充协议、发票记录、验收记录。旧版本保留可读 |
| 依据引用 EvidenceRef | 材料编号、版本、位置 | 随检查结果给出 | 指到某份材料某一版里的一处；点开就是那一处 |
| 检查结果 CheckResult | 规则编号与版本 | 后端按材料的当前版本即时算出 | 通过、未通过、无法判断、依据冲突四种 |
| 机器提议 Proposal | `MP-` 编号 | 后端 | 预制的建议，记着它基于哪些材料的哪一版；不改变事项状态 |
| 人的记录 ReviewRecord | 尝试编号 | 后端 | 提交、退回、接受，各自成记录，互不覆盖 |
| 记录 AuditEvent | `EV-` 编号 | 后端 | 与事项工作台共用的结构 |

金额是币种加最小货币单位的整数。没有发票时金额是空，不是 0。不同币种的金额不比较、不换算。

业务状态有四个：待补件、可提交、待复核、材料已接受。前两个都在提交之前，由检查结果决定；后两个由人的记录决定。最后一个指复核材料被接受，不指已经付款，界面上处处写成“材料已接受，未付款”。

事项的版本号随人的动作加一。材料新增或出新版本也应当让它加一，这样“提交须针对读过的版本”才管得住材料的变化；现在没有登记材料的途径，这条只是写下来的不变量，没有代码执行它。请求的状态（读取中、失败、结果未知）是另一回事，不进业务状态。

### 三种陈述

页面上有三种来路不同的话，必须分得开：

| 来路 | 是什么 | 谁能改 |
|---|---|---|
| 规则检查 | 固定规则对材料当前版本的判定，带规则编号和版本 | 没有人能改结果；材料变了结果跟着变 |
| 机器提议 | 一段预制的建议，标明是机器生成、基于哪一版材料 | 不能改；提交时由复核员写明采纳、修正后采纳还是不采纳 |
| 人的判断 | 复核员的提交、负责人的接受或退回 | 只增不改 |

提交时的检查结论不由人选，也不算人的话：有检查未通过，就是“作为例外提交”，并且必须写说明；全部通过就是“三项检查全部通过”。它随提交一并记录，在记录里单列一行并标明是规则得出的。

对机器提议能作哪几种处置由后端给出。提议基于的材料已经不是当前版本，或它的建议与检查结果相反时，不能原样采纳。记录里写明处置的是哪一份提议。

### 角色

| 演示身份 | 角色 | 可以 |
|---|---|---|
| 沈若溪 | 复核员 | 阅读；提交复核 |
| 顾承安 | 复核负责人 | 阅读；接受复核材料；退回 |
| 唐一鸣 | 观察员 | 阅读非保密事项 |

身份是演示用的假身份，由请求头携带，没有认证。

### 动作

| 动作 | 前置 | 效果 |
|---|---|---|
| 提交复核 `submit-for-review` | 事项尚未提交；版本一致；没有检查处于无法判断或依据冲突；有检查未通过时必须写说明；写明对机器提议的处置；角色为复核员 | 进入待复核；记录结论、说明、对机器提议的处置和此刻各份材料的版本；写一条记录 |
| 接受复核材料 `accept-review` | 待复核；版本一致；提交之后材料没有增减、没有新版本；角色为负责人 | 进入“材料已接受”；写记录，注明付款由财务另行发起 |
| 退回 `return-review` | 待复核，或材料已接受但之后材料有了变化；版本一致；写明理由；角色为负责人 | 回到提交之前；原提交留在历史里 |

### 规则

检查规则，只供演练：

| 规则 | 版本 | 内容 |
|---|---|---|
| CUR-1 | 1 | 发票币种与付款条件表约定的结算币种一致 |
| ACC-1 | 1 | 有本次里程碑的验收记录，并且已签署。手上的记录是别的里程碑的，算缺本次的记录，结果是无法判断 |
| CAP-1 | 1 | 发票金额不超过里程碑上限。付款条件表与补充协议对上限的写法不同时，结果是依据冲突，规则不替人挑一个；币种不同时结果是无法判断 |

动作规则：

| 规则 | 版本 | 内容 | 例外交给 |
|---|---|---|---|
| ROLE-1 | 1 | 提交由复核员作出；接受和退回由负责人作出 | 运营负责人 |
| SUB-1 | 1 | 有检查无法判断或依据冲突时不能提交 | 复核负责人 |
| SUB-2 | 1 | 有检查未通过时只能作为例外提交，并写明说明 | 无例外 |
| SUB-3 | 1 | 机器提议基于旧版本材料、或与检查结果不一致时，不能原样采纳，只能修正后采纳或不采纳 | 无例外 |
| VER-1 | 1 | 提交时的对象版本须是当前版本 | 无例外 |
| VER-2 | 1 | 提交之后材料有了新版本，不能接受 | 无例外，退回后重新提交 |
| ST-1 | 1 | 动作须与事项所处的阶段相符 | 无例外 |

## 3. 失败与恢复

| 情况 | 处理规则 |
|---|---|
| 缺材料 | 检查结果是无法判断，写明缺哪份材料、由谁补；事项停在待补件，提交不可用 |
| 证据冲突 | 冲突的两个写法和各自的出处并列；检查结果是依据冲突，提交不可用，等合同管理员确认 |
| 没有金额 | 显示“未知，尚无发票”；不参与任何金额范围的筛选 |
| 按金额筛选没有指定币种 | 后端拒绝，不猜币种 |
| 材料版本改变 | 提交记着当时各份材料的版本。之后有新版本的，事项标为“材料已更新”，不能接受，只能退回后按新版本重新提交；机器提议标为基于旧版本 |
| 依据引用的版本或位置不存在 | 没有保留的版本返回未找到；位置在这一版里不存在时，照常显示这一版并提示定位失效，不拿相近的段落顶替 |
| 对象被他人更新、提交后结果未知、重复提交、取消与离开 | 与事项工作台相同，由共用的动作面板处理 |
| 局部读取失败 | 检查、机器提议、记录各自读取，各自失败 |
| 权限不足 | 无权的动作不可用并写出规则；保密事项对名单外的人拒绝，它的材料同样拒绝 |
| 人工退回 | 原提交、退回理由和退回人都留在历史里 |

## 4. 验证与结果

fixture 在 [fixtures](../fixtures/README.md)，12 个事项各承载一种情形。验证分三层，结果记在 [README](../README.md)：契约（每个响应按 OpenAPI 校验）、后端行为（19 项测试）、界面（浏览器里手走）；金额的录入与显示另有 5 项测试。

接受率、修正率、复核时间和净减负都没有样本，保持未知。

## 5. 接收与后续责任

交付物是可运行的工作台、契约、fixture、测试和施工发现。只用于检验企业工作面语法能否施工，不用于任何真实付款。

没有做的：登记或上传材料、给事项指定复核员、催补材料、发起付款、真实的规则引擎、换算。这里的组件和事项工作台共用的那些，按 [晋升规则](../../../docs/decisions/002-promotion.md)现在是“两个独立场景都用到”的候选，不是已晋升的 Kit 组件。
