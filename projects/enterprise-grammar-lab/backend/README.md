# 假后端

一个本地进程，按 [契约](../contracts/README.md)为两个场景提供 HTTP 接口，只用 Node 标准库，只绑定 `127.0.0.1`。状态在内存里，重启即恢复到 fixture。

```sh
npm run backend        # http://127.0.0.1:8787/api/matter 与 /api/payment
npm test               # 后端 40 项，逐个响应按契约校验；另有前端金额函数 5 项
```

| 位置 | 职责 |
|---|---|
| `kernel.ts` | 场景之间不该各写一遍的部分：HTTP 进出、演示身份、动作尝试与幂等、延迟和 fixture 里写明的异常行为。场景以一个 `Scenario` 对象挂上来 |
| `fixture.ts` | 读 fixture、换算相对日期、把记录按动作允许的步骤走一遍、fixture 不自洽时拒绝启动 |
| `contract-check.ts` | 测试用：按场景的契约校验每个响应 |
| `server.ts` | 入口，把两个场景挂到一个端口上 |
| [matter](matter/README.md) | 事项工作台的状态、规则、动作和测试 |
| [payment](payment/README.md) | 付款复核台的状态、规则、动作和测试 |

它模拟的不只是数据：延迟、分页、角色差异、信息隔离、版本冲突、他人并发修改、响应丢失、批量作业逐项结果、局部接口失败和幂等重放都有，触发条件见 [fixture 对照表](../fixtures/README.md)。

环境变量：`PORT`（默认 8787）、`FAKE_LATENCY=0` 关掉延迟、`FAKE_CONCURRENT_MS` 改写“他人并发修改”的等待时间。`POST /__fake/reset` 把状态恢复到 fixture，只给测试用，不在契约里。

没有做的：持久化、认证、请求体按契约的自动校验（动作的入参是手写检查）、并发请求下的事务。它不是真实后端的原型，只是让前端面对一个行为像真实系统的对象。

## 它能说明什么，不能说明什么

能验证的是前端怎样表达这些情况：不同身份看到的可做动作、拒绝、内容受限、前置条件、版本冲突、幂等回执和记录时间线。

不能据此证明的：身份认证、服务端授权、信息隔离的真实强度、记录不可篡改、数据库原子性、跨系统只执行一次、数据留存和合规。请求头里的演示身份是浏览器自己报的，真实服务必须从可信会话取得身份。接真实后端时这些控制要在服务端重新实现并验证，不是换一个地址就算完成；替换是否成功，要看同一套契约案例在新后端上是否仍然通过，再另验认证、授权和并发。
