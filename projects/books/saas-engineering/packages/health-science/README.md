# P04 · 医疗、临床试验与实验室

医疗、临床试验与实验室都把一次工作交给多人完成，但三者交付的东西不同。诊疗服务产生病人的检查证据和随后的费用；临床试验产出能回答研究问题的数据；实验室给出可追溯的测量结果，以及针对指定批次的证明。三者共同的工程问题，是什么证据经过谁的判断，可以让哪个对象进入下一状态。回答的结构相同：数值先确定对象身份、方法、单位与版本，才成为证据；决定绑定这些输入版本和决定者的权限，它引发的后果另行确认；输入变化时，沿依赖关系找出受影响的决定，由有权人员修订或重审。三个案例分别落在诊疗与结算（V01）、临床试验（V02）和实验室（V03），迁移时专业权威不随机制一起迁移：临床同意的撤回规则、批次证书的取样范围都要另找依据。

## 共同模型：证据、决定与后果

证据、决定与后果是三个环节：证据要先有身份与版本，决定要由有权的人对指定版本作出，后果要在接收方单独确认。设一个工作台收到数值 `9.8`。单凭这串数字，工程师无法判断下一步。它可能属于另一位受试者，可能是 `mg/L` 而不是 `g/L`，可能由已失效的校准计算，也可能是后来被更正的报告旧版。先确定对象身份、测量方法、单位、发生时间和版本，数值才成为可解释的证据。证据再与目的、规则版本和有权判断的人相连，才支持一个决定；决定引发的后果，还要单独确认是否已经执行。

下表按五个共同环节对照三个案例，对象名称保留各领域原词。

| 环节 | V01 诊疗与结算 | V02 临床试验 | V03 实验室 |
|---|---|---|---|
| 承诺 | ServiceRequest 指定检查请求 | Protocol 指定研究过程 | 方法与取样计划指定测量任务 |
| 对象 | 就诊对象、标本、影像检查 | 研究内受试者与访视 | sample、aliquot 与 lot |
| 证据 | Observation 与 DiagnosticReport | eCRF 数据及 query 处理记录 | 原始仪器输出、校准、QC 与结果 |
| 决定与决定者 | 专业人员报告；支付方 adjudication | 参与者同意；研究者签署；数据负责人锁库 | 复核员确认结果；获授权者签发证书 |
| 后果的完成 | 结果被接收；费用被分配；款项被核销 | 被签署的数据版本进入指定锁库快照 | 指定证书已签发并可查撤销或替代关系 |

一个决定不能替另一个决定作证。报告完成了，费用未必获赔；同意参加研究，也不等于允许任意的未来用途；一份结果合格，不能代表整个 lot 均匀合格。迁移机制时要重新检查这些前提：临床同意关乎人的意愿和研究范围，撤回规则不能从采购审批照搬；批次证书关乎取样代表性，推断范围不能从单个病人的报告照搬。

## 版本绑定与后续变化

一个决定至少绑定 `对象身份 + 输入版本 + 规则版本 + 决定者权限 + 决定含义`。数据库可以在同一事务内检查这些前提，把决定和待发送事件保存下来；接收方只在确认自身事实后改变自己的对象。队列的“已送达”只表示消息交接，替代不了专业签署、资金到账或实物放行。

输入变化后，沿依赖关系找受影响的决定，比把所有状态重置更好解释。例如报告更正要找依赖旧报告版本的费用审核；eCRF 更改要找覆盖该数据版本的签名；校准失效要找使用它的 run、结果和证书。保留旧版，就能说明“当时为什么作出这个决定”，再由有权人员决定修订、重审、暂停或撤销。只追加历史，并不能保证记录不可篡改；实际系统还要设计访问控制、留存、备份恢复和审计独立性。

界面把这套模型变成可操作的工作：对象列表显示各自进度和数据新鲜度，详情列出决定所依赖的版本，按钮提出带权限的命令，冲突说明哪些前提变了，未知结果留出核对入口。缓存帮助查找；提交时仍应向权威记录核验前提。用户离开页面再回来，仍能找到同一次尝试；业务责任不能靠浏览器里的旋转图标保存。

## 进入陌生行业

进入陌生行业，先选一条带例外的工作链，问清对象怎样编号、谁拥有哪项事实、哪些规则来自专业决定、外部系统如何承认结果。再识别现成方案能覆盖哪部分工作，查明所需版本、接口和限制，最后选一个能够观察不变量的最小验证切片。三篇文末的探索方向分别列出应询问的人、应取回的资料和应先验证的失败路径。
