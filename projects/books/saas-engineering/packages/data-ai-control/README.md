# P03 · 数据、文档、安全与 AI SaaS

企业保存数据，还要知道哪份数据可以拿来作决定。报表算出一个金额，口径未必已经获准；系统发现异常，停用账号仍要另行授权；文档获得批准，下游系统未必已经收到；请求生成了一段回答，能否向客户计费是另一回事。这些事实彼此相邻，却不能合并。能搭界面的读者要能辨认：一次点击究竟改了什么，凭什么改，失败后该找谁。四个案例共用一个模型：每项决定带着租户、对象、版本和决定人，执行另有许可和回执。H07 讲数据修订与 BI 发布，H08 讲安全信号与授权响应，H09 讲文档版本与下游记录，X01 把租户开通、计量、计费和退出连成一条链。结果未知时，恢复先查原尝试的证据，另发新请求可能把未知的一次变成确定的两次。

## 共同模型：身份、版本、许可与回执

身份和版本说明一项决定针对哪一件、哪一份，许可和回执说明能否执行、执行到了哪里；证据链和执行链靠这四者互相核对。

设想一个企业工作台。租户 A 的分析员根据订单数据制作月报，安全员调查异常访问，法务批准数据使用协议，客户管理员决定谁能使用 AI 服务。四个人面对同一组织，各自有不同的权威。把四个人的工作连起来的最小单位，是“一项带身份的决定”：针对哪个租户的哪个对象、哪个版本，由谁依据什么规则作出，何时生效，接收方确认到哪一步。

对象身份回答“这是哪一件”，版本回答“当时看的是哪一份”。`tenant=A, object=contract-7, version=3` 与版本 4 是同一合同的两份内容；对版本 3 的批准不能在没有规则的情况下覆盖版本 4。把版本换成报表输入快照、响应目标状态或计量价格版本，同样的问题仍然成立。页面可以只显示易读名称，服务端和持久记录仍要保存完整身份。

许可回答“现在可否执行”，回执回答“到底执行到哪里”。权限检查发生在执行边界；一条历史批准有时是权限判断的输入，却不是永不过期的通行证。发送请求后可能出现成功、明确拒绝、结果未知三类情况。结果未知时，恢复的第一件事是查找原尝试的证据；另发一个新请求，可能把未知的一次变成确定的两次。

身份、版本、许可和回执连成两条互相核对的链。证据链保存来源、版本、规则和决定，让人可以解释结果；执行链保存命令、尝试、外部回执和投影，让人可以恢复工作。两条链都需要租户身份。业务服务对自己的对象负责，外部 provider 对它接收的对象负责，列表中的绿色状态只是某一时刻的投影。复制一份数据不会自动转移权威。

## 相似机制的边界

数据 lineage 是来源与计算依赖；审批图是决定的先决条件；身份授权图是可访问关系。三者都可以沿图遍历，但路径的含义不同。“上游 A 改了，所以 B 需要重算”不能推出“批准 A 的人有权批准 B”，也不能推出“能读 A 的人能读 B”。遍历算法可以复用，边的语义和权限要在新图上重新定义。

同样，撤回一份报表可以切回旧发布指针；撤销一份批准可能要求重新审查；解除隔离需要确认目标已安全；租户退出则可能需要先停止新请求，再结算在途用量并处理保留规则。它们都叫恢复，却不都是回滚。已经发到外部的内容、已经消耗的计算和已经作出的人工决定，不会因本地数据库回退而消失。

AI 在这套模型中可以建议映射、整理告警、抽取条款或回答问题。模型输出是需要验证的输入；工具执行能力仍受身份、租户、对象版本和动作许可约束。确定性规则检验权限和金额，AI eval 检验答案是否有依据、该拒答时是否拒答。二者各有失败标准，不能把“模型答得像”当作“业务做对了”。

## 解题五步

每例按“识题 → 解法 → 演算 → 验算 → 变式”展开，五步的含义见[把业务问题算清楚](../../foundations/README.md)。先用开头的识题线索判断眼前是版本、时间窗、依赖、授权、隔离还是计量问题；再选一个适用方法，跟着小输入手算；随后用重复、迟到、冲突或撤销检验答案；最后改变条件，判断方法哪些部分还能保留。方法名字可以以后查，决定方法适用的前提必须说得清。

例如“同一编号出现两次”可能是重投，也可能是两个租户的合法对象。先辨身份，才知道应该去重还是分开计数。每例文末的探索方向列出下一步要查的实际接口、政策或证据，供把各例搬到陌生业务里继续验证。
