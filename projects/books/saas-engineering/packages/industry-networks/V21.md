# V21 · 约束计划、交付证据与运费支付

供应网络把企业的交付承诺分给供应商、仓库和承运商。计划员判断按现有约束能怎样交付，采购批准人决定企业是否承担这项采购义务，收货人确认实际收到多少，财务认定哪些运输服务已有付款依据。四个判断互相依赖，各由其权威签字：最优计划可能还在等批准，已签约的车可能尚未到场，签收记录可能只支持发票上的一部分附加费。不可拆的订单装车是组合问题，总容量够仍可能装不下，只能在可行解中比较代价；计划获批只锁定有条件的未来供给份额，实收之后仓库才做物理预留；运费逐行对上运输、费率和有效交付证据才能付款。改变判断的是计划输入是否仍然有效：供给减少后，装车模型即使算出同样的结果，原计划也已不可执行，要重新选择。

本例延续包内的“承诺—资源—执行证据—结算”模型，构造一家分销商的两日运输任务。SAP IBP 的公开介绍把需求、供应、库存与 S&OP 放在共同计划范围，并说明 response and supply planning 考虑容量、提前期和库存；本例借它划定计划问题的范围。[SAP IBP，What is SAP IBP / Which modules are part of SAP IBP](https://www.sap.com/products/scm/integrated-business-planning.html)。

## 识题：不可拆分配与执行承诺

供应问题先分清卡在装车组合、未来供给与实物的差别，还是收费依据上。

| 识题线索 | 首选解法 | 后续查证 |
|---|---|---|
| 总容量够，仍有一单装不上车 | 写出不可拆与每天容量约束，再比较可行解的成本 | 计划器的约束、求解状态、时限及可行性检查 |
| 计划已获批，货还没有入仓 | 分开记录未来供给份额与实物预留 | 采购确认、分批收货、库存预留与发运接口 |
| 运输已交付，发票仍有无付款依据的收费行 | 逐行匹配费率、运输和有效履约证据 | 运费附加费授权、签收更正与付款回查 |

## 解法：计划、承诺与实物的分账

计划、供给承诺、物理预留、运输、交付证据和付款各记一本账；获批计划锁定的是有条件的未来供给份额，实收之后才有物理预留。

计划输入必须先固定版本。需求 A、B、C 共 16 托盘；仓库已有 4 托盘，计划拟向供应商采购 12 托盘，要求运输开始前到货，采购批准尚未完成。情景版本 P7 把这 12 托盘作为有条件供给，页面要写明这个条件，“可采购”不能显示成“已在库”。采购批准只让采购单可以发出；预计到货要等供应商确认，可用库存要等仓库点收才增加。P7 获批时锁定这份有条件供给的分配份额，避免另一个计划重复承诺同一份未来供给；这份锁定与实物库存预留分开记录。SC1 实收后，仓库才按当前库存版本预留 16 托盘，供两趟运输使用：S1 运 B+C 共 10 托盘，S2 运 A 的 6 托盘。本例要求出车时已有对应的物理预留；真实业务若允许在途转运，要另加交接与货权规则，这道检查仍然保留。

| 对象与身份 | 权威与状态流转 | 转换所需证据 |
|---|---|---|
| Plan P7，含输入快照与规则版本 | 计划服务；draft → feasible → approved → superseded | feasible 要通过容量、时间与物料约束；approved 还要有批准人和所批准的版本 |
| Supply commitment SC1 | 采购服务记录本地义务，供应商回执证明其接受；proposed → approved → acknowledged → received，另有 rejected | 采购批准是本地义务，供应商回执才是承诺；received 需要实际接收的数量，部分收货保留余额 |
| Physical reservation IR1 | 仓储服务；waiting → reserved → consumed / released | waiting 可关联未来供给，但只有实收后的可用量能转成 reserved；按运输分批消耗 |
| Shipment S1 / S2 | 运输服务；planned → tendered → accepted → dispatched → delivered，另有 exception / cancelled | accepted 是承运商接单；delivered 要核对收货方、货物身份与数量 |
| Delivery evidence E1 / E2 | 证据服务保留来源与修订；reported → verified / disputed → corrected | 承运商报告可作为线索，争议签收不直接作为结算依据 |
| Freight invoice FI1 与付款尝试 PAY1 | 应付服务核对应付，支付系统确认结算；received → matched / disputed → approved → payment_pending → paid | 每个收费行都要对上运输、费率与履约证据；付款超时时，付款尝试记为 unknown，发票不改成 paid |

计划员修改候选分配，供方是否接受以供应商回执为准；采购批准人在限额内批准供给，收到多少由仓库与收货方报告，运输费率不归他们改；财务批准匹配的收费行，不利的交付证据也照样保留。跨组织共享同样按关系授权：承运商只能读自己的 shipment；收货方只能提交指向获授权订单的接收记录，归属按授权关系判定，消息里带的 tenant ID 不作依据。

数量守恒比单一的“完成”标签更能暴露欠交。每条订单在同一计量单位下满足“已交付 + 在途 + 未发 + 已取消 = 已订购”，每个托盘只计入一辆车。计划层预测的 16 托盘与仓库实有的 16 托盘要分别核对：预测表即使加总无误，也补不出仓库里缺的货。

## 演算：可行方案与代价比较

不可拆订单的装车要在全部可行组合里比较代价，逐单排优先级可能错过更好的组合；供给一变，求出的方案就不再代表可执行的计划。

三个订单不可拆分，A 占 6 托盘，B、C 各占 5 托盘。D1、D2 每天各有一辆容量 10 托盘的车，每辆费用 100 记账单位；所有订单都希望 D1 到达，本例把 D2 到达视为迟一天。迟交的内部评估成本按托盘每天计算：A 为 9，B、C 为 7。它是计划目标中的权重，既不是客户赔偿条款，也不是可直接扣减的运费。

设 `x(i,d)` 表示订单 i 是否安排到 d 日，每个值只能为 0 或 1。每个订单必须满足 `x(i,1)+x(i,2)=1`；每天满足 `6x(A,d)+5x(B,d)+5x(C,d)≤10`。目标为两辆车的 200，加上 D2 订单的迟交成本。这个小模型只考虑两日各运输一次、全部订单在 D2 前完成，不含真实道路、装卸时长、多站顺序、温区和司机工时。

逐项列举三个订单的 8 种日期组合，只有两种可行。其余六种都有一天超过 10 托盘：三单同日为 16，A 与 B 或 C 同日为 11。A 在 D1、B+C 在 D2，负载为 6、10，成本为 `200+5×7+5×7=270`。B+C 在 D1、A 在 D2，负载为 10、6，成本为 `200+6×9=254`。在这个完整枚举的小问题中，后一方案最优。若按每托盘迟交成本从高到低先排 A，看似保住了最重要的订单，另两单却合计产生 70 的迟交成本；改按销售额从大到小排，同样解决不了这个容量组合问题。

<!-- svg: v21-enumeration -->

这属于 `ALG:optimization` 与 `ALG:scheduling`：依赖限定供货未到时哪趟运输不能开始，容量限定哪些订单能同车，目标在可行解中挑出一个。对 n 单、D 个可选日期直接枚举，有 D 的 n 次方种分配。稍大的问题可以把整数模型交给 OR-Tools CP-SAT，保存求解输入、时限、可行性检查和求解状态；限时内只得到可行解时显示“当前可行方案”，没有证明最优就不写“最低成本”。先按截止日排序再装车是一种容易解释的启发式，但上面的反例说明，逐单排优先级会错过更好的组合。

物料约束和运输约束必须一起检查。若批准人把供货从 12 改为 8，预计总供给就只有 12，装车模型即使仍算出 254，也已不代表可执行的全链计划。这时应标明 P7 的输入已失效，在延期、补充供给和客户同意取消的订单之间重新选择；没有货，就不能照旧发出全部运输任务。计划审批核对供给份额与版本，防止超额承诺未来供给；实际收货后的物理预留事务另查当前库存与剩余量，防止抢用已在库的货。

## 情景预览与运输确认

预览在本地即时计算，批准只保存可审计的承诺；外部回执到达后才更新 shipment，承运商确认丢失时按客户参考核对，不换 ID 再订车。

React 配合 TypeScript 可以实现需求表、容量条和方案比较：每次拖动订单立即计算本地预览，同时保留醒目的“未批准”标识。Vue 同样可用；选哪一个看团队维护成本和现有组件，业务是否正确与框架无关。键盘移动必须与拖动等价；容量超限时用文字写明“D1 超出 1 托盘”，不只靠变红。方案详情同时列出预计交付、采购条件和成本分解，欠交的订单单独列出，与目标总分并排。

点击“批准计划”时，UI 发送 tenant、plan ID、P7 版本、输入摘要与 operation ID。团队已用 Python 时，FastAPI 便于直接接入求解任务；若以 Java 业务系统为主，Spring Boot 可保留成熟的事务与权限边界，求解器独立运行。PostgreSQL 存储批准版本、供给份额、独立物理预留、运输身份和 outbox；审批成功的事务只保存可审计的承诺，不等承运商网络调用完成。worker 可以依据获批计划提前订车，外部 `accepted` 回执到达后才更新 shipment；正式发车仍要等实际收货和物理预留完成。服务器发送事件（Server-Sent Events，SSE）或轮询把状态投影回页面，页面先报“P7 已批准，待供货 12 托盘；S1 等待承运商”，不报“货已发出”。

拓扑中的 `commands` 是 UI 提出的动作，`requests` 是运输服务发给承运商的请求，`emits` / `delivers` 是回执的消息交接，只有 `owns` 表示对象事实的权威归属。实物的移动由交付证据记录，“消息成功写入队列”替代不了 `delivered` 的证据。承运商确认丢失时，按 `(tenant, carrier account, client shipment reference)` 核对已有订单；外部不提供可核对的幂等身份时，操作保持 unknown，交给调度员联系承运商，而不是换一个 ID 再订一辆。

## 交付证据与结算的分岔

交付证据保留事件时间、记录时间和更正链，收费行对上证据才付款；证据修订不会把已付的款项凭空退回。

GS1 EPCIS（Electronic Product Code Information Services，GS1 的事件共享标准）区分 eventTime 与 recordTime：前者是采集应用声称事件发生的时间，后者是 EPCIS repository 记录的时间。有了这两个时间，“D1 签收、D3 才收到消息”可以如实记录，交付日保持 D1。EPCIS 的 ErrorDeclaration 表示此前的断言有误，保留原记录，并允许链接更正事件。[EPCIS 标准 §7.4.1 / §7.4.1.2](https://ref.gs1.org/standards/epcis/2.0.1/)。标准规定的是事件语义；事实是否属实、本例的支付条件，由业务另行核实。

接收层要据此区分同一 eventID 下的两种记录。普通重复投递可以按发送方消息身份去重；EPCIS 错误声明则允许与原事件使用相同 eventID，而且除 errorDeclaration 与 recordTime 外，其余字段必须与原事件一致。接收服务必须逐字段验证这个条件，保存错误声明及更正引用；不能用 `UNIQUE(eventID)` 把它丢掉，也不能因 ID 相同就接受内容不同的伪声明。内部 inbox 可用发送方传输身份，或经契约明确的“eventID + 声明类型 + declarationTime + 内容摘要”区分记录；无 eventID 的来源要商定稳定的采集身份，相似内容的两次真实扫描不能一律合并。

正常路径是 P7 获批、SC1 接收 12 托盘，S1 运 B+C、S2 运 A，收货方分别确认 10、6 托盘。应付服务把 FI1 的两项基本运费与两趟运输及约定费率匹配，200 记账单位可以进入审批。如果 FI1 总额为 250，多出的 50 标为未经批准的附加费，转入争议；“整单已交付”说明运输完成，发票仍逐行核对。内部目标中的迟交成本 54 也不能自动从 200 中扣除，是否赔付或抵扣要查合同，并另建调整记录。

失败路径上，S1 报告收到 10 托盘，收货方只确认 9，delivery evidence 转为 disputed。仓库调查发现有一托盘未卸货，下一次补送记为新的实物事件；这不是原签收数据录错，因此不能伪造成 ErrorDeclaration。只有调查证实扫描把 9 录成 10，才记录错误声明与更正，重算受影响的交付余额。已经支付的款项保持已付；应付账另开争议/追偿对象，保存已支付的事实。付款请求已被外部接受但响应超时时，PAY1 保持 unknown，确认结算参考号后才把批准金额标记为 paid。

## 验算：约束、外部确认与收费依据

负载数值是待测目标；验收看计划、预留、运输证据和收费行能否互查，重复、乱序、竞争和结果未知都不产生第二份业务效果。

负载目标为 50 个租户，每租户每日 5,000 单，计划窗口 14 天；在线列表 100 并发时 p95 小于 500 ms，审批持久化 p95 小于 800 ms，单个隔离求解作业预算 30 秒。它们是待测目标。求解按租户设并发配额，防止一个大网络占满 worker；超时时保留已验证的可行解，或明确显示“尚无可行解”，CPU 超时不等于业务不可行。按 tenant、plan revision、input hash 缓存结果；库存或供给修订会产生新的输入身份，旧预览可以查看，但不能直接批准。单条 shipment 的回执与更正按版本处理，异步投影落后时显示最后核对时间。

| 验收情境 | 预期结果与证据 |
|---|---|
| 正常提交、供货与两趟交付确认 | P7、SC1、S1/S2、两份签收和 FI1 收费行可互查；固定演算给出 254，付款依据为 200 |
| 同一承运回执重复；随后同 eventID 的合法错误声明 | 原回执只产生一个业务效果；错误声明照样保存，交付余额重算，不当作重复丢弃 |
| D2 的 delivered 先到，D1 的 dispatched 后到 | 保留两种时间，重建证据次序，不按消息到达次序把已交付改回在途 |
| 独立竞争测试：可用 16 托盘，Q1、Q2 各申请预留 16 | 两项不能都提交；旧版本先报告版本冲突，重读后剩余 0 才判库存不足。正常 S1=10、S2=6 在串行处理或重读重试后都能成功，剩余 0；P7 条件批准不替代预留 |
| 两个租户都有 S1，承运商账号也不同 | 详情、附件下载与缓存只返回授权范围内的数据；跨租户的回执映射隔离列为待查项 |
| 承运商已接单，HTTP 响应丢失 | 操作 unknown，可按客户参考核对到已有承运订单，没有第二辆车 |
| 更新签收后 worker 崩溃，恢复重放 | 数量和收费匹配不重复；最后状态可由 outbox/inbox 与业务唯一键追溯 |
| 发票 250 中有 50 未批准附加费 | 200 与 50 分行展示、分行审核；总额低于某个阈值也不整单放行 |

核心计划和付款使用明确规则，不需要生成式 AI。若加入发票字段抽取，由模型生成候选收费行，引用原页坐标，并保留人工批准。可设置 20 份开发样本、60 份独立留出样本，其中 20 份附加费、20 份重复/近似重复、20 份币种或单位陷阱；报告错误金额字段数/全部金额字段数、未标记附加费份数/20，以及人工修正份数/60。阈值和验收集由业务方确认；衡量的是金额正确率，不是模型输出是否流畅。

## 变式：容量、行程与更正

容量、行程或签收一变，守住的仍是每单恰好分配一次、每个数字都有证据；失效的是原方案依赖的那项条件。

**练习一：每天容量从 10 降到 9，仍要求两天送完。** 还能排出可行方案吗？

简答：不能。A 不能与任一其他订单同车，B+C 也达到 10，因此每车最多装一单，两天两车覆盖不了三单。即使总容量 18 大于总需求 16，仍然不可行。保持的不变量是每单恰好分配一次、每车不超载；失效条件是不可拆订单的组合，而非容量总和。检查：枚举全部 8 种分配，可行解为零；UI 应给出增加班次或修改不可拆条件的入口。

**练习二：把运输模型迁到 V10 维护排班，两项任务占 5 小时、5 小时，班次 10 小时。** 只保留容量约束是否足够？

简答：不够。容量约束可以保留，但两项任务若必须由同一技师在相距两小时的地点完成，10 小时并不可行。必须增加行程、技能、许可及设备可用窗口；反例是只把工时相加。检查：在时间线上插入行程后，应能发现超出时间窗口，货物装箱的结果不能直接沿用。`TR:V21:V10:capacity-with-travel`。

**练习三：签收 10 改为 9 时，200 已付。** 付款和证据怎样处理？

简答：保持原付款与原证据历史，修正交付余额，并发起合同约定的争议流程；不回退成“从未支付”，也不自动发起负向付款。检查：原结算参考号仍可查到，待处理数量为 1，调整记录关联到更正原因。这个机制能迁到 V07 的发货收款链，前提是区分客户应收与承运商应付；二者的收款方、计价和抵扣权不能混用。`TR:V21:V07:evidence-before-settlement`。

## 进入供应网络的先查项

进入陌生的供应行业时，先拿一张真实业务表单的匿名结构，辨认它表达的是预测、采购义务、实物交接还是收费请求，再追问每个数字的单位、版本、允许修改的人和外部确认渠道。计划系统适合比较多情景的资源分配，企业资源计划（enterprise resource planning，ERP）与仓储系统负责采购和实物账，运输管理系统负责承运执行，应付系统负责收费核对；对象身份和交接条件稳定之后，把这些成熟方案组合起来才有意义。下一步查采购确认与部分收货文档、承运接口的客户参考与查询能力、签收更正规则及运费合同，再用“供给变少、重复签收、附加费争议、订车结果未知”四组路径验收边界。
