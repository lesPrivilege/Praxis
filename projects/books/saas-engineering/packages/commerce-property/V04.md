# V04 · 产品目录、拆分履约与退货后的净结算

商店向顾客承诺的是具体的商品、数量、价格和交付方式；收到货款，只说明其中一项义务有了进展。本例接续 H01 的“承诺—履约—收款”模型，把一份承诺拆成可以逐件核对的数量账，实物和资金各凭各的证据核对：订单行在接受时冻结目录版本和逐件实付，每份数量只有一个当前去向；整单优惠按原价逐件分摊并精确守恒，仓库分配另受库存和包裹成本约束；退回的实物由验收决定返库或隔离，退款以支付方确认的结果为准，净额靠交易和结算明细解释。改变判断的是外部结果有没有确认：交接回执丢失或退款结果为 unknown 时，凭原操作身份查询；查明之前占用保持，退款也只沿原请求核对。

一家家居商店的顾客购买茶杯 3 个，每个 4,000 分；杯盖 2 个，每个 1,000 分。商品总额 14,000 分，整单优惠 1,001 分，应付 12,999 分。只使用一种币种和整数最小货币单位；不含税、运费、换汇、换货、拒付和会计收入确认。本例的结案条件是：每一件订购数量都已交付、已取消，或有获批的异常处置；每笔已批准的退款都有可核对的结果；库存处置和支付对账都没有悬项。

## 识题：一单多去处

订单已经付款、部分商品还没交付时，先把承诺的数量逐份分到各自的去向，再分别处理退回的实物和退回的资金。

| 识题线索 | 首选解法与适用条件 | 验算与后续查证 |
|---|---|---|
| 一单多仓，先到一部分 | 订单行加履约分配；每份数量有稳定身份及唯一的当前去向 | 各份数量之和等于订购量；查仓库交接与取消以哪一方的确认为准 |
| 整单优惠，逐件退货 | 接受时冻结金额快照，用最大余数法分配整数尾差 | 调换退货顺序后总退款不变；查计价单位、unit 映射与赔偿规则 |
| 退款与收货脱节，净结算有差额 | 退货验收与支付交易分开记录，按交易身份把收款、退款和结算明细逐笔对上 | 退款不直接增加库存；收款减去退款和手续费，应能解释净额；查 returnProcess、OrderTransaction 与批次明细 |

## 解法：目录版本与订单快照

订单接受时把目录版本、单价和优惠分配复制成订单行快照，此后目录的修改只作用于新订单；订单、分配、发货、退货、退款和结算各由自己的负责方推进状态。

目录中的 variant 表示一个可销售的规格，例如“陶瓷茶杯／白色／300 mL”。库存单位（stock keeping unit，SKU）是业务识别码，订单行另用不可变的内部身份引用 variant；SKU 改名或被重新使用时，既有订单仍指向原来的规格。系统让目录管理员发布带版本的名称、规格、价格和可销售规则，客户提交时由服务端重新确认版本，再把接受的内容、单价、优惠分配和规则版本复制到订单行。以后目录改成 4,500 分，旧订单的退款计算仍取 4,000 分的购买快照。

顾客只能请求购买、取消未交接的部分或申请退货；客服可以批准符合政策的退货；钱是否已退到顾客账户，以支付方确认的结果为准，聊天记录不作凭据。库存服务掌握各仓的可用数量，仓库操作员确认拣货和实物交接，财务审核退款及结算差异。超过客服权限额度的退款转交复核；审核人在确认页上能看到原付款、已有退款、本次金额和剩余额度。租户、商店、仓库与支付账户的对应关系由服务端决定，服务端不信任浏览器提交的 `tenant_id`。

Shopify 的公开模型区分 `Order`、`FulfillmentOrder` 和 `Fulfillment`：履约单组织同一地点要履约的项目与数量，实际履约记录另含发货项目和追踪信息；一个订单还可能包含不同的交付方式。真实产品同样把承诺、安排和发货证据分开记录。参见 [Apps in order management，API objects and relationships](https://shopify.dev/docs/apps/build/orders-fulfillment/order-management-apps#api-objects-and-relationships)。

| 对象 | 负责方（权威）与身份 | 状态流转与证据 |
|---|---|---|
| 订单及行快照 | 订单服务；`order_id + line_id + accepted_version` | `draft → accepted → resolved`；接受时固定价格，关闭只汇总已解释的数量与例外，不改写历史 |
| 仓库分配 | 库存服务；订单行、仓库、allocation ID | `reserved → handed_over` 或 `released`；原子占量成功后才承诺仓库份额；实物交接后不能再退回未发货库存 |
| 发货批次 | 履约服务；shipment ID | `planned → packed → handed_over → delivered`；交接和交付分别以承运回执或人工留证确认；途中丢件转入 `exception` |
| 退货 | 退货服务；原发货行、return ID | `requested → authorized → received → inspected → disposed`，或 `rejected`；收到包裹后，验收决定返库、隔离或报损 |
| 退款尝试 | 资金服务保存请求；支付方确认处理结果 | `prepared → pending → succeeded/failed/unknown`；金额获批后，支付方确认才算成功；结果未知时回查原尝试 |
| 结算核对 | 本地对账服务；支付账户、结算批次、规则版本 | `open → reconciled` 或 `discrepancy`；以交易和结算明细为据，银行入账也按结算明细核对 |

这些状态各自推进，同一时刻停在不同的组合上：订单可以已付款、部分发货，同时有一笔缺货退款；也可以全部交付、退货已收件、退款还在核对。订单页要能同时呈现这样的组合。

## 数量去向账

本例对每条原始订单行维护互不相交的去向：`订购量 = 未分配量 + 已占未交接量 + 累计已交接量 + 交接前取消量`。拣货计入“已占未交接”。退货发生在交接之后，另记一支，累计交接量保持不变，退回的货经验收后才可能重新可售；另外核对 `已收退货量 ≤ 可追溯的已交付量`，以及 `重新可售量 ≤ 检验通过且尚未返库的退货量`。拒收、丢件和补寄各自记录原因，补寄另立一项义务；每个去向的数量都是非负数。

北仓有茶杯 2 个、杯盖 2 个，南仓有茶杯 1 个、杯盖 0 个。库存服务先校验商品是否可售、价格是否正确，再按库存行的版本号创建分配：北仓 4 件，南仓 1 件。对单仓单规格，`可用量 = 实存量 − 有效占用量`。占量与 allocation 写入同一个数据库事务；两个订单同时争最后一个杯子时，只允许一个条件更新成功。

北仓先发货后，订单汇总按数量显示“已交接 4／5，另 1 件已占待交接”。南仓迟迟未确认时，客服可以催办或请求取消这一份，但系统要先确认南仓还没有交接。正常路径里南仓随后也交接，累计交接量为 5。顾客后来退回的茶杯和杯盖记在退货支线上，累计交接量仍是 5：茶杯完好返库，杯盖有划痕进入隔离；已收退货 2 件不超过已交付的 5 件，重新可售的 1 件不超过检验通过的 1 件。

若实物已经出库而本地回执丢失，直接释放占用会让另一位顾客买到并不存在的库存：可用量变成 1，另一订单占用它，迟到的回执再记下已交接 1。先把这份分配转入待核对、占用保持，按交接身份向仓库查询，查明后再决定取消还是拦截。

## 按钮与提交边界

界面提交的是带操作身份、版本和证据引用的请求，结果以服务端记录和外部证据为准；结果未知时，页面只让人回查原请求。

商品页允许按规格选购，购物车只给预估；结账确认页显示服务端重新计算的价格和拆分交付方案。目录版本若有变化，界面保留选项并列出差额，要求顾客接受新报价，价格冲突按价格冲突提示。订单页并列展示付款、各仓份额、每批追踪和退货退款卡片。订单列表读的是查询投影，详情页标出最后一次核对的时间；用户离开再回来，仍能凭同一个操作身份找到这次提交的结果。

仓库操作员点击“确认交接”时，提交 `operation_id、allocation_id、expected_version、quantity、交接证据引用`。服务校验该仓的权限及未交接量，在事务中保存状态和待通知事件，然后返回“交接已记录”。异步 worker 再把这次交接通知其他系统；承运人是否送达，以发货批次的交付证据为准。客服点击“退款”时，先拿到退款金额的计算预览，提交的请求绑定这份预览的版本和原付款；等待页依次区分“请求已保存”“支付方处理中”“结果待核对”“已确认退款”。结果为 unknown 时，页面只提供“重新查询”，不提供“换一个请求再退”。

结构数据里的拓扑用几种边表示关系：人使用界面记为 `operates`，界面发出动作记为 `commands`，对事实负责的一方记为 `owns`，记录保存的位置记为 `stores`。本地操作送往仓储或支付系统记为 `requests`；`emits → delivers` 只表示通知的交接，商品实际移动仍以 shipment 和 return 的证据为准。对象状态投影到界面记为 `projects`，授权以权威记录为依据，投影只供呈现。支付 provider 节点是可替换的边界。

一个可以实现的起点是用 React 或 Vue 做订单工作台，服务端用 TypeScript/NestJS 或 Python/Django，PostgreSQL 保存订单行快照、库存、分配与资金操作。前端选 React 还是 Vue，取决于团队的维护成本。PostgreSQL 的事务与唯一约束适合数量和金额的竞争更新。队列起初可以用数据库 outbox 加 worker 实现，量大了再换托管消息队列；引入队列会多出交接点，业务唯一键仍要保留。Redis 可以缓存目录和订单列表；最终的可用量以 PostgreSQL 中的库存与分配为准。

## 演算：优惠分摊与仓库分配

优惠分配与仓库分配都叫“分配”，目标却不同。优惠必须精确守恒，用最大余数法按比例分摊；仓库安排受库存和运输成本约束，另行求可行解或较优解。

先给 5 件商品各编一个稳定的 unit ID。总优惠 1,001 分按原价权重分配，三个茶杯各得 `1001 × 4000 / 14000 = 286` 分；两只杯盖各应得 71.5 分。先取整数部分得到 `286,286,286,71,71`，合计 1,000 分；剩下的 1 分给余数最大的杯盖，余数相同时按固定的 unit ID 排序。因此最终优惠为 `286,286,286,72,71`，实付分别为 `3714,3714,3714,928,929`，合计 12,999 分。unit ID 只用来标明金额归哪一件，与实物序列号无关；同规格商品无法逐件辨认时，本例把退货记到编号最小、尚未退过的 unit ID 上，并在退款预览中写明这条规则。金额与余数用整数乘法和整除计算，避免二进制浮点误差。最大余数法全排序的代价是 O(n log n)，对普通订单的 n 件商品足够；大批量同价商品可以按区间保存分配，仍要稳定映射到可退单位。

顾客后来退回一个茶杯和第一只杯盖，按原快照退款 `3714 + 928 = 4642` 分。若每次都按当前目录价格计算，或把优惠重新分摊到剩余商品，分批退货的总额可能与一次全退不同。朴素地把两只杯盖都四舍五入成 72 分，优惠会变成 1,002 分；反过来都舍去，则只优惠 1,000 分。保存接受时的逐件分配，是为了让最后一件退货时总额仍能对齐。

仓库安排可以先逐个 SKU 扫描可用的仓库，生成满足数量的可行解；D 个 SKU、W 个候选仓库的简单扫描约 O(DW)。按本例的库存，这单只能由两仓拆分发货。若优化目标改成最少包裹或最低运费，逐件选“最便宜仓”可能得到更贵的方案：A 仓只有杯子，发一包成本 4；B 仓有杯子和杯盖，发一包成本 5。先把杯子给 A，再从 B 发杯盖，总成本 9；全部从 B 发只需 5。每开一个包裹都有固定成本，不同 SKU 选哪个仓因此互相牵连。小规模可以枚举仓库集合验证最优，较大规模可用有时间预算的整数规划或启发式；演示只能把启发式结果称作可行方案。价格是否算准、履约是否选优，要分开验收。

## 退货、退款与结算核对

退回的实物、退款和结算分别凭验收记录、支付交易和结算明细确认，每一项各有自己的证据；净待结算额与顾客净支付额是两个数。

正常路径中，两仓分别交接，承运证据确认交付；退货申请引用原发货行，仓库收件后检验。茶杯完好返库，杯盖有划痕进入隔离，可售库存分别增加 1 和 0。财务按批准金额发起 4,642 分的退款，确认成功后才计入已退款合计。未交接商品经核实取消后，依据原订单的取消记录发起退款。两种退款都受原付款和原单位实付的上限约束。Shopify 文档把 return 定义为买方退回商品的意图，并说明 `returnProcess` 可处理全部、部分或延后退款，以及是否重新入库的处置；这支持把退回的实物和退款分开跟踪。参见 [Build for return management，Step 1 与 Step 9](https://shopify.dev/docs/apps/build/orders-fulfillment/returns-apps/build-return-management#step-9-issue-a-refund-and-dispose-return-items)。

退款资金是否处理成功，看退款关联的 `OrderTransaction` 状态；Shopify 的 `Refund` 文档明确这样要求。参见 [Refund，说明与 transactions](https://shopify.dev/docs/api/admin-graphql/latest/objects/Refund)。本例的退款 worker 若在支付方受理后超时，把原尝试保留为 unknown，按支付账户和外部交易身份查询；核对为成功后追加成功的证据，不再创建第二笔退款。重复到达的通知只作用于同一笔退款；晚到的 pending 不能覆盖已核实的成功。Stripe 的文档说明事件可能重复、送达不保证顺序，并要求验证签名；本例的回调消费者按这几种情形处理。参见 [Stripe Webhooks，Event ordering 与 Handle duplicate events](https://docs.stripe.com/webhooks)。

本例再假设支付手续费固定为 260 分、不退还，收款和退款落在同一个结算批次。净待结算额为 `12999 − 4642 − 260 = 8097` 分。顾客净支付额是另一个数，8,357 分；两者都不是利润。若 provider 实际先结算收款、后扣退款，应分别显示两批及尚未结算的余额，不能强行要求某一笔银行入账恰好等于 8,097。核对时先按交易身份匹配，再核对金额、币种、批次和手续费；金额相同的两笔可能是不同的付款。

## 验算：规模目标与失败检查

规模目标尚未实测；验算的重点是在目标负载下找出还欠着顾客结果的操作，并让故意写错的实现在反例输入上失败。

负载目标为 100 家商店、每店 2 万个活跃 SKU、平台峰值每秒 100 张订单、每单最多 50 行；单个热门 SKU 可占写入的 30%。目录热缓存下读取 p95 目标 200 ms，本地订单接受及占量 p95 目标 500 ms，不含支付和物流的网络耗时。这些是待测的目标，尚未实测。缓存 key 包含 tenant、商品版本与币种；目录发布新版本后，新报价只用新版本，历史订单照常有效。热点库存按仓库和 SKU 串行化条件更新。定时扫描最早的 unknown 结果和未送达的 outbox 记录，比只看平均请求延迟更能发现还欠着顾客结果的操作。

验算沿 UI、命令记录、数量账、外部核对和投影逐段收集证据。[结构数据](../../../../../vault/distilled/saas-engineering-atlas/packages/commerce-property/V04.json)定义了七种必需路径及额外的反例：两人抢最后一件；重复的退款通知；迟到的待发状态；跨商店同号订单与缓存；退款受理后断网；占量提交后 worker 崩溃；部分发货取消；不合格退货被错误加回可售库存；分批退款总额溢出；结算扣费遗漏。尤其要留一个故意写错的实现：退款一成功就把库存加回去；用“已退款但货未寄回”的输入测试，它必须失败。本例没有模型参与定价、批准或状态确认，AI eval 不适用。

## 变式：条件改变后的判断

回执缺失或目录涨价时，判断仍回到两条不变量：每份数量只有一个当前去向，每件退款不超过它原来分到的实付。

**练习一：南仓实际已交接，但回执丢失，顾客要求取消最后一个茶杯。** 能否立即把剩余 1 件释放并退款？

简答：不能立即释放和退款。每一份数量只能有一个当前去处，本地缺回执也不能说明实物没动：先把这份分配转入待核对，按交接身份向仓库查询；确认未交接再取消并释放，已交接则转拦截或按退货政策处理。反例是先释放、后收到交接回执，两个订单共占一件并不存在的货。检查回执迟到后数量没有变成负数、货没有第二次售出，顾客页面仍显示取消待确认的原因。若仓库给不出交接身份或交接证据，自动恢复的前提就不成立，转由仓库主管核查。（`TR:V04:V05:irreversible-handoff`）

<!-- svg: v04-handoff -->

**练习二：两只杯盖先后分两次退货，目录已经涨价到 1,200 分。** 两次各退多少？

简答：按原 unit ID 分别退 928 分和 929 分，共 1,857 分。不变量是：这两件的累计退款不超过各自原来分到的实付，整单全退最多 12,999 分。反例是两次都退 929，多退 1 分。检查时调换退货顺序，累计仍为 1,857 分。若销售政策允许额外赔偿，另立 goodwill adjustment 并授权，赔偿与原商品的退款上限分开计算。

迁到 V06 的住宿房晚（`TR:V04:V06:partitioned-obligation`），“把总承诺拆成可核对的部分”仍然适用；不同在于房晚受日历约束：过去的一晚不能重新卖回库存，日期一变就要重新检查容量。迁到 V16 的退租和押金（`TR:V04:V16:return-and-money`），“实物验收与资金处置分开”仍然适用，但类比只到结构为止，电商的退款期限和可退价不能套用到押金扣款上。

## 进入零售履约的先查项

先用一张跨仓订单及其一次售后，把订单行、仓库分配、运单、退货收件和支付交易逐一对应，要求每个金额和数量都能找到原身份。成熟解法包括订单管理系统（order management system，OMS）的拆分履约、库存预留、逆向物流与支付对账；前提是能拿到足够细的行项目和交接证据。若仓库只有每天的汇总表，实时取消就不能沿用这里的自动核对路径。下一步研究应优先查实际连接器的可取消阶段、退货处置、refund transaction 状态与数据更新频率，再补税费、换货和拒付规则。验收从一件货“已出库但回执迟到”开始，订单的解释、库存数量和退款责任三者要互不矛盾；通过后再扩展到更多仓库。
