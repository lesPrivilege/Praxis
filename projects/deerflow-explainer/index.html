DeerFlow 怎样工作

DeerFlow 2.0 是一个开源的 agent harness。一个 lead agent 在“调用模型、执行工具”的循环里工作，harness 替它管理文件、执行环境、上下文、记忆、skill 和分工，任务因此可以持续几分钟到几小时。

  1. 一个后端进程网关既提供 REST 接口，也运行 agent；nginx 是唯一的对外入口。见12
  2. 一条中间件链模型和工具的每次调用都要穿过一条四十项左右的中间件链。环境准备、上下文保护、工具管控和失控防护都放在这条链上。见34
  3. 四类可替换的能力工具、MCP 服务器、skill 和 subagent 都由配置装入，主循环不用改。见56
  4. 固定的虚拟路径agent 只看到 /mnt/user-data 下的三个目录；背后的执行环境可以是本机、容器或 Kubernetes Pod。见7
  5. 四处状态thread 文件、checkpoint、数据库和长期记忆分开存放，生命周期各不相同。见8
  6. 多个入口，一条 run 路径网页、IM 渠道、定时任务和 GitHub webhook 在网关里发起的是同一种 run；终端界面和嵌入式客户端不经过网关，装配的是同一个 lead agent。见910
  7. 默认面向本机单人默认配置假定本地可信环境。隔离执行、限制出网、多副本和细粒度授权都要另行开启。见11

术语沿用英文原词：run 是从收到一条消息到给出回答的一次执行，thread 是一个会话及其状态，checkpoint 是 thread 状态的快照，artifact 是登记给用户的输出文件，skill 是按需读入的说明文件目录。

2.0 是重写，与 1.x 不共享代码。1.x 是 Deep Research 多 agent 框架，保留在 main-1.x 分支；在 2.0 里，深度研究是 23 个内置 skill 中的一个。

1

系统全景

浏览器只访问 nginx 的 2026 端口。nginx 把页面请求交给前端，把 /api 请求交给网关；agent 在网关进程里运行，没有独立的 LangGraph 服务。

两个配置文件的分工

config.yaml 是主配置：模型、工具、沙箱、记忆、摘要、数据库、subagent、IM 渠道等都在这里。模板的版本号已到 59，旧文件用 make config-upgrade 合并新字段。多数改动在下次读取时生效；少数在启动时冻结，例如 subagent 并发、批处理和扩展包列表。

extensions_config.json 只放 MCP 服务器和 skill 的启用状态。它可以经网关接口在运行时改写，所以会引入代码的扩展包列表不允许放在这里。

2

一条消息的行程

一条消息变成一次 run：网关建立 run 记录并装配 lead agent，lead agent 在模型和工具之间循环，过程以事件流返回，结束时写入 checkpoint、核对 artifact 并把对话交给记忆队列。

3

lead agent 与中间件

lead agent 是一个“调用模型、执行工具”的循环，每次 run 按请求现场装配。循环本身只做这两件事，行为由挂在六个位置上的中间件决定。

四种模式对应三个开关

输入框里的四种模式是前端的预设。后端只认三个布尔开关和一个推理强度，通过 API 调用时可以直接传这几个参数。

细节
模型与思考开关的选定

模型按三级取值：请求里指定的，自定义 agent 配置的，models 列表的第一项。指定的名字不存在时退回默认模型并记一条告警；选出的模型还要通过授权检查，被拒绝时换成第一个允许的模型。

思考开关同样三级：请求，自定义 agent 的默认值，全局默认（开）。取到的值再按模型能力校正，模型不支持思考就自动降为不思考，一般不会报错。

各家模型开关思考的写法不同。适配写在每个模型的配置里：要么声明一份“推理契约”（是否支持、用哪种方言、有哪些强度取值），要么提供开启和关闭时各自要合并的参数。代码里没有按厂商写死的分支。

系统提示词的组成

系统提示词是静态的，对所有用户和所有会话逐字节相同，目的是让模型服务端的前缀缓存能够命中。各段依次是：角色，自定义 agent 的人设（如果有），思考方式，澄清规则，skill 清单，记忆工具说明，延迟工具清单，subagent 说明（仅在开启时出现），工作目录，回答风格，引用规则，关键提醒。

会变的内容都不在这里：日期、记忆、上传清单和项目指令由中间件放进消息或每次请求的临时附加部分（见第 4 章的表）。

thread 状态的内容

thread 状态是随 checkpoint 保存的那部分数据。除了消息历史，还有：沙箱编号，thread 目录路径，标题，artifact 路径列表，待办清单，目标及其结果，本 thread 的上传文件，看过的图片（只存路径、类型、大小和哈希，不存图片内容），已取回定义的延迟工具，subagent 委派台账（最多 50 条），已加载的 skill 引用（最多 8 条），摘要文本，后台任务。

并发写入的合并规则按字段定义：artifact 去重并保持顺序，待办后写覆盖，委派台账里已到终态的记录不会被非终态覆盖。

计划模式与步数上限

计划模式只在请求打开时生效。模型多得到一个 write_todos 工具和一段使用说明，待办项有待办、进行中、已完成三种状态，保存在 thread 状态里，前端把它显示在输入框上方。

一次 run 里图能执行的步数有上限，默认 100，请求可以提高，服务端封顶 1000；网页前端每次请求都传 1000。

自定义 agent

自定义 agent 是一份命名的配置：人设文件 SOUL.md、描述、可用的 skill 和工具组白名单、可用的 subagent 白名单、默认模型和思考设置。run 请求带上它的名字，装配时就按这份配置收窄工具、skill 和可委派的类型。用户可以通过内置的 bootstrap skill 在对话里创建，agent 也可以用 update_agent 工具修改自己的配置；由 webhook 触发的 run 不提供这个工具。

上下文与失控防护

上下文的体积靠静态提示词、一次性注入、输出外置和摘要压缩来控制。失控由循环检测、委派限额、步数和 token 上限拦截。需要人回答时，run 直接结束，等用户的下一条消息。

系统提示词最前装配时渲染，内容固定否

记忆在首轮注入后冻结，所以对话中途新提炼出的记忆要到下一个对话才出现。

减小上下文的四种做法

工具输出外置。工具结果超过 12000 字符时，全文存进 thread 目录，上下文里只留一段摘要和读取它的方法。沙箱工具自己还有一道截断：bash 20000 字符，读文件 50000，列目录 20000。

摘要压缩。上下文达到阈值时，较早的消息交给模型压成摘要，近期消息原样保留（默认最近 20 条）。摘要不写回消息历史，而是存在独立字段里，每次请求时附上。一条模型消息和它的工具结果不会被拆开，最新的用户请求不会被压缩。压缩之前，将被压掉的消息先送进记忆队列。用户也可以用 /compact 手动触发。

按需加载。skill 只列名称和描述，MCP 工具可以只列名字，正文和定义用到时再取（见第 5 章）。

隔离上下文。subagent 在自己的上下文里完成中间过程，只把结果交回主对话（见第 6 章）。

摘要压缩在代码里的默认值是关闭、没有触发条件；配置模板把它打开，并设为 32000 token 触发。按模板生成配置的部署是开启的。

细节
guardrail 与授权

guardrail 在工具真正执行之前把调用交给一个外部策略判断，默认关闭。策略出错时默认按拒绝处理。内置的策略只有按工具名的允许和禁止名单，更细的规则需要自己接入。每次放行或拒绝都记入 run 事件。

细粒度授权（按角色决定能用哪些模型、工具和沙箱）复用同一个拦截点，排在 guardrail 之前，默认也是关闭的。

目标循环

用户可以用 /goal 给 thread 设一个完成条件。run 结束时条件还没达成，系统自动续跑，默认最多 8 次，连续 2 次没有进展就停下。

5

工具、MCP 与 skill

工具表在每次装配时由五个来源依次拼成。MCP 把外部服务器的工具并进这张表。skill 是另一层：它是目录里的说明文件，提示词只列名称和描述，正文在用到时才读入。

工具表的五个来源

  1. 配置声明的工具。config.yaml 的 tools 段逐条写明用哪个实现。配置模板里有沙箱的文件与命令工具、网页搜索（DuckDuckGo）、网页抓取（Jina）和图片搜索。换服务商只改这一条的实现路径。
  2. 内置工具。登记 artifact、向用户提问、审查 skill 包三个始终存在，其余按条件加入（见下表）。
  3. MCP 工具。来自部署级和用户个人配置的 MCP 服务器；两者同名时保留部署级的。
  4. ACP agent。配置了外部的 ACP 兼容 agent 时，多一个调用它的工具。
  5. 扩展包的工具。运营者安装的扩展包可以带模型工具，排在最后。

五个来源按这个顺序合并，重名时先到的保留。合并之后还要裁剪：自定义 agent 的工具组白名单，主机 bash 是否允许，模型是否支持视觉，以及授权策略。被裁掉的工具不会交给模型。

MCP：接入外部工具服务器

每个 MCP 服务器是 extensions_config.json 里的一条配置，写明传输方式（stdio、SSE 或 HTTP）、启动命令或地址、认证方式。工具名默认加上服务器名作前缀，避免冲突。一个服务器配置有误只影响它自己。

工具定义在第一次用到时加载并缓存。缓存按配置文件的指纹判断是否过期，所以通过网关接口增删服务器之后，各进程不必重启。stdio 服务器的会话放在池里，按“服务器 + 用户或 thread”隔离。

认证可以叠加四层，后面的覆盖前面的：静态请求头，OAuth（自动刷新令牌），按 DeerFlow 用户映射的凭据，单次请求带入的密钥。

skill：按需读入的说明文件

一个 skill 就是一个目录，里面必须有 SKILL.md：开头一段 YAML 写名称、描述和可选的声明，后面是 Markdown 正文。skill 有三个来源：随仓库发布的公共 skill，用户自己安装或创建的，以及托管集成带来的只读 skill（例如飞书）。启用状态记在 extensions_config.json，没有记录的视为启用。

细节
MCP 工具的延迟加载

默认情况下，所有 MCP 工具的完整定义都交给模型。服务器一多，定义本身就占去不少上下文。打开 tool_search 之后，提示词里只列工具名字，模型调用 tool_search 取回定义才能使用，每次最多取 5 个。服务器或工具可以配置路由关键词，命中时系统在模型调用前自动取回最相关的几个（默认 3 个）。这个开关默认关闭。

MCP 长任务

有些 MCP 工具只是提交一个耗时任务，结果要靠另一个工具反复查询。可以在服务器配置里把“提交、查询、取消”三个工具绑成一组：模型只看到提交，拿到一个本地任务编号后继续做别的；网关在 agent 循环之外每 5 秒轮询一次，完成后通知。模型可以列出和取消后台任务。这个功能默认关闭，开关在启动时读取。

通过接口注册 MCP 服务器的限制

stdio 服务器意味着在网关主机上启动一个进程。经 HTTP 接口注册时，命令只允许 npx 和 uvx（可用环境变量扩充），并拒绝能执行任意代码的参数。文档说明这是纵深防御，不构成信任边界：网关管理员权限事实上等同于主机上的代码执行权限。个人 MCP 配置指向非公网地址时需要管理员权限。

能力目录与扩展包的区别

能力目录是界面上的一组连接器卡片，共 15 张（飞书、钉钉、企业微信、腾讯文档、Notion、GitHub、Atlassian、HubSpot、数据库等）。添加一张卡片，结果就是写入一条普通的 MCP 配置；其中搜索、抓取和浏览器几张只给出配置指引。

扩展包是运营者安装进网关进程的 Python 包，列在 config.yaml 的 plugins 里，启动时加载。它可以提供中间件、任务生命周期钩子、后台服务、HTTP 路由，以及带页面和模型工具的完整插件。扩展代码以网关的权限运行，不在沙箱里；增删或开关都要重启网关。仓库附带六个示例，其中书签和多 agent 协作两个是带界面的完整插件。

skill 的安装、扫描与自我修改

skill 包是扩展名为 .skill 的 ZIP 文件，上传后解压到用户的 skill 目录。解压有上限（4096 个条目，总量 512 MiB），拒绝越界路径、符号链接和可执行二进制；之后先过一遍离线的确定性扫描，发现严重问题直接拦截，再过一遍模型扫描。

内置的 skill 评审工具只读地检查一个 skill 包，给出三档结论：阻断、需修改、可发布。它把被审对象当作不可信数据，不激活也不安装。

允许 agent 自己创建和修改 skill 的开关默认关闭。打开后，每次写入都要经过安全审查，审查模型不可用时全部拦截。

skill 密钥的传递

skill 可以声明自己需要哪些密钥。密钥只随单次请求传入，作为环境变量注入这次激活的 bash 进程，不进入提示词、工具参数、checkpoint 和日志；subagent 不继承。

6

subagent

lead agent 用 task 工具把边界清楚的子任务交出去。subagent 有自己的上下文，与父 thread 共用沙箱，不能再往下委派；并发、总数、时长和 token 都有上限。

一次委派的过程

  1. 委派。lead agent 给出任务说明、subagent 类型，以及可选的验收条件。上下文有两种给法：默认只给任务说明；也可以附上父对话当时的历史和摘要作为背景，之后父对话的变化不再同步过去。
  2. 执行。执行器取得一个运行槽位，启动 subagent。它的系统提示词末尾附有一份汇报约定。
  3. 进度。task 工具在后端每 5 秒查看一次结果，模型不参与轮询。开始、每条新消息和结束各发一个事件，前端据此更新子任务卡片。
  4. 汇报。按约定，subagent 声称做过的动作要引用对应的工具回执编号，交付物要带可核对的标识，例如路径、网址或编号。
  5. 验收。如果传了验收条件，由代码检查，不由模型判断。

“完成”只表示 subagent 执行结束。代码能核对的验收条件只有几种：文件存在、非空、是合法 JSON、确实被写过，以及一条测试命令通过。其他写法的条件一律标成“未验证”，不会默认算通过。

细节
批处理：大量互相独立的小任务

lead agent 可以显式调用 batch_task，一次提交一批条目，立即拿到批次编号。条目写入数据库，由网关里的批处理服务逐步领取，交给同一个执行器和同一批槽位。lead agent 用配套工具查看进度、取消批次、分段读取结果。界面上可以暂停、恢复、取消、重试单条，以及导出全部结果。

这个功能默认关闭，需要 SQLite 或 Postgres。默认每批最多 5000 条，同时在途 100 条，同时运行 3 条，每条最多尝试 3 次。排队超时本身不消耗尝试次数。批处理不会自动触发：模型不调用这个工具，系统不会把普通委派改成批处理。

失败、超时与共用沙箱

subagent 的模型调用如果最终失败，结果按失败返回。超时的结果单独标记。终态只写一次，后到的状态不会覆盖它。

并行的 subagent 与 lead agent 共用同一个 thread 沙箱和 thread 目录。沙箱按持有者计数，最后一个持有者释放时才真正归还。subagent 的追踪记录挂在父 thread 的会话之下。

沙箱与文件

agent 只认识几个固定的虚拟目录。命令在哪里执行由沙箱提供方决定：配置模板默认在网关本机执行并禁用 bash，需要隔离时换成容器或 Pod。沙箱按“用户 + thread”复用，空闲 10 分钟后回收。

四类沙箱提供方

沙箱的生命周期

上传与 artifact

上传。文件经网关写入 thread 的上传目录，默认限制是每次 10 个、单个 50 MiB、合计 100 MiB。沙箱与网关不共享存储时，文件再同步进沙箱。下一条消息之前，系统把这批文件的名称、大小、路径和文档大纲写给模型。

文档转换。把 PDF 和 Office 文件自动转成 Markdown 的功能默认关闭，原因是不想在网关主机上解析不受信任的文档。关闭时 thread 里只有原文件。

artifact。agent 把成品写到输出目录，再调用 present_files 登记，界面才会展示。run 结束时，系统比较输出目录前后的差别：这一轮新写或改过输出文件、却一个都没登记，run 按失败结束。

改动记录。每轮结束时生成一份工作区改动摘要，列出新增、修改、删除的文件和文本差异，最多 200 个文件。文件名像密钥或凭据的，只记哈希和大小，不记内容。

细节
限制沙箱出网

出网策略有三档，默认是不限制。

  • 不限制：容器按 Docker 的普通方式联网。
  • 完全隔离：每个沙箱一个内部网络，禁止一切出站。
  • 域名白名单：内部网络加一个代理容器，只放行发往指定域名的 HTTP 和 HTTPS 请求；解析到内网、回环或云元数据地址的目标一律拒绝。

白名单模式可以配合人工审批：被拒的域名在对话里弹出一张卡片，用户可以拒绝、临时允许 300 秒，或在这个沙箱里一直允许。批准后不会自动重放刚才失败的命令。无人值守的 run 和 subagent 一律自动拒绝。

后两档只支持本地 Docker，且要求 Docker Engine 28 以上；在不支持的环境里直接报错，不会悄悄降级成不限制。

Provisioner 的职责

Provisioner 是一个独立的小服务。网关向它发请求，它在集群的指定命名空间里创建沙箱 Pod 和对应的 Service，挂上 skill 目录（只读）和 thread 目录（读写），并负责查询状态和删除。创建请求是幂等的。这样网关自己不需要 Docker 套接字，也不需要直接持有集群的创建权限。

文件工具的保护措施

改写已有文件之前，模型必须读过这个文件的当前版本；写入之后，之前的“已读”标记作废。这是为了防止模型凭旧印象覆盖文件或重复追加。这项检查默认开启。

命令默认 600 秒超时。超时的命令不会自动重放，因为不知道它执行到了哪一步。模型的单次输出有长度上限时，写文件工具的说明里会附上估算的安全长度，提示它分段追加。

多个网关实例共用沙箱

网关有多个实例时，需要知道每个容器由谁负责回收。这份登记默认放在进程内存，只适合单实例；多实例要改用 Redis。登记只决定谁来回收，不限制谁能使用。登记写不进去时，网关不交付这个沙箱，直接报错。

状态与记忆

一次对话的状态存在四处：thread 文件在磁盘目录里，对话状态在 checkpoint 里，thread、run 和用户的记录在数据库里，长期记忆由后台模型从对话中提炼成每个用户的摘要和事实，在下一个对话开头注入。

长期记忆的形成

写入长期记忆的条件

每条候选事实由提炼模型打上三个标签：作用范围（用户、thread、项目）、时效（长期、临时）和性质（描述性、事务性）。只有“用户、长期、描述性”能写入。任务期限、项目约定和一次性授权因此不会进入长期记忆。

闸门判定示例（构造的例子，按提炼提示词的分类规则推演，不是运行结果）
对话中的语句范围 · 时效 · 性质结果
我做支付风控，平时写 Python用户 · 长期 · 描述性写入
以后别用表格回答我用户 · 长期 · 描述性（纠正类）写入，注入时优先
这个项目的接口字段一律用下划线命名项目 · 长期 · 描述性不写入
这份报告下午三点前要交thread · 临时 · 描述性不写入
这次可以直接删掉旧分支thread · 临时 · 事务性不写入

内容。摘要分两部分：用户背景（工作、个人、当前关注、思考风格）和历史（近几个月、更早、长期背景）。事实有七个类别：偏好、知识、背景、行为、认知、目标、纠正；每条带一个 0 到 1 的置信度，低于 0.7 的不保留。

容量。每个用户在每个 agent 下最多 100 条事实。超出时默认按置信度淘汰。90 天没有再被确认的事实进入复查，每轮最多清理 10 条，纠正类不清理。

注入。事实按置信度从高到低放入，到 2000 token 为止；纠正类另有 500 token 的保底额度，先于其他类别放入。读取记忆超过 5 秒就跳过这一次，不阻塞对话。

范围。记忆按用户隔离。摘要在这个用户的所有 agent 之间共享，事实按 agent 分开存放。没有项目级的记忆。

管理。用户可以在设置页查看全部记忆，增删改单条事实，清空，导出和导入。

细节
工具方式：让模型自己读写记忆

记忆有两种工作方式。默认的中间件方式是上面讲的被动流程。改成工具方式后，对话开头只注入摘要，不注入事实；模型用查找、读取、新增、修改、删除五个工具自己操作记忆。工具方式的写入不经过提炼闸门。

容量淘汰的混合策略

只按置信度淘汰时，置信度高但早已过时的事实会挤掉刚被用户纠正过的事实。仓库提供了一个需要手动开启的混合策略，分数由三项相加：置信度占 0.65，最近一次被用户确认的新近程度占 0.25，被检索命中的热度占 0.10；纠正类事实另留一成容量。

仓库自带的基准说明给出的数字是：容量为 7 时，45 个测试例中，混合策略全部保住了回答所需的事实，纯置信度保住 27 个；接上真实模型问答后，答对数是 40 对 24。这些数字出自仓库文档，没有复现。

checkpoint 的两种存储方式与保留策略

checkpoint 默认每一步存一份完整状态。另一种增量方式只存消息的变化，每 10 步存一次完整快照，体积更小，代价是增量 thread 不能直接分叉。两种方式在进程启动时选定，所有共用数据库的进程必须一致。

分支、重新生成和编辑重发都沿着 checkpoint 的父子链回溯，删掉中间的 checkpoint 会让这些功能报错。仓库里关于 checkpoint 保留策略的文档仍是草案，没有看到已经落地的自动清理。

项目：一组 thread 共用的指令和资料

项目把相关的 thread 归在一起，带一段项目指令（最多 8192 字节）和一个资料架。属于项目的 thread 每次 run 开始时，系统取一份最新的项目指令和资料索引（最多 50 条）临时附在请求上，不写进消息历史。agent 用两个工具列出和读取资料。资料按内容寻址，内容相同的文件只存一份；删除的资料进回收站，保留 30 天。

网页、IM、定时任务和 GitHub webhook 在网关里变成同一种 run，差别在于谁发起、能否向人提问、结果送到哪里。终端界面和嵌入式客户端不经过网关。

从 IM 消息到一次 run

  1. 平台适配器从长连接收到消息，放进网关内部的消息队列。
  2. 渠道管理器取出消息，先去重：同一条消息 10 分钟内只处理一次。
  3. 处理命令。/new 开新 thread，/model 换模型，/agent 换 agent，/goal 设目标，/skill-name 激活 skill，/connect 绑定码 绑定账号。
  4. 按“平台 + 会话（+ 话题）”查到对应的 thread，没有就新建。
  5. 像普通客户端一样通过 HTTP 调用网关的 run 接口，请求里带内部令牌和所有者的用户编号。
  6. 支持流式的平台，每隔至少 1 秒或每累积 60 个字符更新一次同一条消息或卡片；其他平台等 run 结束后一次发出。
  7. 结束时，把登记为 artifact 的文件从这个用户的输出目录取出，随最终消息发回平台。

渠道管理器默认 5 个并发工作单元。同一 thread 正在运行时，新消息得到一条“正忙”的回复。IM 入口的默认配置是开思考、不开 subagent。多副本部署时，同一个机器人只能由一个实例连接。

账号绑定默认关闭。启用后，用户在网页上生成一次性绑定码（600 秒内有效），到 IM 里发给机器人完成绑定；之后这个 IM 身份发起的 run 都算在该用户名下，没有绑定的身份发来的消息被拒绝。一个 IM 身份只能绑定一个账号，后绑定的覆盖先绑定的。

定时任务

一个任务包含提示词、计划（一次性、五段 cron 或固定间隔）、时区、使用哪个 agent，以及每次触发是开新 thread 还是沿用同一个。可以附带一个目标和停止条件、最多运行次数、截止时间。

调度服务每 5 秒轮询。到期的触发先写成一条持久化的排队记录，再在并发上限之内启动：全局同时 3 个，每个用户同时 2 个，排队超过 1 小时作废。run 结束后归为成功、目标未达成、失败或中断；目标连续 3 次未达成，任务自动暂停。固定间隔的任务不补跑错过的触发。

有两个开关，默认都关：一个开启调度功能本身，另一个允许 agent 在对话里自己创建定时任务。

登录、权限与数据隔离

登录。首次启动时没有管理员，第一个管理员在设置页创建。之后可以用邮箱加密码登录，也可以接 OIDC 单点登录。登录状态是一个有效期 7 天的令牌，放在脚本读不到的 cookie 里；改密码会让旧令牌全部失效。同一账号连续输错 5 次，锁定 300 秒。供脚本使用的个人访问令牌只能操作 thread、run 和项目，不能访问记忆、agent 和渠道配置。

隔离。文件、记忆和自定义 agent 都放在各自的用户目录下；数据库查询自动按当前用户过滤；访问别人的 thread 得到 404。客户端在请求里自报的用户编号会被去掉。

授权。细粒度授权默认关闭，这时所有登录用户拥有全部接口权限（用户管理等管理员专用接口除外）。开启后，按“角色 → 资源类型 → 允许或拒绝”的表判定，拒绝优先；资源类型包括工具、模型、skill、沙箱、MCP 服务器、接口和插件。判定在两处执行：装配时，不允许的工具不交给模型；运行时，工具调用再拦一次。

细节
run 接口的默认行为
  • 同一 thread 已有在途 run 时，新的 run 请求被拒绝。可按请求改为打断旧 run，或回滚到旧 run 开始之前。
  • 发起 run 的那条连接断开时，接口的默认行为是取消 run，可按请求改为继续。旁观的连接断开不影响 run。网页前端是否改写了这个默认值，没有核实。
  • 取消有两种：保留已有进度，或回滚到 run 之前。
  • 事件流每 15 秒发一次心跳。断线重连时凭最后收到的事件编号续传；缺口超出保留范围时，服务端发一个专门的事件，客户端改为重新加载已保存的状态。
GitHub 集成

每个自定义 agent 可以在自己的配置里绑定仓库和触发条件。GitHub 把事件投递到网关，签名校验通过后，每个匹配的 agent 各收到一条消息；同一个 PR 上的不同 agent 各用各的 thread。run 之前，网关签发一个约 1 小时有效的 GitHub App 安装令牌放进沙箱环境，agent 用 gh 命令自己决定是否评论或提交。

默认只在 PR 新建时触发，评论类事件要 @ 到机器人才触发。没有配置 webhook 密钥时，这条路由不存在。

终端界面与嵌入式客户端

终端界面是一个全屏的终端应用，也有不带界面的单次问答和逐行 JSON 输出模式，可以续接上一个会话。它把 thread 写进网关读取的同一个数据库，所以终端里的会话会出现在网页的侧栏里；数据库后端是内存时不写。

嵌入式客户端把 agent 当作普通的 Python 对象使用：一个方法返回完整回答，另一个方法逐个产出事件。它没有 run 管理和 StreamBridge；不传入 checkpoint 存储时，没有多轮记忆。IM 渠道不使用这个客户端，而是经 HTTP 回调网关。

多实例部署的前提

网关开多个进程或多个副本时，启动检查要求四项同时满足：数据库用 Postgres，run 事件入库，开启 run 租约心跳，StreamBridge 用 Redis。缺任何一项，启动失败。IM 渠道、微信扫码登录和浏览器工具仍然只能单实例运行。

流式显示

前端用 LangGraph 的官方 SDK 连接网关，只订阅三种流：消息增量、状态更新和自定义事件，不订阅每一步的全量状态。子任务的进度走自定义事件，subagent 内部的消息因此不会混进主对话。

收到的消息被归成七类：用户消息，思考与工具步骤，回答，文件呈现，子任务，提问，定时任务。一轮还在进行时，只有正文的模型消息暂时留在“思考与工具步骤”里，这一轮结束才变成回答气泡。

刷新页面后，前端查到 thread 还有在途的 run，就重新加入它的事件流。服务端报告事件有缺口时，前端重新加载已保存的状态再加入，最多重连 5 次。创建 run 的那个请求不做自动重试，以免同一条消息建出两次 run。

已保存的消息带有 thread 内的全局序号，显示顺序以它为准。重新生成针对最后一轮；编辑后重发也只限最近一轮，要改更早的轮次，需从那里分支出一个新 thread。

部署与默认值

三种部署方式的差别在配套服务：本地只有网关、前端和 nginx；Docker 加上 Redis；Helm 再加上 Postgres，并默认用 Provisioner 创建沙箱 Pod。默认配置按本机可信环境设计，对外提供服务之前有几处必须改。

默认开启与默认关闭的功能

默认开

  • 长期记忆被动提炼，对话首轮注入
  • 摘要压缩配置模板开启，32000 token 触发；代码默认关
  • 循环检测3 次警告，5 次强制停止
  • 先读后写改写已有文件前必须读过
  • 工具输出外置超过 12000 字符
  • 工具回执每个工具结果附哈希与时间
  • 标题生成、token 用量统计 
  • 跟进建议、输入润色建议最多 3 条
  • 开放注册可以关闭

默认关

  • 主机 bash本机沙箱下不提供 bash 工具
  • 沙箱出网限制默认不限制
  • 文档自动转 MarkdownPDF 与 Office 文件
  • 细粒度授权、guardrail、个人信息脱敏 
  • token 预算开启后默认每次 run 20 万
  • 定时任务功能本身与对话内创建任务各一个开关
  • subagent 批处理、MCP 长任务 
  • MCP 工具延迟加载默认把全部定义交给模型
  • skill 自我修改、IM 账号绑定、知识库 

对外提供服务前的必改项

  1. 更换本机沙箱。默认配置下，agent 的文件操作直接发生在网关主机上。换成容器或 Pod；同时要注意，容器方案要求网关持有 Docker 套接字。
  2. 给入口加 TLS 和访问控制。默认只监听本机回环地址；README 的安全说明写明，默认配置按本地可信环境设计。
  3. 固定几个密钥。登录令牌的签名密钥、内部调用令牌和凭据加密密钥不设置时会自动生成；多进程或重建容器时要显式固定，否则登录状态和已存的凭据会失效。
  4. 确认数据库后端。不能留在内存；多实例用 Postgres。
  5. 按主机权限管理管理员账号。管理员可以注册 stdio 类型的 MCP 服务器，等于能在网关主机上启动进程。
  6. 按需打开授权和出网限制。两者默认都关。

常见追问

十二个常见问题的简答与对应章节。

DeerFlow 和 LangGraph 是什么关系
lead agent 是用 LangChain 和 LangGraph 编译出来的一张图，checkpoint、流式事件和 thread 接口都沿用 LangGraph 的约定。但部署里没有独立的 LangGraph 服务，运行时嵌在网关进程里。第 1 章
Ultra 模式比 Pro 多了什么
多一个开关：模型得到 task 工具，可以委派 subagent。模型本身没有变，默认推理强度从 medium 升到 high。第 3 章
上一个对话里说过的偏好，新对话为什么没用上
记忆在对话结束后 30 秒到 5 分钟才提炼，而且只在新对话的第一轮注入一次。新对话开得太快，或者那句话被判成了项目约定或临时要求，就不会出现。第 8 章
agent 说生成了文件，界面上为什么没有
文件必须写在输出目录并用 present_files 登记才会显示。写了输出文件却没有登记的 run，会按失败结束。第 7 章
默认配置下 agent 能执行命令吗
不能。配置模板用本机沙箱，bash 默认禁用，只有文件读写工具。要执行命令，换成容器类沙箱，或显式允许主机 bash。第 7 章
对话很长时会怎样
按配置模板，上下文到 32000 token 时，较早的消息被压成摘要，最近的消息原样保留。过长的工具输出在此之前已经改存为文件。第 4 章
最多能同时跑几个 subagent
默认整个网关进程同时运行 3 个，所有用户共用；一次响应最多委派 3 个，一次 run 最多 6 个，超出的调用被去掉。这几个数都能调。第 6 章
换模型或换搜索服务商要改代码吗
不用。模型和工具都在 config.yaml 里用实现路径指定，换一家改一条配置。第 5 章
agent 陷入循环怎么办
相同的工具调用重复 3 次会收到警告，5 次被强制停止调用并要求直接作答；另有每次 run 100 步的上限。第 4 章
无人值守的 run 遇到需要确认的事怎么办
定时任务和 webhook 触发的 run 不提供提问工具。提示词要求它们按风险最低的假设继续并写明假设，风险高时停下并返回 BLOCKED。第 4 章
多用户之间隔离到什么程度
文件、记忆、thread 和自定义 agent 按用户隔离。但细粒度授权默认关闭；用本机沙箱时，所有用户的命令和文件操作都发生在同一台主机上。第 9 章
能水平扩展吗
网关可以多副本，前提是 Postgres、Redis StreamBridge、run 事件入库和 run 租约心跳四项齐备。IM 渠道和浏览器工具仍然只能单实例。第 9 章
